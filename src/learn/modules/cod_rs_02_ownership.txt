+++ question | A tank handed out and handed back
--- ask
What does this print? Type the output on one line.

```rust
struct Tank(&'static str);

impl Drop for Tank {
    fn drop(&mut self) {
        print!("drop:{} ", self.0);
    }
}

fn inspect(t: Tank) -> Tank {
    print!("inspect:{} ", t.0);
    t
}

fn vent(t: Tank) {
    print!("vent:{} ", t.0);
}

fn main() {
    let lox = Tank("lox");
    let rp1 = Tank("rp1");
    let lox = inspect(lox);
    vent(rp1);
    print!("end ");
}
```
--- answer
inspect:lox vent:rp1 drop:rp1 end drop:lox
--- why
`inspect` takes the tank by value, so `lox` moves in, and returning `t` moves it back out into a new `lox` binding. Nothing is dropped on that round trip: ownership only travelled. `vent` also takes its tank by value but never gives it back, so `rp1` is dropped when `vent` ends, before "end" prints. At the end of `main`, only the second `lox` still owns a tank, so it is the only drop left. The first `lox` binding and `rp1` were moved away, and a moved-from binding is never dropped. Two tanks, two drops.

+++ question | What survives a let

```rust
    lat: f64,

fn main() {
    let a = Fix { lat: 28.5, lon: -80.6 };
    let b = a;
    let c = (7u16, [0.5f64; 3]);
    let d = c;

    let f = e;
    let g = (String::from("GPS"), 4u8);
    let h = g;
    // the line goes here
}
```

Pick every line that compiles where the comment is.
--- choice correct
`println!("{:?}", a);`
--- choice correct
`println!("{:?}", c);`
--- choice
`println!("{:?}", e);`
--- choice
`println!("{}", g.1);`
--- why
`Fix` derives `Copy`, and both fields are `f64`, so `let b = a;` duplicates it and `a` stays usable. A tuple is Copy when every part is, and `u16` and `[f64; 3]` both are, so `c` survives too. `e` is a `Vec`: `let f = e;` moves the 24-byte header and ends `e` (E0382). `g` holds a `String`, so the tuple as a whole is not Copy, and `let h = g;` moves all of it, the `u8` included. +++ question | A loop that eats the list
--- ask
What happens with this program?

```rust
fn main() {
    let names = vec![String::from("IMU-A"), String::from("IMU-B")];
    let mut total = 0;
    for n in names {
        total += n.len();
    }
    println!("{} {}", total, names.len());
}
```
--- choice
It prints `10 2`.
--- choice
It prints `10 0`: the loop emptied the vector, and an empty vector has length 0.
--- choice correct
It does not compile: `for n in names` calls `into_iter`, which takes `names` by value, so `names.len()` uses a moved value (E0382). Loop over `&names` instead.
--- choice
It does not compile: `n` is a `String`, and `len` only works on a borrowed `&str`.
--- why
A `for` loop calls `into_iter` on whatever follows `in`. For a `Vec<String>` taken by value, that consumes the vector: each `String` moves out into `n` and is dropped at the end of its pass, and the buffer is freed when the loop ends. There is no empty vector left to measure; the binding is dead. `for n in &names` lends the vector instead, gives `n` the type `&String`, and leaves `names` usable, so the program prints `10 2`. `len` works on a `String` and a `&String` alike.

+++ question | Which types may be Copy
--- ask
Pick every type that `#[derive(Clone, Copy)]` is allowed on.
--- choice correct
`struct Imu { t: f64, gyro: [f64; 3] }`
--- choice correct
`struct Label { name: &'static str, id: u8 }`
--- choice
`struct Count { n: Box<u32> }`
--- choice
`struct Probe { t: f64 }`, which also has an `impl Drop for Probe`
--- choice correct
`enum Phase { Idle, Burn(u32) }`
--- choice correct
`struct Frame { data: [u8; 4096] }`
--- why
Copy is allowed when every part is Copy and the type has no `Drop`. `&'static str` is a shared reference, and shared references are Copy: a copy is a second pointer to the same text, and neither copy frees it. An enum is Copy when the data of every variant is. A `Box` owns heap memory, so two bitwise copies would free it twice: E0204. A type with `Drop` cannot be Copy either (E0184): which copy would run the cleanup? `Frame` is allowed, but Copy is not a speed setting: every pass by value copies 4096 bytes, so pass it as `&Frame`.

+++ question | A report that ends the burn
--- ask
This should print the report and then the delta-v, but it does not compile. What is wrong, and what is the best fix?

```rust
struct Burn {
    dv: f64,
    log: Vec<String>,
}

impl Burn {
    fn report(self) -> String {
        format!("{} m/s, {} entries", self.dv, self.log.len())
    }
}

fn main() {
    let b = Burn { dv: 12.5, log: Vec::new() };
    println!("{}", b.report());
    println!("{}", b.dv);
}
```
--- choice correct
`report` takes `self` by value, so `b.report()` moves `b` into the method, and `b.dv` afterwards uses a moved value. Change it to `fn report(&self)`, since it only reads.
--- choice
Nothing is wrong: `dv` is an `f64`, which is Copy, so reading it after the call is fine.
--- choice
Derive `Clone` and call `b.clone().report()`: the clone is consumed and `b` survives.
--- choice
Derive `Clone` and `Copy` for `Burn`, so the call copies `b` instead of moving it.
--- why
A method whose receiver is `self` takes ownership, exactly like a parameter of type `Burn`. The compiler says so: "`Burn::report` takes ownership of the receiver `self`, which moves `b`". That `dv` is Copy does not help, because the whole of `b` was moved, not one field. Cloning compiles, but it copies the whole `log` vector just to print a line. Copy is impossible, because a `Vec<String>` field is not Copy (E0204). A method that only reads should borrow: `&self`.

+++ question | A spare valve from the rack
--- ask
What does this print? Type the output on one line.

```rust
struct Valve(u8);

impl Drop for Valve {
    fn drop(&mut self) {
        print!("close:{} ", self.0);
    }
}

fn main() {
    let spare;
    {
        let mut rack = Vec::new();
        rack.push(Valve(1));
        rack.push(Valve(2));
        spare = rack.remove(0);
        print!("inner ");
    }
    print!("outer ");
    let _kept = spare;
    print!("end ");
}
```
--- answer
inner close:2 outer end close:1
--- why
`rack.remove(0)` moves `Valve(1)` out of the vector and into `spare`, which lives in the outer scope. The vector keeps only `Valve(2)`. At the inner closing brace, `rack` goes out of scope and drops what it still owns, so "close:2" comes right after "inner". `let _kept = spare;` moves the valve again, and a move prints nothing. `_kept` owns it until the end of `main`, after "end". Each valve closed exactly once, by whoever owned it last.

+++ question | Looking at the last waypoint, then adding one
--- ask
What happens?

```rust
fn main() {
    let mut plan = vec![120.0, 240.0];
    let last = plan.last();
    println!("{:?}", last);
    plan.push(360.0);
    println!("{:?}", plan);
}
```
--- choice correct
It compiles, and prints `Some(240.0)` and then `[120.0, 240.0, 360.0]`.
--- choice
E0502: `last` borrows `plan` until the end of `main`, so the push conflicts with it.
--- choice
It prints `Some(360.0)` first, because `last` shows the vector as it is when printed.
--- choice
E0499: `last` and `push` both borrow `plan` mutably.
--- why
`plan.last()` returns an `Option<&f64>`, a shared borrow of the vector. A borrow lasts from where it is made to its last use, not to the closing brace: that is non-lexical lifetimes. The last use of `last` is the first `println!`, so by the `push` no shared borrow is alive, and `push` may take its exclusive one. Swap the print and the push and you get E0502, because `last` would then be used after the vector may have moved its buffer. `last` takes `&self`; only `push` borrows mutably.

+++ question | Halving the readings
--- ask
The compiler rejects this. Which error code does it report? Type the code.

```rust
fn scale(v: &mut [f64], k: f64) {
    for x in v.iter_mut() {
        *x *= k;
    }
}

fn main() {
    let readings = vec![1.0, 2.0, 4.0];
    scale(&mut readings, 0.5);
    println!("{:?}", readings);
}
```
--- answer
E0596
0596
error[E0596]
--- why
`scale` needs a `&mut [f64]`, and the call writes `&mut readings`, but `readings` was declared with a plain `let`. You may only lend a value exclusively if its owner allows changes: `let mut readings`. The message is "cannot borrow `readings` as mutable, as it is not declared as mutable". The `mut` on the `let` is the owner's permission; the `&mut` at the call is the claim to be the one writer. With `let mut`, it prints `[0.5, 1.0, 2.0]`: a borrowed `Vec<f64>` is accepted where a slice is asked for.

+++ question | Hot readings, then clear
--- ask
This fails with E0502 on `temps.clear();`. Which change makes it compile and still print `2`?

```rust
fn main() {
    let mut temps = vec![20.0, 85.5, 90.1];
    let hot: Vec<&f64> = temps.iter().filter(|t| **t > 80.0).collect();
    temps.clear();
    println!("{}", hot.len());
}
```
--- choice correct
Replace the `let hot` line with `let hot: Vec<f64> = temps.iter().copied().filter(|t| *t > 80.0).collect();`
--- choice
Declare it `let mut hot: Vec<&f64> = ...`, so `hot` may change after the clear.
--- choice
Move `temps.clear();` up, so it comes before the `let hot` line.
--- choice
Put the `let hot` line in its own block, `{ ... }`, so its borrow ends at the brace.
--- why
`hot` is a vector of references into `temps`, so it keeps `temps` borrowed for as long as `hot` is used, which is up to the `println!`. `clear` needs `&mut temps` in the middle: a reader and a writer at once. `copied()` turns each `&f64` into an independent `f64`, so `hot` owns its numbers and the borrow of `temps` ends with the `let` line. Clearing first compiles but prints 0, so the program no longer means the same thing. A `mut` on `hot` changes nothing about what it borrows, and a block would hide `hot` from the `println!` altogether.

+++ question | Two rates, two writers
--- ask
What happens?

```rust
fn main() {
    let mut rates = vec![0.10, 0.20, 0.30];
    let a = &mut rates[0];
    let b = &mut rates[1];
    *a += 0.01;
    *b += 0.01;
    println!("{:?}", rates);
}
```
--- choice
It compiles: `a` and `b` point at different elements, so nothing is aliased.
--- choice correct
E0499: `&mut rates[0]` borrows the whole vector exclusively, and the borrow checker does not compare index values, so `b` is a second `&mut` of `rates` while `a` is still used.
--- choice
E0502, because indexing is a shared borrow.
--- choice
It compiles, but panics while running, because two `&mut` to one vector are detected at run time.
--- why
`&mut rates[i]` goes through the vector as a whole: the compiler sees "an exclusive borrow of `rates`", whatever `i` is. It does not work out that 0 and 1 differ, and in general it could not, because indices are usually computed while the program runs. So two exclusive borrows overlap: the two-writers error. When you really need two exclusive views, `rates.split_at_mut(1)` gives two slices and promises in its signature that they do not overlap. Borrow rules are checked at compile time, never at run time.

+++ question | Removing zeros while walking the queue
--- ask
This should remove every zero from the queue. What is wrong, and what is the right fix?

```rust
fn main() {
    let mut queue = vec![3, 0, 5, 0];
    for (i, x) in queue.iter().enumerate() {
        if *x == 0 {
            queue.remove(i);
        }
    }
    println!("{:?}", queue);
}
```
--- choice
Nothing: it compiles and prints `[3, 5]`.
--- choice correct
E0502: the loop's iterator holds a shared borrow of `queue` for the whole loop, and `remove` needs `&mut queue` in the middle of it. Read first, then write: `let kept: Vec<i32> = queue.iter().copied().filter(|x| *x != 0).collect();` and then `queue = kept;`
--- choice
It compiles, but panics with an index out of bounds once the vector has shrunk.
--- choice
E0308: `remove` wants a `usize`, and `enumerate` gives a `&usize`.
--- why
This is iterator invalidation. `remove` shifts every later element one place left, and the same loop in C++, with `erase`, can walk off the end or skip elements. Rust rejects the shape: a reader (the loop) and a writer (`remove`) alive at once. Even an index loop that compiled would be wrong: after removing a zero at index 1, the element that slides into index 1 is never looked at, so two zeros in a row leave one behind. Building the kept list first and then assigning it has one clear meaning. `enumerate` gives a plain `usize` index; only the item is a reference.

Each program uses `thread::scope`.

```rust
let config = vec![1.5, 2.5];

    s.spawn(|| b[0] = 2);
});

// D
let mut count = 0u64;
thread::scope(|s| {
    s.spawn(|| {
        for _ in 0..100 {
            count += 1;
        }
    });
    println!("{}", count);
});
```

Pick every program the compiler accepts.
--- choice correct
A
--- choice
B
--- choice correct
C
--- choice
D
--- why
The rule is the same with or without threads: many readers, or one writer. In A, both closures hold a `&Vec<f64>`, which is fine. In B, the pushing closure needs `&mut log` for as long as its thread may run, and the other closure's `&log` overlaps it: E0502. In C++ that would be a data race. In C, the two `&mut` slices cover different elements, so nothing is both shared and written. +++ question | Three labels for one conflict
--- ask
The compiler prints this for a five-line `main`:

```text
error[E0502]: cannot borrow `target` as mutable because it is also borrowed as immutable
 --> src/main.rs:4:5
  |
3 |     let view = &target;
  |                ------- immutable borrow occurs here
4 |     target.push_str("-2");
  |     ^^^^^^^^^^^^^^^^^^^^^ mutable borrow occurs here
5 |     println!("{}", view);
  |                    ---- immutable borrow later used here
```

Which fix follows from reading the labels, with no clone?
--- choice correct
Move the `println!` above the `push_str` line. The borrow's last use then comes before the conflict, so the borrow has ended when `push_str` asks for `&mut target`.
--- choice
Change line 3 to `let view = &mut target;`, so both lines borrow the same way.
--- choice
Move `let view = &target;` below the `println!`.
--- choice
Write line 4 as `target.clone().push_str("-2");`.
--- why
Read the three points. Line 3, dashes: the shared borrow starts. Line 4, carets: the conflict, a `push_str` that needs `&mut target`. Line 5, dashes: the borrow is still used. The fix is to move one of the three so the conflict no longer sits inside the borrow; printing first ends the borrow before the push. A `&mut` borrow on line 3 gives E0499 instead, because `push_str` needs its own. Moving the `let` below its use leaves `view` undeclared where it is printed. And `target.clone().push_str(...)` changes a throwaway copy, so `target` never gets its suffix.

```rust
fn main() {
```

Match on the value instead of a reference: `if let Mode::Burn(dv) = mode {`

+++ question | Keeping every reading
--- ask
What happens?

```rust
fn main() {
    let mut latest: Vec<&f64> = Vec::new();
    for i in 0..3 {
        let reading = i as f64 * 1.5;
        latest.push(&reading);
    }
    println!("{:?}", latest);
}
```
--- choice
It prints `[0.0, 1.5, 3.0]`.
--- choice correct
E0597: each `reading` is dropped at the end of its pass through the loop, but `latest` keeps a reference to it and is used after the loop. Store the numbers themselves: a `Vec<f64>` and `latest.push(reading)`.
--- choice
E0499: the loop borrows `reading` three times.
--- choice
It prints `[3.0, 3.0, 3.0]`, because every reference points at the same variable.
--- why
Each pass through the loop body is its own scope, so a fresh `reading` is born and dies every time. The closing brace of the body is the conflict ("`reading` dropped here while still borrowed"), and the `println!` is where the borrow is still needed. In C, storing the address of a loop variable like this is the classic dangling pointer. +++ question | A downlink that sends twice
--- ask
`send` should hand over the pending bytes once and leave nothing pending, so the program should print `3 0`. It fails with E0507.

```rust
struct Downlink {
    pending: Option<Vec<u8>>,
}

impl Downlink {
    fn send(&mut self) -> usize {
        match self.pending {
            Some(bytes) => bytes.len(),
            None => 0,
        }
    }
}

fn main() {
    let mut d = Downlink { pending: Some(vec![1, 2, 3]) };
    println!("{} {}", d.send(), d.send());
}
```

Which fix does what was asked?
--- choice
Follow the compiler's help and match on `&self.pending`.
--- choice correct
Match on `self.pending.take()`, which moves the `Vec` out and leaves `None` behind.
--- choice
Change `send` to take `self` instead of `&mut self`.
--- choice
Write the arm as `Some(bytes) => bytes.clone().len()`.
--- why
`send` only borrows the `Downlink`. Moving the `Vec` out of `self.pending` would leave the owner's field broken, so it is refused. `Option::take` is the tool for moving out through a `&mut`: it returns what was inside and puts `None` in its place, so the second call finds nothing and gives 0. The compiler's help, `match &self.pending`, compiles but only looks: both calls see the same 3 bytes, and it prints `3 3`. Taking `self` would consume the whole downlink, so `send` could not be called twice. The clone comes too late: the pattern has already moved `bytes`, so it is still E0507.

+++ question | Two getters for one rig
--- ask
This fails with E0499 on `let r = rig.right_mut();`.

```rust
struct Rig {
    left: Vec<f64>,
    right: Vec<f64>,
}

impl Rig {
    fn left_mut(&mut self) -> &mut Vec<f64> {
        &mut self.left
    }
    fn right_mut(&mut self) -> &mut Vec<f64> {
        &mut self.right
    }
}

fn main() {
    let mut rig = Rig { left: vec![1.0], right: vec![2.0] };
    let l = rig.left_mut();
    let r = rig.right_mut();
```

--- choice correct
`let l = &mut rig.left; let r = &mut rig.right; l.push(r[0]);`
--- choice correct
`let x = rig.right_mut()[0]; rig.left_mut().push(x);`
--- choice
`let l = rig.left_mut(); let r = &rig.right; l.push(r[0]);`
--- choice correct
Add `fn both_mut(&mut self) -> (&mut Vec<f64>, &mut Vec<f64>) { (&mut self.left, &mut self.right) }` to the impl, then write `let (l, r) = rig.both_mut(); l.push(r[0]);`

Copying the `f64` out first ends the first borrow before the second begins.

+++ question | The first word of a dropped line
--- ask
What happens?

```rust
fn first_word(s: &str) -> &str {
    s.split(' ').next().unwrap_or("")
}

fn main() {
    let w;
    {
        let line = String::from("ALT 1200");
        w = first_word(&line);
    }
    println!("{}", w);
}
```
--- choice
It prints `ALT`.
--- choice correct
E0597: by elision rule 2, the result borrows from the only input, so `w` keeps `line` borrowed, and `line` is dropped at the inner brace while `w` is still needed.
--- choice
E0106: `first_word` returns a reference, so it needs a written lifetime.
--- choice
It prints `ALT`, because `split` makes a new string that `w` owns.
--- why
`fn first_word(s: &str) -> &str` has one input lifetime, so rule 2 gives it to the output: written out, `fn first_word<'a>(s: &'a str) -> &'a str`. No annotation is needed, and the caller reads the signature: `w` points into `line`. That is also true: `split` hands out slices of the original text, not copies. The owner dies at the inner closing brace, and the borrow is used on the next line. Declare `line` in the outer block, or return a `String` if the word must outlive the line.

+++ question | A cursor over a packet
--- ask
What does this print? Type the output.

```rust
struct Cursor<'a> {
    data: &'a [u8],
    pos: usize,
}

impl<'a> Cursor<'a> {
    fn take(&mut self, n: usize) -> Option<&'a [u8]> {
        let end = self.pos + n;
        if end > self.data.len() {
            return None;
        }
        let out = &self.data[self.pos..end];
        self.pos = end;
        Some(out)
    }
}

fn main() {
    let buf = [0x01u8, 0x02, 0x03, 0x04, 0x05];
    let mut c = Cursor { data: &buf, pos: 0 };
    let a = c.take(2);
    let b = c.take(2);
    let d = c.take(2);
    println!("{:?} {:?} {:?}", a, b, d);
}
```
--- answer
Some([1, 2]) Some([3, 4]) None
Some([1,2]) Some([3,4]) None
--- why
Each `take` returns a slice of `buf` and moves `pos` on: bytes 0 and 1, then 2 and 3. The third call would need bytes 4 and 5, but `end = 6` is past the 5 bytes, so it returns `None`. The key is the return type, `Option<&'a [u8]>`: each slice borrows the *buffer*, for `'a`, not the cursor. So `a` stays usable while `c.take` borrows `c` mutably again. Write the return type as `Option<&[u8]>` and rule 3 ties it to `&mut self` instead: `a` would then keep the cursor borrowed exclusively, and the second `take` would fail with E0499. Same body, a different promise.

+++ question | A counter that loses counts
--- ask
Two threads each count 100,000 packets. Three runs printed 176198, 156812 and 200000.

```rust
use std::sync::{Arc, Mutex};
use std::thread;

    let packets = Arc::new(Mutex::new(0u64));
    let mut handles = Vec::new();
    for _ in 0..2 {
        let counter = Arc::clone(&packets);
        handles.push(thread::spawn(move || {
            for _ in 0..100_000 {
                let n = *counter.lock().unwrap();
                *counter.lock().unwrap() = n + 1;
            }
        }));
    }
    for h in handles {
        h.join().unwrap();
    }
    println!("{}", *packets.lock().unwrap());
}
```

What is wrong?
--- choice correct
Each increment locks twice: once to read, released at the semicolon, then again to write. Between the two, the other thread can count, and its update is overwritten. Hold one guard for both steps: `*counter.lock().unwrap() += 1;`
--- choice
It is a data race: Rust's compile-time promise has failed here.
--- choice
Each thread gets its own copy of the counter, so the two totals are never added.
--- choice
The `u64` overflows and wraps around.
--- why
The lock protects each access, not the sequence. Thread A reads 41 and releases the lock; thread B reads 41 and writes 42; A writes 42. Two packets, one count. +++ question | A hit counter in a static
--- ask

```rust
    hits: Cell<u32>,
}

}
```

--- ask
What happens?

```rust

    &log[log.len() - 1]
```

--- choice correct

+++ question | Handles, owners and drops
--- ask
What does this print? Type the output on one line.

```rust
use std::rc::Rc;

struct Log(&'static str);

impl Drop for Log {
    fn drop(&mut self) {
        print!("drop:{} ", self.0);
    }
}

fn main() {
    let a = Rc::new(Log("eps"));
    let b = Rc::clone(&a);
    {
        let c = Rc::clone(&b);
```

+++ question | Two lifetimes, one result
--- ask
What does the compiler say about this function?

```rust
fn prefer<'a, 'b>(primary: &'a str, backup: &'b str, ok: bool) -> &'a str {
    if ok { primary } else { backup }
}
```
--- choice
It compiles: both inputs are borrowed strings, so either may be returned.
--- choice correct
It fails in the body: the signature promises a result valid for `'a`, but `backup` is only known to live for `'b`, which may be shorter ("lifetime may not live long enough"). Use one lifetime for both inputs, or add the bound `'b: 'a`.
--- choice
It compiles, and callers learn from the body that `backup` must stay alive too.
--- choice
E0106: a function may not have two lifetime parameters.
--- why
A signature is checked from both sides. Callers rely only on the label, which here says "the result depends only on `primary`". So the body must keep that promise, and returning `backup`, whose lifetime `'b` has no stated relation to `'a`, breaks it. The compiler even suggests `'b: 'a`, read "tick b outlives tick a". The usual fix is one `'a` on both inputs, which tells callers the truth: the result may come from either, so both must stay alive. Two lifetime parameters are allowed; what matters is that the relation between them is stated.

--- why
`a.clone()` on an `Rc` is the cheap kind: one more handle to the same `RefCell`, so pushes through `b` are seen through `a`. `a.borrow().clone()` clones the `Vec` inside, a deep copy with its own heap buffer, made while the vector held 3 numbers. The later push reaches `a` and `b`, which now see 4, but not `c`, which keeps 3. Whether `.clone()` shares or copies depends on the type: for `Rc` and `Arc` it counts, for `Vec` and `String` it allocates.

+++ question | How many copies of the code
--- ask
How many compiled copies of `log_all` does this program contain, and how many of `log_dyn`? Type the two numbers, separated by a space.

```rust
use std::fmt::Display;

fn log_all<T: Display>(items: &[T]) {
    for x in items {
        println!("{}", x);
    }
}

fn log_dyn(items: &[&dyn Display]) {
    for x in items {
        println!("{}", x);
    }
}

fn main() {
    log_all(&[1.0, 2.0]);
    log_all(&[3u32]);
    log_all(&[4.5]);
    log_all(&["a", "b"]);
    log_dyn(&[&1.0, &3u32, &"a"]);
}
```
--- answer
3 1
3, 1
3,1
--- why
The compiler writes one copy of a generic function for each concrete type it is used with: `T` is `f64` (for both `1.0, 2.0` and `4.5`), `u32`, and `&str`, so three copies, each with a direct call to its type's formatting that can be inlined. `log_dyn` is not generic: it is compiled once, and each `x` is a fat pointer whose vtable finds the right formatting code while the program runs. More types would mean more copies of `log_all` and still one `log_dyn`: code size traded against call speed.

+++ question | Threads that keep their data
--- ask
`main` starts with `let log = vec![1];`, `let s = String::from("x");` and `let name = "IMU-A";`. Pick every line that compiles after them, each tried on its own.
--- choice correct
`thread::spawn(move || name.len());`
--- choice
`thread::spawn(|| log.len());`
--- choice correct
`thread::spawn(move || log.len());`
--- choice
`let r = &s; thread::spawn(move || r.len());`
--- choice
`let n = Rc::new(5); thread::spawn(move || *n + 1);`
--- why
`spawn` needs a closure that is `Send` and `'static`, since the thread may outlive `main`'s locals. `name` is a `&'static str`, a borrow that never expires, and `move` copies it in. Without `move`, the closure borrows `log`: E0373. With `move`, it owns the vector and holds no borrow, so it passes. Moving `r` in moves only the reference, and a reference to a local `String` is still a borrow that expires: E0597, "`s` is borrowed for `'static`". The `Rc` fails the other half, Send (E0277).
