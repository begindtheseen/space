+++ practice | A deep folder, and an empty one
--- task
orbit-sim is getting a `models` folder. Make the next commit hold these two things:

- the file `models/atmosphere/density.py`, whose one line is `RHO0 = 1.225`;
- the folder `models/gravity/`, which has no code yet.

A tree is a list of the files and folders inside it, so Git has no way to store a folder with nothing in it. The usual answer is an empty file named `.keep` inside the folder: then the folder has one entry, and its tree can be written.

Stage everything with one `git add models`, and commit with the message `Add models folder with atmosphere density`.
--- starter
git init

git commit -m "Add README"
--- solution

echo "RHO0 = 1.225" > models/atmosphere/density.py
touch models/gravity/.keep
git add models
git commit -m "Add models folder with atmosphere density"
--- hint
`mkdir -p` makes a folder and every folder above it that is missing, in one command. `touch` makes an empty file.
--- hint
An empty folder gives `git add` nothing to record. Once `models/gravity/.keep` exists, `git add models` picks the folder up.
--- check shell | The density file is in the new snapshot, two folders down
git . commits == 2
git . at HEAD message == Add models folder with atmosphere density
git . at HEAD file models/atmosphere/density.py == RHO0 = 1.225
--- check shell | The empty folder made it in, through .keep

+++ practice | The commit that left its test behind
--- task
Ravi wrote a drag model and its test, then typed `git add drag.py` and `git commit -m "Add drag model and its test"`. The message promises a test, but the snapshot has only `drag.py`. The test file is still in the folder, untracked.

--- hint

+++ question | One file copied
--- ask
orbit-sim's newest commit holds `README.md`, `gravity.py` and `tests/test_gravity.py`. You copy `gravity.py` to `gravity_backup.py` without changing a byte, run `git add gravity_backup.py`, and commit.

How many **new blob** objects does that commit write into `.git/objects`? Type the number.
--- answer
0
zero
none
no new blobs
no new blob
0 blobs
0 new blobs
--- why
None. A blob is named by the hash of its contents alone, and those exact contents are already stored as `gravity.py`'s blob. Git finds the same hash and reuses the object. The commit still writes two objects: a new root tree, whose list now has a fourth entry, `gravity_backup.py`, pointing at the old blob, and the new commit. The file name lives in the tree, never in the blob.

+++ question | One line in a test, three levels of objects
--- ask
orbit-sim's newest commit holds `README.md`, `gravity.py` and `tests/test_gravity.py`. You change one line in `tests/test_gravity.py` and commit. Which objects does the new commit write?
--- choice
Only a new blob for the test file. The trees are reused, because no file was added, removed or renamed.
--- choice correct
A new blob for the test file, a new tree for `tests`, a new root tree and the new commit.
--- choice
A new blob, a new tree for `tests` and the new commit. The root tree is reused, because `README.md` and `gravity.py` did not change.
--- choice
New blobs for all three files, new trees and a new commit, because every commit is a complete snapshot.
--- why
The changed file gets a new blob. The `tests` tree lists that blob's hash, so its text changes and it gets a new hash too. The root tree lists the `tests` tree's hash, so it changes as well. That is 4 new objects, counting the commit. `README.md` and `gravity.py` are reused: the new root tree points at their old blobs. A complete snapshot does not mean stored again, and a change always climbs every tree on its way up to the root.

+++ question | Two letters: AM
--- ask
`git status -s` prints `AM tests/test_drag.py`. What does that mean, and what would `git commit` record for this file right now?
--- choice correct
The file is new and staged, and it was edited again after `git add`. The commit records it as it was at the `git add`.
--- choice
The file is new and staged. The commit records its current contents, because a commit reads the files on disk.
--- choice
The file was added on two branches and merged. The commit records both versions.
--- choice
The file is untracked but modified. The commit leaves it out until you run `git add`.
--- why
The left letter compares the index with the last commit: `A` means the index holds a file the last commit does not have, so it is new and staged. The right letter compares the working tree with the index: `M` means the file on disk has changed since it was staged. `git commit` builds its snapshot from the index, so it records the version from the moment of `git add`, and the newer edit stays behind in the working tree until you add the file again.

+++ question | Pick the message
--- ask
A commit fixes `accel_vector` in `gravity.py`: it returned a vector pointing away from Earth, so every orbit flew off. The fix flips one sign. Which message follows the rules for commit messages?
--- choice
`Fixed the sign bug in accel_vector.`, with no body.
--- choice correct
The subject `Fix sign of gravity vector in accel_vector`, a blank line, then a body saying that the vector pointed away from Earth so orbits escaped, and why the sign was flipped here and not in the callers.
--- choice
The subject `Update gravity.py`, then a body listing the line that changed and its old and new text.
--- choice
The subject `Fix bug`, a blank line, then a body explaining the symptom and the fix.
--- why
A good subject is imperative ("Fix", not "Fixed"), specific, about 50 characters or fewer, with no full stop, and a body after one blank line says *why*. The first choice is past tense, ends in a full stop and has no reason. The third wastes the subject on the file name and, in its body, repeats what the diff already shows. The fourth has a body, but "Fix bug" tells someone scanning `git log --oneline` nothing at all.

+++ question | What -diff turns off
--- ask
A repository's `.gitattributes` has the line `*.csv -diff`. What changes for the CSV files in it?
--- choice
They are no longer tracked: Git treats them as if they were in `.gitignore`.
--- choice correct
They are still committed and merged line by line as before, but `git diff` shows a one-line "Binary files differ" notice instead of their changed lines.
--- choice
They are stored through Git LFS, as pointer files.
--- choice
Git stops converting their line endings, but diffs still show every changed line.
--- why
`.gitattributes` never decides whether a file is tracked; that is `.gitignore`'s job, and only for untracked files. Each attribute turns off exactly one behavior: `-diff` stops the line-by-line diff, `-merge` stops the line-by-line merge, and `-text` stops line-ending conversion. `binary` is the shorthand for all three. LFS happens only through `filter=lfs`.

+++ question | Eight versions of a telemetry file
--- ask
A 20,000,000-byte golden telemetry file is re-exported and committed 8 times, without LFS. Each export is completely different from the last. After packing, about how many MiB does this file's history add to every clone? Round to a whole number, and type just the number.
--- answer
153
153 MiB
153MiB
about 153
about 153 MiB
--- why
Git stores a complete new blob for each version, and random-looking data neither compresses nor shares pieces with the other versions, so the pack holds all 8 versions in full: 8 × 20,000,000 = 160,000,000 bytes. A MiB is 2^20 = 1,048,576 bytes, and 160,000,000 / 1,048,576 ≈ 152.6, about 153 MiB. With LFS, the repository would hold eight small pointer files instead, and a clone would download only the payload the checked-out commit needs.

+++ question | Which tag describe picks
--- ask
Commit `A` carries the annotated tag `v2.1.0`. One commit later, commit `B`, whose short hash is `5c0d7e2`, carries only a lightweight tag, `nightly`. HEAD is on `B`. What does plain `git describe` print?

+++ question | The order git tag lists
--- ask
A repository has exactly three tags: `v0.9.0`, `v0.10.0` and `v0.9.1`. In what order does plain `git tag` list them? Type the three names, top to bottom, separated by spaces.
--- answer
v0.10.0 v0.9.0 v0.9.1
v0.10.0, v0.9.0, v0.9.1
v0.10.0,v0.9.0,v0.9.1
v0.10.0, v0.9.0 and v0.9.1
v0.10.0 v0.9.0 and v0.9.1

Plain `git tag` sorts names as text, one character at a time. All three start `v0.`; then `1` comes before `9`, so `v0.10.0` is first even though 10 is bigger than 9. +++ question | Fast-forward or not?
--- ask
Since `feature` was made from `main`, `main` has gained two commits and `feature` has two of its own. On `main`, you run `git merge feature`. What happens?
--- choice
A fast-forward: `feature` is newer, so `main` slides to its tip.
--- choice correct
A three-way merge: neither tip is an ancestor of the other, so Git combines the merge base, ours and theirs, and, without a conflict, makes a merge commit with two parents.
--- choice
Git refuses, because `main` has commits that `feature` lacks.
--- choice
A fast-forward, and `main`'s two new commits are dropped from its history.
--- why
A fast-forward is possible only when your tip is an ancestor of the other tip, so that the other branch is your branch plus more.
