+++ practice | Antennas at the ground stations
--- task
The database already has a `satellite` table and a `station` table. Add a table for the dish antennas at each ground station.

Create a table named `antenna` with these four columns:

- `antenna_id`: text, the table's primary key.
- `station_id`: text.
- `dish_m`: the dish diameter in meters, a measured number with a decimal point (type `REAL`).
- `band`: text, the radio band, such as `X` or `S`.

Every column must hold a value on every row. Remember that SQLite lets a primary-key column hold NULL unless you also write `NOT NULL`.

Then insert these three antennas and end with `SELECT * FROM antenna;` so you can see them:

| antenna_id | station_id | dish_m | band |
| --- | --- | --- | --- |
| SVB-A1 | SVB | 11.3 | X |
| SVB-A2 | SVB | 7.3 | S |
| AWA-A1 | AWA | 9.1 | X |
--- starter
-- Create the antenna table, insert the three antennas, then look at them.

--- solution
CREATE TABLE antenna (
    antenna_id TEXT NOT NULL PRIMARY KEY,
    station_id TEXT NOT NULL,
    dish_m     REAL NOT NULL,
    band       TEXT NOT NULL
);

INSERT INTO antenna (antenna_id, station_id, dish_m, band) VALUES
  ('SVB-A1', 'SVB', 11.3, 'X'),
  ('SVB-A2', 'SVB', 7.3,  'S'),
  ('AWA-A1', 'AWA', 9.1,  'X');

SELECT * FROM antenna;
--- hint
Model it on the `CREATE TABLE satellite` statement in the lesson: a name, then in parentheses one line per column with its name, its type and its rules.
--- hint
The key column needs both `PRIMARY KEY` and `NOT NULL` in SQLite. Every other column needs `NOT NULL`. Text values go in single quotes; numbers do not.
--- check query | The table holds the three antennas
SELECT antenna_id, station_id, dish_m, band FROM antenna ORDER BY antenna_id
=> [["AWA-A1", "AWA", 9.1, "X"], ["SVB-A1", "SVB", 11.3, "X"], ["SVB-A2", "SVB", 7.3, "S"]]

--- check query | The dish size is stored as a number

--- check query | A second SVB-A1 is refused
INSERT OR IGNORE INTO antenna (antenna_id, station_id, dish_m, band) VALUES ('SVB-A1', 'SVB', 3.0, 'S');

--- check query | An antenna with no id is refused

+++ practice | A pass table that keeps every real pass
--- task
The database has a `satellite` table (key `sat_id`) and a `station` table (key `station_id`). Create a table named `pass` for satellite passes over ground stations, with these columns:

- `sat_id`: text, which satellite.
- `station_id`: text, which ground station heard it.
- `aos`: text, the time the pass starts, such as `2026-04-10T06:00:00Z`.
- `los`: text, the time the pass ends.
- `bytes`: integer, the data received. It may be missing, because a pass's data can arrive hours later.

Every column except `bytes` must always hold a value.

Choose the primary key from these facts:

- Two stations can hear the same satellite at the same moment.
- A station has several antennas, so it can start passes of two different satellites at the same moment.
- One station cannot start two passes of the same satellite at the same moment.

Also make `sat_id` a foreign key that references `satellite (sat_id)`, and `station_id` one that references `station (station_id)`.
--- starter
-- Create the pass table.

--- solution
CREATE TABLE pass (
    sat_id     TEXT NOT NULL REFERENCES satellite (sat_id),
    station_id TEXT NOT NULL REFERENCES station (station_id),
    aos        TEXT NOT NULL,
    los        TEXT NOT NULL,
    bytes      INTEGER,
    PRIMARY KEY (sat_id, station_id, aos)
);
--- hint
Ask what makes one pass different from every other. A single column cannot do it: which combination of columns never repeats?
--- hint
The facts rule out (sat_id, aos) and (station_id, aos). The key needs all three of sat_id, station_id and aos. Declare it on its own line: `PRIMARY KEY (…, …, …)`.
--- hint
A foreign key is written on the column: `sat_id TEXT NOT NULL REFERENCES satellite (sat_id)`.
--- check query | The key is the satellite, the station and the start time
SELECT name FROM pragma_table_info('pass') WHERE pk > 0 ORDER BY name
=> [["aos"], ["sat_id"], ["station_id"]]
--- check query | Both foreign keys are declared
SELECT "from", "table", "to" FROM pragma_foreign_key_list('pass') ORDER BY "from"
=> [["sat_id", "satellite", "sat_id"], ["station_id", "station", "station_id"]]
--- check query | Passes that the facts allow all go in, one without bytes
INSERT OR IGNORE INTO pass (sat_id, station_id, aos, los, bytes) VALUES
  ('OSP-01', 'SVB', '2026-04-10T06:00:00Z', '2026-04-10T06:09:00Z', 1000),
  ('OSP-01', 'AWA', '2026-04-10T06:00:00Z', '2026-04-10T06:08:00Z', NULL),
  ('HRN-01', 'SVB', '2026-04-10T06:00:00Z', '2026-04-10T06:07:00Z', 500);
SELECT COUNT(*) FROM pass
=> [[3]]
--- check query | The same pass twice is refused
INSERT OR IGNORE INTO pass (sat_id, station_id, aos, los, bytes) VALUES ('OSP-01', 'SVB', '2026-04-10T06:00:00Z', '2026-04-10T06:10:00Z', 2000);
SELECT COUNT(*) FROM pass
=> [[3]]
--- check query | A pass with no end time is refused
INSERT OR IGNORE INTO pass (sat_id, station_id, aos, bytes) VALUES ('HRN-01', 'AWA', '2026-04-10T07:00:00Z', 10);
SELECT COUNT(*) FROM pass

+++ practice | Mode changes that obey the rules
--- task
Create a table named `mode_change` that logs each time a satellite switches mode, with three columns:

- `sat_id`: text, a foreign key that references `satellite (sat_id)`.
- `ts`: text, when the switch happened.
- `new_mode`: text, the mode it switched into.

The rules:

- No column may ever be empty.
- A satellite switches mode at most once at any one moment, but two satellites can switch at the same moment. Choose the primary key to match.
- `new_mode` must be exactly one of `ACTIVE`, `SAFE_MODE`, `COMMISSIONING` or `DEORBITED`, in capitals. Add the rule to the column as `CHECK (new_mode IN ('ACTIVE', 'SAFE_MODE', 'COMMISSIONING', 'DEORBITED'))`.

Then insert these three rows:

| sat_id | ts | new_mode |
| --- | --- | --- |
| OSP-02 | 2026-04-09T22:15:00Z | SAFE_MODE |
| TRN-04 | 2026-04-09T22:15:00Z | ACTIVE |
| OSP-02 | 2026-04-10T03:00:00Z | ACTIVE |
--- starter
-- Create the mode_change table, then insert the three rows.

--- solution
CREATE TABLE mode_change (
    sat_id   TEXT NOT NULL REFERENCES satellite (sat_id),
    ts       TEXT NOT NULL,
    new_mode TEXT NOT NULL CHECK (new_mode IN ('ACTIVE', 'SAFE_MODE', 'COMMISSIONING', 'DEORBITED')),
    PRIMARY KEY (sat_id, ts)
);

INSERT INTO mode_change (sat_id, ts, new_mode) VALUES
  ('OSP-02', '2026-04-09T22:15:00Z', 'SAFE_MODE'),
  ('TRN-04', '2026-04-09T22:15:00Z', 'ACTIVE'),
  ('OSP-02', '2026-04-10T03:00:00Z', 'ACTIVE');
--- hint
"At most once per satellite per moment" names the columns of the key.
--- hint
The key is `(sat_id, ts)`. The CHECK rule goes at the end of the `new_mode` line, after `NOT NULL`.

+++ practice | The key that lets a contradiction in
--- task
The `thermal` table holds temperature readings from several sensors on each satellite. One sensor measures one temperature at a time, so a row for the same satellite, the same moment and the same sensor should only ever exist once.

The starter creates the table and loads four readings. But its key lets this row in next to the existing 21.5 reading:

```text
('OSP-01', '2026-04-10T06:00:00Z', 'PANEL_X', 23.9)
```

Two different temperatures for one sensor at one moment is a contradiction. Fix the table so that row is refused, while all four starter readings still go in, and a second sensor at the same moment is still allowed. Change only the key.
--- starter
DROP TABLE IF EXISTS thermal;
CREATE TABLE thermal (
    sat_id TEXT NOT NULL REFERENCES satellite (sat_id),
    ts     TEXT NOT NULL,
    sensor TEXT NOT NULL,
    temp_c REAL NOT NULL,
    PRIMARY KEY (sat_id, ts, sensor, temp_c)
);

INSERT INTO thermal (sat_id, ts, sensor, temp_c) VALUES
  ('OSP-01', '2026-04-10T06:00:00Z', 'PANEL_X', 21.5),
  ('OSP-01', '2026-04-10T06:00:00Z', 'PANEL_Y', 19.0),
  ('OSP-01', '2026-04-10T06:01:00Z', 'PANEL_X', 21.7),
  ('HRN-01', '2026-04-10T06:00:00Z', 'PANEL_X', 30.2);

SELECT * FROM thermal;
--- solution
DROP TABLE IF EXISTS thermal;
CREATE TABLE thermal (
    sat_id TEXT NOT NULL REFERENCES satellite (sat_id),
    ts     TEXT NOT NULL,
    sensor TEXT NOT NULL,
    temp_c REAL NOT NULL,
    PRIMARY KEY (sat_id, ts, sensor)
);

INSERT INTO thermal (sat_id, ts, sensor, temp_c) VALUES
  ('OSP-01', '2026-04-10T06:00:00Z', 'PANEL_X', 21.5),
  ('OSP-01', '2026-04-10T06:00:00Z', 'PANEL_Y', 19.0),
  ('OSP-01', '2026-04-10T06:01:00Z', 'PANEL_X', 21.7),
  ('HRN-01', '2026-04-10T06:00:00Z', 'PANEL_X', 30.2);

SELECT * FROM thermal;
--- hint
A key promises "no two rows share this combination". With the measured value inside the key, two rows only clash when their temperatures are equal too.
--- hint
Take `temp_c` out of the key. What identifies a reading is where and when it was taken, not what it said.
--- check query | All four starter readings are in

=> [[4]]
--- check query | A second, different temperature for the same sensor and moment is refused
INSERT OR IGNORE INTO thermal (sat_id, ts, sensor, temp_c) VALUES ('OSP-01', '2026-04-10T06:00:00Z', 'PANEL_X', 23.9);
SELECT temp_c FROM thermal WHERE sat_id = 'OSP-01' AND ts = '2026-04-10T06:00:00Z' AND sensor = 'PANEL_X'
=> [[21.5]]
--- check query | A third sensor at the same moment is still allowed
INSERT OR IGNORE INTO thermal (sat_id, ts, sensor, temp_c) VALUES ('OSP-01', '2026-04-10T06:00:00Z', 'PANEL_Z', 18.4);
SELECT COUNT(*) FROM thermal
=> [[5]]
--- check query | The key is the satellite, the moment and the sensor
SELECT name FROM pragma_table_info('thermal') WHERE pk > 0 ORDER BY name
=> [["sat_id"], ["sensor"], ["ts"]]

+++ practice | The command log
--- task
Every command the ground sends to a satellite is logged. Create a table named `command_log` with these columns, none of which may be empty:

- `sat_id`: text, a foreign key that references `satellite (sat_id)`.
- `seq`: integer, the command's number.
- `sent_ts`: text, when it was sent.
- `opcode`: text, what the command does.

Choose the primary key from these facts, which the flight software team gave you:

- Each satellite numbers its own commands 1, 2, 3 and so on, and never uses a number twice.
- Every satellite starts from 1, so two satellites use the same numbers.
- The ground often sends two commands to one satellite within the same second, so `sent_ts` repeats.

Then insert these rows:

| sat_id | seq | sent_ts | opcode |
| --- | --- | --- | --- |
| OSP-01 | 41 | 2026-04-10T06:02:11Z | HEATER_ON |
| OSP-01 | 42 | 2026-04-10T06:02:11Z | TLM_RATE_HIGH |
| HRN-01 | 41 | 2026-04-10T06:05:40Z | WHEEL_RESET |
--- starter
-- Create the command_log table, then insert the three rows.

--- solution
CREATE TABLE command_log (
    sat_id  TEXT    NOT NULL REFERENCES satellite (sat_id),
    seq     INTEGER NOT NULL,
    sent_ts TEXT    NOT NULL,
    opcode  TEXT    NOT NULL,
    PRIMARY KEY (sat_id, seq)
);

INSERT INTO command_log (sat_id, seq, sent_ts, opcode) VALUES
  ('OSP-01', 41, '2026-04-10T06:02:11Z', 'HEATER_ON'),
  ('OSP-01', 42, '2026-04-10T06:02:11Z', 'TLM_RATE_HIGH'),
  ('HRN-01', 41, '2026-04-10T06:05:40Z', 'WHEEL_RESET');
--- hint
Go through the facts one at a time and cross out the keys each one breaks. `seq` alone repeats across satellites; anything with `sent_ts` in it can repeat within a second.
--- hint
Which combination does the first fact promise never repeats?

+++ question | Which statement is refused
--- ask
In SQLite, with foreign keys switched on, these statements have run:

```sql
PRAGMA foreign_keys = ON;
CREATE TABLE satellite (
    sat_id TEXT NOT NULL PRIMARY KEY,
    name   TEXT NOT NULL
);
CREATE TABLE pass (
    pass_id INTEGER NOT NULL PRIMARY KEY,
    sat_id  TEXT NOT NULL REFERENCES satellite (sat_id),
    station TEXT NOT NULL
);
INSERT INTO satellite VALUES ('OSP-01', 'Osprey-1'), ('OSP-02', 'Osprey-2');
INSERT INTO pass VALUES (1, 'OSP-01', 'Svalbard');
```

Which one of these next statements does the database refuse?
--- choice
`DELETE FROM satellite WHERE sat_id = 'OSP-02';`
--- choice correct
`DELETE FROM satellite WHERE sat_id = 'OSP-01';`
--- choice
`INSERT INTO pass VALUES (2, 'OSP-02', 'Svalbard');`
--- choice
`INSERT INTO satellite VALUES ('OSP-03', 'Osprey-1');`
--- why
Pass 1 points at OSP-01. Deleting OSP-01 would leave that pass orphaned, pointing at nothing, so the foreign key refuses it. OSP-02 has no passes, so deleting it is fine. A pass for OSP-02 is fine because OSP-02 exists. And a third satellite named Osprey-1 is allowed: only `sat_id` is the key, and nothing says names are unique. That is one reason a name makes a poor key.

+++ question | Which patterns can use the index
--- ask
The `satellite` table has an ordinary sorted index on `name`. Which of these conditions let the database jump to one block of the index, instead of reading every row?

```sql
name LIKE 'Tern%'
name LIKE '%-3'
name LIKE '_ern%'
```
--- choice correct
Only `name LIKE 'Tern%'`.
--- choice
`name LIKE 'Tern%'` and `name LIKE '_ern%'`, because both have fixed text before the `%`.
--- choice
All three, because any `LIKE` can use an index on the column it tests.
--- choice
None of them: `LIKE` always reads every row.
--- why
A sorted index can only narrow a search by how a value *begins*. `'Tern%'` starts with fixed text, so every match sits in one block: from `Tern` up to, but not including, `Tero`. `'%-3'` starts with a wildcard, so its matches are scattered all through the sorted order. `'_ern%'` looks close to the first, but `_` is a wildcard too: the first letter could be anything, so `Bern…`, `Fern…` and `Tern…` sit in different places, and the database must scan.

+++ question | Sorting a DISTINCT result
--- ask
In PostgreSQL this query fails with `for SELECT DISTINCT, ORDER BY expressions must appear in select list`:

```sql
SELECT DISTINCT station
FROM pass
ORDER BY aos;
```

SQLite runs it and returns an answer. Why does PostgreSQL refuse?
--- choice correct
DISTINCT merges all of a station's passes into one row, so there is no single `aos` left to sort that row by.
--- choice
ORDER BY may only ever name columns that are in the SELECT list, with or without DISTINCT.
--- choice
DISTINCT runs after ORDER BY, so the sort would be thrown away.
--- choice
`aos` is text, and text cannot be sorted once DISTINCT has run.
--- why
DISTINCT happens before ORDER BY. After it, the one Svalbard row stands for five passes with five different start times, and "sort by aos" no longer has one value to use for it. So PostgreSQL insists you sort a DISTINCT result by columns you selected. Without DISTINCT, sorting by a column you did not select is fine. SQLite's answer is worse than an error: it quietly picks one of the five times for you.

+++ question | Divide, then multiply
--- ask
What does SQLite print for this query? Type the number.

```sql
SELECT 3 / 4 * 100 AS pct;
```
--- answer
0
--- why
Division and multiplication are done left to right, so `3 / 4` comes first. Both are whole numbers, so it is integer division: 3 divided by 4 is 0, remainder 3. Then 0 times 100 is 0. Writing `3 * 100 / 4` gives 75, and `3.0 / 4 * 100` gives 75.0, because a decimal point on one side keeps the fraction.

+++ question | Everything except one satellite
--- ask
The `anomaly` table has three rows: one for OSP-02, one for HRN-01, and one whose `sat_id` is NULL because nobody knows yet which satellite it belongs to. You want every anomaly that is not OSP-02's, including the one that belongs to nobody yet. Which WHERE clause returns exactly those two rows?
--- choice
`WHERE sat_id <> 'OSP-02'`
--- choice
`WHERE NOT (sat_id = 'OSP-02')`
--- choice
`WHERE sat_id NOT IN ('OSP-02')`
--- choice correct
`WHERE sat_id IS DISTINCT FROM 'OSP-02'`
--- why
For the unattributed row, `sat_id <> 'OSP-02'` compares NULL with a value, which is UNKNOWN, and WHERE drops it. `NOT (UNKNOWN)` is still UNKNOWN, and `NOT IN` is the same `<>` test in disguise, so all three return only HRN-01's anomaly. `IS DISTINCT FROM` treats NULL as an ordinary value that is simply different from `'OSP-02'`, so it answers TRUE and keeps the row. `sat_id <> 'OSP-02' OR sat_id IS NULL` says the same thing in longer words.

+++ question | Three tenths in SQLite
--- ask
What does SQLite print for this query? Type the value exactly as it prints.

```sql
SELECT 0.1 + 0.2 = 0.3;
```
--- answer
0
false
--- why
It prints 0, SQLite's FALSE. SQLite has no exact decimal type: every number with a decimal point is an 8-byte binary float. 0.1 and 0.2 are each stored as the nearest binary number, and their sum is 0.30000000000000004, while the float nearest to 0.3 is a little smaller. PostgreSQL answers TRUE here, but only because it reads typed decimals as exact NUMERIC. Put the same values in REAL columns there and the test fails too. Compare floats with a range, or store the value exactly, as integer cents or counts.

+++ question | A wall clock turned into an instant
--- ask
In PostgreSQL, with the session's time zone set to `UTC`, you run:

```sql
SELECT TIMESTAMP '2026-04-10 06:00:00' AT TIME ZONE 'Asia/Tokyo';
```

Tokyo is 9 hours ahead of UTC. What does it print?
--- choice
`2026-04-10 15:00:00+00`
--- choice correct
`2026-04-09 21:00:00+00`
--- choice
`2026-04-10 06:00:00+09`
--- choice
`2026-04-10 06:00:00`
--- why
A plain TIMESTAMP is a wall-clock reading. `AT TIME ZONE 'Asia/Tokyo'` asks: "at what instant did clocks in Tokyo read 06:00 on 10 April?" Tokyo runs 9 hours ahead, so that instant is 9 hours earlier in UTC: 21:00 on 9 April. The result is a TIMESTAMPTZ, printed in the session's zone, UTC, so it ends in `+00`. Going the other way, a TIMESTAMPTZ `AT TIME ZONE 'Asia/Tokyo'` gives the Tokyo wall clock, and 15:00 would be the answer for an instant of 06:00 UTC. Mixing up the two directions is the classic mistake.

+++ question | Follow the rows through the stations
--- ask
A table `reading` has six rows:

```text
 sat_id | value
--------+-------
 A      |  0.9
 A      |  NULL
 B      |  0.4
 B      |  0.2
 B      |  NULL
 C      |  0.7
```

What does this query print? Type the `sat_id` and `n` with a space between, like `A 3`.

```sql
SELECT sat_id, COUNT(*) AS n
FROM reading
WHERE value < 0.8
GROUP BY sat_id
HAVING COUNT(*) >= 2
ORDER BY n DESC
LIMIT 1;
```
--- answer
B 2
B, 2
B,2
B | 2
B|2
--- why
Take the steps in logical order. WHERE drops A's 0.9 (not below 0.8) and both NULL rows, because `NULL < 0.8` is UNKNOWN. Three rows are left: B 0.4, B 0.2 and C 0.7. GROUP BY makes two piles: B with 2 rows, C with 1. HAVING keeps only B. SELECT computes `n` = 2, ORDER BY sorts one row, and LIMIT keeps it. `COUNT(*)` counted 2 for B, not 3, because the NULL row was already gone at step 2.

The profile showed text where a number belongs. SQLite keeps whatever it is given, whatever the declared type says, so check what the value column really holds.

Create the view `answer` with the columns `stored_as` and `n`: for each storage class that `typeof(v)` reports in the `sample` table, how many samples have it. Sort by `stored_as`.
--- starter

FROM sample;

--- solution
DROP VIEW IF EXISTS answer;
CREATE VIEW answer AS
SELECT typeof(v) AS stored_as, COUNT(*) AS n
FROM sample
GROUP BY typeof(v)
ORDER BY stored_as;

--- task
Someone asks: "Which spacecraft ran hot on 9 April 2026?" Answer it with the method, not a guess.

Create the view `answer` with the columns `craft_code`, `t_utc` and `temp_c`, listing every panel +X temperature sample that:

- was really measured, not suspect and not filled in on the ground;

+++ question | What the key says one row is
--- ask
A table you inherit is declared like this:

```sql
CREATE TABLE downlink_file (
    station TEXT    NOT NULL,
    sat_id  TEXT    NOT NULL,
    aos     TEXT    NOT NULL,
    file_no INTEGER NOT NULL,
    bytes   INTEGER,
    PRIMARY KEY (station, aos, file_no)
);
```

Which of these can the table **not** hold?
--- choice
Files 1 and 2 from the same pass of OSP-01 at Svalbard.
--- choice correct
File 1 from OSP-01 and file 1 from HRN-01, both at Svalbard, both passes starting at 06:00:00.
--- choice
File 1 from OSP-01 at Svalbard and file 1 from OSP-01 at Awarua, both passes starting at 06:00:00.
--- choice
File 1 from two different passes of OSP-01 at Svalbard, at 06:00:00 and at 07:35:00.
--- why
The key is the table's grain: one row is one file, from the pass that started at one instant at one station. `sat_id` is not in it. Two satellites whose passes start at the same instant at the same station would both need the key (Svalbard, 06:00:00, 1), and the second is refused. A station with two antennas can really do that, so this key is worth asking the designer about. Different file numbers, different stations or different start times all give different keys, so the other three are fine.

+++ problem | Battery triage for one hour
--- task
The `reading` table holds one row per reading: `sc_id`, `ts` (ISO text in UTC), `channel` and `value`. The channel `SOC` is the battery state of charge, a fraction from 0 to 1.

Create the view `answer` with the columns `sc_id`, `ts`, `value` and `state`, holding every `SOC` reading taken from `2026-05-02T14:00:00Z` (included) to `2026-05-02T15:00:00Z` (not included). The state is:

- `NO DATA` when the value is missing;
- `CRITICAL` below 0.25;
- `LOW` from 0.25 up to, but not including, 0.50;
- `OK` at 0.50 or more.

Sort the rows so the operator sees the worst first: all `CRITICAL` rows, then `NO DATA`, then `LOW`, then `OK`. Within each state, sort by `value`, lowest first, then by `sc_id`, then by `ts`.
--- starter
DROP VIEW IF EXISTS answer;
CREATE VIEW answer AS
SELECT sc_id, ts, value, 'OK' AS state
FROM reading;

SELECT * FROM answer;
--- solution
DROP VIEW IF EXISTS answer;
CREATE VIEW answer AS
SELECT sc_id,
       ts,
       value,
       CASE WHEN value IS NULL THEN 'NO DATA'
            WHEN value < 0.25  THEN 'CRITICAL'
            WHEN value < 0.50  THEN 'LOW'
            ELSE 'OK'
       END AS state
FROM reading
WHERE channel = 'SOC'
  AND ts >= '2026-05-02T14:00:00Z'
  AND ts <  '2026-05-02T15:00:00Z'
ORDER BY CASE WHEN value < 0.25  THEN 1
              WHEN value IS NULL THEN 2
              WHEN value < 0.50  THEN 3
              ELSE 4
         END,
         value, sc_id, ts;

SELECT * FROM answer;

+++ problem | A raw import, cleaned and summed
--- task
This problem has its own table, `raw_soc`, loaded from a station file with every field as text: `sc_id`, `ts`, `soc_text` and `temp_text`. In `soc_text`, an empty string `''` means the reading was dropped, and `'-1'` means the sensor was switched off: neither is a reading. In `temp_text` (degrees Celsius), a missing temperature is written as `''` or as `'N/A'`.

Create the view `answer` with exactly one row and five columns:

- `n_rows`: how many rows the table has.
- `n_soc`: how many real charge readings there are.
- `mean_soc`: the average of the real charge readings, as a number.
- `n_temp`: how many real temperature readings there are.
- `max_temp_c`: the highest real temperature, as a number.
--- schema
CREATE TABLE raw_soc (
    sc_id     TEXT NOT NULL,
    ts        TEXT NOT NULL,
    soc_text  TEXT NOT NULL,
    temp_text TEXT NOT NULL,
    PRIMARY KEY (sc_id, ts)
);
INSERT INTO raw_soc (sc_id, ts, soc_text, temp_text) VALUES
  ('LYR-04', '2026-05-02T14:00:00Z', '0.49', '20.5'),
  ('LYR-04', '2026-05-02T14:01:00Z', '',     '20.6'),
  ('LYR-04', '2026-05-02T14:02:00Z', '-1',   'N/A'),
  ('LYR-04', '2026-05-02T14:03:00Z', '0.47', ''),
  ('LYR-04', '2026-05-02T14:04:00Z', '0.45', '21.9'),
  ('LYR-04', '2026-05-02T14:05:00Z', '0.44', '19.8');
--- starter
DROP VIEW IF EXISTS answer;
CREATE VIEW answer AS
SELECT COUNT(*)                     AS n_rows,
       COUNT(soc_text)              AS n_soc,
       AVG(CAST(soc_text AS REAL))  AS mean_soc,
       COUNT(temp_text)             AS n_temp,
       MAX(temp_text)               AS max_temp_c

--- solution

       COUNT(NULLIF(NULLIF(soc_text, ''), '-1'))                      AS n_soc,
       AVG(CAST(NULLIF(NULLIF(soc_text, ''), '-1') AS REAL))          AS mean_soc,
       COUNT(NULLIF(NULLIF(temp_text, ''), 'N/A'))                    AS n_temp,
       MAX(CAST(NULLIF(NULLIF(temp_text, ''), 'N/A') AS REAL))        AS max_temp_c
FROM raw_soc;

+++ question | IN and NOT IN with a NULL
--- ask
Which one of these conditions is TRUE?
--- choice correct
`'LYR-02' IN ('LYR-02', NULL)`
--- choice
`'LYR-03' NOT IN ('LYR-02', NULL)`
--- choice
`'LYR-03' IN ('LYR-02', NULL)`

`NULL = NULL`

SQLite never raises an error on a bad cast. It converts as much of the text as looks like a number, the leading `7.9`, and drops the rest. (Text with no number at the front, such as `'abc'`, becomes 0.) PostgreSQL would stop with `invalid input syntax for type real`, which is the more useful answer: it tells you the data holds a unit where a number belongs. In SQLite, check with `typeof()` and clean text before you cast it.
