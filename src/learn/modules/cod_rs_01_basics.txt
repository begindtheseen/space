+++ question | A pinned toolchain
--- ask
Your default toolchain is stable 1.94.1. You clone a team's repository whose top folder holds this `rust-toolchain.toml`:

```toml
[toolchain]
channel = "1.90.0"
```

You run `cargo build` inside that folder. Which compiler builds the code?
--- choice
Stable 1.94.1, because it is your default and it is newer.
--- choice correct
Rust 1.90.0. rustup reads the file and uses that version for every command in the folder, installing it first if it is missing.
--- choice
Nightly, because a pinned version number is treated as an experimental build.
--- choice
None: Cargo stops with an error until you run `rustup default 1.90.0` by hand.
--- why
`rust-toolchain.toml` overrides your default for that folder. rustup reads it before `cargo` runs, and installs the named version if you do not have it yet. That is the point of the file: everyone who builds this repository, on any machine, gets the same compiler. Your default only applies in folders that do not pin one.

+++ question | A caret range on a young crate
--- ask
A `Cargo.toml` has this line under `[dependencies]`:

```toml
nalgebra = "0.33.1"
```

The published versions are 0.32.9, 0.33.0, 0.33.2, 0.34.0 and 1.0.0. There is no `Cargo.lock` yet. Which version does Cargo pick? Type the version number.
--- answer
0.33.2
v0.33.2
--- why
`"0.33.1"` is a caret requirement: at least 0.33.1, and below the next version that may break you. For a crate whose version starts with 0, the MINOR number is the breaking one, so the range is at least 0.33.1 and below 0.34.0. That rules out 0.32.9 and 0.33.0 (too old) and 0.34.0 and 1.0.0 (may break). Cargo picks the newest version left, 0.33.2, and writes it into `Cargo.lock`.

+++ question | Making release stop like the tests
--- ask
A function adds two `u16` values that arrive in a telemetry packet. In the dev build, a sum that is too big stops the program with "attempt to add with overflow". The build you ship, made with `cargo build --release`, carries on with a wrong, wrapped number instead. Which one line under `[profile.release]` in `Cargo.toml` makes the release build stop on overflow too?
--- choice
`opt-level = 0`
--- choice
`debug = true`
--- choice correct
`overflow-checks = true`
--- choice
`edition = "2024"`
--- why
Whether integer overflow is caught is its own profile setting, `overflow-checks`: on in `dev`, off in `release`. Turning the optimizer down (`opt-level = 0`) makes the program slower but does not turn the check on. `debug = true` only adds debug information for the debugger. The edition is a `[package]` setting and has nothing to do with overflow. The safest code avoids relying on either profile and uses `checked_add` or `wrapping_add`, but this line at least makes the shipped program behave like the one you tested.

+++ question | A function nobody asked for
--- ask
A workspace has three crates. `units` has an optional feature `imperial` that adds `units::altitude_ft`. `sim` depends on `units` with `features = ["imperial"]`. `gui` depends on `units` with no features, yet its `main.rs` calls `units::altitude_ft`.

Running `cargo build` at the top of the workspace, which builds all three, succeeds. Why, and what is the catch?
--- choice
`gui` gets every feature of `units` automatically, because they are in the same workspace. Nothing can go wrong.
--- choice correct
`units` is compiled once for the whole build, with the features any crate asked for, so `imperial` is on for `gui` too. Built on its own with `cargo build -p gui`, `gui` fails with "cannot find function `altitude_ft`".
--- choice
Features only affect release builds, so in the dev build every `#[cfg(feature = ...)]` item is compiled.
--- choice
`cargo build` ignores `#[cfg(feature = ...)]` lines unless `--features` is typed on the command line.
--- why
Features are unified: when one build needs a crate, it compiles it once with every feature any crate in that build asked for. So `gui` borrowed `sim`'s request by accident. Build `gui` alone and nobody asks for `imperial`, the function is never compiled, and the call breaks. This is why features must only add things, and why each crate should list the features it really uses.

+++ question | Two builds of the same commit
--- ask
Two engineers build the same git commit of a ground-station program and get programs that behave differently. `cargo tree`, which lists the exact dependency versions, shows `serde 1.0.210` on one machine and `serde 1.0.197` on the other. `Cargo.toml` says `serde = "1.0.150"`. The repository's `.gitignore` reads:

```text
/target
Cargo.lock
```

What is the mistake?
--- choice
`/target` should be committed so that both machines share the same compiled files.
--- choice
The requirement `"1.0.150"` is wrong; it should be `"1.0"` so that Cargo picks one version.
--- choice correct
`Cargo.lock` is ignored, so each machine chose its own newest allowed version. Commit `Cargo.lock` for a program you build and ship.
--- choice
serde versions 1.0.197 and 1.0.210 have different MAJOR numbers, so Cargo should have refused to build.

`"1.0.150"` allows anything from 1.0.150 up to below 2.0.0, so both versions fit the range. The file that records the one version actually chosen, with a checksum, is `Cargo.lock`. +++ question | A build server that catches everything

+++ question | Three ways to take 9 from 5
--- ask
What does this print?

```rust
fn main() {
    let level: u8 = 5;
    println!(
        "{} {} {:?}",
        level.saturating_sub(9),
        level.wrapping_sub(9),
        level.checked_sub(9)
    );
}
```
--- answer
0 252 None
--- why
$5 - 9 = -4$ does not fit in a `u8`, whose range is 0 to 255. `saturating_sub` sticks at the floor: 0. `wrapping_sub` adds $2^8 = 256$ until the answer fits: $-4 + 256 = 252$. `checked_sub` reports the overflow as `None`, which `{:?}` prints as `None`. The same three operations give the same three answers in every build profile.

+++ question | Wrapping below the floor
--- ask
What does this print?

```rust
fn main() {
    let x: i8 = -100;
    println!("{}", x.wrapping_sub(50));
}
```
--- answer
106
--- why
An `i8` holds $-128$ to $127$. The true answer, $-100 - 50 = -150$, is below $-128$. Wrapping adds $2^8 = 256$ until it fits: $-150 + 256 = 106$. A reading that should be very negative has turned into a large positive one, which is why wrapping is only right when rolling over is the documented behavior.

+++ question | Half of seven, doubled
--- ask
What happens with this program?

```rust
fn main() {
    println!("{}", 7 / 2 * 2.0);
}
```
--- choice
It prints `7`.
--- choice
It prints `6`.
--- choice
It prints `7.0`.
--- choice correct
It does not compile.
--- why
`7 / 2` is integer division of two whole numbers, which gives 3. Multiplying that integer by the decimal `2.0` would mix two number types, and Rust never converts between them by itself: the error is "cannot multiply `{integer}` by `{float}`". +++ question | A negative offset cast
--- ask
A calibration offset of $-1$ arrives as an `i32` and is cast to fit a `u8` field. What does this print?

```rust
fn main() {
    let offset: i32 = -1;
    println!("{}", offset as u8);
}
```
--- answer
255
--- why
`as` never fails; it keeps the low 8 bits, which is the same as wrapping into 0 to 255: $-1 + 256 = 255$. So a small negative correction silently becomes the largest possible value. When a value might not fit, `u8::try_from(offset)` returns an error instead of a wrong number, and the code has to deal with it.

+++ question | Fuel that came back
--- ask
This should subtract two burns, 120 kg and then 80 kg, from 500 kg and print 300. It prints `fuel left: 420 kg`.

```rust
fn main() {
    let mut fuel_kg = 500.0;
    {
        let fuel_kg = fuel_kg - 120.0; // first burn
    }
    fuel_kg -= 80.0; // second burn
    println!("fuel left: {fuel_kg} kg");
}
```

What is wrong?
--- choice
`-=` does not work on decimal numbers; the second burn needs `fuel_kg = fuel_kg - 80.0`.
--- choice correct
The `let` inside the braces makes a new variable that shadows `fuel_kg` until the closing brace. The outer `fuel_kg` never changes. The line should be `fuel_kg -= 120.0;`.
--- choice
The outer variable needs to be declared inside the braces as well, so that both burns happen in the same scope.
--- choice
`500.0` is inferred as an integer, so the subtraction of `120.0` is thrown away.
--- why
A `let` always makes a new variable, even with a name that already exists. Inside the braces, `fuel_kg` means the new one, holding 380; at the brace it disappears and the outer 500 is back. Then $500 - 80 = 420$. The compiler even warns that the inner variable is never used. To change a value, write a plain assignment (no `let`) to a `let mut` variable.

+++ question | A microsecond clock for a year
--- ask
A flight computer counts microseconds since power-on in an unsigned integer. The mission lasts one year, about $3.2 \times 10^{7}$ seconds, and the counter must never overflow. Which is the smallest type that is enough?
--- choice
`u16`
--- choice
`u32`
--- choice correct
`u64`
--- choice
`u128`
--- why
One year is about $3.2 \times 10^{7} \times 10^{6} = 3.2 \times 10^{13}$ microseconds. A `u32` holds up to $2^{32} - 1 \approx 4.3 \times 10^{9}$, which is only about $4295$ seconds, or 72 minutes of microseconds. A `u64` holds up to about $1.8 \times 10^{19}$, enough for about 585 000 years. `u128` also works but doubles the size for nothing. Work out $2^n$ against the longest run before choosing a counter's width.

+++ question | Bytes and characters in a delta-v label
--- ask
The Greek letter Δ takes 2 bytes in UTF-8. What does this print? Type the two numbers separated by a space.

```rust
fn main() {
    let s = "Δv=9.4";
    println!("{} {}", s.len(), s.chars().count());
}
```
--- answer
7 6
7, 6
7,6
--- why
The characters are Δ, v, =, 9, . and 4: six of them. Δ takes 2 bytes and each of the other five takes 1, so there are $2 + 5 = 7$ bytes. `.len()` counts bytes and `.chars().count()` counts characters. For the same reason `&s[0..1]` would panic: byte 1 is in the middle of Δ.

+++ question | One label function, four callers
--- ask
Here is a function and one owned `String`:

```rust
fn label_len(s: &str) -> usize {
    s.len()
}

let owned = String::from("STAGE 2");
```

Pick every call that compiles.
--- choice correct
`label_len("MECO")`
--- choice correct
`label_len(&owned)`
--- choice correct
`label_len(&owned[0..5])`
--- choice
`label_len(owned)`
--- why
A `&str` parameter takes any borrowed text: a literal, which is already a `&str`; a borrowed `String`, which Rust turns into a `&str` of the whole text by itself; and a slice of either. `label_len(owned)` hands over the `String` itself, which is not a borrow, so the compiler says "expected `&str`, found `String`" and suggests `&owned`. Had the parameter been `&String`, only `&owned` would work, which is why read-only text parameters take `&str`.

+++ question | Popping into a String
--- ask
What does this print?

```rust
fn main() {
    let mut stack = vec!["A", "B", "C"];
    let mut out = String::from(">");
    while let Some(s) = stack.pop() {
        out.push_str(s);
        out.push('-');
    }
    println!("{out}");
}
```
--- answer
>C-B-A-
--- why
`pop` takes from the end, so the items come out last in, first out: C, then B, then A. Each pass adds the item with `push_str` and one `'-'` with `push`. When the list is empty, `pop` returns `None`, the pattern `Some(s)` no longer matches, and the loop ends. The last dash stays, because nothing removes it.

+++ question | Cutting a microsecond
--- ask
The micro sign µ takes 2 bytes in UTF-8. What happens here?

```rust
fn main() {
    let t = "T+3µs";
    println!("{}", &t[0..4]);
}
```
--- choice
It prints `T+3µ`.
--- choice
It prints `T+3`, dropping the half of µ that does not fit.
--- choice correct
It compiles, then panics: byte 4 is in the middle of µ.
--- choice
It does not compile, because strings cannot be sliced.
--- why
Slice ranges count bytes. `T`, `+` and `3` are bytes 0, 1 and 2, and µ is bytes 3 and 4. The range `0..4` stops before byte 4, which would cut µ in half. Rust checks this while the program runs and panics with "byte index 4 is not a char boundary", rather than hand you half a character. `&t[0..3]` gives `T+3` and `&t[0..5]` gives `T+3µ`.

+++ question | A gain that is never returned
--- ask
This does not compile. What is wrong?

```rust
fn gain(n: u32) -> u32 {
    if n > 5 { 10 } else { 20 };
}
```
--- choice
An `if` cannot give back a value; you need `return 10;` and `return 20;`.
--- choice
The condition needs round brackets: `if (n > 5)`.
--- choice correct
The semicolon after the `if` turns its value into a statement and throws it away. The body then ends with no value, which is `()`, not a `u32`. Remove the semicolon.
--- choice
`10` and `20` are `i32` literals, which do not match the `u32` return type.
--- why
In Rust, `if` is an expression, and a function returns the value of its last expression when that expression has no semicolon. The semicolon turns the expression into a statement, so the function's body produces `()`, Rust's "nothing" value, and the compiler says "expected `u32`, found `()`", suggesting you remove the semicolon. The literals take their type from what is expected, so they become `u32`.

+++ question | Which loop does break leave?
--- ask
What does this print? Then what would it print if the outer loop were labeled `'outer:` and the `break` became `break 'outer`? Type the two numbers separated by a space.

```rust
fn main() {
    let mut count = 0;
    for a in 1..=4 {
        for b in 1..=4 {
            if b > a {
                break;
            }
            count += 1;
        }
    }
    println!("{count}");
}
```
--- answer
10 1
10, 1
10,1
--- why
A plain `break` leaves only the loop it is in. For each `a`, the inner loop counts `b` from 1 up to `a` and then stops, so `count` grows by 1, 2, 3 and 4: $1 + 2 + 3 + 4 = 10$. With `break 'outer`, the first time `b > a` happens (when `a` is 1 and `b` is 2) both loops end at once, after only one count.

+++ question | Speed bands
--- ask
What does this print?

```rust
fn class(v_m_s: u32) -> &'static str {
    match v_m_s {
        0 => "stopped",
        1..=340 => "subsonic",
        341..=1_700 => "supersonic",
        _ => "hypersonic",
    }
}

fn main() {
    println!("{} {} {}", class(340), class(341), class(7800));
}
```
--- answer
subsonic supersonic hypersonic
--- why
A range pattern with `..=` includes both ends, so 340 is the last value of `1..=340` and 341 the first of `341..=1_700`. 7800 fits none of the ranges and falls to the wildcard `_`. The arms are tried from top to bottom and the first that fits wins.

+++ question | Readings of three kinds
--- ask
What does this print?

```rust
enum Reading {
    Temp(f64),
    Pressure { kpa: f64 },
    Offline,
}

fn status(r: Reading) -> &'static str {
    match r {
        Reading::Temp(t) if t > 85.0 => "hot",
        Reading::Temp(_) => "ok",
        Reading::Pressure { kpa } if kpa < 10.0 => "vacuum",
        Reading::Pressure { kpa: _ } => "ok",
        Reading::Offline => "no data",
    }
}

fn main() {
    let all = [
        Reading::Temp(90.0),
        Reading::Temp(20.0),
        Reading::Pressure { kpa: 5.0 },
        Reading::Offline,
    ];
    for r in all {
        print!("{} ", status(r));
    }
}
```
--- answer
hot ok vacuum no data
--- why
Each pattern first checks the variant, then names the data inside, then the guard after `if` must also be true. `Temp(90.0)` fits the first arm. `Temp(20.0)` fails its guard and falls to `Temp(_)`. `Pressure { kpa: 5.0 }` passes the guard $5 < 10$. `Offline` carries nothing and fits its own arm. The unguarded arms for `Temp` and `Pressure` are what make the match cover every value.

+++ question | A counter that will not count
--- ask
What happens with this program?

```rust
struct Counter {
    hits: u32,
}

impl Counter {
    fn hit(&mut self) {
        self.hits += 1;
    }
    fn hits(&self) -> u32 {
        self.hits
    }
}

fn main() {
    let c = Counter { hits: 0 };
    c.hit();
    println!("{}", c.hits());
}
```
--- choice
It prints `1`.
--- choice
It prints `0`, because `hit` changed a copy.
--- choice correct
It does not compile: `hit` takes `&mut self`, and `c` was not declared `mut`.
--- choice
It does not compile: a method cannot have the same name as a field.

`c.hit()` means `Counter::hit(&mut c)`, a mutable borrow, and you can only borrow a variable mutably if it was declared with `let mut`. +++ question | Almost every byte

```rust
fn band(n: u8) -> &'static str {
```

+++ question | The limit that never fires
--- ask
`check(90.0)` should return `"too hot"`, but it returns `"warm"`. The compiler gives no warning.

```rust
fn check(temp_c: f64) -> &'static str {
    match temp_c {
        t if t > 60.0 => "warm",
        t if t > 85.0 => "too hot",
        _ => "ok",
    }
}
```

What is wrong?
--- choice
`t` is a copy of `temp_c`, so the second guard compares an old value.
--- choice correct
The arms are tried in order, and 90 is already above 60, so the first arm wins. Put the `> 85.0` arm first. The compiler cannot warn, because it does not work out what guards will do.
--- choice
Guards only work on integers, so the float comparisons are skipped.
--- choice
A `match` on an `f64` always takes the first arm that has a guard.
--- why
The first arm that fits runs. Every value above 85 is also above 60, so the second arm can never be reached. For patterns without guards, such as a `_` placed first, the compiler spots the unreachable arm and warns. A guard is an arbitrary condition, though, so the compiler does not reason about it, and the order is up to you.

+++ question | States with no meaning
--- ask
Compare two ways to store a throttle:

```rust
enum Throttle {
    Off,
    On(u8),
}

struct ThrottleBox {
    on: bool,
    level: u8,
}
```

`ThrottleBox` can hold states such as "off, at level 40", which mean nothing. How many more possible values does `ThrottleBox` have than `Throttle`? Type a number.
--- answer
255
--- why
The enum has $1 + 256 = 257$ values: `Off`, or `On` with one of 256 levels. The struct has $2 \times 256 = 512$: every combination of `on` and `level`. Its 256 "off" states all mean the same thing as `Off`, so 255 of them are extra, and every piece of code that reads a `ThrottleBox` has to decide what they mean. $512 - 257 = 255$. +++ question | Building a packet from outside
--- ask
What happens when this is compiled?

```rust
mod telemetry {
    pub struct Packet {
        pub id: u16,
        crc: u32,
    }

    impl Packet {
        pub fn new(id: u16) -> Packet {
            Packet { id, crc: 0 }
        }
    }
}

fn main() {
    let p = telemetry::Packet { id: 7, crc: 0 };
    println!("{}", p.id);
}
```
--- choice
It compiles and prints 7: the struct is `pub`, so all of it is public.
--- choice correct
It does not compile: `crc` is private, so code outside `telemetry` cannot build a `Packet` with braces. It has to call `telemetry::Packet::new(7)`.
--- choice
It compiles, because `main` only reads `id`, which is `pub`; private fields are only checked when they are read.
--- choice
It does not compile, because `main` needs `use telemetry::Packet;` first.
--- why
`pub struct` makes the type public, but each field needs its own `pub`. Building a struct with braces means giving every field a value, and you cannot name a private field from outside the module, so the error is "field `crc` of struct `Packet` is private". That is how a module guards an invariant, such as a correct checksum: the only way in is its own `new`. A full path like `telemetry::Packet` needs no `use`.

+++ question | A slice of a slice
--- ask
What does this print?

```rust
fn main() {
    let a = [10, 20, 30, 40, 50, 60];
    let s = &a[1..4];
    println!("{} {:?} {:?}", s.len(), s.get(3), &s[1..]);
}
```
--- answer
3 None [30, 40]
3 None [30,40]
--- why
`&a[1..4]` takes positions 1, 2 and 3 of `a`, so `s` is `[20, 30, 40]`, with length $4 - 1 = 3$. Positions in `s` count from its own start, so `s.get(3)` asks for a fourth element that does not exist and gives `None` instead of panicking. `&s[1..]` is `s` from its position 1 on: `[30, 40]`.

+++ question | Counting events in order
--- ask
What does this print?

```rust
use std::collections::BTreeMap;

fn main() {
    let events = ["ARM", "FIRE", "ARM", "SAFE", "ARM"];
    let mut counts: BTreeMap<&str, u32> = BTreeMap::new();
    for e in events {
        *counts.entry(e).or_insert(0) += 1;
    }
    for (k, v) in &counts {
        print!("{k}={v} ");
    }
}
```
--- answer
ARM=3 FIRE=1 SAFE=1
--- why
`entry(e).or_insert(0)` finds the slot for `e`, puts 0 there the first time, and hands back a mutable reference, which `+= 1` bumps. ARM arrives three times, FIRE and SAFE once each. A `BTreeMap` keeps its keys sorted, so the loop visits them in alphabetical order on every run. With a `HashMap` the counts would be the same, but the order could change from run to run.

+++ question | Zeroing through a read-only view
--- ask
This does not compile. The function should set the first `n` elements to zero.

```rust
fn zero_first(xs: &[f64], n: usize) {
```

--- choice correct

--- choice

+++ question | A time range in a log
--- ask
What does this print? Type it exactly.

```rust
use std::collections::BTreeMap;

fn main() {
    let mut log = BTreeMap::new();
    for (t, p) in [(300, 9.1), (100, 2.0), (250, 7.7), (400, 9.4)] {
        log.insert(t, p);
    }
    let n = log.range(100..300).count();
    let first = log.range(260..).next();
    println!("{n} {:?}", first);
}
```
--- answer
2 Some((300, 9.1))
2 Some((300,9.1))
--- why
A `BTreeMap` keeps its keys sorted: 100, 250, 300, 400, whatever order they went in. `100..300` includes 100 and stops before 300, so it holds 100 and 250: a count of 2. `260..` starts at the first key of at least 260, which is 300. `next` wraps that entry in an `Option`, because a range can be empty. A `HashMap` has no order, so it could not answer "everything from 260 on" without checking every key.

+++ question | What text operations cost
--- ask
`text` is a `String` holding $n$ bytes. What do `text.len()`, `text.chars().count()` and `&text[10..20]` cost, in that order?
--- choice correct
$O(1)$, $O(n)$, $O(1)$
--- choice
$O(1)$, $O(1)$, $O(1)$: a `String` stores its character count beside its length.
--- choice
$O(1)$, $O(n)$, $O(n)$: a slice copies the bytes it covers.
--- choice
$O(n)$, $O(n)$, $O(n)$: every string operation walks the text.
--- why
A `String` stores its length in bytes, so `len` just reads it. It does not store a character count, and UTF-8 characters take 1 to 4 bytes, so counting them means walking every byte. That is also why Rust gives no `text[i]` for the i-th character: finding it would be $O(n)$.

+++ question | A gain captured by move
--- ask
What number does `scale(3.0)` return here?

```rust
fn main() {
    let mut gain = 2.0;
    let scale = move |x: f64| x * gain;
    gain = 10.0;
    println!("{}", scale(3.0));
}
```
--- answer
6
6.0
--- why
`move` makes the closure take its own copy of `gain` at the moment the closure is made, while `gain` is 2.0. An `f64` is copied, not given away, so the outer `gain` can still be changed. Setting it to 10.0 afterwards changes only the outer variable, and the closure still has 2.0: $3 \times 2 = 6$. Without `move`, the closure would borrow `gain`, and the assignment while it is borrowed would not compile.

+++ question | Clippy on the build server
--- ask
The build server runs `cargo fmt --check`, then `cargo clippy -- -D warnings`, then `cargo test`. A pull request adds these two correctly formatted functions:

```rust
    xs.iter().sum()
}
```

What happens?
--- choice
Every step passes: both functions compile, and no test covers them.
--- choice correct
The clippy step fails: `3.1416` trips `approx_constant`, which is an error by default, and `-D warnings` also turns the `ptr_arg` warning about `&Vec<f64>` into an error.

+++ question | An average of percentages
--- ask
What happens when `mean_pct(&[90, 95, 80])` runs in a debug build?

```rust

    let total: u8 = xs.iter().sum();
    total / xs.len() as u8
}
```
--- choice
It returns 88, the mean rounded down.
--- choice
It returns 3.
--- choice correct

+++ question | A command line from the ground
--- ask
What does `classify("  THR 150\n")` return? Type the text.

```rust
fn classify(cmd: &str) -> String {
    let cmd = cmd.trim();
    match cmd.split_once(' ') {
        Some(("THR", v)) => match v.parse::<u8>() {
            Ok(p) if p <= 100 => format!("throttle {p}"),
            Ok(p) => format!("reject {p}"),
            Err(_) => String::from("bad"),
        },
        Some((other, _)) => format!("unknown {other}"),
        None => format!("single {cmd}"),
    }
}
```
--- answer
reject 150
--- why
The shadowing `let` replaces `cmd` with a trimmed view, `"THR 150"`, with no spaces around it and no newline. `split_once(' ')` gives `Some(("THR", "150"))`, which fits the first arm, with `v` = `"150"`. 150 fits in a `u8`, so the parse is `Ok(150)`. The guard $150 \le 100$ is false, so the next arm, `Ok(p)`, gives "reject 150". Without the `trim`, the leading spaces would make `split_once` split at the first space, giving an empty first part, and the result would be "unknown ".

+++ question | A benchmark in the wrong build
--- ask
A teammate times an iterator chain against a hand-written index loop that does the same work, using `cargo run`. The iterator version takes twice as long, so they propose banning iterators from flight code. What is the right reply?

+++ question | Counting packets per channel
--- ask
The compiler rejects this:

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
struct Channel {
    id: u8,
    gain: f64,
}
```

You want to count packets per channel in a `HashMap`. What is the best fix?
--- choice
Keep the derive line and write `impl Eq for Channel {}` by hand, so `Channel` can be the key.
--- choice
Use a `BTreeMap<Channel, u32>` instead, since a `BTreeMap` does not hash its keys.
--- choice correct
Derive only `Debug, Clone, Copy, PartialEq` for `Channel`, and key the map by the channel's `id`: `HashMap<u8, u32>`.
--- choice
Remove `Copy`, which is what stops `Eq` and `Hash` from being derived.

+++ question | A lock file and an update
--- ask
`Cargo.toml` has `hifitime = "3.8"`. The committed `Cargo.lock` pins 3.8.2. Since then, 3.8.5, 3.9.0 and 4.0.0 have been published. Which version does `cargo build` use now, and which one after `cargo update`? Type the two versions separated by a space.

3.8.2 3.9.0

3.8.2,3.9.0
