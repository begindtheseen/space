+++ question | What docker diff reports for an edited file
--- ask
The image `gnc-sim:2.0` contains the file `/etc/sim.conf`, added in its second layer. You start a container named `edit` from it, and the container appends one line to that file, then exits:

```bash
docker run --name edit gnc-sim:2.0 sh -c 'echo "cases = 500" >> /etc/sim.conf'
docker diff edit
```

What does `docker diff edit` print?
--- choice
`A /etc/sim.conf`
--- choice
`D /etc/sim.conf` and then `A /etc/sim.conf`
--- choice
Nothing, because the line was written into the image's second layer.
--- choice correct
`C /etc` and `C /etc/sim.conf`
--- why
The file already existed in the image, so it was changed, not added: `C`. Its folder `/etc` also shows `C`, because something inside it changed. Behind the scenes the union filesystem copied the whole file up into the container's writable layer and edited the copy (copy-on-write). The second layer still holds the old file, untouched, and every new container from `gnc-sim:2.0` sees the old version. `A` would mean a path the image never had, and `D` a path the container removed.

+++ question | A time step that comes back
--- ask
An image has two layers that both hold `/etc/sim.conf`. The lower layer's copy reads `dt = 0.1`; the upper layer's copy reads `dt = 0.05`. You run:

```bash
docker run --name a gnc-sim:2.1 sh -c 'echo "dt = 0.02" > /etc/sim.conf'
docker rm a
docker run --rm gnc-sim:2.1 cat /etc/sim.conf
```

What does the last command print?
--- answer
dt = 0.05
dt=0.05
0.05
--- why
Two rules decide it. First, the top layer wins: of the two read-only copies, a container sees the upper one, `dt = 0.05`. Second, the edit to `dt = 0.02` went into container `a`'s writable layer only, and `docker rm a` destroyed that layer. The new container starts with a fresh, empty writable layer over the unchanged image, so it sees `dt = 0.05` again. The lower copy, `dt = 0.1`, is still stored in the image, hidden under the upper one.

+++ question | The virtual size of a container
--- ask
`docker history` for an image lists these layers, newest at the top:

```text
CREATED BY                                                    SIZE
CMD ["python3", "/app/run.py"]                                0B
RUN /bin/sh -c rm /data/raw.bin                               0B
COPY run.py /app/                                             12.3kB
RUN /bin/sh -c mkdir /data && head -c 250000000 /dev/urandom… 250MB
RUN /bin/sh -c set -eux; … (installs Python)                  41.4MB
# debian.sh --arch 'amd64' out/ 'trixie' …                    87.6MB
```

A container from this image has written 4 MB of logs, and `docker ps -s` shows its size as `4MB (virtual … MB)`. What is the virtual size, in megabytes, to the nearest whole number?
--- answer
383
383 MB
383MB
383.0
383.0 MB
383.0MB
--- why
The virtual size is the writable layer plus every image layer underneath: $87.6 + 41.4 + 250 + 0.0123 + 4 \approx 383$ MB. The trap is the `rm /data/raw.bin` row. It added only a whiteout marker, 0 B, and could not take anything away from the 250 MB layer below it, which is read-only. The container cannot see `/data/raw.bin`, yet the image still stores and ships all 250 MB of it.

+++ question | The kernel version on a Mac
--- ask
On a MacBook with Docker Desktop installed, you run:

```bash
docker run --rm debian:bookworm-slim uname -r
```

Which kernel version does it print?
--- choice
The version of macOS's own kernel, because a container shares its host's kernel.
--- choice
The kernel that Debian 12 ships, because the image is Debian 12.
--- choice correct
The version of the Linux kernel running inside Docker Desktop's small hidden virtual machine.
--- choice
Nothing: containers cannot run on macOS, so the command fails.
--- why
A container has no kernel of its own; it runs on whatever Linux kernel is underneath it. An image only brings the files above the kernel, so Debian's own kernel version never appears. A Linux container needs a Linux kernel, and macOS's kernel is not Linux, so Docker Desktop runs a small hidden Linux virtual machine and starts every container inside it. `uname -r` therefore reports that virtual machine's kernel.

+++ question | Shrinking an image from inside a container
--- ask
The image `wind-db:3` is 1.9 GB, most of it a raw wind archive in `/opt/archive`. To make it smaller, a colleague runs:

```bash
docker run -d --name tidy wind-db:3 sleep 600
docker exec tidy rm -rf /opt/archive
docker images wind-db
```

The image is still 1.9 GB. Why?
--- choice
`docker images` shows a stale size; it updates after the container stops.
--- choice
`rm` inside a container needs `sudo`, so nothing was deleted.
--- choice correct
The deletion happened in the container's writable layer. The image's layers are read-only and never change, so the image cannot shrink; the container's layer only gained whiteout markers.
--- choice
The image shrinks only when the container `tidy` is removed with `docker rm`.
--- why
An image is immutable. Everything a container does, including deleting, is recorded in its own writable layer: here, whiteout markers that hide `/opt/archive` from that one container. The 1.9 GB still sits in the image's layers, and every other container from `wind-db:3` still sees the archive. Removing the container throws the whiteouts away and changes nothing else. The only way to a smaller image is to build a new one that never contained the archive.

+++ question | A Monte Carlo that stopped with 137
--- ask
You start a dispersion run with a memory cap:

```bash
docker run --name mc --memory 512m mc-image:1.0 --cases 200000
```

After a minute, `docker ps -a` shows `Exited (137)`. The program has no bug, but it needs about 2 GB for this many cases. What happened?
--- choice
The container's pid namespace ran out of process numbers, so the program could not continue.
--- choice correct
The control group (cgroup) that Docker set up capped memory at 512 MB. When the program went over, the kernel killed it with SIGKILL, and 137 is 128 + 9, the code for death by signal 9.
--- choice
The image is corrupt: exit code 137 means a layer failed its digest check.
--- choice
The writable layer filled up, because a container can only store 512 MB of files.
--- why
Namespaces decide what a process can see; cgroups decide how much it can use. `--memory 512m` puts the process in a control group with a 512 MB memory budget, and the kernel enforces it by killing the process outright. A shell reports a process killed by signal N as exit code 128 + N, so SIGKILL (9) gives 137. The fix is a larger cap or fewer cases per run, not a different image.

+++ question | The status server on another port
--- ask
The image `status:0.1.0` ends with:

```dockerfile
ENTRYPOINT ["python3", "-m", "http.server"]
CMD ["8000"]
```

You start it with:

```bash
docker run -d status:0.1.0 9000 --bind 127.0.0.1
```

Type the full command the container runs.
--- answer
python3 -m http.server 9000 --bind 127.0.0.1
--- why
The container runs the `ENTRYPOINT` followed by the arguments. Arguments typed after the image name replace the whole `CMD`, so `8000` is gone and `9000 --bind 127.0.0.1` takes its place, while `python3 -m http.server` stays. The default port only applies when you type no arguments at all.

+++ question | Which values reach the container
--- ask
Here is a Dockerfile:

```dockerfile
FROM python:3.12-slim
ARG MODEL=j2
ENV GRAVITY_MODEL=${MODEL}
ARG CASES=100
RUN echo "$MODEL $CASES" > /build.txt
CMD ["sh", "-c", "echo $GRAVITY_MODEL $MODEL $CASES; cat /build.txt"]
```

You build it with `docker build -t grav --build-arg CASES=5000 .` and run `docker run --rm grav`. What are the two lines it prints?
--- choice
`j2 j2 5000`, then `j2 5000`
--- choice correct
`j2`, then `j2 5000`
--- choice
`j2`, then `j2 100`
--- choice
An empty line, then `j2 5000`
--- why
Build arguments exist only while the image is being built. The `RUN` step saw `MODEL=j2` (the default) and `CASES=5000` (from `--build-arg`), and froze `j2 5000` into `/build.txt`. At run time neither `MODEL` nor `CASES` is set, so the shell drops them and `echo` prints only `$GRAVITY_MODEL`, which is `j2`: the `ENV` line copied the argument's value into the image, and `ENV` values survive into every container.

+++ question | A user id the folder does not trust
--- ask
Your host account is uid 1000. The folder `results` on the host belongs to you, and `ls -ld results` shows `drwxr-xr-x`. The Dockerfile of the image `mc:2.0` contains:

```dockerfile
RUN useradd --uid 1001 --create-home sim
USER sim
```

You run `docker run --rm -v "$PWD/results:/out" mc:2.0`, and the program tries to write `/out/run1.csv`. What happens?
--- choice
The file is written, owned by uid 1001 on the host.
--- choice
The file is written, owned by uid 1000, because the folder belongs to uid 1000.
--- choice correct
The write fails with "Permission denied": to the host folder, uid 1001 is "others", and others have only read and execute permission.
--- choice
The file is written, owned by root, because Docker's daemon runs as root.
--- why
A bind mount is the host's own folder, so the host's permission rules apply to the container process's uid, a plain number. `drwxr-xr-x` gives write permission to the owner, uid 1000, only. Uid 1001 is not the owner and not in the group, so it falls under "others", who may list the folder but not create files in it. Matching the uid (`useradd --uid 1000`) or running with `--user "$(id -u):$(id -g)"` fixes it.

+++ question | Flags for an image with only a CMD
--- ask
An image was built from:

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY apogee.py .
CMD ["python3", "apogee.py", "--alt", "3000", "--speed", "250"]
```

It has no `ENTRYPOINT`. What happens when you run `docker run --rm apogee:cmdonly --alt 1000 --speed 300`?
--- choice
It runs `python3 apogee.py --alt 1000 --speed 300`.
--- choice
It runs `python3 apogee.py --alt 3000 --speed 250 --alt 1000 --speed 300`.
--- choice
It ignores the flags and prints the default apogee, 6187 m.
--- choice correct
It fails: the flags replace the whole `CMD`, so Docker tries to start a program called `--alt`, which does not exist.
--- why
With no `ENTRYPOINT`, the `CMD` is the entire command, program included. Arguments after the image name replace all of `CMD`, so the command becomes `--alt 1000 --speed 300`, and Docker reports that the executable `--alt` cannot be found. This is exactly why the tool belongs in `ENTRYPOINT` and only its default flags in `CMD`: then typed flags replace the flags and the program stays.

+++ question | A health check that always fails
--- ask
A team adds this line to the status-page image from the lesson, which is built `FROM python:3.12-slim`:

```dockerfile
HEALTHCHECK --interval=10s --timeout=3s --retries=3 \
  CMD ["curl", "-f", "http://localhost:8000/"]
```

The page loads fine in a browser, yet `docker ps` soon shows `(unhealthy)` and stays that way. What is the bug?
--- choice
`--retries=3` is too few; a server needs at least 10 tries to report healthy.
--- choice correct
The slim image has no `curl`. The test command cannot even start, which counts as a failure every time, so after three in a row the container is marked unhealthy.
--- choice
A `HEALTHCHECK` cannot use `localhost`; it must use the host's address.
--- choice
The `CMD` inside `HEALTHCHECK` replaced the container's own `CMD`, so the server never started.
--- why
Docker runs the health test inside the container, with only the programs the image contains. Any non-zero result counts as a failure, including "program not found". The slim Python image has no `curl`, which is why the lesson's check fetched the page with a one-line Python script instead. The `CMD` inside a `HEALTHCHECK` line is only the test; it does not touch the container's own `CMD`, which is why the page still loads.

+++ question | The one Dockerfile that meets every requirement
--- ask
You need an image for `mc.py` that meets four requirements:

1. `docker run mc:1.0` runs `python3 /app/mc.py --cases 100`.
2. `docker run mc:1.0 --cases 5 --seed 3` runs `python3 /app/mc.py --cases 5 --seed 3`.
3. The program runs as uid 1000.
4. The program reads its version from the environment variable `MC_VERSION`, set at build time with `--build-arg MC_VERSION=1.0`.

Each file starts with `FROM python:3.12-slim`, `WORKDIR /app` and `COPY mc.py .`. The rest:

```dockerfile
# A
ARG MC_VERSION=dev
RUN useradd --uid 1000 sim
USER sim
ENTRYPOINT ["python3", "/app/mc.py"]
CMD ["--cases", "100"]

# B
ARG MC_VERSION=dev
ENV MC_VERSION=${MC_VERSION}
USER sim
RUN useradd --uid 1000 sim
ENTRYPOINT ["python3", "/app/mc.py"]
CMD ["--cases", "100"]

# C
ARG MC_VERSION=dev
ENV MC_VERSION=${MC_VERSION}
RUN useradd --uid 1000 sim
USER sim
ENTRYPOINT python3 /app/mc.py --cases 100

# D
ARG MC_VERSION=dev
ENV MC_VERSION=${MC_VERSION}
RUN useradd --uid 1000 sim
USER sim
ENTRYPOINT ["python3", "/app/mc.py"]
CMD ["--cases", "100"]
```

Which one meets all four?
--- choice
A
--- choice
B
--- choice
C
--- choice correct
D
--- why
A never copies the build argument into an `ENV`, so `MC_VERSION` is gone when the container runs (requirement 4). B switches to `sim` before the user exists, so the `useradd` step runs as a user that is not there and the build fails; only root may add users anyway. C uses the shell form, which Docker runs as `/bin/sh -c "…"`, so arguments typed after the image name are ignored (requirement 2). D does each thing in the right order: argument into `ENV`, create the user as root, switch to it, the tool in exec-form `ENTRYPOINT`, and its default flags in `CMD`.

=== ops01-l03 | Practice: Fast rebuilds and slim images

+++ question | An edit to the data folder
--- ask
A telemetry replay image is built from:

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY data/ ./data/
COPY src/ ./src/
ENTRYPOINT ["python3", "src/replay.py"]
```

The build log numbers six steps, from `[1/6] FROM` to `[6/6] COPY src/ ./src/`. After one full build, you edit only `data/wind_profile.csv` and build again. How many of the six steps run again instead of showing `CACHED`?
--- answer
2
two
--- why
`FROM`, `WORKDIR`, `COPY requirements.txt` and the `pip install` are unchanged and sit below the edit, so they come from the cache. `COPY data/` misses, because the checksum of the files it copies changed. Then the cascade: `COPY src/` runs again even though nothing in `src/` changed, because its parent layer is new. That makes 2. The install step stays cached because it sits below the data copy, which is the whole point of the ordering.

+++ question | A build id that does not change
--- ask
Here is a Dockerfile:

```dockerfile
FROM python:3.12-slim
RUN python3 -c "import secrets; print(secrets.token_hex(4))" > /build_id
ENTRYPOINT ["cat", "/build_id"]
```

You build it as `stamp:1`, and `docker run --rm stamp:1` prints `5e0c9a1f`. Without changing any file, you run `docker build -t stamp:1 .` again on the same machine, then `docker run --rm stamp:1`. What does it print?
--- choice
A new random id, because a `RUN` step runs again on every build.
--- choice
`5e0c9a1f` again, but only if you add `--no-cache` to the build.
--- choice
A new random id, because `ENTRYPOINT` runs the `RUN` step again when the container starts.
--- choice correct
`5e0c9a1f` again, because the `RUN` step's text and parent layer are unchanged, so the build reuses the cached layer.
--- why
The cache decides by the instruction's text and its parent layer; it never runs a step to see whether the result would differ. Same text, same parent, so the old layer, with the old id in it, is reused. `docker build --no-cache` is what forces the step to run and draw a new id. The same effect is why an unpinned `pip install` stays at last month's versions on a machine with a warm cache, while a fresh build machine gets today's.

+++ question | Results files and a notes file
--- ask
A project uses this order (version A from the lesson):

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY . .
RUN pip install --no-cache-dir -r requirements.txt
ENTRYPOINT ["python3", "dispersion.py"]
```

Its `.dockerignore` contains the line `results/`. You make two changes, rebuilding after each: first a simulation run writes three new files into `results/`; then you edit `notes.md` in the project folder. What happens to the `pip install` step?
--- choice correct
It stays cached after the new results, because ignored files never reach the build context; it runs again after the `notes.md` edit, because that file changes what `COPY . .` copies.
--- choice
It runs again both times, because both changes are inside the project folder.
--- choice
It stays cached both times, because `requirements.txt` did not change.
--- choice
It runs again after the new results, because the context got bigger; it stays cached after the `notes.md` edit, because Markdown files are skipped.
--- why
`.dockerignore` removes paths from the build context before anything is sent, so the results files cannot affect `COPY . .` at all. `notes.md` is not ignored, so editing it changes the checksum of what `COPY . .` copies, the step misses, and the install above it in the cascade runs again. The cache does not know the install only reads `requirements.txt`; the lasting fix is to copy the manifest and install before `COPY . .`.

+++ question | Which edit breaks the copy's cache
--- ask
A Dockerfile has the step `COPY src/ ./src/`. After a full build, you make one of these changes and rebuild. Which one makes that step miss the cache?
--- choice
`touch src/main.py`, which updates the file's modification time and nothing else.
--- choice correct
`chmod +x src/run.sh`, which makes the script executable without changing its contents.
--- choice
`git commit` of the files in `src/`, which records them in `.git` but leaves them unchanged.
--- choice
Editing `README.md` at the top of the project, outside `src/`.
--- why
The checksum behind a `COPY` covers each file's contents, name and permissions, but not its modification time. `chmod +x` changes the permissions, so the step misses even though no byte of the script changed. `touch` changes only the time, a commit changes only `.git`, which is outside `src/`, and `README.md` is not part of this copy at all.

+++ question | Built fine, missing a file at run time
--- ask
A project's `.dockerignore` reads:

```text
.git
results/
data/
```

The `data/` line was added to keep 3 GB of raw flight logs out of the build. The Dockerfile ends with `COPY . .`, and the build succeeds. But the container stops at once with `FileNotFoundError: data/atmosphere.csv`, a 40 kB table the simulation needs. What is wrong?
--- choice
`COPY` cannot copy `.csv` files, so the table must be added with `RUN`.
--- choice
The container runs as a non-root user that may not read `data/`.
--- choice
The file was copied, but a later layer deleted it with a whiteout.
--- choice correct
`data/` in `.dockerignore` removed the whole folder from the build context, including the table, and `COPY . .` silently copies only what the context holds.
--- why
The builder only ever sees the build context, and `.dockerignore` decides what the context holds. `COPY . .` copies "everything that was sent", so an ignored file is not an error, it is simply absent. Narrow the pattern to what really should stay out, such as `data/raw/`, or add an exception line after it, `!data/atmosphere.csv`. Then run the final image once before trusting it.

+++ question | A C++ edit in a two-stage build
--- ask
A project builds a C++ propagator and ships it with a Python analysis layer:

```dockerfile
FROM gcc:14 AS build
WORKDIR /src
COPY cpp/ .
RUN g++ -O2 -o propagate propagate.cpp

FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY --from=build /src/propagate /usr/local/bin/propagate
COPY analysis/ ./analysis/
ENTRYPOINT ["python3", "analysis/run.py"]
```

After one full build, you edit `cpp/propagate.cpp` so that it prints one more column, and rebuild. Which steps run again?
--- choice
Only the build stage's `COPY cpp/ .` and `RUN g++`; the final stage comes from the cache, because it is a separate stage.
--- choice correct
The build stage's `COPY cpp/ .` and `RUN g++`, then the final stage's `COPY --from=build` and `COPY analysis/`. The `pip install` stays cached.
--- choice
Every step of the final stage, including `pip install`, because the stage it copies from changed.
--- choice
The build stage's two steps and the final stage's `COPY --from=build`; `COPY analysis/` stays cached because `analysis/` did not change.
--- why
Each stage has its own chain of layers. In the final stage, `WORKDIR`, `COPY requirements.txt` and `pip install` depend only on their own parents, which did not change, so they are cached. `COPY --from=build` copies a new program, so it misses, and from there the cascade reruns `COPY analysis/` too, because its parent layer is new. Putting the cross-stage copy below the slow install is what keeps a C++ edit from reinstalling the Python packages.

+++ question | Where a wheel fits
--- ask
A wheel is named:

```text
h5py-3.16.0-cp312-cp312-musllinux_1_2_aarch64.whl
```

`aarch64` is the name Linux uses for 64-bit ARM processors. On which of these would pip install it?
--- choice
`python:3.12-slim` on an x86-64 server.
--- choice
`python:3.12-alpine` on an x86-64 server.
--- choice correct
`python:3.12-alpine` on a 64-bit ARM machine.
--- choice
`python:3.12-slim` on a 64-bit ARM machine.
--- choice
`python:3.13-alpine` on a 64-bit ARM machine.
--- why
Every field of the label has to fit. `cp312` needs CPython 3.12, which rules out 3.13. `musllinux_1_2` needs musl 1.2 or newer, which only the Alpine images have; the slim images carry glibc, and a musllinux wheel is never on their list. `aarch64` needs a 64-bit ARM processor, which rules out the x86-64 servers.

+++ question | A glibc program on Alpine
--- ask
To make the image as small as possible, a teammate changes the final stage of a two-stage C++ build:

```dockerfile
FROM gcc:14 AS build
WORKDIR /src
COPY src/ .
RUN g++ -O2 -o period period.cpp

FROM alpine:3.22
COPY --from=build /src/period /usr/local/bin/period
ENTRYPOINT ["period"]
```

The build succeeds and `ls -l /usr/local/bin/period` inside the image shows the file. But starting the container fails at once with `exec /usr/local/bin/period: no such file or directory`. Why?
--- choice
`COPY --from` lost the file's execute permission.
--- choice
Alpine cannot run C++ programs.
--- choice correct
The program was compiled in a Debian image against glibc. Alpine has only musl, so the glibc loader and libraries the program asks for do not exist there.
--- choice
The `ENTRYPOINT` must give the full path `/usr/local/bin/period`.
--- why
A compiled program records which C library it was built against and which loader should start it; for a glibc program that loader is a file like `/lib64/ld-linux-x86-64.so.2`. Alpine has none of those files, so the kernel cannot start the program, and the "no such file" in the message is about the missing loader, not the program. Use a final stage on the same distribution release as the build stage, here `debian:trixie-slim`.

+++ question | Which direction breaks
--- ask
Glibc keeps old interfaces working in newer versions. Debian 12 ("bookworm") has glibc 2.36; Debian 13 ("trixie") has glibc 2.41. Which of these combinations fails?
--- choice
A wheel tagged `manylinux_2_28_x86_64` installed on bookworm.
--- choice correct
A program compiled on trixie, copied into a `debian:bookworm-slim` final stage and run there.
--- choice
A program compiled on bookworm, copied into a `debian:trixie-slim` final stage and run there.
--- choice
A wheel tagged `manylinux_2_17_x86_64` installed on trixie.
--- why
Building against an older C library and running on a newer one works, because the newer one still provides every old interface. The reverse fails: a program built on trixie may use interfaces that bookworm's older libraries do not have yet, and the loader refuses to start it, with an error such as "version `GLIBCXX_3.4.32' not found".

+++ question | A forty-minute build

+++ question | Switching floors under a regression test

+++ question | A data source that points at itself

=== ops01-l06 | Practice: Registries, tags and digests

+++ question | The full name behind a short one
--- ask
A compose file says `image: grafana/grafana`, with no tag. Which full reference does Docker pull?
--- choice
`docker.io/library/grafana/grafana:latest`
--- choice
`docker.io/grafana/grafana` at its newest version number, such as `11.6.0`
--- choice
`ghcr.io/grafana/grafana:latest`
--- choice correct
`docker.io/grafana/grafana:latest`
--- why
Docker fills in what you leave out. No registry means Docker Hub, `docker.io`. The `library/` namespace is only added for official images named with one word, like `python`; `grafana/grafana` already names its namespace, `grafana`. No tag means `latest`, which is only a default name, not a promise of the newest version. For anything automated, write a real tag, and better a digest.

+++ question | A name that can never move
--- ask
Which of these references can only ever name one exact image?
--- choice
`python:3.12.14-slim-bookworm`, because it names the Python patch and the Debian release.
--- choice
`ghcr.io/gnc-team/landing-mc:git-3f9c2ab`, because it names a git commit.
--- choice correct
`python@sha256:392307d22300de8b5986851a12d9176dfc0fc073e65bf6523ebd7dcbeb23564e`
--- choice
`python:latest`, because it always means the same thing: the newest image.
--- why
Every tag is a row in the registry's table, and a push can rewrite it. `3.12.14-slim-bookworm` is still rebuilt for security fixes. A git-commit tag is stable only as long as your team never pushes it twice, which is a habit, not a guarantee. A digest is computed from the image's content, so different bytes would have a different digest; nobody can point it at anything else.

+++ question | A wheel on CI, a compile on the laptop
--- ask
The same commit is built on your laptop and on a fresh CI machine. The build used your laptop's old local copy of the tag, made when it still meant Debian 12 with glibc 2.36; CI pulled the tag's current image, Debian 13 with glibc 2.41. Only glibc 2.39 or newer accepts that wheel.
--- choice
The lockfile resolved differently on the two machines.
--- choice
Your laptop's kernel is older, and the kernel decides which wheels fit.
--- choice
CI has a compiler installed on the host, and builds use the host's tools.
--- why
A local copy of a tag is used as is; nothing checks the registry unless you pull. So one line, `FROM python:3.12-slim`, meant two different floors on two machines. The wheel's `manylinux_2_39` label needs glibc 2.39 or newer, so pip on the old floor fell back to source. +++ question | A line added to the lockfile by hand
--- ask
A Dockerfile installs with `pip install --no-cache-dir --require-hashes -r requirements.lock`. A teammate needs pandas and appends this one line to `requirements.lock` by hand:

+++ question | Two runners, one tag, two answers
--- ask
A pipeline runs `docker run landing-mc:1.0.0` on two build machines, and their output files differ. On each machine you run `docker image inspect landing-mc:1.0.0 --format '{{json .RepoDigests}}'` and get two different digests. What is the most likely story, and the fix?
--- choice

--- choice
The two machines have different kernels, which changes the image's digest.
--- choice

--- choice correct

+++ question | A digest that no longer pulls
--- ask
A 2026 results record says `image = registry.example/gnc/landing-mc@sha256:d71b…`. In 2031 an investigator runs that exact reference and the registry answers "manifest unknown". Meanwhile the tag `1.0.0` was pushed over twice. What went wrong, and what should have been done in 2026?

--- choice

--- choice correct

+++ question | Pods restarted in a loop
--- ask
A decoder spends 90 seconds loading a star catalog before it answers on `/healthz`. Its Deployment has:

```yaml

  httpGet:
    path: /healthz
    port: 8080
```

and no other probe. `kubectl describe pod` shows each pod being restarted about every 40 seconds, forever. What is the fix?
--- choice correct
Check "not ready yet" with a `readinessProbe`, which keeps traffic away until the pod answers, and give any liveness probe enough time before its first check.

--- choice

--- choice

--- why

+++ question | Same image, different last digits
