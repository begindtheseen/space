+++ practice | Battery readings with names
--- task
The `reading` table (`sat_id`, `ts`, `channel`, `value`) knows only a satellite's id. The `satellite` table (`sat_id`, `name`, `plane`, `launched`) knows its name.

List every reading on the `BATT_V` channel (battery voltage) together with the name of the satellite that sent it. Return three columns: `name`, `ts` and `value`. Sort by `ts`, then by `name`.
--- starter
SELECT r.sat_id, r.ts, r.value
FROM reading AS r
WHERE r.channel = 'BATT_V'
ORDER BY r.ts;
--- solution
SELECT s.name, r.ts, r.value
FROM reading AS r
JOIN satellite AS s ON s.sat_id = r.sat_id
WHERE r.channel = 'BATT_V'
ORDER BY r.ts, s.name;
--- hint
The name lives in another table. Join `satellite` to `reading` on the column they share.
--- hint
`JOIN satellite AS s ON s.sat_id = r.sat_id` puts each reading's satellite on the same row, so you can select `s.name`.
--- check result | Five battery readings, oldest first, each with its satellite's name
ordered

+++ practice | Channels and the readings that broke their limit
--- task
The `channel` table (`channel`, `units`, `hi_limit`) lists every channel the fleet can report, with its upper limit.

For every channel, list the readings above that channel's `hi_limit`. A channel with no such reading must still appear once, with NULL in the reading's columns. Return four columns: `channel` (from `channel`), `sat_id`, `ts` and `value`. Sort by `channel`, then by `ts`.
--- starter
SELECT c.channel, r.sat_id, r.ts, r.value
FROM channel AS c
LEFT JOIN reading AS r ON r.channel = c.channel
WHERE r.value > c.hi_limit
ORDER BY c.channel, r.ts;
--- solution
SELECT c.channel, r.sat_id, r.ts, r.value
FROM channel AS c
LEFT JOIN reading AS r
       ON r.channel = c.channel
      AND r.value > c.hi_limit
ORDER BY c.channel, r.ts;
--- hint
Run the starter: two channels are missing. On their rows the left join put NULL in `r.value`, and the WHERE test threw those rows away.
--- hint
"Above the limit" is part of what counts as a matching reading, so it belongs in the ON clause, next to the channel match.
--- check result | BUS_TEMP has one breach; BATT_V and SUN_ANGLE appear once each with NULLs
ordered
[["BATT_V", null, null, null], ["BUS_TEMP", "SAT-101", "2026-04-02T00:00:00Z", 27.0], ["SUN_ANGLE", null, null, null]]

+++ practice | Fleet and plan disagreements
--- task
The `contact_plan` table (`sat_id`, `station`) was imported from a spreadsheet, with no foreign key, so its ids are not checked against the fleet.

List every disagreement between the fleet (`satellite`) and the plan: satellites with no planned contact, and planned contacts whose `sat_id` is not in the fleet. Return three columns:

- `fleet_id`: `satellite.sat_id` (NULL for a contact whose satellite is not in the fleet)
- `plan_id`: `contact_plan.sat_id` (NULL for a satellite with no contact)
- `station`

Sort by whichever of the two ids is present: `ORDER BY COALESCE(s.sat_id, c.sat_id)`.
--- starter
SELECT s.sat_id AS fleet_id, c.sat_id AS plan_id, c.station
FROM satellite AS s
LEFT JOIN contact_plan AS c ON c.sat_id = s.sat_id
WHERE c.sat_id IS NULL
ORDER BY COALESCE(s.sat_id, c.sat_id);
--- solution
SELECT s.sat_id AS fleet_id, c.sat_id AS plan_id, c.station
FROM satellite AS s
FULL OUTER JOIN contact_plan AS c ON c.sat_id = s.sat_id
WHERE s.sat_id IS NULL OR c.sat_id IS NULL
ORDER BY COALESCE(s.sat_id, c.sat_id);
--- hint
A left join can only keep leftovers from its left table. You need the leftovers from both sides.
--- hint
Use `FULL OUTER JOIN`, then keep only the rows where one side is missing: `WHERE s.sat_id IS NULL OR c.sat_id IS NULL`.
--- check result | Two satellites with no contact, and one contact for a satellite that does not exist
ordered
[["SAT-104", null, null], ["SAT-105", null, null], [null, "SAT-107", "Hawaii"]]
--- check source | Keeps unmatched rows from both sides

+++ practice | Every satellite, every channel
--- task
For the satellites in orbital planes 2 and 3, list every pairing of a satellite with a channel from the `channel` table, together with that satellite's readings on that channel.

- A pair with readings gives one row per reading.
- A pair with no readings appears once, with NULL `ts` and `value`.
- A satellite with no readings at all still gets one row for each channel.

Return `name`, `channel`, `ts` and `value`. Sort by `name`, then `channel`, then `ts`.
--- starter
SELECT s.name, ch.channel, r.ts, r.value
FROM satellite AS s
JOIN reading AS r ON r.sat_id = s.sat_id
JOIN channel AS ch ON ch.channel = r.channel
WHERE s.plane IN (2, 3)
ORDER BY s.name, ch.channel, r.ts;
--- solution
SELECT s.name, ch.channel, r.ts, r.value
FROM satellite AS s
CROSS JOIN channel AS ch
LEFT JOIN reading AS r
       ON r.sat_id = s.sat_id
      AND r.channel = ch.channel
WHERE s.plane IN (2, 3)
ORDER BY s.name, ch.channel, r.ts;
--- hint
The pairs that ought to exist do not come from the readings. Build them first: every satellite with every channel.
--- hint
`satellite CROSS JOIN channel` makes the grid. Then left-join `reading` on both the satellite and the channel, so a pair with no reading keeps one row of NULLs.

+++ practice | Command acknowledgement report
--- task
`event_log` (`event_id`, `sat_id`, `ts`, `kind`, `ref_id`) records each command sent to a satellite as a row of kind `'CMD'`. When the satellite confirms a command, it writes a row of kind `'ACK'` whose `ref_id` is the command's `event_id`.

For every command, return four columns:

- `cmd`: the command's `event_id`
- `sat_id`
- `delay_s`: seconds from the command to its acknowledgement, worked out as `unixepoch(ack_ts) - unixepoch(cmd_ts)`; NULL when there is no acknowledgement
- `status`: `'ok'` if the acknowledgement came within 60 seconds (60 counts as within), `'slow'` if it came later, `'missing'` if there is none

Every command must appear. Sort by `cmd`.
--- starter
SELECT c.event_id AS cmd, c.sat_id,
       unixepoch(a.ts) - unixepoch(c.ts) AS delay_s,
       'ok' AS status
FROM event_log AS c
JOIN event_log AS a ON a.ref_id = c.event_id
ORDER BY c.event_id;
--- solution
SELECT c.event_id AS cmd,
       c.sat_id,
       unixepoch(a.ts) - unixepoch(c.ts) AS delay_s,
       CASE
           WHEN a.event_id IS NULL THEN 'missing'
           WHEN unixepoch(a.ts) - unixepoch(c.ts) <= 60 THEN 'ok'
           ELSE 'slow'
       END AS status
FROM event_log AS c
LEFT JOIN event_log AS a
       ON a.ref_id = c.event_id
      AND a.kind = 'ACK'
WHERE c.kind = 'CMD'
ORDER BY c.event_id;
--- hint
Commands and acknowledgements are rows of the same table, so this is a self-join: one copy for the command, one for its answer. Make it a left join, or unanswered commands vanish.
--- hint
`c.kind = 'CMD'` is about the left copy, so it goes in WHERE. `a.kind = 'ACK'` is about the partner, so it goes in ON.
--- hint
Test for the missing acknowledgement first in the CASE. On a row with no partner the delay is NULL, and `NULL <= 60` is not true, so it would fall through to `'slow'`.
--- check result | Five commands: two ok, one slow, two missing
ordered
[[1, "SAT-101", 5, "ok"], [3, "SAT-102", 100, "slow"], [4, "SAT-103", 9, "ok"], [6, "SAT-101", null, "missing"], [8, "SAT-104", null, "missing"]]
--- check source | Works out the delay with unixepoch
unixepoch
--- check source absent | Does not type the delays
\b(100|5|9)\s+AS\b

+++ practice | Downlink and power, key named once
--- task
`downlink_day` (`sat_id`, `day`, `mb`) holds the megabytes each satellite sent to the ground each day. `power_day` (`sat_id`, `day`, `wh`) holds the watt-hours of solar energy it collected each day. Both have the key `(sat_id, day)`.

Write `SELECT *` over the two tables joined on their whole key, so that each key column appears only once. The result has four columns: `sat_id`, `day`, `mb`, `wh`. Keep only the satellite-days found in both tables. Sort by `sat_id`, then `day`.
--- starter
SELECT *
FROM downlink_day AS d
JOIN power_day AS p ON p.sat_id = d.sat_id AND p.day = d.day

SELECT *

JOIN power_day USING (sat_id, day)

List every satellite-day found in either table, with its `mb` and `wh`, NULL where that table has no row. The `sat_id` and `day` columns must never be NULL: they show the key from whichever table has it. Return `sat_id`, `day`, `mb`, `wh`, sorted by `sat_id`, then `day`.

+++ practice | Temperature and voltage side by side
--- task
Some satellites record a bus temperature (`BUS_TEMP`) and a battery voltage (`BATT_V`) at the same instant. In `reading` (`sat_id`, `ts`, `channel`, `value`), a pair like that is two rows.

Pair each `BUS_TEMP` reading with the `BATT_V` reading of the same satellite at exactly the same `ts`. A reading with no partner is left out. Return `sat_id`, `ts`, `temp` and `volts`, sorted by `sat_id`, then `ts`.
--- starter
SELECT t.sat_id, t.ts, t.value AS temp, v.value AS volts
FROM reading AS t
JOIN reading AS v ON v.sat_id = t.sat_id
WHERE t.channel = 'BUS_TEMP' AND v.channel = 'BATT_V'

+++ question | A GROUPING number
--- ask
In PostgreSQL, a row from `GROUP BY CUBE (plane, channel)` shows plane 2 and a NULL channel, and that NULL is there because the channel was rolled up. What is `GROUPING(plane, channel)` on that row?
--- answer
1
one
--- why
`GROUPING(a, b)` packs one bit per column: $2 \times$ GROUPING(a) $+$ GROUPING(b). The plane was kept, so its bit is 0; the channel was rolled up, so its bit is 1: $2 \times 0 + 1 = 1$. A channel's total across all planes would give 2, and the grand total 3. If the NULL had been a real NULL in the data, the answer would be 0.

+++ question | A partial rollup
--- ask
Which grouping sets does `GROUP BY s.plane, ROLLUP (day)` produce?
--- choice correct
`(plane, day)` and `(plane)`: a row per plane per day and a subtotal per plane, but no grand total.
--- choice
`(plane, day)`, `(plane)` and `()`: the same as `ROLLUP (plane, day)`.
--- choice
`(plane, day)`, `(plane)`, `(day)` and `()`: every combination.
--- choice
`(day)` and `()`: the plain `plane` is ignored once ROLLUP is present.
--- why
A plain column next to ROLLUP stays in every grouping set, and ROLLUP only drops its own columns, from the right. So `plane` is always kept and `day` is kept or rolled up: `(plane, day)` and `(plane)`. With no set that drops `plane`, there is no grand total. That is useful when a total across planes would mean nothing.

+++ practice | First and last temperature
--- task
For each satellite with at least two `BUS_TEMP` readings, return `name`, `first_temp` (its earliest `BUS_TEMP` value), `last_temp` (its latest) and `change` (last minus first).

Write it as chained CTEs: one step finds each satellite's first and last `BUS_TEMP` timestamps, the next looks up the values at those times, and the main query attaches the names. Careful: some satellites record another channel at exactly the same instant. Sort by `name`.

WITH bounds AS (
    SELECT sat_id, MIN(ts) AS first_ts, MAX(ts) AS last_ts
    FROM reading
    WHERE channel = 'BUS_TEMP'
    GROUP BY sat_id
    HAVING COUNT(*) >= 2
),
ends AS (
    SELECT b.sat_id, f.value AS first_temp, l.value AS last_temp
    FROM bounds AS b
    JOIN reading AS f ON f.sat_id = b.sat_id AND f.ts = b.first_ts AND f.channel = 'BUS_TEMP'
    JOIN reading AS l ON l.sat_id = b.sat_id AND l.ts = b.last_ts  AND l.channel = 'BUS_TEMP'
)

FROM ends AS e
JOIN satellite AS s ON s.sat_id = e.sat_id
ORDER BY s.name;

+++ question | A step used twice
--- ask
In PostgreSQL 16, a CTE named `daily` summarizes a billion readings per satellite per day, and two later steps both read it. The main query keeps only `sat_id = 'SAT-101'`. Why can this be slow, and what changes it?
--- choice correct
A CTE read more than once is materialized: `daily` is computed in full for every satellite and stored, and the filter on one satellite cannot reach inside it. Writing `daily AS NOT MATERIALIZED (…)` lets each use be planned with the filter pushed into the scan.
--- choice
It cannot be slow: since PostgreSQL 12 every CTE is pasted in where it is used.
--- choice
A CTE is saved in the database like a view, so it is recomputed on every read; `AS MATERIALIZED` makes it a cached table.
--- choice
WITH forces a nested-loop join; the only fix is to rewrite the steps as nested subqueries.
--- why
PostgreSQL 12 and later inline a CTE that is used once and is not recursive. One read two or more times is materialized: computed once, on its own, and stored, so the planner does not look across it, and here that means summarizing every satellite to show one. `NOT MATERIALIZED` asks for inlining, at the price of doing the work once per use. Which is faster depends on the data, so compare the plans with `EXPLAIN`.

+++ question | Where the doubling stops
--- ask
What does this return?

```sql
WITH RECURSIVE t (n) AS (
    SELECT 3
    UNION ALL
    SELECT n * 2 FROM t WHERE n < 40
)
SELECT MAX(n) FROM t;
```
--- answer
48
forty-eight
forty eight
--- why
The anchor makes 3, and each round doubles the one row made the round before: 6, 12, 24. The round that reads 24 passes `24 < 40` and makes 48. The round that reads 48 fails the test, makes nothing, and the recursion stops. The stop test is checked on the row being read, not on the row about to be made, which is why the result goes past 40.

+++ question | How many rows UNION keeps
--- ask
In `reading`, the distinct `(sat_id, channel)` pairs are: SAT-101 with both `BUS_TEMP` and `BATT_V`, SAT-102 with both, SAT-103 with both, and SAT-104 with `BATT_V`, from 13 rows in all. `reading_archive` has 5 rows, whose pairs are SAT-101 `BUS_TEMP` (three rows), SAT-102 `BUS_TEMP` and SAT-104 `BATT_V`. How many rows does this return?

```sql
SELECT sat_id, channel FROM reading
UNION
SELECT sat_id, channel FROM reading_archive;
```
--- answer
7
seven
--- why
UNION stacks the 18 rows and keeps each different row once. The live table already has 7 different pairs, and every pair in the archive is one of them, so the answer is 7. UNION ALL would return all $13 + 5 = 18$ rows. Removing the duplicates costs a sort or a hash over everything, which is why UNION ALL is the default choice when you do not need it.

CREATE VIEW assembly_mass AS
SELECT p.part_id, p.name, COUNT(c.part_id) AS parts_inside,
       ROUND(p.mass_kg + SUM(c.mass_kg), 1) AS total_kg

--- solution
CREATE VIEW assembly_mass AS
WITH RECURSIVE below (top_id, part_id, mass_kg) AS (
    SELECT part_id, part_id, mass_kg
    FROM part
    UNION ALL
    SELECT b.top_id, p.part_id, p.mass_kg
    FROM part AS p
    JOIN below AS b ON p.parent_id = b.part_id
)

       COUNT(*) - 1               AS parts_inside,
       ROUND(SUM(b.mass_kg), 1)   AS total_kg
FROM below AS b
JOIN part AS t ON t.part_id = b.top_id
GROUP BY t.part_id, t.name
HAVING COUNT(*) > 1;

Each child row looks up its parent by the parent's primary key, so it matches at most one row: the join cannot fan out. The left join keeps the spacecraft, whose NULL parent matches nothing, with a NULL `parent_name`. So exactly one row per part: 10. An inner join would return 9.
