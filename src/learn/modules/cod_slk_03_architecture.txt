=== slk03-l01 | Practice: Virtual and atomic subsystems
--- for
l01-virtual-and-atomic-subsystems

+++ question | Which order is still allowed
--- ask
A model has five Gain blocks and no delays. A feeds B, and B feeds C. Separately, D feeds E. You select B and E, press Ctrl+G, and then select **Treat as atomic unit** on the new subsystem S.

Which of these sorted execution orders can Simulink use now?
--- choice
A, B, D, E, C
--- choice correct
A, D, B, E, C
--- choice
A, B, C, D, E
--- choice
D, E, A, B, C
--- why
All four orders respect the arrows, so all four were legal while S was virtual: flattening removes the box and B and E are sorted on their own. Atomic S takes one place in the order and runs start to finish, so B and E must sit next to each other. S also counts as direct feedthrough, so it can only run after both of its sources, A and D, and before C, which reads its output. Only A, D, then B and E together, then C does all of that.

+++ question | An overheat flag one step late
--- ask
A thermal monitor and a heater-cutoff block run in a 10 Hz model, so one step is 0.1 s. The monitor writes a data store `overtemp`, true when the battery temperature is above 80 °C. The cutoff block reads `overtemp` through a Data Store Read. No signal line joins them. In a test the temperature is $62 + 3k$ degrees at step $k$, starting at step 0 at time 0.

The sorted order happens to put the reader before the writer. At what time, in seconds, does the cutoff block first see `overtemp` true?
--- answer
0.8
0.8 s
0.80
0.80 s
0.8s
.8
0.8 seconds
--- why
At step 6 the temperature is $62 + 18 = 80$, which is not above 80. At step 7 it is 83, so the monitor first writes true at step 7, at 0.7 s. With the reader first, on step 7 it reads the store before the monitor updates it and still sees step 6's false. It sees true on step 8, at 0.8 s. Nothing warns you: only the order moved the answer by one step. A signal line from the monitor to the cutoff block would force the right order.

+++ question | A delay or a checkbox
--- ask
An atomic subsystem in a 100 Hz attitude model holds two paths: a Unit Delay path and a Gain path. A feedback line outside it creates an artificial algebraic loop. Two fixes are proposed:

- Engineer 1: add a Unit Delay to the outside feedback line.
- Engineer 2: select **Minimize algebraic loop occurrences** on the subsystem.

Which is the better fix, and why?
--- choice
Engineer 1: a Unit Delay is the standard way to break any algebraic loop, and it costs nothing.
--- choice correct
Engineer 2: the loop is artificial, since the math already has a delay in it, so asking Simulink to split the output calculation removes it without changing the model's dynamics. The extra Unit Delay would add a real one-step lag to the loop.
--- choice
Engineer 1: the Minimize option only works on virtual subsystems.
--- choice
Neither: an artificial algebraic loop can only be removed by deleting the subsystem.
--- why
From the solvers module, a Unit Delay at sample time $T_s$ costs $\omega T_s$ radians of phase at frequency $\omega$: it changes what the controller does. That is the right price for a genuine loop. Here the loop exists only because the atomic box hides the delay that is already inside it. Minimize algebraic loop occurrences lets Simulink compute the delayed output before the input is known. Leaving the subsystem virtual, if atomicity is not needed, works too.

+++ question | The loop no setting removes
--- ask
A subsystem has one input and one output. Outside it, the output goes through a Gain of 0.5 and back into the input. Which contents make the model an algebraic loop **even when the subsystem is virtual**?
--- choice
The input goes through a Unit Delay, then a Gain of 2, to the output.
--- choice correct
The input goes through a Gain of 2, then a Sum that adds a constant, to the output.
--- choice
The input goes through an Integrator to the output.
--- choice
The input goes through a Memory block to the output.
--- why
A genuine loop is one where every block around it has direct feedthrough. Gain and Sum both need their input now to produce their output now, and so does the outside Gain, so the sort has nowhere to start. Unit Delay, Integrator and Memory have no direct feedthrough: their output this step was settled before this step's input arrived, which gives the loop a starting point. Flattening a virtual box cannot remove a loop that is really in the math.

+++ question | Why Reusable function was refused
--- ask
Six identical atomic subsystems, PitchLimiter, are set to Function packaging **Reusable function**. Code generation stops and says the subsystem cannot be reused. Which block inside is the most likely reason?
--- choice
A Unit Delay that remembers the last output.
--- choice correct
A Data Store Write that sets the global data store `limit_active`.
--- choice
A Saturation block that clamps the output.
--- choice
A Gain whose value is 0.8.
--- why
A reusable function must be reentrant: everything it touches arrives through its arguments, so each call can be handed its own copy of the data. State is fine, because each instance's Unit Delay memory is passed in as an argument, like `wheel_state[i]` in the lesson's sketch. A write to one global data store is not: all six calls would share it. Pass the flag out through an Outport instead, and write the store outside the subsystem.

+++ question | When sharing starts to pay
--- ask
An atomic subsystem's body is 9 lines of C. Count code like this:

- **Inline:** the 9 lines are pasted once per instance, with no calls.
- **Reusable function:** one function of 9 lines plus a 3-line wrapper, and 1 line per instance to call it.

What is the smallest number of identical instances for which Reusable function gives fewer lines than Inline? Type a whole number.
--- answer
2
two
--- why
With $n$ instances, Inline is $9n$ lines and Reusable is $9 + 3 + n = 12 + n$. For $n = 1$: 9 against 13, so Inline wins, which is why a single instance is usually inlined. For $n = 2$: 18 against 14, and Reusable is already smaller. After that the gap grows by 8 lines per extra instance, because each new instance costs Inline a whole body but Reusable only one call.

=== slk03-l02 | Practice: Conditional subsystems
--- for
l02-conditional-subsystems

+++ question | A timer that remembers
--- ask
An enabled subsystem integrates the constant 1, so its state grows by 1 for each second it runs. Its enable signal is positive from $t = 2$ to $5\,\mathrm{s}$, zero from 5 to $9\,\mathrm{s}$, and positive again from 9 to $12\,\mathrm{s}$. The Enable block has States when enabling set to **held**. The Outport has Output when disabled set to **reset**, with an Initial output of 0.

What does the subsystem output at $t = 11\,\mathrm{s}$?
--- answer
5
5 s
5.0
5 seconds
--- why
The first run counts $5 - 2 = 3$. While disabled, the output is reset, so it reads 0 from 5 to 9 s, but the **state** is held at 3. On re-enable at 9 s the state carries on from 3, and two seconds later it reads $3 + 2 = 5$. The two settings are independent: one decides what the output shows while switched off, the other what the states remember when switched back on.

+++ question | A pulse that starts high
--- ask
A triggered subsystem adds 1 to a count each time it runs. Its trigger signal is 1 for $0 \le t < 0.4\,\mathrm{s}$, then 0 for $0.4 \le t < 0.8\,\mathrm{s}$, and repeats with a period of 0.8 s. The stop time is 3.0 s. Trigger type is **either**.

How many times does the subsystem run?
--- answer
7
seven
--- why
Falling edges: 0.4, 1.2, 2.0 and 2.8 s, which is 4. Rising edges: 0.8, 1.6 and 2.4 s, which is 3; the next one, at 3.2 s, is after the stop time. The signal starting at 1 is not an edge, because nothing crossed zero at $t = 0$. So "either" gives $4 + 3 = 7$ runs. A triggered subsystem counts events, not elapsed time.

+++ question | What a triggered subsystem accepts
--- ask
A triggered subsystem runs on each rising edge of a frame pulse. Which block, placed inside it, is accepted?
--- choice
A Transfer Fcn low-pass filter.
--- choice
A Discrete Transfer Fcn with its sample time set to 0.01.
--- choice correct
A Unit Delay with its sample time set to -1.
--- choice
An Integrator with a saturation limit.
--- why
A triggered subsystem runs only at trigger moments, with no regular spacing. Continuous states, like those of a Transfer Fcn or an Integrator, need a solver visiting them at every step, so they are refused. A block with its own fixed sample time of 0.01 is refused too, because blocks inside must take their timing from the trigger. From the solvers module, a sample time of -1 means inherited: the Unit Delay then runs once per trigger and remembers the value from the previous trigger.

+++ question | A mode nobody listed
--- ask
A Switch Case block reads the guidance mode, with Case conditions `{1, [2 3]}` and **Show default case** turned off. Its two action subsystems feed a Merge. For a long time the mode is 2, then it becomes 4. What does the Merge output while the mode is 4?
--- choice
0, because no branch is running.
--- choice correct
The value case `[2 3]` last wrote, because Merge carries the most recently written input and nothing writes while no branch runs.
--- choice
An error: Switch Case must always run exactly one branch.
--- choice
The average of the two branches' last outputs.
--- why
With no default case, a value outside the list runs no action subsystem at all. Both Outports are held, as Merge requires, so nothing writes to the Merge, and it keeps the last value written: the `[2 3]` branch's output. Before any branch has ever run, it would show its Initial output. A frozen command with no warning is rarely what you want, so decide on purpose what an unlisted mode should do, usually with a default case.

+++ question | A per-burn timer that keeps counting
--- ask
An engineer wants an enabled subsystem to show the current burn's duration: 0 at each ignition, counting up during the burn. She sets Output when disabled to **reset** with Initial output 0 and leaves the rest at defaults. In a test with a 60 s first burn, the second burn's timer starts at 60. Which change fixes it?
--- choice
Set Output when disabled to held.
--- choice
Set the Initial output to -60.
--- choice correct
Set the Enable block's States when enabling to reset.
--- choice
Replace the enabled subsystem with a triggered one.
--- why
Output when disabled only decides what the output shows while the subsystem is switched off, which is why it read 0 during the coast. What the integrator remembers when the subsystem switches back on is the Enable block's States when enabling. Left at held, the state resumes from 60: a lifetime counter. Set to reset, the state returns to its initial condition at each ignition: a per-burn counter. A triggered subsystem could not hold the integrator at all.

+++ question | Four valves, one body
--- ask
A For Each subsystem models four valves. Each follows the discrete lag $y_{k+1} = y_k + \frac{T_s}{\tau}(u_k - y_k)$ with $T_s = 5\,\mathrm{ms}$. The time constants $\tau$ ("tau") are a partitioned mask parameter, $[0.010,\ 0.020,\ 0.025,\ 0.050]$ seconds. All four are commanded fully open ($u = 1$) from rest ($y_0 = 0$).

What is the third element of the output vector after 3 steps? Give three decimal places.
--- answer
0.488
.488
0.4880
--- why
The partition hands iteration 3 its own $\tau = 0.025\,\mathrm{s}$, so $T_s/\tau = 0.005/0.025 = 0.2$. The gap to fully open shrinks by the factor $1 - 0.2 = 0.8$ each step, so $y_3 = 1 - 0.8^3 = 1 - 0.512 = 0.488$. The other elements are $1 - 0.5^3 = 0.875$, $1 - 0.75^3 \approx 0.578$ and $1 - 0.9^3 = 0.271$. Each iteration keeps its own state and gets its own parameter, and the four answers are concatenated into one vector.

=== slk03-l03 | Practice: Masks, libraries and projects
--- for
l03-masks-libraries-and-projects

+++ question | Two masks deep
--- ask
A masked subsystem has a mask parameter `K` set to 4. Inside it sits a second masked block with a mask parameter `gain` set to 0.5. Inside that block, a Gain block has the value `K*gain`. A script has also left `K = 10` and `gain = 3` in the base workspace. The Gain's input is 2.

What is the Gain's output?
--- answer
4
4.0
--- why
Simulink searches from the inside out and stops at the first match. `gain` is found in the nearest mask workspace: 0.5. `K` is not in the inner mask, so the search goes one mask out and finds 4 there. The base-workspace values are never reached. So the output is $4 \times 0.5 \times 2 = 4$. With both names declared by masks, the stray variables cannot change the answer.

+++ question | A number that is really text
--- ask
A test script reads a masked valve's time constant and doubles it:

```matlab
blk = 'vehicle/RCS/ValveLag3';
t = get_param(blk, 'tau');     % the dialog shows 0.025
t2 = 2 * t;
```

`t2` does not come out as 0.05. Why?
--- choice
`get_param` returns the value in milliseconds.
--- choice correct
`get_param` returns the text typed in the dialog, such as '0.025', not a number. Doubling text doubles its character codes. Convert it first, for example with `str2double(t)`.
--- choice
The mask workspace is private, so a script can only read a copy that is rounded.
--- choice
`get_param` cannot read mask parameters; it returned an empty value.
--- why
A mask parameter's value is stored as the text in the dialog, because it may be an expression such as `1/40` or a variable name. `get_param` hands back that text, and `set_param` takes text too. Arithmetic on a character array works on the character codes, which gives a vector of meaningless numbers. Turn the text into a number before doing arithmetic on it.

+++ question | Changing one thruster without cutting the link
--- ask
A model has 12 linked blocks from the library block `RCSThruster`. Thruster 3 is mounted differently and needs a different thrust direction. Which change keeps its link active, so it still receives future library fixes?
--- choice correct
Type the new direction into Thruster 3's mask dialog, as a value of its mask parameter.
--- choice
Look under the mask and change the Constant block that holds the direction.
--- choice
Add a Gain block inside Thruster 3 to rotate the direction.
--- choice
Break the link, change the direction, and keep the result.
--- why
A linked block takes its contents from the library and keeps only its own mask parameter values. Changing a mask parameter is exactly what each instance is allowed to do, so the link stays resolved. Editing anything under the mask changes the contents, which belong to the library, so it needs a disabled link first. That creates the fork that misses the next fix. Breaking the link loses the library for good. If thrusters really differ, the difference should be a mask parameter.

+++ question | The fork a script cannot find
--- ask
Before each release, a script lists every block whose `LinkStatus` is `'inactive'`, so that forgotten local copies get restored. Last year someone **broke** the link on Thruster 9 and edited its contents. What does the script report for Thruster 9?
--- choice
It lists Thruster 9 as inactive, with its library block.
--- choice correct
Nothing: a broken link has `LinkStatus` `'none'`, like a block that was never linked, so the script cannot tell it came from the library.
--- choice
It reports Thruster 9 as `'unresolved'`.
--- choice
It restores Thruster 9 automatically.
--- why
A disabled link is a local copy that still remembers its library block, which is why a script can find it and why the Links Tool can restore or push it. A broken link forgets the library completely. It is an ordinary subsystem now, and nothing in its link status says where it came from. That makes breaking a link a much bigger decision than disabling one: the copy drops out of every search for stale forks.

+++ question | The initialization code with a side effect
--- ask
A masked valve block has this initialization code:

```matlab
if Ts <= 0 || tau <= 0
    error('Ts and tau must be positive.');
end
a = Ts / tau;
assignin('base', 'a', a);        % so the telemetry block can use it
iconText = sprintf('lag %g ms', 1000*tau);
```

The model holds four copies with different `tau`. The telemetry block, outside the masks, shows a value of `a` that matches whichever valve was updated last. Which line is the bug?
--- choice
The `if` test, because it should use `&&` instead of `||`.
--- choice
`a = Ts / tau;`, because `a` should be computed by the blocks inside.
--- choice correct
The `assignin` line, which writes to the base workspace from mask code.
--- choice
The `sprintf` line, because icon text must be computed in the icon commands.
--- why
Mask code should read its own parameters and write its own mask workspace, nothing else. `assignin('base', ...)` writes one shared variable from four blocks, and initialization code runs on every update in an order you do not control, so the last one wins. The `||` test is right: stop if either value is not positive. If the telemetry block needs each valve's `a`, bring it out through a port.

+++ question | Two engineers, one model file
--- ask
The repository's `.gitattributes` marks `*.slx` as binary. Two engineers edit `VehicleSim.slx` on separate branches: one changes the sensor subsystem, the other the drag model. Merging the branches, Git reports a conflict on the file. What should the team do?
--- choice
Remove the binary mark, so Git can merge the two versions line by line.
--- choice
Accept whichever version Git keeps, and assume the other change was small.
--- choice correct
Use MATLAB's model comparison and merge tools from the project to combine the two sets of changes. Then split the model so sensors and aerodynamics live in separate files.
--- choice
Open both versions and copy one engineer's blocks into the other by eye, then commit without comparing.
--- why
An `.slx` file is a compressed archive, so a line-by-line merge could corrupt it; the binary mark exists to stop exactly that. Simulink's comparison and merge tools work on blocks, lines and parameters, so they can combine structural edits. The lasting fix is structural: give each component its own file, owned by one person, so the conflict never happens. That is the model reference lesson.

=== slk03-l04 | Practice: Bus objects, bus blocks and C structs
--- for
l04-bus-objects

+++ question | By name or by index
--- ask
A signal `wheel_cmd` is a plain 4-element vector of wheel torques. During a test you want to replace only its second element with 0, leaving the other three untouched. Which block does that?
--- choice
Bus Assignment, choosing element 2.
--- choice correct
Assignment, with the index set to 2 and the index mode set to one-based.
--- choice
Bus Selector, choosing element 2.
--- choice
Bus Creator, with the zero wired into its second input.
--- why
`wheel_cmd` is a vector, not a bus: its elements have positions, not names. Assignment copies the vector and overwrites chosen positions, which is the job. Bus Assignment does the same thing by element name, on a bus. Bus Selector only reads elements out, and Bus Creator builds a new bus. Check the index mode: with zero-based counting, index 2 would be the third element.

+++ question | How big is the telemetry struct
--- ask
A nonvirtual bus has these elements, in this order: `flag` (uint8), `t` (double), `count` (uint16), `mode` (uint8). On the lesson's 64-bit processor a double takes 8 bytes and must start at a multiple of 8, a uint16 takes 2 bytes and must start at a multiple of 2, and a uint8 takes 1 byte. The struct's size is rounded up to a multiple of 8.

What does `sizeof` give for the generated struct, in bytes?
--- answer
24
24 bytes
--- why
`flag` takes byte 0. `t` must start at a multiple of 8, so bytes 1 to 7 are padding and `t` fills bytes 8 to 15. `count` fills 16 and 17, and `mode` takes 18, for 19 bytes. Rounding up to a multiple of 8 gives 24. Putting `t` first would give $8 + 2 + 1 + 1 = 12$, rounded to 16. The bus object's element order is the struct's field order, so it is a layout decision.

+++ question | A bus into a MATLAB Function block
--- ask
A Bus Creator bundles `pos`, `vel` and `mode` and feeds a MATLAB Function block that reads `nav.vel(3)`. The Bus Creator's Output data type is `Inherit: auto`. Updating the diagram fails at the MATLAB Function block's input. What is the fix?
--- choice
Replace the Bus Creator with a Mux, since MATLAB Function blocks only accept vectors.
--- choice correct
Define a bus object, say `NavBus`, and set the MATLAB Function block's input data type (and the Bus Creator's output) to `Bus: NavBus`.
--- choice
Make the bus nonvirtual with a Signal Conversion block, and leave the types at inherit.
--- choice
Rename the input `nav` to match the Bus Creator's block name.
--- why
A MATLAB Function block receives a bus as a MATLAB structure, and it compiles to code, so it must know the structure's fields, types and sizes in advance. A bus object is where that knowledge lives. A Mux would throw the names away and force one data type on all elements. A nonvirtual bus also needs a bus object, so asking for one without defining it does not help.

+++ question | Forcing the mode to 5
--- ask
In a test harness you use a Bus Assignment to force the `mode` element of a NavBus to 5. The bus object says `mode` is `uint8`. You wire a Constant block with the value 5, leaving all its settings at their defaults, into the Bus Assignment's `mode` input. What happens when you press Ctrl+D?
--- choice
It works: Simulink converts 5 to `uint8` automatically.
--- choice correct
The update stops with a data type mismatch: the Constant's output is a `double` by default, and a Bus Assignment's new value must match the element's type. Set the Constant's output data type to `uint8`.
--- choice
It works, but `mode` becomes a `double` in the output bus.
--- choice
Nothing happens until the simulation reaches the first step that uses `mode`.
--- why
From the first module, a signal is a `double` unless something says otherwise, and a Constant block is no exception. Bus Assignment replaces an element in place, so the new value must have the same type and size as the old one; otherwise the output would no longer match the bus object. The check runs when the diagram is updated, before any step, which is the point of a typed interface.

+++ question | Wires in the wrong order
--- ask
A bus object `AttBus` lists `q` (double, 4 elements), then `rate` (double, 3 elements), then `valid` (boolean). A Bus Creator has its Output data type set to `Bus: AttBus`. Its first input is wired to the 3-element rate signal, its second to the 4-element quaternion, its third to the valid flag. What happens?
--- choice
Simulink matches the inputs to the elements by their signal names, so it works.
--- choice
It runs, and the quaternion's first three values land in `rate`.
--- choice correct
Updating the diagram reports a dimension mismatch for `q`: the Bus Creator's inputs must match the bus object's elements in order, and a 3-element signal cannot fill a 4-element slot.
--- choice
It runs, and the extra quaternion element is dropped silently.
--- why
With a bus object on its output, a Bus Creator's inputs are checked against the elements in order: input 1 against `q`, input 2 against `rate`. The first input has 3 elements where `q` needs 4, so the update stops before any step. That is the contract working. Without a bus object, the Bus Creator would have built whatever arrived, and the swap would have surfaced later as wrong numbers.

+++ question | What reordering saves
--- ask
A telemetry bus becomes a C struct with its elements in this order: `mode` (uint8), `t` (double), `valid` (uint8), `temp` (single), `count` (uint16), `alt` (double). Each type must start at a multiple of its own size: 8 for a double, 4 for a single, 2 for a uint16, 1 for a uint8. The struct's size is rounded up to a multiple of 8.

How many bytes smaller is the best possible ordering of these six elements than the order given?
--- answer
16
16 bytes
--- why
Given order: `mode` at 0, padding to 8, `t` at 8 to 15, `valid` at 16, padding to 20, `temp` at 20 to 23, `count` at 24 and 25, padding to 32, `alt` at 32 to 39. That is 40 bytes. The data itself is $8 + 8 + 4 + 2 + 1 + 1 = 24$ bytes. Largest first, `t`, `alt`, `temp`, `count`, `mode`, `valid`, packs it with no gaps into 24 bytes, already a multiple of 8, so nothing can be smaller. The saving is $40 - 24 = 16$ bytes per struct, and a telemetry buffer holds many of them.

+++ question | Four wheels, one file
--- ask
A spacecraft uses four Model blocks that all name `ReactionWheel.slx`. The wheels are identical except for the axis each one spins about. How should the axis be given to each wheel?
--- choice
Copy `ReactionWheel.slx` four times, one file per axis.
--- choice correct
Declare the axis as a model argument of `ReactionWheel`, and set its value on each Model block.
--- choice
Put a variable `axis` in the base workspace and change it between runs.
--- choice
Turn each Model block into a subsystem so each can have its own contents.
--- why
Model arguments exist for exactly this: one file, one set of blocks, and a few numbers each instance sets for itself. Copying the file brings back the problem model reference solves, since a fix would have to be made four times. A base-workspace variable holds one value, so all four wheels would share it. Converting to subsystems loses separate compilation and the single file.

+++ question | A shared bus changes
--- ask
A vehicle model has six referenced models. Their compile times in seconds are: environment 30, aerodynamics 50, propulsion 40, dynamics 70, sensors 25, GNC 85. The thin top model takes 15. An engineer adds an element to the bus object `StateBus`, which types root ports of aerodynamics, dynamics and GNC, and changes nothing else.

How many seconds does the next build take?
--- answer
220
220 s
220 seconds
--- why
A change to a bus object used at a model's ports changes that model's interface, so its saved build no longer matches and it must be compiled again. Aerodynamics, dynamics and GNC use `StateBus`, and the top model wires them: $50 + 70 + 85 + 15 = 220\,\mathrm{s}$. Environment, propulsion and sensors are reused. A full build would be 315 s, so the saving is smaller than for a change inside one component, which is why shared interfaces should stay stable.

+++ question | A data store that stops at the boundary
--- ask
The parent model VehicleSim has a Data Store Memory block `fault_flag`. A Data Store Read inside the GNC subsystem reads it. You run `convertToModelReference` on GNC, and the conversion fails. What is the best way forward?
--- choice
Copy the Data Store Memory block into the new GNC model as well.
--- choice
Set `AutoFix` to `true`; it will make the data store visible across the boundary.
--- choice correct
Make `fault_flag` a real input port of GNC. If a shared store is truly needed, define it as a global data store with a Simulink.Signal object instead of a Data Store Memory block.
--- choice
Leave GNC as a virtual subsystem, since data stores only work in virtual subsystems.
--- why
A referenced model is compiled on its own, so it cannot see a Data Store Memory block in its parent. A second Data Store Memory block would be a separate store with the same name, not the same data. Turning the hidden link into a port writes the interface down, and a port also fixes the order problem from lesson 1: the writer must run first. A Simulink.Signal object makes a global store both models can see, but the ordering caveat remains.

+++ question | Two rates at the boundary
--- ask
The referenced model Sensors has a root Inport with data type `double`, dimensions 3, and sample time 0.01 s. In the parent, the truth-motion signal feeding it is a 3-element `double` at 0.02 s. What happens, and what is the usual fix?
--- choice
Simulink quietly runs Sensors at 0.02 s instead.
--- choice
It runs, and Sensors reads each input value twice without any record.
--- choice correct
Updating the diagram reports a sample time mismatch at the Model block, before the simulation runs. Put a Rate Transition block between the two rates.
--- choice
Nothing, because only data type and dimensions are checked at a model boundary.
--- why
Sample time is part of a referenced model's interface, together with data type, dimensions and complexity. The saved build was made for 0.01 s, so a 0.02 s signal is reported at once. From the solvers module, a Rate Transition block moves data between rates on purpose, and because 0.02 is an integer multiple of 0.01 the transfer can be made deterministic.

+++ question | Three hundred files nobody wrote
--- ask
After running the vehicle simulation once, `git status` shows several hundred new and changed files, all under a folder `slprj`. A teammate who pulls them gets merge conflicts in files nobody edited. What went wrong?
--- choice
The project's startup files wrote temporary copies of every model.
--- choice correct
`slprj` is Simulink's build cache for the referenced models. It was committed; it should be listed in `.gitignore` and removed from the repository.
--- choice
`slprj` is the project definition, and two people edited it at once.
--- choice
Accelerator mode writes its results into the repository, so the Model blocks should be in Normal mode.
--- why
Separate compilation saves each referenced model's build in `slprj` so it can be reused. That folder is a product of building, regenerated on every machine, and it changes on every build. Committed, it causes conflicts over files nobody wrote and can hand a teammate a build that does not match the models. Despite its name, it has nothing to do with Projects. Ignore it; deleting it only costs one slow rebuild.

+++ question | How many runs pay for the build
--- ask

+++ question | After, at 25 Hz
--- ask
A chart runs at 25 Hz. A state has the transition `[after(0.3, sec)]`. Counting the wake-up that enters the state as wake-up 0, on which wake-up is the transition taken?
--- answer

eight
wake-up 8
--- why
At 25 Hz the step is $h = 0.04\,\mathrm{s}$. The transition is taken on the first wake-up $j$ with $0.04\,j \ge 0.3$, so $j = \lceil 0.3/0.04 \rceil = \lceil 7.5 \rceil = 8$, at $0.32\,\mathrm{s}$. +++ question | The event that is still allowed
--- ask
A team's modeling standard bans local events in flight charts. The chart must run the ValveDriver subsystem exactly once, at a definite point in its step. Which design fits the standard?

--- choice correct

--- why
A function-call output event runs the named subsystem once, synchronously, and returns, like a function call in a program: it schedules work in Simulink and never re-enters the chart. +++ question | A timeout that never fires

+++ question | Duration on the fourth sample

A variant slot must hold exactly one part, and Simulink refuses to guess, so the mistake is caught before anything runs. That is why guards must be made exclusive by construction, or their priority documented, and why tools like transition-conflict checks and Design Verifier exist: the chart itself will not complain.

+++ question | Navigation, then guidance, every step
--- ask
Each step, the navigation filter must run before guidance, and both must run only while the chart is in FLIGHT. Your team's standard bans local events. Which design states that order in the model, so the generated code keeps it?
--- choice
Put the two subsystems in one virtual subsystem, navigation drawn on the left, so it runs first.
--- choice
Make both enabled subsystems driven by an `in_flight` output of the chart, and trust the sorted order.
--- choice correct
Make both function-call subsystems, and have the chart's FLIGHT state call them with function-call output events, navigation first, then guidance.
--- choice
Have the chart send a local event to each subsystem in turn.
--- why
A function-call subsystem runs exactly when it is called, and the caller fixes the order, so "navigation, then guidance" is written in the model and carried into the code. A function-call output event runs its subsystem once and returns, without re-entering the chart, so it fits a no-local-events rule. Drawing position means nothing to a flattened virtual subsystem. Enabled subsystems run wherever the sort puts them, and a signal line from navigation to guidance is the only thing that would force the order there.
