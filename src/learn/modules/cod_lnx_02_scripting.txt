+++ practice | A script that says how it was called
--- task
Create `bin/status.sh`. Its first line is the shebang `#!/usr/bin/env bash`. Its second line prints one line:

```
called as <path> with <n> arguments
```

where `<path>` is the script's path exactly as it was typed, and `<n>` is the number of arguments it was given.

Make it executable, then run it twice from `~/project`:

- `./bin/status.sh alpha beta` must print `called as ./bin/status.sh with 2 arguments`
- `bash bin/status.sh` must print `called as bin/status.sh with 0 arguments`
--- starter
mkdir -p bin
--- solution
echo '#!/usr/bin/env bash' > bin/status.sh
echo 'echo "called as $0 with $# arguments"' >> bin/status.sh
chmod +x bin/status.sh
./bin/status.sh alpha beta
bash bin/status.sh
--- hint
Inside a script, `$0` (dollar zero) is the path it was started by, as typed, and `$#` (dollar hash) is the number of arguments.
--- hint
Write the shebang with `>` so it lands on line 1, and the second line with `>>`. Single quotes around the second line stop `$0` and `$#` from being filled in while you write the file.
--- hint
`chmod +x bin/status.sh` adds the execute bit.
--- check shell | The script starts with the shebang and is executable
file bin/status.sh contains #!/usr/bin/env bash
file bin/status.sh exec
--- check shell | Run by its path, it names that path and counts two arguments
printed-line called as ./bin/status.sh with 2 arguments
--- check shell | Run with bash, it names the path you typed and counts none
printed-line called as bin/status.sh with 0 arguments

+++ question | One option on the shebang line
--- ask
On Linux, `trace.sh` is executable and starts with this line:

```bash
#!/usr/bin/env bash -x
```

What happens when you run `./trace.sh`?
--- choice
The script runs with tracing switched on, as if you had typed `bash -x trace.sh`.
--- choice
The script runs normally; the kernel ignores anything after the interpreter's name.
--- choice correct
`env` reports that it cannot find a program called `bash -x`, and no line of the script runs.
--- choice
bash reports a syntax error on line 1, because `-x` is not allowed in a comment.
--- why
The kernel passes everything after the interpreter on the `#!` line as one single argument. So `env` is asked to run a program literally named `bash -x`, space included, and there is none. The portable fix is a `set -x` line inside the script; GNU `env` also accepts `#!/usr/bin/env -S bash -x`, where `-S` splits the rest of the line into words.

+++ question | Fine in the terminal, broken from Python
--- ask
`tidy.sh` is executable and has no shebang line. `./tidy.sh` works when you type it in a bash terminal. A Python program runs the same file with `subprocess.run(["./tidy.sh"])` and gets:

```text
OSError: [Errno 8] Exec format error: './tidy.sh'
```

Why?
--- choice
Python needs `chmod +x` to be run again after the file was last saved.
--- choice correct
Only a shell falls back to reading a file without `#!` itself. Python asks the kernel to run the file directly, and the kernel knows neither a compiled program nor a `#!` script in it.
--- choice
Python runs scripts with `/bin/sh`, which is `dash` on Ubuntu and rejects bash features.
--- choice
The file has Windows line endings, which only Python notices.
--- why
When bash's request to run a file fails with "exec format error", bash quietly runs the file with itself instead. That rescue belongs to shells, not to the kernel. Python's `subprocess`, `make`, `systemd` and CI runners all call the kernel directly, so they fail. The fix is to give the script a shebang. Windows line endings give a different message: the interpreter named on the first line "is not found", because its name ends in a hidden carriage return.

+++ practice | The count that kills a clean run
--- task
`warns.sh` prints how many lines of a log contain `WARN`. It has `set -eo pipefail`, and on a log with no warnings it prints nothing and exits 1. It dies on the happy path.

Rewrite it so that:

- `bash warns.sh logs/clean.log` prints `warnings: 0` and exits 0;
- `bash warns.sh logs/noisy.log` prints `warnings: 2`;
- on a file that cannot be read, the script prints nothing to standard output and stops with status 2 before it counts anything. Record this case with `bash warns.sh logs/nope.log; echo $? > nope_status.txt`.

Keep `set -eo pipefail`.
--- starter
mkdir -p logs
printf 'case 1 OK\ncase 2 OK\n' > logs/clean.log
printf 'case 1 WARN retry\ncase 2 OK\ncase 3 WARN retry\n' > logs/noisy.log
printf '#!/usr/bin/env bash\nset -eo pipefail\nn=$(grep -c WARN "$1")\necho "warnings: $n"\n' > warns.sh
--- solution
echo '#!/usr/bin/env bash' > warns.sh
echo 'set -eo pipefail' >> warns.sh
echo 'if [ ! -r "$1" ]; then exit 2; fi' >> warns.sh
echo 'n=$(grep -c WARN "$1" || true)' >> warns.sh
echo 'echo "warnings: $n"' >> warns.sh
bash warns.sh logs/clean.log
bash warns.sh logs/noisy.log
bash warns.sh logs/nope.log; echo $? > nope_status.txt
--- hint
`grep -c` prints `0` and exits 1 when nothing matches. An assignment's status is the status of its command substitution, so `set -e` ends the script.
--- hint
`cmd || true` says "a failure here is fine". But it also swallows the "cannot read the file" failure, so check that the file is readable first: `[ -r "$1" ]` is true when it is.
--- check shell | A clean log gives zero, not a silent death
printed-line warnings: 0
--- check shell | A noisy log is counted
printed-line warnings: 2
--- check shell | A missing log still stops the script with status 2
file nope_status.txt == 2

+++ practice | The and-and chain that hides a failed case
--- task
`sweep.sh` has `set -e`, and it runs three cases. Case 2 fails with status 3. Yet the sweep goes on to case 3, prints `sweep finished` and exits 0.

Change the loop body so that the sweep stops at the first failed case, with that case's status. After each case that succeeds, it must still append `case N ok` to `done.txt`.

--- hint

--- check shell | Only the case that succeeded before the failure is recorded

--- check shell | The sweep stopped with the failed case's status
printed-line case 2 diverged
file status.txt == 3
--- check shell | The chain is gone

+++ question | Which line ends the script
--- ask
Which line ends this script, if any?

```bash
#!/usr/bin/env bash
set -euo pipefail
false || true                          # line A
out="$(false; echo ok)"                # line B
if ! grep -q NOPE /etc/hostname; then :; fi   # line C
n=$(false)                             # line D
echo "end"
```
--- choice
Line A: `false` fails, and `set -e` stops the script.
--- choice
Line B: the substitution contains a failing command.
--- choice
Line C: `grep` finds nothing and returns 1.
--- choice correct
Line D: the assignment's status is `false`'s status, and nothing is testing it.
--- choice
None of them: the script prints `end`.
--- why
`set -e` ignores a failure whose status is being used: the left side of `||` (A) and the condition of an `if`, here negated with `!` (C). In B the substitution runs in a subshell that does not inherit `-e`, so `false` is ignored there, and the last command, `echo ok`, succeeds. In D the whole line is a plain assignment, whose status is its substitution's status, 1, so the script ends with status 1 before `end`.

+++ question | A loop over a quoted list
--- ask
What does this print?

```bash
files="a.txt b.txt"
for f in "$files"; do echo "<$f>"; done
```
--- answer
<a.txt b.txt>
--- why
The quotes stop word splitting, so `"$files"` is one word, `a.txt b.txt`, and the loop runs once with that whole value. Quoting is right when a variable holds one value. When you need a list of separate values, keep them as separate words from the start: a glob, the script's arguments, or an array.

+++ question | An array after an unset
--- ask
What does the last line print?

```bash
a=(alpha "two words")
a+=(gamma)
unset "a[0]"
echo "${#a[@]} ${!a[@]}"
```
--- answer
2 1 2
--- why
`+=( )` appends `gamma` at index 2. `unset "a[0]"` removes element 0 and leaves a hole, so the array holds indices 1 and 2. `${#a[@]}` counts elements, 2, and `${!a[@]}` lists the indices, `1 2`. That hole is why a loop counting from 0 to the length is wrong for arrays; loop over `"${a[@]}"` or `"${!a[@]}"` instead.

+++ question | The status after a clean re-raise
--- ask
A driver has this handler, installed with `trap 'on_term' TERM`:

+++ question | Cleanup that arrives ten minutes late
--- ask
A script's last line is `sleep 600`, standing in for a long simulation case. It has a `TERM` handler that prints a message and removes a scratch folder. You send `kill -TERM` one second after starting it. The message appears only ten minutes later. Why, and what fixes it?
--- choice
`sleep` blocks all signals; replace it with a loop of `sleep 1`.
--- choice correct
Bash runs a trap only after the foreground command it is waiting for finishes. Start the long command in the background and `wait "$!"` for it: a caught signal interrupts `wait` at once.
--- choice

--- choice

+++ question | What getopts leaves behind
--- ask
`sweep.sh` parses its options like this:

```bash
n=10; out=results; verbose=0
while getopts ":n:o:v" opt; do
  case "$opt" in
    n) n="$OPTARG" ;;
    o) out="$OPTARG" ;;
    v) verbose=1 ;;
    :) echo "missing value for -$OPTARG" >&2; exit 2 ;;
    \?) echo "unknown option -$OPTARG" >&2; exit 2 ;;
  esac
done
shift $((OPTIND - 1))
echo "n=$n out=$out verbose=$verbose files=$#"
```

What does `./sweep.sh -vn 20 -o camp a.log b.log` print?
--- answer

--- why
`-vn 20` is two bundled options: `-v`, which takes no value, and `-n`, whose value is the next word, `20`. `-o camp` sets `out`. The first word that is not an option, `a.log`, is word 5, so the loop ends with `OPTIND` at 5, and `shift 4` removes the four option words (`-vn`, `20`, `-o`, `camp`), leaving the two file names. A colon after a letter in `":n:o:v"` means that option takes a value; the colon at the front switches on the script's own error messages.

+++ question | A mean over one channel
--- ask
`run.log` holds these four lines:

```text
t=1 chan=TANK val=310
t=2 chan=BUS val=28
t=3 chan=TANK val=316
t=4 chan=BUS val=29
```

What does this print?

```bash
awk -F'[= ]+' '$4 == "TANK" { n++; s += $6 } END { print n, s / n }' run.log
```
--- answer
2 313
--- why
The separator `[= ]+` cuts `t=1 chan=TANK val=310` into six fields: `t`, `1`, `chan`, `TANK`, `val`, `310`. So `$4` is the channel and `$6` the value. Two lines are `TANK`; their values add to 626, and 626 / 2 is 313. Counting `n` in the same rule that adds to `s` is what makes the mean right; dividing by `NR` would divide by all four lines.

+++ question | An empty field with an explicit separator
--- ask
What does this print?

```bash
printf 'A,B,,D\n' | awk -F, '{ print NF, $3 "|" $NF }'
```
--- answer
4 |D
--- why
With `-F,` every comma is a cut, so the two commas in a row make an empty third field: four fields, `A`, `B`, empty and `D`. `print NF, …` puts a space (the `OFS`) between its comma-separated items, and `$3 "|" $NF` joins an empty string, a bar and `D`. Only the default whitespace splitting merges runs of separators; an explicit separator never does.

--- why

+++ question | Keeping the failure visible
--- ask
`shellcheck` reports SC2155 on this line inside a function:

```bash

```

Which rewrite removes the warning and lets `set -e` see a failing `run_case`?
--- choice
`local out="$(run_case "$c")"`
--- choice correct
`local out` on one line, then `out=$(run_case "$c")` on the next.
--- choice
`# shellcheck disable=SC2155` above the line.
--- choice
`local out=$(run_case "$c") || true`
--- why
`local` is a command, and when the assignment is one of its arguments, the line's status is `local`'s own: success. The failure of `run_case` is thrown away. +++ question | Killed by the kernel
--- ask
A driver sets `trap 'rm -rf "$tmp"' EXIT` right after `tmp=$(mktemp -d)`. One night the scheduler's log shows it ended with status 137, and its scratch folder is still on disk. Which statement is true?
--- choice
The trap was quoted wrongly; with double quotes it would have run.
--- choice
The script must have called `exit 137` itself, which skips `EXIT` traps.
--- choice correct
137 is 128 + 9: the driver was killed with `SIGKILL`, often by the out-of-memory killer. No trap can run for it, so the script should remove stale scratch folders of its own when it starts.
--- choice
137 means `SIGTERM`; adding `TERM` to the trap line would have cleaned up.
--- why
A status above 128 means "killed by signal N", with N = status − 128, and 9 is `SIGKILL`. The kernel carries it out without asking the process, so no handler of any kind runs. An `EXIT` trap covers normal ends, `exit`, `set -e` failures, `INT` and `TERM` — 130 and 143 — but not this. The defence is outside the dying process: a fixed scratch path per job, cleaned at the next start, or a sweeper.

`opt` is `?` and `OPTARG` is unset, and `getopts` prints its own message.
--- why
The colon after `c` says `-c` takes a value, and there is none. With the leading colon in the option string (silent mode), a missing value sets `opt` to `:` and puts the letter in `OPTARG`, so the script can print its own message. +++ question | Skipping every header
--- ask
`a.tsv` has 4 lines and `b.tsv` has 3; each starts with one header line. What does this print?

```bash
awk 'FNR == 1 { next } { n++ } END { print n }' a.tsv b.tsv
```
--- answer
5
--- why
`FNR` counts lines within the current file and starts again at 1 for each new file, so `FNR == 1` is true on both headers, and `next` skips them. That leaves 3 data lines from `a.tsv` and 2 from `b.tsv`. `NR == 1` would have skipped only the first file's header, because `NR` keeps counting across files.

+++ question | Whole numbers and decimals
--- ask
What does this print?

```bash
total=15; n=4
echo "$(( total / n )) $(awk -v t="$total" -v n="$n" 'BEGIN { printf "%.2f", t / n }')"
```
--- answer
3 3.75
--- why
Bash arithmetic has only whole numbers, and division drops the fraction: 15 / 4 is 3. `awk` works in floating point, and `%.2f` prints two decimal places. The values go in with `-v`, never pasted into the program text. Arithmetic on measurements is also one of the signals that the logic has outgrown bash.

+++ question | Three ways to pass an array
--- ask
What does this print?

```bash
count() { local label=$1; shift; echo "$label:$#"; }
flags=(--seed 42 --out "entry burn 01")
count A "${flags[@]}"
count B ${flags[@]}
count C "${flags[*]}"
```
--- choice
`A:4`, `B:4`, `C:4`
--- choice correct
`A:4`, `B:6`, `C:1`
--- choice
`A:5`, `B:7`, `C:2`
--- choice
`A:1`, `B:6`, `C:4`
--- why
Inside the function, `shift` removes the label, so `$#` counts only what came after it. `"${flags[@]}"` gives one word per element: 4. Unquoted, each element is split again, and `entry burn 01` becomes three words: 6. `"${flags[*]}"` joins everything into one word: 1. The same three spellings with `"$@"`, `$@` and `"$*"` behave the same way, which is why forwarding is always `"$@"` or `"${arr[@]}"`.

+++ question | Which tests say 9 is less than 100
--- ask
Which letters does this print? Type them in order, separated by spaces.

```bash

[[ $v < 100 ]] && echo A
[[ $v -lt 100 ]] && echo B
(( v < 100 )) && echo C
[ "$v" \< 100 ] && echo D
```
--- answer
B C
BC
B, C
B,C
--- why
Inside `[[ ]]` and `[ ]`, the symbol-shaped `<` compares strings in dictionary order, and the character `9` sorts after `1`, so A and D are false. `-lt` is the numeric test (B), and inside `(( ))` everything is arithmetic, so `<` means what it looks like (C). Numbers read from logs arrive as text, and a string comparison that is right for 1 to 9 is wrong from 10 on.

+++ question | The right crontab line
--- ask
Which crontab line runs `/srv/bin/sync.sh` at 02:15 on weekdays and keeps both its output and its error messages in `/srv/log/sync.log`?
--- choice
`2 15 * * 1-5 /srv/bin/sync.sh >> /srv/log/sync.log 2>&1`
--- choice correct
`15 2 * * 1-5 /srv/bin/sync.sh >> /srv/log/sync.log 2>&1`
--- choice
`15 2 * * 1-5 /srv/bin/sync.sh 2>&1 >> /srv/log/sync.log`
--- choice
`15 2 1-5 * * /srv/bin/sync.sh >> /srv/log/sync.log 2>&1`
--- why
The fields are minute, hour, day of month, month, day of week, so 02:15 on weekdays is `15 2 * * 1-5`.
