+++ question | A mask of 007
--- ask
Your umask is `007`. You run `mkdir results`. What mode does the new folder `results` get? Type it in digits.
--- answer
770
0770
rwxrwx---
drwxrwx---
--- why
A new folder asks for 777, and the kernel then removes every bit that is set in the mask. The mask 007 blocks nothing for the owner and nothing for the group, and blocks read, write and execute for others. So the owner keeps `rwx` (7), the group keeps `rwx` (7), and others get nothing (0): 770. A file made under the same mask asks for 666 and gets 660, which is why 007 suits a folder shared by a team and closed to everyone else.

+++ question | The owner who cannot write
--- ask
`ls -l` shows:

```text
-r--rw-r-- 1 ana team 812 Apr  2 09:10 limits.yaml
```

Ana owns the file and is also a member of `team`. Can Ana add a line to it without changing its mode first?
--- choice
Yes: she is in `team`, and the group has write permission.
--- choice correct
No: for the owner the kernel checks only the owner's three bits, and they say `r--`.
--- choice
Yes: the owner of a file can always write to it.
--- choice
No: nobody can write a file whose last three bits have no `w`.
--- why
The kernel checks exactly one group of three bits. If you are the owner, it uses the owner's bits and stops; it never falls back to the group's, even when they would allow more. So Ana, the owner, is refused, while any other member of `team` may write. Ana can still fix it, because the owner may always run `chmod` on her own file: `chmod u+w limits.yaml`.

+++ question | What capital X can bring back
--- ask
After an accidental `chmod -R 644 tree`, someone runs `chmod -R u+rwX,go+rX tree` to repair it. `tree` holds folders, data files and a few shell scripts. What is the result?
--- choice
Everything is exactly as it was before the accident.
--- choice correct
The folders get their `x` back, but the scripts stay without `x`: nothing on disk records that they were programs.
--- choice
Folders, data files and scripts all get `x`.
--- choice
Nothing gets `x`: capital `X` only acts on things that are already executable, and nothing is.
--- why
Capital `X` adds execute to every folder, and to a file only if at least one of its execute bits is already set. The 644 removed execute from everything, so no file qualifies any more; the folders do, because `X` always applies to folders. The folders become passable again and the data files are right, but each script must be marked by name with `chmod +x`. That is why a digit-style `chmod -R` on a mixed tree does damage that cannot be undone automatically.

=== lnx01-l04 | Practice: Processes, signals and job control
--- for
l04-processes-signals-and-job-control

+++ question | Interrupted, by number
--- ask
A solver that installs no signal handlers of its own is running as process 4211. You send it `kill -INT 4211`, the same signal `Ctrl-C` sends, and it ends. What exit status does the shell report for it? Type the number.
--- answer
130
--- why
`SIGINT` is signal 2. The solver has no handler, so the default action runs and the process is terminated by the signal. A process killed by signal N is reported as 128 + N, so 128 + 2 = 130. The same rule gives 143 for `SIGTERM` (15) and 137 for `SIGKILL` (9). A status above 128 tells you that something outside the program ended it.

+++ question | Parked on purpose
--- ask
To let an urgent job run, you pause a large analysis with `kill -STOP 5120`. Which statement about process 5120 is true while it stays stopped?
--- choice correct
It gets no CPU time, but it keeps all its memory and open files; `kill -CONT 5120` resumes it exactly where it was.
--- choice
Its memory is written to disk and freed until it is resumed.
--- choice
It restarts from the beginning when it receives `SIGCONT`.
--- choice
It could have ignored the stop if its authors had installed a handler for it.
--- why
A stopped process, state `T`, is simply not scheduled: it keeps its place in the calculation, its open files and all of its memory. `SIGCONT` puts it back in line for the CPU. Two consequences: stopping a job does not free memory for anyone else, and `SIGSTOP`, like `SIGKILL`, can never be caught, blocked or ignored. `Ctrl-Z` sends `SIGTSTP`, the catchable cousin.

+++ question | A busy machine that is not computing
--- ask
On a machine where `nproc` prints 8, `uptime` shows `load average: 16.2, 15.8, 9.0`. `top` shows `3.0 us`, `1.0 sy` and `90.0 wa`, and many processes are in state `D`. What is the best reading?
--- choice
The CPUs are overloaded twice over: add more cores or run fewer jobs at once.
--- choice correct
The tasks are waiting on disk or network I/O, not computing; more threads or cores will not help, so find what they are waiting on.
--- choice
The load is falling fast, so the problem is already over.
--- choice
`D` marks daemons, so the load comes from background services and can be ignored.
--- why
The load average counts tasks that are runnable **or** in uninterruptible sleep, `D`. Here the CPU is almost idle (3% user, 1% system) and 90% of the time is spent waiting for I/O, so the high load is a queue in front of a disk or a network file server, not a shortage of CPUs. The trend, 16.2 over one minute against 9.0 over fifteen, says it got worse recently. Adding work makes the queue longer.

+++ question | Thousands of zombies
--- ask
`ps` lists 4,000 processes in state `Z`, all with the same parent, `collector` (process 812). What is the right fix?
--- choice
`kill -9` each zombie: `SIGKILL` cannot be ignored.
--- choice correct
Fix or restart the parent, `collector`: the zombies are finished processes waiting for their parent to collect their exit status.
--- choice
Reboot at once: the zombies are using all the CPU.
--- choice
Nothing ever: zombies disappear on their own after a few minutes.
--- why

+++ question | Leaving now, and no tmux
--- ask
Over SSH you started `./run_campaign.sh > run.log 2>&1 &` and it is job 1. You have to disconnect in a minute, and tmux is not installed. Which single command, typed now, keeps the job running after the connection drops?
--- choice

--- choice correct
`disown %1`
--- choice
`nice -n 19 ./run_campaign.sh`
--- choice
`kill -STOP %1`
--- why
When the connection drops, your shell receives `SIGHUP` and passes it on to every job on its job list, and the default action of `SIGHUP` is to terminate. `disown %1` removes the job from that list, so the shell never passes the hang-up on. `bg` changes nothing: the job is already in the background and still on the list. `nice` only changes CPU priority (and would start a second copy). `kill -STOP` freezes the job. +++ question | A key that is too open
--- ask
`ssh sim01` prints `Permissions 0644 for '/home/eng/.ssh/id_ed25519' are too open.` and ignores the key. Which mode should the private key file have? Type it in digits.
--- answer
600

--- why
SSH refuses a private key that anyone but its owner could read, so the group and others bits must all be 0. +++ question | Who logs in
--- ask
Your `~/.ssh/config` is:


--- answer

--- why
For each setting, the first value found wins. `Host *` matches every name and comes first, so `User root` is set before the `sim01` block is read, and the later `User eng` is ignored. `HostName` still comes from the `sim01` block, because nothing set it earlier. +++ question | Running, but not for long
--- ask
`systemctl status license-srv` shows:

```text
     Active: active (running) since Mon 2026-03-02 08:14:02 UTC; 1 month ago
```

--- choice correct

--- choice

--- choice

--- choice

--- why
Running now and starting at boot are two separate facts. `start` and `stop` are about now; `enable` and `disable` are about boot. `disabled` on the `Loaded:` line means there is no link in any target's `.wants` folder, so boot will not pull it in. +++ question | A loop that never trips the limit
--- ask
A unit has `Restart=on-failure` and `RestartSec=5`. Its program dies with an error one second after every start. The start limit is the default of 5 starts within 10 seconds. What happens?
--- choice correct

--- choice

--- choice

--- choice

The service crash-loops for ever. The tell is `Active: active (running) since 3s ago` every time you look; `journalctl -u NAME` shows the repeating cycle and the program's last words.

+++ question | Changing a packaged unit

=== lnx01-l13 | Practice: Diagnosing a machine, disk, network, syscalls, kernel

+++ question | Small files, two sizes
--- ask
A folder holds 100,000 files of 100 bytes each, on a filesystem with 4 KiB blocks. Roughly what do `du -sb` and `du -sh` report for it?
--- choice correct
`du -sb` about 10 MB, the bytes written; `du -sh` about 400 MB, the whole blocks the files take up.
--- choice
Both about 10 MB.
--- choice
Both about 400 MB.
--- choice
`du -sh` about 10 MB and `du -sb` about 400 MB.
--- why
`du -sb` counts bytes written, as `ls -l` does: 100,000 × 100 = 10,000,000 bytes, about 10 MB. Plain `du` counts blocks, and each tiny file takes a whole 4096-byte block: 100,000 × 4096 = 409,600,000 bytes, which `du -sh` shows as about 391M. Forty times more disk than data: many tiny files waste space, and they use up inodes as well.

On a folder, `r` means reading the list of names, and `x` means going through the folder to use a name. Others have `r--` on `results`, so the names can be listed and nothing can be reached; the file's own 644 is never even checked. `ls -l results` would show a row of question marks for the same reason. `chmod o+x results` (755 in all) would let Bob in.

+++ question | A handler that exits cleanly
--- ask
A solver installs a handler for `SIGTERM` that flushes its output and then exits with status 0. You run `kill 5120` on it, and it ends. What exit status does the shell report? Type the number.
--- answer
0
--- why
`kill` sends `SIGTERM` by default, and this program catches it: its handler runs, flushes, and chooses to exit with 0. The status 128 + 15 = 143 appears only when the signal's default action terminates a program that has no handler. With `kill -9`, `SIGKILL` cannot be caught, the handler never runs, nothing is flushed, and the status is 137.

+++ question | One job dies, one lives
--- ask
Over SSH you start the same six-hour job twice: once with `./sweep.sh &` in your login shell, and once inside a tmux session that you then detach from. The connection drops. What happens, and why?
--- choice correct
The `&` job dies from the `SIGHUP` your login shell passes on to its jobs; the tmux job lives, because its terminal belongs to the tmux server, which the dropped connection never touches.
--- choice
Both survive: `&` puts a job in the background, and background jobs never receive `SIGHUP`.
--- choice
Both die: the kernel ends every process you started when your connection drops.
--- choice
The tmux job dies too, unless it was also started with `nohup` inside tmux.
--- why
`&` only frees your prompt; the job stays on your shell's job list and in your terminal's session. When the connection drops, the shell gets `SIGHUP` and passes it on to every job, and the default action is to terminate. Inside tmux, the only thing attached to your SSH terminal is the tmux client, which exits. The job's terminal was created by the tmux server, a separate process with no link to your login, so no hang-up reaches it.

+++ question | The slash that was left off
--- ask
On your laptop you run `rsync -a runs sim01:/srv/campaign/runs/`, with no slash after the first `runs`. Where does the laptop's `runs/case_0001.log` end up on `sim01`? Type the full path.
--- answer
/srv/campaign/runs/runs/case_0001.log
--- why
Without a trailing slash, the source means "this folder itself", so rsync creates a folder `runs` inside the destination: `/srv/campaign/runs/runs/`. With a slash, `runs/` means "the contents of this folder", and the logs land directly in `/srv/campaign/runs/`. A slash at the end of the destination makes no difference. Say it aloud before running: "contents of runs, into runs".

+++ question | A dashboard two hops away
--- ask
A dashboard runs on `gpu07` and listens on port 3000 on all its addresses. Your laptop cannot reach `gpu07`, but `sim01` can, and you can SSH to `sim01`. Which command makes `http://localhost:3000` on your laptop show the dashboard?
--- choice correct
`ssh -f -N -L 3000:gpu07:3000 sim01`
--- choice
`ssh -f -N -L 3000:127.0.0.1:3000 sim01`
--- choice
`ssh -f -N -R 3000:gpu07:3000 sim01`
--- choice
`ssh -f -N -L 3000:127.0.0.1:3000 gpu07`

In `-L local:host:port`, the `host:port` part is dialed **by the server**, here `sim01`. +++ question | Appended, and still not used
--- ask
You put your own `python3` wrapper in `~/bin`, and your `~/.bash_profile` has `export PATH="$PATH:$HOME/bin"`. In a brand-new login shell, `type python3` still says `python3 is /usr/bin/python3`. Why?
--- choice correct
The line appends `~/bin` to the end of `PATH`, and the search stops at the first match, which is `/usr/bin/python3`; to override, prepend it instead.
--- choice
`$HOME` is not expanded inside `PATH`.
--- choice
Programs in your own `~/bin` must always be started with `./`.
--- choice
`PATH` is searched from right to left, so `~/bin` should be listed first to be searched last.
--- why
The shell searches the folders in `PATH` from left to right and runs the first match. Appending puts `~/bin` last, so it is used only for names nothing earlier provides; `/usr/bin` comes first and wins. `export PATH="$HOME/bin:$PATH"` puts your folder first, so it shadows the system's copy. `./` is needed only for a folder that is not on `PATH`, such as the current one.

+++ question | Two solver versions, side by side
--- ask
On a machine you administer, you must keep solver 2.1 working and also install version 3.0 from source, so that both can be used. Which layout is right?
--- choice correct
Install each under its own prefix, such as `--prefix=/opt/solver-2.1` and `--prefix=/opt/solver-3.0`, and choose one with `PATH`.
--- choice
`--prefix=/usr` for 3.0, so that it replaces the packaged files in the standard place.
--- choice
The default prefix for both: `/usr/local` keeps them apart automatically.
--- choice
Install 3.0 with `make install` into `/usr/bin`, and keep 2.1 as the package.
--- why
`/usr` belongs to the package manager: files you install there are overwritten by the next upgrade and make `dpkg -S` misleading. Two builds with the same default prefix, `/usr/local`, land on the same paths, so the second overwrites the first. A versioned prefix under `/opt` keeps each version complete and separate, and one `PATH` line picks which one runs, which is also how you reproduce last quarter's results with last quarter's solver.

+++ question | Started, then failed
--- ask
`systemctl start sim-post; echo $?` prints `0`. A minute later `systemctl is-active sim-post` prints `failed`. Which statement is true?
--- choice correct
`start` only reported that systemd launched the program; the program then exited with an error. `systemctl status sim-post` and `journalctl -u sim-post` show why.
--- choice
The service ran successfully, as the `0` proves; `is-active` is showing a stale state.
--- choice
The unit file changed on disk, and `failed` goes away after `systemctl daemon-reload`.
--- choice
The unit is disabled, so systemd stopped it after a minute.
--- why
`systemctl start` succeeds once the process has been launched; what the program does afterwards is a separate question. `status` shows the result (`failed (Result: exit-code)`), how long it ran and its exit code, and the log lines under it usually name the cause, such as a missing file. `disabled` is about boot and has nothing to do with a service stopping.

+++ question | A 404, according to curl
--- ask
The page `https://sim01:8443/status` answers with HTTP status 404. You run `curl -sS -o /dev/null https://sim01:8443/status; echo $?`. What number is printed? Type it.
--- answer
0
--- why
`curl` counts any answer from the server as success: the network worked and the server replied, so the exit status is 0 even though the page is missing. A script that tests only `$?` would call this page healthy. With `-f` (`--fail`), any HTTP status of 400 or more becomes exit status 22. +++ question | :wq in insert mode
--- ask
You are typing in vim, and the bottom line shows `-- INSERT --`. You type `:wq` and press Enter. What happens?
--- choice correct
The characters `:wq` and a new line are typed into the file, and you are still in insert mode; press `Esc` first, then `:wq`.
--- choice
The file is saved and vim quits.
--- choice
vim refuses with `E37: No write since last change`.
--- choice
The file is saved, but vim stays open until you press `Esc`.
--- why
In insert mode every key is a character for the file, so `:`, `w`, `q` and Enter are simply typed in. Commands such as `:wq` work only from normal mode, and `Esc` always gets you there. If you are unsure which mode you are in, press `Esc` twice, then type the command.
