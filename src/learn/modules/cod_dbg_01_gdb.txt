=== dbg01-l01 | Practice: Debugging as an experiment

+++ question | Which one is the infection?
--- ask
A star tracker program keeps the spacecraft's attitude as a quaternion, four numbers whose squares should add up to 1. Line 40 is meant to normalize it, but it divides each of the four numbers by the sum of their squares instead of by the square root of that sum. The quaternion stored in memory now has a length of 0.98. Three minutes later, the ground display shows the spacecraft slowly spinning, although it is holding still.

In the words of the lesson, what is the **infection**?
--- choice correct
The quaternion with length 0.98, sitting in memory.
--- choice
Line 40, which divides by the wrong number.
--- choice
The spinning attitude on the ground display.
--- choice
The three minutes between line 40 running and the display going wrong.
--- why
The defect is the wrong line of code (line 40). The infection is the bad value that line creates in memory (the quaternion that is no longer of length 1). The failure is what you finally see from outside (the display shows a spin). Debugging walks backwards from the failure, through the infection, to the defect. Fixing the display code would treat the stain on the ceiling and leave the leaking pipe alone.

+++ question | How long to trust a fix
--- ask
Before your fix, the Monte Carlo suite failed about once in 200 runs. After the fix, you want to be 95% sure that the bug, if it were still there, would have shown up at least once. About how many runs in a row, all passing, do you need?
--- choice
200 runs, because that is how often it failed.
--- choice
About 300 runs.
--- choice correct
About 600 runs.
--- choice
About 20,000 runs.
--- why
If the bug were still present, each run would miss it with probability $1 - \tfrac{1}{200} = 0.995$. All $n$ runs miss it with probability $0.995^n$, and you want that to be at most 0.05: $n \ge \ln 0.05 / \ln 0.995 = -2.996 / -0.00501 \approx 598$. That is the "about $3N$ runs for a one-in-$N$ failure" rule. After only 200 passing runs, a bug that is still there would have stayed hidden about $0.995^{200} \approx 37\%$ of the time.

+++ question | Tests to bisect a log
--- ask
A 5,000-line sensor log makes a program fail, and an empty log makes it pass. The failure has one switch point: every prefix shorter than some length passes, and every longer one fails. You bisect on the prefix length. At most how many test runs does bisection need to find the first line that breaks it? Type a whole number.
--- answer
13
13 tests
13 runs
--- why
Each test halves the range of possible lengths, so the most tests is $\lceil \log_2 5000 \rceil$. $2^{12} = 4096$ is less than 5,000 and $2^{13} = 8192$ is more, so $\log_2 5000 \approx 12.3$, which rounds up to 13. Thirteen runs instead of up to 5,000.

+++ question | A bisect script with set -e
--- ask
A teammate writes this script for `git bisect run`:

```bash
#!/usr/bin/env bash
# repro.sh: exit 0 if this commit is good, non-zero if the bug is present.
set -euo pipefail
g++ -O0 -o /tmp/nav_bisect nav.cpp
./tests/replay.sh /tmp/nav_bisect data/pass_17.log
```

Some commits in the range do not compile. What goes wrong at those commits, and what is the fix?
--- choice
Nothing: `set -e` makes git skip any commit where a command fails.
--- choice
The script keeps going and runs the old `/tmp/nav_bisect` from an earlier step, so the verdict belongs to another commit. Adding `set -e` would fix it.
--- choice
`git bisect run` stops the whole search with an error at the first commit that does not compile.
--- choice correct
`g++` fails, `set -e` ends the script with g++'s non-zero status, and git marks the commit bad. Bisection can then blame the wrong commit. Write `g++ -O0 -o /tmp/nav_bisect nav.cpp || exit 125` so git skips commits it cannot build.
--- why
`git bisect run` reads only the script's exit status: 0 is good, 125 is skip, and other codes from 1 to 127 are bad. With `set -e`, a failed build ends the script with the compiler's status, 1, so a commit that could not even be tested is reported as containing the bug. Git trusts every verdict, so one false "bad" can move the answer to the wrong commit. The `|| exit 125` turns "cannot build" into "skip". (Without `set -e`, the danger in the choice about the old binary would be real: the script would carry on and test the old binary from an earlier step. Either way, the build line needs its own explicit check.)

+++ question | A fix that only hides the failure
--- ask
A heading filter averages the samples that passed a quality check:

```cpp
double mean_heading = sum / n_valid;
if (std::isnan(mean_heading)) mean_heading = 0.0;   // the fix
```

Before the fix, the program printed `nan` when no sample passed the check, because `n_valid` was 0 and `sum` was 0.0. After the fix, the test that printed `nan` passes. What is wrong with this fix?
--- choice
Nothing: the test that failed now passes, and that is what verifying a fix means.
--- choice
`std::isnan` cannot detect the result of $0.0 / 0$, so the check never runs.
--- choice correct
It treats the failure, not the defect. When no sample is valid, the program now reports a heading of 0 degrees as if it were real. The code should notice `n_valid == 0` and report "no valid heading" instead.
--- choice
The fix is right, but it belongs before the division, so that the division never produces a NaN.
--- why
A NaN was an honest signal that there was no answer. Replacing it with 0.0 turns an obvious failure into a believable wrong number, which is worse. The defect is dividing when there is nothing to average, so the fix belongs there: check `n_valid` and say that no heading is available. Verifying a fix also means asking whether it fixed the right thing, not only whether the red test turned green.

+++ question | Two bad samples and one reset
--- ask
`gyro_int` adds up one gyro sample per line and exits with status 1 if its total angle is not finite at the end. A line reading `RESET` sets the total back to 0. A 10,000-line log has a corrupt sample that reads `nan` at line 4,000, a `RESET` at line 4,100, and another `nan` sample at line 9,000.

You run the lesson's prefix-bisection script on it, starting from good = 0 and bad = 10,000. Which line does it report as the shortest failing prefix? Type the number.
--- answer
9000
9,000
line 9000
line 9,000
--- why
Prefixes shorter than 4,000 lines pass, 4,000 to 4,099 fail, 4,100 to 8,999 pass again (the reset cleared the NaN), and 9,000 or more fail. The first test is the middle, 5,000 lines: it passes, so good becomes 5,000. From then on the search only looks between 5,000 and 10,000, where the one switch point is line 9,000. The corrupt sample at line 4,000 is never found. Prefix bisection assumes a single switch point; when something in the input can undo the failure, it finds a switch, not necessarily the first one.

+++ question | Moving down the stack
--- ask
A telemetry program crashes, and `bt` prints:

```text
#0  __memmove_avx_unaligned_erms () at ../sysdeps/x86_64/multiarch/memmove-vec-unaligned-erms.S:317
#1  0x0000555555555a1c in pack_frame (buf=0x7fffffffc800 "", hdr=0x0) at telem.cpp:48
#2  0x0000555555555b40 in send_telemetry (link=...) at telem.cpp:71
#3  0x0000555555555c2e in main () at telem.cpp:102
```

You type `frame 3`, then `down`. Which function's variables does `print` now look at? Type the function name.
--- answer
send_telemetry
send_telemetry()
--- why
`frame 3` selects `main`, the outermost frame. `down` moves one frame back toward frame 0, the innermost, so you land in frame 2, `send_telemetry`. `up` goes toward `main`, `down` toward the frame where the program stopped. Frame 1 is also worth a look: `hdr=0x0` means `pack_frame` was handed a null header, and the library copy in frame 0 only tripped over it.

+++ question | A variable gdb cannot show
--- ask
You build with `g++ -g -O2 -o filt filt.cpp`, stop at a breakpoint inside the filter loop, and type `print dt`. gdb answers `$1 = <optimized out>`. What is going on, and what do you do?
--- choice correct
The optimizer kept `dt` in a register, or dropped it, so at this spot it has no home gdb can read. Rebuild with `-g -O0` for this session.
--- choice
`-g` was ignored because `-O2` came after it on the command line. Put `-g` last.
--- choice
`dt` is a local of another frame. Type `up` and print it there.
--- choice
The breakpoint is on a line before `dt` is set, so gdb refuses to print it.
--- why
`-g` adds the tables that map code back to lines and variables, and it works at any optimization level. But at `-O2` the compiler keeps values in registers, reuses those registers, and removes values it no longer needs, so a variable can truly have no location at that moment. With `-O0`, every variable stays in memory where gdb can find it. A variable that is not set yet is not reported as optimized out; gdb prints whatever bytes are in its slot.

+++ question | A watchpoint that stops inside the C library
--- ask
A packet's `gain` field keeps turning into 0. You set `watch p.gain` in `main`, where `p` lives, and continue. gdb stops here:

```text
Hardware watchpoint 2: p.gain

Old value = 0.80000000000000004
New value = 0
__memset_avx512_unaligned_erms () at ../sysdeps/x86_64/multiarch/memset-vec-unaligned-erms.S:217
```

That is a C library function you did not write. What is the next step?
--- choice
Continue: a watchpoint inside a library is a false alarm, and the real write will come later in your own code.
--- choice
Set a breakpoint on `memset` and run again, since `memset` must be broken.
--- choice
Replace `watch` with `watch -l`, because a hardware watchpoint cannot see writes made by library code.
--- choice correct
Type `bt`. The frames above `memset` show which line of your code called it and with what size. That call is the culprit.
--- why
The watchpoint caught the exact instruction that changed the value, and that instruction happens to be inside `memset`. A library function writes where it is told, so the question is who told it. `bt` answers: here the next frame was `clear_name (p=...) at cmd.cpp:21`, a call that cleared 24 bytes of a 16-byte name and ran over into `gain`. Walk up to your first frame and read the call there.

+++ question | A watchpoint that never fires
--- ask
You suspect that line 31, `sensor.mode = 0;`, is what switches the sensor to mode 0. You set `watch sensor.mode` and continue. The program runs to the end without the watchpoint ever stopping, yet a plain breakpoint shows that line 31 runs 50 times. Why, and how do you stop on every run of line 31?
--- choice
Hardware watchpoints only watch pointers. Use a software watchpoint.
--- choice
`sensor` is a global, and gdb deletes watchpoints on globals when `main` starts. Use `watch -l`.
--- choice correct
`mode` was already 0, so line 31 wrote the same value back, and `watch` only stops when the value changes. Put a breakpoint on line 31, or use `awatch sensor.mode`, which stops on every read or write.
--- choice
The watchpoint fired, but gdb only reports a watchpoint after the program exits.
--- why
A watchpoint compares the value before and after each write it sees, and it stops only when they differ. Writing 0 over 0 changes nothing, so it stays quiet. That is usually what you want: it skips harmless writes and stops at the one that corrupts. When you really want every access, `awatch` stops on reads and writes (it prints `Value = 0` each time), and `rwatch` on reads only.

+++ question | A condition with one equals sign
--- ask
A teammate sets this breakpoint to catch the moment the controller enters mode 2:

```text
(gdb) break control.cpp:40 if mode = 2
```

`mode` is a global. What happens when they run the program?
--- choice correct
gdb evaluates `mode = 2` as an assignment each time line 40 is reached. The result, 2, counts as true, so it stops on every pass, and it also sets `mode` to 2, changing the program's behavior.
--- choice
gdb rejects the command, because a condition must use `==`.
--- choice
It works as intended: gdb treats `=` in a condition as a comparison.
--- choice
The breakpoint never stops, because an assignment has no true or false value.
--- why
The condition is a C++ expression, evaluated in the program. `mode = 2` stores 2 in `mode` and has the value 2, which is not zero, so it counts as true. The breakpoint fires on every pass, and each check quietly forces the controller into mode 2: the debugger is now causing the behavior it was meant to catch. Write `if mode == 2`.

+++ question | Four gains and a mode
--- ask
Built with `g++ -g -O0`, counting lines from the first `#include` as line 1:

```cpp
struct Cmd {
    float gains[3];
    int   mode;                     // 2 = FINE_POINT, 0 = SAFE
};

void reset_gains(Cmd& c) {          // line 9
    for (int i = 0; i <= 3; ++i) {  // line 10
        c.gains[i] = 0.0f;          // line 11
    }
}
```

`main` makes `Cmd c{{0.5f, 0.2f, 0.1f}, 2};` and calls `reset_gains(c)`. After the call, the spacecraft is in SAFE mode. You set `watch c.mode` in `main` before the call and continue. What does gdb report?
--- choice
It stops at line 11 with `New value = 0`, the line that did the write.
--- choice
It never stops, because `reset_gains` only writes to `gains`, not to `mode`.
--- choice
It stops with `New value = 1065353216`, the bits of a float read as an int.
--- choice correct
It stops at line 10 with `Old value = 2` and `New value = 0`. The write was line 11, on the pass with `i = 3`.
--- why
The loop runs for `i` equal to 0, 1, 2 and 3, but `gains` has only three elements. `gains` takes bytes 0 to 11 of the struct and `mode` bytes 12 to 15, so `c.gains[3]` is the same 4 bytes as `mode`. Writing `0.0f` there stores four zero bytes, which read as the `int` 0: SAFE. A watchpoint reports after the write has finished, at the next thing to run, here the loop's `++i` on line 10, so the guilty line is the one before it. The fix is `i < 3`.

=== dbg01-l03 | Practice: Looking inside a stopped program

+++ question | How many bytes x reads
--- ask
`q` is an array of four `double`s holding an attitude quaternion. How many bytes of memory does `x/3xg &q` show? Type a whole number.
--- answer
24
24 bytes
--- why
The shape is `x/NFU`: N = 3 units, F = `x` for hexadecimal, U = `g` for "giant", 8 bytes. Three units of 8 bytes is 24 bytes, so it shows the first three elements of `q` as three 16-digit hex numbers, not the fourth.

+++ question | The middle of an array behind a pointer
--- ask
`raw` is an `int16_t*` pointing at 8 ADC counts. You want gdb to print only the elements at indices 2, 3, 4 and 5. Which command does that?
--- choice correct
`print raw[2]@4`
--- choice
`print raw@4`
--- choice
`print *raw@2..5`
--- choice
`x/4dh raw`
--- why
`@` repeats the value on its left: `raw[2]@4` means "four elements starting at `raw[2]`", so it prints `{30, 40, 50, 60}` when the counts are 10, 20, ..., 80. `raw@4` repeats the pointer itself, not what it points at. There is no range syntax with two dots. `x/4dh raw` does show four 2-byte numbers, but starting at element 0, not element 2 (`x/4dh raw+2` would work).

+++ question | A sync word in memory
--- ask
A telemetry frame starts with the 32-bit sync word `0x1ACFFC1D`. In your ground tool, running on x86-64, it is held in `std::uint32_t sync = 0x1ACFFC1D;`. What does `x/4xb &sync` print after the address? Type the four bytes as gdb shows them, separated by spaces.
--- answer
0x1d 0xfc 0xcf 0x1a
1d fc cf 1a
0x1D 0xFC 0xCF 0x1A
0x1d, 0xfc, 0xcf, 0x1a
--- why
x86-64 is little-endian: the least significant byte is stored at the lowest address. The least significant byte of `0x1ACFFC1D` is `0x1d`, so the bytes come out in reverse order: `0x1d 0xfc 0xcf 0x1a`. On the radio link the same word is sent big-endian, `1a cf fc 1d`, which is why a tool that copies it off the wire without swapping sees a different number.

+++ question | An array, and the pointer it became
--- ask
`main` declares `double samples[6] = {1.5, 2.5, 3.5, 4.5, 5.5, 6.5};` and calls `mean(samples, 6)`, where `mean` takes `const double* s`. Stopped inside `mean`, you type `print s`. Then you type `up` and `print samples`. What do you see?
--- choice
Both print all six numbers, because they are the same memory.
--- choice
`print s` shows the six numbers, and `print samples` fails because arrays cannot be printed without `@`.
--- choice
Both show only the address `0x7fffffffc900`.
--- choice correct
`print s` shows only an address, `(const double *) 0x7fffffffc900`. `print samples` in `main` shows all six numbers, because there it is an array whose size gdb knows.
--- why
In `main`, `samples` has the type `double [6]`, and gdb knows its length from the debug information. When passed to `mean`, the array decays to a pointer, and a pointer carries no length. So gdb prints the address and needs to be told the count: `print *s@6`, or `print *s@n`. The same memory, two types, two answers.

+++ question | Bytes of the wrong thing
--- ask
`state` is a `double*` pointing at a heap block of six doubles. To see the raw bytes of the first element, a teammate types:

```text
(gdb) x/8xb &state
0x7fffffffc8d8:	0xb0	0xb2	0x56	0x55	0x55	0x55	0x00	0x00
```

They conclude that the first state value is corrupted. What did they really look at?
--- choice
The first element, stored big-endian, so it must be byte-swapped to read.
--- choice
The first element, which holds a subnormal number close to zero.
--- choice correct
The 8 bytes of the pointer `state` itself, on the stack. Read backwards they are `0x000055555556b2b0`, a heap address. `x/8xb state` shows the first element.
--- choice
Random memory, because `x` cannot read heap addresses.
--- why
`&state` is the address of the pointer variable, so `x` dumped the pointer's own 8 bytes. Little-endian, backwards: `0x55555556b2b0`, which has the shape of a heap address. `x` wants the address of the data, and `state` already is that address, so `x/8xb state` (or `x/8xb &state[0]`) shows the double. With `x`, ask yourself whether the thing after the format is the address you mean.

+++ question | A crash with no names
--- ask
A supplier's library has no debug information. It crashes in a function that sums the bytes of a buffer:

```text
Program received signal SIGSEGV, Segmentation fault.
0x0000555555555149 in sum_bytes(unsigned char const*, int) ()
(gdb) x/i $pc
=> 0x555555555149 <_Z9sum_bytesPKhi+32>:	movzbl (%rdx,%rax,1),%eax
(gdb) info registers rax rdx
rax            0x7ffff000          2147479552
rdx            0x55555556b2b0      93824992326320
```

In AT&T syntax, `(%rdx,%rax,1)` means "the memory at address rdx + rax × 1", and `movzbl` loads one byte. What do the registers suggest?
--- choice correct
`rdx` looks like a sensible heap address for the buffer, and `rax` is an index of about 2.1 billion. The loop ran far past the end, so the length or loop count is wrong, not the buffer pointer.
--- choice
`rdx` is garbage, so the buffer pointer is bad and the caller passed a corrupt pointer.
--- choice
The instruction writes a byte, so the crash is a buffer overflow on the stack.
--- choice
Nothing can be concluded without debug information.
--- why
The instruction loads the byte at `rdx + rax`. `rdx` holds `0x55555556b2b0`, the shape of a heap address under gdb, so the buffer's start is plausible. `rax` is 2,147,479,552: no telemetry buffer is 2 GB long, so the index has run away, and reading that far past the buffer left the program's memory. Check the length the caller passed; a negative or uninitialized `int` length is a classic cause. Without names, `x/i $pc` and `info registers` still tell you which value was wrong.

=== dbg01-l04 | Practice: Stepping and changing state

+++ question | Where step lands
--- ask
A thermal model, built with `g++ -g -O0`, with line numbers counted from the `#include`:

```cpp
#include <cstdio>

double loss(double temp) {
    double k = 0.05;                  // line 4
    return k * (temp - 20.0);         // line 5
}

void limit(double& cmd) {
    if (cmd > 1.0) cmd = 1.0;         // line 9
}

int main() {
    double temp = 80.0;
    double throttle = 0.4;
    for (int i = 0; i < 3; i++) {     // line 15
        double q = loss(temp);        // line 16
        temp = temp - q * 10.0;       // line 17
        limit(throttle);              // line 18
    }
    std::printf("temp = %.2f, throttle = %.2f\n", temp, throttle);
    return 0;
}
```

You are stopped at a breakpoint on line 16 and type `step`. On which line does gdb stop? Type the line number.
--- answer
4
line 4
--- why
Line 16 calls `loss`, which has debug information, so `step` goes into it and stops at its first line, line 4, printing `loss (temp=80) at ...:4` on the way in. `next` would have run the whole call and stopped at line 17. gdb skips the function's setup code and stops at the first line of its body.

+++ question | Reusing a returned value
--- ask
Same program. On the second pass of the loop, where `temp` is 50, you step into `loss` and type `finish`. gdb prints `Value returned is $1 = 1.5`. You then type `print $ * 4`. What does gdb print as the value? Type the number.
--- answer
6
$2 = 6
6.0
--- why
`finish` saves the returned value in the value history as `$1`, and `$` on its own means the most recent value, here `$1`. So `print $ * 4` is $1.5 \times 4 = 6$, saved as `$2`. Check the 1.5 too: $0.05 \times (50 - 20) = 1.5$.

+++ question | until meets a breakpoint
--- ask
Same program. A breakpoint is set on line 16. On the first pass you walk with `next` through lines 16, 17 and 18, and arrive at line 15, the `for` line, about to add one to `i` and jump back. You type `until`, hoping to run the remaining passes and land on the `printf`. Where does gdb stop?
--- choice
On the `printf` line, because `until` never stops at an earlier line.
--- choice
On line 17, because `until` behaves exactly like `next`.
--- choice correct
On line 16 again, at the start of the second pass, because the breakpoint on line 16 stops it.
--- choice
Nowhere: `until` runs the program to the end.
--- why
`until` lets the program run at full speed and will not stop by itself at a line earlier than where you are, but any breakpoint met on the way still stops it. Line 16 is hit on the next pass, so you stop there with `i` equal to 1. Delete the breakpoint first (`delete 1`), or turn it off with `disable 1`, then `until` from line 15 runs the rest of the loop and lands on the `printf`.

+++ question | until at the top of the body
--- ask
Same program, no breakpoints left. You are stopped on line 16, the first line of the loop body, and type `until`. Where does gdb stop?
--- choice
On the `printf` line, after all three passes.
--- choice
Inside `loss`, on line 4.
--- choice
On line 15, the `for` line.
--- choice correct
On line 17, exactly as `next` would.
--- why
`until` is `next` with one extra rule: never stop at a line earlier in the program than the current one. Line 17 is later than line 16, so nothing stops it from stopping there, and it behaves like `next`. It only skips the rest of a loop when you type it at the bottom of the loop, where the next step would jump back up.

+++ question | Changing a value through a reference
--- ask
Same program. You set `break limit`, run, and stop on line 9 during the first pass. `limit` takes its argument by reference, `double& cmd`, and `main` passed `throttle`, which is 0.4. You type `set var cmd = 3.0`, then `delete`, then `continue`. What does the program print for `throttle`? Type the number as it prints.
--- answer
1.00
1
1.0
--- why
`cmd` is a reference: another name for `main`'s `throttle`, not a copy. So `set var cmd = 3.0` changes `throttle` itself to 3.0. Line 9 has not run yet, because gdb stops before the line, so it now runs, sees $3.0 > 1.0$, and clamps it to 1.0. The next two passes leave 1.0 alone. The program prints `temp = 27.50, throttle = 1.00`. With a parameter passed by value, the change would have been lost when `limit` returned.

+++ question | A print that moved the program on
--- ask
Built with `g++ -g -O0`:

```cpp
double table[6] = {1.5, 2.5, 3.5, 4.5, 5.5, 6.5};
int idx = 0;

double next_sample() {
    return table[idx++];
}

int main() {
    for (int k = 0; k < 3; ++k) {
        double s = next_sample();     // breakpoint here
        std::printf("%.1f\n", s);
    }
    return 0;
}
```

You stop at the breakpoint on the first pass, before the call runs. To check what the function returns, you type `print next_sample()` twice, then `delete` and `continue`. What does the program print? Type the three lines, separated by spaces.
--- answer
3.5 4.5 5.5
3.5, 4.5, 5.5
3.5,4.5,5.5
--- why
`print next_sample()` really runs the function inside the paused program, side effects included. The two prints returned 1.5 and 2.5, and each one moved `idx` on by one. So the program's own three calls read `table[2]`, `table[3]` and `table[4]`: 3.5, 4.5 and 5.5. The first two samples were used up by the debugger. Calling a function from gdb is an experiment on the program, and it can change what happens next.

=== dbg01-l05 | Practice: Attaching and core dumps

+++ question | Allowing core files
--- ask
`ulimit -c` prints `0` in your terminal. Which command, typed in that same terminal, lets the programs you start from it write core files of any size?
--- answer
ulimit -c unlimited
--- why
The core size limit belongs to the shell and to the programs it starts afterwards. A limit of 0 means "write nothing". `ulimit -c unlimited` removes it for this shell only, so reproduce the crash in the same terminal. Also check `/proc/sys/kernel/core_pattern` to know where the file will go.

+++ question | A core that went into a pipe
--- ask
You allowed core files and reproduced the crash. The shell printed `Segmentation fault (core dumped)`, but there is no `core` file in the working directory. `cat /proc/sys/kernel/core_pattern` prints:

```text
|/usr/lib/systemd/systemd-coredump %P %u %g %s %t %c %h
```

Where is the core, and how do you open it?
--- choice correct

+++ question | Which one is a race?
--- ask
Three programs share a global `int status = 0;` between `main` and one other thread:

- **A:** `main` sets `status = 1;`, then starts the thread, which reads `status`. `main` then joins the thread.
- **B:** the thread sets `status = 1;` and ends. `main` joins it, then reads `status`.
- **C:** `main` starts the thread, which sets `status = 1;`. While it runs, `main` reads `status` in a loop, and joins it at the end.

--- choice

--- choice
A and C, because both read `status` from a second thread.
--- choice
None, because an `int` is written in a single instruction.
--- choice correct
Only C.
--- why
TSan asks whether one access happens before the other. In A, everything `main` did before creating the thread happens before the thread starts. In B, the thread's end happens before the `join` returns, so `main`'s read comes after the write. In C, `main` reads while the thread may be writing, with nothing ordering them: a race, even if the loop happens to see the right value. "Single instruction" does not help: a data race is undefined behavior, and the compiler may, for example, keep `status` in a register and never see the change.

+++ question | Where the newest sample sits
