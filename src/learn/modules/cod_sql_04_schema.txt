+++ practice | Split the sheet into four tables
--- task
`tlm_sheet` holds one row per satellite, time and channel, and repeats everything else on every row. Its real rules are:

- `sat_id` decides `sat_name` and `operator`;
- `operator` decides `operator_country`;
- `channel` decides `units`;
- `(sat_id, ts, channel)` decides `value`.

Split it into third normal form. Create and fill these four tables, with every column `NOT NULL`:

- `operator (operator, country)`, key `operator`;
- `satellite (sat_id, sat_name, operator)`, key `sat_id`, with `operator` a foreign key that references `operator (operator)`;
- `channel (channel, units)`, key `channel`;
- `sample (sat_id, ts, channel, value)`, key `(sat_id, ts, channel)`, with `sat_id` referencing `satellite (sat_id)` and `channel` referencing `channel (channel)`.

Fill each one from `tlm_sheet`, so that each fact is stored once.
--- starter
-- Create the four tables, then fill them from tlm_sheet.

--- solution
CREATE TABLE operator (
    operator TEXT NOT NULL PRIMARY KEY,
    country  TEXT NOT NULL
);
CREATE TABLE satellite (
    sat_id   TEXT NOT NULL PRIMARY KEY,
    sat_name TEXT NOT NULL,
    operator TEXT NOT NULL REFERENCES operator (operator)
);
CREATE TABLE channel (
    channel TEXT NOT NULL PRIMARY KEY,
    units   TEXT NOT NULL
);
CREATE TABLE sample (
    sat_id  TEXT NOT NULL REFERENCES satellite (sat_id),
    ts      TEXT NOT NULL,
    channel TEXT NOT NULL REFERENCES channel (channel),
    value   REAL NOT NULL,
    PRIMARY KEY (sat_id, ts, channel)
);

INSERT INTO operator  SELECT DISTINCT operator, operator_country FROM tlm_sheet;
INSERT INTO satellite SELECT DISTINCT sat_id, sat_name, operator FROM tlm_sheet;
INSERT INTO channel   SELECT DISTINCT channel, units FROM tlm_sheet;
INSERT INTO sample    SELECT sat_id, ts, channel, value FROM tlm_sheet;
--- hint
One table per left side of a rule. Each table's key is that left side, and its other columns are what the left side decides.
--- hint
The copies collapse to one row per fact with `SELECT DISTINCT`, for example `INSERT INTO channel SELECT DISTINCT channel, units FROM tlm_sheet;`.
--- check query | Two operators, four satellites, three channels, eight samples
SELECT (SELECT COUNT(*) FROM operator), (SELECT COUNT(*) FROM satellite), (SELECT COUNT(*) FROM channel), (SELECT COUNT(*) FROM sample)
=> [[2, 4, 3, 8]]
--- check query | Each table has the key its rule gives it
SELECT m.name, p.name FROM sqlite_master AS m JOIN pragma_table_info(m.name) AS p
WHERE m.type = 'table' AND m.name IN ('operator', 'satellite', 'channel', 'sample') AND p.pk > 0
ORDER BY m.name, p.pk
=> [["channel", "channel"], ["operator", "operator"], ["sample", "sat_id"], ["sample", "ts"], ["sample", "channel"], ["satellite", "sat_id"]]
--- check query | The three foreign keys are declared
SELECT 'satellite', "from", "table" FROM pragma_foreign_key_list('satellite')
UNION ALL
SELECT 'sample', "from", "table" FROM pragma_foreign_key_list('sample')
ORDER BY 1, 2
=> [["sample", "channel", "channel"], ["sample", "sat_id", "satellite"], ["satellite", "operator", "operator"]]
--- check query | Joining the four back rebuilds the sheet exactly, both ways
SELECT
  (SELECT COUNT(*) FROM (
     SELECT s.sat_id, t.sat_name, t.operator, o.country, s.ts, s.channel, c.units, s.value
     FROM sample s JOIN satellite t USING (sat_id) JOIN operator o ON o.operator = t.operator JOIN channel c USING (channel)
     EXCEPT SELECT * FROM tlm_sheet)),
  (SELECT COUNT(*) FROM (
     SELECT * FROM tlm_sheet EXCEPT
     SELECT s.sat_id, t.sat_name, t.operator, o.country, s.ts, s.channel, c.units, s.value
     FROM sample s JOIN satellite t USING (sat_id) JOIN operator o ON o.operator = t.operator JOIN channel c USING (channel)))
=> [[0, 0]]

--- task
Before splitting a sheet, check whether its data already breaks the rules it is supposed to follow. This `tlm_sheet` has the same columns and the same three rules as before: `sat_id` decides `sat_name`, `operator` decides `operator_country`, and `channel` decides `units`.

Write one query that lists every value of a left side that appears with more than one value of its right side. Return three columns:

- `rule`: `'name'` for `sat_id` → `sat_name`, `'country'` for `operator` → `operator_country`, `'units'` for `channel` → `units`;
- `key_value`: the `sat_id`, `operator` or `channel` that breaks its rule;
- `n_values`: how many different right-side values it appears with.

Sort by `rule`, then `key_value`. A left side that always has the same right side must not appear.
--- starter
SELECT 'name' AS rule, sat_id AS key_value, COUNT(DISTINCT sat_name) AS n_values
FROM tlm_sheet
GROUP BY sat_id
ORDER BY rule, key_value;
--- solution
SELECT 'name' AS rule, sat_id AS key_value, COUNT(DISTINCT sat_name) AS n_values
FROM tlm_sheet GROUP BY sat_id HAVING COUNT(DISTINCT sat_name) > 1
UNION ALL
SELECT 'country', operator, COUNT(DISTINCT operator_country)
FROM tlm_sheet GROUP BY operator HAVING COUNT(DISTINCT operator_country) > 1
UNION ALL
SELECT 'units', channel, COUNT(DISTINCT units)
FROM tlm_sheet GROUP BY channel HAVING COUNT(DISTINCT units) > 1
ORDER BY rule, key_value;
--- hint
A rule `A → B` is broken when one value of A goes with two or more values of B. Group by A alone and count the distinct values of B.
--- hint
Write one grouped query per rule, keep groups with `HAVING COUNT(DISTINCT …) > 1`, and glue the three together with `UNION ALL`.

--- check source absent | Does not name the culprits by hand
'(SAT-012|Southern Sky|BUS_T)'

--- task
The fleet's tables are in third normal form: `operator (operator, country)`, `satellite (sat_id, sat_name, operator)`, `channel (channel, units)` and `sample (sat_id, ts, channel, value)`. The analysts want one wide table they can group without joins.

1. Build it as a derived copy: `CREATE TABLE sample_flat AS SELECT …` with the columns `sat_id`, `sat_name`, `operator`, `country`, `ts`, `channel`, `units`, `value`, one row per sample.
2. Then answer their first question from `sample_flat` alone: for each `country` and `channel`, the number of samples `n` and the mean `value` as `mean_value`, rounded to 2 decimals. Return `country`, `channel`, `n`, `mean_value`, sorted by `country`, then `channel`.
--- starter
CREATE TABLE sample_flat AS
SELECT s.sat_id, s.ts, s.channel, s.value
FROM sample AS s;

SELECT channel, COUNT(*) AS n, ROUND(AVG(value), 2) AS mean_value
FROM sample_flat
GROUP BY channel
ORDER BY channel;
--- solution
CREATE TABLE sample_flat AS
SELECT s.sat_id, t.sat_name, t.operator, o.country, s.ts, s.channel, c.units, s.value
FROM sample AS s
JOIN satellite AS t ON t.sat_id = s.sat_id
JOIN operator  AS o ON o.operator = t.operator
JOIN channel   AS c ON c.channel = s.channel;

SELECT country, channel, COUNT(*) AS n, ROUND(AVG(value), 2) AS mean_value
FROM sample_flat
GROUP BY country, channel
ORDER BY country, channel;
--- hint
The country is two joins away from a sample: sample to satellite, then satellite to operator.
--- hint
Join all four tables once, inside the `CREATE TABLE … AS SELECT`. The question afterwards is a plain `GROUP BY country, channel` on `sample_flat`.
--- check query | The flat copy has one row per sample, with every column

+++ practice | Lossless, checked both ways
--- schema
CREATE TABLE tlm_sheet (
    sat_id   TEXT NOT NULL,
    sat_name TEXT NOT NULL,
    plane    INTEGER NOT NULL,
    ts       TEXT NOT NULL,
    channel  TEXT NOT NULL,
    value    REAL NOT NULL
);
INSERT INTO tlm_sheet VALUES
  ('SAT-011', 'Tern-1', 1, '2026-05-01T00:00:00Z', 'BATT_V', 28.1),
  ('SAT-011', 'Tern-1', 1, '2026-05-01T00:01:00Z', 'BATT_V', 28.0),
  ('SAT-012', 'Tern-2', 1, '2026-05-01T00:00:00Z', 'BATT_V', 27.6),
  ('SAT-021', 'Kite-1', 2, '2026-05-01T00:00:00Z', 'BATT_V', 27.9),
  ('SAT-021', 'Kite-1', 2, '2026-05-01T00:00:00Z', 'BATT_V', 27.9);
CREATE TABLE part_a AS SELECT DISTINCT sat_id, plane, ts, channel, value FROM tlm_sheet;
CREATE TABLE part_b AS SELECT DISTINCT plane, sat_name FROM tlm_sheet;
--- task
A colleague split `tlm_sheet (sat_id, sat_name, plane, ts, channel, value)` into `part_a (sat_id, plane, ts, channel, value)` and `part_b (plane, sat_name)`, and wants to know whether joining them on `plane` gives the sheet back. Notice that `tlm_sheet` has no key, and one sample was loaded twice.

Create a view named `lossless_report` that returns one row with four columns:

- `invented`: how many distinct rows the join `part_a JOIN part_b USING (plane)` produces that are not in the sheet;
- `lost`: how many distinct rows of the sheet the join does not produce;
- `sheet_rows`: `COUNT(*)` of `tlm_sheet`;
- `rebuilt_rows`: `COUNT(*)` of the join.

The join's columns must be in the sheet's order: `sat_id`, `sat_name`, `plane`, `ts`, `channel`, `value`. End with `SELECT * FROM lossless_report;`. The view must stay right when the tables change.
--- starter
CREATE VIEW lossless_report AS
SELECT
  (SELECT COUNT(*) FROM (
     SELECT a.sat_id, b.sat_name, a.plane, a.ts, a.channel, a.value
     FROM part_a AS a JOIN part_b AS b USING (plane)
     EXCEPT SELECT * FROM tlm_sheet)) AS invented;

SELECT * FROM lossless_report;
--- solution
CREATE VIEW lossless_report AS
WITH rebuilt AS (
  SELECT a.sat_id, b.sat_name, a.plane, a.ts, a.channel, a.value
  FROM part_a AS a JOIN part_b AS b USING (plane)
)
SELECT
  (SELECT COUNT(*) FROM (SELECT * FROM rebuilt EXCEPT SELECT * FROM tlm_sheet)) AS invented,
  (SELECT COUNT(*) FROM (SELECT * FROM tlm_sheet EXCEPT SELECT * FROM rebuilt)) AS lost,
  (SELECT COUNT(*) FROM tlm_sheet) AS sheet_rows,
  (SELECT COUNT(*) FROM rebuilt)   AS rebuilt_rows;

SELECT * FROM lossless_report;
--- hint
One direction of `EXCEPT` finds rows the join made up; the other finds rows it dropped. You need both, because a split can fail either way.
--- hint
`EXCEPT` compares distinct rows, so it cannot see the sample that was loaded twice. That is why the report also counts rows with `COUNT(*)` on each side.
--- hint
Put the join in a `WITH rebuilt AS (…)` at the top of the view, then write four scalar subqueries over `rebuilt` and `tlm_sheet`.
--- check result | Three invented rows, none lost, five against seven
[[3, 0, 5, 7]]
--- check query | A sheet row the parts do not hold shows up as lost
INSERT INTO tlm_sheet VALUES ('SAT-031', 'Gull-1', 3, '2026-05-01T00:00:00Z', 'BATT_V', 28.4);
SELECT * FROM lossless_report
=> [[3, 1, 6, 7]]
--- check query | With one satellite per plane, nothing is invented

DELETE FROM part_a WHERE sat_id = 'SAT-012';
DELETE FROM tlm_sheet WHERE sat_id IN ('SAT-012', 'SAT-031');

=> [[0, 0, 4, 3]]

+++ practice | Fix the channel-list splitter
--- schema
CREATE TABLE sat_channels (
    sat_id   TEXT NOT NULL PRIMARY KEY,
    channels TEXT NOT NULL
);
INSERT INTO sat_channels VALUES
  ('SAT-011', 'BATT_V,BUS_T,WHEEL_RPM'),
  ('SAT-012', 'SUN_ANG,BATT_V'),
  ('SAT-014', 'BUS_T'),
  ('SAT-099', '');
--- task
`sat_channels` breaks first normal form: each satellite's channels sit in one text cell, separated by commas. `SAT-099` has just launched and reports no channels yet, so its list is empty.

The starter creates the 1NF table `sat_channel (sat_id, channel)`, key `(sat_id, channel)`, and fills it by splitting each list with a recursive CTE. It loses channels: SAT-011 gets only two of its three, and SAT-014 gets none. Fix the CTE so that `sat_channel` holds exactly one row per satellite and channel. SAT-099 must get no rows, not an empty channel.
--- starter
CREATE TABLE sat_channel (
    sat_id  TEXT NOT NULL,
    channel TEXT NOT NULL,
    PRIMARY KEY (sat_id, channel)
);

INSERT INTO sat_channel
WITH RECURSIVE split (sat_id, channel, rest) AS (
  SELECT sat_id, NULL, channels FROM sat_channels
  UNION ALL
  SELECT sat_id,
         substr(rest, 1, instr(rest, ',') - 1),
         substr(rest, instr(rest, ',') + 1)
  FROM split
  WHERE instr(rest, ',') > 0
)
SELECT sat_id, channel FROM split WHERE channel <> '';
--- solution
CREATE TABLE sat_channel (
    sat_id  TEXT NOT NULL,
    channel TEXT NOT NULL,
    PRIMARY KEY (sat_id, channel)
);

INSERT INTO sat_channel
WITH RECURSIVE split (sat_id, channel, rest) AS (
  SELECT sat_id, NULL, channels || ',' FROM sat_channels
  UNION ALL
  SELECT sat_id,
         substr(rest, 1, instr(rest, ',') - 1),
         substr(rest, instr(rest, ',') + 1)
  FROM split
  WHERE instr(rest, ',') > 0
)
SELECT sat_id, channel FROM split WHERE channel <> '';
--- hint
Each step cuts the text up to the next comma. What happens to the piece after the last comma, which has no comma behind it?
--- hint
Give every list a comma at its end before the first step, so the last channel is followed by one too: `channels || ','`.

  ('SAT-011', 'Tern-1',  '2026-05-02T00:00:00Z', 'BATT_V', 28.0),
  ('SAT-012', 'Tern-2',  '2026-05-01T00:00:00Z', 'BATT_V', 27.6),
  ('SAT-012', 'Tern-2',  '2026-05-01T00:00:00Z', 'BUS_T',  23.5),
  ('SAT-012', 'Tern-2B', '2026-05-02T00:00:00Z', 'BATT_V', 27.5),
  ('SAT-012', 'Tern-2B', '2026-05-02T00:00:00Z', 'BUS_T',  23.1),
  ('SAT-021', 'Kite-1',  '2026-05-01T00:00:00Z', 'BATT_V', 27.9),
  ('SAT-021', 'Kite-1A', '2026-05-01T12:00:00Z', 'BATT_V', 27.7),
  ('SAT-021', 'Kite-1',  '2026-05-02T00:00:00Z', 'BUS_T',  19.5);
--- task
`tlm_sheet (sat_id, sat_name, ts, channel, value)` repeats the satellite's name on every sample, and a rename script only fixed some rows. The operators' rule is: a satellite's current name is the name on its **latest** row, by `ts`. (SAT-021 was renamed to Kite-1A by mistake and then back to Kite-1, so its latest row says Kite-1.)

Split the sheet into two tables, every column `NOT NULL`:

- `satellite (sat_id, sat_name)`, key `sat_id`, one row per satellite with its current name;
- `reading (sat_id, ts, channel, value)`, key `(sat_id, ts, channel)`, with `sat_id` referencing `satellite (sat_id)`, one row per sample.

End with `SELECT * FROM satellite ORDER BY sat_id;`.
--- starter
CREATE TABLE satellite (
    sat_id   TEXT NOT NULL,
    sat_name TEXT NOT NULL,
    PRIMARY KEY (sat_id, sat_name)
);
INSERT INTO satellite SELECT DISTINCT sat_id, sat_name FROM tlm_sheet;

SELECT * FROM satellite ORDER BY sat_id;
--- solution
CREATE TABLE satellite (
    sat_id   TEXT NOT NULL PRIMARY KEY,
    sat_name TEXT NOT NULL
);
CREATE TABLE reading (
    sat_id  TEXT NOT NULL REFERENCES satellite (sat_id),
    ts      TEXT NOT NULL,
    channel TEXT NOT NULL,
    value   REAL NOT NULL,
    PRIMARY KEY (sat_id, ts, channel)
);

INSERT INTO satellite
SELECT sat_id, sat_name
FROM (
  SELECT sat_id, sat_name,
         ROW_NUMBER() OVER (PARTITION BY sat_id ORDER BY ts DESC) AS rn
  FROM tlm_sheet
)
WHERE rn = 1;

INSERT INTO reading SELECT sat_id, ts, channel, value FROM tlm_sheet;

SELECT * FROM satellite ORDER BY sat_id;
--- hint
A key of `(sat_id, sat_name)` lets one satellite have two names, which is exactly the contradiction you are removing. The key is `sat_id` alone.
--- hint
Pick each satellite's latest row with `ROW_NUMBER() OVER (PARTITION BY sat_id ORDER BY ts DESC)` and keep row number 1, as in the deduplication lesson of the windows module.
--- check result | One row per satellite, each with the name on its latest row
ordered
[["SAT-011", "Tern-1"], ["SAT-012", "Tern-2B"], ["SAT-021", "Kite-1"]]
--- check query | satellite is keyed by sat_id alone
SELECT name FROM pragma_table_info('satellite') WHERE pk > 0
=> [["sat_id"]]
--- check query | reading keeps all nine samples, keyed by satellite, time and channel
SELECT (SELECT COUNT(*) FROM reading), (SELECT group_concat(name, ',') FROM (SELECT name FROM pragma_table_info('reading') WHERE pk > 0 ORDER BY pk))
=> [[9, "sat_id,ts,channel"]]
--- check query | reading's sat_id points at satellite
SELECT "from", "table" FROM pragma_foreign_key_list('reading')
=> [["sat_id", "satellite"]]

+++ question | A sum over two grains
--- ask
`pass_fact` was meant to hold one row per ground-station pass, with the bytes downlinked. A nightly job also writes one "daily total" row per satellite into the same table. For SAT-011 on 1 May the table holds three passes of 100, 200 and 250 MB, and the job's daily total row of 550 MB. What does this return?

```sql
SELECT SUM(mb) FROM pass_fact
WHERE sat_id = 'SAT-011' AND day = '2026-05-01';
```
--- answer
1100
1100 MB
--- why
The table mixes two grains: rows that are one pass and a row that is already a whole day. The sum adds the passes (100 + 200 + 250 = 550) and then the day's total of the same passes again: 1100, twice the truth. Writing down the grain of a fact table, and keeping coarser rollups in a table of their own, stops this.

+++ question | Why the counter still loses frames
--- ask
Two ingest workers each run this at about the same time in PostgreSQL, at the default READ COMMITTED level. Worker A adds 50, worker B adds 30, and the station started at 100. The program reads the count, adds its number, and writes the result back:

```sql
BEGIN;
SELECT frames FROM ingest_stats WHERE station = 'AWARUA';   -- the program reads 100
UPDATE ingest_stats SET frames = 150 WHERE station = 'AWARUA';   -- 100 + 50, worked out in the program
COMMIT;
```

Some days the total ends at 130 instead of 180. Which change fixes it?
--- choice
Nothing: each worker already runs inside `BEGIN` … `COMMIT`, so the problem must be elsewhere.
--- choice correct
Let the database do the arithmetic: `UPDATE ingest_stats SET frames = frames + 50 WHERE station = 'AWARUA';`.
--- choice
Run both workers at READ UNCOMMITTED, so each one sees the other's change sooner.
--- choice
Put an index on `station`, so each update finishes faster and the two cannot overlap.
--- why
Being inside a transaction does not lock a row you only read, so at READ COMMITTED both workers can read 100 before either writes; the second write then overwrites the first. With `frames = frames + 50` there is no gap between reading and writing: the second update waits for the first one's row lock, then adds to the committed value. PostgreSQL treats READ UNCOMMITTED as READ COMMITTED, and a faster update only makes the collision rarer, not impossible.

--- schema

--- task
A database finds deadlocks by keeping a graph of who waits for whom and looking for a cycle. `waits_for (waiter, holder)` has one row per edge: transaction `waiter` is waiting for a lock that transaction `holder` has. Each transaction waits for at most one other.

Create a view `deadlocked` with one column, `txn`: every transaction that is part of a cycle. A transaction that waits for a deadlocked one without being in the cycle itself (like 106) is not part of it. End with `SELECT * FROM deadlocked ORDER BY txn;`. --- starter

WHERE holder IN (SELECT waiter FROM waits_for);

--- solution
CREATE VIEW deadlocked AS
WITH RECURSIVE walk (start, cur, steps) AS (
  SELECT waiter, holder, 1 FROM waits_for
  UNION ALL
  SELECT w.start, f.holder, w.steps + 1
  FROM walk AS w
  JOIN waits_for AS f ON f.waiter = w.cur
  WHERE w.cur <> w.start
    AND w.steps < (SELECT COUNT(*) FROM waits_for)
)
SELECT DISTINCT start AS txn
FROM walk
WHERE cur = start;

SELECT * FROM deadlocked ORDER BY txn;
--- hint
Start at each transaction and follow the edges: waiter, then its holder, then that one's holder, and so on. A transaction is in a cycle if the walk comes back to it.
--- hint
A recursive CTE can carry `(start, cur, steps)`. Stop a walk when it is back at its start, or after as many steps as there are edges, so it cannot run forever.
--- hint
Keep the starts where some step has `cur = start`.

Each B-tree page holds about `fanout` entries, so one level reaches `fanout` rows, two levels `fanout × fanout`, and so on. The number of levels a tree needs is the smallest whole number L, at least 1, with $fanout^L \geq n\_rows$ (read "fanout to the power L is at least the number of rows").

  SELECT name, n_rows, fanout, 1, fanout FROM btree_case
  UNION ALL
  SELECT name, n_rows, fanout, levels + 1, reach * fanout
  FROM grow
  WHERE reach < n_rows
)

FROM grow
GROUP BY name, n_rows, fanout
ORDER BY n_rows, fanout DESC;

)

INSERT INTO ingest_rate VALUES
  ('raw_frame', 2000000), ('sample', 50000000), ('sat_state', 6000), ('event', 10000);
--- task
Every row inserted writes into the table's own B-tree and into every index on it. In SQLite a table is itself a B-tree keyed by its rowid, and an `INTEGER PRIMARY KEY` is that rowid, so it costs no extra index. Any other `PRIMARY KEY` or `UNIQUE` gets an automatic index, which `pragma_index_list` lists like the ones you create.

For each table in `ingest_rate (tbl, rows_per_day)`, return:

- `tbl`;
- `n_indexes`: how many indexes the table has, from `pragma_index_list(tbl)`;
- `writes_per_row`: B-tree writes per inserted row, the table plus each index;
- `writes_per_day`: `writes_per_row` times `rows_per_day`.

Sort by `writes_per_day`, largest first. Read the indexes from SQLite, not by hand.
--- starter
SELECT tbl, 0 AS n_indexes, 1 AS writes_per_row, rows_per_day AS writes_per_day
FROM ingest_rate
ORDER BY writes_per_day DESC;
--- solution
SELECT r.tbl,
       COUNT(i.name)                      AS n_indexes,
       1 + COUNT(i.name)                  AS writes_per_row,
       (1 + COUNT(i.name)) * r.rows_per_day AS writes_per_day
FROM ingest_rate AS r
LEFT JOIN pragma_index_list(r.tbl) AS i
GROUP BY r.tbl, r.rows_per_day
ORDER BY writes_per_day DESC;
--- hint
`pragma_index_list('sample')` returns one row per index on `sample`. You can join it to each row of `ingest_rate` by passing the column: `pragma_index_list(r.tbl)`.

+++ practice | Where each gap starts
--- task
A bad estimate spreads upward: every node above a wrong guess inherits it. To find the cause, look for where each gap **starts**: a node whose estimate is off by a factor of 10 or more in either direction, none of whose children is off by that much.

From `plan_node (node_id, parent_id, node_type, est_rows, act_rows, loops)`, where the root has `parent_id` NULL, return each such node with its depth in the tree (the root is depth 0, its children depth 1, and so on): `node_id`, `node_type`, `depth`. Sort by `node_id`.
--- starter
SELECT node_id, node_type, 0 AS depth
FROM plan_node
WHERE act_rows >= 10 * est_rows OR est_rows >= 10 * act_rows
ORDER BY node_id;
--- solution
WITH RECURSIVE tree (node_id, depth) AS (
  SELECT node_id, 0 FROM plan_node WHERE parent_id IS NULL
  UNION ALL
  SELECT p.node_id, t.depth + 1
  FROM plan_node AS p JOIN tree AS t ON p.parent_id = t.node_id
),
off AS (
  SELECT * FROM plan_node
  WHERE act_rows >= 10 * est_rows OR est_rows >= 10 * act_rows
)
SELECT o.node_id, o.node_type, t.depth
FROM off AS o
JOIN tree AS t ON t.node_id = o.node_id
WHERE NOT EXISTS (SELECT 1 FROM off AS c WHERE c.parent_id = o.node_id)
ORDER BY o.node_id;
--- hint
Depth comes from walking down from the root with a recursive CTE: each child is one deeper than its parent.
--- hint
Put the badly estimated nodes in a CTE of their own, then keep those with `NOT EXISTS` a badly estimated child.

--- task
PostgreSQL prices a sequential scan as: `seq_page_cost` for each page, plus `cpu_tuple_cost` for each row, plus `cpu_operator_cost` for each operator of the filter evaluated on each row. The three settings are in `cost_param (name, value)`. `scan_stats (tbl, pages, n_rows, filter_ops)` gives each table's size and how many operators its filter has; a scan with no `WHERE` has 0.

For every table return `tbl` and `total_cost`, rounded to 2 decimals, largest first. Read the three settings from `cost_param`, not by typing them. An empty table costs 0.
--- starter

FROM scan_stats
ORDER BY total_cost DESC;
--- solution
WITH p AS (
  SELECT MAX(value) FILTER (WHERE name = 'seq_page_cost')     AS page_cost,
         MAX(value) FILTER (WHERE name = 'cpu_tuple_cost')    AS tuple_cost,
         MAX(value) FILTER (WHERE name = 'cpu_operator_cost') AS op_cost
  FROM cost_param
)
SELECT s.tbl,
       ROUND(s.pages * p.page_cost + s.n_rows * p.tuple_cost + s.n_rows * s.filter_ops * p.op_cost, 2) AS total_cost
FROM scan_stats AS s CROSS JOIN p
ORDER BY total_cost DESC;
--- hint
Turn the three rows of `cost_param` into one row with three columns, for example with `MAX(value) FILTER (WHERE name = …)`, then join it to every table.
--- hint
Cost is `pages × page_cost + n_rows × tuple_cost + n_rows × filter_ops × op_cost`. The number of rows the filter keeps does not appear at all.

+++ practice | Dictionary-encode the channel column
--- task
A column store keeps `channel` as a short dictionary of its distinct names plus a small number per row. Build that encoding for `tlm (row_no, sat_id, ts, channel, value)`:

1. Create `channel_dict (code, channel)`, one row per distinct channel, with codes 0, 1, 2, … in alphabetical order of the channel names.
2. Create `channel_col (row_no, code)`, one row per row of `tlm`, holding the code of its channel.

Build both with `CREATE TABLE … AS SELECT`. Joining them back must give every row's channel exactly.
--- starter
CREATE TABLE channel_dict AS
SELECT DISTINCT ROW_NUMBER() OVER (ORDER BY channel) AS code, channel FROM tlm;
--- solution
CREATE TABLE channel_dict AS
SELECT DENSE_RANK() OVER (ORDER BY channel) - 1 AS code, channel
FROM (SELECT DISTINCT channel FROM tlm);

CREATE TABLE channel_col AS
SELECT t.row_no, d.code
FROM tlm AS t
JOIN channel_dict AS d ON d.channel = t.channel;

Rank the distinct names alphabetically and subtract 1, so the first code is 0. Doing the `DISTINCT` first, in a subquery, gives one row per name.
--- hint
Then `channel_col` is a join of `tlm` to `channel_dict` on the name, keeping `row_no` and `code`.

+++ practice | Cut arrivals into micro-batches
--- schema
CREATE TABLE arrival (
    seq        INTEGER PRIMARY KEY,
    arrival_ms INTEGER NOT NULL
);
INSERT INTO arrival VALUES
  (1, 0), (2, 100), (3, 150), (4, 180), (5, 200),
  (6, 900), (7, 1300), (8, 2500), (9, 2600), (10, 2700),
  (11, 2750), (12, 3400);
--- task
A micro-batching writer collects rows and writes them in one transaction when the batch has **4 rows**, or when a new row arrives **1000 ms or more** after the batch's first row, whichever comes first. In the second case the new row starts the next batch. `arrival (seq, arrival_ms)` lists rows in arrival order.

Number the batches from 1 and return, for each: `batch`, `n_rows`, `first_ms` and `last_ms` (the arrival times of its first and last row). Sort by `batch`. Whether a row starts a new batch depends on the batch before it, so work through the rows in order.
--- starter
SELECT (seq - 1) / 4 + 1 AS batch, COUNT(*) AS n_rows,
       MIN(arrival_ms) AS first_ms, MAX(arrival_ms) AS last_ms
FROM arrival GROUP BY (seq - 1) / 4 ORDER BY batch;
--- solution
WITH RECURSIVE walk (seq, arrival_ms, batch, batch_start, n_in_batch) AS (
  SELECT seq, arrival_ms, 1, arrival_ms, 1 FROM arrival WHERE seq = 1
  UNION ALL
  SELECT a.seq, a.arrival_ms,
         CASE WHEN w.n_in_batch = 4 OR a.arrival_ms - w.batch_start >= 1000 THEN w.batch + 1 ELSE w.batch END,
         CASE WHEN w.n_in_batch = 4 OR a.arrival_ms - w.batch_start >= 1000 THEN a.arrival_ms ELSE w.batch_start END,
         CASE WHEN w.n_in_batch = 4 OR a.arrival_ms - w.batch_start >= 1000 THEN 1 ELSE w.n_in_batch + 1 END
  FROM walk AS w
  JOIN arrival AS a ON a.seq = w.seq + 1
)
SELECT batch, COUNT(*) AS n_rows, MIN(arrival_ms) AS first_ms, MAX(arrival_ms) AS last_ms
FROM walk
GROUP BY batch
ORDER BY batch;
--- hint
A recursive CTE can walk the rows one at a time, carrying the current batch number, when that batch started, and how many rows it has so far.
--- hint
At each step, a new batch starts if the current one already has 4 rows or the new row is at least 1000 ms after the batch's start. Then reset the start and the count; otherwise keep the start and add 1 to the count.

+++ practice | Decode space packet headers
--- task
A CCSDS space packet starts with a 6-byte primary header. `pkt_header (pkt_id, w1, w2, w3)` holds each header as three 16-bit whole numbers, the first, second and third pairs of bytes. The fields, from the most significant bit down, are:

- `w1`: version (3 bits), type (1 bit: 0 telemetry, 1 command), secondary header flag (1 bit), APID (11 bits);
- `w2`: sequence flags (2 bits: 3 means a whole packet), sequence count (14 bits);
- `w3`: data length, which stores the number of bytes in the data field **minus one**.

SQLite has the same bit operators as Python: `x >> n` shifts `x` right by `n` bits, and `x & m` keeps only the bits set in the mask `m`. For each packet return `pkt_id`, `pkt_type`, `sec_hdr`, `apid`, `seq_flags`, `seq_count` and `data_bytes` (the real number of bytes in the data field). Sort by `pkt_id`.
--- starter
SELECT pkt_id, w1 >> 12 AS pkt_type, w1 >> 11 AS sec_hdr, w1 AS apid,
       w2 >> 14 AS seq_flags, w2 AS seq_count, w3 AS data_bytes
FROM pkt_header ORDER BY pkt_id;
--- solution
SELECT pkt_id,
       (w1 >> 12) & 1   AS pkt_type,
       (w1 >> 11) & 1   AS sec_hdr,
       w1 & 2047        AS apid,
       w2 >> 14         AS seq_flags,
       w2 & 16383       AS seq_count,
       w3 + 1           AS data_bytes
FROM pkt_header
ORDER BY pkt_id;
--- hint
To read one bit, shift it down to the bottom and keep only that bit with `& 1`. To read the low bits, mask them: 11 bits is `& 2047` ($2^{11} - 1$), 14 bits is `& 16383`.
--- hint
The top two bits of `w2` need no mask: shifting right by 14 leaves only them. The data length field is one less than the real count.

--- task
InfluxDB takes each sample as one line of text:

```text
telemetry,sat_id=SAT-0417,channel=BATT_V,station=SVALBARD value=28.1 1777608720000000000
```

That is the measurement `telemetry`, then comma-separated tags, a space, the field `value=…`, a space, and the time in **nanoseconds** since 1 January 1970. In a tag value, a space and a comma would end the tag early, so each one must be written with a backslash in front: `GS A` becomes `GS\ A`.

For each row of `tlm (sat_id, channel, station, ts, value)`, return one column `line`, built exactly like the example, sorted by `ts`, then `sat_id`. Work the time out with `unixepoch(ts)`, in whole numbers.
--- starter
SELECT 'telemetry,sat_id=' || sat_id || ',channel=' || channel || ',station=' || station
       || ' value=' || value || ' ' || unixepoch(ts) AS line
FROM tlm ORDER BY ts, sat_id;
--- solution
SELECT 'telemetry,sat_id=' || sat_id
       || ',channel=' || channel
       || ',station=' || replace(replace(station, ',', '\,'), ' ', '\ ')
       || ' value=' || value
       || ' ' || (unixepoch(ts) * 1000000000) AS line
FROM tlm
ORDER BY ts, sat_id;
--- hint
`unixepoch(ts)` is in seconds; multiply by 1000000000 for nanoseconds. It stays a whole number, and a 64-bit integer holds it easily.
--- hint
`replace(text, ' ', '\ ')` puts a backslash before every space. Do the same for commas, in a second `replace` around the first.

+++ practice | A retention plan that respects legal holds
--- task
`part_bounds (part, range_from, range_to)` lists monthly partitions, each holding `range_from <= ts < range_to`. `retention_policy (today, keep_days)` says data older than `keep_days` days before `today` may go; that moment is the cutoff. `legal_hold (hold_id, hold_from, hold_to, reason)` lists holds, each covering `hold_from <= ts < hold_to`; a hold with `hold_to` NULL is still open and covers everything from `hold_from` on.

Create a view `retention_plan (part, past_retention, on_hold, may_drop)`, one row per partition, with 1 or 0 in each flag:

- `past_retention`: every row the partition can hold is before the cutoff;
- `on_hold`: some hold overlaps the partition's range;
- `may_drop`: past retention and not on hold.

Work the cutoff out from `retention_policy` with `strftime` and a `'-90 days'` style modifier built from `keep_days`. End with `SELECT * FROM retention_plan ORDER BY part;`.
--- starter
CREATE VIEW retention_plan AS
SELECT part,
       range_to <= '2026-03-03T00:00:00Z' AS past_retention,
       0 AS on_hold,
       range_to <= '2026-03-03T00:00:00Z' AS may_drop
FROM part_bounds;

SELECT * FROM retention_plan ORDER BY part;
--- solution
CREATE VIEW retention_plan AS
WITH cutoff AS (
  SELECT strftime('%Y-%m-%dT%H:%M:%SZ', today, '-' || keep_days || ' days') AS t
  FROM retention_policy
),
flags AS (
  SELECT p.part,
         CASE WHEN p.range_to <= c.t THEN 1 ELSE 0 END AS past_retention,
         CASE WHEN EXISTS (SELECT 1 FROM legal_hold AS h
                           WHERE h.hold_from < p.range_to
                             AND (h.hold_to IS NULL OR h.hold_to > p.range_from)) THEN 1 ELSE 0 END AS on_hold
  FROM part_bounds AS p CROSS JOIN cutoff AS c
)
SELECT part, past_retention, on_hold,
       CASE WHEN past_retention = 1 AND on_hold = 0 THEN 1 ELSE 0 END AS may_drop
FROM flags;

SELECT * FROM retention_plan ORDER BY part;
--- hint
`strftime('%Y-%m-%dT%H:%M:%SZ', today, '-' || keep_days || ' days')` gives the cutoff. A partition is past retention when its range **ends** on or before it.
--- hint
Two half-open ranges overlap when each starts before the other ends. An open hold has no end, so allow `hold_to IS NULL` in place of `hold_to > range_from`.

+++ question | A colleague at the next desk
--- ask
Your team works in the United States. A contractor joins the team and sits at the next desk; she is not a U.S. person. She asks you to share a CSV of thruster control-loop telemetry, which the export-control office has classified as controlled, so she can check a plot. What is right?
--- choice
It is fine: she is inside the United States, and an export needs data to leave the country.
--- choice
It is fine as long as the file goes over the company's internal network, not the internet.
--- choice correct
Showing or sending her controlled data counts as an export to her country, a deemed export. Ask the export-control office before sharing anything; they decide whether it is allowed or needs a license.
--- choice
It is fine if you remove the satellite names from the file first.
--- why
Releasing controlled technical data to a foreign person inside the United States is treated as an export to that person's country: the knowledge can travel with her. Where the data sits, which network it crosses and whether names are removed do not change what it is. The engineer holding the file does not decide; the export-control office does, and the database should also enforce who can see what, rather than relying on people to remember.

An upsert that overwrites a value destroys the old version, and then no as-of query can rebuild an old plot. So `batt_version (sat_id, ts, value, ingested_at)` never overwrites: a correction is a new row for the same `(sat_id, ts)` with a later `ingested_at`.

--- starter

SELECT sat_id, ts, value
FROM batt_version
WHERE ingested_at <= (SELECT t FROM as_of);

--- solution
CREATE VIEW batt_as_of AS
SELECT sat_id, ts, value
FROM (
  SELECT v.sat_id, v.ts, v.value,
         ROW_NUMBER() OVER (PARTITION BY v.sat_id, v.ts ORDER BY v.ingested_at DESC) AS rn
  FROM batt_version AS v
  WHERE v.ingested_at <= (SELECT t FROM as_of)
)
WHERE rn = 1;

SELECT ts, value FROM batt_as_of ORDER BY ts;

--- hint

--- task
A downlink batch sits in `stage (frame_id, line, sat_id, ts, channel, value, quality)`, one row per sample, several samples per frame. Load it into `sample (sat_id, ts, channel, value, quality)`, whose key is `(sat_id, ts, channel)`, by these rules:

1. A frame is bad if any of its samples has a missing `value` or a `quality` outside 0 to 3. Put each bad frame's id once into `frame_reject (frame_id)`; no sample of a bad frame may reach `sample`.
2. The good frames repeat some keys. For each key keep one copy: the lowest `quality`, and on a tie the lowest `line`.
3. Upsert those copies: a new key is inserted; a key already in `sample` takes the copy only if its `quality` is strictly lower than the stored one.
--- starter

--- solution
INSERT INTO frame_reject
SELECT DISTINCT frame_id FROM stage
WHERE value IS NULL OR quality NOT BETWEEN 0 AND 3;

INSERT INTO sample (sat_id, ts, channel, value, quality)
SELECT sat_id, ts, channel, value, quality
FROM (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY sat_id, ts, channel ORDER BY quality, line) AS rn
  FROM stage
  WHERE frame_id NOT IN (SELECT frame_id FROM frame_reject)
)
WHERE rn = 1
ON CONFLICT (sat_id, ts, channel) DO UPDATE
  SET value = excluded.value, quality = excluded.quality
  WHERE excluded.quality < sample.quality;

--- task
`rx_packet (apid, seq, vehicle_ts, rx_ts, station)` keeps every copy of every packet as received: `vehicle_ts` is when it was measured onboard, `rx_ts` when the ground got it. Each APID's 14-bit sequence count rises by one per packet and wraps from 16383 to 0. A packet is identified by `(apid, seq, vehicle_ts)`; two stations may deliver copies of it.

For each APID, return:

- `n_rows`: copies received;
- `n_packets`: distinct packets;
- `n_missing`: packets lost, from the steps between consecutive distinct packets in vehicle-time order, taken modulo 16384;
- `n_late`: distinct packets that arrived late, judging each packet by its first copy's arrival: late if some packet whose first copy arrived earlier has a later vehicle time.

An APID with no gap or no late packet shows 0. Sort by `apid`.
--- starter
SELECT apid, COUNT(*) AS n_rows, COUNT(DISTINCT seq) AS n_packets,
       MAX(seq) - MIN(seq) + 1 - COUNT(DISTINCT seq) AS n_missing, 0 AS n_late

--- solution
WITH pkt AS (
  SELECT apid, seq, vehicle_ts, MIN(rx_ts) AS first_rx
  FROM rx_packet
  GROUP BY apid, seq, vehicle_ts
),
stepped AS (
  SELECT apid,
         (seq - LAG(seq) OVER (PARTITION BY apid ORDER BY vehicle_ts) + 16384) % 16384 AS step
  FROM pkt
),
arrival AS (
  SELECT apid, vehicle_ts,
         MAX(vehicle_ts) OVER (PARTITION BY apid ORDER BY first_rx
                               ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING) AS latest_before
  FROM pkt
)
SELECT r.apid,
       (SELECT COUNT(*) FROM rx_packet AS x WHERE x.apid = r.apid) AS n_rows,
       (SELECT COUNT(*) FROM pkt AS p WHERE p.apid = r.apid) AS n_packets,
       (SELECT COALESCE(SUM(step - 1), 0) FROM stepped AS s WHERE s.apid = r.apid AND s.step > 1) AS n_missing,
       (SELECT COUNT(*) FROM arrival AS a WHERE a.apid = r.apid AND a.vehicle_ts < a.latest_before) AS n_late
FROM (SELECT DISTINCT apid FROM rx_packet) AS r
ORDER BY r.apid;

       CASE WHEN COUNT(v.value) = p.n AND ROUND(AVG(v.value), 2) = p.mean_v THEN 1 ELSE 0 END AS matches
FROM published AS p
LEFT JOIN batt_version AS v ON v.sat_id = p.sat_id AND substr(v.ts, 1, 13) = p.hour
GROUP BY p.plot_id

--- solution
WITH seen AS (
  SELECT p.plot_id, v.value,
         ROW_NUMBER() OVER (PARTITION BY p.plot_id, v.ts ORDER BY v.ingested_at DESC) AS rn
  FROM published AS p
  JOIN batt_version AS v
    ON v.sat_id = p.sat_id
   AND substr(v.ts, 1, 13) = p.hour
   AND v.ingested_at <= p.as_of
),
rebuilt AS (
  SELECT p.plot_id, p.n AS pub_n, p.mean_v AS pub_mean,
         COUNT(s.value) AS n, ROUND(AVG(s.value), 2) AS mean_v
  FROM published AS p
  LEFT JOIN seen AS s ON s.plot_id = p.plot_id AND s.rn = 1
  GROUP BY p.plot_id, p.n, p.mean_v
)
SELECT plot_id, n, mean_v,
       CASE WHEN n = pub_n AND mean_v IS pub_mean THEN 1 ELSE 0 END AS matches
FROM rebuilt
ORDER BY plot_id;

+++ question | Which normal form it breaks
--- ask
`pass_log (station_id, aos, sat_id, station_city, sat_name, mbytes)` has one row per ground-station pass and the key `(station_id, aos)`. A station is in one city, and a satellite has one name. Which statement is right?
--- choice
It is in third normal form: every column depends on the key.
--- choice
It breaks 2NF because of `station_city`, and `sat_name` is fine because `sat_id` is not part of the key.
--- choice correct
It breaks 2NF, because `station_city` depends on `station_id`, part of the key; and after that is fixed it still breaks 3NF, because `sat_name` depends on `sat_id`, a non-key column.
--- choice
It breaks 1NF, because a table may hold only one id column.
--- why
`station_id → station_city` is a partial dependency on the composite key, the mark of a 2NF violation. `sat_id → sat_name` is a transitive dependency, `(station_id, aos) → sat_id → sat_name`, which 3NF forbids. The fix is one table per determinant: `station (station_id, station_city)`, `satellite (sat_id, sat_name)`, and `pass_log` keeping only the two ids, the key and `mbytes`.

+++ question | Two antennas taken down at once
--- ask
The rule is that each ground station keeps at least one antenna online. Two operators, at the same moment, each run a transaction at REPEATABLE READ: count the station's online antennas, see 2, and switch a **different** antenna offline. Both commit, and the station has none online. What is true?
--- choice
REPEATABLE READ should have raised "could not serialize access", because both transactions read the same rows; the database has a bug.
--- choice correct
This is write skew. REPEATABLE READ allows it because the two transactions wrote different rows; SERIALIZABLE would abort one of them, which must then retry.
--- choice
It is a lost update: the second write overwrote the first, and READ COMMITTED would have prevented it.
--- choice
It is a dirty read: each operator saw the other's uncommitted change.
--- why
Each transaction checked a rule over several rows and then wrote a row the other had only read. Neither overwrote the other, so REPEATABLE READ sees no conflict, yet no one-at-a-time order ends with zero antennas online. Only SERIALIZABLE detects that pattern, and it does so by cancelling a transaction, so the code needs a retry loop.

+++ question | Two jobs that deadlock
--- ask
Job A updates SAT-2 then SAT-1 in one transaction; job B updates SAT-1 then SAT-2 in another. A few times a day one of them fails with `deadlock detected`. Which change prevents the deadlocks?
--- choice correct
Make both jobs update their rows in the same order, for example sorted by `sat_id`.
--- choice
Raise `deadlock_timeout`, so the jobs wait longer before giving up.
--- choice
Run both jobs at SERIALIZABLE.
--- choice
Add an index on `sat_id`, so each update finishes sooner.
--- why
A deadlock is a cycle: A holds SAT-2 and waits for SAT-1 while B holds SAT-1 and waits for SAT-2. If every transaction takes its locks in one agreed order, whoever gets the first row also gets the second, and the other simply waits: no cycle can form. A longer timeout only delays the detection, a stricter isolation level adds serialization failures instead of removing lock waits, and speed makes the collision rarer, not impossible.

+++ question | Levels in a big tree
--- ask
Each B-tree page holds about 250 entries. How many levels does the tree need to index 2,000,000,000 rows? Type a whole number.
--- answer
4
four
--- why
One level reaches 250 entries, two reach $250^2 = 62\,500$, three reach $250^3 = 15\,625\,000$, and four reach $250^4 \approx 3.9 \times 10^9$, the first that covers two billion. A lookup reads about four pages, and ten times more rows would still need only five.

+++ question | A BRIN index after a backfill
--- ask
A telemetry table arrived in time order, and a BRIN index on `ts` made hour-long queries fast. Then a backfill `UPDATE` corrected a third of the old rows, and PostgreSQL wrote their new versions wherever it found free space. What happens to the hour-long queries?
--- choice
Nothing changes: a BRIN index is updated with each row, exactly like a B-tree.
--- choice
They start returning wrong answers, because BRIN can no longer find the moved rows.
--- choice correct
They slow down: the block ranges now mix old and new times, so their minimum-to-maximum spans widen and rule out less, and `pg_stats.correlation` for `ts` drops. Rewriting the table in time order, or a B-tree, restores the speed.
--- choice
The planner stops using indexes on the table until the next VACUUM.
--- why
BRIN keeps only the smallest and largest value per block range. It never gives wrong answers, because every row in a range it reads is rechecked, but it only helps while each range covers a narrow slice of time. Rows scattered by updates or late backfills widen those slices, and the index reads more pages. Keeping ingest append-only, and clustering a partition once it is closed, keeps correlation near 1.

+++ question | The longest left prefix
--- ask
A table has `INDEX (station, sat_id, aos)`. Which condition lets it seek on the most index columns?
--- choice
`station = 'SVB' AND aos >= '2026-06-02'`
--- choice correct
`station = 'SVB' AND sat_id IN ('SAT-061', 'SAT-062') AND aos >= '2026-06-02'`
--- choice
`sat_id = 'SAT-061' AND aos >= '2026-06-02'`
--- choice
`aos >= '2026-06-02' AND station LIKE '%VB'`
--- why
An index seeks only on a left prefix of its columns, with equalities before the range. +++ question | Which update stays inside the page
--- ask
A PostgreSQL table with `fillfactor = 90` has two indexes: one on `(sat_id, ts)` and a covering one on `(sat_id, channel, ts) INCLUDE (value)`. Which update can be a HOT update, touching no index?
--- choice correct
`UPDATE tlm SET quality = 1 WHERE …`, since `quality` is in no index.
--- choice
`UPDATE tlm SET value = value + 0.001 WHERE …`, since `value` is not a key column of any index.
--- choice
`UPDATE tlm SET ts = ts + interval '1 second' WHERE …`, since `ts` changes by only a second.
--- choice
None of them: every update in PostgreSQL writes a new entry in every index.
--- why
An update is HOT when it changes no indexed column and the new version fits on the same page, which the free 10 percent allows. Columns in `INCLUDE` count as indexed, because the index stores them, so changing `value` needs a new entry in the covering index. `ts` is a key column of both indexes, however small the change. Only `quality` qualifies.

+++ question | A cast on the column
--- ask
`tlm.sat_id` is an `integer` with a B-tree index, yet a query from a pipeline program runs as a sequential scan, with this line in the plan: `Filter: ((sat_id)::numeric = '7'::numeric)`. Why?
--- choice
The statistics are stale; running ANALYZE will bring the index back.
--- choice correct
The program sent 7 as a `numeric` parameter, so PostgreSQL cast the column to `numeric` to compare, and a predicate on a converted column cannot seek in the index on the bare one. Bind the parameter as an integer.
--- choice
The index is corrupt; REINDEX will fix it.
--- choice
Comparing numerics is slower, so the planner prefers a scan even though the index could be used.
--- why
When types differ, PostgreSQL converts one side, and converting `integer` to `numeric` loses nothing, so it casts the column. The `(sat_id)::numeric` in the plan is the tell: the column is wrapped, exactly as if you had written a function around it, so the predicate is no longer SARGable. Matching the parameter's type to the column's puts `sat_id = 7` back in the index condition.

+++ question | The consumer that crashed
--- ask
A consumer reads a batch of messages from Kafka, inserts their samples into a table with no key using plain `INSERT`, and then records its offset. The machine loses power after the insert, before the offset is recorded. What happens after the restart, and what fixes it?
--- choice
Nothing goes wrong: Kafka offers exactly-once delivery, so the batch is not delivered again.
--- choice
The batch is lost, because the offset was never recorded: this is at-most-once delivery.
--- choice correct
The consumer reads the batch again and inserts its samples a second time: at-least-once delivery. A key on `(sat_id, ts, channel)` and an upsert make the second write harmless.
--- choice
The database rolls the insert back when the consumer restarts, so nothing is duplicated.
--- why
The consumer resumes from its last recorded offset, which is before the batch, so every message in it is processed again. That is at-least-once, the usual default because losing flight data is worse than seeing it twice. Kafka's exactly-once covers Kafka's own parts; across the boundary into a database it comes from an idempotent write: a natural key with `ON CONFLICT`.

+++ question | Where the access rule lives
--- ask
Controlled channels are hidden from analysts who are not U.S. persons by a `WHERE` clause in the dashboard's code. Analysts can also connect to the database with their own SQL tools. Where should the rule live?
--- choice
In the dashboard is enough, as long as its code is reviewed carefully.
--- choice correct
In the database itself: roles with a row-level security policy (or access only through views that apply the rule), so every query from every tool gets the filter, with access logged.
--- choice
Encrypt the controlled columns and give every analyst the key.
--- choice
Rename the controlled channels so their meaning is not obvious.
--- why
A filter in one application protects only that application: any other tool, or one bug in the dashboard, shows everything. Row-level security adds its condition to every query from a role, which the user cannot forget or remove, and logging answers "who read this, and when". Handing everyone the key protects nothing, and hiding names does not change what the data is. What is controlled is decided by the export-control office; enforcing it is the database's job.
