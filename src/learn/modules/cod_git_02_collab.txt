+++ practice | Publish orbit-sim, both branches
--- task
Maya's orbit-sim in `~/project` has two branches: `main`, with two commits, and `drag-model`, with one more. There is no server copy yet.

1. Make a bare repository at `~/server/orbit-sim.git`, to be the team's shared copy.
2. Connect Maya's repository to it under the name `origin`.
3. Send both branches to it, each with its upstream set, so that plain `git push` and `git pull` work on `main` and on `drag-model` from now on.

The server's `main` must not contain the drag work.
--- starter
git init
git config user.name "Maya Chen"
printf 'MU_EARTH = 3.986004418e14\n' > gravity.py
git add gravity.py
git commit -m "Add Earth's gravitational parameter"
printf '# orbit-sim\n' > README.md
git add README.md
git commit -m "Add README"
git switch -c drag-model
printf 'RHO0 = 1.225\n' > drag.py
git add drag.py
git commit -m "Add sea-level air density"
git switch main
--- solution
git init --bare ~/server/orbit-sim.git
git remote add origin ~/server/orbit-sim.git
git push -u origin main
git push -u origin drag-model
git branch -vv
--- hint
`git init --bare <folder>` makes a repository with no working tree: the right kind for a copy nobody edits files in.
--- hint
After `git remote add origin <folder>`, each branch needs its own push, and `-u` on each one records the upstream: `git push -u origin <branch>`.
--- check shell | The server copy exists, and origin points to it
git ~/server/orbit-sim.git repo
git . remote origin
--- check shell | The server has both branches, each at the right commit
git ~/server/orbit-sim.git at main message == Add README
git ~/server/orbit-sim.git at main missing drag.py
git ~/server/orbit-sim.git at drag-model message == Add sea-level air density
--- check shell | Both local branches track their partner on the server
git . tracks main origin/main
git . tracks drag-model origin/drag-model
?? A branch pushed without -u has no upstream. Push it again with git push -u origin <branch>.

+++ practice | Read what arrived, then fast-forward
--- task
Maya is in `~/project`. Her `git status` says `Your branch is up to date with 'origin/main'`, but Leo says he pushed three commits an hour ago.

1. Download what is on the server, without changing any of Maya's files.
2. Save the list of commits that `origin/main` has and `main` does not into a file `incoming.txt` in `~/project`, one line per commit, exactly as `git log --oneline` prints them. (Send the output of the right `git log` into the file with `>`.)
3. Then bring `main` up to date with the server, with no merge commit.

Do not commit `incoming.txt`.
--- starter
git init
git config user.name "Maya Chen"
printf 'MU_EARTH = 3.986004418e14\n' > gravity.py
git add gravity.py
git commit -m "Add Earth's gravitational parameter"
git init --bare ~/server/orbit-sim.git
git remote add origin ~/server/orbit-sim.git
git push -u origin main
git clone ~/server/orbit-sim.git ~/leo
cd ~/leo
git config user.name "Leo Park"
printf 'MU_EARTH = 3.986004418e14\nJ2 = 1.08262668e-3\n' > gravity.py
git commit -am "Add J2 oblateness constant"
printf 'MU_EARTH = 3.986004418e14\nJ2 = 1.08262668e-3\nR_EARTH = 6378137.0\n' > gravity.py
git commit -am "Add equatorial radius"
mkdir tests
printf 'from gravity import J2\n' > tests/test_gravity.py
git add tests
git commit -m "Test the J2 constant"
git push
cd ~/project
--- solution
git fetch
git status
git log --oneline main..origin/main > incoming.txt
cat incoming.txt
git merge origin/main
git status
--- hint
`status` only compares `main` with the note `origin/main`, and only `git fetch` refreshes that note.
--- hint
`A..B` lists the commits reachable from `B` but not from `A`. Write the list before you merge: afterwards there is nothing left to list.
--- check shell | incoming.txt lists Leo's three commits and nothing else
file incoming.txt contains Add J2 oblateness constant
file incoming.txt contains Add equatorial radius
file incoming.txt contains Test the J2 constant
file incoming.txt excludes Add Earth's gravitational parameter
file incoming.txt lines == 3
?? If the file is empty, the list was written after the merge, or before the fetch.
--- check shell | main now matches the server, by a fast-forward
git . same main origin/main
git . at main message == Test the J2 constant
git . commits == 4
git . merges == 0
--- check shell | incoming.txt was not committed
git . untracked incoming.txt
git . clean

+++ practice | Rejected push, with work in progress
--- task
Maya committed `Add escape speed helper` on `main` in `~/project`, but her push was refused: Leo pushed `List the constants' units in the README` first. She has also started a docstring in `gravity.py` that is not ready to commit.

Get her commit onto the server **after** Leo's, with no merge commit anywhere. Afterwards her unfinished docstring must still be in `gravity.py` as an uncommitted change, exactly as it is now, and nothing may be left set aside.

+++ question | What a push would send
--- ask
Maya has fetched, and wants to see exactly the commits a `git push` of `main` would send to the server. Which command lists them?
--- choice
`git log --oneline main..origin/main`
--- choice correct
`git log --oneline origin/main..main`
--- choice
`git diff main origin/main`
--- choice
`git status`, because it counts the commits she is ahead by on the server
--- why
`A..B` means the commits reachable from `B` but not from `A`. A push sends what `main` has and `origin/main` lacks, so `origin/main..main`. The other way round, `main..origin/main`, is what a pull would bring in, a very common slip. `git diff` shows a change in files, not a list of commits. `git status` does count ahead and behind, but against the note `origin/main`, not against the server itself, and it lists no commits.

+++ question | New commits from each catch-up
--- ask
Your branch has 4 commits since its merge base with `main`, and `main` has 2 new commits. How many **new commit objects** does `git merge main` create, and how many does `git rebase main` create instead?
--- choice
Merge: 1. Rebase: 6, because the rebase copies `main`'s 2 commits too.
--- choice correct
Merge: 1. Rebase: 4.
--- choice
Merge: 3, because the 2 commits from `main` are copied into your branch. Rebase: 4.
--- choice
Merge: 1. Rebase: 0, because a rebase only moves the branch pointer.
--- why
A merge adds exactly one commit, with two parents, and leaves every existing commit as it is; `main`'s commits are not copied, they become reachable. A rebase re-creates each of your 4 commits on the new base: new parent, usually a new tree, a new committer time, so 4 new hashes. `main`'s 2 commits are the new base and keep their hashes. Only a branch whose commits all sit on top of the new base already could be "moved" with no new commits.

+++ question | A fixup in the wrong place
--- ask
In a todo list of eight lines, line 7 is `pick 7e4481b fix typo`, a commit that fixes a comment written in line 1's commit. You want it melted into line 1's commit. What do you change?
--- choice
Change line 7 to `fixup` where it is: a fixup always finds the commit it belongs to.
--- choice correct
Move the line up so it sits directly below line 1, and change its command to `fixup`.
--- choice
Change line 7 to `squash` where it is, then edit the combined message.
--- choice
Change line 1 to `edit` and leave line 7 as it is.
--- why
A `fixup` or `squash` melts a commit into the line directly **above** it: the commit that has just been made when Git reaches that line. Left at line 7 it would melt into line 6's commit. So you reorder the line to sit under line 1, then mark it `fixup`. The move is safe as long as the commits in between do not touch the same lines; if they do, Git may stop with a conflict.

+++ question | Whose resolution is it?
--- ask
Leo has `rerere.enabled true` and resolved a conflict in `guidance.py` last week. Maya, working in her own clone with rerere on too, now hits the identical conflict. What happens in Maya's clone?
--- choice
Git prints `Resolved 'guidance.py' using previous resolution`, because Leo pushed his resolution with his merge commit.
--- choice correct
Nothing special: the recorded resolution lives in Leo's `.git/rr-cache`, which is never pushed or cloned, so Maya resolves it herself.
--- choice
Git refuses the merge until Maya fetches Leo's `rr-cache` from the server.
--- choice
Git applies Leo's resolution and stages the file, because rerere shares resolutions through the remote.
--- why
rerere's memory is a folder inside one clone, `.git/rr-cache`, holding the conflicted hunk (the preimage) and its resolution (the postimage). Like the reflog, it is local: push, fetch and clone never carry it. Leo's merge commit does carry his *result*, so if Maya merges that commit she gets it; but a fresh identical conflict in her clone is new to her rerere.

+++ question | An empty base section
--- ask
With `merge.conflictStyle diff3`, a conflict shows lines under `<<<<<<< HEAD`, then a `||||||| e3621a2` line with **nothing** under it, then `=======` and more lines. What does the empty section tell you?
--- choice
Both sides deleted the same lines, so either version can be taken.
--- choice correct
At the merge base those lines did not exist: both sides added new lines at the same place.
--- choice
Git could not find a merge base, so it shows no base.
--- choice
The base is the same as `HEAD`, so only the other side changed anything.
--- why
The middle section of a `diff3` or `zdiff3` conflict is the merge base's version of the conflicted region. Empty means the region was empty at the fork: each side inserted lines there. So the question is not "which edit wins" but "which of the new lines are wanted, and in what order". If the base were the same as one side, Git would not have reported a conflict at all: it takes the side that changed.

+++ question | A workflow for the CubeSat team
--- ask
Six students build flight software for a university CubeSat. All six may push to the shared repository. They ship one version at a time to the flight model, but version 1 also runs on a partner university's ground-station tool, which must receive bug fixes for a year while version 2 is developed. Which setup fits best?
--- choice
GitFlow, with `develop`, feature, release and hotfix branches, because two versions exist.
--- choice correct
Trunk-based development on `main`, plus one long-lived `release/1.x` branch that receives only fixes.
--- choice
The forking workflow, so that each student works in a fork and one maintainer merges everything.
--- choice
Trunk-based development only: fix version 1 by releasing from `main`, which will contain version 2's unfinished work.
--- why
Two facts decide it: who may push (everyone, so forks solve a problem they do not have) and how many versions need fixes at once (two). Trunk-based development keeps integration small for the active version; one release branch protects version 1 and takes only fixes. That is GitFlow's good idea without `develop` and its double merges. Releasing version 1 fixes from `main` would ship version 2's half-finished work to the partner.

+++ question | Counting GitFlow's merges
--- ask

--- answer
6

--- why
Each feature merges once, into `develop`: 2. The release branch merges into `main` (where it is tagged) and back into `develop`: 2 more. The hotfix merges into `main` and into `develop`: 2 more. +++ question | Chaining two rotations
--- ask
Code has `C_be` (Earth-fixed components to body components) and `C_ie` (Earth-fixed components to inertial components). Which expression is `C_bi`, the matrix that takes inertial components to body components?
--- choice
`C_be @ C_ie`
--- choice
`C_ie @ C_be`
--- choice correct
`C_be @ C_ie.T`
--- choice
`C_ie.T @ C_be`
--- why
Read each matrix as "to the first subscript, from the second", and make neighboring subscripts match. You need body from inertial: `C_bi = C_be C_ei`. There is no `C_ei`, but for a rotation the transpose is the inverse, so `C_ei = C_ie.T`, giving `C_be @ C_ie.T`: `e` next to `e`. `C_be @ C_ie` puts `e` next to `i`, which is the mismatch a reviewer should spot at a glance. All four expressions are valid rotations, so no test of orthonormality can tell them apart.

+++ question | What NaN does to three comparisons
--- ask
What does this print?

```python
import math

rate = math.nan
LIMIT = 0.035
print(rate > LIMIT, rate <= LIMIT, rate != rate)
```
--- answer
False False True
False, False, True
--- why
Every ordered comparison with NaN is false, so `rate > LIMIT` and `rate <= LIMIT` are both `False`: a guard written either way treats NaN as "not over the limit" or "not within it", depending on which you wrote. `!=` is the one comparison that is true for NaN, and `rate != rate` is the classic test for it (`math.isnan(rate)` says the same thing more plainly). A reviewer asks, for every comparison, "what happens if this is NaN?"

+++ question | Reading a hunk header
--- ask
A hunk in a pull request's diff starts `@@ -12,7 +12,9 @@`, and it has no lines starting with `-`. How many lines does this hunk add? Type the number.
--- answer
2
two
--- why
The header says the hunk shows 7 lines of the old file starting at line 12, and 9 lines of the new file starting at line 12. With nothing removed, all 7 old lines are unchanged context that appears on both sides, so the new side has 9 − 7 = 2 added lines, marked with `+`.

+++ question | A millisecond counter
--- ask
A flight computer counts milliseconds since boot in a signed 32-bit integer. It wraps around (becomes negative) once the count passes 2^31 − 1. How many days after boot does that happen? Round to one decimal place.
--- answer
24.9
24.9 days
about 24.9 days
--- why
2^31 milliseconds is 2,147,483,648 ms = 2,147,483.648 s. Divide by 86,400 seconds in a day: about 24.855 days, so 24.9 after rounding. A review question for every counter is "what is the largest value this can ever hold, and when does it get there?" Nobody tests a spacecraft left running for 25 days by accident.

+++ question | The base of a cherry-pick
--- ask
You run `git cherry-pick 8491d16` while on `release/1.4`. Git applies the change with a three-way merge. Which snapshot does it use as the **base** of that merge?
--- choice
The merge base of `release/1.4` and the branch `8491d16` is on.
--- choice correct
The parent of `8491d16`.
--- choice
The tip of `release/1.4`.
--- choice
The first commit of the repository, which every branch shares.
--- why
A cherry-pick means "make here the change that `8491d16` made against its parent". So the base is that parent, "theirs" is `8491d16` itself, and "ours" is `HEAD`, the tip of `release/1.4`. The base can be far from your branch in the graph. That is why a pick conflicts exactly when the lines the fix touched look different on your branch than they did in the fix's parent.

+++ question | The commit that undid an update
--- ask
Maya moved orbit-sim's `extern/frames` submodule to v0.4.0 and pushed. Ravi runs `git pull`, which updates the gitlink, then fixes a typo in the README and runs `git commit -a -m "Fix README typo"` without running `git submodule update`. What does his commit do to the submodule?
--- choice
Nothing: `commit -a` never touches submodules.
--- choice correct
It records the old commit still checked out in his `extern/frames` as the new pin, silently moving orbit-sim back to v0.3.0.
--- choice
It copies the library's files into orbit-sim's history.
--- choice
It updates his `extern/frames` checkout to v0.4.0 first, then commits.
--- why
`git pull` moved the pin (the gitlink in the commit) but not the submodule's checkout on disk, which still has the old commit. `git status` then shows `modified: extern/frames (new commits)` and `git submodule status` a `+`. `commit -a` stages every modified tracked path as it is on disk, the gitlink included, so the old commit becomes the pin again. +++ question | What a submodule puts in your history
--- ask
After `git submodule add ../frames.git extern/frames` and a commit, what does orbit-sim's own history hold for the library?
--- choice
Every file of the library, like any other folder.
--- choice
The library's whole history, squashed into one commit.
--- choice correct
A `.gitmodules` file with the library's address, and one tree entry of mode `160000` whose hash is a commit in the library's repository.
--- choice
Only a line in `.git/config`, which is not committed.
--- why
A submodule is a pointer, not a copy. The tree entry, a gitlink, names one commit of the other repository, and `.gitmodules` says where that repository lives. None of the library's files enter orbit-sim's objects. That is why a plain clone leaves the folder empty until `git submodule update --init` fetches the library and checks out the pinned commit.

+++ question | Where a subtree keeps the version
--- ask
`frames` was brought into orbit-sim with `git subtree add --prefix=extern/frames ../frames.git v0.3.0 --squash`. Where does orbit-sim record exactly which commit of `frames` its files came from?
--- choice
In `.gitmodules`.
--- choice
In a mode `160000` entry for `extern/frames`.
--- choice correct
In the squash commit's message, in a `git-subtree-split:` trailer line.
--- choice
Nowhere: a subtree cannot tell which version it holds.
--- why
A subtree's files are ordinary files, mode `100644`, so the tree has no pin. `git subtree` writes the source commit into the message of the squash commit it makes: `git-subtree-dir: extern/frames` and `git-subtree-split: <commit>`. +++ question | A vendor's driver
--- ask
A star-tracker vendor delivers its C driver as a tarball twice a year. It goes into the flight build, which auditors must be able to read in full from one repository, and your team patches one line of it for your processor. Which way of bringing it in fits best?

--- choice correct
Vendoring: copy the release into `third_party/`, with a record of the version, its source and the local one-line change.
--- choice

+++ question | Two attributes in the wrong order
--- ask
A repository's `.gitattributes` has the line `*.slx diff=slx binary`, and `diff.slx.textconv` is configured with a working unzip-and-print script. What does `git diff` show for a changed `models/attitude.slx`?
--- choice
The model's XML, one tag per line, through the `slx` driver.
--- choice correct
`Binary files a/models/attitude.slx and b/models/attitude.slx differ`
--- choice
A text diff of the raw ZIP bytes.
--- choice
An error, because `binary` and `diff=slx` cannot appear on one line.
--- why
`binary` is a shorthand for `-diff -merge -text`, and when attributes on a line disagree, the later one wins. Here `binary` comes last, so its `-diff` switches off the `diff=slx` set before it. The lesson's order, `*.slx binary diff=slx`, turns diffing off and then back on through the driver, while merging stays off. Check with `git check-attr diff -- models/attitude.slx`.

+++ question | Unlocking too early
--- ask
Ravi holds the lock on `models/attitude.slx`, has edited it, and has **not** committed. He runs `git lfs unlock models/attitude.slx` to let Maya start. What happens?
--- choice
The lock is released, and his edits stay on his disk.
--- choice correct
Git LFS refuses: `Cannot unlock file with uncommitted changes`.
--- choice
The lock is released and his edits are thrown away.
--- choice
The lock passes to Maya automatically.
--- why
Releasing a lock while the edits exist only on a laptop would let someone else start from the old model, and one of the two sets of work would have to be redone by hand. So Git LFS refuses. +++ question | Who stopped Ravi's push?
--- ask
Maya holds the lock on `models/attitude.slx`. Ravi made his copy writable, committed a change to it and pushed, and the push was refused with `Cannot update locked files`. Where did that refusal come from?
--- choice

--- choice correct

--- choice
From Git itself, which checks every push against the lock list.
--- choice
From Maya's clone, which watches the server for changes to her files.
--- why
Git has no locks. Git LFS adds them: the server keeps the list, and the `pre-push` hook that `git lfs install` put in Ravi's clone asks it whether any file he changed is locked by someone else. +++ question | Fewer waits for the same lock

+++ question | A pointer diff
--- ask

--- choice

+++ question | What a fetch changes
--- ask
Leo has uncommitted edits in `gravity.py` and two unpushed commits on `main`. He runs `git fetch`, and the server's `main` has three commits he did not have. What has changed in his repository?
--- choice
His `main` now includes the three commits, and his edits were merged into them.
--- choice correct
Only the remote-tracking branch `origin/main` (and the downloaded commits): his `main`, his index and his edited files are exactly as before.
--- choice
Nothing yet: a fetch only lists what is new until he runs `git status`.
--- choice
His two unpushed commits were replayed on top of the three new ones.
--- why
`git fetch` downloads commits and moves the remote-tracking branches, and does nothing else. So it is always safe, even with work in progress. His `main` is now "ahead 2, behind 3" of `origin/main`; integrating is a separate step (merge, rebase, or `pull`, which is fetch plus one of those). Replaying his commits is what `git pull --rebase` would do.

+++ question | Which branch may be rebased?
--- ask
Which of these is safe to rebase onto the latest `main`, by the golden rule and the exception teams allow?
--- choice
`release/1.4`, to pick up `main`'s fixes in a straight line.
--- choice
`nav-filter`, a branch that Maya, Leo and Ravi all commit to, before tonight's merge.
--- choice correct
Your own pushed feature branch that the team agreed nobody else builds on, then pushed with `--force-with-lease`.
--- choice
`main` itself, after a teammate's merge made its history untidy.
--- why
The golden rule: never rebase commits that exist outside your repository, because everyone who has them faces duplicates and conflicts. `main`, release branches (with their tags and test records) and branches several people commit to are the clearest cases. The one agreed exception is a personal feature branch nobody else builds on, rewritten before merge and pushed with the checked force, so a colleague's unexpected commit is refused rather than erased.

+++ question | The message after the plan
--- ask
A branch's commits, oldest first, are `Add sun sensor model`, `typo`, `Add sun sensor tests`, `wip`. Leo saves this todo list:

```text
pick   a1 Add sun sensor model
fixup  b2 typo
pick   c3 Add sun sensor tests
fixup  d4 wip
```

What is the message of the **newer** of the two resulting commits? Type it exactly.
--- answer
Add sun sensor tests
--- why
`fixup` melts a commit into the line directly above it and throws its message away, keeping the message of the line above. So `wip` disappears into `Add sun sensor tests`, whose message stays, and `typo` disappears into `Add sun sensor model`. With `squash` instead, Git would have opened the editor with both messages to combine.

+++ question | A lease renewed behind your back
--- ask
Leo rewrote his branch `feature`. His editor fetches in the background, and it fetched a minute ago, after Ravi pushed a commit to the server's `feature`. Leo has not looked at what arrived. He runs `git push --force-with-lease`. What happens?

It is refused with `stale info`, because Ravi's commit is on the server.

--- choice
It succeeds and keeps Ravi's commit, because a lease push merges.

+++ question | ours during a rebase
--- ask
You are rebasing your branch onto `main`, and a conflict stops it on one of **your** commits in the generated file `ephemeris_table.py`. You want **your** commit's version of that file whole. Which side is that?
--- choice
`--ours`, because it is your branch being rebased.
--- choice correct
`--theirs`: during a rebase, HEAD ("ours") is the new base plus what has been replayed, and "theirs" is the commit being replayed, yours.
--- choice
Either: in a rebase both labels mean your branch.
--- choice
Neither: a rebase conflict can only be resolved by hand.
--- why
A rebase first moves to `main`, then applies your commits one by one onto it. So while it applies, `HEAD` is `main`'s side and the commit being applied is "theirs". In a merge it is the other way round: you stand on your branch and `main` comes in as "theirs". Read the labels in the markers rather than assuming; taking a whole side is fine for a generated file, never for code someone changed for a reason.

+++ question | What rerere does not replay
--- ask
With rerere on, Leo resolved a conflict in `drag.py` during a merge, and in the same merge fixed `tests/test_drag.py`, which had merged cleanly but called an old signature. Next week the identical conflict appears in a rebase. What does rerere do?
--- choice
It restores both files as Leo left them.
--- choice correct
It writes Leo's resolution into `drag.py` but leaves it for him to check and `git add`; the test fix is not replayed, because that file never conflicted.
--- choice
It commits the resolution and carries on with the rebase by itself.
--- choice
Nothing, because the conflict came from a merge and now it is a rebase.
--- why
rerere records conflicted hunks and their resolutions, fingerprinted with the two sides sorted, so a merge's resolution also fits the same clash in a rebase. It does not record ordinary edits to files that merged cleanly, so the semantic fix to the test must be made again (or better, made once in its own commit). And unless `rerere.autoUpdate` is on, the file stays unmerged until you review it, run the tests and `git add` it.

+++ question | A test that cannot see a transpose
--- ask
A pull request adds `quat_to_dcm(q)` and one test: for a random quaternion, `np.allclose(C @ C.T, np.eye(3))` and `det(C) == 1`. The implementation returns the transpose of the correct matrix. Does the test catch it?
--- choice correct
No: the transpose of a rotation matrix is also a rotation matrix, so it passes both checks. A lopsided case with a known answer, such as a 90° yaw, is needed.
--- choice
Yes: a transposed matrix is not orthonormal.
--- choice
Yes: its determinant is −1.
--- choice
Only if the random quaternion happens to be the identity.
--- why
For a rotation, `C.T` is the inverse rotation: its columns are still perpendicular unit vectors and its determinant is still +1. So orthonormality tests pass for `C` and `C.T` alike, and the identity quaternion is worse, since the identity equals its own transpose. Ask for a case where the right answer and the likely wrong one differ: a +90° yaw must take inertial +x to body −y, not +y.

+++ question | Two copies of one fix
--- ask
A fix was made on `main` and cherry-picked to `release/1.4`, where it needed a small adaptation. Months later, someone merges `release/1.4` into `main`. What is the risk?
--- choice
None: Git recognizes the two commits as the same change and skips one.
--- choice correct
The two copies are unrelated commits to Git: the merge can conflict between the two versions, or, if nearby lines changed, go through cleanly with the fix applied twice or half-undone.
--- choice
The merge is refused because the release branch contains a cherry-picked commit.
--- choice
Only the commit messages clash, because both say the same thing.
--- why
A cherry-pick makes a new commit with no arrow in the graph back to the original. An exact copy may merge silently (both sides made the same change), but an adapted copy differs, so the merge must reconcile two versions of one fix. That is why a team picks one direction and writes it down: fix on `main` and pick back without ever merging release branches into `main`, or fix on the oldest release and merge forward, never both.

+++ question | A plus in the first column
--- ask
Right after `git pull`, `git submodule status` prints `+b462cf3… extern/frames (v0.3.0)`. What does the `+` mean, and what should you normally run?
--- choice
The submodule has new commits of yours; commit them with `git commit -a`.
--- choice correct
The commit checked out in the submodule differs from the pin; after a pull that usually means you are behind, so run `git submodule update`.
--- choice
The submodule is not initialized; run `git submodule update --init`.
--- choice
The library has a newer release; run `git submodule update --remote`.
--- why
The first column compares the checkout on disk with the gitlink the superproject records. A space means they match, `-` means not initialized, `+` means they differ. The pull moved the pin to the new version; your checkout is still on the old one. `git submodule update` checks out the pinned commit. Committing now with `-a` would pin the old version again, silently undoing a teammate's update.

+++ question | Lock first
--- ask
Ravi must edit `models/nav_filter.slx`, which is lockable. Leo has just finished editing it. Why is "`git lfs lock`, then `git pull`" the safe order, and "`git pull`, then `git lfs lock`" not?
--- choice
Locking first makes the pull faster.
--- choice correct
While Ravi holds the lock nobody else can push the file, so a pull after locking is guaranteed to bring its newest version; pulling first leaves a gap in which Leo can push a newer version Ravi never sees.
--- choice
`git pull` releases all of your locks, so it must come first.
--- choice
Either order is safe, because Git LFS merges the two versions.
--- why
The lock closes the window. Pull-then-lock: Ravi pulls version A, Leo pushes B and unlocks, Ravi locks and edits A, and one of the two sets of work must be redone by hand, because a model cannot be three-way merged. Lock-then-pull: the lock can only be taken once Leo has released it, after his push, and from then on the file cannot change under Ravi.
