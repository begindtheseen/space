+++ practice | One chunk per worker
--- task
A ground tool splits `samples` telemetry samples between worker threads, one contiguous chunk per worker. `hint` is the number that `std::thread::hardware_concurrency()` returned.

Write `std::vector<std::pair<int, int>> plan_chunks(int samples, unsigned hint)`. Each pair is one chunk, written as a half-open range: `{first, last}` means samples `first` up to, but not including, `last`.

- Use `hint` workers. `hardware_concurrency()` may return 0 when it cannot tell, so a `hint` of 0 means one worker.
- Never plan more workers than there are samples: no chunk may be empty.
- If `samples` is 0 or negative, return an empty vector.
- The chunks are in order and together cover 0 up to `samples`. Their sizes differ by at most one, and the bigger chunks come first.

For example, `plan_chunks(10, 4)` returns `{0, 3}, {3, 6}, {6, 8}, {8, 10}`.
--- starter
#include <utility>
#include <vector>

std::vector<std::pair<int, int>> plan_chunks(int samples, unsigned hint) {
    return {};
}
--- solution
#include <utility>
#include <vector>

std::vector<std::pair<int, int>> plan_chunks(int samples, unsigned hint) {
    std::vector<std::pair<int, int>> chunks;
    if (samples <= 0) return chunks;

    // hardware_concurrency() is only a hint, and 0 means "unknown".
    int workers = hint == 0 ? 1 : static_cast<int>(hint);
    if (workers > samples) workers = samples;     // no empty chunks

    const int base = samples / workers;
    const int extra = samples % workers;          // the first 'extra' chunks get one more
    int first = 0;
    for (int w = 0; w < workers; ++w) {
        const int size = base + (w < extra ? 1 : 0);
        chunks.push_back({first, first + size});
        first += size;
    }
    return chunks;
}
--- hint
Work out the number of workers first, from `hint` and `samples`. Then every chunk has `samples / workers` samples, and some get one more.
--- hint
`samples % workers` is how many chunks get the extra sample. Give it to the first ones, and keep a running `first` that each chunk starts from.

--- check case | Twelve samples split evenly

=> std::vector<std::pair<int, int>>{{0, 3}, {3, 6}, {6, 9}, {9, 12}}
--- check case | A hint of 0 means one worker

=> std::vector<std::pair<int, int>>{{0, 10}}
--- check case | More hardware threads than samples
plan_chunks(3, 8)
=> std::vector<std::pair<int, int>>{{0, 1}, {1, 2}, {2, 3}}
--- check case | No samples
plan_chunks(0, 4)
=> std::vector<std::pair<int, int>>{}
--- check case | A negative count

=> std::vector<std::pair<int, int>>{}

+++ practice | A beacon that stops when asked
--- task
A beacon task sends one frame per cycle. In flight a `std::jthread` runs it and passes it a `std::stop_token`; here the checks call it directly.

Write `int beacon_loop(std::stop_token st, int max_cycles, const std::function<void(int)>& send)`:

- At the top of every cycle, check the token. If a stop has been requested, stop at once.
- Otherwise call `send(cycle)`, where `cycle` counts 0, 1, 2 and so on.
- Stop after `max_cycles` cycles even if nobody asks.
- Return how many cycles ran, which is how many times `send` was called.

`send` may request the stop itself, the way `main` would from outside. If `send` requests it during cycle 2, cycles 0, 1 and 2 have run, the check at the top of cycle 3 sees the request, and the function returns 3. A default-constructed `std::stop_token` has no stop source behind it, so it never reports a stop.
--- starter
#include <functional>
#include <stop_token>

int beacon_loop(std::stop_token st, int max_cycles, const std::function<void(int)>& send) {
    return 0;
}
--- solution
#include <functional>
#include <stop_token>

// Stopping is cooperative: the loop reads the token once per cycle, at a safe point.
int beacon_loop(std::stop_token st, int max_cycles, const std::function<void(int)>& send) {
    int cycle = 0;
    while (cycle < max_cycles && !st.stop_requested()) {
        send(cycle);
        ++cycle;
    }
    return cycle;
}
--- hint
One loop does it. Its condition has two parts: cycles left, and no stop requested yet.
--- hint
Put the token check in the loop condition, so it runs before the first cycle too. Then a stop requested before the call means no cycle runs at all.
--- check test | A stop requested during cycle 2 ends the loop after it
[] { std::stop_source src; std::vector<int> sent; int n = beacon_loop(src.get_token(), 10, [&](int c) { sent.push_back(c); if (c == 2) src.request_stop(); }); return n == 3 && sent == std::vector<int>{0, 1, 2}; }()
--- check test | A stop requested before the call runs no cycle
[] { std::stop_source src; src.request_stop(); int calls = 0; int n = beacon_loop(src.get_token(), 10, [&](int) { ++calls; }); return n == 0 && calls == 0; }()

[] { std::stop_source src; int calls = 0; int n = beacon_loop(src.get_token(), 5, [&](int) { ++calls; }); return n == 5 && calls == 5; }()
--- check test | A default-constructed token never stops the loop

--- check test | Zero cycles allowed
[] { std::stop_source src; int calls = 0; int n = beacon_loop(src.get_token(), 0, [&](int) { ++calls; }); return n == 0 && calls == 0; }()

+++ practice | The rules std::thread enforces
--- task
Build a small class that follows the ownership rules of `std::thread`, without running anything, so the rules can be tested. A global counter stands in for `std::terminate`: where a real `std::thread` would end the program, add one to it instead.

```cpp
int g_terminations = 0;
```

Write `class Handle` with:

- `Handle()`: refers to no thread, so it is not joinable.
- `explicit Handle(int id)`: refers to a running thread with this id. The id is always positive. Joinable.
- `bool joinable() const` and `int id() const`. `id()` returns 0 when the handle refers to no thread.
- `bool join()` and `bool detach()`: if joinable, stop referring to the thread and return `true`. If not joinable, change nothing and return `false` (a real `std::thread` would throw here).
- A move constructor: the new handle takes over the thread, and the old one refers to no thread.
- A move assignment: if the handle being assigned to is still joinable, add one to `g_terminations` first, as `std::thread` would terminate. Then take over the other handle's thread.
- Copying deleted.
- A destructor that adds one to `g_terminations` if the handle is still joinable.

Mark both move operations `noexcept`, as `std::thread` does.
--- starter
int g_terminations = 0;  // stands in for std::terminate

class Handle {
public:
    Handle() = default;
    explicit Handle(int id) {}
    Handle(Handle&& other) noexcept {}
    Handle& operator=(Handle&& other) noexcept { return *this; }
    ~Handle() {}
    bool joinable() const { return false; }
    int id() const { return 0; }
    bool join() { return false; }
    bool detach() { return false; }
};
--- solution
int g_terminations = 0;  // stands in for std::terminate

// The ownership rules of std::thread, with a counter instead of std::terminate.
class Handle {
public:
    Handle() = default;
    explicit Handle(int id) : id_(id) {}

    Handle(const Handle&) = delete;             // one thread, one owner
    Handle& operator=(const Handle&) = delete;

    Handle(Handle&& other) noexcept : id_(other.id_) { other.id_ = 0; }

    Handle& operator=(Handle&& other) noexcept {
        if (this != &other) {
            if (joinable()) ++g_terminations;  // overwriting a live thread
            id_ = other.id_;
            other.id_ = 0;
        }
        return *this;
    }

    ~Handle() {
        if (joinable()) ++g_terminations;      // destroyed while still joinable
    }

    bool joinable() const { return id_ != 0; }
    int id() const { return id_; }

    bool join() { return release(); }
    bool detach() { return release(); }

private:
    bool release() {
        if (!joinable()) return false;
        id_ = 0;
        return true;
    }

    int id_ = 0;  // 0: refers to no thread
};
--- hint
One member is enough to hold the state: the id, with 0 meaning "no thread". `joinable()` is then a single comparison.
--- hint
The move constructor copies the id and sets the other handle's id to 0. The move assignment checks its own `joinable()` before it overwrites anything, and the destructor makes the same check.
--- hint
`join()` and `detach()` do the same thing to the state: they differ only in what the real thread does next. Share one private helper.

--- check test | A default handle is not joinable and cannot be joined
[] { g_terminations = 0; bool ok = false; { Handle h; ok = !h.joinable() && !h.join() && !h.detach(); } return ok && g_terminations == 0; }()
--- check test | Moving hands the thread over
[] { g_terminations = 0; bool ok = false; { Handle a(3); Handle b = std::move(a); ok = !a.joinable() && b.joinable() && b.id() == 3; b.join(); } return ok && g_terminations == 0; }()
--- check test | Assigning over a joinable handle terminates
[] { g_terminations = 0; int at_assign = -1; { Handle a(1); Handle b(2); a = std::move(b); at_assign = g_terminations; a.join(); } return at_assign == 1 && g_terminations == 1; }()
--- check test | Assigning over a joined handle is fine
[] { g_terminations = 0; bool ok = false; { Handle a(1); a.join(); Handle b(2); a = std::move(b); ok = a.id() == 2 && !b.joinable(); a.join(); } return ok && g_terminations == 0; }()

[] { g_terminations = 0; { std::vector<Handle> v; for (int i = 1; i <= 20; ++i) v.emplace_back(i); for (auto& h : v) h.join(); } return g_terminations == 0; }()

+++ practice | A log drain that runs once too often
--- task
At shutdown, a `std::jthread` runs `drain_log` to move the pending log lines to storage. It should move lines from `pending` to `written`, oldest first, one per cycle, and before every move check two things: that a line is pending, and that no stop has been requested. It returns how many lines it moved.

Instead, when a stop was already requested it still moves one line, and when nothing is pending it reads the front of an empty `std::deque`, which is undefined behavior. Fix it. Keep the signature.
--- starter
#include <deque>
#include <stop_token>
#include <string>
#include <vector>

// Moves pending log lines to 'written', oldest first, until nothing is
// pending or a stop is requested. Returns how many lines it moved.
int drain_log(std::stop_token st, std::deque<std::string>& pending,
              std::vector<std::string>& written) {
    int moved = 0;
    do {
        written.push_back(pending.front());
        pending.pop_front();
        ++moved;
    } while (!pending.empty() && !st.stop_requested());
    return moved;
}
--- solution
#include <deque>
#include <stop_token>
#include <string>
#include <vector>

// Moves pending log lines to 'written', oldest first, until nothing is

int drain_log(std::stop_token st, std::deque<std::string>& pending,

+++ question | A const reference, passed straight to std::thread
--- ask
```cpp
#include <cstdio>
#include <thread>
#include <vector>

void log_gains(const std::vector<double>& gains) {
    std::printf("%.1f\n", gains[0]);
}

int main() {
    std::vector<double> g(4, 1.0);
    std::thread t(log_gains, g);
    g[0] = 5.0;
    t.join();
}
```

Which statement is true?
--- choice
It does not compile: a reference parameter always needs `std::ref` or `std::cref`.
--- choice correct
It compiles and always prints 1.0: the constructor copied `g` into storage the new thread owns, and the parameter binds to that copy.
--- choice
It prints 1.0 or 5.0, depending on which thread runs first, and it is a data race on `g[0]`.
--- choice
It always prints 5.0, because a `const` reference refers to `main`'s vector.
--- why
`std::thread` copies every argument before the constructor returns, and then passes the copy on as a temporary. A `const std::vector<double>&` can bind to a temporary, so this compiles, unlike a non-`const` reference, which is the case that fails with the static assertion. The thread reads its own copy, made before `g[0] = 5.0` ran, so it prints 1.0 every time, and since the two threads never touch the same vector there is no data race. `std::cref(g)` would share `main`'s vector instead, and then this program would have a race.

+++ question | The order a jthread finishes in
--- ask
```cpp
#include <cstdio>
#include <stop_token>
#include <thread>

void worker(std::stop_token st) {
    while (!st.stop_requested()) { }
    std::puts("worker done");
}

int main() {
    {
        std::jthread w(worker);
        std::puts("A");
    }
    std::puts("B");
}
```

In what order are the three lines printed?
--- choice correct
A, then worker done, then B, every time.
--- choice
A, then B; "worker done" is never printed, because `main` returns first.
--- choice
The program never ends, because the worker's loop never stops.
--- choice
It aborts with "terminate called without an active exception".
--- why
At the closing brace the `std::jthread` destructor calls `request_stop()` and then `join()`. The worker's loop checks its token every pass, so it sees the request, prints "worker done" and returns; only then does `join()` return and `main` print "B". A plain `std::thread` here would call `std::terminate` at the brace, and a worker that never checked its token would make the join wait forever.

+++ practice | Is this pair a data race?
--- task
A race checker describes each memory access with this struct:

```cpp
struct Access {
    int thread;    // which thread made the access
    int location;  // which memory location it touched
    bool write;    // true for a write, false for a read
    bool atomic;   // true if it went through a std::atomic operation
    int phase;     // the program starts and joins its threads between phases
};
```

Threads are only started and joined between phases, so every access in an earlier phase happens before every access in a later phase. Inside one phase, accesses from different threads are not ordered at all. Accesses by the same thread are always ordered, by program order.

Write `bool is_data_race(const Access& x, const Access& y)` that returns `true` exactly when the two accesses form a data race, by the lesson's definition. Accesses that are both atomic never form a data race; one atomic and one plain access to the same location can.
--- starter
struct Access {
    int thread;    // which thread made the access
    int location;  // which memory location it touched
    bool write;    // true for a write, false for a read
    bool atomic;   // true if it went through a std::atomic operation
    int phase;     // the program starts and joins its threads between phases
};

bool is_data_race(const Access& x, const Access& y) {
    return false;
}
--- solution
struct Access {
    int thread;    // which thread made the access
    int location;  // which memory location it touched
    bool write;    // true for a write, false for a read
    bool atomic;   // true if it went through a std::atomic operation
    int phase;     // the program starts and joins its threads between phases
};

bool is_data_race(const Access& x, const Access& y) {
    const bool conflict = x.location == y.location && (x.write || y.write);
    const bool unordered = x.thread != y.thread && x.phase == y.phase;
    const bool both_atomic = x.atomic && y.atomic;
    return conflict && unordered && !both_atomic;
}
--- hint
Split the definition into parts: do the two accesses conflict, and is either one ordered before the other?
--- hint
They conflict when the location is the same and at least one is a write. They are unordered when the threads differ and the phase is the same. Then leave out the case where both are atomic.

=> false
--- check case | Different locations

#include <cstddef>
#include <set>
#include <vector>

struct Access {
    int thread;
    int location;
    bool write;
    bool atomic;
    int phase;  // threads are only started and joined between phases
};

bool races(const Access& x, const Access& y) {
    return x.location == y.location && (x.write || y.write) &&
           x.thread != y.thread && x.phase == y.phase && !(x.atomic && y.atomic);
}

std::vector<int> racy_locations(const std::vector<Access>& trace) {
    std::set<int> found;  // sorted, each location once
    for (std::size_t i = 0; i < trace.size(); ++i)
        for (std::size_t j = i + 1; j < trace.size(); ++j)
            if (races(trace[i], trace[j])) found.insert(trace[i].location);
    return {found.begin(), found.end()};
}

+++ practice | Every total a racy counter can reach
--- task
Two threads share a counter that starts at 0. Thread A adds one to it `a` times, thread B `b` times, with a plain `++`. As in the lesson, each `++` is really two steps that matter: a **load** of the counter into the thread's own register, then a **store** of that register plus one. (The add happens inside the register, where the other thread cannot see it.)

Write `std::set<int> possible_totals(int a, int b)` that returns every final value of the counter over every possible interleaving of the two threads' steps. Each thread does its own steps in order; the scheduler may switch threads between any two steps. `a` and `b` are between 0 and 5.

For example, with one increment each the answer is `{1, 2}`: 2 if one thread stores before the other loads, 1 if both load 0 before either stores.
--- starter
#include <set>

std::set<int> possible_totals(int a, int b) {
    return {};
}
--- solution
#include <set>

struct Worker {
    int left = 0;         // increments still to do
    bool loaded = false;  // true between its load and its store
    int reg = 0;          // the value it loaded
};

// Take one step of w: a load if it has not loaded yet, otherwise a store.
void step(Worker& w, int& counter) {
    if (!w.loaded) {
        w.reg = counter;
        w.loaded = true;
    } else {
        counter = w.reg + 1;
        w.loaded = false;
        --w.left;
    }
}

// Try both choices of which thread moves next, until both are done.
void explore(Worker a, Worker b, int counter, std::set<int>& totals) {
    if (a.left == 0 && b.left == 0) {
        totals.insert(counter);
        return;
    }
    if (a.left > 0) {
        Worker na = a;
        int c = counter;
        step(na, c);
        explore(na, b, c, totals);
    }
    if (b.left > 0) {
        Worker nb = b;
        int c = counter;
        step(nb, c);
        explore(a, nb, c, totals);
    }
}

std::set<int> possible_totals(int a, int b) {
    std::set<int> totals;
    Worker wa, wb;
    wa.left = a;
    wb.left = b;
    explore(wa, wb, 0, totals);
    return totals;
}
--- hint
Describe each thread by three things: increments left, whether it has loaded but not yet stored, and the value in its register. The shared counter is the fourth piece of state.
--- hint
From any state there are at most two moves: A takes its next step, or B does. Try each one on a copy of the state, recursively, and record the counter whenever both threads are finished.
--- hint
The numbers are small: with 5 increments each there are only 20 steps, so trying every order is fast.
--- check case | One increment each

=> std::set<int>{1, 2}
--- check case | Two each
possible_totals(2, 2)
=> std::set<int>{2, 3, 4}
--- check case | One against three: the single stale store wins
possible_totals(1, 3)
=> std::set<int>{1, 2, 3, 4}

+++ question | A volatile stop flag
--- ask
The lesson's control loop spun forever at `-O2` because `g_stop` was a plain `bool`. A colleague changes it to `volatile bool g_stop = false;`, and now the loop stops every time at `-O2`. Which statement is right?
--- choice
It is fixed: `volatile` forces a real read of `g_stop` on every pass, and that is all the problem was.
--- choice correct
The loop now happens to stop, but it is still a data race and so still undefined behavior: `volatile` makes no access atomic and orders no other memory between the threads. `std::atomic<bool>` is the fix.
--- choice
It is fixed only on x86; on ARM `volatile` must be combined with `-O0`.
--- choice
It is now worse: `volatile` stops the compiler from keeping `g_cycles` in a register, so the count is wrong.
--- why
The hang was one symptom of the race: the compiler may assume no other thread writes a plain variable without synchronization, so it read `g_stop` once. `volatile` removes that one optimization, which is why the loop appears to work, but the standard still sees two threads accessing one location, one writing, with no happens-before between them. Nothing makes `volatile` accesses indivisible, and nothing orders the other data the two threads share, such as a command the flag was meant to announce. `volatile` is for memory-mapped hardware registers. `std::atomic<bool>` (or a `std::stop_token`) creates the synchronization the program needs.

+++ question | Bit-fields and bytes
--- ask
```cpp

    std::uint8_t mode  : 3;
    std::uint8_t armed : 1;
    std::uint8_t spare;

--- choice correct
`mode` and `armed` only.
--- choice
`armed` and `spare` only.
--- choice
Every pair: they all sit in one struct.
--- choice
No pair: every member has its own name, so each is its own memory location.
--- why
A memory location is one scalar object, or one run of adjacent bit-fields. `mode` and `armed` are adjacent bit-fields, so together they are one location: writing either means reading the byte, changing some bits and writing the byte back, which can undo the other thread's change. `spare` is an ordinary member, a location of its own, so a thread writing it never conflicts with a thread writing `mode` or `armed`. #include <mutex>

// Records how it is used, so the checks can see it. Do not change it.
struct SpyMutex {
    int locks = 0;
    bool held = false;
    bool misuse = false;  // locked while already held, or unlocked while free
    void lock() { if (held) misuse = true; held = true; ++locks; }
    void unlock() { if (!held) misuse = true; held = false; }

struct Frame { int seq; double values[4]; };

// Never waits: a busy mutex means "skip this cycle".
template <typename Mutex>
bool copy_if_free(Mutex& m, const Frame& shared, Frame& out, int& skipped) {
    std::unique_lock<Mutex> lock(m, std::try_to_lock);
    if (!lock.owns_lock()) {
        ++skipped;
        return false;       // the unique_lock owns nothing, so it unlocks nothing
    }
    out = shared;
    return true;            // the destructor unlocks
}

--- hint

- `gate`, `snapshot` and `flights_at` take the mutex **shared**, with `std::shared_lock`, exactly once per call, even when the flight number is out of range. `snapshot` and `flights_at` read all 8 gates under that one lock, so they never see a half-done change.
- `set_gate` takes it **exclusively**, with `std::unique_lock`, once per call, even when it ignores the call.

The given `RwSpy` counts shared and exclusive locks and notices misuse; with `std::shared_mutex` the same class must work unchanged.

// Records how it is used, so the checks can see it. Do not change it.
struct RwSpy {
    int exclusive = 0, shared = 0;  // how often each kind was taken
    int readers = 0;                // shared holders right now
    bool writer = false;            // exclusive holder right now
    bool misuse = false;

template <typename SharedMutex>
class Board {
public:
    int gate(int flight) const {
        std::shared_lock<SharedMutex> lock(m_);   // readers share
        return valid(flight) ? gates_[flight] : -1;
    }

    void set_gate(int flight, int gate) {
        std::unique_lock<SharedMutex> lock(m_);   // the writer is alone
        if (valid(flight)) gates_[flight] = gate;
    }

    std::array<int, 8> snapshot() const {
        std::shared_lock<SharedMutex> lock(m_);   // one lock for all 8
        return gates_;
    }

    int flights_at(int gate) const {
        std::shared_lock<SharedMutex> lock(m_);
        int n = 0;
        for (int g : gates_)
            if (g == gate) ++n;
        return n;
    }

    SharedMutex& mutex() const { return m_; }

private:
    static bool valid(int flight) { return flight >= 0 && flight < 8; }

    mutable SharedMutex m_;
    std::array<int, 8> gates_{};  // guarded by m_
};

+++ question | Which line protects the increment?
--- ask
`m` is a `std::mutex` and `hits` is a global `int` that several threads increment. Each option is the line placed directly above `++hits;`, in the same block. Which one really protects the increment?
--- choice
`std::lock_guard<std::mutex>{m};`
--- choice
`std::scoped_lock lock;`
--- choice
`std::unique_lock<std::mutex> lock(m, std::defer_lock);`
--- choice correct
`std::scoped_lock lock(m);`
--- why
Only the named `std::scoped_lock lock(m);` holds `m` until the end of the block, which is exactly a `std::lock_guard` on one mutex. The unnamed `std::lock_guard<std::mutex>{m};` is a temporary: it locks and unlocks again at its own semicolon, so `++hits` runs unprotected. `std::scoped_lock lock;` names no mutex, so class template argument deduction gives a lock of nothing at all. And a `std::unique_lock` built with `std::defer_lock` holds nothing until someone calls `lock.lock()`. All three compile, which is what makes them dangerous.

+++ practice | Who is stuck forever?
--- task
A hung process was stopped in the debugger. For each thread blocked in `lock()`, you know the mutex it waits for, and for each held mutex, the thread that owns it:

- `waiting` maps a thread's name to the mutex it is blocked on. A thread that is not in `waiting` is running.
- `owner` maps a mutex's name to the thread that holds it. A mutex that is not in `owner` is free.

Write:

```cpp
std::vector<std::string> stuck(const std::map<std::string, std::string>& waiting,
                               const std::map<std::string, std::string>& owner);
```

It returns, in alphabetical order, every thread that can never continue. Follow the arrows from a blocked thread: the mutex it waits for, then that mutex's owner, then what the owner waits for, and so on. If the chain reaches a running thread or a free mutex, the thread will get its turn eventually. If the chain comes back to a thread it has already visited, it has run into a cycle, and the thread is stuck, whether it is on the cycle itself or only waiting for a thread on it. A thread waiting for a mutex it owns itself is a cycle of one.
--- starter
#include <map>
#include <string>
#include <vector>

std::vector<std::string> stuck(const std::map<std::string, std::string>& waiting,
                               const std::map<std::string, std::string>& owner) {
    return {};
}
--- solution
#include <map>
#include <set>
#include <string>
#include <vector>

std::vector<std::string> stuck(const std::map<std::string, std::string>& waiting,
                               const std::map<std::string, std::string>& owner) {
    std::vector<std::string> result;
    for (const auto& [start, first_mutex] : waiting) {   // map order: alphabetical
        std::set<std::string> seen{start};
        std::string mutex = first_mutex;
        bool forever = false;
        while (true) {
            auto held = owner.find(mutex);
            if (held == owner.end()) break;              // free: it will get it
            const std::string& t = held->second;
            if (seen.count(t)) { forever = true; break; } // back to a visited thread
            seen.insert(t);
            auto w = waiting.find(t);
            if (w == waiting.end()) break;               // the owner is running
            mutex = w->second;
        }
        if (forever) result.push_back(start);
    }
    return result;
}
--- hint
Each blocked thread waits for exactly one mutex, and each mutex has at most one owner, so from any thread there is only one path to follow. Walk it with a loop, remembering the threads you have passed.
--- hint
Stop when the mutex is free or its owner is not waiting (it is running): not stuck. Stop when the owner is a thread already seen, the start included: stuck.
--- hint
Iterating over `waiting`, a `std::map`, visits the threads in alphabetical order already.

+++ practice | The first lock that breaks the order
--- task
Every mutex in a program has a rank. The rule from the lesson: a thread may only lock a mutex whose rank is **lower than every rank it already holds**.

```

Every name appears in `rank`, and an unlock always names a mutex the thread holds, though not always the one it locked last. Locking a mutex the thread already holds breaks the rule too, since its rank is not lower than itself.

--- solution
#include <cstddef>
#include <map>
#include <set>
#include <string>
#include <vector>

struct Op {
    bool lock;          // true: lock the mutex; false: unlock it
    std::string mutex;
};

int first_violation(const std::vector<Op>& ops, const std::map<std::string, int>& rank) {
    std::multiset<int> held;  // ranks this thread holds; begin() is the lowest
    for (std::size_t i = 0; i < ops.size(); ++i) {
        const int r = rank.at(ops[i].mutex);
        if (ops[i].lock) {
            if (!held.empty() && r >= *held.begin()) return static_cast<int>(i);
            held.insert(r);
        } else {
            held.erase(held.find(r));  // remove one copy only
        }
    }
    return -1;
}
--- hint
Only the lowest rank held matters: a new lock must be below it. Keep the held ranks in a sorted container.
--- hint
Unlocks may come in any order, so a single "current rank" variable is not enough. A `std::multiset<int>` keeps every held rank, sorted, and `erase(find(r))` removes one of them.

+++ practice | A lock-order graph, like ThreadSanitizer's
--- task
ThreadSanitizer finds potential deadlocks without waiting for a hang: every time a thread locks a mutex while holding others, it draws an arrow from each held mutex to the new one. A cycle of arrows means two orders exist that could deadlock, even if this run never did.

Each task's lock operations are given as strings: `"+nav"` locks `nav`, `"-nav"` unlocks it. The tasks may have run one after another; only the orders matter.

Write `bool potential_deadlock(const std::vector<std::vector<std::string>>& tasks)` that builds the graph from all tasks together and returns `true` if it contains a cycle of two or more mutexes. Unlocks may come in any order. A task that locks one mutex at a time, never holding two, adds no arrows.
--- starter
#include <string>
#include <vector>

bool potential_deadlock(const std::vector<std::vector<std::string>>& tasks) {
    return false;
}
--- solution
#include <map>
#include <set>
#include <string>
#include <vector>

using Graph = std::map<std::string, std::set<std::string>>;

// Depth-first search: reaching a mutex that is still on the current path is a cycle.
bool has_cycle_from(const Graph& g, const std::string& m, std::set<std::string>& on_path,
                    std::set<std::string>& done) {
    if (on_path.count(m)) return true;
    if (done.count(m)) return false;
    on_path.insert(m);
    auto it = g.find(m);
    if (it != g.end())
        for (const auto& next : it->second)
            if (has_cycle_from(g, next, on_path, done)) return true;
    on_path.erase(m);
    done.insert(m);
    return false;
}

bool potential_deadlock(const std::vector<std::vector<std::string>>& tasks) {
    Graph g;  // arrow held -> taken
    for (const auto& ops : tasks) {
        std::set<std::string> held;
        for (const auto& op : ops) {
            const std::string m = op.substr(1);
            if (op[0] == '+') {
                for (const auto& h : held) g[h].insert(m);
                held.insert(m);
            } else {
                held.erase(m);
            }
        }
    }
    std::set<std::string> on_path, done;
    for (const auto& [m, next] : g)
        if (has_cycle_from(g, m, on_path, done)) return true;
    return false;
}
--- hint
First build the graph: for each task, keep the set of mutexes it holds, and on every `+` add an arrow from each held mutex to the new one. A `std::map<std::string, std::set<std::string>>` holds the arrows.
--- hint
Then look for a cycle with a depth-first search that remembers which mutexes are on the current path. Reaching one of those again closes a cycle. Mutexes already fully explored can be skipped.

+++ question | Which condition does it break?
--- ask
The telemetry task holds the frame mutex and needs the bus mutex too. It is changed so that, if the bus mutex is busy, it releases the frame mutex, and tries both again next cycle. Which of the four deadlock conditions does that change break?
--- choice
Mutual exclusion
--- choice
Hold and wait
--- choice correct
No preemption
--- choice
Circular wait
--- why
The task now gives up a resource it holds when it cannot get the next one, which is the same as letting the held mutex be taken back: that breaks "no preemption". Mutual exclusion still holds, since each mutex has one holder at a time. It still holds one mutex while it *tries* the other, so hold and wait is not what changed, and nothing forces a global order, so circular wait is still possible on its own; it just can no longer last. The price is retries, and two tasks doing this in step can livelock.

+++ question | Busy, but going nowhere
--- ask
A process has stopped making progress. `top` shows two of its threads each using 100 percent of a core. Their backtraces show both threads inside a loop that calls `try_lock` on one mutex, fails, unlocks the mutex it holds, and starts again. Neither is in `futex_wait`. What is this?
--- choice
A deadlock: two threads each hold what the other wants.
--- choice correct
A livelock: both threads keep running and retrying in step, but neither ever gets both mutexes.
--- choice
Priority inversion: one of them has a lower priority.
--- choice
A data race on the two mutexes.
--- why
In a deadlock the threads sleep inside `lock()`, which shows as `futex_wait` and no CPU use. +++ practice | A one-slot mailbox
--- task
The problems in this set use `FakeCV`, a stand-in for `std::condition_variable` that needs no second thread. Its `wait(lock)` unlocks the lock, runs `on_wait` (standing for whatever the other threads did while this one slept), and locks again. Like a real wait, it may return when nothing changed. Its predicate form is exactly `while (!pred()) wait(lock);`. It is given in the starter; do not change it.

Write `class Mailbox`, a single slot that a sensor thread fills and a processing thread empties:

- `void put(int v)`: store `v`, replacing any value not yet taken, then call `notify_one()` on the mailbox's condition variable, once per call.
- `int take()`: wait until the slot holds a value, then empty the slot and return the value. If a value is already there, it must return at once, without waiting.
- `FakeCV& cv()`: the condition variable, so a check can set `on_wait` and read the counters.

The state lives in ordinary members guarded by a `std::mutex`, never in the condition variable.
--- starter
#include <cstdlib>
#include <functional>
#include <mutex>

// A stand-in for std::condition_variable, for checks without threads. wait(lock)
// unlocks, runs on_wait (what other threads did meanwhile), and locks again. It
// may return with nothing changed, like a spurious wakeup. Do not change it.
struct FakeCV {
    std::function<void()> on_wait;
    int waits = 0, notify_ones = 0, notify_alls = 0;
    void wait(std::unique_lock<std::mutex>& lock) {
        if (++waits > 100) std::abort();  // it would sleep forever
        lock.unlock();
        if (on_wait) on_wait();
        lock.lock();
    }
    template <typename Pred>
    void wait(std::unique_lock<std::mutex>& lock, Pred pred) {
        while (!pred()) wait(lock);
    }
    void notify_one() { ++notify_ones; }
    void notify_all() { ++notify_alls; }
};

class Mailbox {
public:

+++ question | What the predicate form really is
--- ask
Which loop does exactly what `cv.wait(lock, pred)` does?
--- choice
`if (!pred()) cv.wait(lock);`
--- choice
`do { cv.wait(lock); } while (!pred());`
--- choice correct
`while (!pred()) cv.wait(lock);`
--- choice
`cv.wait(lock); while (!pred()) { }`
--- why
The `while` loop checks before the first sleep, so a notify that came before the wait is not lost, and it checks again after every return from `wait`, so a spurious or stolen wakeup sends the thread back to sleep. The `if` checks only once: after a spurious wakeup it goes on with the condition false. The `do`-`while` sleeps before looking, so if the state was already true it may sleep forever: the lost wakeup. The last one spins with the lock held after one sleep, so no other thread can ever change the state.

+++ question | An atomic flag, set without the mutex
--- ask
A producer sets a `std::atomic<bool> ready` to `true` without locking the mutex, then calls `cv.notify_one()`. The consumer does `std::unique_lock<std::mutex> lock(m); cv.wait(lock, [&] { return ready.load(); });`. What can go wrong?
--- choice
Nothing: `ready` is atomic, so there is no data race and every notify is heard.
--- choice correct
The consumer can check `ready` (false), and then, before it is asleep, the producer sets it and notifies; the notify finds nobody asleep, and the consumer sleeps forever.
--- choice
The consumer can read a torn value of `ready`.
--- choice
The program does not compile: `wait` needs a `bool`, not a `std::atomic<bool>`.
--- why
The mutex is what closes the gap between the consumer's check of the predicate and its going to sleep: `wait` unlocks and sleeps as one step, but only a producer that must take the same mutex to change the state is kept out of that gap. With the change made outside the mutex, the flag can flip and the notify can be sent exactly in between, and a condition variable remembers nothing. Atomicity rules out a data race, not a lost wakeup. The producer must set the state while holding the mutex, even if only for that one line.

// exchange writes true and hands back what was there: only the first caller sees false.
bool first_report(std::atomic<bool>& reported) {
    return !reported.exchange(true);
}

int claim_leader(std::atomic<int>& leader, int id) {

    // One attempt, so the strong form: a failure means the value really was not 0.
    if (leader.compare_exchange_strong(expected, id)) return id;

+++ practice | A counter with a ceiling
--- task
A log counts bytes queued for the radio, and must never count past a ceiling, so `fetch_add` cannot be used: it would overshoot. Write:

```cpp
unsigned add_capped(std::atomic<unsigned>& total, unsigned k, unsigned cap);
```

It adds as much of `k` as fits without going above `cap`, and returns how much it actually added. If `total` is already at or above `cap`, it adds nothing and returns 0. Several threads call it at once, so read, decide and write must be one atomic step: use a compare-and-exchange loop.

Mind the edges: `total + k` can be larger than the biggest `unsigned`, and wrap. For example, with `total` at 4,000,000,000 and a cap of 4,294,967,295 (the largest 32-bit value), adding 500,000,000 adds only 294,967,295.
--- starter
#include <atomic>

unsigned add_capped(std::atomic<unsigned>& total, unsigned k, unsigned cap) {
    return 0;
}
--- solution
#include <atomic>

unsigned add_capped(std::atomic<unsigned>& total, unsigned k, unsigned cap) {
    unsigned old = total.load(std::memory_order_relaxed);
    unsigned add = 0;
    do {
        if (old >= cap) return 0;                       // no room at all
        const unsigned room = cap - old;                // cannot wrap: old < cap
        add = k < room ? k : room;
    } while (!total.compare_exchange_weak(old, old + add, std::memory_order_relaxed));
    // On failure, compare_exchange_weak reloaded 'old'; the loop recomputes from it.
    return add;
}
--- hint
Work out the room left as `cap - old` after checking `old < cap`: that subtraction cannot wrap, while `old + k` can.
--- hint
Put the whole decision inside the retry loop. When `compare_exchange_weak(old, old + add)` fails, `old` holds the fresh value, and the amount to add must be worked out again from it.

+++ practice | A word of fault flags
--- task
Thirty-two fault flags share one `std::atomic<std::uint32_t>`: bit `n` set means fault `n` is active. Any thread may raise or clear faults at any time. Write:

- `bool raise_fault(std::atomic<std::uint32_t>& word, int bit)`: set bit `bit` (0 to 31) and return `true` if this call is the one that set it, `false` if it was already set. For a `bit` outside 0 to 31, change nothing and return `false`.
- `std::uint32_t clear_faults(std::atomic<std::uint32_t>& word, std::uint32_t mask)`: clear every bit that is set in `mask`, and return the bits of `mask` that were set before the call.
- `int active_faults(const std::atomic<std::uint32_t>& word)`: how many bits are set right now.

Each of the first two must be one atomic read-modify-write, so that two threads raising the same fault at the same moment never both get `true`. Relaxed ordering is enough: nothing else is published through these flags.
--- starter

#include <cstdint>

    return false;
}

--- solution
#include <atomic>
#include <bitset>
#include <cstdint>

bool raise_fault(std::atomic<std::uint32_t>& word, int bit) {
    if (bit < 0 || bit > 31) return false;
    const std::uint32_t mask = std::uint32_t{1} << bit;
    // fetch_or returns the word before: the bit was clear there only for the caller that set it.
    const std::uint32_t before = word.fetch_or(mask, std::memory_order_relaxed);
    return (before & mask) == 0;
}

std::uint32_t clear_faults(std::atomic<std::uint32_t>& word, std::uint32_t mask) {
    const std::uint32_t before = word.fetch_and(~mask, std::memory_order_relaxed);
    return before & mask;
}

int active_faults(const std::atomic<std::uint32_t>& word) {
    return static_cast<int>(std::bitset<32>(word.load(std::memory_order_relaxed)).count());
}
--- hint
`fetch_or(mask)` sets bits and `fetch_and(~mask)` clears them, each in one step, and both return the value before. That "before" value answers both questions.
--- hint
Build the mask with `std::uint32_t{1} << bit`, after checking the range: shifting by 32 or more is undefined. `std::bitset<32>(x).count()` counts the set bits.

+++ practice | A spinlock from one flag
--- task
For a critical section of a few instructions, some flight code uses a spinlock instead of a mutex: a thread that finds it taken retries at once instead of sleeping. Build one from `std::atomic_flag`:

```cpp
class SpinLock {
public:
    void lock();
    void unlock();
    bool try_lock();   // take it if free, return whether it did
};
```

- `lock()` spins until it takes the flag, with `test_and_set`.
- `try_lock()` makes one attempt.
- `unlock()` clears the flag.
- Taking the lock must work like an acquire and releasing it like a release, so that what one holder wrote inside is visible to the next: pass `std::memory_order_acquire` to the operation that takes the flag and `std::memory_order_release` to the one that clears it.

With `lock()` and `unlock()`, `std::lock_guard<SpinLock>` works with it.
--- starter
#include <atomic>

    void lock() {}
    void unlock() {}
    bool try_lock() { return false; }

private:
    std::atomic_flag flag_ = ATOMIC_FLAG_INIT;
};
--- solution
#include <atomic>

class SpinLock {
public:
    void lock() {
        while (flag_.test_and_set(std::memory_order_acquire)) {
            // someone holds it: try again at once
        }
    }

    void unlock() { flag_.clear(std::memory_order_release); }

    // test_and_set returns the old value: false means it was free and is now ours.
    bool try_lock() { return !flag_.test_and_set(std::memory_order_acquire); }

private:
    std::atomic_flag flag_ = ATOMIC_FLAG_INIT;  // clear: unlocked
};
--- hint
`test_and_set` sets the flag and returns what it was. If it was already set, somebody else holds the lock.
--- hint
Taking the lock is an acquire, like the load that sees a published flag; releasing it is a release, like the store that publishes. That is exactly the ordering a mutex gives.

+++ question | Five atomic operations in a row
--- ask
What does this print?

```cpp
#include <atomic>
#include <cstdio>

int main() {
    std::atomic<int> a{5};
    int x = a.fetch_add(3);
    int y = a.exchange(1);
    int e = 2;
    bool ok = a.compare_exchange_strong(e, 9);
    std::printf("%d %d %d %d %d\n", x, y, ok, e, a.load());
}
```
--- answer
5 8 0 1 1
--- why
`fetch_add(3)` returns the value before, 5, and leaves `a` at 8. `exchange(1)` returns the value before, 8, and leaves 1. The compare-and-exchange compares `a` (1) with `e` (2): they differ, so nothing is written, it returns `false` (printed as 0), and it copies the current value 1 into `e`. `a` is still 1. Every one of these read-modify-write operations hands back the old value in some way; that is what makes them useful for "who was first?".

+++ question | Store buffering, by ordering
--- ask
`x` and `y` are `std::atomic<int>`, both 0. Thread A runs `x.store(1, S); r1 = y.load(L);`. Thread B runs `y.store(1, S); r2 = x.load(L);`. For which choice of orderings `S` and `L` is the result `r1 == 0 && r2 == 0` impossible?
--- choice
`S` = relaxed, `L` = relaxed
--- choice
`S` = release, `L` = acquire
--- choice correct
`S` = seq_cst, `L` = seq_cst
--- choice
None: at least one load must see the other thread's store, whatever the ordering.
--- why
Only `seq_cst` puts all four operations into one total order that both threads agree on. Whichever store comes first in that order, the other thread's load comes after it and reads 1. Release and acquire do not forbid a store being overtaken by a later load of a different variable, and that is exactly what an x86 store buffer does: both stores wait in their buffers, both loads read 0. The lesson caught this outcome on x86 with relaxed and with release/acquire, and never with `seq_cst`, which is why a `seq_cst` store compiles to `xchg`.

+++ practice | Counting memory locations
--- task
A struct's members are described, in declaration order, by one number each:

- `-1`: an ordinary member, such as a `double` or an `int`;
- a positive number: a bit-field of that many bits;
- `0`: an unnamed zero-width bit-field, `unsigned : 0;`, which holds no data but ends a run of bit-fields.

Write `std::vector<int> location_ids(const std::vector<int>& widths)` that gives each member the number of the memory location it belongs to. Number the locations 0, 1, 2 and so on, in order. Use the standard's rule: each ordinary member is a location of its own, and a maximal run of adjacent bit-fields of non-zero width shares one location. A zero-width bit-field belongs to no location: give it -1, and let it end the run it follows.

For example, `{-1, 3, 1, -1}` (a `double`, then `mode : 3` and `armed : 1`, then an `int`) gives `{0, 1, 1, 2}`: two threads may write `mode` and the `int` at once, but not `mode` and `armed`.
--- starter
#include <vector>

std::vector<int> location_ids(const std::vector<int>& widths) {
    return {};
}
--- solution
#include <vector>

std::vector<int> location_ids(const std::vector<int>& widths) {
    std::vector<int> ids;
    int next = 0;               // the next unused location number
    bool in_run = false;        // is the previous member a non-zero-width bit-field?
    for (int w : widths) {
        if (w < 0) {            // ordinary member: a location of its own
            ids.push_back(next++);
            in_run = false;
        } else if (w == 0) {    // zero-width bit-field: no location, ends the run
            ids.push_back(-1);
            in_run = false;
        } else {                // bit-field: joins the current run or starts one
            if (!in_run) ++next;
            ids.push_back(next - 1);
            in_run = true;
        }
    }
    return ids;
}
--- hint
Walk the members once, keeping two things: the next location number to hand out, and whether the previous member was a bit-field of non-zero width.
--- hint
A bit-field starts a new location only when the member before it was not a non-zero-width bit-field. Ordinary members and zero-width bit-fields both end a run.

--- task
Every atomic variable has one modification order: the sequence of values it held, which every thread agrees on. Coherence then says that a thread reading the variable again and again never goes backwards in that order. It may read the same value several times, and it may skip values.

Write `bool coherent(const std::vector<int>& history, const std::vector<int>& reads)`. `history` is the variable's modification order, starting with its initial value; all its values are different. `reads` is what one thread's successive loads returned. Return `true` if the reads are allowed: every value read appears in `history`, and each read is at the same place in the history as the one before it, or later. A thread that reads nothing is always fine.
--- starter

    return false;
}
--- solution
#include <cstddef>
#include <vector>

bool coherent(const std::vector<int>& history, const std::vector<int>& reads) {
    std::size_t at = 0;  // position in the history of the latest value read
    for (int v : reads) {
        std::size_t pos = 0;
        while (pos < history.size() && history[pos] != v) ++pos;
        if (pos == history.size()) return false;  // a value nobody wrote
        if (pos < at) return false;               // back in time
        at = pos;
    }
    return true;
}
--- hint
Turn each value read into its position in `history`. Then the reads are allowed exactly when those positions never decrease.
--- hint
Keep the position of the latest read. A value not in the history at all is never allowed: no store wrote it.

--- task
A trace of one run lists events from several threads. The events of any one thread appear in the vector in their program order.

struct Event {
    int thread;

                // 'S' release store, 'L' acquire load,
                // 's' relaxed store, 'l' relaxed load

Write `bool happens_before(const std::vector<Event>& ev, int a, int b)` that says whether event `a` happens before event `b`, using the lesson's two relations:

- **sequenced-before**: `a` comes before `b` in the same thread;
- **synchronizes-with**: `a` is a release store `'S'` and `b` is an acquire load `'L'` that read it (`b`'s `from` is `a`).

--- solution
#include <cstddef>
#include <vector>

struct Event {
    int thread;
    char kind;  // 'w', 'r', 'S', 'L', 's', 'l'
    int from;   // index of the store a load read, or -1
};

// One step of the relation: sequenced-before, or synchronizes-with.
bool edge(const std::vector<Event>& ev, int i, int j) {
    if (ev[i].thread == ev[j].thread) return i < j;
    return ev[i].kind == 'S' && ev[j].kind == 'L' && ev[j].from == i;
}

bool happens_before(const std::vector<Event>& ev, int a, int b) {
    const int n = static_cast<int>(ev.size());
    std::vector<bool> reached(n, false);
    std::vector<int> todo{a};
    while (!todo.empty()) {               // everything reachable from a in one or more steps
        const int i = todo.back();
        todo.pop_back();
        for (int j = 0; j < n; ++j) {
            if (!reached[j] && edge(ev, i, j)) {
                reached[j] = true;
                todo.push_back(j);
            }
        }
    }
    return reached[b];
}
--- hint
Think of the trace as a graph: an arrow from `i` to `j` when `i` is sequenced before `j`, or when `i` synchronizes with `j`. Happens-before is "reachable by following arrows".
--- hint
Search from `a`: keep a list of events still to explore and a record of those already reached. Only mark events reached through at least one arrow, so that `a` does not count as happening before itself.

--- solution
#include <array>
#include <cstddef>
#include <map>
#include <set>
#include <vector>

struct Instr {
    bool store;  // true: var = arg; false: register arg = var
    char var;
    int arg;
};

struct State {
    std::map<char, int> mem;  // variables not in the map are still 0
    std::array<int, 4> reg{};
};

void apply(const Instr& in, State& s) {
    if (in.store) {
        s.mem[in.var] = in.arg;
    } else {
        auto it = s.mem.find(in.var);
        s.reg[in.arg] = it == s.mem.end() ? 0 : it->second;
    }
}

// i and j: how many instructions of each thread have run so far.
void explore(const std::vector<Instr>& t1, const std::vector<Instr>& t2, std::size_t i,
             std::size_t j, const State& s, std::set<std::array<int, 4>>& out) {
    if (i == t1.size() && j == t2.size()) {
        out.insert(s.reg);
        return;
    }
    if (i < t1.size()) {
        State next = s;
        apply(t1[i], next);
        explore(t1, t2, i + 1, j, next, out);
    }
    if (j < t2.size()) {
        State next = s;
        apply(t2[j], next);
        explore(t1, t2, i, j + 1, next, out);
    }
}

std::set<std::array<int, 4>> sc_outcomes(const std::vector<Instr>& t1, const std::vector<Instr>& t2) {
    std::set<std::array<int, 4>> out;
    explore(t1, t2, 0, 0, State{}, out);
    return out;
}
--- hint
A state is how far each thread has got, plus the memory and the registers. From any state, either thread 1 runs its next instruction or thread 2 does.
--- hint
Try both choices on copies of the state, recursively. When both threads have finished, insert the registers into the result set. A `std::map<char, int>` works for memory, with a missing variable read as 0.

--- task

#include <utility>
#include <vector>

#include <cstddef>
#include <cstdint>
#include <utility>
#include <vector>

// The first offset at or after 'offset' that is a multiple of 'align' (a power of two).
// Adding align - 1, not align, leaves an offset that is already aligned where it is.

        offsets.push_back(at);

    }

+++ question | A hundred milliseconds apart
--- ask
The estimator thread writes a plain `double g_alt`. The display thread sleeps for 100 ms, which is always long after the write has finished, and then reads `g_alt`. There are no atomics, mutexes or joins between them. Which statement is right?
--- choice
It is safe: the write finished long before the read, so the read happens after it.
--- choice
It is safe on x86, where a finished store is visible to every core, and a race only on ARM.
--- choice correct
It is a data race: sleeping creates no happens-before relation, so the conflicting accesses are unordered, whatever a clock says.
--- choice
It is not a race, because only one of the two threads writes.
--- why
Happens-before comes only from chains of sequenced-before and synchronizes-with: thread start and join, unlock then lock, a release store read by an acquire load, a promise and its future. Time is not on that list. With no such chain, a write and a read of one location in two threads are a data race, the program is undefined, and the compiler may, for instance, keep the reader's value of `g_alt` in a register. One writer is enough for a conflict; two reads would not be.

+++ question | The promise of a race-free program
--- ask
A program has no data races, and every atomic operation in it uses the default `seq_cst` ordering. What does the C++ memory model promise about it?
--- choice
Nothing more than for any other program: the compiler and processor may still reorder its operations in ways the threads can see.
--- choice correct
It behaves as if the steps of all its threads were interleaved into one single sequence, each thread's steps in program order, so it can be reasoned about line by line.
--- choice
Its threads run one at a time, in the order they were created.
--- choice
Every run gives the same output.
--- why
This is sequential consistency for data-race-free programs, the bargain at the heart of the model. The compiler and hardware keep all their reorderings, but none of them can be observed by a program that has no races and uses only `seq_cst`. It does not make the program deterministic: different interleavings can still give different results, which is why a race condition is still possible. Break the no-race condition and every guarantee is gone, not only this one.

#include <vector>

std::future<double> request_reading(std::vector<std::promise<double>>& pending) {
    std::promise<double> p;

--- solution
#include <cstdint>
#include <future>
#include <utility>
#include <vector>

std::future<int> lazy_checksum(std::vector<std::uint8_t> data, int& runs) {
    // deferred: nothing runs now; the first get() or wait() runs it on its own thread.
    // The lambda owns the bytes, so the caller's vector may be gone by then.
    return std::async(std::launch::deferred, [bytes = std::move(data), &runs] {
        ++runs;
        int sum = 0;
        for (std::uint8_t b : bytes) sum = (sum + b) % 256;
        return sum;
    });
}
--- hint
`std::launch::deferred` makes `std::async` return at once without running anything; the function runs inside the first `get()` or `wait()`.
--- hint

--- solution
#include <cstddef>
#include <deque>
#include <future>
#include <utility>

class JobQueue {
public:
    template <typename F>
    auto submit(F f) -> std::future<decltype(f())> {
        using R = decltype(f());
        std::packaged_task<R()> task(std::move(f));
        std::future<R> ticket = task.get_future();
        // One queue type for every job: a void() task that owns the real one.
        jobs_.emplace_back([t = std::move(task)]() mutable { t(); });
        return ticket;
    }

    bool run_one() {
        if (jobs_.empty()) return false;
        std::packaged_task<void()> job = std::move(jobs_.front());
        jobs_.pop_front();   // take it out first: the job may submit more
        job();
        return true;
    }

    int run_all() {
        int n = 0;
        while (run_one()) ++n;
        return n;
    }

    std::size_t pending() const { return jobs_.size(); }

private:
    std::deque<std::packaged_task<void()>> jobs_;
};
--- hint
`std::packaged_task<R()> task(std::move(f));` then `task.get_future()` gives the ticket. The task is move-only, so it must be moved into the queue.
--- hint
A `std::deque<std::packaged_task<void()>>` can hold every job, if each entry is a small `mutable` lambda that owns the real task and calls it. Take a job out of the queue before running it, because it may push new jobs onto the same queue.

+++ practice | How long the crew takes
--- task
A pool of `workers` threads takes jobs from one queue, in order: whenever a worker is free, it takes the next job. Every worker is free at time 0, and a job takes exactly its listed time.

Write `long long makespan(const std::vector<int>& jobs_ms, int workers)` that returns the time, in milliseconds, at which the last job finishes. With no jobs it is 0. With `workers` 0 or negative nothing can run, so return -1.

The lesson's example, eight jobs of 100 ms on four workers, gives 200. On three workers the same jobs give 300.
--- starter
#include <vector>

long long makespan(const std::vector<int>& jobs_ms, int workers) {
    return 0;
}
--- solution
#include <functional>
#include <queue>
#include <vector>

long long makespan(const std::vector<int>& jobs_ms, int workers) {
    if (workers <= 0) return -1;
    // When each worker is next free; the earliest is on top.
    std::priority_queue<long long, std::vector<long long>, std::greater<long long>> free_at;
    for (int w = 0; w < workers; ++w) free_at.push(0);
    long long end = 0;
    for (int job : jobs_ms) {
        const long long start = free_at.top();  // the next job goes to the first free worker
        free_at.pop();
        const long long done = start + job;
        free_at.push(done);
        if (done > end) end = done;
    }
    return end;
}
--- hint
Keep, for each worker, the time it will next be free. Each job, in order, goes to the worker that is free earliest.
--- hint
A `std::priority_queue` with `std::greater` keeps the smallest time on top. The answer is the latest finishing time of any job, which is not always the last job's.

+++ practice | Reading a ring's indices
--- task
A telemetry ring of `n` slots, `n` a power of two, uses the one-empty-slot rule: `head` is the slot the producer writes next, `tail` the slot the consumer reads next, both always between 0 and `n - 1`. Write three functions:

std::size_t ring_next(std::size_t i, std::size_t n) {

--- solution
#include <cstddef>

// n is a power of two, so n - 1 is a block of ones and & (n - 1) is the remainder.
std::size_t ring_next(std::size_t i, std::size_t n) {
    return (i + 1) & (n - 1);
}

// Unsigned subtraction wraps round; masking it gives the distance from tail to head.
std::size_t ring_count(std::size_t head, std::size_t tail, std::size_t n) {
    return (head - tail) & (n - 1);
}

// One slot always stays empty, so "full" is "one more push would make head == tail".
bool ring_full(std::size_t head, std::size_t tail, std::size_t n) {
    return ring_next(head, n) == tail;
}
--- hint
All three are one line. The mask `& (n - 1)` keeps a value inside 0 to `n - 1`, for any unsigned value, including one that wrapped below zero.
--- hint

--- task
The starter holds a working single-producer, single-consumer ring in the counters form: `head_` and `tail_` count every item ever pushed and popped, as 32-bit unsigned numbers that are allowed to wrap round, and all `N` slots are usable. The constructor takes the counters' starting value, so a test can start them just below the wrap.

The radio task, the consumer, wants three more member functions. Add them; they are called only by the consumer:

- `std::uint32_t size() const`: how many items are in the ring.
- `bool peek(T& out) const`: copy the oldest item into `out` without removing it; `false` if the ring is empty.

#include <array>
#include <atomic>
#include <cstdint>

template <typename T, std::uint32_t N>
class Ring {
    static_assert(N >= 1 && (N & (N - 1)) == 0, "N must be a power of two");

public:
    explicit Ring(std::uint32_t start = 0) : head_(start), tail_(start) {}

    bool push(const T& v) {  // producer only
        const std::uint32_t h = head_.load(std::memory_order_relaxed);
        if (h - tail_.load(std::memory_order_acquire) == N) return false;  // full
        buf_[h & (N - 1)] = v;
        head_.store(h + 1, std::memory_order_release);
        return true;
    }

    bool pop(T& out) {  // consumer only
        const std::uint32_t t = tail_.load(std::memory_order_relaxed);
        if (t == head_.load(std::memory_order_acquire)) return false;  // empty
        out = buf_[t & (N - 1)];
        tail_.store(t + 1, std::memory_order_release);
        return true;
    }

    // Consumer only. Wrapping subtraction gives the count even across the wrap.
    std::uint32_t size() const {
        return head_.load(std::memory_order_acquire) - tail_.load(std::memory_order_relaxed);
    }

    bool peek(T& out) const {  // consumer only: tail_ is ours, head_ is the producer's
        const std::uint32_t t = tail_.load(std::memory_order_relaxed);
        if (t == head_.load(std::memory_order_acquire)) return false;
        out = buf_[t & (N - 1)];  // no store: the slot stays in the ring
        return true;
    }

    std::uint32_t pop_many(T* out, std::uint32_t max) {  // consumer only
        const std::uint32_t t = tail_.load(std::memory_order_relaxed);
        const std::uint32_t h = head_.load(std::memory_order_acquire);  // once for the batch
        std::uint32_t n = h - t;
        if (n > max) n = max;
        for (std::uint32_t i = 0; i < n; ++i) out[i] = buf_[(t + i) & (N - 1)];
        if (n > 0) tail_.store(t + n, std::memory_order_release);    // frees all n slots at once
        return n;
    }

private:
    std::array<T, N> buf_{};
    std::atomic<std::uint32_t> head_;  // written by the producer
    std::atomic<std::uint32_t> tail_;  // written by the consumer
};

+++ practice | How big must the ring be?
--- task
The 1 kHz control task pushes one telemetry record into a ring every millisecond. The radio task runs once every `period_ms` milliseconds and pops up to `batch` records. Both numbers are at least 1. When the ring is full, the control task never waits: it drops the new record and counts the drop.

Simulate it, millisecond by millisecond, for `t` from 0 to `ms - 1`:

1. The control task pushes record `t`. If the ring already holds `capacity` records, the record is dropped instead.
2. The high-water mark is the most records the ring has ever held right after a push.
3. If `t % period_ms == period_ms - 1`, the radio task runs and pops as many records as it can, up to `batch`.

- `Stats simulate(std::uint32_t capacity, int period_ms, int batch, int ms)` with `struct Stats { int dropped; std::uint32_t high_water; int delivered; };` where `delivered` counts the records the radio popped.

For example, a radio that pops 20 records every 20 ms never lets more than 20 pile up, so a ring of 32 drops nothing; a ring of 16 drops 20 of the first 100 records.

#include <cstdint>

struct Stats {
    int dropped;
    std::uint32_t high_water;
    int delivered;
};

Stats simulate(std::uint32_t capacity, int period_ms, int batch, int ms) {
    Stats s{0, 0, 0};
    std::uint32_t held = 0;                       // records in the ring
    for (int t = 0; t < ms; ++t) {
        if (held == capacity) ++s.dropped;        // full: drop and count, never wait
        else ++held;
        if (held > s.high_water) s.high_water = held;
        if (t % period_ms == period_ms - 1) {     // the radio's turn
            const std::uint32_t take = held < static_cast<std::uint32_t>(batch) ? held : batch;
            held -= take;
            s.delivered += static_cast<int>(take);
        }
    }
    return s;
}

std::uint32_t smallest_capacity(int period_ms, int batch, int ms) {
    for (std::uint32_t cap = 2; cap <= 65536; cap *= 2)
        if (simulate(cap, period_ms, batch, ms).dropped == 0) return cap;
    return 0;
}

+++ question | Where each design sits on the ladder
--- ask
Which list gives the right progress guarantee for each of these three?

1. `push` of the lesson's single-producer, single-consumer ring.
2. A counter that must stop at a limit, updated by several threads with a `compare_exchange_weak` retry loop.
3. A telemetry queue whose `push` locks a `std::mutex`.
--- choice
1 lock-free, 2 wait-free, 3 lock-free
--- choice correct
1 wait-free, 2 lock-free, 3 blocking
--- choice
1 wait-free, 2 wait-free, 3 blocking
--- choice
1 blocking, 2 lock-free, 3 blocking
--- why
The ring's `push` is a fixed handful of steps with no loop and no waiting: when the ring is full it returns `false` at once, so every call finishes in a bounded number of its own steps, which is wait-free. A compare-and-exchange loop only fails because some other thread's attempt succeeded, so the system always progresses, but one unlucky thread can lose again and again: lock-free, not wait-free. A mutex is blocking: if its holder is descheduled, everyone who wants it waits for as long as that lasts. Real-time analysis wants the first kind.

+++ question | Counters across the wrap
--- ask
A ring of 8 slots uses free-running 32-bit unsigned counters. Right now `head` is `0x00000002` and `tail` is `0xFFFFFFFE`: the producer's counter has wrapped round, and the consumer's has not yet. How many items does the ring hold? Type the number.
--- answer
4
four
--- why
`head - tail` is computed in 32-bit unsigned arithmetic, which wraps round: 2 minus 4,294,967,294 is 4 modulo 2 to the power 32. That is exactly the number of pushes since the consumer's position: tail was at `0xFFFFFFFE`, and pushes happened at `0xFFFFFFFE`, `0xFFFFFFFF`, `0x00000000` and `0x00000001`. Because 8 divides 2 to the power 32, the slots `count & 7` also stay continuous across the wrap, which is why the counters form keeps working through it.

#include <cstdint>

bool share_line(std::uint64_t a, std::uint32_t a_size, std::uint64_t b, std::uint32_t b_size,
                std::uint32_t line) {
    // The lines an object touches: from its first byte's line to its last byte's line.
    const std::uint64_t a_first = a / line, a_last = (a + a_size - 1) / line;

}

};

bool bytes_overlap(const Var& x, const Var& y) {
    return x.addr < y.addr + y.size && y.addr < x.addr + x.size;
}

bool lines_overlap(const Var& x, const Var& y, std::uint32_t line) {
    const std::uint64_t x_first = x.addr / line, x_last = (x.addr + x.size - 1) / line;
    const std::uint64_t y_first = y.addr / line, y_last = (y.addr + y.size - 1) / line;
    return x_first <= y_last && y_first <= x_last;
}

std::vector<std::pair<int, int>> false_sharing(const std::vector<Var>& vars, std::uint32_t line) {
    std::vector<std::pair<int, int>> pairs;
    for (std::size_t i = 0; i < vars.size(); ++i)
        for (std::size_t j = i + 1; j < vars.size(); ++j)
            if (vars[i].thread != vars[j].thread && !bytes_overlap(vars[i], vars[j]) &&
                lines_overlap(vars[i], vars[j], line))
                pairs.push_back({static_cast<int>(i), static_cast<int>(j)});
    return pairs;
}
--- hint
Two tests on byte ranges: do the bytes themselves overlap (that is true sharing, not reported), and do the ranges of line numbers overlap (that is sharing a line).
--- hint
Byte ranges `[a, a + s)` and `[b, b + t)` overlap when `a < b + t` and `b < a + s`. Loop over pairs with `j` starting at `i + 1`, and the output is already in the right order.

+++ practice | Padded slots that still share
--- task
A statistics table is carved out of a buffer at address `base`: one slot of `size` bytes per core, each meant to own its cache line so the cores never falsely share. `slot_address(base, index, size, line)` returns where slot `index` goes. `size` is never larger than `line`, and `line` is a power of two.

It spaces the slots one line apart, but it does not start them on a line boundary. When `base` is not a multiple of `line`, a slot can cross into the next line, where the next slot begins, and two cores share that line again. Fix `slot_address` so every slot starts on a line boundary: slot 0 at the first multiple of `line` at or after `base`, and each later slot one line further on.
--- starter
#include <cstddef>
#include <cstdint>

// Address of per-core slot 'index' in a buffer that starts at 'base'.
std::uint64_t slot_address(std::uint64_t base, int index, std::uint32_t size, std::uint32_t line) {
    return base + static_cast<std::uint64_t>(index) * line;
}
--- solution
#include <cstddef>
#include <cstdint>

// Address of per-core slot 'index' in a buffer that starts at 'base'.
std::uint64_t slot_address(std::uint64_t base, int index, std::uint32_t size, std::uint32_t line) {
    // First line boundary at or after base; then one whole line per slot.
    const std::uint64_t first = (base + line - 1) & ~static_cast<std::uint64_t>(line - 1);
    return first + static_cast<std::uint64_t>(index) * line;
}
--- hint
Spacing the slots one line apart is only half of it: the first slot must also start where a line starts, or every slot straddles the same way.
--- hint

+++ question | More threads, slower loop
--- ask
```cpp
long counts[4];   // global

void worker(int id, const std::vector<int>& samples) {
    for (int s : samples)
        if (s > 1000) ++counts[id];
}
```

Each of four threads runs `worker` with its own `id` on its own samples. Each thread writes only its own element, and the counts come out right, but four threads take longer than one thread doing all the work. Which change is the best fix for a loop over millions of samples?
--- choice
Make `counts` an array of `std::atomic<long>`.
--- choice
Protect each `++counts[id]` with a mutex.
--- choice correct
Count in a local variable inside `worker`, and write it to `counts[id]` once, after the loop.
--- choice
Declare `counts` `volatile`, so each core sees the others' writes sooner.
--- why
The four `long`s sit in one cache line, so every increment takes the line away from the other cores: false sharing, the classic cause of code that gets slower as threads are added. A local counter lives in a register or on the thread's own stack, so the hot loop touches nothing shared, and the shared array is written four times in total. Padding each element to its own line also works, but still writes memory on every hit. Atomics and mutexes make each increment more expensive and keep the line bouncing; `volatile` forces every write to memory and helps nothing.

+++ question | The other interference constant
--- ask
A control task reads a small struct of three values together every cycle: the current attitude error, rate and gain. You want the whole struct to fit in one cache line, so reading it costs one line fetch. Which constant from `<new>` describes that goal?
--- choice
`std::hardware_destructive_interference_size`: pad the struct to it.
--- choice correct
`std::hardware_constructive_interference_size`: keep the struct no larger than it, and aligned so it does not straddle a line.
--- choice
Neither: `alignof` of the struct already says how many lines it touches.
--- choice
`sizeof(std::max_align_t)`
--- why
The destructive size is the spacing that keeps things written by different threads apart. The constructive size is the largest block you can expect to sit in one line, the one to stay within for data that one thread uses together. Both are 64 with g++ 13 on x86-64, but they answer opposite questions: separate, or keep together. `alignof` says where an object may start, not how big a line is, and `std::max_align_t` is about the strictest alignment of an ordinary type.

#include <vector>

+++ practice | Worst-case response times
--- task
Using `struct Task { long long c; long long t; };` (worst-case execution time and period, in microseconds, deadline equal to period), write `std::vector<long long> response_times(const std::vector<Task>& tasks)`.

- Priorities are rate-monotonic: a shorter period means a higher priority. Two tasks with the same period: the one earlier in the vector has the higher priority. The tasks may be listed in any order.
- For each task, compute its worst-case response time with the lesson's iteration: start with R = c plus the `c` of every higher-priority task, then repeat R = c + the sum, over higher-priority tasks j, of ceiling(R / t_j) × c_j, until R stops changing.
- If R ever goes above the task's deadline, stop: the task misses, and its entry is -1.
- Return the results in the same order as the input.

Work in whole numbers. The ceiling of `a / b` for positive whole numbers is `(a + b - 1) / b`.
--- starter
#include <vector>

struct Task { long long c; long long t; };

    return {};
}
--- solution
#include <cstddef>
#include <vector>

struct Task { long long c; long long t; };  // microseconds; deadline = period

// Does task j have a higher priority than task i? Shorter period wins; ties go to the earlier one.
bool higher(const std::vector<Task>& tasks, std::size_t j, std::size_t i) {
    if (tasks[j].t != tasks[i].t) return tasks[j].t < tasks[i].t;
    return j < i;
}

std::vector<long long> response_times(const std::vector<Task>& tasks) {
    std::vector<long long> result(tasks.size());
    for (std::size_t i = 0; i < tasks.size(); ++i) {
        long long r = tasks[i].c;
        for (std::size_t j = 0; j < tasks.size(); ++j)
            if (higher(tasks, j, i)) r += tasks[j].c;
        while (true) {
            if (r > tasks[i].t) { r = -1; break; }        // past the deadline: a miss
            long long next = tasks[i].c;
            for (std::size_t j = 0; j < tasks.size(); ++j)
                if (higher(tasks, j, i))
                    next += (r + tasks[j].t - 1) / tasks[j].t * tasks[j].c;  // releases in r, rounded up
            if (next == r) break;                          // settled: the answer
            r = next;
        }
        result[i] = r;
    }
    return result;
}
--- hint
Write a small function that says whether task `j` outranks task `i`: shorter period, or the same period and an earlier index. Then the higher-priority tasks of `i` are the `j` for which it is true.
--- hint
Each round, compare the new R with the old one: equal means done; above the deadline means a miss. The count of releases of task j in a window of length R is `(R + t_j - 1) / t_j`.

+++ practice | Run the schedule for a whole hyperperiod
--- task
Response-time analysis predicts; this problem simulates. Periodic tasks run on one processor under preemptive, fixed-priority, rate-monotonic scheduling. Time moves in whole ticks. Each task is `struct Task { long long c; long long t; };`, `c` and `t` in ticks, with `1 <= c` and `1 <= t <= 1000`.

- Every task releases a job at time 0 and every `t` ticks after that. The job needs `c` ticks of processor time, and its deadline is the task's next release.
- In each tick, the processor runs one tick of the highest-priority task that has work left (shorter period first; same period, earlier in the vector first), or idles.
- A job still unfinished when its task's next release comes is a deadline miss.

Write `std::pair<int, long long> first_miss(const std::vector<Task>& tasks)` that simulates from time 0 to the hyperperiod, the least common multiple of all periods, and returns `{task index, time}` of the first deadline miss, or `{-1, -1}` if none happens. At one instant, check for misses before releasing new jobs, and if several tasks miss at the same instant, report the lowest index. Check at the hyperperiod itself too. For no tasks, return `{-1, -1}`.
--- starter
#include <utility>
#include <vector>

struct Task { long long c; long long t; };

std::pair<int, long long> first_miss(const std::vector<Task>& tasks) {
    return {-2, -2};
}
--- solution
#include <cstddef>
#include <numeric>
#include <utility>
#include <vector>

struct Task { long long c; long long t; };  // ticks; deadline = next release

std::pair<int, long long> first_miss(const std::vector<Task>& tasks) {
    if (tasks.empty()) return {-1, -1};
    long long hyper = 1;
    for (const Task& k : tasks) hyper = std::lcm(hyper, k.t);

    const std::size_t n = tasks.size();
    std::vector<long long> left(n, 0);  // work left in each task's current job
    for (long long now = 0; now <= hyper; ++now) {
        for (std::size_t i = 0; i < n; ++i)          // misses first, lowest index first
            if (now > 0 && now % tasks[i].t == 0 && left[i] > 0)
                return {static_cast<int>(i), now};
        if (now == hyper) break;
        for (std::size_t i = 0; i < n; ++i)          // then this instant's releases
            if (now % tasks[i].t == 0) left[i] = tasks[i].c;

        int run = -1;                                // highest priority with work left
        for (std::size_t i = 0; i < n; ++i) {
            if (left[i] == 0) continue;
            if (run < 0 || tasks[i].t < tasks[run].t) run = static_cast<int>(i);
        }
        if (run >= 0) --left[run];                   // one tick of processor time
    }
    return {-1, -1};
}
--- hint
Keep one number per task: the work its current job still needs. At each tick: check misses, release new jobs, then give the tick to one task.
--- hint
`std::lcm` from `<numeric>` gives the hyperperiod. When choosing the task to run, a strict `<` on the period while scanning in index order keeps ties with the earlier task.

#include <string>
#include <vector>

struct User {
    std::string task;
    int priority;
    std::vector<std::string> mutexes;
};

std::map<std::string, int> ceilings(const std::vector<User>& users) {

        for (const std::string& m : u.mutexes) {
            auto it = ceiling.find(m);

        }
    }
    return ceiling;
}

+++ practice | Response times with blocking
--- task
With priority inheritance or ceilings, a task's worst-case response time grows by its blocking time `b`:

R = c + b + the sum, over higher-priority tasks j, of ceiling(R / t_j) × c_j.

```cpp
struct Task { long long c; long long t; long long b; };  // microseconds; deadline = period
```

Write `std::vector<long long> response_times(const std::vector<Task>& tasks)`. Priorities are rate-monotonic: shorter period first, and for equal periods the earlier task first; the tasks may be in any order. Start with R = c + b + the `c` of every higher-priority task and iterate until R stops changing. If R ever goes above the task's period, its entry is -1. Return the results in input order, using whole numbers only.
--- starter

    return {};
}
--- solution
#include <cstddef>
#include <vector>

struct Task { long long c; long long t; long long b; };  // microseconds; deadline = period

bool higher(const std::vector<Task>& tasks, std::size_t j, std::size_t i) {
    if (tasks[j].t != tasks[i].t) return tasks[j].t < tasks[i].t;
    return j < i;
}

std::vector<long long> response_times(const std::vector<Task>& tasks) {
    std::vector<long long> result(tasks.size());
    for (std::size_t i = 0; i < tasks.size(); ++i) {
        long long r = tasks[i].c + tasks[i].b;
        for (std::size_t j = 0; j < tasks.size(); ++j)
            if (higher(tasks, j, i)) r += tasks[j].c;
        while (true) {
            if (r > tasks[i].t) { r = -1; break; }
            long long next = tasks[i].c + tasks[i].b;   // blocking: once per activation
            for (std::size_t j = 0; j < tasks.size(); ++j)
                if (higher(tasks, j, i)) next += (r + tasks[j].t - 1) / tasks[j].t * tasks[j].c;
            if (next == r) break;
            r = next;
        }
        result[i] = r;
    }
    return result;
}
--- hint
It is last lesson's iteration with one more constant term. `b` is added once, like `c`, not once per release of another task.
--- hint
Keep the priority test in its own function: shorter period, or equal period and earlier index. The ceiling of `R / t` is `(R + t - 1) / t`.

+++ practice | Simulate the inversion
--- task
Simulate three or more jobs on one processor, one tick at a time, with one shared mutex, under three protocols:

```cpp
enum class Protocol { None, Inherit, Ceiling };
struct Job {
    int priority;  // higher number = more urgent; all different
    int release;   // the tick at which it becomes ready
    int before;    // ticks of work before it needs the mutex
    int locked;    // ticks of work while holding the mutex (0: it never takes the mutex)
    int after;     // ticks of work after it releases the mutex
};
```

Write `std::vector<int> finish_times(const std::vector<Job>& jobs, Protocol p)` that returns, in input order, the tick at which each job finishes (a job whose last tick of work is tick 104 finishes at 105). Rules, applied at every tick `t` from 0:

1. A job is **ready** once `t >= release`, until it finishes.
2. A ready job is **blocked** if it has done all its `before` work, still has `locked` work, does not hold the mutex, and another job holds it.
3. **Effective priority**: normally the job's own priority. Under `Inherit`, the holder of the mutex runs at the highest priority among itself and the ready jobs blocked on the mutex. Under `Ceiling`, the holder runs at the highest of its own priority and the ceiling, the highest priority of any job with `locked` work.
4. Of the ready jobs that are not blocked, the one with the highest effective priority runs this tick; if two tie, the holder of the mutex runs. If none can run, the processor idles.
5. The running job does one tick of its next phase. If that is its first tick of `locked` work, it takes the mutex at the start of the tick; after its last tick of `locked` work it releases the mutex.
--- starter

    int before;
    int locked;
    int after;

--- solution
#include <algorithm>
#include <cstddef>
#include <vector>

enum class Protocol { None, Inherit, Ceiling };

struct Job {
    int priority;
    int release;
    int before;
    int locked;
    int after;
};

std::vector<int> finish_times(const std::vector<Job>& jobs, Protocol p) {
    const int n = static_cast<int>(jobs.size());
    std::vector<Job> left = jobs;              // work still to do, phase by phase
    std::vector<int> finish(n, -1);
    int holder = -1;                           // which job holds the mutex, or -1
    int ceiling = 0;
    for (const Job& j : jobs)
        if (j.locked > 0) ceiling = std::max(ceiling, j.priority);

    int done = 0;
    for (int t = 0; done < n; ++t) {
        auto ready = [&](int i) { return jobs[i].release <= t && finish[i] < 0; };
        auto blocked = [&](int i) {
            return left[i].before == 0 && left[i].locked > 0 && holder >= 0 && holder != i;
        };

        std::vector<int> eff(n);
        for (int i = 0; i < n; ++i) eff[i] = jobs[i].priority;
        if (holder >= 0 && p == Protocol::Inherit)
            for (int i = 0; i < n; ++i)
                if (ready(i) && blocked(i)) eff[holder] = std::max(eff[holder], jobs[i].priority);
        if (holder >= 0 && p == Protocol::Ceiling) eff[holder] = std::max(eff[holder], ceiling);

        int run = -1;
        for (int i = 0; i < n; ++i) {
            if (!ready(i) || blocked(i)) continue;
            if (run < 0 || eff[i] > eff[run] || (eff[i] == eff[run] && i == holder)) run = i;
        }
        if (run < 0) continue;                 // idle tick

        Job& w = left[run];
        if (w.before > 0) {
            --w.before;
        } else if (w.locked > 0) {
            holder = run;                      // takes it on its first locked tick (it was free)
            if (--w.locked == 0) holder = -1;  // released after the last one
        } else {
            --w.after;
        }
        if (w.before == 0 && w.locked == 0 && w.after == 0) {
            finish[run] = t + 1;
            ++done;
        }
    }
    return finish;
}
--- hint
Keep, per job, the work left in each of its three phases, plus one number for the mutex: which job holds it, or -1. Each tick: work out who is ready and who is blocked, then the effective priorities, then pick one job and do one tick of its work.
--- hint
Only the holder's effective priority ever changes. Under `Inherit` it rises to the highest ready blocked job's priority; under `Ceiling` it rises to the ceiling from the moment it takes the mutex.
--- hint
Picking the runner: scan the jobs that can run, keep the best so far, and replace it when the new one's effective priority is higher, or equal and it is the holder.

+++ question | std::mutex on a real-time Linux box
--- ask
A Linux flight program runs its control thread under `SCHED_FIFO` at priority 80 and a logging thread under `SCHED_FIFO` at priority 10, with other real-time threads in between. The two share a buffer protected by a `std::mutex`, and the schedulability analysis includes a blocking term equal to the logger's longest critical section. Is that analysis sound?
--- choice
Yes: Linux applies priority inheritance to every mutex once threads are `SCHED_FIFO`.
--- choice
Yes, as long as the kernel is PREEMPT_RT.
--- choice correct
No: `std::mutex` offers no protocol setting and is a plain `PTHREAD_PRIO_NONE` mutex, so a middle-priority thread can preempt the logger while it holds the lock, and the control thread's wait has no bound.
--- choice
No, because `std::mutex` cannot be used by `SCHED_FIFO` threads at all.
--- why
A bounded blocking term assumes priority inheritance or a ceiling, and the C++ standard says nothing about priorities, so `std::mutex` cannot turn either on. The fix is a wrapper around a `pthread_mutex_t` created with `PTHREAD_PRIO_INHERIT` or `PTHREAD_PRIO_PROTECT`, on every mutex shared across priorities, or no mutex at all, such as a lock-free ring buffer. PREEMPT_RT makes the kernel preemptible and gives kernel-internal locks inheritance, but it does not change what an application's `std::mutex` does. The scheduling classes themselves work fine with any mutex.

+++ question | Blocked by a mutex it never locks
--- ask
In the lesson's example, navigation (priority 20) never locks the vehicle-state mutex that control (30) and telemetry (10) share, yet its response time includes a blocking term of 0.2 ms. Why?
--- choice
Because every task on the processor must include every critical section in its analysis.
--- choice correct
Because while telemetry holds the mutex with control waiting, inheritance runs telemetry at control's priority, above navigation, so navigation can be kept waiting for the rest of telemetry's critical section.

Because navigation preempts telemetry and must wait for it to finish.
--- choice

--- solution
#include <cstddef>
#include <cstdint>
#include <string>

// Reads a core number at list[i], moving i past it. -1 if there is none or it is above 63.
int read_core(const std::string& list, std::size_t& i) {
    if (i >= list.size() || list[i] < '0' || list[i] > '9') return -1;
    int n = 0;
    while (i < list.size() && list[i] >= '0' && list[i] <= '9') {
        n = n * 10 + (list[i] - '0');
        if (n > 63) return -1;
        ++i;
    }
    return n;
}

std::uint64_t parse_cpu_list(const std::string& list) {
    std::uint64_t mask = 0;
    std::size_t i = 0;
    while (true) {
        const int a = read_core(list, i);
        if (a < 0) return 0;
        int b = a;
        if (i < list.size() && list[i] == '-') {
            ++i;
            b = read_core(list, i);
            if (b < a) return 0;  // also catches b == -1
        }
        for (int c = a; c <= b; ++c) mask |= std::uint64_t{1} << c;
        if (i == list.size()) return mask;
        if (list[i] != ',') return 0;
        ++i;                      // past the comma: another item must follow
    }
}
--- hint
Read the string left to right with an index. Each item is a number, optionally followed by `-` and a second number, and then either the end of the string or a comma.
--- hint
Stop reading a number as soon as it passes 63, before it can grow large. Build the mask with `std::uint64_t{1} << c`: a plain `1 << c` is an `int`, and shifting it by 32 or more is undefined.

#include <string>
#include <vector>

struct Thread {
    std::string name;
    char policy;
    int rt_prio;
    int nice;
};

std::string runs_first(const std::vector<Thread>& ready) {
    const Thread* best = nullptr;
    auto realtime = [](const Thread& t) { return t.policy == 'F' || t.policy == 'R'; };
    for (const Thread& t : ready) {
        if (!best) { best = &t; continue; }
        if (realtime(t) != realtime(*best)) {         // real time beats time-sharing
            if (realtime(t)) best = &t;
        } else if (realtime(t)) {
            if (t.rt_prio > best->rt_prio) best = &t; // strict: ties keep the earlier one
        } else {
            if (t.nice < best->nice) best = &t;
        }
    }
    return best ? best->name : "";
}

constexpr long long kNsPerSec = 1'000'000'000LL;

Ts add_ns(Ts t, long long ns) {
    long long total = t.nsec + ns % kNsPerSec;   // stays small: no overflow
    long long sec = t.sec + ns / kNsPerSec;
    sec += total / kNsPerSec;
    total %= kNsPerSec;
    if (total < 0) {                              // % keeps the sign of the left side
        total += kNsPerSec;
        --sec;
    }
    return {sec, total};
}

long long diff_ns(Ts a, Ts b) {
    return (a.sec - b.sec) * kNsPerSec + (a.nsec - b.nsec);
}
--- hint
Split `ns` into whole seconds and leftover nanoseconds with `/` and `%`, add each to its field, then carry any overflow of `nsec` into `sec`.
--- hint
In C++, `%` of a negative number is negative. When the nanoseconds come out below 0, add one second's worth and take one from `sec`.

+++ practice | Relative sleep drifts
--- task
Compare two ways to write a periodic loop. Cycle 0 starts at time 0. `work[i]` is how long cycle `i`'s work takes, and `late[i]` how late the operating system wakes the thread at the end of cycle `i`. All times are in microseconds.

- **Relative sleep**, `work(); sleep_for(period);`: cycle `i + 1` starts at start `i` + `work[i]` + `period` + `late[i]`.
- **Absolute deadlines**, sleeping until the next point of the grid 0, `period`, 2 × `period` and so on: cycle `i + 1` is due at (`i + 1`) × `period`. It starts at the later of that grid time and the end of cycle `i`'s work (a sleep until a time already past returns at once), plus `late[i]`.

Write `std::vector<long long> start_times(const std::vector<long long>& work, const std::vector<long long>& late, long long period, bool absolute)` that returns the start times of cycles 0 to `n`, where `n` is the size of `work`: `n + 1` numbers. `late` has the same size as `work`.
--- starter
#include <vector>

std::vector<long long> start_times(const std::vector<long long>& work, const std::vector<long long>& late,
                                   long long period, bool absolute) {
    return {};
}
--- solution
#include <cstddef>
#include <vector>

std::vector<long long> start_times(const std::vector<long long>& work, const std::vector<long long>& late,
                                   long long period, bool absolute) {
    std::vector<long long> start{0};
    for (std::size_t i = 0; i < work.size(); ++i) {
        const long long done = start[i] + work[i];
        long long wake;
        if (absolute) {
            const long long due = static_cast<long long>(i + 1) * period;  // the grid never moves
            wake = (done > due ? done : due) + late[i];
        } else {
            wake = done + period + late[i];  // every delay adds up
        }
        start.push_back(wake);
    }
    return start;
}
--- hint
Build the answer one cycle at a time from the previous start. The only difference between the two loops is where the sleep ends.
--- hint
For absolute deadlines the due time depends only on the cycle number, `(i + 1) * period`, not on when earlier cycles really started. That is why lateness does not accumulate.

--- check case | Absolute: one overrun delays only the next start

+++ question | Two threads at the same priority
--- ask
Two threads on one core both run at real-time priority 50. Thread A computes in a long loop that never blocks; thread B became ready just after A started. What happens to B under `SCHED_FIFO`, and under `SCHED_RR`?
--- choice
Under both, the scheduler shares the core fairly between them.
--- choice correct
Under `SCHED_FIFO`, B waits until A blocks or yields, which here is never (apart from Linux's real-time throttling safety net). Under `SCHED_RR`, A and B take turns, each getting a time slice (100 ms on the lesson's machine).
--- choice
Under `SCHED_FIFO`, B preempts A because it became ready more recently.
--- choice
Under both, B runs first, because the kernel favors the thread that has waited.
--- why
`SCHED_FIFO` has no time slice: a thread keeps its core until it blocks, yields, or a higher priority becomes ready, and equal priorities queue in the order they became ready. `SCHED_RR` is the same with one change: equal priorities take turns by time slice. Fairness belongs to `SCHED_OTHER`. The runtime limit of 950,000 µs per second keeps a runaway real-time thread from freezing everything, but it is a seat belt, not a design: a real-time loop must sleep every cycle.

+++ question | A big buffer after mlockall
--- ask
A process without `CAP_IPC_LOCK` calls `mlockall(MCL_CURRENT | MCL_FUTURE)` at start-up, with `RLIMIT_MEMLOCK` at 8192 KiB. Later, in its main loop, it calls `malloc` for a 16 MiB buffer. What happens?

The buffer is allocated but not locked, since `MCL_FUTURE` only covers memory that existed at start-up.
--- choice correct

#include <array>
#include <optional>

struct Verdict {
    bool ok;
    long long value;
    int odd_one;
};

Verdict judge3(std::optional<long long> a, std::optional<long long> b, std::optional<long long> c) {
    const std::array<std::optional<long long>, 3> in{a, b, c};
    for (int i = 0; i < 3; ++i) {
        for (int j = i + 1; j < 3; ++j) {
            if (in[i] && in[j] && *in[i] == *in[j]) {       // a pair agrees
                const int k = 3 - i - j;                     // the third string
                const bool third_agrees = in[k] && *in[k] == *in[i];
                return {true, *in[i], third_agrees ? -1 : k};
            }
        }
    }
    return {false, 0, -1};                                   // no two agree
}

--- solution
#include <cstdint>

// A bit is 1 in the result when at least two of the inputs have it: some pair has it.
std::uint32_t vote_bits(std::uint32_t a, std::uint32_t b, std::uint32_t c) {
    return (a & b) | (a & c) | (b & c);
}

// Where a differs from b, or b differs from c, the three are not all equal.
std::uint32_t disagreement(std::uint32_t a, std::uint32_t b, std::uint32_t c) {
    return (a ^ b) | (b ^ c);
}
--- hint
At least two of three have a bit exactly when some pair both have it. `&` finds what a pair shares, `|` combines the pairs.
--- hint
`a ^ b` has a 1 wherever `a` and `b` differ. If every position had `a == b` and `b == c`, all three would agree there.

+++ practice | How many doubles apart?
--- task
When two cores disagree, the ground team wants to know by how much, measured in representable `double` values rather than in decimals: the number of units in the last place (ulps) between them. Neighbouring doubles are 1 ulp apart.

Write `long long ulp_distance(double a, double b)`:

- Map each `double`'s bits to an integer that keeps their order: take `std::bit_cast<std::int64_t>(x)`; if it is negative (the sign bit is set), replace it with `INT64_MIN - value`. Then neighbouring doubles map to neighbouring integers, and `0.0` and `-0.0` both map to 0.
- Return the absolute difference of the two mapped integers.
- If either value is a NaN, return -1.

The lesson's two sums, 8.9412200000000013 and 8.9412199999999995, are 1 ulp apart.
--- starter
long long ulp_distance(double a, double b) {
    return 0;

--- solution
#include <bit>
#include <cmath>
#include <cstdint>
#include <limits>

// Orders doubles like integers: positives keep their bits, negatives are mirrored below zero.
std::int64_t ordered(double x) {
    const std::int64_t i = std::bit_cast<std::int64_t>(x);
    return i < 0 ? std::numeric_limits<std::int64_t>::min() - i : i;
}

long long ulp_distance(double a, double b) {
    if (std::isnan(a) || std::isnan(b)) return -1;
    const std::int64_t ia = ordered(a), ib = ordered(b);
    return ia > ib ? ia - ib : ib - ia;
}
--- hint
`std::bit_cast<std::int64_t>` gives the bits as a signed integer. For negative doubles those integers run the wrong way, so mirror them with `INT64_MIN - i` (`std::numeric_limits<std::int64_t>::min()`).
--- hint
Check for NaN first with `std::isnan`. Then subtract the smaller mapped value from the larger, so the result is never negative.

--- ask

+++ problem | A downlink queue that never makes the producer wait
--- task
The control task hands telemetry records to the downlink task through a bounded queue. The control task must never wait, so its push fails when the queue is full; the downlink task sleeps until there is a record or the queue is closed at shutdown.

The condition variable is the given `FakeCV`, a stand-in for `std::condition_variable` that needs no second thread: its `wait(lock)` unlocks, runs `on_wait` (what other threads did meanwhile), and locks again, and it may return with nothing changed. Do not change it. Write:

```cpp
class DownlinkQueue {
public:
    explicit DownlinkQueue(std::size_t capacity);
    bool try_push(int rec);        // never waits
    std::optional<int> pop();      // waits for a record, or for the close
    void close();
    FakeCV& cv();
};
```

- `try_push` adds `rec` at the back and returns `true`, then calls `notify_one()` once. If the queue is full or closed, it returns `false`, changes nothing and notifies nobody.
- `pop` waits, using the predicate form, until the queue holds a record or is closed. It returns the oldest record if there is one, even after the close, so nothing queued is lost; it returns an empty `std::optional` once the queue is closed and empty.
- `close` marks the queue closed and wakes every waiting consumer with `notify_all()`. Closing a queue that is already closed does nothing, and notifies nobody.

class DownlinkQueue {
public:
    explicit DownlinkQueue(std::size_t capacity) : capacity_(capacity) {}

    bool try_push(int rec) {
        {
            std::lock_guard<std::mutex> lock(m_);
            if (closed_ || q_.size() >= capacity_) return false;  // never wait: refuse
            q_.push_back(rec);
        }
        cv_.notify_one();  // one record, one consumer
        return true;
    }

    std::optional<int> pop() {
        std::unique_lock<std::mutex> lock(m_);
        cv_.wait(lock, [this] { return !q_.empty() || closed_; });
        if (q_.empty()) return std::nullopt;  // closed and drained
        int rec = q_.front();
        q_.pop_front();
        return rec;
    }

    void close() {
        {
            std::lock_guard<std::mutex> lock(m_);
            if (closed_) return;
            closed_ = true;
        }
        cv_.notify_all();  // every waiting consumer must hear it
    }

    FakeCV& cv() { return cv_; }

private:
    std::mutex m_;
    FakeCV cv_;
    std::deque<int> q_;       // guarded by m_
    std::size_t capacity_;
    bool closed_ = false;     // guarded by m_
};

+++ problem | Always the newest value: a triple buffer
--- task
The navigation task publishes its latest state 100 times a second; the control task, at 1 kHz, only ever wants the newest one, and neither may wait for the other. A **triple buffer** does this for one producer and one consumer with three slots and one atomic:

- The producer owns one slot, the *back* slot, and writes each new value there. The consumer owns another, the *front* slot, and reads from it. The third slot is the *middle*.
- One `std::atomic<unsigned>` holds the middle slot's index (0, 1 or 2) plus a *fresh* bit, value 4, meaning "the middle slot holds a value the consumer has not taken".
- `write(v)`: store `v` in the back slot, then, with one `exchange`, put "back index | fresh" into the atomic; the index that comes out is the producer's new back slot.
- `read(out)`: if the fresh bit is not set, return `false`. Otherwise, with one `exchange`, put the front index (fresh bit clear) into the atomic; the index that comes out is the consumer's new front slot. Copy that slot into `out` and return `true`.
- Start with back = 0, middle = 1, front = 2, fresh clear.

Write `template <typename T> class TripleBuffer` with `void write(const T& v)` and `bool read(T& out)`. Use `std::memory_order_acq_rel` on both exchanges: each one both publishes a slot (release) and receives one (acquire).
--- starter

#include <atomic>

public:
    void write(const T& v) {}
    bool read(T& out) { return false; }
};
--- solution
#include <array>
#include <atomic>

template <typename T>
class TripleBuffer {
public:
    void write(const T& v) {  // producer only; never waits
        slots_[back_] = v;
        const unsigned old = middle_.exchange(back_ | kFresh, std::memory_order_acq_rel);
        back_ = old & 3u;     // the old middle becomes our next back slot
    }

    bool read(T& out) {       // consumer only; never waits
        if ((middle_.load(std::memory_order_relaxed) & kFresh) == 0) return false;
        const unsigned old = middle_.exchange(front_, std::memory_order_acq_rel);
        front_ = old & 3u;    // the freshly written slot is ours now
        out = slots_[front_];
        return true;
    }

private:
    static constexpr unsigned kFresh = 4u;
    std::array<T, 3> slots_{};
    unsigned back_ = 0;                  // producer's slot
    unsigned front_ = 2;                 // consumer's slot
    std::atomic<unsigned> middle_{1u};   // middle slot index, plus the fresh bit
};

+++ problem | Deriving a lock ranking from what the code does
--- task
A team wants to introduce ranked mutexes into existing code without breaking it, so it records the order in which each task takes its locks, as strings: `"+nav"` locks `nav`, `"-nav"` unlocks it. Whenever a task locks mutex `B` while holding mutex `A`, `A` must rank above `B`.

Unlocks may come in any order.
--- starter

    return {"?"};
}
--- solution
#include <functional>
#include <map>
#include <queue>
#include <set>
#include <string>
#include <vector>

std::vector<std::string> ranking(const std::vector<std::vector<std::string>>& tasks) {
    std::map<std::string, std::set<std::string>> below;  // held -> taken while held
    std::map<std::string, int> above;                    // how many must come before each
    for (const auto& ops : tasks) {
        std::set<std::string> held;
        for (const auto& op : ops) {
            const std::string m = op.substr(1);
            above.emplace(m, 0);
            if (op[0] == '+') {
                for (const auto& h : held)
                    if (below[h].insert(m).second) ++above[m];
                held.insert(m);
            } else {
                held.erase(m);
            }
        }
    }
    // Repeatedly take the smallest mutex with nothing left above it.
    std::priority_queue<std::string, std::vector<std::string>, std::greater<std::string>> ready;
    for (const auto& [m, n] : above)
        if (n == 0) ready.push(m);
    std::vector<std::string> order;
    while (!ready.empty()) {
        const std::string m = ready.top();
        ready.pop();
        order.push_back(m);
        for (const auto& b : below[m])
            if (--above[b] == 0) ready.push(b);
    }
    if (order.size() != above.size()) return {};         // a cycle: no ranking exists
    return order;
}

+++ problem | Races in a trace with mutexes
--- task
A race detector reads a trace of one run. Each event is:

```cpp

    int thread;
    char kind;         // 'L' lock mutex, 'U' unlock mutex, 'r' read variable, 'w' write variable

The events appear in the order they happened. #include <cstddef>
#include <set>
#include <string>
#include <vector>

struct Ev {
    int thread;
    char kind;
    std::string name;
};

std::vector<std::string> racy(const std::vector<Ev>& trace) {
    const std::size_t n = trace.size();
    std::vector<std::vector<std::size_t>> next(n);  // one-step happens-before arrows
    for (std::size_t i = 0; i < n; ++i) {
        for (std::size_t j = i + 1; j < n; ++j)     // program order
            if (trace[j].thread == trace[i].thread) { next[i].push_back(j); break; }
        if (trace[i].kind == 'U')                   // unlock -> next lock of that mutex
            for (std::size_t j = i + 1; j < n; ++j)
                if (trace[j].kind == 'L' && trace[j].name == trace[i].name) { next[i].push_back(j); break; }
    }
    // reach[i][j]: event i happens before event j.
    std::vector<std::vector<bool>> reach(n, std::vector<bool>(n, false));
    for (std::size_t i = 0; i < n; ++i) {
        std::vector<std::size_t> todo{i};
        while (!todo.empty()) {
            const std::size_t x = todo.back();
            todo.pop_back();
            for (std::size_t y : next[x])
                if (!reach[i][y]) { reach[i][y] = true; todo.push_back(y); }
        }
    }
    std::set<std::string> found;
    auto access = [](char k) { return k == 'r' || k == 'w'; };
    for (std::size_t i = 0; i < n; ++i)
        for (std::size_t j = i + 1; j < n; ++j) {
            const Ev& a = trace[i];
            const Ev& b = trace[j];
            if (access(a.kind) && access(b.kind) && a.name == b.name && a.thread != b.thread &&
                (a.kind == 'w' || b.kind == 'w') && !reach[i][j] && !reach[j][i])
                found.insert(a.name);
        }
    return {found.begin(), found.end()};
}

+++ problem | How much time can the task grow?
--- task
Tasks are `struct Task { long long c; long long t; long long b; };`: worst-case execution time, period (the deadline) and blocking time, in microseconds, with rate-monotonic priorities (shorter period first; equal periods, earlier task first). A task set is schedulable if every task's response time, from R = c + b + the sum over higher-priority tasks j of ceiling(R / t_j) × c_j, is at most its period.

Write `long long max_wcet(const std::vector<Task>& tasks, int k)` that returns the largest execution time, from 1 up to `tasks[k].t`, that task `k` could have with the whole set still schedulable, everything else unchanged. Growing task `k` also delays the tasks below it, so check them all. Return 0 if even 1 µs does not fit. Work in whole numbers.
--- starter

struct Task { long long c; long long t; long long b; };

    return -1;
}
--- solution
#include <cstddef>
#include <vector>

struct Task { long long c; long long t; long long b; };

bool higher(const std::vector<Task>& ts, std::size_t j, std::size_t i) {
    return ts[j].t != ts[i].t ? ts[j].t < ts[i].t : j < i;
}

bool schedulable(const std::vector<Task>& ts) {
    for (std::size_t i = 0; i < ts.size(); ++i) {
        long long r = ts[i].c + ts[i].b;
        for (std::size_t j = 0; j < ts.size(); ++j)
            if (higher(ts, j, i)) r += ts[j].c;
        while (true) {
            if (r > ts[i].t) return false;
            long long next = ts[i].c + ts[i].b;
            for (std::size_t j = 0; j < ts.size(); ++j)
                if (higher(ts, j, i)) next += (r + ts[j].t - 1) / ts[j].t * ts[j].c;
            if (next == r) break;
            r = next;
        }
    }
    return true;
}

// Schedulability only gets worse as one task's c grows, so a binary search finds the edge.
long long max_wcet(const std::vector<Task>& tasks, int k) {
    std::vector<Task> ts = tasks;
    long long lo = 0, hi = ts[k].t;          // lo always fits (0 means "nothing fits yet")
    while (lo < hi) {
        const long long mid = lo + (hi - lo + 1) / 2;
        ts[k].c = mid;
        if (schedulable(ts)) lo = mid;
        else hi = mid - 1;
    }
    return lo;
}

+++ problem | A sum that is the same on every core
--- task
A filter sums a long array of sensor values by splitting it into chunks, one per worker, as a thread pool would. Here each chunk's sum is a `std::future<double>` from `std::async` with the deferred policy, so the checks run on one thread. Both cores of a flight string run this code, so the result must be bit-identical every time, whatever order work finishes in.

Write `double chunked_sum(const std::vector<double>& x, unsigned chunks)`:

- The number of chunks is `chunks`, but 1 if `chunks` is 0, and never more than the number of values. For an empty array, return 0.0.
- The chunks are contiguous and in order; their sizes differ by at most one, the bigger ones first.
- Each chunk is summed from its first value to its last, starting from 0.0, inside its own deferred future.
- The chunk sums are then added in chunk order, starting from 0.0: `((s0 + s1) + s2) + ...`.

The lambda in each future must own or safely refer to what it reads when it finally runs.
--- starter
#include <vector>

double chunked_sum(const std::vector<double>& x, unsigned chunks) {
    return -1.0;
}
--- solution
#include <cstddef>
#include <future>
#include <vector>

double chunked_sum(const std::vector<double>& x, unsigned chunks) {
    const std::size_t n = x.size();
    if (n == 0) return 0.0;
    std::size_t k = chunks == 0 ? 1 : chunks;
    if (k > n) k = n;
    const std::size_t base = n / k, extra = n % k;

    std::vector<std::future<double>> parts;
    std::size_t first = 0;
    for (std::size_t c = 0; c < k; ++c) {
        const std::size_t last = first + base + (c < extra ? 1 : 0);
        // x outlives every future: they all run inside this function, below.
        parts.push_back(std::async(std::launch::deferred, [&x, first, last] {
            double s = 0.0;
            for (std::size_t i = first; i < last; ++i) s += x[i];
            return s;
        }));
        first = last;
    }
    double total = 0.0;
    for (auto& p : parts) total += p.get();  // fixed order, never "as they finish"
    return total;
}

--- solution
#include <array>
#include <atomic>
#include <cstddef>
#include <cstdint>
#include <vector>

struct Record { std::uint32_t seq; float value; };

class Tap {
public:
    explicit Tap(std::uint32_t start = 0) : head_(start), tail_(start) {}

    bool publish(const Record& r) {  // producer only: wait-free
        const std::uint32_t h = head_.load(std::memory_order_relaxed);
        if (h - tail_.load(std::memory_order_acquire) == kN) {
            dropped_.fetch_add(1, std::memory_order_relaxed);  // drop and count
            return false;
        }
        buf_[h & (kN - 1)] = r;
        head_.store(h + 1, std::memory_order_release);
        return true;
    }

    std::uint32_t drain(std::vector<Record>& out) {  // consumer only
        const std::uint32_t t = tail_.load(std::memory_order_relaxed);
        const std::uint32_t h = head_.load(std::memory_order_acquire);
        for (std::uint32_t c = t; c != h; ++c) out.push_back(buf_[c & (kN - 1)]);
        tail_.store(h, std::memory_order_release);
        return h - t;
    }

    std::uint32_t dropped() const { return dropped_.load(std::memory_order_relaxed); }

private:
    static constexpr std::uint32_t kN = 8;
    std::array<Record, kN> buf_{};
    std::atomic<std::uint32_t> head_;
    std::atomic<std::uint32_t> tail_;
    std::atomic<std::uint32_t> dropped_{0};
};

std::uint32_t lost(const std::vector<std::uint32_t>& seqs) {
    std::uint32_t missing = 0;
    for (std::size_t i = 1; i < seqs.size(); ++i)
        missing += seqs[i] - seqs[i - 1] - 1u;  // unsigned: correct across the wrap
    return missing;
}

--- solution
#include <cstdint>
#include <map>
#include <string>
#include <vector>

struct Field { std::string name; std::uint32_t size; int writer; };
struct Layout { std::map<std::string, std::uint32_t> offset; std::uint32_t size; };

std::uint32_t round_up(std::uint32_t x, std::uint32_t a) { return (x + a - 1) / a * a; }

Layout plan(const std::vector<Field>& fields, std::uint32_t line) {
    std::vector<int> writers;                     // in order of first appearance
    for (const Field& f : fields) {
        bool seen = false;
        for (int w : writers) if (w == f.writer) seen = true;
        if (!seen) writers.push_back(f.writer);
    }
    Layout out{{}, 0};
    std::uint32_t at = 0;
    for (int w : writers) {
        at = round_up(at, line);                  // each writer's group on a fresh line
        for (const Field& f : fields) {
            if (f.writer != w) continue;
            at = round_up(at, f.size);            // natural alignment inside the group
            out.offset[f.name] = at;
            at += f.size;
        }
    }
    out.size = round_up(at, line);
    return out;
}

--- task

- `max_ns` is the largest lateness; `p99_ns` is the lateness at index `(n - 1) * 99 / 100` of the sorted latenesses, in whole numbers; `over_half` counts the wake-ups more than half a period late.

--- starter

--- solution
#include <algorithm>
#include <cstddef>
#include <vector>

struct Ts { long long sec; long long nsec; };
struct Late { long long max_ns; long long p99_ns; int over_half; };

constexpr long long kNsPerSec = 1'000'000'000LL;

long long to_ns(const Ts& t) { return t.sec * kNsPerSec + t.nsec; }

Late lateness(Ts start, long long period_ns, const std::vector<Ts>& woke) {
    if (woke.empty()) return {0, 0, 0};
    std::vector<long long> late;
    late.reserve(woke.size());
    const long long t0 = to_ns(start);
    for (std::size_t i = 0; i < woke.size(); ++i) {
        const long long due = t0 + static_cast<long long>(i + 1) * period_ns;  // the fixed grid
        late.push_back(to_ns(woke[i]) - due);
    }
    int over = 0;
    for (long long l : late)
        if (l > period_ns / 2) ++over;
    std::sort(late.begin(), late.end());
    return {late.back(), late[(late.size() - 1) * 99 / 100], over};
}

--- solution
#include <array>
#include <cstddef>
#include <cstdint>
#include <optional>
#include <vector>

struct Upset { int frame; int string; int core; int bit; };

std::vector<std::optional<long long>> fly(const std::vector<long long>& inputs, const std::vector<Upset>& upsets) {
    std::array<std::array<long long, 2>, 3> x{};  // each core's own copy of the state
    std::array<bool, 3> silent{};
    std::vector<std::optional<long long>> judged;
    for (std::size_t f = 0; f < inputs.size(); ++f) {
        for (const Upset& u : upsets)
            if (u.frame == static_cast<int>(f))
                x[u.string][u.core] ^= static_cast<long long>(std::uint64_t{1} << u.bit);

        std::array<std::optional<long long>, 3> cmd;
        for (int s = 0; s < 3; ++s) {
            long long c[2];
            for (int k = 0; k < 2; ++k) {             // identical code on both cores
                x[s][k] += inputs[f];
                c[k] = 2 * x[s][k] + inputs[f];
            }
            if (c[0] != c[1]) silent[s] = true;       // the pair disagrees: fail silent
            if (!silent[s]) cmd[s] = c[0];
        }

        std::optional<long long> out;
        const int pairs[3][2] = {{0, 1}, {0, 2}, {1, 2}};
        for (const auto& p : pairs)
            if (!out && cmd[p[0]] && cmd[p[1]] && *cmd[p[0]] == *cmd[p[1]]) out = cmd[p[0]];
        judged.push_back(out);
    }
    return judged;
}

--- why
A promise destroyed without a result stores a `broken_promise` error, so no waiter hangs: `get()` reports the error. Normally that is a `std::future_error` the waiter can catch; in a build without exceptions the library aborts at the throw. Either way the real bug is in the producer: every path must set a value or an error.

+++ question | Masking a ring of ten slots
--- ask
A ring buffer has 10 slots, and its code computes the slot for counter value `i` as `i & (N - 1)`. Which slot does the counter value 12 use? Type the number.
--- answer
8
--- why
`N - 1` is 9, `0b1001`, and 12 is `0b1100`: the bits both have is `0b1000`, which is 8. The right slot, 12 modulo 10, is 2. The mask trick only equals the remainder when `N` is a power of two, because only then is `N - 1` a solid block of ones; with 10 slots the ring silently writes into the wrong places. A `static_assert` that `N` is a power of two turns this into a compile error.

+++ question | The padding that made it slower
--- ask
A ring buffer whose `push` reads `tail_` and whose `pop` reads `head_` on every call is changed to put `alignas(64)` on both indices. The benchmark gets slower. Why?
--- choice
`alignas(64)` makes the atomics lock-based.
--- choice correct
Each side still reads the other side's index on every operation, so a line must cross between the cores every time anyway; padded, two lines cross instead of one.
--- choice
The ring now holds fewer items, so both sides wait more.
--- choice
Padding only helps on ARM.
--- why
Padding removes false sharing, but here most of the sharing is true sharing: every push needs the consumer's index and every pop the producer's. Packed, the two indices travel together as one line; padded, both lines travel. Padding pays once each side keeps a private copy of the other's index and rereads the real one only when its copy says "full" or "empty", so that most operations touch only their own line. Advice about caches is a hypothesis until it is measured.

+++ question | One response time, by hand
--- ask
Three independent periodic tasks, deadlines equal to periods, are scheduled rate-monotonically: A with C = 1 and T = 4, B with C = 2 and T = 6, and C with C = 3 and T = 12. What is task C's worst-case response time? Type the number.
--- answer
10
--- why
Start with R = 3 + 1 + 2 = 6. A is released ceiling(6/4) = 2 times and B ceiling(6/6) = 1 time: R = 3 + 2 + 2 = 7. Then ceiling(7/4) = 2 and ceiling(7/6) = 2: R = 3 + 2 + 4 = 9. Then ceiling(9/4) = 3 and ceiling(9/6) = 2: R = 3 + 3 + 4 = 10. Then ceiling(10/4) = 3 and ceiling(10/6) = 2: R = 10 again, so it has settled, and 10 is within the deadline of 12. The utilization, about 0.83, is above the three-task bound of 0.780, yet every deadline is met: the bound is sufficient, not necessary.

+++ question | Inheritance or ceiling?
--- ask
Which statement correctly compares priority inheritance with the priority ceiling protocol?
--- choice
Inheritance raises the lock holder as soon as it locks; the ceiling protocol raises it only when someone waits.
--- choice correct
The ceiling protocol raises the holder to the mutex's ceiling as soon as it locks, so a task is blocked at most once per activation and some deadlocks become impossible, at the price of knowing every mutex's users in advance; inheritance raises the holder only while a higher-priority task waits.
--- choice
Both remove all blocking, so the blocking term in the response time becomes zero.
--- choice
Only inheritance works on Linux; the ceiling protocol exists only in VxWorks.
--- why
Inheritance lends the holder the highest waiter's priority for as long as someone waits. The ceiling protocol, `PTHREAD_PRIO_PROTECT` on Linux, raises the holder to a fixed ceiling at once, which is why the lesson's third run showed the high task waiting to be scheduled rather than inside `lock()`: the delay was the same, it just moved. Neither removes blocking; both bound it by a lower task's critical section, which is the blocking term in the analysis.

+++ question | The attribute that was ignored
--- ask
A thread is created with a `pthread_attr_t` on which the code set `SCHED_FIFO` and priority 80, checking every return value. But `chrt -p` shows the new thread running as `SCHED_OTHER`. What was missing?
--- choice
`mlockall`, without which the kernel refuses real-time policies.
--- choice correct
`pthread_attr_setinheritsched(&attr, PTHREAD_EXPLICIT_SCHED)`: without it the new thread inherits its creator's policy, and the attribute's policy is ignored with no error.
--- choice
Pinning the thread to one core with `pthread_setaffinity_np`.
--- choice
A nice value of -20 on the creating thread.
--- why
By default a new thread inherits its creator's scheduling, and the policy and priority stored in the attribute are simply not used, so every call returns success. Setting explicit scheduling makes the attribute count, and then a missing permission shows up as a real error (`EPERM`) that the code can check. Memory locking and pinning are separate parts of the real-time setup, and nice only matters within `SCHED_OTHER`.
