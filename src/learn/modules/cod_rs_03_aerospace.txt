+++ question | What a heap-free library may use
--- ask
A `#![no_std]` filter library will be linked into firmware that has no allocator at all. Pick every item the library can use and still let the firmware build for `thumbv7em-none-eabihf`.
--- choice correct
A `static` `core::sync::atomic::AtomicU32` counting samples
--- choice correct
A `[f32; 8]` window summed with `.iter().fold(0.0, |a, x| a + x)`
--- choice
`alloc::string::String`, after `extern crate alloc;`
--- choice
`std::collections::HashMap` to look up calibration values
--- choice
`x.sqrt()` on an `f32` sample
--- choice correct
`libm::sqrtf(x)` from the `libm` crate
--- why
Atomics, arrays, iterators and closures are all part of the language, so they live in `core` and need neither a heap nor an operating system. `String` lives in `alloc`: the library compiles, but the firmware fails at its final link with "no global memory allocator found". `HashMap` is in `std`, which a `no_std` crate cannot name at all. Square root on floats comes from the operating system's maths library, so on this toolchain `f32` has no `sqrt` method in `core` (error E0599). `libm` is a pure-Rust maths library, so it works on a bare chip.

+++ question | How much RAM, from four bytes
--- ask
You dump the start of flash on an unknown STM32 board. Its RAM starts at `0x20000000`, and its start-up code puts the stack at the very top of RAM. The first word of `.vector_table` prints as:

```text
 8000000 00800120 ...
```

How many KiB of RAM does the chip have? Type the number.
--- answer
96
96 KiB
96KiB
96 KB
96KB
96 k
96K
--- why
Cortex-M is little-endian, so the bytes `00 80 01 20` hold the word `0x20018000`: reverse them to read it. Word 0 is the initial stack pointer, and the stack starts at the top of RAM because it grows downward. So RAM ends at `0x20018000`. Subtract the start: `0x20018000 - 0x20000000 = 0x18000`, which is $98\,304$ bytes, and $98\,304 / 1024 = 96$ KiB. Reading the digits in the order printed would give `0x00800120`, an address with no RAM behind it.

+++ question | Counting the sections
--- ask
`size -A` on a release build lists these sections:

```text
section           size
.vector_table      408
.text             6212
.rodata            344
.data               12
.bss              1540
```

How many bytes of flash does the program use, and how many bytes of RAM do its statics use? Type the two numbers, flash first, separated by a space.
--- answer
6976 1552
6976, 1552
6976,1552
--- why
Flash holds the vector table, the code, the constants and the starting values of `.data`: $408 + 6212 + 344 + 12 = 6976$ bytes. RAM holds `.data` and `.bss`: $12 + 1540 = 1552$ bytes. `.data` is counted twice, once in each: its starting values must survive power-off, so they sit in flash, and `Reset` copies them into RAM. `.bss` costs no flash, because the start-up code only fills it with zeros. The two common slips are leaving `.data` out of flash (6964) and putting `.bss` in flash (8516).

+++ question | Which entry functions compile
--- ask
Each choice is a whole function marked `#[entry]` from cortex-m-rt, in a `#![no_std]` `#![no_main]` program with a panic handler. `init` returns `()` and `done` returns `bool`. Pick every one that compiles.
--- choice correct
`fn main() -> ! { loop { cortex_m::asm::nop(); } }`
--- choice correct
`fn main() -> ! { init(); panic!("init finished") }`
--- choice
`fn main() { loop { cortex_m::asm::nop(); } }`
--- choice
`fn main() -> ! { loop { if done() { break; } } }`
--- why
`#[entry]` insists on the signature `fn() -> !`, so a `main` with no return type is rejected by the attribute itself, even though its loop never ends. A `loop` with no `break` has type `!`, the never type, so it satisfies the signature. `panic!` also has type `!`: it never returns, so ending the body with it type-checks, even though it is an odd way to end a program. A `loop` that contains a `break` can finish, so its type is `()`, and the compiler reports mismatched types: expected `!`, found `()`.

+++ question | A new board that dies before main
--- ask
A team moves its firmware to a smaller part: 256 KiB of flash at `0x08000000` and 64 KiB of RAM at `0x20000000`. The project keeps its old `memory.x`:

```text
MEMORY
{
  FLASH : ORIGIN = 0x08000000, LENGTH = 256K
  RAM   : ORIGIN = 0x20000000, LENGTH = 128K
}
```

The build succeeds, but a breakpoint on the first line of `main` is never reached. What is wrong?
--- choice correct
The RAM `LENGTH` should be `64K`. The linker puts the initial stack pointer at `0x20020000`, 64 KiB past the end of real RAM, so the first stack push in `Reset` faults before `main` is ever called.
--- choice
The FLASH line is wrong: `ORIGIN` must be the end of flash, because the vector table is placed at the top.
--- choice
Nothing in `memory.x` is wrong; the panic handler is looping, and a panic in `main` stops the breakpoint.
--- choice
The RAM line is fine, since a larger `LENGTH` only leaves unused space; the problem must be a missing `#![no_main]`.
--- why
The linker believes `memory.x`, so it computes the top of RAM as $\mathtt{0x20000000} + 128 \times 1024 = \mathtt{0x20020000}$ and writes that into word 0 of the vector table. On this chip RAM really ends at `0x20010000`. The very first thing that uses the stack writes to an address with no memory behind it, the chip faults, and it never reaches your code. A breakpoint in a panic path would not help either, because nothing in `main` ever ran. Always take `ORIGIN` and `LENGTH` from the datasheet of the exact part on the board.

+++ question | The wheel after a panic
--- ask
A reaction-wheel controller uses `panic-halt`. Its wheel driver switches the motor off when it is dropped:

```rust
impl Drop for Wheel {
    fn drop(&mut self) {
        self.set_duty(0); // motor off
    }
}

#[entry]
fn main() -> ! {
    let mut wheel = Wheel::new();
    loop {
        let cmd = next_command(); // an index out of bounds in here panics
        wheel.set_duty(cmd);
    }
}
```

The wheel is spinning at duty 70 when `next_command` panics. What happens to the wheel?
--- choice
`drop` runs while the panic unwinds out of `main`, so the motor is switched off.
--- choice
The chip resets at once, and the motor stops because the reset clears the timer.
--- choice correct
It keeps spinning at duty 70. On Cortex-M the panic strategy is abort, so nothing unwinds and `drop` never runs; the processor just loops in the panic handler.
--- choice
The panic handler returns to `main`, which carries on with the next command.
--- why
With `std` on a laptop a panic unwinds the stack and runs every `Drop` on the way. On Cortex-M targets the panic strategy is abort: control jumps into the `#[panic_handler]`, which must never return (its type is `!`), and no destructor runs. `panic-halt` just loops, so the timer that drives the motor keeps its last setting. Nothing resets unless something makes it, such as a watchdog. That is why a flight panic handler must make the hardware safe itself, or let a watchdog reset the chip into a safe mode.

+++ question | The LED on PC13
--- ask
On the STM32F411, the GPIOC base address is `0x40020800`, and the output data register `ODR` sits at offset `0x14` in every GPIO port. A board's LED is on pin PC13. Which address and mask toggle it, as in `*odr ^= mask`?
--- choice correct
Address `0x40020814`, mask `0x2000`
--- choice
Address `0x40020814`, mask `0x0D`
--- choice
Address `0x40020800`, mask `0x2000`
--- choice
Address `0x40020814`, mask `0x04000000`
--- why
The register's address is the port's base plus the offset: $\mathtt{0x40020800} + \mathtt{0x14} = \mathtt{0x40020814}$. Pin 13 is bit 13 of `ODR`, so its mask is $2^{13} = 8192$, which is `0x2000`. `0x0D` is the number 13 itself, not a mask with bit 13 set. `0x40020800` is the port's base, where `MODER` lives. `0x04000000` is $1$ shifted left 26 places: the `01` output pattern for pin 13 in `MODER`, whose two bits are 26 and 27. It belongs in a different register.

+++ question | Reading a mode register
--- ask
A debugger shows `GPIOA_MODER = 0x00000C51`. Each pin has two bits, starting at bit $2n$, and the patterns are `00` input, `01` output, `10` alternate function, `11` analog. Which pins of port A are general-purpose outputs? Type their numbers in increasing order, separated by spaces.
--- answer
0 2 3
0, 2, 3
0,2,3
0, 2 and 3
0 2 and 3
PA0 PA2 PA3
PA0, PA2, PA3
PA0, PA2 and PA3
pins 0 2 3
pins 0, 2, 3
pins 0, 2 and 3
--- why
Write the low bits out: `0xC51` is binary `1100 0101 0001`. Take them in pairs from the right. Bits 1 and 0 are `01`: pin 0 is an output. Bits 3 and 2 are `00`: pin 1 is an input. Bits 5 and 4 are `01`: pin 2 is an output. Bits 7 and 6 are `01`: pin 3 is an output. Bits 9 and 8 are `00`: pin 4 is an input. Bits 11 and 10 are `11`: pin 5 is analog, not an output. Every higher pair is `00`. So the outputs are pins 0, 2 and 3.

+++ question | A helper that takes the peripherals
--- ask
A student adds a helper to a PAC program:

```rust
fn led_on() {
    let dp = stm32f411::Peripherals::take().unwrap();
    dp.GPIOA.odr().modify(|_, w| w.odr5().set_bit());
}

#[entry]
fn main() -> ! {
    let dp = stm32f411::Peripherals::take().unwrap();
    dp.RCC.ahb1enr().modify(|_, w| w.gpioaen().set_bit());
    dp.GPIOA.moder().modify(|_, w| w.moder5().output());
    led_on();
    loop {}
}
```

It builds with `panic-halt`. What happens on the board?
--- choice
The LED lights: each call to `take()` returns its own handle to the same registers.
--- choice
It does not compile: `dp` is moved into `main`, so `led_on` cannot name the peripherals.
--- choice correct
The LED stays off. The second `take()` returns `None`, `.unwrap()` panics, and `panic-halt` stops the chip in a loop.
--- choice
The LED lights, but the two handles race, so it flickers.
--- why
`Peripherals::take()` is the singleton pattern: it hands out the chip's peripherals once, returning `Some` the first time and `None` after that, so two parts of the program can never both believe they own GPIOA. The code compiles, because the check happens when it runs. The panic in `led_on` goes to `panic-halt`, which loops forever, so the write to `ODR` never happens. The fix is ownership: pass `&dp.GPIOA` (or the pin) into the helper instead of taking the peripherals again.

+++ question | One pair of bytes, three readings
--- ask
An MPU-6050 at its $\pm 2\,g$ range (16384 counts per $g$) sends `80 00` for the x axis, high byte first. What does this print, line by line?

```rust
let raw = [0x80u8, 0x00];
println!("{}", i16::from_be_bytes(raw) as f32 / 16384.0);
println!("{}", u16::from_be_bytes(raw) as f32 / 16384.0);
println!("{}", i16::from_le_bytes(raw) as f32 / 16384.0);
```
--- choice correct
`-2`, then `2`, then `0.0078125`
--- choice
`-2`, then `-2`, then `-2`
--- choice
`2`, then `2`, then `0.0078125`
--- choice
`-2`, then `2`, then `-2`
--- why
Read high byte first, `80 00` is `0x8000`. As a signed 16-bit number that is the most negative value, $32768 - 65536 = -32768$, and $-32768 / 16384 = -2$: the right reading, the bottom of the range. Taken unsigned, the same bits are $+32768$, giving $+2$: the sign is lost. Taken low byte first, the bytes mean `0x0080` $= 128$, and $128 / 16384 = 0.0078125$. Both wrong readings are the classic first-day bugs with a new sensor, and only `i16::from_be_bytes` gets both halves right.

+++ question | A driver that names the wrong error
--- ask
A BMP280 pressure sensor answers at I2C address `0x76`, and its chip-id register is `0xD0`. This generic driver does not compile:

```rust
use embedded_hal::i2c::I2c;

pub struct Bmp280<I> {
    i2c: I,
}

impl<I: I2c> Bmp280<I> {
    pub fn chip_id(&mut self) -> Result<u8, stm32f4xx_hal::i2c::Error> {
        let mut b = [0u8; 1];
        self.i2c.write_read(0x76, &[0xD0], &mut b)?;
        Ok(b[0])
    }
}
```

What is wrong, and what is the fix?
--- choice correct
The return type names an STM32 error, but the bus is any `I`, whose error is `I::Error`; `?` cannot turn one into the other. Return `Result<u8, I::Error>`.
--- choice
`0xD0` is an 8-bit bus address; pass the 7-bit address `0x68` instead.
--- choice
`write_read` needs a mutable slice for the register, `&mut [0xD0]`.
--- choice
Nothing is wrong with the code; the crate is missing the `critical-section-single-core` feature.
--- why
Inside `impl<I: I2c>`, the only error the compiler knows about is `I::Error`, the one each bus names through `ErrorType`. `?` would need a conversion from any `I::Error` into `stm32f4xx_hal::i2c::Error`, and no such conversion exists, so the build fails (E0277). Returning `I::Error` keeps the driver chip-free: an STM32 bus, a Nordic bus and a fake desk bus all work. Here `0xD0` is a register number sent as data, not an address; `0x76` is already the 7-bit address embedded-hal wants.

+++ question | An ADC you cannot read too early
--- ask
You are writing a HAL for an ADC that returns garbage until it has been calibrated once. You want "read before calibrate" to be a compile error, not a bug found on the bench. Which design does that?
--- choice
One `Adc` type with a `calibrated: bool` field; `read` returns `Err` when the flag is false.
--- choice correct
Two types, `Adc<Raw>` and `Adc<Calibrated>`. `calibrate(self)` consumes the raw one and returns the calibrated one, and only `Adc<Calibrated>` has a `read` method.
--- choice
One `Adc` type with `calibrate(&mut self)` and `read(&mut self)`, and a doc comment that says to call `calibrate` first.
--- choice
Mark `read` as `unsafe fn`, with a `# Safety` section that says calibration must come first.
--- why
This is typestate, the same trick as a pin that has no `set_high` until `into_push_pull_output()` turns it into an output. Because `calibrate` takes `self` by value, the raw value is moved and cannot be used again, so there is never an uncalibrated handle left to read from. The flag version catches the mistake only when it runs. The doc comment and the `unsafe` version both leave the rule to a human, and `unsafe` is meant for memory-safety promises, not for ordering rules the type system can enforce.

+++ question | Who may interrupt a lock
--- ask
An RTIC app has four tasks. A (priority 1) and B (priority 3) both use the shared resource `r`. C (priority 4) and D (priority 6) do not use `r`. E (priority 2) does not use `r` either. While A is inside `cx.shared.r.lock(|r| ...)`, which tasks can start if their interrupt fires? Pick every one.
--- choice
B
--- choice correct
C
--- choice correct
D
--- choice
E
--- why
The ceiling of `r` is the highest priority of any task that uses it: 3, from B. While A holds the lock, RTIC raises the running priority to 3, so nothing at 3 or below can start. B is kept out, which is the point, since it would find `r` half-updated. E is at 2 and is held off too, even though it never touches `r`: that is a small cost of the scheme. C and D are above the ceiling. They never ask for `r`, so letting them run cannot hurt it, and they preempt at once.

+++ question | What Hubris does
--- ask
Pick every statement that is true of Hubris, the operating system from Oxide Computer Company.
--- choice correct
The list of tasks, their memory and their priorities is fixed in a configuration file when the system is built.
--- choice correct
Device drivers run as ordinary unprivileged tasks, each in its own MPU-protected memory.
--- choice
Drivers are kernel capsules, kept apart because capsule code may not use `unsafe`.
--- choice
New applications, written in C or Rust, can be loaded and replaced separately from the kernel.
--- choice correct
Tasks talk by synchronous messages: the sender waits until the receiver replies.
--- choice correct
When a task crashes, the kernel stops it, and a supervisor task can restart it while the others keep running.
--- why
Hubris is static and all-Rust: tasks are decided at build time, the kernel never allocates, drivers are separate unprivileged programs behind the MPU, messages are synchronous (a phone call, not a letter), and a crashed task can be restarted. The two wrong statements describe Tock. Tock puts drivers in the kernel as capsules isolated by the type system, and its separately loadable processes, in C or Rust, are what the MPU walls off.

+++ question | A checksum that makes the IMU late
--- ask
One Embassy executor runs two tasks. `housekeeping` wakes every 100 ms and computes a checksum over a log block in one plain loop that takes 6 ms and has no `.await` in it. `imu_read` wakes every 2 ms and awaits an I2C read. Sometimes `imu_read` runs 6 ms late. Pick every change that bounds that lateness.
--- choice correct
Split the checksum into chunks of a few hundred bytes, with an `.await` between chunks, so the executor can switch tasks.
--- choice correct
Run `imu_read` on an `InterruptExecutor` at a higher interrupt priority, so it can preempt the ordinary executor.
--- choice
Turn the checksum loop into an `async fn` and call it with `.await`, leaving the loop itself unchanged.
--- choice
Give `imu_read` more task slots in its `#[embassy_executor::task]` attribute.
--- choice
Replace the `Timer` in `housekeeping` with a `Ticker`.
--- why
The executor is cooperative: it can switch tasks only at an `.await`. A 6 ms stretch with none holds up every other task on that executor for 6 ms, whatever the other task's period. Adding `.await` points between chunks gives the executor places to switch, so the worst delay shrinks to one chunk. An `InterruptExecutor` runs inside an interrupt, so the NVIC hardware can preempt the busy task. Wrapping the loop in an `async fn` changes nothing if the loop still never awaits. Task slots decide how many copies of a task can exist, not when it runs, and `Ticker` only changes how the wake-ups are timed.

+++ question | One counter in two local lists
--- ask
A student wants both RTIC tasks to count interrupts in the same variable, so both list it as a local resource:

```rust
#[local]
struct Local {
    ticks: u32,
}

#[task(binds = TIM2, priority = 3, local = [ticks])]
fn control_loop(cx: control_loop::Context) {
    *cx.local.ticks += 1;
}

#[task(binds = USART1, priority = 1, local = [ticks])]
fn radio_rx(cx: radio_rx::Context) {
    *cx.local.ticks += 1;
}
```

What happens?
--- choice
It compiles, and the count is sometimes wrong, because the two tasks race on `ticks`.
--- choice
It compiles, and RTIC quietly adds a lock around each access.
--- choice correct
It does not compile: a local resource belongs to exactly one task. Data used by two tasks must go in `#[shared]` and be reached through `lock`.
--- choice
It compiles, and each task gets its own copy of `ticks`, starting at the value from `init`.
--- why
RTIC hands out `&mut` access to a local resource with no locking at all, which is only safe because exactly one task can ever touch it. A second task naming the same local would break that promise, so RTIC rejects the program when it compiles. Move `ticks` to `#[shared]`: the priority-1 task then locks it, raising the running priority to 3 for the length of the closure, and the data race becomes impossible. RTIC never inserts locks you did not write, and it never copies resources behind your back.

+++ question | The second blinker
--- ask
This Embassy program should blink a green and a red LED at different rates:

```rust
#[embassy_executor::task]
async fn blink(mut led: Output<'static>, period_ms: u64) {
    loop {
        led.toggle();
        Timer::after_millis(period_ms).await;
    }
}

#[embassy_executor::main]
async fn main(spawner: Spawner) {
    let p = embassy_stm32::init(Default::default());
    let green = Output::new(p.PA5, Level::Low, Speed::Low);
    let red = Output::new(p.PB14, Level::Low, Speed::Low);
    spawner.spawn(blink(green, 500).unwrap());
    spawner.spawn(blink(red, 200).unwrap());
    loop {
        Timer::after_millis(1000).await;
    }
}
```

The board has `panic-halt`. The green LED toggles once and freezes, and the red one never lights. Why?
--- choice correct
A task has one slot by default, so the second `blink(red, 200)` returns an error and `.unwrap()` panics. Give the task two slots, for example `#[embassy_executor::task(pool_size = 2)]`.
--- choice
Two tasks cannot both call `Timer::after_millis`; the second timer cancels the first.
--- choice
`Output<'static>` cannot be passed to a task; the pins must be globals.
--- choice
The executor only runs tasks after `main` returns, and this `main` never returns.
--- why
Embassy stores every task in memory reserved when the program is built, so each task function has a fixed number of slots, one unless you ask for more. Calling `blink(...)` fills a slot and returns a token, or an error if none is free. The first call used the only slot. The second got an error, `unwrap` panicked, and `panic-halt` froze the chip before the executor ever ran the green task past its first toggle. Many tasks can wait on timers at once, and `main` is itself a task that the executor switches away from at each `.await`.

+++ question | Proving the logger's deadline
--- ask
An RTIC design has two tasks. The attitude loop runs at the higher priority with period $T_1 = 2\,\mathrm{ms}$ and worst case $C_1 = 0.5\,\mathrm{ms}$. The logger runs below it with period $T_2 = 25\,\mathrm{ms}$ and worst case $C_2 = 6\,\mathrm{ms}$. Using the iteration $R \leftarrow C_2 + \lceil R / T_1 \rceil\, C_1$, starting from $R = C_2$, what is the logger's worst response time $R_2$ in milliseconds?
--- answer
8
8 ms
8ms
8.0
8.0 ms
--- why
Start at $R = 6$. Then $6 + \lceil 6/2 \rceil \times 0.5 = 6 + 3 \times 0.5 = 7.5$. Next $6 + \lceil 7.5/2 \rceil \times 0.5 = 6 + 4 \times 0.5 = 8$. Next $6 + \lceil 8/2 \rceil \times 0.5 = 6 + 4 \times 0.5 = 8$, the same, so it has settled: $R_2 = 8\,\mathrm{ms}$, inside the 25 ms period. Each round counts how many attitude-loop runs can start while the logger is still working; the ceiling rounds up because a run that starts even slightly inside the window costs its full 0.5 ms. The logger is the lowest priority here, so it has no blocking term.

+++ question | Ten bytes into eight slots
--- ask
What does this print? Type the output exactly.

```rust
use heapless::spsc::Queue;

fn main() {
    let mut q: Queue<u8, 8> = Queue::new();
    let mut dropped = 0;
    for b in 1..=10u8 {
        if q.enqueue(b).is_err() {
            dropped += 1;
        }
    }
    q.dequeue();
    q.dequeue();
    let _ = q.enqueue(42);
    println!("{} {} {:?}", q.len(), dropped, q.peek());
}
```
--- answer
6 3 Some(3)
--- why
A `Queue<T, 8>` holds at most 7 items, because one slot stays empty so full and empty look different. So bytes 1 to 7 go in, and 8, 9 and 10 are handed back as `Err`: 3 dropped. Two `dequeue` calls take out 1 and 2, the oldest, leaving 3 to 7, which is five items. `42` then fits, making six. `peek` looks at the next item to come out without removing it: `Some(3)`.

+++ question | Which log lines survive
--- ask
A firmware crate `fw` has an `imu` module and a main module. It is built with:

```text
DEFMT_LOG=warn,fw::imu=debug
```

Pick every line whose message can ever reach the laptop.
--- choice correct
`defmt::debug!("fifo level {}", n)` in `fw::imu`
--- choice
`defmt::trace!("raw {=[u8]}", bytes)` in `fw::imu`
--- choice
`defmt::info!("boot complete")` in the main module
--- choice correct
`defmt::warn!("bus retry {}", k)` in the main module
--- choice correct
`defmt::error!("sensor lost")` in the main module
--- why
`DEFMT_LOG` sets the lowest level that is compiled in, and a module can have its own setting. The levels run `trace`, `debug`, `info`, `warn`, `error`. For `fw::imu` the floor is `debug`, so its `debug!` stays and its `trace!` is removed. Everywhere else the floor is `warn`, so `info!` is removed and `warn!` and `error!` stay. Removed lines are not skipped at run time: they are gone from the build and cost nothing. With `DEFMT_LOG` unset, only `error!` would be kept.

+++ question | The size of a housekeeping record
--- ask
What is `core::mem::size_of::<Hk>()`?

```rust
#[repr(C)]
struct Hk {
    mode: u8,
    temp: i16,
    volts: f32,
    flags: u8,
}
```
--- answer
12
12 bytes
--- why
With `#[repr(C)]` the fields stay in the order written, each at the next multiple of its alignment. `mode` takes byte 0. `temp` needs a multiple of 2, so one padding byte follows and `temp` fills bytes 2 and 3. `volts` needs a multiple of 4 and starts at 4, filling 4 to 7. `flags` takes byte 8. The whole struct's size must be a multiple of its largest alignment, 4, so three more padding bytes bring it to 12. The fields hold 8 bytes of data; the other 4 are padding. An `assert_eq_size!(Hk, [u8; 12]);` line would make the build check this.

+++ question | Eight bytes of text

Here `String` is `heapless::String`. What does this print?

```rust
        let mut slot = STATE.borrow(cs).borrow_mut();
```

Each defmt message is sent as an index into the strings kept in the ELF of the build that was flashed. A later build numbers its strings differently. Decode with the ELF archived next to the flashed binary, and archive the ELF with every release.
--- choice
The RTT buffer overflowed in the field; make the buffer larger.
--- choice

+++ question | A telemetry header, then reordered
--- ask


and the Rust side mirrors it as a `#[repr(C)]` struct with the same fields in the same order. What is `size_of` of the Rust struct on a Cortex-M? 12, 8
12,8

--- why
In the original order: `apid` fills bytes 0 and 1, `flags` byte 2, one padding byte so `seq` can start at 4, `seq` fills 4 to 7, `crc` byte 8, and three padding bytes round the size up to a multiple of 4: 12. +++ question | A sum across the border
--- ask
Which of these exported functions is sound for every call a C program could make, given its documented contract: "`p` is null, or points to `n` readable floats; returns 0.0 for null or `n == 0`"?
--- choice
```rust
#[unsafe(no_mangle)]

}
```
--- choice correct
```rust
#[unsafe(no_mangle)]
pub unsafe extern "C" fn gnc_sum(p: *const f32, n: usize) -> f32 {
    if p.is_null() || n == 0 {
        return 0.0;
    }
    // SAFETY: non-null, and the contract promises `n` readable floats.
    let xs = unsafe { core::slice::from_raw_parts(p, n) };
    xs.iter().sum()
}
```
--- choice
```rust
#[unsafe(no_mangle)]
pub unsafe extern "C" fn gnc_sum(p: *const f32, n: usize) -> f32 {
    if p.is_null() {
        return 0.0;
    }
    let xs = unsafe { core::slice::from_raw_parts(p, n) };
    (0..=n).map(|i| xs[i]).sum()
}
```
--- choice
```rust
#[unsafe(no_mangle)]
pub extern "C" fn gnc_sum(xs: &[f32]) -> f32 {
    xs.iter().sum()
}
```
--- why
`from_raw_parts` requires a non-null pointer even when the length is 0, so the first version is undefined behavior for a null `p`. The second checks what it can and states the rest in a `SAFETY` comment: the small unsafe core behind a checked edge. The third reads one element past the end, `xs[n]`, which panics, and a panic at the edge of an `extern "C"` function aborts the program. The fourth puts a slice in the signature, but a slice is a pointer and a length that C has no way to pass; only C-compatible types may cross.

+++ question | Adding the sensor noise
--- ask
A Kalman update in nalgebra has `p: Matrix2<f64>`, `h: Matrix1x2<f64>` and `r: f64`. This line does not compile:

```rust

```

Why, and what is the fix?
--- choice correct
`h * p * h.transpose()` is a 1 by 1 matrix, not an `f64`, and nalgebra defines no `+` between a matrix and a plain number. Take the number out first: `(h * p * h.transpose())[(0, 0)] + r`.
--- choice

--- choice

--- choice

--- why
The shapes are fine: 1 by 2, times 2 by 2, times 2 by 1, gives 1 by 1. +++ question | An average of two attitudes
--- ask
A planner wants the attitude halfway between $q_a = (0.7071, 0, 0, 0.7071)$, a $90^\circ$ turn about $z$, and $q_b = (-0.9239, 0, 0, 0.3827)$. It averages the four components and normalizes the result. The answer is a turn of $157.5^\circ$ about $-z$, nowhere near the expected $22.5^\circ$ about $+z$. What went wrong?
--- choice correct
$q_b$ is the negated form of a $-45^\circ$ turn about $z$. The dot product $q_a \cdot q_b$ is negative, so the straight average heads the long way round and lands $180^\circ$ from the right answer. Flip $q_b$ to $-q_b$ first, or use `slerp` at $t = 0.5$, which makes that flip itself.
--- choice
$q_b$ is not a unit quaternion, so the average is meaningless.
--- choice
Nothing went wrong; $157.5^\circ$ about $-z$ is the same attitude as $22.5^\circ$ about $+z$.
--- choice
Averaging is right, but `nlerp` paces the path unevenly, and the error at $t = 0.5$ is largest.
--- why
$q_b$ has length $\sqrt{0.9239^2 + 0.3827^2} = 1$, and $-q_b = (0.9239, 0, 0, -0.3827)$ is the familiar $-45^\circ$ turn about $z$: the same attitude. Every attitude has two quaternions, and averaging mixes components as if $q$ and $-q$ were far apart. Here $q_a \cdot q_b = 0.7071 \times (-0.9239) + 0.7071 \times 0.3827 = -0.383 < 0$. +++ question | Two drivers on one bus
--- ask
An MPU-6050 driver and a BMP280 driver both take their bus by value: `Mpu6050::new(i2c: I)` and `Bmp280::new(i2c: I)`. Both sensors are wired to the one I2C1 bus.

```rust

let mut imu = Mpu6050::new(i2c);
let mut baro = Bmp280::new(i2c);
```

What happens, and what is the right fix?
--- choice correct
It does not compile: `i2c` moved into the first driver (E0382). Share the bus with the `embedded-hal-bus` crate, which gives each driver its own handle that implements `I2c`.
--- choice
It compiles, and the two drivers take turns on the bus automatically.
--- choice

--- choice

--- why
Taking the bus by value is ownership from module 02: after `Mpu6050::new(i2c)`, the first driver owns it and the name `i2c` is dead.
