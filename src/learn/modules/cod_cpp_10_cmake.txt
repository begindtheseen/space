=== cpp10-l01 | Practice: Why CMake, and a first project
--- for
l01-why-cmake-and-a-first-project

+++ question | Two mistakes, two commands
--- ask
A new project has two mistakes. In `CMakeLists.txt`, a command is misspelled:

```cmake
add_executible(burn_timer main.cpp)
```

In `main.cpp`, the semicolon after `return 0` is missing. You run `cmake -S . -B build`, fix whatever it reports, and then run `cmake --build build`. Which command reports which mistake?
--- choice correct
`cmake -S . -B build` stops on the misspelled command ("Unknown CMake command"). The missing semicolon is only found by `cmake --build build`, when the compiler finally reads `main.cpp`.
--- choice
`cmake -S . -B build` reports both, because configure checks every file of the project.
--- choice
`cmake --build build` reports both, because configure only writes files and never checks anything.
--- choice
Neither: CMake guesses that `add_executible` means `add_executable`, and the compiler adds the missing semicolon with a warning.
--- why
Configure runs `CMakeLists.txt` as a script, so a command CMake does not know stops it at once, with the line number. It never opens `main.cpp`: no source file is compiled until the build step runs the compiler. So a clean configure only says that the CMake file makes sense. Mistakes in your C++ show up at `cmake --build`.

+++ question | The build folder that kept its settings
--- ask
You configure a folder for timing:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
```

A week later you add a source file to `CMakeLists.txt` and run only:

```bash
cmake -S . -B build
cmake --build build
```

With GCC, which optimization and assert flags is the new file compiled with?
--- choice
None: without `-DCMAKE_BUILD_TYPE` the build type is empty, so there is no `-O` and no `-DNDEBUG`.
--- choice
`-g`, because Debug is the default whenever the build type is not given on the command line.
--- choice
The new file gets no flags, while the old files keep `-O3 -DNDEBUG`, so the program mixes two build types.
--- choice correct
`-O3 -DNDEBUG`: the folder's `CMakeCache.txt` still holds `CMAKE_BUILD_TYPE=Release` from the first configure.
--- why
Every `-D` you pass is written into the build folder's cache, and later configures of that folder read it back. The second configure reset nothing: the whole folder, old files and new, is still Release. That is usually what you want, but it means a folder can carry a choice made long ago. To be sure what a folder holds, read its `CMakeCache.txt`, or delete the folder and configure it again.

+++ question | A minimum that is too low
--- ask
A project starts with `cmake_minimum_required(VERSION 3.20)` and is configured with CMake 3.28. Policy CMP0083 was added in CMake 3.14, and CMP0135 in CMake 3.24. What does this print?

```cmake
cmake_policy(GET CMP0083 a)
cmake_policy(GET CMP0135 b)
message(STATUS "CMP0083='${a}' CMP0135='${b}'")
```
--- choice
`CMP0083='NEW' CMP0135='NEW'`, because CMake 3.28 knows both fixes.
--- choice correct
`CMP0083='NEW' CMP0135=''`: only the policies up to 3.20 are set to NEW. CMP0135 is left unset, so CMake uses its OLD behavior.
--- choice
`CMP0083='' CMP0135=''`, because a policy is only set when you call `cmake_policy(SET ...)` yourself.
--- choice
Nothing: configure stops, because CMake 3.28 refuses to run a file that asks for 3.20.
--- why
The minimum does two jobs. It rejects an older CMake, and it sets every policy introduced up to that version to NEW. CMP0083 (3.14) is below 3.20, so it is NEW. CMP0135 (3.24) is above it, so it stays unset, and unset means the OLD behavior, even though the CMake you are running knows the fix. A newer CMake runs a file with a lower minimum without complaint. Raise the number to the version your team really uses and you get every fix up to there.

+++ question | Where the assert still fires
--- ask
`main.cpp` holds `assert(dt_s > 0.0);`, and the program is always given `dt_s = 0.0`. With GCC, the project is configured five times into five folders: with `-DCMAKE_BUILD_TYPE=Debug`, with `Release`, with `RelWithDebInfo`, with `MinSizeRel`, and with no build type at all. In which builds does the program stop at the assert?
--- choice
Only in Debug.
--- choice
In Debug and RelWithDebInfo, because both carry debug information.
--- choice correct
In Debug, and in the build with no build type.
--- choice
In none of them, because CMake adds `-DNDEBUG` unless you ask for Debug.
--- why
An `assert` disappears only when `NDEBUG` is defined. Release, RelWithDebInfo and MinSizeRel all add `-DNDEBUG`; debug information (`-g`) has nothing to do with it. An empty build type adds no flags at all: no `-O`, no `-g` and no `-DNDEBUG`. So the assert survives there too, in a program that is also unoptimized. An empty build type is not a quiet Release.

+++ question | Release that runs like Debug
--- ask
A benchmark script configures its build folder like this:

```bash
cmake -S . -B build/bench -DCMAKE_BUILD_TYPE=Relase
cmake --build build/bench
```

Configure and build succeed with no warning. But the filter runs about ten times slower than in a colleague's Release build, and a test `assert` still fires. What is wrong?
--- choice
Nothing in the commands; the colleague must be using a newer compiler.
--- choice
`build/bench` is inside `build`, and CMake applies the build type only to a folder named `build`.
--- choice
The build type must be written in lower case, `release`, or CMake ignores it.
--- choice correct
`Relase` is misspelled. CMake has default flags only for its four known build types, so an unknown name gets none: no `-O3` and no `-DNDEBUG`.
--- why
CMake picks the optimization and assert flags by looking up the build type's name. `Relase` is not Debug, Release, RelWithDebInfo or MinSizeRel, so nothing is found and nothing is added: the same as an empty build type, unoptimized and with every `assert` on. CMake does not treat the unknown name as an error. Running `cmake --build build/bench --verbose` shows the real compile command, and the missing `-O3 -DNDEBUG` is plain to see.

+++ question | A Makefile that forgets
--- ask
A teammate ran `cmake .` in the project's top folder, the one holding `CMakeLists.txt`. Then he opened the generated `Makefile` and added `-O2` to the compile line. It worked until he added a new file to `CMakeLists.txt`: now `-O2` is gone, and `git status` lists `CMakeCache.txt`, `CMakeFiles/`, `Makefile` and `cmake_install.cmake` as new files. What should he do?
--- choice correct
Delete the generated files from the source folder, configure out of source with `cmake -S . -B build -DCMAKE_BUILD_TYPE=RelWithDebInfo` (which gives `-O2`), and put `build/` in `.gitignore`. Never edit the generated `Makefile`.
--- choice
Commit the `Makefile`, so that his edit is kept in git and cannot be lost again.
--- choice
Add `CMakeCache.txt` to `.gitignore`, and redo the `-O2` edit in the `Makefile` after every change to `CMakeLists.txt`.
--- choice
Run `rm -rf build`, then configure again with `cmake .`.
--- why
The `Makefile` is CMake's output. It is rewritten every time a `CMakeLists.txt` changes, so hand edits are thrown away. Optimization is chosen with the build type: RelWithDebInfo adds `-O2 -g -DNDEBUG`, Release adds `-O3 -DNDEBUG`. The in-source build is the second problem: CMake's files are mixed in with his own, and one of them will soon be committed. With `-B build`, every generated file lives in one folder that one `.gitignore` line hides and one delete cleans. `rm -rf build` does nothing here, because his generated files are not in `build`.

=== cpp10-l02 | Practice: Targets, libraries and executables
--- for
l02-targets-libraries-and-executables

+++ question | The file on disk
--- ask
On Linux, a `CMakeLists.txt` holds:

```cmake
add_library(telemetry SHARED src/decode.cpp src/frames.cpp)
```

What is the name of the one library file this line makes in the build folder? Type the file name.
--- answer
libtelemetry.so
build/libtelemetry.so
--- why
The target is called `telemetry`, and on Linux CMake turns it into `lib` + name + an ending that depends on the kind: `.so` for `SHARED`, `.a` for `STATIC`. Both source files are compiled and linked into that single `libtelemetry.so`. The target name is a CMake name, not a file name: the same line gives `telemetry.dll` on Windows, and CMake picks the right spelling for each system.

+++ question | One switch, three libraries
--- ask
A project defines three libraries:

```cmake
add_library(nav src/ekf.cpp)
add_library(logbook STATIC src/logbook.cpp)
add_library(units INTERFACE)
```

It is configured with `-DBUILD_SHARED_LIBS=ON` and built. Which library files appear in the build folder?
--- choice
`libnav.so`, `liblogbook.so` and `libunits.so`: the switch makes every library shared.
--- choice
`libnav.a`, `liblogbook.a` and `libunits.a`, because the switch only matters for installed libraries.
--- choice correct
`libnav.so` and `liblogbook.a`, and nothing at all for `units`.
--- choice
Only `libnav.so`: `logbook` is skipped, because `STATIC` conflicts with the switch.
--- why
`BUILD_SHARED_LIBS` only decides for libraries that leave their kind out. `nav` says nothing, so it obeys the switch and becomes shared. `logbook` says `STATIC` outright, and an explicit kind always wins. `units` is an INTERFACE library: it has no sources and is never built, so it has no file at all, only usage requirements. That is why flight libraries usually write their kind: a packager's switch cannot turn them shared by accident.

+++ question | A header-only function that is not inline
--- ask
A header-only library is declared with `add_library(quat INTERFACE)` and an INTERFACE include folder. Its header:

```cpp
#pragma once
namespace quat {
struct Q { double w, x, y, z; };

double dot(const Q& a, const Q& b) {
    return a.w * b.w + a.x * b.x + a.y * b.y + a.z * b.z;
}
}  // namespace quat
```

The program `attitude_app` has two source files, `main.cpp` and `control.cpp`. Both include this header and call `quat::dot`, and the program links `quat`. What happens?
--- choice
Configure fails, because an INTERFACE library may not hold function definitions.
--- choice correct
The link fails with "multiple definition of `quat::dot`". Each source file compiles its own ordinary copy of `dot`. Marking it `inline` (or `constexpr`) fixes it.
--- choice
It builds and runs: an INTERFACE library is compiled once, so `dot` exists only once.
--- choice
`main.cpp` fails to compile with "redefinition of `dot`", because the header is included twice.
--- why
An INTERFACE library compiles nothing; its header is compiled inside every file that includes it. `#pragma once` stops a header being pasted twice into the *same* file, but `main.cpp` and `control.cpp` are two translation units, and each gets its own full definition of `dot`. Two ordinary definitions break the one-definition rule, and the linker says so. An `inline` or `constexpr` function is allowed in many files: the copies become weak symbols (`W` in `nm`), and the linker keeps one.

+++ question | The line an INTERFACE library accepts
--- ask
A header-only library is declared with `add_library(frames INTERFACE)`. Which one of these lines does CMake accept for it?
--- choice correct
`target_link_libraries(frames INTERFACE Eigen3::Eigen)`
--- choice
`target_include_directories(frames PRIVATE include)`
--- choice
`target_compile_features(frames PUBLIC cxx_std_20)`
--- choice
`target_compile_definitions(frames PRIVATE FRAMES_FAST=1)`
--- why
An INTERFACE library is never built, so there is no "me" for a setting to apply to. `PRIVATE` means only "me", and `PUBLIC` means "me and my users", so both are refused with "may only set INTERFACE properties on INTERFACE targets". `INTERFACE` means "my users only", which is all this target can have. Linking Eigen with `INTERFACE` is exactly right when the headers use Eigen types: every user of `frames` receives Eigen's include folder too.

+++ question | The folder that was renamed
--- ask
`gnc` is a `SHARED` library, and `orbit_report` links it. Straight after the build, `./build/orbit_report` runs fine. Then you rename the folder with `mv build build-old`, and:

```text
$ ./build-old/orbit_report
./build-old/orbit_report: error while loading shared libraries: libgnc.so: cannot open shared object file: No such file or directory
```

`libgnc.so` is still right there in `build-old`. Why does the program not find it?
--- choice
It should find it: the loader always searches the folder the program is in, so something else must be broken.
--- choice
`mv` changed the permissions of `libgnc.so`, so the loader may no longer read it.
--- choice
The program was linked statically, and a static program cannot open any `.so`.
--- choice correct
At link time CMake wrote the full path of the build folder into the program as the place to look for `libgnc.so`. That folder no longer exists. Rebuild in the new folder, link `gnc` statically, or install both properly.
--- why
A shared library is found at every start-up, by the dynamic loader. It searches the places recorded in the program, then the system folders. CMake recorded the absolute path of the build folder (the `-Wl,-rpath` on the link line) so the program runs from the build tree. Rename the folder and that path points nowhere, so `main` never runs and the exit code is 127. The loader does not search the program's own folder unless told to. A missing `.so` is always a start-up error, never a build error.

+++ question | What the linker takes from an archive
--- ask
`libgnc.a` holds four object files:

- `orbit.o` defines `orbit_speed`
- `drag.o` defines `drag_force`, which calls `log_msg`
- `logbook.o` defines `log_msg`
- `ekf.o` defines `ekf_step`

A program's `main` calls only `drag_force`, and the program links `gnc`, a `STATIC` library. Which members of the archive end up inside the program?
--- choice
All four: linking a static library copies the whole archive into the program.
--- choice
Only `drag.o`, because `main` calls nothing else.
--- choice correct
`drag.o` and `logbook.o`.
--- choice
None of them: a static library is loaded when the program starts.
--- why
The linker pulls in only the archive members that define a symbol the program still needs. `main` needs `drag_force`, so `drag.o` comes in. `drag.o` needs `log_msg`, so `logbook.o` comes in too. Nothing needs `orbit_speed` or `ekf_step`, so those members stay out. Running `nm -C` on the program would show `drag_force` and `log_msg` as `T`, and nothing else from `gnc`. After linking, the archive is not needed at all.

=== cpp10-l03 | Practice: Usage requirements, PUBLIC, PRIVATE and INTERFACE
--- for
l03-usage-requirements-public-private-interface

+++ question | Reading the keywords back from the flags
--- ask
`nav_app` links the library `gnc`. From `compile_commands.json`:

- `gnc`'s own file, `guidance.cpp`, is compiled with `-DGNC_SIM=1`. `nav_app`'s `main.cpp` is not.
- `main.cpp` is compiled with `-DGNC_FRAME=ECI`. `guidance.cpp` is not.

Which keywords did `target_compile_definitions(gnc ...)` use for the two names?
--- choice
Both `PUBLIC`.
--- choice correct
`GNC_SIM` is `PRIVATE`, and `GNC_FRAME` is `INTERFACE`.
--- choice
`GNC_SIM` is `INTERFACE`, and `GNC_FRAME` is `PRIVATE`.
--- choice
`GNC_SIM` is `PRIVATE`, and `GNC_FRAME` is `PUBLIC`.
--- why
Read each flag by where it landed. On the library's own file only: that is `PRIVATE`, "for me alone". On the consumer only: that is `INTERFACE`, "for my users alone". `PUBLIC` would have put `GNC_FRAME` on both lines. An `INTERFACE` definition on a compiled library is rarer, but it fits a macro that only the users' side reads, for example one tested in a public header that `gnc`'s own `.cpp` files never include.

+++ question | A link that skips a step
--- ask
```cmake
add_library(B STATIC b.cpp)
target_include_directories(B PUBLIC b/include)

add_library(A STATIC a.cpp)
target_link_libraries(A INTERFACE B)

add_executable(P main.cpp)
target_link_libraries(P PRIVATE A)
```

Which of the three targets `B`, `A` and `P` have their files compiled with `-Ib/include`? Type the target names.
--- answer
B P
P B
B and P
P and B
B, P
P, B
B,P
P,B
B and P only
only B and P
--- why
`B` sets its folder `PUBLIC`, so `B`'s own files get it. `A` links `B` with `INTERFACE`, which means "do not use it to build me, but hand it to my users". So `a.cpp` is compiled without it. `P` is a user of `A`, and receives everything `A` hands on, which now includes `B`'s folder. So `B` and `P` get the flag, and `A`, in the middle, does not. That is right only if `a.cpp` never includes `B`'s headers; if it did, the link should be `PUBLIC`.

+++ question | C++20 kept to itself
--- ask
`gnc`'s public header:

```cpp
#pragma once
#include <span>

namespace gnc {
double mean(std::span<const double> samples);
}  // namespace gnc
```

and its `CMakeLists.txt`:

```cmake
add_library(gnc STATIC src/stats.cpp)
target_include_directories(gnc PUBLIC include)
target_compile_features(gnc PRIVATE cxx_std_20)

add_executable(ground_tool apps/ground_tool.cpp)
target_link_libraries(ground_tool PRIVATE gnc)
```

GCC 13 compiles as C++17 unless told otherwise, and `std::span` is C++20. What happens when you build?
--- choice
Configure fails, because `target_compile_features` may not be `PRIVATE` on a static library.
--- choice correct
`gnc` builds. `ground_tool` fails with "'span' is not a member of 'std'", reported inside `gnc`'s header, because `ground_tool` is compiled as C++17. The feature should be `PUBLIC`.
--- choice
`gnc` itself fails to compile, because `PRIVATE` features apply only to consumers.
--- choice
Everything builds, because the stronger standard always wins across a link.
--- why
The header is compiled again inside every file that includes it, with that file's flags. `PRIVATE` gave C++20 to `stats.cpp` only, so `ground_tool.cpp` meets `std::span` as C++17 and the error appears in the library's header: the fingerprint of a requirement that is too private. "The stronger standard wins" is true only when the requirement reaches the consumer, which needs `PUBLIC` here. With `PUBLIC`, the consumer is compiled as C++20, or gets a clear message if its compiler cannot do C++20.

+++ question | A private link that still reaches the linker
--- ask
```cmake
add_library(logbook STATIC logbook.cpp)
target_include_directories(logbook PUBLIC logbook/include)

add_library(gnc STATIC guidance.cpp)
target_link_libraries(gnc PRIVATE logbook)

add_executable(nav_app main.cpp)
target_link_libraries(nav_app PRIVATE gnc)
```

`guidance.cpp` calls functions from `logbook`. No public header of `gnc` mentions `logbook`. What do `nav_app`'s compile line and link line contain?
--- choice
Neither mentions `logbook`: `PRIVATE` hides it completely, so the link fails with undefined references to the logbook functions.
--- choice
Both: the compile line gets `-Ilogbook/include` and the link line gets `liblogbook.a`.
--- choice
The compile line gets `-Ilogbook/include`, but the link line does not list `liblogbook.a`.
--- choice correct
The compile line has no `-Ilogbook/include`, but the link line lists `liblogbook.a` after `libgnc.a`.
--- why
A static library is only a bag of object files. It cannot link its own dependencies, so `libgnc.a` still holds calls into `logbook` when the program is linked. CMake knows this and passes `logbook` to the final link as a link-only dependency (recorded as `$<LINK_ONLY:logbook>`). The compile side stays private: `main.cpp` never sees `logbook`'s folder, which is correct because it never includes its headers. A shared `libgnc.so` records its own dependencies, so there a `PRIVATE` link really stays inside.

+++ question | It builds here and nowhere else
--- ask
The top `CMakeLists.txt` of the `gnc` repository holds:

```cmake
include_directories(extern/mathlib/include)

add_library(gnc STATIC src/guidance.cpp)
target_include_directories(gnc PUBLIC include)
```

`gnc`'s public header includes `<mathlib/vec3.hpp>`. Everything in this repository, `gnc`'s own tests included, builds. The simulation team adds `gnc` to their project with `add_subdirectory(gnc)` and links it. Their `main.cpp` fails with "mathlib/vec3.hpp: No such file or directory", reported inside `gnc/guidance.hpp`. Why, and what is the fix?
--- choice correct
`include_directories` only reaches targets in its own folder and below, so everything in `gnc`'s repository got the folder, and that hid the missing requirement. The simulation's folder is not below it. Give `mathlib` a target that carries its include folder, link `gnc` to it `PUBLIC`, and delete the global line.
--- choice
The simulation team should copy the `include_directories` line into their own top file.
--- choice
`gnc`'s `include` folder should be `PRIVATE`, so the simulation stops reading `gnc/guidance.hpp`.
--- choice
`add_subdirectory` passes no usage requirements, so the simulation must use `find_package(gnc)` instead.
--- why
A directory-wide setting belongs to a folder, not to a target, so it never travels with `gnc`. Inside the repository every target sat below that line, so no build of `gnc`'s own could show the bug. A consumer outside the folder gets `gnc`'s real usage requirements, and those never mentioned `mathlib`. Copying the global line into every consumer spreads the problem. With a `PUBLIC` link to a `mathlib` target, the folder reaches every user of `gnc`, from `add_subdirectory` or from an installed package.

+++ question | The macro that changed a struct
--- ask
`gnc`'s public header:

```cpp
#pragma once
#ifndef GNC_MAX_THRUSTERS
#define GNC_MAX_THRUSTERS 8
#endif

namespace gnc {
struct ThrusterTable {
    double duty[GNC_MAX_THRUSTERS];
    int count;
};
void fill_table(ThrusterTable& t);
}  // namespace gnc
```

The library sets `target_compile_definitions(gnc PRIVATE GNC_MAX_THRUSTERS=12)`. `nav_app` links `gnc`, makes a `ThrusterTable` on the stack and calls `fill_table`. Everything compiles and links without a warning. What is wrong when it runs?
--- choice
Nothing: definitions are copied to every file of the program, so both sides see 12.
--- choice
The linker would have reported a "multiple definition" of `ThrusterTable`, so the build cannot have succeeded.
--- choice correct
`fill_table` was compiled seeing 12 slots, and `nav_app` seeing 8, so the two disagree about the struct's size. `fill_table` writes past the end of `nav_app`'s smaller table and corrupts the stack, with no error at all. The definition must be `PUBLIC`.
--- choice
It is harmless: `nav_app` simply ignores the four extra slots.
--- why
The header fills in a default of 8 whenever the macro is missing, so `nav_app`, which never received the `PRIVATE` definition, compiles happily. `gnc`'s code thinks a table is 104 bytes, with `count` at byte 96. `nav_app` gives it a 72-byte table, with `count` at byte 64. The linker only matches names, not layouts, so nothing catches it. Any macro a public header tests is part of the interface and must reach every consumer with the same value: `PUBLIC`.

=== cpp10-l04 | Practice: Generator expressions and build configurations

+++ question | Two compilers and two configurations
--- ask
You want `-fno-omit-frame-pointer` on `gnc` only when the compiler is GCC or Clang *and* the configuration is Debug or RelWithDebInfo, with single-config and multi-config generators alike. Which line does that?
--- choice correct
`target_compile_options(gnc PRIVATE "$<$<AND:$<CXX_COMPILER_ID:GNU,Clang>,$<CONFIG:Debug,RelWithDebInfo>>:-fno-omit-frame-pointer>")`
--- choice
`target_compile_options(gnc PRIVATE "$<$<OR:$<CXX_COMPILER_ID:GNU,Clang>,$<CONFIG:Debug,RelWithDebInfo>>:-fno-omit-frame-pointer>")`
--- choice
`target_compile_options(gnc PRIVATE "$<IF:$<CXX_COMPILER_ID:GNU,Clang>,$<CONFIG:Debug,RelWithDebInfo>,-fno-omit-frame-pointer>")`
--- choice
An `if(CMAKE_CXX_COMPILER_ID MATCHES "GNU|Clang" AND CMAKE_BUILD_TYPE MATCHES "Debug|RelWithDebInfo")` block around a plain `target_compile_options` line.
--- why
Two yes-or-no questions joined by "and" is `$<AND:...,...>`, and `$<condition:text>` gives the flag only when the answer is 1. `OR` would also add the flag for MSVC in Debug, a compiler that does not know it. The `IF` line gives `1` or `0` for GCC and Clang, and the flag itself for every other compiler: backwards. The `if()` block runs at configure time, when a multi-config generator has no build type yet, so it adds nothing in any configuration there.

+++ question | How many report files
--- ask
A project writes a small report with:

```cmake
file(GENERATE OUTPUT "flags-$<CONFIG>.txt" CONTENT "config = $<CONFIG>\n")
```

It is configured once with `-G "Ninja Multi-Config"`, with the generator's default list of configurations. How many report files does CMake write? Type the number.
--- answer
3
three
3 files
three files
--- why
A generator expression is filled in once per configuration, at generate time. Ninja Multi-Config writes build rules for its default configurations, Debug, Release and RelWithDebInfo, so CMake writes `flags-Debug.txt`, `flags-Release.txt` and `flags-RelWithDebInfo.txt`. With a single-config generator and `-DCMAKE_BUILD_TYPE=MinSizeRel`, there is one configuration and one file, `flags-MinSizeRel.txt`.

+++ question | A generator expression with no build type
--- ask
```cmake
target_compile_definitions(gnc PRIVATE
  $<$<CONFIG:Debug>:GNC_CHECK_LEVEL=2>
  $<IF:$<CONFIG:Release>,GNC_FAST=1,GNC_FAST=0>)
```

The project is configured with plain `cmake -S . -B build` (Unix Makefiles, no build type) and built. Which definitions does `gnc` get?
--- choice
`GNC_CHECK_LEVEL=2` and `GNC_FAST=0`, because Debug is the default configuration.
--- choice
`GNC_FAST=1` only, because an empty build type is a release build.
--- choice
None: configure stops, because `$<CONFIG>` needs a build type.
--- choice correct
`GNC_FAST=0` only.
--- why
With a single-config generator the configuration is whatever `CMAKE_BUILD_TYPE` holds, and here it is empty. So "is it Debug?" is `0` and "is it Release?" is `0` too. The first line adds nothing, and the `IF` takes its else branch, `GNC_FAST=0`. Nothing fails; you just get a build that is neither Debug nor Release, unoptimized and without the Debug checks. Always give a single-config folder a build type.

+++ question | Apple's compiler
--- ask
A Debug build on a Mac uses Apple's own Clang, which CMake identifies as `AppleClang`. What does this expression give? Type the result exactly.


+++ question | Flags that grow
--- ask
A toolchain file holds:

```cmake
set(CMAKE_CXX_FLAGS "${CMAKE_CXX_FLAGS} -mcpu=cortex-m4 -mthumb")
```

What is wrong with it?
--- choice
`CMAKE_CXX_FLAGS` may not be set in a toolchain file; configure fails.
--- choice
The flags reach only C files, because the variable is read after `project()`.
--- choice
`-mthumb` must come before `-mcpu`, or the compiler ignores it.
--- choice correct
The file is read at the start of configure and again inside every try-compile, so each read appends the flags once more to whatever it was given. Put fixed values in `CMAKE_CXX_FLAGS_INIT`, which CMake copies into the cache once.

+++ question | A vendor library built the other way
--- ask
A sensor vendor supplies a prebuilt `libimu.a` for the Cortex-M4, compiled with `-mfloat-abi=soft`. The firmware uses the lesson's toolchain file, with `-mfloat-abi=hard`. The link fails with a message like "fin_controller uses VFP register arguments, libimu.a(imu.o) does not". Which fix is right?
--- choice correct
Get (or build) `libimu.a` with the same CPU flags as the toolchain file: `-mcpu=cortex-m4 -mthumb -mfloat-abi=hard -mfpu=fpv4-sp-d16`.

Add `-mfloat-abi=soft` to `fin_controller` alone, with `target_compile_options`, so it matches the vendor library.

--- why

So `gnc` is built right here, `$<BUILD_INTERFACE:...>` keeps its path, and `${CMAKE_CURRENT_SOURCE_DIR}` is where the source was downloaded, under `_deps`. `$<INSTALL_INTERFACE:...>` is kept only in an installed package's exported file. The alias `gnc::gnc` is what lets the simulation write the same name either way.

+++ question | Configure-time questions that are fine
--- ask
The cross-compiling lesson's project uses `if(CMAKE_CROSSCOMPILING)` in its `CMakeLists.txt`, while the generator expressions lesson says never to write `if(CMAKE_BUILD_TYPE STREQUAL "Debug")`. Both are ordinary `if()` tests. Why is one fine and the other not?
--- choice
`CMAKE_CROSSCOMPILING` is a cache variable, and `if()` can only read cache variables reliably.
--- choice
`if(CMAKE_CROSSCOMPILING)` is actually evaluated at generate time, like a generator expression.
--- choice correct
Whether the build is a cross build is settled before `project()`, by the toolchain file, and is the same for the whole folder. The configuration may not be chosen until build time, with a multi-config generator, so it is not known while `if()` runs.

+++ question | An Arm package that could not be found
--- ask

It is configured with `-DCMAKE_PREFIX_PATH=/opt/arm-libs`, and `find_package(gnc REQUIRED)` fails. `/opt/arm-libs/lib/cmake/gnc/gncConfig.cmake` is there. Why?
--- choice
`find_package` never works when cross-compiling; the firmware must use FetchContent.
--- choice correct
With mode `ONLY`, every search path is looked for inside the root paths, so `/opt/arm-libs` becomes `/usr/lib/arm-none-eabi/opt/arm-libs`, which does not exist. Add `/opt/arm-libs` to `CMAKE_FIND_ROOT_PATH`.
--- choice
The package was installed for the host, because `cmake --install` ignores the toolchain file.
--- choice
`CMAKE_PREFIX_PATH` needs the full path of the config file's folder, `/opt/arm-libs/lib/cmake/gnc`.

+++ question | A preset file that broke both builds
--- ask
A teammate adds a cross-compiling preset to the shared `CMakePresets.json`:

```json
{
  "name": "m4-release",
  "binaryDir": "build-m4",
  "toolchainFile": "${CMAKE_SOURCE_DIR}/cmake/arm-none-eabi.cmake",
  "cacheVariables": { "CMAKE_BUILD_TYPE": "MinSizeRel" }

```

What happens when anyone runs `cmake --preset host-debug`, a preset he did not touch?

+++ question | Which flag does it get
--- ask
```cmake
option(GNC_SANITIZE "Build with AddressSanitizer" OFF)
target_compile_options(gnc PRIVATE
  "$<IF:$<AND:$<BOOL:${GNC_SANITIZE}>,$<NOT:$<CONFIG:Release>>>,-fsanitize=address,-O2>")
```

A folder is configured with `-DGNC_SANITIZE=ON -DCMAKE_BUILD_TYPE=RelWithDebInfo`. Which of the two flags in the expression does `gnc` get? Type it exactly.
--- answer
-fsanitize=address
fsanitize=address
--- why
`${GNC_SANITIZE}` is an ordinary variable, filled in while the file is read, so the expression holds `$<BOOL:ON>`, which is `1`. +++ question | The flight build and the assert
--- ask
The PID controller's `update` starts with `assert(dt_s > 0.0f);`. The `m4-release` preset builds the flight program with `CMAKE_BUILD_TYPE` set to `MinSizeRel`. On the board, a timing fault delivers `dt_s = 0` once. What happens in that call?
--- choice correct

--- choice

+++ question | A warning with a date on it
--- ask
A project starts with `cmake_minimum_required(VERSION 3.16)` and downloads a dependency with FetchContent from a `URL` with a `URL_HASH`. With CMake 3.28, every configure prints "CMake Warning (dev)": "The DOWNLOAD_EXTRACT_TIMESTAMP option was not given and policy CMP0135 is not set. The policy's OLD behavior will be used."
