=== py4-01 | Debugging: closures and late binding
--- teach
The advanced course ended with binary search: throw away half the range at every step until the answer is pinned down. This expert course goes back inside Python itself. First comes the machinery serious code is built on (closures, descriptors, class hooks and coroutines; each gets its own lesson, so the names need not mean anything yet). Then typing, testing and designing code so it is easy to change. Last come hard problems that need a real algorithm.

It opens with a bug. You make several functions that should each do something different, and they all do the same thing. To see why, you need to know exactly how a closure remembers.

**A reminder: what a closure is.** You met closures in the decorators lesson. A function defined inside another function can keep using the outer function's variables, even after the outer function has returned. The inner function together with the variables it remembers is a **closure**.

```python
def make_greeter(greeting):
    def greet(name):
        return f"{greeting}, {name}"
    return greet

hello = make_greeter("hello")
print(hello("ada"))     # hello, ada
```

By the time `hello("ada")` runs, `make_greeter` has already finished. Yet `greet` still knows `greeting`. Two rules about *how* it remembers cause most closure bugs.

**Rule 1: a closure keeps the variable, not the value.** Think of a variable as a labelled box. A closure does not take a photo of what is in the box when the function is made. It keeps the box itself, and opens it to look inside *each time the function runs*. Looking a name up when the function runs, instead of when it was made, is called **[[late binding|late-binding-name]]**.

```python
def make():
    n = 1
    def show():
        return n
    n = 2              # change the box after show was made
    return show

print(make()())        # 2, not 1
```

`show` was made while `n` was 1. But it only looks inside the box when it is called, and by then the box holds 2.

**Where it bites: functions made in a loop.** Here a loop makes three small functions with a **[[lambda|lambda-recap]]**. Each one should return the loop number it was made in:

```python
funcs = [lambda: i for i in range(3)]
print([f() for f in funcs])     # [2, 2, 2], not [0, 1, 2]
```

There is only **one** box called `i`. The loop puts 0 in it, then 1, then 2. All three lambdas share that one box. When you finally call them, the loop is over and the box holds 2, so every one of them says 2.

**Fix A: a default argument.** Default values are **[[worked out once, when the function is defined|defaults-once]]**. So a default can take a snapshot of the value right now:

```python
funcs = [lambda i=i: i for i in range(3)]
print([f() for f in funcs])     # [0, 1, 2]
```

Read `lambda i=i: i` aloud as "a function with a parameter called `i`, whose default is the value the loop's `i` has at this moment". Each lambda now has its own `i`, filled in when it was made.

**Fix B: a factory function.** A **factory** is a function whose job is to make and return another function. Every call to a function gets brand-new local variables, so every call to the factory makes a fresh box:

```python
def make(i):
    return lambda: i        # this i belongs to this one call of make

funcs = [make(i) for i in range(3)]
print([f() for f in funcs])     # [0, 1, 2]
```

Both fixes work. The factory is the cleaner one, because it does not add an extra parameter a caller could fill in by mistake.

This bug turns up most often when a program makes one **[[event handler|event-handlers]]** per button in a loop: every button ends up doing what the last one should.

**Rule 2: assigning to a name makes it local.** Reading an outer variable is fine, as `greet` did with `greeting`. *Assigning* to it is different. Before a function runs, Python scans its body. Any name that is assigned anywhere inside it (with `=`, `+=` and friends) is treated as that function's own **local** variable for the *whole* body.

```python
def make_counter():
    count = 0
    def increment():
        count += 1          # crashes
        return count
    return increment

make_counter()()
# UnboundLocalError: cannot access local variable 'count' where it is not associated with a value
```

`count += 1` means `count = count + 1`. That assignment makes `count` local to `increment`. So the right-hand side tries to read the *local* `count`, which has no value yet. Python stops with **[[UnboundLocalError|unbound-local]]**: a local variable was read before anything was put in it.

The fix is one line. `nonlocal count` tells Python "`count` is not mine; it is the box belonging to the function around me":

```python
def make_counter():
    count = 0
    def increment():
        nonlocal count
        count += 1
        return count
    return increment

c = make_counter()
print(c(), c(), c())    # 1 2 3
```

Each call to `make_counter()` makes a new `count` box, so two counters never share a count.

**How to debug it: look inside the closure.** When several functions "all return the same thing", suspect a shared variable. You can check. A function made inside another function has a `__closure__`: a tuple of **[[cells|closure-cells]]**, the boxes it remembers. `.cell_contents` shows what is in a box right now:

```python
funcs = [lambda: i for i in range(3)]
print(funcs[0].__closure__[0].cell_contents)                 # 2
print(funcs[0].__closure__[0] is funcs[2].__closure__[0])    # True: one shared box
```

`is` asks "is this the very same object?". `True` here proves the first and last function share one box. After the factory fix the same test prints `False`.

**Watch out:** the bug hides if you test each function *inside* the loop, right after making it. At that moment the box still holds the "right" value, so everything looks fine. It only goes wrong later, once the loop has moved on. Always test the functions after the loop has finished, the way the real program will call them.

::: context late-binding-name What "binding" means
To **bind** a name is to connect it to a value. *Late* binding means Python makes that connection as late as possible: at the moment the line runs, not when the function was written or created.

It is the same reason a function can use a variable that is only created further down the file, as long as the variable exists by the time the function is called. Python does not check names in advance; it looks them up at run time.

Late binding is a feature, not a flaw. It is what lets `make_counter` update its count. It only becomes a bug when you expected a snapshot and got a live box instead.
:::

::: context lambda-recap A lambda is a one-line function
You met `lambda` in the sorting lesson. `lambda x: x * 2` is a small function with no name. It is the same as writing:

```python
def double(x):
    return x * 2
```

A lambda holds one expression and returns its value automatically. `lambda: i` takes no arguments at all and returns `i`.

Lambdas follow exactly the same closure rules as `def` functions. They only look different; they remember variables the same way.
:::

::: context defaults-once The mutable-default lesson, turned into a tool
In the intermediate course, a list used as a default argument surprised you: it was created once, when the `def` ran, and then shared by every call.

That same fact, "defaults are worked out once, at definition time", is exactly what fixes late binding. `lambda i=i: i` copies the value of `i` into the default at the moment the lambda is made. The behaviour that caused one bug is the cure for another. Knowing *when* Python evaluates each thing is most of expert debugging.
:::

::: context event-handlers Buttons, handlers and ground stations
An **event** is something that happens while a program runs: a click, a key press, a message arriving. An **event handler** is the function the program calls when that event happens.

A mission-control screen might make one button per command from a list: "open valve", "arm", "abort". If each button's handler is a lambda made in the loop, every button can end up sending the last command in the list. A button labelled "open valve" that sends "abort" is a serious bug, and it is exactly this one. The task's `make_handlers` is a small model of it.
:::

::: context unbound-local Why Python decides "local" in advance
Python reads a whole function before it runs it, and decides once which names are local. It does not decide line by line. So an assignment on the *last* line of a function makes the name local on the *first* line too.

That is why the error is so confusing: the line that crashes looks like it only reads `count`. The cause is the assignment hidden inside `+=`.

There are two keywords to override the rule. `nonlocal x` means "the `x` of the function around me". `global x` means "the `x` at the top level of the file". Reaching for `global` is usually a sign the design needs rethinking; `nonlocal` inside a closure is normal.
:::

::: context closure-cells One shared box versus a box each
A **cell** is Python's name for the box a closure keeps. Functions made in a loop without a fix all point at one cell. With a factory, each call makes its own cell.

1. `make_multipliers(4)` should return four functions, where the function at position `k` multiplies its argument by `k` (so the first multiplies by 0, the last by 3). Instead, all of them multiply by 3.
2. `make_handlers(["save", "open"])` should return a dictionary mapping each name to a function that returns `"clicked <name>"`. Instead, every handler says `"clicked open"`.

    def times(k):
        return lambda x: k * x
    return [times(i) for i in range(n)]

    handlers = {}
    for name in names:
        handlers[name] = lambda name=name: f"clicked {name}"
    return handlers


def make_counter():
    count = 0

    def increment():
        nonlocal count
        count += 1
        return count

    return increment

=== py4-02 | Descriptors: how @property really works
--- teach
Last lesson showed exactly how a closure finds its variables. This one shows how Python finds an **attribute**: what really happens when you write `obj.attr`. In the intermediate course you used `@property` to check a value whenever it was set. Here you build the machinery underneath `@property` yourself, and then use it to write a checker once and reuse it on every field.

**Step 1: every object has its own dictionary.** When you write `self.x = 3`, Python stores it in a dictionary that belongs to that one object, called `__dict__`. The built-in `vars(obj)` shows the same dictionary.

```python
class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

p = Point(3, 4)
print(p.__dict__)     # {'x': 3, 'y': 4}
print(vars(p))        # {'x': 3, 'y': 4}
```

**Step 2: a class has attributes too.** A name set directly in the class body, not on `self`, is a **[[class attribute|class-vs-instance]]**. It belongs to the class and is shared by every object made from it. It does not appear in any object's `__dict__`.

```python
class Ship:
    fleet = "Artemis"          # class attribute: one, shared
    def __init__(self, name):
        self.name = name       # instance attribute: one per object

a = Ship("Orion")
print(a.fleet)        # Artemis   (found on the class)
print(vars(a))        # {'name': 'Orion'}
```

**Step 3: a descriptor answers for the attribute.** Picture a hotel. Usually, when you ask for something, you go and get it from your own room. But for a few things the hotel has put a receptionist at the front desk, and anyone who asks for *those* gets their answer from the receptionist instead.

A **[[descriptor|descriptor-word]]** is that receptionist: an object with a `__get__` method, stored as a class attribute. When you read `obj.attr`, Python first checks the *class* for an attribute of that name. If it finds a descriptor there, Python calls its `__get__` and hands you whatever it returns.

```python
class Loud:
    def __get__(self, obj, owner):
        return "HELLO"

class Thing:
    greeting = Loud()     # a descriptor, stored on the CLASS

print(Thing().greeting)   # HELLO   (Loud.__get__ was called)
```

`__get__(self, obj, owner)` gets three things:

- `self`: the descriptor itself (the `Loud` object).
- `obj`: the object the attribute was read from. When it is read from the class itself, as in `Thing.greeting`, there is no object, so `obj` is `None`. By convention the descriptor then returns itself.
- `owner`: the class (`Thing`).

**Step 4: `__set__` catches assignments.** Give a descriptor a `__set__(self, obj, value)` method too, and every `obj.attr = value` calls it instead of storing the value directly. A descriptor with `__set__` is a **data descriptor**, and it **[[wins over the object's own dictionary|lookup-order]]**: Python always asks it first.

**Step 5: `__set_name__` tells it its name.** When the class is created, Python calls `__set_name__(self, owner, name)` on each descriptor once, passing the name it was assigned to. For `username = NonEmpty()`, `name` is `"username"`. The descriptor saves it as `self.name` so it can use it later.

**Step 6: where the value lives.** Not on the descriptor! There is one descriptor per *class*, shared by every object. Each object's value goes in that object's own `__dict__`, under the attribute's name, **[[written straight into the dictionary|why-dict-direct]]**: `obj.__dict__[self.name] = value`.

Put together, here is a reusable "must not be empty" checker. With `@property` you would write the same getter and setter again for every field. A descriptor writes it once:

```python
class NonEmpty:
    def __set_name__(self, owner, name):
        self.name = name
    def __get__(self, obj, owner):
        if obj is None:
            return self
        return obj.__dict__[self.name]
    def __set__(self, obj, value):
        if not value:
            raise ValueError(f"{self.name} must not be empty")
        obj.__dict__[self.name] = value

class User:
    username = NonEmpty()
    email = NonEmpty()
    def __init__(self, username, email):
        self.username = username      # goes through NonEmpty.__set__
        self.email = email

u = User("ada", "ada@example.com")
print(vars(u))       # {'username': 'ada', 'email': 'ada@example.com'}
User("", "x@example.com")
# ValueError: username must not be empty
```

The check runs both when the object is made and on any later assignment such as `u.email = ""`.

**Checking for a number.** `isinstance(value, (int, float))` is true when `value` is an `int` *or* a `float`: a tuple of types means "any of these". So `isinstance(2.5, (int, float))` is `True` and `isinstance("5", (int, float))` is `False`. One surprise: in Python **[[True counts as a whole number|bool-is-int]]**, so `isinstance(True, int)` is `True`. A careful number check also rejects `bool`.

**Step 7: a descriptor with only `__get__`.** Without `__set__` it is a **non-data descriptor**, and now the object's own `__dict__` wins over it. That allows a neat trick: the first time the attribute is read, `__get__` computes the value and stores it in the object's `__dict__` under the *same name*. From then on Python finds the stored value first and never calls `__get__` again. The standard library's `functools.cached_property` works exactly this way, to **[[compute once, then remember|cached-property]]**:

```python
from functools import cached_property

class Report:
    @cached_property
    def summary(self):
        print("working...")
        return "all systems go"

r = Report()
print(r.summary)    # prints working... and then all systems go
print(r.summary)    # all systems go   (no "working..." this time)
print(vars(r))      # {'summary': 'all systems go'}
```

`@cached_property` above a method works like any decorator: `summary = cached_property(summary)`. The class attribute `summary` is then the descriptor, and it is given the method to call.

This one rule is how `@property` itself works: `property` is a data descriptor built into Python. Even plain **[[methods|methods-are-descriptors]]** are found this way.

**Watch out:** storing the value on the descriptor, as `self.value = value` inside `__set__`. It looks fine with one object. But every object shares the one descriptor, so they all share one value: make a product priced 1, then one priced 2, and the first product's price is now 2 as well. Always store in `obj.__dict__`.

::: context class-vs-instance One descriptor, many objects
A class attribute lives on the class, once. Each object has its own `__dict__` for its own data. A descriptor is a class attribute, so every object uses the same descriptor, but each object's value lives in that object's dictionary.

Changing a class attribute changes it for everyone at once, which is useful for shared settings and dangerous for anything that should be per object.

::: context descriptor-word Why "descriptor"
The object *describes* how an attribute behaves: what happens when it is read, set, or looked up on the class. The attribute itself is just a name; the descriptor is the set of rules behind it.

The methods `__get__`, `__set__` and `__set_name__` are **special methods** (the double-underscore kind, sometimes called "dunder" methods, from "double underscore"), like `__repr__` and `__eq__` in the intermediate course. You never call them yourself; Python calls them at the right moment.
:::

::: context lookup-order The order Python searches in
When you read `obj.attr`, Python checks in this order:

1. A **data descriptor** (has `__set__`) named `attr` on the class. If there is one, its `__get__` answers.
2. The object's own `__dict__`. If `attr` is there, that value is the answer.
3. A **non-data descriptor** (only `__get__`), or a plain class attribute, on the class.
4. Otherwise, `AttributeError`.

Data descriptors come first so a checker cannot be skipped by a value sitting in the dictionary. Non-data descriptors come after the dictionary, which is what lets a cached value hide the descriptor.
:::

::: context why-dict-direct Why not write obj.price = value?
Inside `__set__`, it is tempting to store the value with `setattr(obj, self.name, value)` or `obj.price = value`. But that *is* an assignment to the attribute, so Python calls `__set__` again, which assigns again, which calls `__set__` again, forever, until Python gives up with `RecursionError`.

Writing into `obj.__dict__[self.name]` is a plain dictionary assignment. It does not go through the descriptor, so it breaks the loop. Reading works the same way: `__get__` reads the dictionary directly, not `obj.price`.
:::

::: context bool-is-int True and False are secretly 1 and 0
In Python, `bool` is a subclass of `int`: `True` behaves like 1 and `False` like 0. So `isinstance(True, int)` is `True`, and `True + True` is `2`.

That means a check like "is it an `int` or `float` greater than 0?" would accept `True` as the number 1. A price of `True` is almost certainly a bug, so a careful check adds `or isinstance(value, bool)` to its list of things to reject.
:::

::: context cached-property Compute once, then remember
Some values take real work to compute: parsing a large file, loading a star catalogue, fitting a curve to thousands of sensor readings. If the answer never changes for that object, there is no point computing it every time it is read.

`cached_property` computes on the first read and stores the result in the object's `__dict__`. Later reads are ordinary dictionary look-ups. Deleting it (`del r.summary`) removes the stored value, so the next read computes it again.

Only use it for values that really cannot change. If the data underneath changes, the cached answer quietly goes stale.
:::

::: context methods-are-descriptors Even methods are descriptors
Every function has a `__get__` method, so a function stored in a class is a non-data descriptor. When you write `acct.deposit`, Python finds the function on the class and calls its `__get__`, which returns a **bound method**: the function with `acct` already filled in as `self`. That is how `self` gets its value without you ever passing it.

Two decorators you will meet in other people's code are descriptors too: `@classmethod` hands the method the class instead of the object, and `@staticmethod` hands it neither.
:::

class Positive:
    def __set_name__(self, owner, name):
        self.name = name

    def __get__(self, obj, owner):
        if obj is None:
            return self
        return obj.__dict__[self.name]

    def __set__(self, obj, value):
        if not isinstance(value, (int, float)) or isinstance(value, bool) or value <= 0:
            raise ValueError(f"{self.name} must be a number greater than 0")
        obj.__dict__[self.name] = value


class lazy:

        self.func = func

    def __set_name__(self, owner, name):
        self.name = name

    def __get__(self, obj, owner):

            return self
        value = self.func(obj)
        obj.__dict__[self.name] = value
        return value

=== py4-03 | Class hooks: __init_subclass__ and the plugin pattern
--- teach
Last lesson, Python called a descriptor's `__set_name__` at the moment its class was created. That was a **hook**: a method Python calls for you at a particular moment. This lesson uses another class-creation hook to solve a real design problem: letting new pieces of a program add themselves.

**The problem.** Some programs are built from **[[plugins|plugins-real]]**: separate pieces that each add one feature, such as one command, one file format or one payment provider. Each lives in its own class, and the core program needs a list of them all. If a person keeps that list by hand, sooner or later someone writes a new class, forgets to add it to the list, and the feature silently does not exist.

Think of a club. A secretary copying names onto a list will eventually miss someone. A sign-up sheet at the door, which every new member signs on the way in, never misses anyone. The fix for plugins is the sign-up sheet: each class **registers itself** the moment it is defined. The shared list is called a **registry**.

**Step 1: a `class` statement is code that runs.** Python builds a class when it reaches the `class` line, the way it runs any other line, usually **[[at import|import-time]]**:

```python
print("before")
class A:
    print("building A")
print("after")
```

```
before
building A
after
```

So there *is* a moment when each class comes into existence, and Python can run code of yours at that moment.

**Step 2: the hook.** If a base class defines `__init_subclass__`, Python calls it every time a **subclass** of it is created. Its first argument, `cls`, is **[[the brand-new class itself|cls-parameter]]**: the subclass (not an object made from it). `cls.__name__` is that class's name as a string.

```python
class Base:
    def __init_subclass__(cls, **kwargs):
        super().__init_subclass__(**kwargs)
        print("new subclass:", cls.__name__)

class Red(Base):
    pass

class Blue(Base):
    pass
```

```
new subclass: Red
new subclass: Blue
```

The hook runs for `Red` and `Blue`, not for `Base` itself. The `super()` line is explained in Step 4.

**Step 3: a registry.** Put a dictionary on the base class as a class attribute (last lesson: one, shared by everyone). The hook adds each new subclass to it:

```python
class Exporter:
    formats = {}

    def __init_subclass__(cls, **kwargs):
        super().__init_subclass__(**kwargs)
        Exporter.formats[cls.extension] = cls

class CsvExporter(Exporter):
    extension = "csv"

class JsonExporter(Exporter):
    extension = "json"

print(Exporter.formats)
# {'csv': <class '__main__.CsvExporter'>, 'json': <class '__main__.JsonExporter'>}
```

Nobody wrote `formats["csv"] = CsvExporter`. Defining the class was enough. The registry stores the *classes* themselves, so the program can later look one up by its extension and make an object from it: `Exporter.formats["csv"]()`.

**Step 4: the three things to get right.**

- **Register on the base class by name** (`Exporter.formats`), so there is one registry that every subclass shares.
- **Call `super().__init_subclass__(**kwargs)`**. `super()` means "the parent class", as in the exceptions lesson, and `**kwargs` passes along any keyword arguments you did not use yourself, as in the `*args, **kwargs` lesson. This lets your hook **[[cooperate|cooperative-super]]** with any other base class that has a hook of its own.
- **Check at definition time.** The hook runs when the `class` statement runs. So a subclass that forgot its `extension`, or reused one that is already taken, can raise an error immediately, when the file is loaded, long before a user hits the problem.

For the check, give the base class a default value, such as `extension = None`. A subclass that does not set its own inherits the parent's `None`, so the hook can test for it:

```python
class Exporter:
    formats = {}
    extension = None

    def __init_subclass__(cls, **kwargs):
        super().__init_subclass__(**kwargs)
        if not cls.extension:
            raise TypeError(f"{cls.__name__} needs an extension")
        Exporter.formats[cls.extension] = cls

class Broken(Exporter):
    pass
# TypeError: Broken needs an extension
```

`if not cls.extension` catches both `None` and an empty string `""`. Checking for a duplicate is one more `if`: is `cls.extension` already a key `in Exporter.formats`?

**A method subclasses must fill in.** The base class can list a method every plugin must provide, and make it fail loudly if a plugin forgets:

```python
def run(self, args):
    raise NotImplementedError
```

`NotImplementedError` is the built-in exception for "a subclass was supposed to replace this method". Each plugin defines its own `run`, which replaces the base one.

**Settings in the class line.** A subclass can also pass keyword arguments to the hook, right in its `class` line: `class Csv(Exporter, extension="csv")` calls `__init_subclass__` with `extension="csv"` as a keyword argument, which the hook can accept as a parameter.

**Other ways to do this.** Before `__init_subclass__` existed, this took a **[[metaclass|metaclass-word]]**: a class whose objects are themselves classes. Metaclasses can do more, but they are harder to read and hard to combine; reach for the hook first. A class decorator (`@register` above each class) also works, but then every plugin author has to remember to write it, which is the very thing we were trying to avoid.

**Making a class with a call.** A class can also be created without a `class` statement, by calling `type(name, bases, namespace)`: the name as a string, a tuple of parent classes, and a dictionary of its attributes. The hook still runs. These two do the same thing:

```python
class Echo(Base):
    sound = "echo"

Echo = type("Echo", (Base,), {"sound": "echo"})     # also prints: new subclass: Echo
```

The checks for this lesson use `type(...)` to add plugins of their own and see whether your registry picks them up.

**Using the registry: a dispatcher.** A **dispatcher** reads a request and hands it to the right plugin. For typed commands, `line.split()` with no argument splits on any run of spaces and drops the empty bits, so `"add 1 2".split()` is `['add', '1', '2']` and `"   ".split()` is `[]`. The first word picks the plugin from the registry with `.get(...)`, and the rest of the words are its arguments.

**Watch out:** a plugin registers itself only when its `class` statement runs. If it sits in a file that the program never imports, its class is never built, and it never appears in the registry. When a plugin "does not exist", first check that its file is actually imported.

::: context plugins-real Plugins in real programs
Plugin systems are everywhere. The testing tool `pytest` finds extra features through plugins. Web frameworks register each page's handler. Code editors load language support as plugins.

Flight software uses the same idea. A spacecraft receives commands from the ground, each with a name or number, and a dispatcher looks the command up in a table and calls the code that handles it. Adding a new command means adding one handler, not editing the dispatcher. That is exactly the shape of this lesson's task.
:::

::: context import-time What "at import" means
When Python loads a file, whether you run it directly or another file does `import` on it, it runs every top-level line from top to bottom. `def` and `class` statements are lines too: running them creates the function or class.

So "import time" is the moment the file is loaded, usually right as the program starts. An error raised by a class hook at import time stops the program before it does any real work, which is exactly when you want to hear about a broken plugin: on the developer's screen, not in the middle of a user's session.
:::

::: context cls-parameter cls instead of self
Ordinary methods receive the *object* as their first argument, and by convention it is called `self`. `__init_subclass__` receives a *class* instead, so by convention its first argument is called `cls`. (`class` itself is a keyword and cannot be a name.)

Python makes `__init_subclass__` a **class method** automatically. Other methods can be made into class methods with the `@classmethod` decorator; you will see them used as extra ways to build an object, such as a method that builds a date from the text "2026-09-27".
:::

::: context cooperative-super Passing the call up the chain
A class can have more than one parent. If two parents both define `__init_subclass__`, each one must call `super().__init_subclass__(**kwargs)`, or the chain stops and the other parent's hook never runs.

::: context metaclass-word A class of classes
Every object has a type: `type(3)` is `int`. Classes are objects too, so they have a type as well, and for ordinary classes it is `type`: `type(int)` is `type`, and so is `type(Red)`. A class whose objects are classes is called a **metaclass**, and `type` is the one Python uses by default.

That is why calling `type(name, bases, namespace)` makes a new class: you are calling the metaclass, the class that makes classes. Writing your own metaclass lets you change how classes are built, which is powerful and rarely needed.
:::

=== py4-04 | Advanced generators: send and yield from
--- teach
The last two lessons were about how classes are built. Now back to generators, from the advanced course. There, `yield` handed a value *out* and paused the function, and `next()` woke it up again. So far that conversation only goes one way: the generator talks, and the caller listens. This lesson adds two things. A generator can also **receive** values, and it can **delegate**: hand its work over to another generator.

**Step 1: `yield` gives back a value.** `yield` is an **[[expression|expression-word]]**, so it can sit on the right of an `=`. The line

```python
x = yield value
```

does two things, with a pause in between. First it hands `value` out and pauses. Later, when the caller wakes it up with `g.send(something)`, the whole `yield value` part turns into `something`, and that is stored in `x`.

```python
def echo_upper():
    reply = None
    while True:
        text = yield reply
        reply = text.upper()

g = echo_upper()
print(next(g))            # None
print(g.send("hi"))       # HI
print(g.send("there"))    # THERE
```

Follow it step by step:

1. `next(g)` runs the body up to the first `yield`, hands out `reply` (still `None`), and pauses there.
2. `g.send("hi")` wakes it. The paused `yield reply` becomes `"hi"`, so `text = "hi"`. Then `reply = "HI"`, the loop goes round, and the next `yield reply` hands out `"HI"`. That is what `send` returns.
3. `g.send("there")` does the same again.

`send` both *puts in* one value and *takes out* the next one.

**Step 2: prime it first.** A brand-new generator has not run any of its body yet, so it is not paused at a `yield`, and there is nowhere for a sent value to go. You must call `next(g)` once (or `g.send(None)`, which is the same) to run it up to the first `yield`. This is called **[[priming|priming]]** the generator. Forget, and Python stops you:

```python
g = echo_upper()
g.send("hi")
# TypeError: can't send non-None value to a just-started generator
```

**Step 3: it remembers between messages.** A generator used with `send` keeps all its local variables between messages. That makes it a small **[[state machine|state-machine]]**, with no class needed. This one remembers the longest word it has been sent:

```python
def longest():
    best = ""
    while True:
        word = yield best
        if len(word) > len(best):
            best = word

g = longest()
next(g)                   # prime it: hands out ''
print(g.send("moon"))     # moon
print(g.send("sun"))      # moon
print(g.send("jupiter"))  # jupiter
```

A plain `x = yield`, with nothing after `yield`, hands out `None` and waits for a value. Use it when the generator only listens.

**Step 4: `yield from` hands over.** Inside a generator, `yield from other` **[[delegates|delegation]]** to another generator: it passes out every value `other` yields, one by one, until `other` finishes. Then the outer generator carries on.

```python
def inner():
    yield 1
    yield 2

def outer():
    yield 0
    yield from inner()
    yield 3

print(list(outer()))      # [0, 1, 2, 3]
```

For plain values, `yield from inner()` does the same as `for v in inner(): yield v`. But it also passes every `send` straight through to `inner`, which a `for` loop cannot do.

**Step 5: recursion with `yield from`.** `yield from` keeps a recursive generator short. This one walks a list that has lists inside it, to any depth:

```python
def walk(tree):
    for node in tree:
        if isinstance(node, list):
            yield from walk(node)    # hand over to the recursive call
        else:
            yield node

print(list(walk([1, [2, [3]], 4])))   # [1, 2, 3, 4]
```

To treat both lists and tuples as containers, pass a tuple of types: `isinstance(node, (list, tuple))` is true for either one.

**Step 6: a generator can `return` a result.** When a generator reaches `return total`, it ends. If someone was driving it with `send`, that `send` raises `StopIteration`, and the returned value **[[rides along on it|stopiteration-value]]** as its `.value`:

```python
def add_up():
    total = 0
    while True:
        x = yield
        if x is None:
            return total      # ends this generator with a result
        total += x

g = add_up()
next(g)
g.send(3)
g.send(4)
try:
    g.send(None)
except StopIteration as stop:
    print(stop.value)         # 7
```

Catching that by hand is clumsy. `yield from` does it for you: when the inner generator returns, the value becomes the result of the `yield from` expression itself.

```python
def outer(results):
    while True:
        results.append((yield from add_up()))

results = []
g = outer(results)
next(g)
g.send(3)
g.send(4)
g.send(None)     # add_up returns 7; outer appends it and starts a fresh add_up
g.send(10)
g.send(None)     # the second add_up returns 10
print(results)   # [7, 10]
```

Every `send` goes through `outer` straight into the current `add_up`. When `add_up` returns, `yield from add_up()` becomes 7, `outer` appends it, loops, and starts a new `add_up`, which runs to its first `yield` and waits. Note the extra brackets in `results.append((yield from add_up()))`: Python requires brackets around a `yield` expression used inside a call like this.

This send-and-delegate machinery is the ancestor of `async` and `await`, which are **[[the next lesson|async-bridge]]**.

**Watch out:** when flattening, do not treat strings as containers. A string can be looped over, and each of its characters is itself a string, so a flatten that recurses into anything loopable **[[never stops|string-forever]]** and crashes with `RecursionError`. Test for `list` and `tuple` by name, so a string like `"ab"` is yielded whole.

::: context expression-word Expressions and statements
An **expression** is a piece of code that produces a value: `2 + 3`, `len(word)`, `x > 0`. A **statement** is an instruction that does something but has no value of its own, like `if`, `for` or `return`.

In early Python, `yield` was only a statement: it could hand a value out, and that was all. Since Python 2.5 it has been an expression, so it can also produce a value: whatever the caller sends in. That small change is what makes everything in this lesson possible.
:::

::: context priming Why it is called priming
Old hand pumps would not work dry. You first poured a little water in, called *priming* the pump, and only then did pumping bring water up. A new generator is the same: one `next()` gets it running to its first `yield`, and only then can it take a value.

::: context state-machine State machines on real vehicles
A **state machine** is something that is always in one of a few states and moves between them when messages arrive. A traffic light is one: green, then amber, then red.

Flight software is full of them. A rocket's flight computer might move from "on the pad" to "ascent" to "coast" to "landing", each move triggered by a sensor reading or a command. A generator that receives readings with `send` and keeps its current state in a local variable is a compact way to write a small one, and it is easy to test by sending in a list of made-up readings.
:::

::: context delegation Delegating is like transferring a phone call
When a help-desk operator transfers your call to a specialist, you talk straight to the specialist until they are done; then the call comes back. `yield from` works like that. Values the inner generator yields go straight out to the caller, values the caller sends go straight in to the inner generator, and when the inner one finishes, the outer one picks the call back up, with the inner one's return value in hand.

::: context stopiteration-value The value rides on StopIteration
You met `StopIteration` in the iterators lesson: it is how an iterator says "no more values". A `for` loop catches it quietly and ends. When a generator ends with `return something`, Python raises `StopIteration` with that value attached as its `.value`. A `for` loop throws the value away; `yield from` catches the `StopIteration` and uses `.value` as its result. So you almost never handle it yourself.
:::

::: context async-bridge Where this is going next
Before Python had `async` and `await`, programs that did many things at once (waiting on many network connections, for example) were written with generators: each task was a generator that paused with `yield` while it waited, and `yield from` let one task wait on another. That style became so common that Python 3.5 gave it its own keywords. `await` works much like `yield from`, in a clearer form, and you will use it in the next lesson.
:::

::: context string-forever Why strings recurse forever
Loop over `"ab"` and you get `"a"` and `"b"`. Loop over `"a"` and you get `"a"` again: a one-letter string contains exactly itself. So a flatten that says "if it can be looped over, go inside" goes into `"a"`, finds `"a"`, goes inside again, and never reaches the bottom. Python stops it after about a thousand nested calls with `RecursionError`. Lists always get smaller as you go inside them; strings do not.
:::

=== py4-05 | asyncio: concurrency with async and await
--- teach
Last lesson a generator learned to pause at `yield`, take a value from `send`, and carry on later. This lesson uses that same pause-and-resume trick for something very practical: doing lots of **waiting** at once.

Picture one cook making dinner. She puts the pasta on to boil. She does not stand and stare at the pot for ten minutes. She chops the salad while the water heats, and goes back to the pot when it is ready. One cook, several dishes on the go, and nobody standing idle.

Programs spend a surprising amount of time [[waiting|why-programs-wait]]: for a reply from another computer, for a database, for a timer. Python's `asyncio` module lets one [[thread|what-a-thread-is]] (one cook) start many waits and deal with whichever finishes first, instead of finishing each wait before starting the next.

That is called **concurrency**: juggling several tasks, switching between them while each one waits. It is not **parallelism**, which means doing several computations at the very same instant on several processors. The cook is concurrent, not parallel: she only ever does one thing at a time, but she never wastes the waiting.

## Step 1: `async def` makes a coroutine

Put `async` in front of `def` and you get a **coroutine function**: a function that is allowed to pause while it waits.

```python
import asyncio

async def fetch(name, delay):
    await asyncio.sleep(delay)      # pretend this is a network call
    return f"{name} ready"
```

`asyncio.sleep(delay)` waits `delay` seconds without blocking anything else. It is our stand-in for "wait for a reply from somewhere".

Here is the surprise. Calling `fetch("a", 1)` does **not** run the function. It hands back a **[[coroutine|where-coroutine-comes-from]] object**, a paused function that has not started yet (just like calling a generator function gives you a generator that has not run yet):

```python
c = fetch("a", 1)
type(c).__name__     # 'coroutine'   nothing has run yet
```

## Step 2: `await` runs it

To actually run a coroutine and get its result, you **`await`** it. The word means "run this, and while it is waiting, let other tasks have a turn":

```python
a = await fetch("a", 1)     # a is now 'a ready'
```

Who hands out the turns? The **[[event loop|the-event-loop]]**: the part of `asyncio` that keeps a list of paused tasks and wakes each one up when the thing it was waiting for is done.

Two rules about `await`:

- It only works inside an `async def` function.
- Or at the top level of a program, in environments that allow it. This editor does, so the code at the bottom of the task can say `await` directly.

## Step 3: one at a time, or all at once

Awaiting one coroutine after another is still one at a time. The second wait does not start until the first has finished:

```python
a = await fetch("a", 1)     # 1 second
b = await fetch("b", 1)     # another second: about 2 seconds in total
```

**`asyncio.gather`** starts all the coroutines you give it, lets them wait **side by side**, and hands back all their results once every one has finished:

```python
a, b = await asyncio.gather(fetch("a", 1), fetch("b", 1))   # about 1 second in total
```

The results come back **in the order you passed them in**, not the order they finished. So this list starts with the slow one, even though the fast one was done first:

```python
await asyncio.gather(fetch("slow", 0.3), fetch("fast", 0.1))
# ['slow ready', 'fast ready']
```

The [[saving in time|picture-of-the-saving]] is the whole point: two one-second waits take about one second, not two.

## Step 4: gather a whole list

Often the jobs arrive as a list. `gather` wants each coroutine as a separate argument, so you build them with a generator expression and **spread** them with `*`, the star you met in the `*args` lesson ("take these items and pass each one as its own argument"):

```python
jobs = [("x", 0.2), ("y", 0.1)]
await asyncio.gather(*(fetch(name, delay) for name, delay in jobs))
# ['x ready', 'y ready']
```

Read the inside first: for each `(name, delay)` pair, make the coroutine `fetch(name, delay)`. The `*` then passes them all to `gather`.

## Step 5: a queue and a fixed number of workers

`gather` starts **everything** at once. Sometimes that is too many: a thousand downloads at the same moment might overload the other computer. Then you want "at most `n` jobs running at a time".

Picture a restaurant: order tickets pile up on a counter, and three cooks each take the next ticket as soon as their hands are free. In `asyncio` the counter is an **`asyncio.Queue`**, a line of items waiting to be handled, first in, first out. The cooks are **worker tasks**.

The pieces, one at a time:

- `queue.put(item)` adds an item to the back of the line. You `await` it.
- `queue.get()` takes the item at the front. If the line is empty, it waits until something arrives. You `await` it too.
- `queue.task_done()` tells the queue "I have finished the item I took".
- `queue.join()` waits until every item that was put in has been marked `task_done()`.
- `asyncio.create_task(coro)` starts a coroutine running as a separate **task**, right away, without waiting for it. It gives you back the task so you can stop it later.
- `task.cancel()` stops a task.

Put together (here `handle` stands for whatever slow work each item needs):

```python
async def worker(queue, results):
    while True:                        # a worker never stops by itself
        item = await queue.get()       # take the next ticket (or wait for one)
        try:
            results.append(await handle(item))
        finally:
            queue.task_done()          # tell the queue this item is finished

async def run(items, n):
    queue = asyncio.Queue()
    results = []
    workers = [asyncio.create_task(worker(queue, results)) for _ in range(n)]
    for item in items:
        await queue.put(item)          # the producer fills the queue
    await queue.join()                 # wait until every item is task_done
    for w in workers:
        w.cancel()                     # the workers loop forever; stop them
    return results
```

The code that fills the queue is the **producer**; the workers are **consumers**. `task_done()` sits in a `finally` (the clean-up block from the exceptions lesson) so it runs even if `handle` raises an error. With 6 items that each take 0.1 seconds and 3 workers, the whole thing takes about 0.2 seconds: two rounds of three.

Notice that the results come back in the order the workers *finished*, which may not match the order of `items`. If order matters, sort them afterwards.

**Watch out** for three mistakes:

- Forgetting `await`. You get a coroutine object and a warning ("coroutine was never awaited"), not a result.
- Calling `time.sleep` inside a coroutine. It freezes **everything**, because while the one thread sleeps, the event loop cannot give anyone else a turn. Use `await asyncio.sleep` instead.
- Forgetting `task_done()`. Then `queue.join()` waits forever for items that already finished.

This machinery is how real programs talk to many things at once; see [[where engineers use it|asyncio-in-real-life]]. And it did not appear from nowhere: it [[grew out of generators|history-of-async]] like the ones from last lesson.

::: context why-programs-wait Why a program waits so much
A computer adds numbers in billionths of a second. A message to a server on another continent and back takes tens of milliseconds, and a slow database query can take much longer. To the processor, that reply takes forever: millions of steps it could have done in the meantime. So a program that talks to a network spends most of its life waiting, not computing. That waiting is what `asyncio` fills with useful work.
:::

::: context what-a-thread-is One line of work
A **thread** is one line of work inside a running program: one "cook" following the instructions step by step. A program can have several threads, but `asyncio` normally uses just one. It gets its speed not from more cooks but from never letting the one cook stand idle. That also makes it simpler to reason about: two tasks never change the same variable at the very same instant, because only one of them runs at a time.
:::

::: context where-coroutine-comes-from Where the word comes from
"Coroutine" was coined by the computer scientist Melvin Conway in the late 1950s. A normal subroutine is called, runs to the end and returns. Co-routines take turns as equals: each runs a while, pauses, and lets another continue from where it stopped. That is exactly what a Python generator does at `yield`, and what a coroutine does at `await`.
:::

::: context the-event-loop The traffic controller
The event loop is a loop inside `asyncio` that repeats one job: "which paused tasks are ready to go on?" A task that reaches `await asyncio.sleep(1)` tells the loop "wake me in a second" and pauses. The loop runs another ready task in the meantime. When the second is up, it resumes the first one right after its `await`. It is the same pause-and-resume you saw with `send` last lesson, driven by the loop instead of by you.
:::

::: context picture-of-the-saving Two timelines side by side
With plain `await`, each wait starts only when the one before has ended, so the total is the sum of the waits. With `gather`, all the waits start together, so the total is only as long as the longest one.

::: context asyncio-in-real-life Where engineers use it
Anything that talks to many other machines at once is a good fit: a web server answering thousands of visitors, a scraper downloading pages, a ground-station tool polling many sensors or radios. Popular Python web frameworks such as FastAPI are built on it. The queue-and-workers pattern shows up whenever you must limit how many requests hit a service at once. === py4-06 | heapq and bisect: the right structure for speed
--- teach
In the Big-O lesson you learned that the right data structure can turn "never finishes" into "instant". Last lesson was about waiting less. This one is about *working* less, with two small standard-library modules.

Some questions come up again and again while a program runs:

- "What is the smallest item right now?"
- "Where does this value belong in sorted order?"

You could sort the list every time you ask. But sorting costs [[O(n log n)|cost-of-sorting]], and paying that on every question adds up fast. `heapq` answers the first question cheaply, and `bisect` answers the second.

## `heapq`: the smallest item, always on top

Picture a sports tournament bracket, upside down. The winner (the smallest number) always sits at the very top. Below it, each item only has to be smaller than the two items under it. Nobody cares about the order between cousins.

That shape is a **[[heap|how-a-heap-sits-in-a-list]]**: a list kept in a special *partial* order where `heap[0]` is always the smallest item. You never arrange it yourself; the `heapq` functions do it for you.

- `heapq.heappush(h, x)` adds `x` and keeps the heap order.
- `heapq.heappop(h)` removes and returns the smallest item.

Both cost only O(log n), because each only repairs one path from top to bottom.

```python
import heapq
h = []
for x in [5, 1, 8, 3]:
    heapq.heappush(h, x)
h                       # [1, 3, 8, 5]   partly ordered, not sorted
h[0]                    # 1   the smallest, without sorting
heapq.heappop(h)        # 1   removes and returns it
heapq.heappop(h)        # 3   the next smallest moves to the top
```

Two ready-made helpers are worth knowing:

```python
heapq.nlargest(2, [5, 1, 8, 3, 9])        # [9, 8]   largest first
list(heapq.merge([1, 4, 9], [2, 3, 10]))  # [1, 2, 3, 4, 9, 10]
```

`nlargest(k, items)` gives the `k` biggest, biggest first. `merge` joins lists that are **already sorted** into one sorted stream.

## Largest on top instead: negate

`heapq` only builds **min-heaps** (smallest on top). For a **max-heap** (largest on top), push each number [[negated|why-negating-works]], with a minus sign, and put the minus sign back when you take it out:

```python
m = []
for x in [5, 1, 8]:
    heapq.heappush(m, -x)      # stores -5, -1, -8
-m[0]                          # 8   the largest
```

## Items with a priority

Heap items can be tuples such as `(priority, item)`. Tuples [[compare by their first element first|how-tuples-compare]], so the lowest priority number comes out first. That makes a heap a **[[priority queue|priority-queues-in-real-code]]**: a to-do list that always hands you the most urgent job.

```python
todo = []
heapq.heappush(todo, (2, "wash"))
heapq.heappush(todo, (1, "launch"))
heapq.heappush(todo, (3, "sleep"))
heapq.heappop(todo)            # (1, 'launch')
```

## Two heaps make a running median

The **[[median|what-a-median-is]]** is the middle value once the numbers are sorted: of 1, 3, 5 it is 3. With an even count there are two middle values, and the median is halfway between them: of 1, 3, 5, 15 it is (3 + 5) / 2 = 4.0.

Suppose numbers arrive one at a time and you need the median after each. Re-sorting every time is slow. Instead, split the numbers into two halves:

- `low` holds the **smaller half**, as a max-heap (stored negated), so its biggest is on top.
- `high` holds the **larger half**, as a min-heap, so its smallest is on top.

Keep two promises: every number in `low` is no bigger than any number in `high`, and `low` has the same size as `high` or one more. Then the middle of everything sits at the two tops:

- If `low` has one more item, the median is the top of `low`.
- If they are the same size, the median is halfway between the two tops.

Watch it with 5, 15, 1, 3 arriving:

| after adding | `low` (smaller half) | `high` (larger half) | median |
|---|---|---|---|
| 5 | 5 | (empty) | 5 |
| 15 | 5 | 15 | 10.0 |
| 1 | 1, 5 | 15 | 5 |
| 3 | 1, 3 | 5, 15 | 4.0 |

When 3 arrived, it went into `low`, which then had one too many, so its biggest (5) moved over to `high`. Each new number costs O(log n), instead of a whole re-sort.

## `bisect`: positions in a sorted list

In the advanced course you wrote `first_at_least` by hand with [[binary search|binary-search-again]]. The `bisect` module is that same function, built in. The list must already be sorted.

- `bisect.bisect_left(a, x)` gives the first index whose value is at least `x`.
- `bisect.bisect_right(a, x)` gives the index just **past** any values equal to `x`.

They only differ when `x` is already in the list:

```python
import bisect
bisect.bisect_left([10, 20, 30], 20)     # 1   the position of the 20
bisect.bisect_right([10, 20, 30], 20)    # 2   just after the 20
bisect.bisect_left([10, 20, 30], 25)     # 2   25 would go between 20 and 30
```

`bisect.insort(a, x)` inserts `x` into the list in its sorted place:

```python
a = [10, 20, 30]
bisect.insort(a, 25)
a                                        # [10, 20, 25, 30]
```

## Sorting a number into bands

A classic use is putting a number into a band without a long `if`/`elif` chain. List the **breakpoints** (where one band ends and the next begins), and one label per band. There is always one more label than breakpoints:

```python
breakpoints = [18.5, 25, 30]
labels = ["under", "normal", "over", "obese"]
labels[bisect.bisect_right(breakpoints, 22.0)]   # 'normal'
labels[bisect.bisect_right(breakpoints, 25)]     # 'over'
```

`bisect_right` counts how many breakpoints are less than or equal to the value: 22.0 is past one breakpoint, so it gets label 1. A value exactly on a breakpoint (25) counts as past it, so it lands in the higher band. That is why `bisect_right` is the right choice here.

**Watch out:** do not read `h[1]` as "the second smallest". A heap is only partly ordered. Push 1, 4, 2, 3 and the list is `[1, 3, 2, 4]`: `h[1]` is 3, but the second smallest is 2. Only `h[0]` means something; to get the next one, `heappop`.

::: context cost-of-sorting The price of one sort
From the Big-O lesson: sorting n items takes about n × log n steps. For a million items that is roughly twenty million steps, a noticeable fraction of a second in Python. Once is fine. After every one of a hundred thousand new numbers, it becomes hours. A heap pays about log n per push or pop instead, which is around 20 steps for a million items.
:::

::: context how-a-heap-sits-in-a-list A tree hiding in a list
A heap is a tree stored in an ordinary list. The item at index `i` has its two children at indexes `2*i + 1` and `2*i + 2`. The only rule is that every parent is no bigger than its children. The heap `[1, 3, 8, 5]` looks like this:

A push adds the item at the end and swaps it upward past any bigger parent. A pop moves the last item to the top and swaps it downward. Each walks one path, at most about log n levels.
:::

::: context why-negating-works Flipping the order with a minus sign
A minus sign turns the order upside down: 8 is bigger than 5, but -8 is smaller than -5. So the smallest stored value, -8, is the negated largest original. The min-heap keeps -8 on top, and putting the minus back gives you 8. It is a little trick, but it is the standard way to get a max-heap in Python.
:::

::: context how-tuples-compare First element first
Python compares tuples the way a dictionary orders words: look at the first elements; only if they are equal, look at the second, and so on. So `(1, "launch")` comes before `(2, "wash")` whatever the words say. If two priorities tie, the second elements get compared, and if those cannot be compared (two dicts, say) you get a `TypeError`. The usual fix is a middle element that always differs, such as a counter: `(priority, count, item)`.
:::

::: context priority-queues-in-real-code Where priority queues work
Operating systems use them to decide which job runs next. Simulations use them to pull out the next event in time order. Route finders use them to explore the closest place first: you will use exactly this in the Dijkstra shortest-path lesson later in this course, where the heap holds `(distance, place)` pairs.
:::

::: context what-a-median-is Why the middle, not the average
The median is the value in the middle once everything is sorted. Unlike the average, one wild value barely moves it: for 1, 3, 5, 1000 the average is 252.25, but the median is 4.0. That makes it a favourite for noisy sensor readings, where one glitch should not drag the answer far off.
:::

::: context binary-search-again The same search, built in
`bisect_left(a, x)` answers the same question as the `first_at_least(nums, target)` you wrote: the first position whose value is at least `x`, found by halving the range each step, in O(log n). Knowing how it works inside is what lets you trust it and pick the right one of `bisect_left` and `bisect_right` for a job.
:::

--- solution
import bisect
import heapq


def k_largest(nums, k):
    return heapq.nlargest(k, nums)


class RunningMedian:
    def __init__(self):
        self.low = []    # max-heap of the smaller half, stored negated
        self.high = []   # min-heap of the larger half

    def add(self, x):
        if self.low and x > -self.low[0]:
            heapq.heappush(self.high, x)
        else:
            heapq.heappush(self.low, -x)
        if len(self.low) > len(self.high) + 1:
            heapq.heappush(self.high, -heapq.heappop(self.low))
        elif len(self.high) > len(self.low):
            heapq.heappush(self.low, -heapq.heappop(self.high))

    def median(self):
        if not self.low:
            raise ValueError("no values yet")
        if len(self.low) > len(self.high):
            return -self.low[0]
        return (-self.low[0] + self.high[0]) / 2


def grade(score):
    return "FDCBA"[bisect.bisect_right([60, 70, 80, 90], score)]

--- hint

=== py4-07 | Typing: Protocols and generics
--- teach
Last lesson picked the right data structure for speed. This one is about making code easier for *people* (and tools) to understand, by writing down what kind of value each part expects.

Picture the labels on a box of parts: "M3 screws, 10 mm". Nobody checks the label when you put the box on the shelf. But the label tells the next person what belongs inside, and a sharp-eyed helper can spot a bolt in the screw box straight away.

## Step 1: type hints

A **type hint** is that label, written in the code. After a parameter you write a colon and its type. After the brackets you write `->` ("returns") and the type of the result:

```python
def mean(values: list[float]) -> float:
    return sum(values) / len(values)

mean([1.0, 2.0, 4.5])     # 2.5
```

Read it aloud: "`mean` takes `values`, a list of floats, and returns a float."

Python itself does **not** enforce hints at [[run time|two-moments-in-a-programs-life]]. This still runs, and only fails inside the function:

```python
def shout(text: str) -> str:
    return text.upper() + "!"

shout(42)     # AttributeError: 'int' object has no attribute 'upper'
```

So who reads the hints? A **[[type checker|type-checkers]]** such as mypy or pyright reads your code *without running it* and complains that `42` is not a `str`, before the bug ever runs. Editors use the same hints to suggest method names as you type. In a big codebase, hints are documentation that cannot quietly go out of date, because the checker complains when they stop matching the code.

A function that returns nothing gets `-> None`. That includes `__init__`.

## Step 2: hints that ask for as little as possible

Sometimes a function does not need a list exactly. The `typing` module has names for "anything that behaves like...":

- **`Iterable[X]`**: anything you can loop over with `for` that gives `X`s: a list, tuple, set, generator.
- **`Sequence[X]`**: anything with a length that you can index with `[0]`: a list, tuple, or string.

```python
from typing import Iterable, Sequence

def total(xs: Iterable[float]) -> float:
    return sum(xs)                # only loops, so any iterable will do

def last(xs: Sequence[str]) -> str:
    return xs[-1]                 # needs indexing, so it asks for a Sequence

last("xyz")                       # 'z'   a string is a sequence of strings
```

Ask for [[the least you need|ask-for-the-least]]: if a function only loops, `Iterable` lets callers pass a generator too.

## Step 3: Protocols, typing by behaviour

Python has always worked by **[[duck typing|where-duck-typing-comes-from]]**: if an object has an `area()` method, you can ask for its area. You never ask what class it is.

A **Protocol** puts that idea into the type system. It is a class that only lists the methods something must have. **Any** class with those methods matches it, without inheriting from it:

```python
from typing import Protocol, runtime_checkable

@runtime_checkable
class Closeable(Protocol):
    def close(self) -> None: ...

class File:
    def close(self) -> None:
        print("closed")

isinstance(File(), Closeable)   # True, though File never mentions Closeable
```

Line by line:

- `class Closeable(Protocol):` says "this is a protocol, a list of required methods".
- `def close(self) -> None: ...` lists one method. The body is [[three dots|the-ellipsis]], which means "nothing here, this is only a description".
- `@runtime_checkable` is a decorator that makes `isinstance` work with the protocol.

Matching by shape like this is called **[[structural typing|matching-by-shape]]**. `isinstance` at run time is only a rough check: it looks at whether the methods **exist**, not at their parameters. A class with `def close(self, loudly):` would still count as `Closeable`. The type checker is the one that checks the details.

## Step 4: generics, one class for many types

A stack of ints and a stack of strings are the same code. You want to say "a stack of *something*, and whatever goes in is what comes out". A **[[type variable|naming-type-variables]]** is that "something": a stand-in type that must be the same everywhere it appears.

```python
from typing import Generic, TypeVar
T = TypeVar("T")

class Box(Generic[T]):
    def __init__(self, item: T) -> None:
        self.item = item
    def get(self) -> T:
        return self.item

b: Box[int] = Box(3)
b.get()          # 3   and the checker knows it is an int
```

`class Box(Generic[T])` makes a **generic class**: a class with a type slot. `Box[int]` is "a box of ints", `Box[str]` "a box of strings", all from one class. A function can use `T` too:

```python
def first(items: list[T]) -> T:      # returns the same type the list holds
    return items[0]
```

To label an attribute that starts empty, write the hint on the assignment: `self.items: list[T] = []`.

(From Python 3.12 you can also write `class Box[T]:` and `def first[T](items: list[T]) -> T:` without the `TypeVar` line. The `TypeVar` form works on every recent version.)

Hints are ordinary Python objects you can look at while the program runs. `typing.get_type_hints(first)` returns them as a dict:

```python
from typing import get_type_hints
get_type_hints(mean)     # {'values': list[float], 'return': <class 'float'>}
```

**Watch out** for two mistakes:

- Making a class *inherit* from a protocol "to be safe". That defeats the point: protocols exist so unrelated classes match by shape alone.
- Treating a hint as a check. It is a label, not a guard. If you need to reject bad values while the program runs, write that check yourself.

::: context two-moments-in-a-programs-life Check time and run time
"Run time" means while the program is actually running. A type checker works at a different moment: before running, by reading the source code, much like a spell-checker reads an essay without acting it out. Python only looks at hints at run time if you ask it to, for example with `get_type_hints` or a library built on them. That is why a wrong type only blows up when the bad line runs, unless a checker caught it earlier.
:::

::: context type-checkers The tools that read the labels
mypy was started by Jukka Lehtosalo around 2012, and Python 3.5 (2015) made hint syntax standard. pyright is Microsoft's checker and powers type hints in VS Code. You run one like any other tool, for example `mypy myfile.py`, and it lists every line where the labels do not fit. Large codebases, such as Dropbox's millions of lines of Python, adopted hints step by step so the checker could catch mistakes before they reached users.
:::

::: context ask-for-the-least Be generous in what you accept
If `total` asked for `list[float]`, a caller holding a tuple or a generator would have to copy it into a list first, just to satisfy the label. Asking for `Iterable[float]` says honestly what the function needs: "something I can loop over". The same thinking makes functions easier to reuse and to test. Be exact in what you return, though, so callers know what they get.
:::

::: context where-duck-typing-comes-from If it quacks like a duck
The name comes from the old saying: "If it walks like a duck and quacks like a duck, then it is probably a duck." Python does not ask an object what it *is*; it tries what it *does*. `len()` works on anything with a `__len__` method, and a `for` loop works on anything with `__iter__`, as you saw in the special-methods lesson.
:::

::: context the-ellipsis Three dots that mean "nothing here"
`...` is a real Python value, called `Ellipsis`. As the body of a function it does nothing, like `pass`, but it reads as "left out on purpose". In a protocol the method never runs; it is only a description of what matching classes must have, so a body with real code in it would be pointless.
:::

::: context matching-by-shape Fits the shape, no family tree needed
With inheritance, a class matches a type only if it says so: `class Square(Shape)`. With a protocol, a class matches if it has the right methods, whatever its family.

When a function needs two independent type slots, people often use `K` and `V` for the keys and values of a dict, or `T` and `U`. `TypeVar("T")` must be given the same name as the variable it is stored in, so the checker can report it by name.

import math
from typing import Generic, Iterable, Protocol, Sequence, TypeVar, runtime_checkable

T = TypeVar("T")


@runtime_checkable
class HasArea(Protocol):
    def area(self) -> float: ...


class Square:
    def __init__(self, side: float) -> None:
        self.side = side

    def area(self) -> float:
        return self.side * self.side


class Circle:
    def __init__(self, radius: float) -> None:
        self.radius = radius

    def area(self) -> float:
        return math.pi * self.radius ** 2


def total_area(shapes: Iterable[HasArea]) -> float:
    return sum(shape.area() for shape in shapes)


class Stack(Generic[T]):
    def __init__(self) -> None:
        self._items: list[T] = []

    def push(self, item: T) -> None:
        self._items.append(item)

    def pop(self) -> T:
        if not self._items:
            raise IndexError("pop from empty stack")
        return self._items.pop()

    def peek(self) -> T:
        if not self._items:
            raise IndexError("peek at empty stack")
        return self._items[-1]

    def __len__(self) -> int:
        return len(self._items)


def first(items: Sequence[T], default: T) -> T:
    return items[0] if items else default

--- hint

=== py4-08 | Testing: write the test that catches the bug
--- teach
Last lesson you labelled code so a checker could catch type mistakes. But a checker cannot tell you whether the *answer* is right: `2 + 2` returning `5` is a perfectly good `int`. For that you need tests.

A **test** is a small program that checks another program. Picture a smoke alarm. Its whole job is to go off when there is a fire. An alarm that stays quiet during a fire is worse than no alarm at all, because you trust it and go back to sleep.

Tests are the same. The valuable ones **fail when the code is wrong**. A test that passes on buggy code gives you confidence you have not earned.

## Step 1: `assert`

The tool for checking is the **[[assert statement|assert-in-real-code]]**, written `assert condition, message`. If the condition is true, nothing happens. If it is false, Python raises `AssertionError`, with your message:

```python
assert 2 + 2 == 4                      # true: nothing happens
assert 2 + 2 == 5, "maths is broken"   # AssertionError: maths is broken
```

The message is optional; it helps you see which check failed.

## Step 2: the shape of a test

A test has three parts, called **arrange, act, assert**:

- **arrange**: set up the input;
- **act**: call the code you are testing;
- **assert**: compare what came back with what it should be.

For small functions all three fit on one line:

```python
def test_slugify():
    assert slugify("Hello, World") == "hello-world"   # arrange, act, assert
    assert slugify("") == ""
```

Test runners such as **[[pytest|how-pytest-finds-tests]]** find every function whose name starts with `test_`, run it, and report each one that raised an `AssertionError`.

## Step 3: choosing the cases

Do not pick random examples. Pick the cases that *break* wrong code. Start from the **specification**, the exact rule the code is meant to follow, and go through this list:

- **Each rule** in the specification gets a case that only passes if that rule is implemented.
- **Boundaries**: a value exactly at a limit, and one just either side of it. [[Off-by-one|off-by-one-bugs]] bugs live there.
- **Exceptions to the rule, and [[exceptions to the exceptions|why-leap-years-are-odd]].** The leap-year rule in the task is full of them.
- **Both outcomes**: if a function answers yes or no, test some yeses *and* some nos. A test that only ever expects `True` cannot catch a function that always returns `True`.
- **Degenerate inputs**: the smallest, emptiest cases: empty, zero, one element, negative.

Here is one rule, "orders of 50 or more ship free", tested at its boundary and with both outcomes:

```python
def test_free_shipping(free_shipping):
    assert free_shipping(49.99) is False   # just under the limit
    assert free_shipping(50) is True       # exactly at the limit
    assert free_shipping(80) is True       # well over it
```

A buggy version written with `>` instead of `>=` fails on `50`. A version that always says `True` fails on `49.99`.

Notice `is True` and `is False` rather than a bare `assert free_shipping(50)`. A bare `assert` accepts anything truthy, such as `1` or `"yes"`, and even `== True` lets `1` through, because `1 == True` in Python. Writing `is True` is an [[exact check|why-is-true]]: it demands the real `True`.

## Step 4: imagine the bugs

A useful habit: before writing cases, **imagine the likely bugs**. "What if someone forgets this rule? Uses `>` instead of `>=`? Always returns `True`?" Then make sure at least one case catches each one.

Professionals check their tests exactly like this, on purpose. They make small deliberate breaks in the code and see whether any test notices. That is called **[[mutation testing|mutation-testing]]**.

## Step 5: here, the test takes the code as a parameter

Normally a test calls a function by its name. In this lesson, your test receives the function to check as a [[parameter|passing-the-code-in]]. That lets the checker call your test several times, with a correct version and with broken ones:

```python
def test_absolute(absolute):
    assert absolute(5) == 5       # catches "return -x"
    assert absolute(-5) == 5      # catches "return x"
    assert absolute(0) == 0       # the boundary between the two cases
```

Called with Python's own `abs`, it passes. Called with `lambda x: -x` or `lambda x: x`, it raises `AssertionError`, which is exactly what a good test should do.

**Watch out** for three mistakes:

- Working out the expected answer with the same logic as the code under test. If the logic is wrong, both are wrong together and the test still passes. Write the expected answer out by hand.
- Asserting on too little: one happy example, and no boundary or "no" case.
- Tests that depend on each other's order or share changing data. Each test should work on its own.

::: context assert-in-real-code A statement that can be switched off
`assert` is a statement, not a function, so do not put brackets round the whole thing: `assert (x, "msg")` asserts a tuple, which is always truthy, and never fails. Running Python with the `-O` flag ("optimise") removes every `assert`. That is why real programs never use `assert` to check user input, and use `if` plus `raise` instead. In tests, `assert` is exactly right.
:::

::: context how-pytest-finds-tests How a test runner works
pytest is the most widely used test runner for Python. Run `pytest` in a folder and it looks for files named `test_*.py`, then for functions named `test_*` inside them, and calls each one. A test passes if it returns without an error. At the end you get a summary, and for each failure pytest shows the exact values on both sides of the `==` that went wrong.
:::

::: context off-by-one-bugs The fence-post mistake
How many posts does a 10-metre fence need with one every metre? Eleven, not ten. Off-by-one bugs are that mistake in code: `<` where it should be `<=`, `range(n)` where it should be `range(n + 1)`. The code is right almost everywhere and wrong exactly at the edge, which is why a random example rarely catches it and a boundary case does.
:::

::: context why-leap-years-are-odd Why the leap-year rule has exceptions
A year (from one spring to the next) is about 365.2422 days long. Adding a leap day every 4 years makes the average 365.25, a little too long, so the calendar slowly drifts. The Gregorian calendar, introduced in 1582, fixes that by skipping the leap day in century years, except those divisible by 400. That averages 365.2425 days.

::: context why-is-true True, and nothing else
In Python, `True == 1` is true, because `True` behaves like the number 1 in arithmetic. So a function that returns `1` passes both `assert f(x)` and `assert f(x) == True`. `is True` asks "is this the very same object as `True`?", and only `True` itself passes. When a function promises to return `True` or `False`, test that promise exactly.
:::

::: context mutation-testing Testing the tests
A mutation-testing tool (for Python, `mutmut` is one) makes many small changes to your code, one at a time: `>` becomes `>=`, `+` becomes `-`, a condition is flipped. Each changed copy is a "mutant". It runs your tests against every mutant. If no test fails, that mutant "survived", which means your tests could not tell the broken code from the real code. The checks in this lesson do the same thing by hand.
:::

::: context passing-the-code-in Handing a test its target
Passing the function in, instead of reaching for it by name, is a small case of **dependency injection**: giving code the things it depends on rather than letting it find them itself. It makes the test reusable with any implementation. The very next lesson, on design, uses the same idea for whole programs, so that the slow or risky parts can be swapped for simple stand-ins in tests.
:::

=== py4-09 | Design: pure logic, thin I/O, injected dependencies
--- teach
Last lesson you wrote tests that catch bugs. This lesson is about the other half of the job: writing code that is *easy* to test in the first place.

Think of a pocket calculator. You press keys and a number appears on the screen. But the chip inside that does the arithmetic does not care about keys or screens. It takes numbers in and hands a number back. A factory can test that chip by feeding it numbers down a wire, with nobody pressing anything. Good programs are built the same way.

### The problem: logic tangled with input and output

Look at almost any hard-to-test program and you find the same problem: the **logic is tangled with the input and output**. The function that decides *what* should happen also reads the keyboard, prints, sends email or looks at the clock. **Input and output** (people say **I/O**) means everything a program takes in from the outside world or sends back out to it.

```python
def check_temperature():
    reading = float(input())      # reads the keyboard
    if reading > 90:
        print("too hot")          # writes to the screen
```

To test this, you would have to type a number and then read the screen. The decision (is it above 90?) is trapped between the reading and the printing.

### Step 1: a pure function

A **pure function** takes data in and returns data out, and does nothing else. Same input, same output, every time. Anything else a function does (printing, reading input, changing a variable outside itself, looking at the clock) is called a **[[side effect|side-effect]]**.

Pull the decision out into a pure function:

```python
def too_hot(reading):
    return reading > 90

too_hot(95)     # True
too_hot(20)     # False
```

Now a test is one line: `assert too_hot(95) is True`. No typing, no screen.

### Step 2: a pure core inside a thin shell

Do that for all the logic, and the program splits into two layers. This design is sometimes called **[[functional core, imperative shell|core-and-shell]]**:

- A **pure core**: functions that take data and return data. No `input()`, no `print()`, no global state, no clock. Same input, same output, every time. Very easy to test.
- A **thin shell**: a small layer that reads input, calls the core, and writes output. It has almost no logic, so it barely needs testing.

### Step 3: hand the function its tools

The shell still has to *do* something with the results: print them, or send an email. How can you test the part that does that without actually printing or emailing?

Picture a plumber who brings her own wrench versus one who is handed a wrench at the door. Hand her a toy wrench and you can watch what she does without flooding the kitchen. **Dependency injection** means the same thing for code: instead of reaching out for `print` or the clock itself, a function *receives* them as parameters. A **dependency** is anything a function relies on from outside itself.

This works because in Python [[a function is a value|functions-are-values]], like a number or a list. You can pass `print` into another function, and it calls whatever it was given:

```python
def run(lines, notify):
    for line in lines:
        if "ERROR" in line:
            notify(f"alert: {line}")

run(["ok", "ERROR disk full"], print)       # the real program: prints alert: ERROR disk full
sent = []
run(["ok", "ERROR disk full"], sent.append) # a test: collect what would be sent
sent                                        # ['alert: ERROR disk full']
```

In the test, `sent.append` stands in for `print`. It is a **[[fake|test-doubles]]**: a stand-in that records what happened instead of doing it for real. `run` cannot tell the difference, and it does not need to.

The same goes for time. Reading [[the clock|injected-time]] inside a function is a hidden input:

```python
from datetime import date

def is_overdue(due, today):
    return today > due

is_overdue(date(2026, 1, 10), date(2026, 1, 11))    # True
```

(`date` comes from the standard library's `datetime` module; `date(2026, 1, 10)` is the 10th of January 2026.) Written like this, `is_overdue(due, today)` is testable for any date. A version `is_overdue(due)` that calls `date.today()` inside is only testable today.

### Step 4: reading input

A program reads what the user types, or what a pipe sends in, from **[[standard input|standard-streams]]**: in this editor, that is the Input box under your code. There are two ways to read it:

- `input()` reads **one line** and returns it without the newline at the end.
- `sys.stdin.read()` reads **all of it at once** as one string. You need `import sys` at the top first; `sys` is the standard library module for talking to the system Python runs on.

Then `.splitlines()` turns that one string into a list of lines. If the Input box holds two lines, `widget 3 10` and `gizmo 25 5`:

```python
import sys

lines = sys.stdin.read().splitlines()
lines       # ['widget 3 10', 'gizmo 25 5']
```

Only the shell reads input. The pure core is handed the lines as an ordinary list, which is why a test can hand it a list it made up.

### Step 5: the entry point

The **entry point** is where a program starts doing things when you run it. In Python it goes under this line:

```python
if __name__ == "__main__":
    run(sys.stdin.read().splitlines(), print)
```

Read it as "if this file is being run as a program". Python gives every file a [[hidden variable|dunder-name]] called `__name__`. That block runs when the file is executed as a program, but not when another file imports it to reuse (or test) the functions. So a test can import `run` without the program starting to read input.

**Watch out:** "injecting" by setting a global variable that the function reads, like `NOTIFY = print` at the top of the file and `NOTIFY(...)` inside the function. That still couples everything to [[one shared value|globals-couple]]. Pass it in as an argument instead.

::: context side-effect Side effects are not bad, only hard to test
"Side effect" sounds like something a medicine does wrong, but in programming it means anything a function does besides handing back a value: printing, writing a file, changing a list it was given, moving a motor. A program with no side effects at all would be useless, because nobody could see its answer. The point is not to avoid them. It is to push them to the edges, into a few short functions, so that the part that thinks never has any.
:::

::: context core-and-shell A core you test, a shell you can see through
"Imperative" means giving commands, like "print this" or "read that". "Functional" here means built from pure functions. The name was popularised by programmer Gary Bernhardt in a 2012 screencast. The shape is the calculator from the start of the lesson: data goes in through the shell, the core does all the deciding, and the shell sends the answer out.

::: context functions-are-values Passing print, not calling it
You met this in the decorators lesson: a function can be stored in a variable and handed to another function. The difference is the brackets. `print` with no brackets is the function itself, the tool. `print("hi")` *uses* the tool, right now. So `run(lines, print)` hands `run` the tool, and `run` decides when to use it. `sent.append` works the same way: it is the `append` method of that one list, not yet called.
:::

::: context test-doubles Crash-test dummies for code
Car makers do not test seat belts with real people. They use crash-test dummies that record every bump. Engineers call the code version a **test double**, and there are a few kinds: a *fake* does the job in a simpler way (a list instead of an email server), a *stub* returns fixed answers, and a *mock* checks that it was called in the right way. People mix the words up; what matters is that the real thing and the stand-in can be swapped because the function was handed its tools.
:::

::: context injected-time Flight software runs on a clock you can control
A clock is an input that changes every time you look at it, so a test that reads the real clock may pass today and fail tomorrow. Spacecraft teams meet this problem at full size. Before launch, flight software is run for hours or days in simulation, where the sensors and the clock are simulated too. That only works if the software asks for the time through something that can be swapped, instead of reading the hardware clock directly. Then a test can jump to "ten seconds before engine cutoff" whenever it likes.
:::

Every program starts with three streams already open: **standard input** (stdin), where it reads; **standard output** (stdout), where `print` writes; and **standard error** (stderr), for error messages. You met the other end in the Terminal course: a pipe such as `cat stock.txt | python3 stock.py` connects one program's stdout to the next one's stdin. In this editor, the Input box plays the part of stdin.

::: context dunder-name What Python puts in __name__
Before a file runs, Python sets a variable called `__name__` in it. When you run the file itself, the value is the string `"__main__"`, meaning "you are the main program". When another file imports it, for example with `import stock`, the value is the module's own name, `"stock"`, and the `if` block is skipped. Names with two underscores on each side are special names Python itself uses; programmers call them "dunder" names, short for "double underscore".

::: context globals-couple Why a global is not really injected
A global variable is one box that every function in the file can reach into. If a function reads `NOTIFY` from there, a test has to change that box before calling it and remember to put it back after. Forget, and the next test quietly uses the wrong tool. Two tests running at once would fight over the same box. An argument belongs to one call only, so each caller hands over its own tool and nothing leaks between them.
:::

import sys


def parse_stock(lines):
    items = []
    for line in lines:
        if not line.strip():
            continue
        name, stock, minimum = line.split()
        items.append((name, int(stock), int(minimum)))
    return items


def needs_reorder(items):
    return [item for item in items if item[1] < item[2]]


def format_alert(item):
    name, stock, minimum = item
    return f"REORDER {name}: {stock} left (minimum {minimum})"


def run(lines, notify):
    items = parse_stock(lines)
    low = needs_reorder(items)
    for item in low:
        notify(format_alert(item))
    notify(f"{len(low)} of {len(items)} items need reordering")
    return len(low)


if __name__ == "__main__":
    run(sys.stdin.read().splitlines(), print)

=== py4-10 | Debugging: floating-point surprises
--- teach
Last lesson you pulled logic out into pure functions so it could be tested. Sometimes a test of a pure function fails and the numbers themselves look impossible. This lesson is about that kind of bug.

Try these, and it looks like Python is broken:

```python
0.1 + 0.2            # 0.30000000000000004
0.1 + 0.2 == 0.3     # False
round(2.675, 2)      # 2.67, not 2.68
```

It is not a bug. It is how floats work in every language.

### Why it happens

Write 1/3 as a decimal and you get 0.3333… forever. You have to stop somewhere, so what you write down is a tiny bit wrong. Computers have the same problem, in a different place.

A `float` stores numbers in **[[binary|binary-fractions]]**: base two, using only the digits 0 and 1. Most decimal fractions, including 0.1, have no exact binary form, the same way 1/3 has no exact decimal form. So each float is **the [[nearest representable value|nearest-float]]**: the closest number the computer *can* store. Tiny errors appear, and they grow when you add many of them up. `2.675` is actually stored as `2.67499999...`, which is why it rounds down.

### Diagnose it

When a comparison of computed numbers fails "impossibly", look at more digits. Print with `repr()` (the exact form Python would type back to you) or with many digits, `f"{x:.20f}"`, where `.20f` means "20 digits after the point":

```python
print(f"{2.675:.20f}")     # 2.67499999999999982236
print(repr(0.1 + 0.2))     # 0.30000000000000004
```

If you see `...0000004` or `...9999998` at the end, it is floating point. This matters for real: a [[tiny error in a tenth of a second|patriot-clock]] has cost lives.

### Fix 1: measurements, compare with a tolerance

For **measurements and science** (lengths, sensor readings, physics), floats are the right tool. But never compare them with `==`. Compare with a **[[tolerance|tolerance]]**: an amount of difference you agree to ignore.

`math.isclose(a, b)` does that. By default it uses a **relative tolerance** of `1e-9` (read "one times ten to the minus nine", 0.000000001): the two numbers may differ by up to a billionth of their size.

```python
import math
math.isclose(0.1 + 0.2, 0.3)                       # True (relative tolerance 1e-9)
math.isclose(1e-12, 0.0)                           # False
math.isclose(1e-12, 0.0, abs_tol=1e-9)             # True: near zero you need abs_tol
```

A billionth of zero is zero. So a relative tolerance alone never considers anything "close" to exactly 0. When zero is a possible answer, also give an **absolute tolerance**, `abs_tol=`: a fixed amount of difference that is always allowed. You can set the relative one yourself too, with `rel_tol=`. The numbers count as close if they pass either one.

### Fix 2: money, use Decimal

For **money**, never use floats. A bank balance that is off by a millionth of a cent will, sooner or later, round the wrong way. Use `decimal.Decimal` instead, a number type that works in [[base ten, like people do|decimal-module]]. Create it **from strings**:

```python
from decimal import Decimal
Decimal("0.10") + Decimal("0.20") == Decimal("0.30")    # True, exactly
Decimal(0.1)      # Decimal('0.1000000000000000055511151231257827...')  the float's error, preserved
```

The second line is the trap. `0.1` without quotes is already a float, with its error baked in, and `Decimal` copies it faithfully. The string `"0.1"` never went through a float.

One more thing you will need. `sum()` starts adding from the int `0`. That is fine for a list of Decimals, but an **empty** list gives back the int `0`, not a Decimal. `sum` takes a second argument, the starting value, to fix that:

```python
sum([Decimal("1.5"), Decimal("2")])      # Decimal('3.5')
sum([], Decimal("0"))                    # Decimal('0'), not the int 0
```

The other way to handle money is to work in **[[whole cents|integer-cents]]**, as an `int`: 10 dollars is `1000`. Ints are always exact.

### Fix 3: exact fractions

For **exact fractions** (ratios, probabilities), `fractions.Fraction` keeps the top and bottom as whole numbers, so nothing is ever rounded. `Fraction(1, 3) * 3 == 1` is exactly `True`.

### Splitting money

**Splitting money** has its own trap. 10.00 split three ways is not three times 3.33, because 3.33 × 3 = 9.99 and a cent disappears. The fix, step by step:

1. Work in cents: 10.00 is `1000` cents.
2. Give everyone the rounded-down share, and find the leftover cents.
3. Hand out the leftover cents one each, to the first people.

For step 2, `divmod(a, b)` does whole-number division and the remainder in one go. It gives back both as a pair, the same as `(a // b, a % b)`:

```python
divmod(1000, 3)      # (333, 1): 333 cents each, 1 cent left over
```

So the shares are 334, 333 and 333 cents: the first person gets the spare cent. To turn cents back into money, divide a Decimal by 100: `Decimal(334) / 100` is `Decimal('3.34')`. The shares add up to exactly 10.00.

**Watch out:** `float(total)` or `Decimal(0.1)` anywhere in money code lets the float error back in. Every amount should start life as a string (`Decimal("0.10")`) or as whole cents.

::: context binary-fractions Why 0.1 never ends in binary
In decimal, the places after the point are tenths, hundredths, thousandths. In binary they are halves, quarters, eighths, sixteenths, and so on. A number has an exact binary form only if it can be built from a *finite* sum of those. 0.5 is one half, 0.75 is a half plus a quarter. But 0.1 written in binary is 0.000110011001100… with the "0011" repeating forever, just as 1/3 is 0.333… in decimal. The computer stops after a fixed number of binary digits, so the stored value is a hair off.
:::

::: context nearest-float Floats are dots on a line, with gaps between
A Python float uses 64 bits, and 53 of them hold the digits, which gives about 15 to 17 significant decimal digits. So the numbers a float can hold are like dots on a number line with small gaps between them. Any real number that falls in a gap is stored as the nearest dot. The gaps grow with the size of the number: near 10^20 they are 16,384 wide, which is why `1e20 + 1 == 1e20` is `True`. (The picture is not to scale.)

::: context patriot-clock A tenth of a second that mattered
In 1991, during the Gulf War, a Patriot missile battery at Dhahran, Saudi Arabia, failed to stop an incoming Scud missile, and 28 American soldiers were killed. Its computer counted time in tenths of a second and multiplied by 0.1 to get seconds, but 0.1 was stored in 24 binary digits, so every tick was off by about 0.000000095 seconds. After about 100 hours of running, the clock was off by about 0.34 seconds. A Scud travels more than half a kilometre in that time, so the system looked in the wrong place.
:::

::: context tolerance Engineers never ask for exactly
No machined part is exactly 50 mm long. A drawing says "50 mm ± 0.05 mm", and any part inside that range passes. That range is the tolerance. Comparing floats works the same way: you decide how close counts as the same. A relative tolerance scales with the numbers, like "within 1 percent", which suits values from millimetres to kilometres. An absolute tolerance is a fixed amount, like "within 0.05 mm", which is what you need near zero.
:::

::: context decimal-module A calculator that counts in tens
The `decimal` module does arithmetic the way you learned at school, digit by digit in base ten. So `Decimal("0.10")` really is ten hundredths, and adding money gives exactly what a person with a pencil would get. It still has a limit, 28 significant digits by default, so `Decimal(1) / 3` is rounded too. But for money, where every amount is a whole number of cents, it never needs to round. It is slower than float, which is why science code sticks with floats.
:::

::: context integer-cents Many payment systems count in cents
Counting in the smallest unit is how a lot of real money software works. Stripe's payment API, for example, takes amounts as whole numbers in the currency's smallest unit, so 10.00 US dollars is sent as `1000`. An `int` in Python is always exact, however big, so adding and subtracting cents can never drift. You only turn cents into dollars and cents at the very end, when you show them to a person.
:::

=== py4-11 | Problem solving: edit distance
--- teach
Last lesson was about numbers that are almost equal. This one asks the same question about words: how different are two strings?

Spell checkers, [[DNA comparison|diff-and-dna]] and `diff` all need a precise answer. When you type "teh", a spell checker suggests "the" because it is only a small change away. To make "small change" exact, count the edits.

### The edit distance

The **edit distance** (also called the **[[Levenshtein distance|levenshtein]]**) is the fewest single-character edits that turn one string into the other. Three kinds of edit are allowed:

- an **insertion**: add one character;
- a **deletion**: remove one character;
- a **substitution**: swap one character for another.

`kitten` → `sitting` takes 3:

```
kitten
sitten     substitute k -> s
sittin     substitute e -> i
sitting    insert g at the end
```

No way does it in 2, so the distance is 3.

### Restate it as smaller problems

Like the coin problems in the dynamic programming lesson, the trick is to answer the big question using answers to smaller ones.

Let `d(i, j)` be the distance between the first `i` characters of `a` and the first `j` characters of `b`. Those beginnings are called **[[prefixes|prefix]]**: `a[:i]` and `b[:j]`. The answer to the whole problem is `d(len(a), len(b))`.

Now look at the last character of each prefix, `a[i-1]` and `b[j-1]` (the `- 1` is there because indexes start at 0):

- If they are **equal**, they cost nothing. Leave them alone and solve the rest: `d(i, j) = d(i-1, j-1)`.
- Otherwise, the last step was one of the three edits. Try all three and take the cheapest:
  - delete `a[i-1]`: `d(i-1, j) + 1`
  - insert `b[j-1]`: `d(i, j-1) + 1`
  - substitute: `d(i-1, j-1) + 1`

**Base cases.** Turning a prefix of length `i` into the empty string takes `i` deletions, so `d(i, 0) = i`. Turning the empty string into `b[:j]` takes `j` insertions, so `d(0, j) = j`.

### Why not plain recursion?

You could write `d` as a recursive function exactly as above, and it would be correct. But each call branches three ways, and the same `(i, j)` pairs come up again and again: the work grows [[exponentially|exponential-blowup]]. Two 10-letter strings with no letters in common already take over 3.7 million calls.

Memoisation (`@lru_cache`) fixes the repeats. But the recursion gets as deep as `len(a) + len(b)` calls, past [[Python's limit|recursion-limit]] for long strings.

### Fill a table, bottom-up

So fill a table **bottom-up**, row by row, with loops. Row `i` is about `a[:i]`, column `j` is about `b[:j]`, and each cell holds `d(i, j)`. Here is the whole table for `kitten` and `sitting`:

```
        ""  s  i  t  t  i  n  g
    ""   0  1  2  3  4  5  6  7
    k    1  1  2  3  4  5  6  7
    i    2  2  1  2  3  4  5  6
    t    3  3  2  1  2  3  4  5
    t    4  4  3  2  1  2  3  4
    e    5  5  4  3  2  2  3  4
    n    6  6  5  4  3  3  2  3
```

The top row and left column are the base cases: 0, 1, 2, 3… The answer is the bottom-right cell, 3.

Take one cell to see the rule work. Row `i`, column `s` (is `"ki"` → `"s"`): `i` and `s` differ, so it is 1 + the smallest of above (1), left (2) and diagonal (1), which is 2. Next cell, row `i`, column `i` (is `"ki"` → `"si"`): the letters match, so copy the diagonal, 1.

### Keep only one row

Each cell needs only [[three neighbours|three-neighbours]]: the cell to its left, the one above, and the one diagonally above-left. So you do not need the whole table. Keep only **the previous row**, and build the current row from it. That cuts memory from `len(a) × len(b)` to `len(b)`.

The time is still one step per cell: `len(a) × len(b)` cells, which is O(n·m) time, where n and m are the two lengths. That is fine for strings of a thousand or so characters each, about a million cells.

**Watch out:** an off-by-one between string indices and table indices. The table has one more row and column than the strings have letters, for the empty prefix. Row `i` of the table is about `a[:i]`, so the character it adds is `a[i - 1]`, not `a[i]`.

::: context diff-and-dna Where the same table shows up
The `git diff` you met in the Git courses finds the fewest line insertions and deletions that turn one version of a file into another. Its default method, Myers' algorithm from 1986, solves a close cousin of this problem with lines in place of letters. Biologists line up DNA the same way: the Needleman–Wunsch method from 1970 fills this kind of table, with scores for matches, mismatches and gaps, to compare genes letter by letter.
:::

::: context levenshtein Named after a Soviet mathematician
Vladimir Levenshtein described this distance in 1965, while working on codes that correct errors in messages sent as strings of 0s and 1s. If noise can drop, add or flip a symbol, you want to know how many of those slips separate two messages. The same count turned out to be useful for words, DNA and files, so the name stuck everywhere. You will also see plain "edit distance", which is a family name: some versions allow only insertions and deletions, or also count swapping two neighbouring letters as one edit.
:::

::: context prefix Prefixes, and why the empty one counts
A prefix is a beginning of a string. The prefixes of `"cat"` are `""`, `"c"`, `"ca"` and `"cat"`: four of them for three letters, because the empty string counts too. In Python, `a[:i]` is the prefix of length `i`. The empty prefix is what makes the base cases work. It is the starting point every edit sequence can be measured from, the same way `best[0] = 0` started the coin table.
:::

::: context exponential-blowup Three branches per call adds up fast
Each call that does not match makes three more calls, and each of those makes three more. So the number of calls can grow like 3 × 3 × 3 … once per level, which is exponential growth: each extra letter multiplies the work instead of adding to it. Counting them for two 10-letter strings that share no letters gives 3,716,073 calls, most of them repeats of the same `(i, j)` pair. The table has only 11 × 11 = 121 cells, so the repeats are almost all of the work.
:::

::: context recursion-limit Python stops deep recursion on purpose
Every function call that has not returned yet takes a slot on Python's **call stack**. To stop a runaway recursion from eating all the memory, Python raises `RecursionError` once the stack gets about 1,000 calls deep; `sys.getrecursionlimit()` shows the exact limit, which is 1000 by default. With 1,000-character strings, the memoised version would need up to 2,000 calls stacked at once. A loop has no such limit, which is one reason bottom-up tables are the usual choice.
:::

::: context three-neighbours Where each cell gets its answer
Each arrow is one kind of last edit. Coming from above means a character of `a` was deleted. Coming from the left means a character of `b` was inserted. Coming along the diagonal means the last two characters were matched (free) or substituted (cost 1). All three neighbours are in the current row or the one before it.

=== py4-12 | Problem solving: Dijkstra's shortest path
--- teach
Last lesson you filled a table to measure how far apart two strings are. This lesson goes back to a question from the advanced course: what is the best route from here to there? There you used **BFS**, which finds the route with the fewest moves. BFS works because every move costs the same: one step. Real maps are not like that. One road is 10 km long, another is 1 km. This lesson finds the *cheapest* route when steps have different costs. The same problem sits inside [[every maps app and every internet router|routing-real]].

## Fewest steps is not always cheapest

Picture four towns. From A there is a long road straight to B: 10 km. There is also a short road from A to C (1 km), one from C to D (1 km), and one from D to B (1 km).

BFS would say "A to B is one step, done". But that one step costs 10 km. The three-step route A, C, D, B costs 1 + 1 + 1 = 3 km. More steps, much cheaper.

In Python you can store this map as a dictionary. Each town maps to a list of `(neighbour, cost)` pairs, one pair for each road out of it:

```python
graph = {
    "A": [("B", 10), ("C", 1)],
    "C": [("D", 1)],
    "D": [("B", 1)],
}
```

A map like this is a **[[weighted graph|graph-words]]**. The places are **nodes**, the roads between them are **edges**, and the cost written on each edge is its **weight**.

Two things to notice:

- The roads here are one way. A lists a road to B, but B lists nothing, so you cannot go from B back to A.
- B is not a key at all. A node with no roads out of it may be left out. So always read the roads with `graph.get(node, [])`, which means "the list for this node, or an empty list if it has none".

## The idea: settle the cheapest place next

**[[Dijkstra's algorithm|dijkstra-history]]** (say it "DIKE-stra") finds the cheapest route from a start to every place it can reach. It needs one promise: no cost is [[negative|negative-costs]].

Think of water poured in at the start and spreading along pipes of different lengths. It reaches near places first and far places later. Dijkstra copies that. For every place reached so far, it keeps the **best cost found so far**, a number that may still get lower. Then, over and over:

1. Pick the place with the lowest cost so far that is not yet settled.
2. **Settle** it: its cost is now final.
3. For each road out of it, check whether going through this place makes the neighbour cheaper. If it does, write down the new, lower cost.

Step 3 has a name: **relaxing** an edge, which means checking whether that road gives a cheaper way to reach its end.

Why is a settled cost final? Any other route to that place would have to leave the settled places through some place that is not settled yet, and every one of those already costs at least as much. Adding more roads can only add cost, because no cost is negative. So no other route can beat it.

## The heap: "cheapest next", fast

Step 1 asks "which place is cheapest right now?" again and again. In the heapq lesson you met the tool for exactly that question. A heap of `(cost, node)` tuples always keeps the smallest cost at the front, because tuples compare by their first item first. A heap used this way is called a **[[priority queue|priority-queue]]**.

Here is Dijkstra finding the cheapest cost from the start to every place it can reach:

```python
import heapq

def costs_from(graph, start):
    best = {start: 0}
    heap = [(0, start)]
    while heap:
        cost, node = heapq.heappop(heap)
        if cost > best[node]:
            continue                      # an old, worse entry: skip it
        for neighbour, weight in graph.get(node, []):
            new = cost + weight
            if new < best.get(neighbour, float("inf")):
                best[neighbour] = new
                heapq.heappush(heap, (new, neighbour))
    return best
```

What each part does:

- `best` holds the cheapest cost found so far for each place. The start costs 0.
- `heapq.heappop(heap)` takes out the cheapest entry. That is steps 1 and 2.
- The `for` loop is step 3. `new` is the cost of reaching the neighbour through this node.
- `best.get(neighbour, float("inf"))` is the neighbour's cost so far, or [[infinity|infinity]] if it has not been reached yet, so any real cost beats it.
- If `new` is lower, it goes into `best`, and the neighbour goes onto the heap.

On the four towns:

```python
costs_from(graph, "A")      # {'A': 0, 'B': 3, 'C': 1, 'D': 2}
```

B costs 3, by the long way round, as it should.

## Old entries on the heap

Here is the order the entries come off the heap for the four towns:

```
(0, 'A')   (1, 'C')   (2, 'D')   (3, 'B')   (10, 'B')
```

B came off twice. When A was settled, the road A to B gave B a cost of 10, so `(10, "B")` went onto the heap. Later, D found a way to B costing 3, so `(3, "B")` went on too.

A heap cannot easily find and change an entry in its middle. So instead of updating the old entry, you push a new one and leave the old one where it is. The old entry is **stale**: out of date. When `(10, "B")` finally comes off, `cost > best[node]` asks "is 10 more than 3?", which is true, and `continue` skips it.

## Getting the route, not only the cost

To know the route, also remember where you came from. Each time you lower a neighbour's cost, write `previous[neighbour] = node`, which means "the cheapest way into this neighbour, so far, comes from this node".

For the four towns, `previous` ends up as `{'B': 'D', 'C': 'A', 'D': 'C'}`. (B was first reached from A, then its entry was overwritten when D found a cheaper way.)

Now walk backwards from the goal. B came from D, D came from C, C came from A. A has no entry, because it is the start. That gives B, D, C, A. Turn it around and you have the route:

```python
path = ["B"]
node = "B"
while node in previous:
    node = previous[node]
    path.append(node)
path[::-1]       # ['A', 'C', 'D', 'B']
```

`path[::-1]` is the list read backwards: a slice with a step of minus one.

## Stopping early

If you only care about one goal, you can stop the moment the goal comes off the heap. It is settled then, so its cost is final, and the rest of the map does not matter.

## Why the heap matters

Each push or pop on a heap is O(log n). With a heap, Dijkstra is **[[O(E log V)|big-o-ev]]**, for E edges and V nodes. Without one, you would scan every place to find the cheapest each time, which is O(V²): for 20,000 places that is about 400 million steps, far too slow.

**Watch out:** in BFS you marked a square as seen when you *added* it to the queue. Do not do that here. With weights, a route found later can still be cheaper: B was first found at a cost of 10, and later at 3. A place is only settled when it is *popped* off the heap.

::: context routing-real Where Dijkstra runs every day
Many internet routers run Dijkstra's algorithm. In a common routing system called OSPF ("Open Shortest Path First"), each router keeps a map of the network, with a cost on every link, and runs Dijkstra on it to decide where to send each packet next. Maps apps face the same question on road networks with millions of junctions. They use faster relatives of Dijkstra, such as A* (which also aims towards the goal) and tricks that pre-compute shortcuts, but the heart of all of them is today's idea: settle the cheapest place next.

::: context dijkstra-history Twenty minutes at a café
Edsger Dijkstra (1930 to 2002) was a Dutch computer scientist. In 1956 he wanted a problem to show off a new computer, the ARMAC, that people who were not mathematicians could understand: the shortest route between two Dutch cities. He later said he worked the algorithm out in about twenty minutes, sitting on a café terrace in Amsterdam, without pencil and paper. He published it in 1959 in a paper about three pages long. It is still one of the most used algorithms in the world.
:::

::: context negative-costs Why a negative cost breaks it
Suppose A to B costs 2, A to C costs 5, and C to B costs minus 4. Dijkstra pops B first, at cost 2, and settles it. Only later does it pop C and find A, C, B, which costs 5 + (−4) = 1: cheaper, but B was already declared final. The promise "more roads can only add cost" was false. Graphs with negative weights need a different algorithm, such as Bellman–Ford, which is slower (about V × E steps) but copes with them. Real costs like distance and time are never negative, so Dijkstra fits most maps.
:::

::: context priority-queue A queue where the most urgent goes first
An ordinary queue is first come, first served, like the line at a shop. A **priority queue** serves the most urgent item first, like a hospital emergency room that sees the worst injury first, whoever arrived earlier. In Python the heap is the usual way to build one. One detail: if two entries have the same cost, the tuples compare their second items, the nodes, to break the tie. `(3, "B")` comes before `(3, "C")`. So all the nodes must be things Python can compare with each other: all strings, or all tuples, not a mixture.
:::

::: context infinity A number bigger than every number
`float("inf")` is a special floating-point value meaning infinity. Every ordinary number is smaller than it: `float("inf") > 10**100` is `True`, and `min(3, float("inf"))` is `3`. That makes it the perfect starting value for "the best cost so far" when you have not found any route yet: the first real cost always beats it. The `math` module has the same value under a shorter name, `math.inf`.
:::

::: context big-o-ev Reading O(E log V)
The big-O lessons measured work in terms of one size, n. A graph has two sizes: V, the number of nodes, and E, the number of edges. Dijkstra looks at every edge once, and each look may push onto the heap, which costs about log V steps. So the total is about E times log V. For a grid of 20,000 places with about 80,000 edges, log₂ of 20,000 is about 14, so that is about 80,000 × 14, roughly a million small steps. Compare that with 400 million for the scanning version.
:::

=== py4-13 | Problem solving: a tokenizer
--- teach
Edit distance and Dijkstra were algorithms someone else invented, which you learned to write. The last lessons of this course build a small program the way real language tools are built: a calculator that understands text like `2 * (3 + 4) - -1`.

Think about how you read a sentence. First you see words and punctuation marks, not single letters. Then you work out how the words fit together. A calculator, and Python itself, and [[every interpreter and compiler|interpreters-too]], works in the same two stages:

1. **Tokenizing** (this lesson): cut the text into meaningful pieces, called **[[tokens|token-word]]**. For `2 * (3 + 4) - -1` the tokens are `2`, `*`, `(`, `3`, `+`, `4`, `)`, `-`, `-`, `1`.
2. **Parsing** (the next lessons): work out how the tokens fit together, and compute the answer.

Splitting the job keeps each half simple. The parser never has to think about spaces, or about how many characters a number has. It gets a tidy list like `[12, "+", 3]`.

## Walking through the text with an index

Keep a number `i` that points at the current character, like a finger resting on the text. Look at the character under your finger and decide what kind of token starts there. Then move the finger past it.

Here is a tokenizer for whole numbers, `+` and `-`:

```python
def tokenize(text):
    tokens = []
    i = 0
    while i < len(text):
        ch = text[i]
        if ch.isspace():
            i += 1                      # a space: skip it, no token
        elif ch.isdigit():
            start = i
            while i < len(text) and text[i].isdigit():
                i += 1                  # move past the whole number
            tokens.append(int(text[start:i]))
        elif ch in "+-":
            tokens.append(ch)
            i += 1
        else:
            raise ValueError("unexpected character")
    return tokens

tokenize("12 + 3")        # [12, '+', 3]
```

Step by step:

- `ch.isspace()` is true for a space (or a tab or newline). Spaces make no token; the finger moves on by one.
- `ch.isdigit()` is true for `0` to `9`. A number can be several digits long, so remember where it began (`start = i`), move `i` forward while you still see digits, and then cut out the whole run with the slice `text[start:i]`. `int` turns the text `"12"` into the number `12`.
- `ch in "+-"` is true when `ch` is one of the characters in that string. An operator is one character, so it becomes a token by itself and `i` moves on by one.
- Anything else is a character the calculator does not understand.

## Numbers with a decimal point

Numbers like `4.5` have a dot. So a number may start with a digit *or* a dot (`.5` is a number too), and the number loop should accept dots as well as digits. Then look at the run you cut out before converting it:

- `"4.5".count(".")` is `1`, so it is a decimal number: `float("4.5")` gives `4.5`.
- `"12"` has no dot, so `int("12")` gives `12`.
- `"1.2.3"` has two dots, and `"."` alone has no digits at all. Neither is a number, so they are errors.

`float` also accepts a dot at either end: `float(".5")` is `0.5` and `float("5.")` is `5.0`.

## Always take the longest token

Python writes powers as `**`: `2 ** 3` is 8. So when you see `*`, you cannot decide yet. It might be a multiplication, or the first half of a power. You have to peek at the next character too.

The rule tokenizers follow is called **[[maximal munch|maximal-munch]]**: always take the *longest* token that fits. `123` is one number, not three. `**` is one power operator, not two multiplications.

A neat way to peek is `text.startswith("**", i)`. It asks: "does the text, starting at position `i`, begin with `**`?"

```python
"2**3".startswith("**", 1)     # True: position 1 starts "**"
"2**3".startswith("**", 0)     # False: position 0 is "2"
```

Check for `**` *before* you check for a single `*`. Otherwise the single `*` wins first and the power is split in two. When you find `**`, move `i` on by 2, not 1.

## Errors that say what and where

When a character does not start any token, raise an error that says *what* the character was and *where* it is:

```python
ch = "$"
i = 4
raise ValueError(f"unexpected character {ch!r} at position {i}")
# ValueError: unexpected character '$' at position 4
```

The [[`!r` inside the braces|repr-quotes]] puts quotes around the character, so you can see exactly what it was. The position is the index `i`, which [[counts from 0|position-zero]]. A message like this is the difference between a tool people can use and one they give up on.

**Watch out:** do not move along by chopping the text, as in `text = text[1:]`. It gives the right tokens, but every chop copies the whole rest of the string. For long input that makes the tokenizer [[quadratic|quadratic-copies]]: twice the text, four times the work. Move the index `i` instead; the text itself never changes.

::: context interpreters-too Python tokenizes your code too
An **interpreter** reads a program and carries it out; a **compiler** translates a program into another form, often machine code, to be run later. Python is usually run by an interpreter, and the very first thing it does with your file is tokenize it. The standard library even lets you watch: the `tokenize` module turns the line `2**3*4` into the pieces `'2'`, `'**'`, `'3'`, `'*'`, `'4'`, plus markers for the end of the line and the end of the file. Your calculator follows the same plan, only smaller.
:::

::: context quadratic-copies Why chopping the string is slow
Python strings cannot be changed, so `text[1:]` builds a brand-new string holding every character but the first. For 100,000 characters, the first chop copies 99,999 characters, the next 99,998, and so on down to 1. That adds up to about 5 billion character copies, where moving an index costs 100,000 small steps. Work that grows with the square of the input's length is called **quadratic**, O(n²) in the big-O lessons' language.

Last lesson your tokenizer turned `2 + 3 * 4` into the list `[2, "+", 3, "*", 4]`. Now for the second stage: what does that list *mean*?

It is not `(2 + 3) * 4 = 20`. You learned in maths that [[multiplication comes before addition|precedence-school]], so it is `2 + 12 = 14`. This lesson teaches your program that rule, for `+`, `-`, `*`, `/` and brackets. The next lesson adds minus signs in front of numbers, powers, and catching bad input.

## Precedence

**Precedence** means which operator is done first. `*` and `/` have higher precedence than `+` and `-`. Programmers say `*` **binds tighter** than `+`: it grabs the numbers next to it first.

## A grammar: the rules written down

A **grammar** is a short set of rules that says how pieces may fit together, like the grammar of English says how words make a sentence. Here is a [[grammar|grammar-history]] for sums with brackets:

```
expr  := term  (("+" | "-") term)*
term  := atom  (("*" | "/") atom)*
atom  := NUMBER  |  "(" expr ")"
```

How to read the symbols:

- `:=` means "is made of".
- `|` means "or".
- Things in quotes, like `"+"`, are that exact token.
- `NUMBER` means any number token.
- `( ... )*` means "the part in brackets, zero or more times".

So, in words:

- An **expr** (short for expression) is a term, then any number of `+ term` or `- term` after it.
- A **term** is an atom, then any number of `* atom` or `/ atom` after it.
- An **atom** is a number, or a whole expr inside brackets.

Look at `2 + 3 * 4` with these rules. The expr is made of two terms joined by `+`: the term `2`, and the term `3 * 4`. The multiplication lives *inside* a term, so it is worked out before the expr adds the terms. That is how the grammar puts precedence in: the [[operator worked out last sits highest|parse-tree]], in the first rule.

## Recursive descent: one function per rule

**Recursive descent** is a way to turn a grammar straight into code: [[one function for each rule|recursive-descent-real]], with the same name. Each function reads the tokens its rule matches and returns their value.

All the functions share one list of tokens and one position in it, so put them in a class:

```python
class Parser:
    def __init__(self, tokens):
        self.tokens = tokens
        self.pos = 0

    def peek(self):
        return self.tokens[self.pos] if self.pos < len(self.tokens) else None

    def take(self):
        token = self.peek()
        self.pos += 1
        return token
```

- `peek()` [[looks at the current token|lookahead]] without moving on. At the end of the list it returns `None`.
- `take()` returns the current token *and* moves the position on by one.

Here is the `expr` rule as a method. Compare it with the grammar line: a term, then "`+` or `-`, then a term" as many times as they appear:

```python
    def expr(self):
        value = self.term()
        while self.peek() in ("+", "-"):
            op = self.take()
            right = self.term()
            value = value + right if op == "+" else value - right
        return value
```

`term` has the same shape, with `atom` in place of `term` and `*` and `/` in place of `+` and `-`.

`atom` takes one token. If it is a number, that is the value. If it is `(`, it calls `self.expr()` to work out everything inside the brackets, then takes the `)` that closes them.

That call is the **recursion** in "recursive descent": `expr` calls `term`, `term` calls `atom`, and `atom` can call `expr` again for a bracket. Each bracket starts a fresh, complete expression. **Descent** is the other half of the name: you start at the top rule and go down through the rules to the numbers.

To evaluate a text, tokenize it, make a `Parser`, and call `expr()`:

```python
Parser(tokenize("2 + 3 * 4")).expr()      # 14
```

## Left to right

`8 - 3 - 2` is `(8 - 3) - 2 = 3`, not `8 - (3 - 2) = 7`. Operators of the same precedence are done **left to right**. The `while` loop gives you this for free. Follow it on `8 - 3 - 2`:

1. `value` starts as `8`.
2. It sees `-`, reads the term `3`, and [[folds it in|left-fold]]: `value` becomes `8 - 3 = 5`.
3. It sees `-`, reads the term `2`: `value` becomes `5 - 2 = 3`.

The same goes for `/`: `100 / 10 / 5` is `(100 / 10) / 5 = 2.0`.

**Watch out:** a tempting way to write `expr` is "a term, then optionally `+` or `-` and another *expr*", calling `self.expr()` for the right side. It looks shorter, but it groups from the right: `8 - 3 - 2` becomes `8 - (3 - 2) = 7`. Use the loop.

In the signed-numbers lesson of the maths track the order was: brackets first, then powers, then multiply and divide from left to right, then add and subtract from left to right. Everyone follows the same order so that everyone gets the same answer from the same line. Python, calculators and spreadsheets all use it. Your parser only has to follow those same rules, and the grammar is where the rules are written down.

class Parser:

        self.tokens = tokens
        self.pos = 0

    def peek(self):

    def take(self):
        token = self.peek()
        self.pos += 1
        return token

    def expr(self):
        value = self.term()
        while self.peek() in ("+", "-"):
            op = self.take()
            right = self.term()
            value = value + right if op == "+" else value - right
        return value

    def term(self):
        value = self.atom()
        while self.peek() in ("*", "/"):
            op = self.take()
            right = self.atom()
            value = value * right if op == "*" else value / right
        return value

    def atom(self):
        token = self.take()
        if token == "(":
            value = self.expr()
            self.take()
            return value
        return token

=== py4-14 | Problem solving: a recursive-descent calculator
--- teach
Last lesson your parser learned `+ - * /` and brackets with three rules: `expr`, `term` and `atom`. Python's arithmetic has three more things your calculator needs: a minus sign in front of a number (`-1`, even `--3`), powers with `**`, and refusing input that makes no sense. This is the last lesson of the course, and it finishes the calculator.

## The full grammar

Two new rules slot in between `term` and `atom`. The loosest rule is still first:

```
expr   := term   (("+" | "-") term)*
term   := unary  (("*" | "/") unary)*
unary  := "-" unary  |  power
power  := atom   ("**" unary)?
atom   := NUMBER  |  "(" expr ")"
```

One new symbol: `?` means "optional", zero times or once. So:

- `term` now multiplies **unary** pieces instead of atoms.
- A **unary** piece is a `-` followed by another unary piece, or else a power.
- A **power** is an atom, optionally followed by `**` and a unary piece.

`expr` and `atom` are the same as before, and `term` only changes which method it calls.

## Unary minus

The `-` sign has two jobs. In `5 - 2` it sits between two numbers and subtracts: that is **binary** minus. In `-2` it sits in front of one number and flips its sign: that is **[[unary minus|unary-binary]]**. The tokenizer makes the same `"-"` token for both. The grammar tells them apart by *where* the minus appears. `expr` only looks for `+` or `-` *after* a finished term, so any minus that starts a piece, like the second one in `2 * -3`, reaches `unary` instead.

```python
def unary(self):
    if self.peek() == "-":
        self.take()
        return -self.unary()
    return self.power()
```

`unary` calls itself after each minus, so any number of minuses work: `--3` is `-(-3)`, which is `3`.

## Powers go right to left

`+ - * /` go left to right. `**` is the exception: `2 ** 3 ** 2` is `2 ** (3 ** 2) = 2 ** 9 = 512`, not `(2 ** 3) ** 2 = 64`. An operator that groups from the right like this is **[[right-associative|right-assoc]]**. Python does it, and so does maths, where a tower of powers is worked out from the top down.

```python
def power(self):
    base = self.atom()
    if self.peek() == "**":
        self.take()
        return base ** self.unary()
    return base
```

The right side of `**` is parsed by calling `unary`, and that can itself contain another `**`. So the rightmost power is finished first. (Last lesson's Watch out showed that a rule calling itself on its right side groups from the right. For `**`, that is exactly what you want.)

## Where the minus goes around a power

`-2 ** 2` is `-(2 ** 2) = -4`, not `(-2) ** 2 = 4`, the [[same rule as in maths|minus-before-power]]. Follow it through: `unary` sees `-` and takes it. It then calls `unary` again, which finds no minus and calls `power`, which reads `2 ** 2 = 4`. Only then does the first `unary` flip the sign: `-4`.

The right side of `**` goes through `unary` too, so `2 ** -1` works: it is `2 ** (-1) = 0.5`. And if you do want the minus inside, brackets say so: `(-2) ** 2` is `4`.

Here is the order from tightest to loosest:

| Rule | Handles | Example |
| --- | --- | --- |
| `atom` | numbers and brackets | `(1 + 2)` |
| `power` | `**`, right to left | `2 ** 3 ** 2` is 512 |
| `unary` | minus in front | `-2 ** 2` is -4 |
| `term` | `*` and `/`, left to right | `100 / 10 / 5` is 2.0 |
| `expr` | `+` and `-`, left to right | `8 - 3 - 2` is 3 |

## Refusing nonsense

A parser must [[reject bad input rather than guess|fail-loudly]]. Three checks catch every kind of nonsense in this grammar:

- **`atom` needs a number or `(`.** If it takes anything else, raise `ValueError`. That includes `None`, which `take()` returns at the end of the tokens. So `2 +` fails (the text ends where a number should be), and so do `* 3` and `()`.
- **After `( expr`, `atom` must find `)`.** If the next token taken is anything else, raise `ValueError`. That catches `(1 + 2`.
- **After the whole `expr`, no token may be left over.** In `evaluate`, check that `peek()` is `None` once `expr()` returns. Without this, `1 2` would quietly give 1, and `1 + 2)` would quietly give 3.

**Watch out:** do not use Python's built-in `eval` to compute the answer. Apart from skipping the whole exercise, [[`eval` on user input is dangerous|eval-danger]]: it runs *any* Python code the user types, not only arithmetic.

Your parser works through recursion, so extremely deep brackets would eventually hit [[Python's recursion limit|recursion-limit]]. Long flat input is fine: the `while` loops handle 20,000 terms in a row without going any deeper. This calculator comes back in [[the projects course|projects-next]], where it grows into a small language of its own.

::: context unary-binary One number or two
**Unary** means "one" and **binary** means "two", as in unicycle and bicycle. A unary operator works on one value (`-x`); a binary operator works on two (`x - y`). Python also has a unary plus, so `+3` is allowed in Python, but your grammar leaves it out. The same symbol doing two jobs is common in programming languages; it is the grammar, not the tokenizer, that knows which job each one is doing.
:::

::: context minus-before-power Not every program agrees
In maths, −3² means −(3 × 3) = −9, as the signed-numbers lesson warned. Python follows maths: `-3 ** 2` is `-9`. But not every program does. In Microsoft Excel, the formula `=-3^2` gives 9, because Excel applies the minus sign before the power. So the same-looking line can give different answers in different tools. When it matters, and in flight software it always matters, write the brackets so no reader has to remember the rule.

::: context fail-loudly Why a parser should not guess
If a calculator quietly answers 1 for `1 2`, the person who typed it never learns that they forgot an operator, and the wrong number travels on into whatever they do next. An error that appears right away is cheap to fix: the person sees it, and fixes the typo. A wrong answer that looks right can go a long way before anyone notices. Engineers call this **failing loudly**, and it is one of the most useful habits in software that other people depend on.

::: context eval-danger What eval would let a user do
`eval` takes a string and runs it as Python. If that string comes from a user, the user is writing your program. Typing `__import__('os').remove('notes.txt')` into an eval-based calculator would delete a file, and worse is easily possible. This kind of attack is called **code injection**. When you really do need to read Python values from text, `ast.literal_eval` accepts only plain values like numbers, strings and lists, and refuses anything that would run code. For arithmetic, a parser like yours is the safe answer.
:::

::: context recursion-limit How deep the brackets can go
Every bracket makes the parser go one level deeper: `atom` calls `expr`, which calls `term`, `unary`, `power` and `atom` again. That is five function calls per bracket. Python stops any chain of calls that gets about 1,000 deep, with a `RecursionError`, to protect itself from running out of memory. So this parser handles a little under 200 levels of nested brackets. People never type that many, but a parser for programs written by other programs must think about it.
:::

def tokenize(text):
    tokens = []
    i = 0
    while i < len(text):
        ch = text[i]
        if ch.isspace():
            i += 1
        elif ch.isdigit() or ch == ".":
            start = i
            while i < len(text) and (text[i].isdigit() or text[i] == "."):
                i += 1
            number = text[start:i]
            if number.count(".") > 1 or number == ".":

            tokens.append(float(number) if "." in number else int(number))
        elif text.startswith("**", i):
            tokens.append("**")
            i += 2
        elif ch in "+-*/()":
            tokens.append(ch)
            i += 1
        else:

class Parser:
    def __init__(self, tokens):
        self.tokens = tokens
        self.pos = 0

    def peek(self):
        return self.tokens[self.pos] if self.pos < len(self.tokens) else None

    def take(self):
        token = self.peek()
        self.pos += 1
        return token

    def expr(self):
        value = self.term()
        while self.peek() in ("+", "-"):
            op = self.take()
            right = self.term()
            value = value + right if op == "+" else value - right
        return value

    def term(self):
        value = self.unary()
        while self.peek() in ("*", "/"):
            op = self.take()
            right = self.unary()
            value = value * right if op == "*" else value / right
        return value

    def unary(self):
        if self.peek() == "-":
            self.take()
            return -self.unary()
        return self.power()

    def power(self):
        base = self.atom()
        if self.peek() == "**":
            self.take()
            return base ** self.unary()
        return base

    def atom(self):
        token = self.take()
        if token == "(":
            value = self.expr()
            if self.take() != ")":
                raise ValueError("expected )")
            return value
        if isinstance(token, (int, float)):
            return token
        raise ValueError(f"expected a number, got {token!r}")


def evaluate(text):
    parser = Parser(tokenize(text))
    value = parser.expr()
    if parser.peek() is not None:
        raise ValueError(f"unexpected {parser.peek()!r}")
    return value
