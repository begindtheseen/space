=== cpp3-01 | RAII: let destructors clean up
--- teach
Last lesson, "Design: give repeated work a name", ended the intermediate course by giving repeated work one home. This course goes one level deeper. In the basics and intermediate courses you *used* types that look after themselves: `std::vector`, `std::string`, `std::map`, `std::unique_ptr`. Now you will *write* them: types that own things, copy and move correctly, work for any element type and behave like built-ins. It starts with the idea underneath all of them.

### Borrow it, give it back

Picture a library book. You borrow it, and you must give it back exactly once: not zero times, not twice. And you must give it back however your week goes: whether you finish it, get bored halfway, or leave on a trip early.

A program borrows things too. Memory, an open file, a lock, a network connection: each one is a **[[resource|resource-word]]**, something the program takes and must give back exactly once. It has to give it back on **every** way out of the code: the normal end, an early `return`, a `break` out of a loop.

Doing that by hand is where leaks come from:

```cpp
bool process(const std::string& name) {
    open_file(name);
    if (name.empty()) return false;   // oops: never closed
    // ...
    close_file(name);
    return true;
}
```

The early `return` leaves the function before it reaches `close_file`. One forgotten path, and a file stays open.

### The destructor: code that runs at the closing brace

You know constructors: the member function that runs when an object is born. A class can also have a **destructor**: a member function that runs automatically when the object dies. Its name is the class name with a `~` in front, read "tilde", and it has no parameters and no return type:

```cpp
struct Say {
    std::string word;
    explicit Say(const std::string& w) : word(w) { std::cout << "hello " << word << "\n"; }
    ~Say() { std::cout << "bye " << word << "\n"; }
};
```

A local object dies when it goes out of scope: when the program reaches the closing `}` of the block where the object was made. You never call the destructor yourself. C++ calls it for you, whichever way the program leaves the block: by reaching the end, by `return`, or by `break`.

### RAII: tie the resource to an object

Put those two ideas together and you get C++'s answer to leaks, **[[RAII|raii-name]]**, short for *Resource Acquisition Is Initialisation*. It means: tie each resource to an object. The constructor takes the resource (it **acquires** it), and the destructor gives it back (it **releases** it). Now the cleanup cannot be forgotten, because it is no longer a line you have to remember on every path.

Here is a lock. A **[[mutex|mutex-word]]** is a lock that lets only one part of a program use something at a time. Imagine a type `Mutex` with two member functions, `lock()` and `unlock()`:

```cpp
class Lock {
public:
    explicit Lock(Mutex& m) : m_(m) { m_.lock(); }
    ~Lock() { m_.unlock(); }
private:
    Mutex& m_;
};
```

Go through it one piece at a time:

- The member `m_` is a reference, `Mutex&`. The `Lock` does not hold a mutex of its own; it refers to the caller's. A reference member must get its value in the member initialiser list, `: m_(m)`, because a reference can never be changed later to refer to something else.
- The constructor body locks. The destructor, `~Lock()`, unlocks.

Now use it:

```cpp
void work(Mutex& m) {
    Lock guard(m);        // locked here
    if (bad()) return;    // unlocked here
}                         // ... and here
```

There is no `unlock` anywhere in `work`, yet every path unlocks. The object `guard` dies at the early `return` and at the closing `}`, and its destructor runs either way.

### Last made, first destroyed

When several objects live in one block, their destructors run in **reverse order** of construction: the last one made is the first one destroyed. So nested guards [[unwind like a stack|reverse-order]] of plates. With the `Say` type from above:

```cpp
int main() {
    Say a("a");
    Say b("b");
}
```

This prints:

```
hello a
hello b
bye b
bye a
```

### Anything that must be undone

A resource does not have to be a file or a lock. Anything that must be undone is a job for RAII. Say a program switches a setting to a temporary value while it does one careful job, and the old value must come back afterwards. An object can remember the old value in its constructor, switch the setting, and put the old value back in its destructor. However the job ends, the setting is restored.

### An owner must not be copied by accident

If a `Lock` could be copied, there would be two objects that both think they own the same lock, and both destructors would unlock it: one unlock too many. A class that owns something usually must not be copied by accident.

Copying goes through two special member functions, which C++ writes for you unless you say otherwise:

- the **copy constructor**, `Lock(const Lock&)`: builds a new `Lock` from an existing one, as in `Lock b = a;`.
- the **copy assignment operator**, `Lock& operator=(const Lock&)`: runs when you write `b = a;` and `b` already exists. `operator=`, read "operator equals", is the name C++ gives the function behind the `=` sign.

Say "no copying" by [[deleting both of them|deleted-functions]]:

```cpp
Lock(const Lock&) = delete;
Lock& operator=(const Lock&) = delete;
```

`= delete`, read "is deleted", tells the compiler this function must not exist. Any code that tries to copy a `Lock` now stops with a compile error that mentions a deleted function. The next lesson writes these two functions properly, for a class that should be copyable.

**Watch out:** the real mistake is doing half the job. If the destructor releases but copying is still allowed, a copy made by accident releases too, and a resource taken once is given back twice. And if you acquire in the constructor but still release by hand somewhere else, you are back to remembering every path. Acquire in the constructor, release in the destructor, delete copying, and nothing else.

You have used RAII types all along: `std::vector` frees its memory, `std::unique_ptr` deletes its object, and a file stream closes its file, each in its destructor.

::: context resource-word What counts as a resource
A resource is anything a program gets from the computer and must hand back, because there is only a limited supply. Memory is the famous one, but files are limited too: on many Linux systems a program may have only 1024 files open at once, and in the Terminal course's bash you can see your limit with `ulimit -n`. A program that forgets to close one file per request works fine in a quick test, then fails after running for an hour. Locks, network connections and hardware devices are resources in the same way.
:::

::: context raii-name A clumsy name for a great idea
Bjarne Stroustrup, who created C++, came up with the name RAII. Even people who love the idea admit the name is awkward: it talks about acquiring, but the important half is the destructor that releases. Some people call it "scope-bound resource management" instead, which describes what it does: the resource lives exactly as long as the scope of the object that owns it. Whatever the name, it is the reason well-written C++ rarely has cleanup code scattered around.
:::

::: context mutex-word Locks and a lander on Mars
"Mutex" is short for *mutual exclusion*: while one part of a program holds the lock, every other part that wants it has to wait. The real C++ types are `std::mutex` and `std::lock_guard`, which is exactly the `Lock` class in this lesson, written for you. Locks matter in flight software. In 1997 the Mars Pathfinder lander kept resetting itself on Mars, because a low-priority task held a mutex that a high-priority task needed. Engineers found the cause on a copy of the system on the ground and sent up a fix that changed how the mutex behaved.
:::

::: context reverse-order Why the last one goes first
Objects made later may depend on objects made earlier: a guard made second might use something the first one set up. Destroying in reverse order means every object is torn down while everything it relies on still exists. It works like a stack of plates: the last plate put on is the first one taken off.

::: context deleted-functions Saying no out loud
`= delete` arrived in C++11. Before that, programmers stopped copying by declaring the copy functions `private` and never writing them, which gave confusing errors. Now the compiler says it plainly. With g++ the message reads "use of deleted function"; with clang, which this app uses, it reads "call to deleted constructor". Either way the mistake is caught before the program ever runs, which is always the cheapest place to catch it. `std::unique_ptr` deletes its copy functions in exactly this way.
:::

--- solution
#include <string>
#include <type_traits>

int open_handles = 0;   // how many files are open right now
void open_file(const std::string&) { ++open_handles; }
void close_file(const std::string&) { --open_handles; }

class FileHandle {
public:
    explicit FileHandle(const std::string& name) : name_(name) { open_file(name_); }
    ~FileHandle() { close_file(name_); }
    FileHandle(const FileHandle&) = delete;
    FileHandle& operator=(const FileHandle&) = delete;
    const std::string& name() const { return name_; }
private:
    std::string name_;
};

class ValueGuard {
public:
    ValueGuard(int& target, int temporary) : target_(target), saved_(target) { target_ = temporary; }
    ~ValueGuard() { target_ = saved_; }
    ValueGuard(const ValueGuard&) = delete;
    ValueGuard& operator=(const ValueGuard&) = delete;
private:
    int& target_;
    int saved_;
};
--- hint
Start with `FileHandle`. The constructor body is the place to acquire: `open_file(name_);`. The destructor, `~FileHandle()`, is the place to release: `close_file(name_);`.
--- hint
`ValueGuard` needs two private members: a reference `int& target_` to the caller's variable, and an `int saved_` holding its old value. Fill both in the initialiser list, `: target_(target), saved_(target)`, then set `target_ = temporary;` in the constructor body.
--- hint
The destructor is `~ValueGuard() { target_ = saved_; }`. Delete copying in both classes with `ClassName(const ClassName&) = delete;` and `ClassName& operator=(const ClassName&) = delete;`, writing the real class name each time.

=== cpp3-02 | Copying: the rule of three
--- teach
Last lesson you wrote owners that must not be copied, and deleted their copy functions. Some owners *should* be copyable, though. A copy of a buffer of numbers ought to be a second buffer with the same numbers in it. This lesson writes the two copy functions by hand.

### What a copy does on its own

When you copy an object and have not written any copy functions, C++ copies each member, one at a time. For `int`s, `std::string`s and `std::vector`s that is exactly right: a copied vector gets its own elements.

A **raw pointer** is different. Copying a pointer copies the *address*, not the thing it points at. Think of a slip of paper with a house address on it: photocopying the slip does not build a second house. You end up with two slips and one house.

### Raw arrays on the heap

To see this go wrong, this lesson and the next break a rule from the basics course on purpose. The basics told you never to write raw `new` and `delete`. Here you will, once, to see what `std::vector` and `std::unique_ptr` do for you.

```cpp
int* data = new int[3]();   // three ints on the heap, all 0
data[1] = 7;                // use it like an array: 0 7 0
delete[] data;              // give all three back
```

- `new int[3]` asks the heap for three `int`s side by side and gives back a pointer to the first one. The `()` after it sets them all to zero; without it they would hold leftover junk, like the uninitialised values in the intermediate course.
- `data[1]` reaches an element through the pointer with square brackets, the same way you index a vector.
- `delete[]`, read "delete array", gives the whole block back. Memory from `new[]` must go back with [[delete with brackets|delete-brackets]], never plain `delete`.

### Two owners, one block

Now put that array inside a class:

```cpp
class Bad {
public:
    Bad() : data_(new int[3]()) {}
    ~Bad() { delete[] data_; }
private:
    int* data_;
};

Bad a;
Bad b = a;   // b.data_ == a.data_
             // writing through b changes a; at the end both destructors
             // delete the same block — a double free
```

`Bad b = a;` copies the member `data_`, so both objects hold the same address. This is a **shallow copy**: the pointer was copied, the block it points at was not. Change a number through `b` and `a` sees it change too. Worse, at the closing `}` both destructors run `delete[]` on the same block. Giving memory back twice is a **[[double free|double-free]]**, and it is undefined behaviour.

What you want is a **deep copy**: the copy gets its own new block, with the same numbers copied into it. The picture in the [[deep copy|shallow-deep]] note shows the difference.

### Copying a range: std::copy

`std::copy(from_begin, from_end, to)`, from `<algorithm>`, copies the elements from `from_begin` up to (not including) `from_end`, and writes them starting at `to`. Plain pointers work as its iterators:

```cpp
int* a = new int[3]{4, 5, 6};   // the braces give the starting values
int* b = new int[3];
std::copy(a, a + 3, b);         // b now holds 4 5 6
delete[] a;
delete[] b;
```

`a` points at the first element, and `a + 3` means [[three ints further along|pointer-arithmetic]]: one past the last element, the end of a half-open range, like `end()` on a vector.

### The rule of three

Here is the rule this lesson is named after. The **[[rule of three|rule-of-three-name]]**: if a class needs its own destructor, it almost certainly needs its own **copy constructor** and **copy assignment operator** too, because all three deal with the same owned resource.

The copy constructor builds a brand-new object, so it only has to make its own block and fill it:

```cpp
Bad(const Bad& other)                  // copy constructor: build a new object
    : data_(new int[3]) {
    std::copy(other.data_, other.data_ + 3, data_);
}
```

`other` is the object being copied. The initialiser list gives the new object its own three `int`s, and the body copies `other`'s numbers into them.

### Copy assignment: overwrite an object that already exists

Assignment is the harder one. The object on the left already owns a block, which must be given back, and assigning an object to itself must be safe:

```cpp
Bad& operator=(const Bad& other) {     // copy assignment: overwrite an existing one
    if (this != &other) {              // a = a must not destroy a's own data
        int* fresh = new int[3];
        std::copy(other.data_, other.data_ + 3, fresh);
        delete[] data_;
        data_ = fresh;
    }
    return *this;
}
```

Take it line by line:

- `this` is the hidden pointer to the object whose member function is running, from the const correctness lesson. `&other` is the address of `other`. So `this != &other`, read "this is not equal to the address of other", asks: is `other` a different object from me? For `a = a;` the answer is no, and there is nothing to do.
- Make the new block `fresh` and copy into it **first**. Only then `delete[]` the old block, and point `data_` at the new one. That order keeps the object valid at every step: at no moment does `data_` point at memory that has been given back.
- `return *this;` hands back the object itself, as a reference (the `Bad&` return type). That is what lets you [[chain assignments|chained-assignment]] like `a = b = c;`, the same as with `int`s.

### One counter for the whole class

The starter also has this line inside the class:

```cpp
static inline int copies = 0;
```

A **static data member** belongs to the class rather than to each object, like the static members in the lesson "Classes that keep their own rules". There is one counter, shared by every `Buffer`, and you reach it as `Buffer::copies`: "copies from Buffer". The word `inline` is what lets you give it its first value right there in the class.

**Watch out:** `Buffer b = a;` has an `=` sign in it, but it does **not** call `operator=`. `b` is being born on that line, so the copy constructor runs. Copy assignment only runs when the object on the left already exists, as in `c = a;` two lines after `Buffer c(4);`. Both paths make a copy, so both must do the deep copy, and both must count it.

In real code you would store a `std::vector<int>` and write none of this; the next lesson shows why. Writing it once by hand is how you understand what those types do for you.

::: context delete-brackets Two kinds of delete
`new int` makes one `int`; `new int[3]` makes an array of them. Each has its own way back: `delete` for one object, `delete[]` for an array. Mixing them up, such as `delete` on memory from `new[]`, is undefined behaviour. The program may seem fine, or it may crash, or quietly damage the heap. The compiler cannot always spot the mix-up, because an `int*` looks the same either way. That is one more reason modern C++ keeps raw arrays inside types like `std::vector`, which always use the right one.
:::

::: context double-free Why giving back twice is so bad
When memory is given back, the heap may hand that same block to the next `new`, for some other part of the program. A second `delete[]` then frees memory that now belongs to someone else, and the heap's own bookkeeping can be corrupted. The damage often shows up far away from the mistake, much later. Double frees and "use after free" bugs are among the most common ways attackers break into programs, which is why security teams hunt for them.
:::

::: context shallow-deep Two slips, one house
A shallow copy duplicates only the pointer, so both objects share one block. A deep copy duplicates the block too, so each object owns its own.

::: context pointer-arithmetic Adding to a pointer
Adding a number to a pointer moves it by that many *elements*, not bytes. An `int` usually takes 4 bytes, so `a + 3` is an address 12 bytes past `a`, which is exactly where a fourth `int` would start. That is also how `data[1]` works: it means `*(data + 1)`, "follow the pointer one element along". Pointing one past the end is allowed, as long as you never follow it with `*`; following it is undefined behaviour, the same as `*` on a vector's `end()`.
:::

::: context rule-of-three-name A rule of thumb with a long history
The rule of three has been taught to C++ programmers since the early 1990s. It is a rule of thumb, not a rule the compiler enforces: the compiler will happily write a shallow copy for a class with a hand-written destructor, and warn about nothing. The rule exists because the three functions share one job, looking after the owned block. Change how one of them treats the block and the other two almost always have to change with it.
:::

::: context chained-assignment Why assignment returns the object
For `int`s, `a = b = c;` means `a = (b = c);`: first `b` gets `c`'s value, then that result is given to `a`. For your own type to work the same way, `operator=` must return the object it has changed. Returning `*this` by reference, `Bad&`, hands back the object itself rather than a copy of it, so no extra copy is made along the way.
:::
--- task
`Buffer` owns an `int` array and frees it in its destructor, but a copy shares the array with the original. Give `Buffer` a **deep** copy constructor, `Buffer(const Buffer& other)`, and a deep copy assignment operator, `Buffer& operator=(const Buffer& other)`.

- Each copy gets its own array with the same size and the same numbers, so changing one buffer never changes the other. After `b = a;`, `b` has `a`'s size, even if it started with a different one.
- Both functions add 1 to the static counter `Buffer::copies` each time they copy.
- Assigning a buffer to itself must leave it unchanged.

No `main`: the checker supplies it.
--- starter
#include <algorithm>
#include <cstddef>

class Buffer {
public:
    static inline int copies = 0;

    explicit Buffer(std::size_t size) : size_(size), data_(new int[size]()) {}
    ~Buffer() { delete[] data_; }

    std::size_t size() const { return size_; }
    int get(std::size_t i) const { return data_[i]; }
    void set(std::size_t i, int value) { data_[i] = value; }

private:
    std::size_t size_;
    int* data_;
};
--- solution
#include <algorithm>
#include <cstddef>

class Buffer {
public:
    static inline int copies = 0;

    explicit Buffer(std::size_t size) : size_(size), data_(new int[size]()) {}
    ~Buffer() { delete[] data_; }

    Buffer(const Buffer& other) : size_(other.size_), data_(new int[other.size_]) {
        std::copy(other.data_, other.data_ + size_, data_);
        ++copies;
    }

    Buffer& operator=(const Buffer& other) {
        if (this != &other) {
            int* fresh = new int[other.size_];
            std::copy(other.data_, other.data_ + other.size_, fresh);
            delete[] data_;
            data_ = fresh;
            size_ = other.size_;
            ++copies;
        }
        return *this;
    }

    std::size_t size() const { return size_; }
    int get(std::size_t i) const { return data_[i]; }
    void set(std::size_t i, int value) { data_[i] = value; }

private:
    std::size_t size_;
    int* data_;
};
--- hint
Start with the copy constructor. It is building a new buffer, so in its initialiser list it takes `other.size_` and makes its own array with `new int[other.size_]`. Then it copies the numbers across with `std::copy` and adds 1 to `copies`.

=== cpp3-03 | Moving, and the rule of zero
--- teach
Last lesson `Buffer` learned to copy itself deeply: a new block, and every number copied across. That is correct, but it costs something. For a big buffer, copying means asking the heap for memory and copying every element. This lesson shows a cheaper way when the original is about to disappear anyway.

### Moving house

When you move house, you do not photocopy your furniture and then burn the old set. You carry it to the new place, and the old house is left empty.

Objects are often in the same spot. The source of a copy is very often about to die: a **temporary** (a value with no name, like `Buffer(4)` passed straight into a function), or a local variable being returned from a function. Copying something that is about to be thrown away is wasted work. It is far cheaper to **steal** its memory: take its pointer, and leave the source empty. That is a **move**.

### The move constructor

```cpp
Buffer(Buffer&& other) noexcept               // move constructor
    : size_(other.size_), data_(other.data_) {
    other.size_ = 0;
    other.data_ = nullptr;                    // the source must still be safe to destroy
}
```

The new object copies two members, the size and the pointer, and no elements at all. Then it empties the source. That last step matters: the source's destructor still runs later, and it will `delete[]` whatever `data_` holds. Setting it to `nullptr` makes that harmless, because [[deleting nullptr|delete-nullptr]] does nothing. Without it, both objects would free the same block: the double free from last lesson.

### && means "about to go away"

`Buffer&&`, with two ampersands, is an **rvalue reference**: a reference that binds only to things that are about to go away, such as temporaries. (One `&` is the ordinary reference you know.) The word [[rvalue|rvalue-word]] roughly means "a value with no lasting name".

So C++ picks the move constructor on its own when the source is a temporary, and the copy constructor when the source is an ordinary named variable that will live on.

### std::move gives permission

Sometimes you have a named variable and you know you are finished with it. `std::move(x)`, from `<utility>`, says so:

```cpp
Buffer a(3);
Buffer b = std::move(a);   // the move constructor runs: b takes a's block
// now a.size() is 0
```

`std::move` does [[not move anything by itself|move-is-a-cast]]. It is a cast: it says "you may treat `x` as expendable". The move constructor does the actual stealing.

After a move, the source is valid but unspecified: you may give it a new value or let it be destroyed, nothing more. Your `Buffer` happens to leave it empty, but you should not count on any particular value in general.

### Move assignment

A move can also overwrite an object that already exists, the way copy assignment does. It follows the same shape as last lesson's `operator=`:

```cpp
Buffer& operator=(Buffer&& other) noexcept {   // move assignment
    if (this != &other) {       // moving a buffer onto itself: nothing to do
        delete[] data_;         // give back my own block first
        data_ = other.data_;    // steal the source's block
        size_ = other.size_;
        other.data_ = nullptr;  // leave the source empty
        other.size_ = 0;
    }
    return *this;
}
```

Here freeing first is safe, because nothing new is allocated: the object takes a block that already exists.

### The rule of five

Adding the move constructor and move assignment to last lesson's three (destructor, copy constructor, copy assignment) gives the **rule of five**: a class that owns a raw resource should think about all five.

### Why noexcept

Both move functions are marked `noexcept`, read "no except". C++ has a way for a function to report an error by jumping straight out of it, called throwing an **[[exception|exceptions-word]]**. `noexcept` is a promise that this function never does that.

It matters because of how a `std::vector` grows. When it runs out of room, it asks for a bigger block and [[moves its elements across|vector-growth]]. If a move could fail halfway, the vector could not put things back the way they were. So it only uses your move constructor if it is marked `noexcept`. Otherwise, to stay safe, it **copies** every element instead.

**Watch out:** forgetting `noexcept` gives no error and no warning. Everything still works; vectors of your type are silently slower, because every time they grow they copy every element. When you write a move constructor or move assignment, write `noexcept` on it.

### The rule of zero

And now the best news. A class whose members already manage themselves should declare **none** of the five. That is the **[[rule of zero|rule-of-zero-name]]**. Members like `std::string`, `std::vector`, `std::unique_ptr`, or a class like your finished `Buffer`, already know how to copy, move and clean up. The compiler writes all five for the outer class, member by member, and each member does its own job correctly:

```cpp
struct Track {
    std::string title;
    std::vector<int> samples;
};   // copies, moves and cleans up correctly with no code at all
```

So the rule of five is for the few low-level types that own a raw resource. Everything built on top of them follows the rule of zero.

::: context delete-nullptr Why nullptr is a safe leftover
The C++ rules say that `delete` and `delete[]` on a null pointer do nothing at all. That is what makes an empty moved-from object safe: its destructor runs as usual, hands `nullptr` to `delete[]`, and nothing happens. The same trick shows up all over the standard library. A moved-from `std::unique_ptr` is guaranteed to hold `nullptr`, so its destructor has nothing to delete.
:::

::: context rvalue-word Where "rvalue" comes from
The name goes back to the language C. An *lvalue* was something that could stand on the **left** of an `=`, like a variable: `x = 5;`. An *rvalue* could only stand on the **right**, like `5` or `a + b`: you cannot write `5 = x;`. Modern C++ has refined these ideas, but the rough picture still works: an lvalue has a name and lives on; an rvalue is a temporary result that disappears at the end of the line. An rvalue reference, `&&`, is the kind of reference that can bind to one of those.
:::

::: context move-is-a-cast std::move is only a label
Inside the library, `std::move(x)` is about one line long: it converts `x` to an rvalue reference, the same as writing `static_cast<Buffer&&>(x)`. No memory changes hands until a move constructor or move assignment receives that reference and does the stealing. If a type has no move functions, "moving" it quietly copies it instead. The name was chosen because of what it lets happen next, not because of what it does itself.
:::

::: context exceptions-word Exceptions, and where they come back
In much C++ code, a function that hits an error can `throw` an exception, which jumps out through every waiting function until some code `catch`es it. This app compiles with exceptions switched off, the way a lot of embedded and flight software does, so `throw` and `try` do not compile here. The lesson "Errors without exceptions", later in this course, shows the other ways C++ reports errors. You still write `noexcept`, because the standard library reads it.
:::

::: context vector-growth How a vector grows
A vector keeps its elements in one block. When the block is full and you `push_back` one more, it asks for a bigger block (usually 1.5 to 2 times the size), transfers every element across, then frees the old block. With a `noexcept` move, each transfer steals a pointer. Without it, each transfer is a full deep copy.

::: context rule-of-zero-name Write no code, get no bugs
The name "rule of zero" became popular in 2012, from a blog post by R. Martinho Fernandes, as the natural partner of the rule of three and the rule of five. The idea is that each class should do one job: either own a resource (and then it writes the special functions carefully), or combine other types (and then it writes none). Code you never write cannot hold a double free. In well-designed code, most classes declare none of the five.

    static inline int copies = 0;
    static inline int moves = 0;

    explicit Buffer(std::size_t size) : size_(size), data_(new int[size]()) {}

        ++copies;
    }

            int* fresh = new int[other.size_];
            std::copy(other.data_, other.data_ + other.size_, fresh);
            delete[] data_;
            data_ = fresh;
            size_ = other.size_;

    std::size_t size_;
    int* data_;
};

=== cpp3-04 | Smart pointers: unique_ptr and shared_ptr
--- teach
Last lesson ended with the rule of zero: build your classes from members that already look after themselves. Writing the rule of five for every owning type would be tiring. Smart pointers are those ready-made members for single objects on the heap: RAII, already written. You met `std::unique_ptr` in the basics course's pointers lesson. Now you will use it to build a tree, and meet its partner for sharing, `std::shared_ptr`. Both need `#include <memory>`.

### std::unique_ptr: exactly one owner

**`std::unique_ptr<T>`** has exactly one owner. It deletes its object when it goes away. It cannot be copied, only moved: its copy functions are deleted, like your `FileHandle`'s, and it has the move functions from last lesson. This is the smart pointer to reach for first.

```cpp
auto p = std::make_unique<Node>();        // p owns a new Node
std::unique_ptr<Node> q = std::move(p);   // ownership moves to q; p is now null
```

`std::make_unique<Node>()` makes a new `Node` on the heap, with its members set to zero or empty, and hands back a `unique_ptr` that owns it. After the move, `q` owns the `Node` and `p` holds `nullptr`. To reach a member through the pointer, use the arrow from the intermediate course's maps lesson: `q->value` means "follow `q`, then take `value`".

### A tree of owners

Picture a spacecraft's parts list. The spacecraft has subsystems; each subsystem has parts; some parts have smaller parts. That shape is a **[[tree|tree-words]]**: each item is a **node**, the top one is the **root**, the nodes hanging under a node are its **children**, and a node with no children is a **leaf**.

Trees are the classic fit for `unique_ptr`, because each parent owns its children:

```cpp
struct Node {
    int value;
    std::vector<std::unique_ptr<Node>> children;
};
```

Read `std::vector<std::unique_ptr<Node>>` from the outside in: a vector of unique pointers, each owning one `Node`. Each child is a `Node`, which has its own `children`, and so on down.

Destroying the root destroys the whole tree, with no cleanup code at all. The root's destructor destroys its vector; the vector destroys each `unique_ptr`; each `unique_ptr` deletes its child; and each child does the same for its own children. RAII, all the way down.

### Adding a child

```cpp
Node root{1, {}};                                   // value 1, no children yet
root.children.push_back(std::make_unique<Node>());  // add one child
Node& kid = *root.children.back();                  // the new child
kid.value = 2;
```

- `Node root{1, {}}` fills the members in order: `value` is 1, and the empty braces `{}` give an empty `children` vector.
- `push_back` is handed a temporary `unique_ptr`, so it moves it in. No copy is needed, which is lucky, since a `unique_ptr` cannot be copied.
- `.back()` gives the **last** element of a vector: here, the `unique_ptr` that was added last. The `*` in front follows it to the `Node` it owns.
- `Node& kid` is a reference to that node, not a copy, so setting `kid.value` changes the child inside the tree.

### Walking a tree with recursion

The basics course's recursion lesson showed a function that calls itself on a smaller problem, with a base case that stops it. A tree is made for this, because its shape is itself recursive: every child is the root of a smaller tree.

To count the nodes in a tree, count this node, then add the count for each child's tree:

```cpp
int count_nodes(const Node& n) {
    int total = 1;                                  // this node
    for (const auto& child : n.children) {
        total += count_nodes(*child);               // each child's whole tree
    }
    return total;
}
```

- `*child` turns a child's `unique_ptr` into the `Node&` it owns, which is what `count_nodes` takes.
- The base case needs no `if`. A leaf has no children, so the loop runs zero times and the function returns 1. That is where the [[recursion stops|recursion-depth]].
- For the root in the example above, with one child, `count_nodes(root)` is 2.

Adding the children's answers suits a sum. Some questions need the **largest** of the children's answers instead. `std::max(a, b)`, from `<algorithm>`, gives the larger of two values: `std::max(3, 8)` is 8.

**Watch out:** in the loop, write `const auto& child`, with the `&`. Plain `auto child` would try to copy each `unique_ptr` out of the vector, and copying one is deleted, so the program does not compile. The error mentions a deleted function, the same kind of error as copying a `FileHandle` in the RAII lesson.

### std::shared_ptr: many owners, one count

Some things have no single owner. Picture a set of game sprites that all draw the same grass picture. Loading the picture once and sharing it is the sensible thing; but which sprite should delete it? The answer: whichever is last.

**`std::shared_ptr<T>`** is shared ownership. It keeps a **[[reference count|ref-count]]**: how many `shared_ptr`s currently point at the object. Copying a `shared_ptr` adds one to the count, and each one that goes away takes one off. The object is deleted when the **last** `shared_ptr` to it goes away. `use_count()` tells you the count.

```cpp
auto tex = std::make_shared<Texture>(Texture{"grass.png"});   // count 1
auto a = tex;          // count 2
auto b = tex;          // count 3
```

- `std::make_shared` makes the object and the `shared_ptr` that owns it, like `make_unique`. `Texture{"grass.png"}` builds a `Texture` with its `file` member set, and `make_shared` places that value in the new shared object.
- `auto a = tex;` copies the pointer, **not** the texture. There is still one `Texture`; now three pointers share it, and `tex.use_count()` is 3. The arrow works here too: `b->file` is `"grass.png"`.

Two cautions. Shared ownership makes it hard to tell when an object will die, so do not reach for `shared_ptr` by default; use it when there genuinely is no single owner. And two objects holding `shared_ptr`s to **each other** never reach a count of zero: a [[leak that never ends|cycles]]. You break such cycles with `std::weak_ptr`, which watches an object without owning it.

### Owning is not the same as using

Code that only *uses* an object, like `count_nodes`, takes a plain reference or raw pointer: `const Node&` or `Node*`. It does not care who owns the node. [[Ownership is the smart pointer's job|owner-vs-user]], not every function's.

::: context recursion-depth How deep can it go
Each waiting call uses some of the call stack, as the basics course's recursion lesson showed. A tree a few levels deep is no problem. A tree shaped like a long chain, a million nodes each with one child, could run out of stack. This is one reason NASA JPL's "Power of Ten" rules for safety-critical code forbid recursion altogether: flight code must be able to prove how much stack it will ever need. Code written to rules like these walks its trees with loops instead. For everyday programs, recursion on trees is the clearest way to write it.

::: context ref-count Counting the owners
The count lives in a small extra block that `make_shared` creates next to the object, called the control block. Every `shared_ptr` to the object points at it too. Copying a `shared_ptr` adds one; destroying or reassigning one takes one away; the one that brings it to zero deletes the object. The counting is made safe for programs that run several tasks at once, which makes copying a `shared_ptr` a little slower than copying a raw pointer. A `unique_ptr` has no count at all, and costs no more than a raw pointer.

::: context cycles Two owners holding each other
Picture two objects, A and B. A holds a `shared_ptr` to B, and B holds one to A. When the rest of the program lets go of both, each still has a count of 1, because the other one is holding it. Neither count reaches zero, so neither is ever deleted. A `std::weak_ptr` points at an object without adding to its count. When you need the object, its `lock()` member gives you a `shared_ptr` to it, or an empty one if the object is already gone. So a child can point back at its parent with a `weak_ptr` and never keep it alive by accident.
:::

::: context owner-vs-user Borrowing, not owning
The C++ Core Guidelines, a set of rules written by Bjarne Stroustrup and Herb Sutter with many others, put it this way: for general use, take `T*` or `T&` arguments rather than smart pointers. A function that takes `const Node&` works for a node owned by a `unique_ptr`, a `shared_ptr`, or a plain local variable, and it cannot accidentally change who owns it. Take a smart pointer as a parameter only when the function really does take part in ownership, such as storing it or handing it on.
:::

--- solution
#include <algorithm>
#include <memory>
#include <string>
#include <vector>

struct Node {
    int value;
    std::vector<std::unique_ptr<Node>> children;
};

struct Texture {
    std::string file;
};

std::unique_ptr<Node> make_node(int value) {
    auto node = std::make_unique<Node>();
    node->value = value;
    return node;
}

Node& add_child(Node& parent, int value) {
    parent.children.push_back(make_node(value));
    return *parent.children.back();
}

int tree_sum(const Node& root) {
    int total = root.value;
    for (const auto& child : root.children) total += tree_sum(*child);
    return total;
}

int tree_depth(const Node& root) {
    int deepest = 0;
    for (const auto& child : root.children) deepest = std::max(deepest, tree_depth(*child));
    return deepest + 1;
}

std::vector<std::shared_ptr<Texture>> share_texture(const std::string& file, int n) {
    std::vector<std::shared_ptr<Texture>> out;
    if (n <= 0) return out;
    auto tex = std::make_shared<Texture>(Texture{file});
    for (int i = 0; i < n; ++i) out.push_back(tex);
    return out;
}
--- hint
`make_node`: make the node with `std::make_unique<Node>()`, set its value through the arrow (`node->value = value;`), and return it. `add_child` can reuse it: `parent.children.push_back(make_node(value));`, then return the new child with `*parent.children.back()`.
--- hint
`tree_sum` and `tree_depth` are recursive, like `count_nodes` in the explanation: loop over `const auto& child : root.children` and call the same function on `*child`. For the sum, start at `root.value` and add each child's sum. For the depth, keep the largest child depth with `std::max`, then return it plus 1 for this node.
--- hint
`share_texture`: if `n <= 0`, return an empty vector. Otherwise make **one** texture with `std::make_shared<Texture>(Texture{file})`, then `push_back` that same `shared_ptr` `n` times in a loop. Copying it shares the texture; it does not make a new one.

=== cpp3-05 | Function templates
--- teach
Last lesson, `std::make_unique<Node>()` and `std::shared_ptr<Texture>` both took a type in angle brackets `< >`. You have been filling in types like that since the basics course: `std::vector<int>`, `std::map<std::string, int>`. Each of those is a **template**: a pattern the compiler completes with the type you hand it. This lesson and the next show you how to write your own. This one is about functions.

### The same function, three times

Say you need the largest number in a list of `int`s:

```cpp
int largest(const std::vector<int>& v) {
    int best = v[0];
    for (const int& x : v) if (best < x) best = x;
    return best;
}
```

Then you need it for a list of `double`s. Then for a list of `std::string`s, where the "largest" string is the one that comes last in dictionary order. Each time you would copy the function and change the type in three places. The steps never change; only the type does. And copies drift apart: fix a bug in one, and the others keep it.

### A function with a blank for the type

Picture a form letter: "Dear ______, your parcel has shipped." You write the letter once and fill in the blank for each person. A **function template** is a function written once, with a blank where the type goes:

```cpp
template <typename T>
T largest(const std::vector<T>& v) {
    T best = v[0];
    for (const T& x : v) if (best < x) best = x;
    return best;
}
```

Read the first line as "a template, for any type T". Word by word:

- `template` says that what follows is a pattern, not yet a real function.
- The angle brackets `< >` hold the **template parameters**: the blanks.
- `typename T` makes one blank, named `T`, that stands for [[a type|typename-word]]. `T` is only a name, the way a function's parameters have names. Calling it `T`, for "type", is the custom.

After that line, write `T` everywhere the type would go: the vector's element type, the local variable `best`, the loop variable and the return type.

### The compiler fills in the blank

You call a template like any other function:

```cpp
largest(std::vector<int>{3, 8, 1});            // 8: T is int
largest(std::vector<std::string>{"b", "a"});   // "b": T is std::string
```

The compiler looks at the argument, sees a `std::vector<int>`, and works out that `T` must be `int`. Working out the type from the arguments is called **deducing** it. The compiler then writes a real `largest` for `int`, compiled exactly like a function you typed by hand. Called with strings, it writes a second, separate `largest` for `std::string`. Each real function made from a template is called an **[[instantiation|instantiation]]**: one real case of the pattern.

### What T has to be able to do

The template never lists which types are allowed. It asks only for what its body does with `T`. Here that is two things: a `T` can be copied (`T best = v[0];`), and two `T`s can be compared with `<`. An `int`, a `double` and a `std::string` can all do both.

Call it with a type that has no `<`, and you get a compile error [[pointing inside the template|template-errors]]:

```cpp
struct Point { int x, y; };
largest(std::vector<Point>{{1, 2}});   // compile error: no < for two Points
```

C++20 has *concepts*, which let a template state its requirements up front and make those errors much easier to read. They come in the expert course.

### Deduction must agree

Deduction has one trap. Every place `T` appears must deduce the **same** type. Here is a template that counts how many items equal `x`:

```cpp
template <typename T>
int count_equal(const std::vector<T>& v, const T& x);

std::vector<std::string> names = {"ada", "lin"};
count_equal(names, "ada");   // error: T is std::string from names,
                             // but an array of 4 chars from "ada"
```

From `names`, `T` must be `std::string`. But `"ada"` is not a `std::string`. It is a string literal, and as the overloading lesson in the intermediate course showed, its type is [[an array of chars|literal-type]]. Two different answers for one blank, so the compiler gives up. It does not try turning `"ada"` into a `std::string` first: deduction only looks for a type that fits exactly.

### Two ways out

**A second blank.** Give the second parameter its own template parameter, `U`:

```cpp
template <typename T, typename U>
int count_equal(const std::vector<T>& v, const U& x);
```

Now `T` is `std::string` and `U` is the array type, and the two never have to agree. Inside, `item == x` still works, because a `std::string` can be compared with a string literal using `==`.

**Tell the compiler not to deduce from `x`.** `std::type_identity_t<T>`, from `<type_traits>`, names the very same type as `T`, but the compiler [[never deduces through it|type-identity]]:

```cpp
template <typename T>
int count_equal(const std::vector<T>& v, const std::type_identity_t<T>& x);
```

Now `T` comes only from the vector, so it is `std::string`. Once `T` is known, `x` is a `const std::string&`, and `"ada"` converts to a `std::string` the ordinary way, as it does for any function that takes one.

### Naming the type yourself

You can also skip deduction and write the type in angle brackets after the function's name:

```cpp
largest<double>({3, 2.5, 1});   // 3: T is double, so the braces become a std::vector<double>
```

Without `<double>` this call does not compile: a list in braces `{ }` has no type of its own, so there is nothing to deduce `T` from.

### Changing a vector in place

A template can also change the vector it is given. Take the vector by plain reference, `std::vector<T>&`, with no `const`, and loop with `T&` so each change lands in the vector itself, not in a copy:

```cpp
template <typename T>
void double_all(std::vector<T>& v) {
    for (T& x : v) x = x + x;   // {1, 5} becomes {2, 10}; {"ab"} becomes {"abab"}
}
```

**Watch out:** the deduction trap strikes whenever the same `T` appears in two or more parameters. Take `template <typename T> void clamp_all(std::vector<T>& v, const T& lo, const T& hi)`. With a `std::vector<int>` called `v`, `clamp_all(v, 0, 10)` works, but `clamp_all(v, 0, 10.5)` does not compile: `T` is `int` from `v` and from `0`, but `double` from `10.5`. When you see "deduced conflicting types" or "no matching function", check that every argument gives `T` the same type.

::: context typename-word Why typename, and sometimes class
`typename T` says "`T` stands for a type". You will also meet `template <class T>`. In this spot the two words mean exactly the same thing, and `T` can still be `int`, which is not a class at all. `class` came first: Bjarne Stroustrup, who created C++, reused an existing keyword rather than add a new one. `typename` arrived with the first official standard, C++98. Many programmers write `typename` because it says what it means. Template parameters can also be values instead of types; the next lesson shows how.
:::

::: context instantiation One pattern, many real functions
A template works like a cookie cutter. The cutter is not a cookie; each time you press it into dough you get a real one. `largest<int>` and `largest<std::string>` end up as two separate functions in the finished program, each as fast as one written by hand, because all the filling-in happens while compiling. There is a cost: each type you use adds its own copy of the code, and heavy use of templates makes compiling slower. A type nobody uses costs nothing, because no code is made for it.

::: context template-errors Reading an error from inside a template
The compiler only discovers the missing `<` when it writes out `largest` for `Point` and reaches the line `best < x`. So the first error points into the template's body, not at your call. The next lines lead back to you: g++ adds a line ending "required from here", and clang adds a note ending "requested here", each naming the line in your code that asked for this instantiation. With the standard library's own templates these messages can run to dozens of lines. Read the first error, then find the "required from" or "requested here" line that names your own file.
:::

::: context literal-type What "ada" really is
In memory, `"ada"` is four `char`s in a row: `'a'`, `'d'`, `'a'` and the hidden zero byte that marks the end. So its type is "array of 4 const chars", written `const char[4]`. In the overloading lesson it arrived in a function as a `const char*`, a pointer to its first letter, because an array passed by value turns into a pointer. A reference parameter like `const T&` keeps the array as it is, so deduction sees the array type. Either way it is not a `std::string`, and deduction will not pretend it is.
:::

::: context type-identity A type the compiler will not look through
`std::type_identity` is a tiny struct from C++20 whose only content says "my type is `T`". `std::type_identity_t<T>` is short for "the type inside `std::type_identity<T>`"; the standard library ends such shortcuts in `_t`. To deduce `T` from it, the compiler would have to guess which `T` produces a matching type inside, and the language rules say it must not guess. A parameter like that is called a **non-deduced context**. `T` is decided by the other parameters, and the argument is then converted to it. Before C++20, programmers wrote this same two-line struct themselves.
:::

=== cpp3-06 | Class templates
--- teach
Last lesson you wrote functions with a blank for the type. A class can have a blank too. You have used plenty of classes like that: `std::vector<T>` from the basics course, `std::optional<T>` from the intermediate course, `std::unique_ptr<T>` from the smart pointers lesson. Now you will write your own.

### A class with a blank for the type

A **class template** is a blueprint for a whole family of classes. You write the class once, with `T` for the type, and each `Box<int>` or `Box<std::string>` you use becomes a real, separate class:

```cpp
template <typename T>
class Box {
public:
    explicit Box(T value) : value_(std::move(value)) {}
    const T& get() const { return value_; }
private:
    T value_;
};
```

The first line is the same as for a function template: "a template, for any type T". Inside the class, `T` is used like any type:

- `T value_;` is a member that holds one `T`.
- The constructor takes a `T` called `value`. `std::move(value)` is the move from the moving lesson: `value` is the constructor's own copy, about to go away, so its insides can be handed to `value_` instead of copied a second time.
- `get()` hands back a `const T&`, a read-only reference, so looking at a big `T` costs no copy.

### Using it

```cpp
Box<int> a(5);              // a Box holding an int
Box<std::string> b("hi");   // a Box holding a std::string
Box c(2.5);                 // C++17: T deduced as double from the constructor
```

Usually you write the type in angle brackets, as with `std::vector<int>`. Since C++17 the compiler can also [[work it out from the constructor|ctad]], as in `Box c(2.5)`.

Member functions written inside the class body need no extra syntax: no second `template` line, no `<T>` after their names.

### Only what you call gets built

The compiler writes out a member function for a particular `T` only when some code calls it. So a `Box<T>` whose `print()` needs `<<` still works for a `T` that has no `<<`, as long as nobody calls `print()`:

```cpp
// inside Box, one more member:
void print() const { std::cout << value_; }

struct Point { int x, y; };
Box<Point> p(Point{1, 2});   // fine
p.get();                     // fine
// p.print();                // would not compile: there is no << for a Point
```

### A value as a template parameter

Template parameters do not have to be types. A parameter can also be a **value** that is known while compiling:

```cpp
template <typename T, std::size_t N>
class Recent { /* keeps at most N items */ };

Recent<int, 3> last_three;
```

Read `std::size_t N` as "a whole number N that cannot be negative", the same `std::size_t` that `v.size()` gives back. The number becomes [[part of the type|value-parameter]]: `Recent<int, 3>` and `Recent<int, 4>` are two different classes, as different as `Box<int>` and `Box<double>`.

### Catching a nonsense size

A `Recent` that keeps zero items makes no sense. Because `N` is known while compiling, the compiler itself can refuse it. **`static_assert`** is a [[check made while compiling|static-assert]]: when its condition is false, the compile stops with your message.

```cpp
template <typename T, std::size_t N>
class Recent {
    static_assert(N > 0, "Recent needs room for at least one item");
    // ...
};

Recent<int, 0> r;   // compile error: static assertion failed: Recent needs room for at least one item
```

The message is optional: `static_assert(N > 0);` works too, with a plainer error.

### Taking from something that might be empty

The task's first class is a **stack**: a container you add to and take from only at the top, like a [[stack of plates|lifo]]. The last item put on is the first one taken off.

"Take the top item" can fail: the stack might be empty. Returning **`std::optional<T>`** is a clean design, because the caller cannot forget that there might be nothing. Here is the same idea in a small function template that takes the last item of a vector:

```cpp
template <typename T>
std::optional<T> take_last(std::vector<T>& v) {
    if (v.empty()) return std::nullopt;   // nothing to give
    T last = std::move(v.back());         // move the item out first
    v.pop_back();                         // then remove its slot
    return last;                          // arrives wrapped in an optional
}
```

### Looking without taking

"Look at the top" should not remove anything, and should not copy either. Return a **`const T*`**: a pointer to the item, read-only, or `nullptr` when there is nothing to see. `&v.back()` is "the address of the last element", with the address-of `&` from the pointers lesson:

```cpp
template <typename T>
const T* peek_last(const std::vector<T>& v) {
    return v.empty() ? nullptr : &v.back();
}
```

The caller checks the pointer before using it: `if (const int* p = peek_last(v)) { ... *p ... }`. Why [[a pointer and not an optional|pointer-not-optional]]? An optional would hold its own copy of the item; the pointer only points at the one already there.

### A container that is cheap at both ends

The second class keeps the most recent items and drops the oldest. Taking from the front of a `std::vector` is slow, because every other element has to shift down one place. One more standard container fits better. **`std::deque<T>`**, from `<deque>` and said "deck", is like a vector that is also cheap to change at the **front**:

```cpp
std::deque<int> q = {1, 2, 3};
q.push_back(4);    // 1 2 3 4
q.pop_front();     // 2 3 4: the oldest is gone
q.front();         // 2
q.back();          // 4
```

To hand the items back as a `std::vector`, build one from the deque's range, as the maps and sets lesson did from a set: `std::vector<int>(q.begin(), q.end())` keeps their order, front first.

**Watch out:** in a function that removes the top item, read the item **before** you remove it. `pop_back()` destroys the last element, so reading `back()` after it gives a different element, or, if that was the only one, undefined behaviour. And calling `back()` or `pop_back()` on an empty vector is undefined behaviour too, which is why `take_last` checks `empty()` first.

::: context ctad Deducing a class's type
The feature is called **class template argument deduction**, CTAD for short, and it arrived in C++17. The compiler looks at the constructor's parameters, as it would for a function template. It can surprise you: `Box d("hi");` gives a `Box<const char*>`, holding a pointer, not a `Box<std::string>`, because a string literal passed by value arrives as a pointer. When the type matters, write it out: `Box<std::string> b("hi");`. Before C++17 you always had to, which is why helper functions like `std::make_pair` existed: functions could deduce, classes could not.
:::

::: context value-parameter Sizes fixed before launch
The standard library's `std::array<T, N>` works this way: `std::array<double, 3>` is exactly three doubles, stored inside the object, with no heap memory at all. Flight software likes sizes fixed like this. NASA JPL's "Power of Ten" rules for safety-critical code forbid allocating memory on the heap after the program has started up, because a heap can run out or break into scattered pieces in the middle of a mission. A container whose size is part of its type can never grow past what was planned and tested.
:::

::: context static-assert Failing on the ground, not in flight
An ordinary check runs while the program runs, so a mistake is only found if that line happens to run during a test. A `static_assert` is checked every time the program is compiled. If it fails, there is no program at all, so the mistake can never reach a spacecraft. It arrived in C++11, and it works on anything the compiler knows while compiling: template parameters, sizes of types, `constexpr` values. `static_assert(sizeof(int) == 4);` is a common one, guarding code that assumes an `int` is four bytes.
:::

::: context lifo Last in, first out
Put plates 1, 2 and 3 on a pile. The one you can take is 3, the last one added. Programmers call this **LIFO**, "last in, first out". Adding is traditionally called *push* and removing *pop*, the same words `std::vector` uses for `push_back` and `pop_back`. Your program runs on a stack too: each function call puts its local variables on top of the **call stack**, and they come off when it returns.

::: context pointer-not-optional Why peeking returns a pointer
`std::optional<T>` keeps its value inside itself, so returning one means copying the top item into it. For a stack of big strings that is wasted work, only to look. A reference, `const T&`, would avoid the copy, but a reference must always refer to something, and an empty stack has nothing to refer to. A pointer can do both jobs: it points at the real item, and `nullptr` means "nothing there". The catch is the one from the pointers lesson: the pointer is only good while the item is still in the stack. After a `pop`, it points at nothing valid.

`Stack<T>`, a last-in-first-out stack:

- `void push(const T& x)` puts `x` on top.
- `std::optional<T> pop()` removes the top item and returns it, or returns `std::nullopt` when the stack is empty.
- `const T* top() const` gives a pointer to the top item without removing it, or `nullptr` when the stack is empty.
- `std::size_t size() const` returns how many items it holds, and `bool empty() const` says whether it holds none.

`Recent<T, N>`, which keeps only the last `N` items added:

- `void add(const T& x)` adds `x`. When it already holds `N` items, the oldest is dropped first.
- `std::vector<T> items() const` returns the items it holds, oldest first. After adding 1, 2, 3, 4 and 5 to a `Recent<int, 3>`, `items()` is `{3, 4, 5}`. With fewer than `N` added, it returns all of them.

#include <cstddef>
#include <deque>
#include <optional>
#include <string>
#include <vector>

template <typename T>
class Stack {
public:
    void push(const T& x) { items_.push_back(x); }
    std::optional<T> pop() {
        if (items_.empty()) return std::nullopt;
        T top = std::move(items_.back());
        items_.pop_back();
        return top;
    }
    const T* top() const { return items_.empty() ? nullptr : &items_.back(); }
    std::size_t size() const { return items_.size(); }
    bool empty() const { return items_.empty(); }
private:
    std::vector<T> items_;
};

template <typename T, std::size_t N>
class Recent {
    static_assert(N > 0, "Recent needs room for at least one item");
public:
    void add(const T& x) {
        if (items_.size() == N) items_.pop_front();
        items_.push_back(x);
    }
    std::vector<T> items() const { return std::vector<T>(items_.begin(), items_.end()); }
private:
    std::deque<T> items_;
};

=== cpp3-07 | Operator overloading: a Fraction type
--- teach
Last lesson your `Stack` and `Recent` worked for any type. But to add, compare or print a type you write yourself, you still need named functions: `add(a, b)`, `equal(a, b)`. An `int` gets `+`, `==`, `<` and `std::cout << x` for free. This lesson gives your own types the same symbols, and ends with a fraction type that does exact arithmetic, with no rounding at all.

### An operator is a function with a special name

On a calculator, the `+` key works for whole numbers and decimals alike. C++ lets you teach `+` what to do for your own type too. **Operator overloading** means writing what a symbol like `+` or `==` does for your type. You write it as a function whose name is the word `operator` followed by the symbol:

```cpp
struct Vec2 { double x, y; };   // for example a velocity: an x part and a y part

Vec2 operator+(const Vec2& a, const Vec2& b) {
    return {a.x + b.x, a.y + b.y};
}

Vec2 v{3, 4};
Vec2 w{1, -2};
Vec2 sum = v + w;   // (4, 2)
```

When the compiler sees `v + w` with two `Vec2`s, it [[calls operator+(v, w)|operator-call]] for you. The function takes both sides by `const` reference, so nothing is copied or changed. `return {a.x + b.x, a.y + b.y};` builds the new `Vec2` from the values in braces, in the order the members are listed.

### Comparing with ==

`==` is an operator like any other. It answers with a `bool`:

```cpp
bool operator==(const Vec2& a, const Vec2& b) {
    return a.x == b.x && a.y == b.y;
}
```

In C++20, writing `==` also gives you `!=` for free: the compiler rewrites `a != b` as "not `a == b`".

### Printing with <<

`<<` is read "put to". To make `std::cout << v` work, write an `operator<<` whose left side is a stream:

```cpp
std::ostream& operator<<(std::ostream& out, const Vec2& v) {
    return out << "(" << v.x << ", " << v.y << ")";
}

std::cout << v << "\n";   // (3, 4)
```

`std::ostream`, from `<ostream>`, means "output stream". It is [[the type behind std::cout|ostream-family]], and behind `std::ostringstream` too, so this one function prints to both. It takes the stream by reference and **returns the stream**. That is what lets calls chain: `out << a << b` runs as `(out << a) << b`, so the second `<<` puts `b` into whatever the first one gave back, which is `out` again.

### Mean what the symbol means

The rule that keeps operators pleasant: `+` adds, `==` compares, `<` puts things in order. Someone reading `a + b` expects a sum. An `operator+` that prints, or a `<` that secretly changes something, is a trap for every reader after you.

### A whole number can turn into your type

The rest of the lesson builds a `Fraction`. A constructor like this one has **default arguments**, as in the overloading lesson of the intermediate course:

```cpp
class Fraction {
public:
    Fraction(long long num = 0, long long den = 1);   // Fraction(3) is 3/1
    // ...
};
```

`long long` is a whole number at least 64 bits wide, far bigger than an `int`. In the intermediate course you put `explicit` on one-value constructors to stop surprise conversions. Here the constructor is left **not** `explicit` on purpose: a whole number really is a fraction, 3 is 3/1, so C++ may turn `1` into `Fraction(1)` whenever a `Fraction` is needed.

### Write two-sided operators outside the class

An operator with two sides, like `+` or `==`, is called a **binary operator**. You could write one as a member function, with the left side as the object:

```cpp
// as a member: the left side is the object itself
Fraction operator+(const Fraction& b) const;

Fraction half(1, 2);

half + 1;   // fine: 1 converts to Fraction(1)
1 + half;   // compile error: 1 is an int, and an int has no member operator+
```

The left side of a member call is [[never converted|left-side]]. Written as a **non-member** function, outside the class, both sides are ordinary parameters, and both can be converted:

```cpp
Fraction operator+(const Fraction& a, const Fraction& b);

half + 1;   // fine
1 + half;   // fine: 1 becomes Fraction(1)
```

So write binary operators as non-member functions. They can reach the data through public members like `num()` and `den()`.

### An invariant makes == easy

In the intermediate course, a class kept an **invariant**: a rule that is true of every object, always. For a fraction, choose this rule: it is always stored **in lowest terms, with a positive denominator**. Then 2/4 and 1/2 are stored identically, as 1 and 2, and `==` only has to compare two pairs of numbers.

The constructor makes the rule true. First the sign: if the denominator is negative, flip the sign of both parts, which does not change the value. Then reduce: divide both parts by their **greatest common divisor**, the biggest whole number that divides both. `std::gcd`, from `<numeric>`, [[works it out|gcd]]:

```cpp
std::gcd(6, 4);    // 2
std::gcd(-6, 4);   // 2: it ignores signs
std::gcd(0, 5);    // 5, so 0/5 becomes 0/1
```

So 6/−4 becomes −6/4 after the sign step, and −3/2 after dividing both by 2.

### Arithmetic on fractions

Each operator builds a new `Fraction` from the parts and lets the constructor tidy it up. These are the school rules, with `b` and `d` the denominators:

- add: a/b + c/d = (a·d + c·b) / (b·d)
- subtract: a/b − c/d = (a·d − c·b) / (b·d)
- multiply: a/b · c/d = (a·c) / (b·d)
- divide: a/b ÷ c/d = (a·d) / (b·c), multiplying by the flipped fraction

For 1/2 + 1/3: (1·3 + 1·2) / (2·3) = 5/6. The products in these formulas [[grow fast|overflow]], which is one more reason to reduce every answer as soon as it is made. Dividing by a negative fraction gives a negative denominator, and the constructor flips it, so the invariant holds whatever the operator produces.

### Comparing without decimals

Is 1/3 less than 1/2? Turning both into decimals means rounding, and rounding can make two different fractions look equal. Instead, **cross-multiply**. With positive denominators, a/b < c/d is true exactly when a·d < c·b:

```cpp
// is 1/3 < 1/2 ?   1·2 = 2  and  1·3 = 3,  and 2 < 3, so yes
// in code, for two fractions x and y:
x.num() * y.den() < y.num() * x.den()
```

This is exact: only whole numbers, no rounding. It needs the denominators to be [[positive|cross-multiply]], which your invariant already promises.

C++20 can also generate all six comparisons, `<`, `<=`, `>`, `>=`, `==` and `!=`, from one operator, `operator<=>`, nicknamed the [[spaceship operator|spaceship]]. But writing `==` and `<` yourself first is the best way to see what they mean.

**Watch out:** a simple `==` that compares the parts is only right because every `Fraction` is reduced. If the constructor skips the reducing, `Fraction(2, 4) == Fraction(1, 2)` is false although both are one half. Make every new fraction, including every operator's answer, go through the constructor, so no unreduced fraction can exist at all.

::: context operator-call What a + b really is
To the compiler, `v + w` is a call to a function named `operator+`. You can even write the call out in full, `operator+(v, w)`, and it does the same thing. There are limits. You cannot invent new symbols, like `**` for powers. You cannot change how many sides an operator has, or which one goes first: `a + b * c` still does the `*` first, whatever your types are. And at least one side must be a class or an enum, so nobody can change what `1 + 2` means.
:::

::: context ostream-family One function for every output stream
`std::cout` is a `std::ostream`. So is a `std::ostringstream`, the string stream from the intermediate course, and so is a `std::ofstream`, which writes to a file. The last two are kinds of `std::ostream`, built from it; the virtual functions lesson shows how one class is built from another. That is why one `operator<<` taking `std::ostream&` works for all of them. The stream is passed and returned by reference because a stream cannot be copied: two copies of `std::cout` writing to one screen would make no sense.
:::

::: context left-side Why the left side is never converted
For a member function, `half + 1` means `half.operator+(1)`: the left side is the object the function belongs to. To call a member function, C++ must already have an object of the right class; it will not build a temporary `Fraction` out of `1` only to find a member on it. The argument in the parentheses is different: it is an ordinary parameter, and ordinary parameters get conversions. A non-member puts both sides in the parentheses, so both get the same treatment. Mathematics says `1 + half` and `half + 1` are equal, and the non-member version keeps that true.
:::

::: context gcd The oldest algorithm still in use
`std::gcd` uses the idea in Euclid's *Elements*, written about 300 BC. Replace the pair (a, b) with (b, a % b), and repeat until the second number is 0; the first is then the answer. For 48 and 18: 48 % 18 is 12, 18 % 12 is 6, 12 % 6 is 0, so the answer is 6.

::: context overflow Big enough, until it is not
Cross-multiplying and adding make numbers grow. The largest `long long` is 9,223,372,036,854,775,807, about 9.2 × 10¹⁸, and a product of two parts near 10¹⁰ passes it. Signed overflow is undefined behaviour, as the overflow lesson in the intermediate course showed. Real software has failed this way: in 1996, Ariane 5 flight 501 broke up about 37 seconds after lift-off when a 64-bit floating-point value was converted to a 16-bit whole number too small to hold it. For the numbers in this lesson, `long long` is plenty.
:::

::: context cross-multiply Why the denominators must be positive
Cross-multiplying is multiplying both sides of a/b < c/d by b and by d. Multiplying both sides of an inequality by a positive number keeps it true. Multiplying by a negative number flips it: 2 < 3, but −2 > −3. So with a negative denominator the test would give the wrong answer. Try 1/−2 against 1/3: −1/2 is less than 1/3, but 1·3 < 1·(−2) says 3 < −2, which is false. The positive-denominator invariant means you never have to think about this again.
:::

::: context spaceship The spaceship operator
`<=>` is officially the **three-way comparison** operator, nicknamed "spaceship" for its shape. It answers "less, equal or greater" in one go, and from it the compiler can write the four ordering comparisons for you; asking for a default one, `auto operator<=>(const Fraction&) const = default;`, gives `==` and `!=` as well. For a fraction the default would compare `num_` first and then `den_`. That is ordering by parts, not by value, and it would say 1/2 < 1/3, because the tops are equal and 2 < 3. That is exactly why you write `<` yourself here.
:::

#include <numeric>
#include <ostream>

class Fraction {
public:
    Fraction(long long num = 0, long long den = 1) : num_(num), den_(den) {
        if (den_ < 0) {
            num_ = -num_;
            den_ = -den_;
        }
        long long g = std::gcd(num_, den_);
        if (g > 1) {
            num_ /= g;
            den_ /= g;
        }
    }
    long long num() const { return num_; }
    long long den() const { return den_; }
private:
    long long num_;
    long long den_;
};

Fraction operator+(const Fraction& a, const Fraction& b) {
    return Fraction(a.num() * b.den() + b.num() * a.den(), a.den() * b.den());
}
Fraction operator-(const Fraction& a, const Fraction& b) {
    return Fraction(a.num() * b.den() - b.num() * a.den(), a.den() * b.den());
}
Fraction operator*(const Fraction& a, const Fraction& b) {
    return Fraction(a.num() * b.num(), a.den() * b.den());
}
Fraction operator/(const Fraction& a, const Fraction& b) {
    return Fraction(a.num() * b.den(), a.den() * b.num());
}
bool operator==(const Fraction& a, const Fraction& b) {
    return a.num() == b.num() && a.den() == b.den();
}
bool operator<(const Fraction& a, const Fraction& b) {
    return a.num() * b.den() < b.num() * a.den();
}

    out << f.num();
    if (f.den() != 1) out << "/" << f.den();

=== cpp3-08 | Virtual functions and interfaces
--- teach
Last lesson your `Fraction` behaved like a built-in number. A template, like your `Stack<T>`, works for many types, but each `Stack<int>` or `Stack<std::string>` is its own class, fixed while compiling, and holds only one type. Sometimes one piece of code must handle a **mix** of kinds at once: "add up the area of these shapes", whatever shapes they turn out to be.

Picture a spacecraft's power system asking every device on board, "how much power do you need?" The camera, the heater and the radio each work out their answer in their own way. The question is the same; the answers depend on who is asked. Code that asks one question and gets the right answer from each kind of object, chosen while the program runs, is called **runtime [[polymorphism|polymorphism-word]]**. In C++ it takes three ingredients: a base class, classes built on it, and calls made through a pointer or reference. This lesson adds them one at a time.

### One class built on another

A class can be built on top of another one, taking everything it has and adding more:

```cpp
class Vehicle {
public:
    std::string id() const { return "V-1"; }
};

class Rover : public Vehicle {
public:
    int wheels() const { return 6; }
};

Rover r;
r.id();       // "V-1": Rover got this from Vehicle
r.wheels();   // 6: Rover's own
```

Read `class Rover : public Vehicle` as "a Rover is a kind of Vehicle". `Rover` **derives from** `Vehicle`: it has every member `Vehicle` has, plus its own. `Vehicle` is the **base class**, and `Rover` is a **derived class**. The word `public` there means the whole program may [[treat a Rover as a Vehicle|is-a]].

### A base reference can refer to a derived object

Because a `Rover` is a kind of `Vehicle`, a `Vehicle` reference or pointer may refer to one:

```cpp
Vehicle& v = r;    // v refers to the Rover r
Vehicle* p = &r;   // p points at it
```

This is what lets one piece of code take "any vehicle": it takes a `Vehicle&`, and you hand it a rover, a lander, whatever derives from `Vehicle`.

### Without virtual, the base version runs

Now give both classes a `name()` and call it through a base reference:

```cpp
class Shape {
public:
    std::string name() const { return "shape"; }
};

class Circle : public Shape {
public:
    std::string name() const { return "circle"; }
};

Circle c;
const Shape& s = c;
s.name();   // "shape"! The compiler only knows s is a Shape.
```

The compiler picks the function from the type it can see, `Shape`, while compiling. It never looks at what `s` really refers to. The task's starter behaves exactly like this.

### virtual: ask the real object

Mark the function **`virtual`** in the base class:

```cpp
class Shape {
public:
    virtual std::string name() const { return "shape"; }
};
```

Now `s.name()` gives `"circle"`. A **virtual function** is one where a call through a base pointer or reference runs the version for the object's *real* type, [[looked up while the program runs|vtable]]. That is the whole trick of runtime polymorphism.

### override: let the compiler check your spelling

In the derived class, write **`override`** after the function's parameters:

```cpp
class Circle : public Shape {
public:
    std::string name() const override { return "circle"; }
};
```

`override` asks the compiler to check that there really is a virtual function with exactly this name, these parameters and this `const` in the base. Misspell the name, or forget the `const`, and it is a compile error, "marked 'override', but does not override". Without `override`, the mistake would compile quietly as a [[brand-new function|override-history]] that no call through a `Shape` ever reaches.

### Pure virtual: a promise with no body

Some base classes have no sensible answer of their own. What is the area of "a shape"? Write `= 0` instead of a body:

```cpp
class Shape {
public:
    virtual ~Shape() = default;               // essential, see below
    virtual double area() const = 0;
    virtual std::string name() const = 0;
};
```

Read `= 0` as "no body here: every derived class must supply one". A function like that is **pure virtual**. A class with one or more is **abstract**: you cannot make an object of it, so `Shape s;` does not compile. A base class made of pure virtual functions is an **interface**: it only states what every shape can do, and each derived class says how. This is how [[flight software is often organised|interfaces-in-flight]].

### Implementing the interface

A class that derives from `Shape` and overrides every pure virtual function is a real, complete class you can create:

```cpp
class Circle : public Shape {
public:
    explicit Circle(double r) : r_(r) {}
    double area() const override { return 3.141592653589793 * r_ * r_; }
    std::string name() const override { return "circle"; }
private:
    double r_;
};
```

A derived class that leaves any pure virtual function without a body is still abstract, and still cannot be created.

### A virtual destructor

The line `virtual ~Shape() = default;` in the interface is essential. `= default` means "the compiler writes the usual body", which here is empty. The `virtual` is what matters.

You will hold shapes as `std::unique_ptr<Shape>`, and a `unique_ptr<Shape>` deletes its object through a `Shape*`. With a **virtual destructor** in the base, deleting a `Circle` through a `Shape*` runs `Circle`'s destructor too, then `Shape`'s. Without it, that delete is [[undefined behaviour|virtual-destructor]]. The rule: a class meant to be used through base pointers gets a virtual destructor.

### Deriving from a derived class

A derived class can itself be a base. A square *is a* rectangle with equal sides, so `Square` can derive from `Rectangle`, reuse its constructor, and override only `name()`. A derived constructor passes arguments to its base's constructor in the initialiser list, where members usually go:

```cpp
class Square : public Rectangle {
public:
    explicit Square(double side) : Rectangle(side, side) {}
    std::string name() const override { return "square"; }
};
```

`Square` gets `Rectangle`'s `area()` and `perimeter()` without writing them again: a 4 by 4 rectangle already knows its area is 16.

### A collection of mixed shapes

Now the payoff. One vector holds circles, rectangles and squares side by side, each owned by a `std::unique_ptr<Shape>`:

```cpp
std::vector<std::unique_ptr<Shape>> shapes;
shapes.push_back(std::make_unique<Circle>(1.0));   // a unique_ptr<Circle> becomes a unique_ptr<Shape>
shapes.push_back(std::make_unique<Square>(3.0));

double total = 0;
for (const auto& s : shapes) total += s->area();   // Circle::area, then Rectangle::area
```

`s->area()` reads through the pointer, as in the smart pointers lesson, and `virtual` makes it run the right `area` for each shape. To keep track of one shape without owning it, use a plain pointer: `s.get()` gives the `Shape*` a `unique_ptr` holds, as in `const Shape* best = s.get();`.

**Watch out:** if you forget `virtual` in the base class, everything still compiles, and every call through a `Shape` quietly runs the base version: the starter's `"shape"` and `0`. Your guard is `override`. Put it on every function in a derived class that is meant to replace a base one; if the base function is not virtual, or the two do not match exactly, the compiler stops you. The next lesson shows one more way a derived object can [[lose its real type|square-rectangle]].

::: context polymorphism-word Many shapes
"Polymorphism" is Greek for "many shapes": *poly*, many, and *morphe*, shape. One call, `s->area()`, takes many shapes of behaviour depending on the object. C++ has two kinds. Templates give **compile-time** polymorphism: the compiler makes a separate function for each type, and each call is fixed before the program runs. Virtual functions give **runtime** polymorphism: one function call, and the choice is made each time it runs. Use the first when the types are known while compiling, and the second when a collection mixes kinds.
:::

::: context is-a "Is a kind of"
Deriving says "every Rover is a Vehicle". Test a design by saying it aloud: "a circle is a shape" is true, so `Circle` may derive from `Shape`. "A rover is a wheel" is false: a rover *has* wheels, so a rover should hold them as members instead. The `public` in `: public Vehicle` makes the "is a" relationship visible to everyone, so a `Rover` can be passed wherever a `Vehicle&` is wanted. C++ also has `private` inheritance, where only the class itself knows, but it is rare; nearly every base you meet is public. ::: context vtable How a virtual call finds its function
The C++ standard does not say how, but every major compiler does it in the same basic way. Each class with virtual functions gets a table of the addresses of its versions, the **vtable**. Each object carries a hidden pointer to its class's table. A virtual call follows the object's pointer to the table and calls the address found there. That is why a virtual call costs a little more than a plain one, and why `sizeof` grows: with g++ on a 64-bit machine, a struct holding one `double` is 8 bytes, and 16 once it has a virtual function.

::: context override-history A keyword added after the bugs
`override` arrived in C++11, along with `final`, which forbids any further overriding. Before that, a derived function that did not quite match its base, a missing `const` or an `int` where the base had a `long`, compiled as a separate function with the same name. Every call through a base pointer then ran the base version, and nothing said why. Large codebases collected these bugs for years. Many coding standards now require `override` on every overriding function, and compilers can warn when it is missing.
:::

::: context interfaces-in-flight Interfaces in real flight software
NASA JPL's open-source flight software framework, F Prime, flew on the Ingenuity helicopter on Mars. It is written in C++, and its pieces are built around this pattern: a tool generates a base class for each software component, and engineers write a class that derives from it and fills in its virtual functions. Components talk to each other only through typed connections called ports, never by reaching inside each other. So a component can be swapped for another with the same ports, for example a simulated sensor during ground tests, without changing the rest.
:::

::: context virtual-destructor Half a destruction
Without a virtual destructor, deleting through a `Shape*` picks the destructor the way a non-virtual call does: from the type the compiler sees. So only `~Shape` would be considered, and whatever `Circle` owns, a buffer or a file, would never be released. The standard goes further and calls the whole delete undefined behaviour, so anything can happen. With `-Wall`, compilers warn in some of these cases, for example clang when a `unique_ptr` deletes such a class, but not all of them, so do not count on a warning. Write the virtual destructor.
:::

It works here because a shape never changes after it is made. Add `set_width` to `Rectangle`, and a `Square` could be given a width different from its height, breaking what a square is. The design lesson at the end of this course, "composition over inheritance", takes that up.

=== cpp3-09 | Debugging: object slicing
--- teach
Last lesson, virtual functions let one loop ask every shape for its area and get the right answer for each: circle, rectangle or square. That worked because the loop reached the shapes through a pointer or a reference. This lesson is about the bug you get when you forget that part.

### A dog that forgets it is a dog

Picture a photocopier loaded with small paper. You feed in a big poster, and out comes only the top corner. Nothing jams and no light blinks. The copy is smaller than the original, and whatever did not fit is gone.

C++ can do the same to an object. Here is a bug that confuses many people who come to C++ from Java, Python or C#:

```cpp
Dog rex("Rex");
Animal a = rex;        // copies only the Animal part of rex
a.sound();             // "..." — Animal's version, not Dog's
```

`Dog` derives from `Animal` and overrides `sound()` to say `"woof"`. Yet `a.sound()` runs `Animal`'s version and says `"..."`.

This is **object slicing**: copying a derived object into a variable of the base type, so that only the base part survives. A variable of type `Animal` has room for exactly an `Animal`. Copying `rex` into it keeps the `Animal` part (the name) and [[slices off the rest|slicing-picture]]. The copy is built as a plain `Animal`, so it also loses the "I am really a Dog" information that [[virtual calls rely on|how-virtual-works]].

No error, no warning: the program compiles cleanly and quietly calls the wrong function.

### Where slicing hides

The copy is not always as easy to see as `Animal a = rex;`. Slicing hides in three places.

**By-value parameters.** A parameter without `&` is a fresh copy of what the caller passed in, as you saw in the intermediate course's lesson on [[the function that changed a copy|copy-again]]. So this function slices every `Dog` handed to it:

```cpp
void describe(Animal a);     // a is a new Animal, copied from the argument
describe(Dog("Rex"));        // inside, a.sound() is "..."
```

**Containers of the base type.** A `std::vector<Animal>` stores `Animal`s, and nothing bigger fits in its slots. `push_back` copies the dog in, and the copy is sliced:

```cpp
std::vector<Animal> zoo;
zoo.push_back(Dog("Rex"));   // zoo[0] is a plain Animal
```

**Assignments** like `Animal a = rex;` from the start of the lesson.

### Finding it: the usual debugging method

Debugging slicing follows the same steps as the debugging lessons in the intermediate course.

1. **Reproduce** it with the smallest case: one `Dog`, one call.
2. **Check your assumption.** You are assuming "this call is virtual, so it will use `Dog`'s version." That is only true when the call goes through a **pointer or reference** to the object.
3. **Search** for every place a derived object is converted to a base **value**: a parameter with no `&`, a `std::vector<Animal>`, an `Animal x = …`.

### The fix: pointers and references

Keep objects that should act polymorphically behind references and pointers. A reference is another name for the same object, so nothing is copied and nothing is sliced.

For a parameter, add `const` and `&`, read "a const reference to an Animal":

```cpp
void describe(const Animal& a);   // a is the caller's own object
describe(Dog("Rex"));             // a.sound() is "woof"
```

For a collection, store owning pointers, as in the smart pointers lesson. A `std::unique_ptr<Animal>` can point at a `Dog`, and `std::make_unique<Dog>("Rex")` builds the dog directly on the heap, with no copy:

```cpp
std::vector<std::unique_ptr<Animal>> zoo;
zoo.push_back(std::make_unique<Dog>("Rex"));
zoo[0]->sound();                  // "woof"
```

The `->`, read "arrow", calls a member through a pointer: `zoo[0]->sound()` means "the object `zoo[0]` points at, its `sound()`". When you loop over such a vector, `const auto& a` gives you each pointer by reference, and `a->sound()` calls through it.

### Making the compiler catch it

To stop slicing from coming back, a base class meant for polymorphism can [[forbid copying|delete-copy]]. Write the copy constructor and mark it `= delete`, read "deleted: this function does not exist":

```cpp
class Animal {
public:
    Animal(const Animal&) = delete;   // no copying an Animal
    // ...
};
```

Now `Animal a = rex;`, a by-value `Animal` parameter and `push_back` into a `std::vector<Animal>` are all compile errors, so an accidental slice can no longer slip through. `std::make_unique<Dog>("Rex")` still works, because it builds a new dog rather than copying one.

**Watch out:** the loop variable of a range-for is a copy too, unless you add `&`. With `std::vector<Dog> dogs`, the loop `for (Animal a : dogs)` slices every dog. Write `for (const Animal& a : dogs)` instead.

The copy gets only the `Animal` part, and because it is built as an `Animal`, its hidden note says `Animal`. Even a `Dog` that adds no data of its own is sliced this way: the part that is lost is the knowledge that it was a dog.
:::

::: context how-virtual-works How a virtual call finds the right function
Every major compiler does it the same way. For each class with virtual functions, it makes a table listing which function to run for each virtual call: one table for `Animal`, one for `Dog`. Each object carries a hidden pointer to its class's table, set by the constructor that built it.

A call like `a.sound()` through a reference or pointer follows that hidden pointer to the table and runs whatever function is listed there. A `Dog` points at the `Dog` table, so you get `"woof"`. When you copy a dog into an `Animal` variable, the `Animal` copy constructor builds the new object, so its hidden pointer points at the `Animal` table. That is why the sliced copy says `"..."`.
:::

::: context copy-again The same root as an earlier bug
In the intermediate course, a function changed its parameter and the caller's variable stayed the same, because the parameter was a copy. Slicing is that bug's cousin. Both come from one C++ rule: a parameter or variable without `&` holds its own object, made by copying.

Java, Python and C# behave differently. There, a variable of a class type holds a reference to an object, so passing a `Dog` around never copies it and never slices it. People coming from those languages expect C++ to act the same way, which is why this bug catches them.
:::

::: context delete-copy Why polymorphic classes forbid copying
`= delete` works on any function: the function is declared, but any code that would call it fails to compile. In the copying lesson you met the copy constructor as one of the rule of three. Deleting it is one more way of taking charge of copying.

The C++ Core Guidelines, a widely used rule book edited by Bjarne Stroustrup and Herb Sutter, say it directly (rule C.67): a polymorphic class should suppress public copy and move. A copy of a base-class object can only ever be a base-class object, so copying is almost always a slice waiting to happen. Deleting the copy constructor also means the class gets no automatic move constructor, so a move cannot slice either.
:::

=== cpp3-10 | std::function and callbacks
--- teach
Last lesson, a `std::vector<std::unique_ptr<Animal>>` let one vector hold dogs, cats and plain animals, all behind one common type. This lesson does the same trick for pieces of code: one type that can hold any function you like, so you can store functions and call them later.

### Code to run later

Picture ordering telescope parts from a shop. You do not stand at the counter until they arrive. You leave your phone number and say, "Call me when they come in." The shop keeps your number and calls it at the right moment.

A **callback** is the code version of that phone number: code you hand to someone else, for them to [[run later|callbacks-everywhere]]. "When a message arrives, call this." "When the timer runs out, call this."

The receiver has to keep many callbacks, from many callers, in one place. They come in different kinds: lambdas with different captures, plain functions, and **function objects** (objects of a class that has an `operator()`, so you can call them like functions).

### Every lambda is its own type

Here is the problem. Each lambda has [[its own unique type|lambda-types]], with no name you could write down. These two lambdas look alike, but their types are different:

```cpp
auto add = [](int a, int b) { return a + b; };
auto mul = [](int a, int b) { return a * b; };
add = mul;   // error: add and mul are different types
```

So there is no way to write "a vector of lambdas like these" using the lambdas' own types. You need one common type that can hold any of them.

### std::function: one type for "anything callable"

That common type is `std::function<Signature>`, from `<functional>`. Inside the angle brackets goes a [[signature|reading-signatures]]: what the function takes and what it gives back. Read `int(int, int)` as "takes two ints, gives back an int":

```cpp
#include <functional>

std::function<int(int, int)> op = [](int a, int b) { return a + b; };
op(2, 3);                      // 5
op = [](int a, int b) { return a * b; };
op(2, 3);                      // 6
```

The same `op` held two different lambdas, one after the other. It can hold a plain function too, as long as the signature matches:

```cpp
int add(int a, int b) { return a + b; }

op = add;
op(4, 5);                      // 9
```

A `std::function` can also be **empty**: holding nothing at all. Test it like a `bool` before calling it:

```cpp
std::function<void()> empty;   // void(): takes nothing, gives back nothing
if (!empty) { /* nothing stored: calling it would be an error */ }
```

Calling an empty `std::function` is an error. With exceptions switched off, as in this app, it ends the program.

### What it costs

`std::function` is a small example of **type erasure**: hiding many different types behind one. Whatever you put in, from the outside it is [["something callable with this signature"|type-erasure]]. Its real type is erased.

That convenience [[costs a little|the-cost]]: it may need a heap allocation to store a bigger callable, and every call goes through an extra step to find the real function.

So choose by what you need:

- When a function only **passes a callable straight through** and calls it, use a template parameter, as in the function templates lesson. The compiler then knows the exact type and there is no extra cost:

```cpp
template <typename F>
int apply_twice(F f, int x) { return f(f(x)); }

apply_twice([](int x) { return x + 1; }, 3);   // 5
```

- When you need to **store** callables for later, especially many of different kinds, use `std::function`.

### Storing callbacks: an event bus

A typical design is an **event bus**: a central place where parts of a program [[subscribe to events|software-bus]] and publish them. It could map each event name to a list of handlers:

```cpp
std::map<std::string, std::vector<std::function<void(int)>>> handlers;

handlers["tick"].push_back([](int v) { /* react to v */ });
for (const auto& h : handlers["tick"]) h(3);   // call every "tick" handler with 3
```

Callers will also want to **unsubscribe**: to take a handler off the list later. They cannot find their handler again by looking for the lambda, because two lambdas cannot be compared with `==`, and neither can two `std::function`s. So `subscribe` hands back a **handle**: a number, the id, that the caller keeps and gives back later.

To keep an id with each handler, store small records in one vector. The vector also keeps the order they subscribed in:

```cpp
struct Subscription {
    int id;
    std::string event;
    std::function<void(int)> handler;
};
std::vector<Subscription> subs;
subs.push_back({1, "tick", [](int v) { /* … */ }});
```

To remove the record with a given id, walk the vector with an iterator (as in the iterators lesson) and pass the match to `erase`, which takes that element out and closes the gap:

```cpp
for (auto it = subs.begin(); it != subs.end(); ++it) {
    if (it->id == 1) {
        subs.erase(it);
        break;                 // stop: it no longer points at a valid element
    }
}
```

After `erase`, the iterator `it` is no longer valid, so stop the loop at once, with `break` or a `return`.

### Returning a function

Functions can **return** callables, too. `compose(f, g)` builds a new function that runs `g` first, then runs `f` on the result, so `compose(f, g)(x)` is `f(g(x))`:

```cpp
std::function<int(int)> compose(std::function<int(int)> f, std::function<int(int)> g) {
    return [f, g](int x) { return f(g(x)); };
}
```

The lambda captures `f` and `g` **by value**. They are parameters, so they end when `compose` returns, and the lambda needs its own copies to use later.

**Watch out:** a handler that captures a local variable **by reference** must not outlive that variable. If a function subscribes `[&count](int) { ++count; }` and then returns, the bus is left holding a reference to a `count` that no longer exists. When that handler is called, the program has undefined behaviour, and nothing warns you. Capture by value, or make sure the handler is unsubscribed first.

::: context callbacks-everywhere You have used callbacks already
The comparator you gave `std::sort` in the lambdas lesson was a callback: `sort` called your code every time it needed to compare two values. A button in an app works the same way: the app hands the button a function, and the button calls it on each click.

The name comes from the telephone: you "call back" someone who left you their number. Callbacks let one piece of code react to events without the code that raises the event knowing anything about it.
:::

::: context lambda-types Why each lambda has its own type
The lambdas lesson showed what the compiler does with a lambda: it writes a small class with no usable name, and the lambda is an object of that class. Every lambda expression gets its own class, even when two are written the same, character for character. `add` and `mul` are objects of two different classes, so assigning one to the other fails, the same way assigning a `std::string` to an `int` would.

That is why `auto` is how you usually store a lambda: it is the only way to name its type.
:::

::: context reading-signatures Reading a function type
`int(int, int)` is a **function type**: the return type first, then the parameter types in brackets, with no function name. A few more:

- `void()` takes nothing and gives back nothing;
- `bool(const std::string&)` takes a string by const reference and gives back true or false;
- `void(int)` takes an int and gives back nothing, like the handlers in this lesson's event bus.

A callable fits a `std::function` if it can be called with those argument types and its result can be turned into the return type.
:::

::: context type-erasure One box, many shapes
Type erasure means the outside of an object shows one type while the inside can be many. A `std::function<int(int, int)>` hides a lambda, a plain function or a function object behind the same face: "call me with two ints, get an int".

You have met the same idea already: a `std::unique_ptr<Animal>` hides whether it holds a dog or a cat, and a virtual call finds the right function. Inside, `std::function` works in a similar way.
:::

::: context the-cost Where the cost comes from
A `std::function` object has a fixed size, but the callables put into it do not: a lambda that captures ten strings is much bigger than one that captures nothing. Standard libraries keep a small space inside the `std::function` for small callables, and put bigger ones on the heap.

Each call also goes through a pointer to find the real function, so the compiler usually cannot paste the function's body in at the call site, a speed-up it makes all the time for templates.

Flight software watches this closely. NASA JPL's "Power of 10" coding rules forbid dynamic memory allocation after initialisation, so a program that stores callbacks registers them while it starts up, not in the middle of a flight.
:::

::: context software-bus A bus on a real spacecraft
NASA's core Flight System (cFS), free flight software that has flown on many NASA missions, is built around a **Software Bus**. Each application subscribes to the kinds of message it cares about, identified by a number called a message ID. Another application publishes a message, and the bus delivers it to every subscriber, without the publisher knowing who they are.

That is this lesson's event bus on a larger scale: the camera software does not need to know which programs want its pictures, and a new program can subscribe later without changing the camera code.
:::

--- solution
#include <functional>
#include <map>
#include <string>
#include <utility>
#include <vector>

class EventBus {
public:
    int subscribe(const std::string& event, std::function<void(int)> handler) {
        int id = next_id_++;
        subs_.push_back({id, event, std::move(handler)});
        return id;
    }

    bool unsubscribe(int id) {
        for (auto it = subs_.begin(); it != subs_.end(); ++it) {
            if (it->id == id) {
                subs_.erase(it);
                return true;
            }
        }
        return false;
    }

    int publish(const std::string& event, int value) {
        int called = 0;
        for (const auto& s : subs_) {
            if (s.event == event) {
                s.handler(value);
                ++called;
            }
        }
        return called;
    }

private:
    struct Subscription {
        int id;
        std::string event;
        std::function<void(int)> handler;
    };
    std::vector<Subscription> subs_;
    int next_id_ = 1;
};

std::function<int(int)> compose(std::function<int(int)> f, std::function<int(int)> g) {
    return [f = std::move(f), g = std::move(g)](int x) { return f(g(x)); };
}
--- hint
Store each subscription as a small struct `{ id, event, handler }` in a private `std::vector` — the vector keeps subscription order for free. A private `int next_id_ = 1;` member gives out the ids.
--- hint

--- hint
`compose` returns a lambda that captures `f` and `g` **by value**, `[f, g](int x) { return f(g(x)); }`, because they must outlive the call to `compose`.

=== cpp3-11 | std::variant and std::visit
--- teach
Last lesson, `std::function` let one type hold any callable. In the intermediate course, `std::optional<T>` held "a T, or nothing". This lesson's type holds one value out of a short list of types, and always knows which one it is holding.

### Exactly one of several

Picture a parking space with a sign next to it. The space fits a car, a bike or a van, but only one at a time, and the sign always says which is parked there right now. You never have to guess.

`std::variant<A, B, C>`, from `<variant>`, is that parking space. It holds **exactly one** of `A`, `B` or `C`. It is a type-safe **[[union|union-history]]**: a value that can be one of several types, and that remembers which one it holds.

```cpp
#include <variant>

std::variant<int, double, std::string> v = 42;   // holds an int
v = "hello";                                     // now holds a std::string
```

Writing that long type again and again is tiring. `using Value = …;` gives a type a shorter name, so from here on `Value` means that whole variant:

```cpp
using Value = std::variant<int, double, std::string>;
Value v = 2.5;   // holds a double
```

### Asking what is inside

Three ways to ask a variant about its contents:

```cpp
Value v = "hello";

v.index();                          // 2: the position of the held type (int 0, double 1, string 2)
std::holds_alternative<int>(v);     // false: it is not holding an int
std::get_if<std::string>(&v);       // pointer to the string, or nullptr
```

`std::get_if` takes the **address** of the variant, `&v`, and gives back a [[pointer|get-if-pointer]]. If `v` holds a string, the pointer points at it. If not, it is `nullptr`, the pointer to nothing. So you can test and use it in one go:

```cpp
if (auto* s = std::get_if<std::string>(&v)) {
    // here s points at the string: s->size() is 5
}
```

`std::get<T>(v)` also exists, and gives you the value directly. But if `v` is not holding a `T`, it signals an error with an exception, and with exceptions switched off, as in this app, a wrong guess ends the program. Prefer `get_if` or `holds_alternative`.

### std::visit: handle every case

The real power is **`std::visit`**: it calls a function with whatever the variant holds. You give it a **visitor**, something callable with each of the variant's types, and the variant itself.

A common way to build a visitor bundles several lambdas, one per type, into one object. It needs this helper, one line long:

```cpp
template <class... Fs> struct overloaded : Fs... { using Fs::operator()...; };
```

For now, treat `overloaded` as a recipe to copy: it bundles several lambdas into one object that has [[all of their call operators|overloaded-recipe]]. How its `class... Fs` works (variadic templates) is covered in the expert course.

With it, a function that describes any `Value`:

```cpp
std::string describe(const Value& v) {
    return std::visit(overloaded{
        [](int i)                { return "int " + std::to_string(i); },
        [](double)               { return std::string("a double"); },
        [](const std::string& s) { return "text " + s; },
    }, v);
}
// describe(Value(42)) is "int 42", describe(Value(2.5)) is "a double"
```

`[](double)` has a parameter with no name: that lambda does not need the value, only the fact that it is a double. Every lambda must return the **same** type, here `std::string`, because `std::visit` has one return type.

Leave out a case and, usually, it does not compile: the compiler checks that the visitor can handle every type in the variant.

**Watch out:** that check is about what can be *called*, not what you meant. Numbers convert to each other, so if you leave out the `double` lambda above, a `double` quietly goes to the `int` lambda: `describe(Value(2.5))` becomes `"int 2"`, with no error and no warning. Write one lambda for every type in the variant, in the same order, so a missing one stands out.

### Closed sets and open sets

A variant is the right tool for a **closed** set of alternatives: a list you know in full, up front. Tokens in a parser (a number, a name, a symbol), the kinds of value in a spreadsheet cell. Adding a new type means changing the variant, and then every `std::visit` that misses it is flagged.

Virtual functions suit the [[opposite: an open set|closed-and-open]] of types that other people will add later, each in its own class, without touching your code.

### Visiting two variants at once

`std::visit` can also take **two** variants. The visitor then gets both values, one from each, which is handy for "combine two values of mixed kinds":

```cpp
std::visit(visitor, a, b);   // calls visitor(value in a, value in b)
```

With three types in each variant, that is 3 × 3 = 9 combinations, and the visitor must handle all nine. Writing nine lambdas would be a lot. The next step shows a shorter way.

### One lambda for every type

Instead of one lambda per type, you can write a single **generic lambda**, one with `auto` as its parameter type:

```cpp
auto show = [](const auto& x) { /* … */ };
```

The compiler stamps out a fresh copy of it for each type it is called with, the same way it does for a function template. Inside, you can ask what `x` really is, in three small steps.

**Its plain type.** `decltype(x)`, read "declared type of x", gives the type `x` was declared with: for a string that is `const std::string&`. `std::decay_t<…>` strips the `const` and `&`, leaving `std::string`:

```cpp
using X = std::decay_t<decltype(x)>;   // X is int, double or std::string
```

**Comparing types.** `std::is_same_v<A, B>`, from `<type_traits>`, is `true` when two types are the same type:

```cpp
constexpr bool is_text = std::is_same_v<X, std::string>;
```

**Choosing a branch.** **`if constexpr (…)`** is an `if` decided while compiling. It keeps only the branch that applies to this type; the [[other branches are not even compiled|why-if-constexpr]] for it:

```cpp
if constexpr (std::is_same_v<X, std::string>) {
    // only compiled when x is a string: x.size() is fine here
} else {
    // only compiled when x is an int or a double
}
```

### Saying the return type

A lambda normally works out its return type from its `return` statements. When its branches would return different types, say the return type yourself by writing `->` and the type after the parameters:

```cpp
auto half = [](const auto& x) -> std::optional<Value> {
    using X = std::decay_t<decltype(x)>;
    if constexpr (std::is_same_v<X, std::string>) {
        return std::nullopt;            // no half of a string
    } else {
        return Value(x / 2.0);          // a double
    }
};
std::visit(half, Value(3));             // an optional holding the double 1.5
```

Without `-> std::optional<Value>`, one branch returns `std::nullopt` and the other a `Value`, and the compiler would stop, because a lambda cannot return two different types.

::: context get-if-pointer Why get_if works with pointers
A pointer can say "nothing" in a way a reference cannot: it can be `nullptr`. That makes it a natural answer for a question that might have no answer, "give me the string, if there is one". The same pattern comes back in the next lesson, on errors without exceptions, where `std::get_if<ParseError>(&result)` checks whether a function failed.

`auto* s` means "a pointer, of whatever type the right side gives": here `std::string*`. Inside the `if`, `s` is known not to be `nullptr`, so following it with `->` is safe.
:::

::: context overloaded-recipe What the overloaded recipe does
Each lambda is an object of its own unnamed class, with a call operator, `operator()`. `overloaded` is a struct that inherits from every one of those classes at once, so it has all their call operators. The `using Fs::operator()...;` line brings them together into one overload set, so the compiler can pick the right one for each argument, exactly as it picks between overloaded functions, a choice you met in the overloading lesson.

`overloaded{ lambda1, lambda2, lambda3 }` then builds one object from the three lambdas. The `...` is what lets one line handle any number of lambdas; that is the variadic template part the expert course explains.
:::

::: context closed-and-open Two ways to handle "many kinds"
With virtual functions, adding a new *type* is easy: write one new class, and no old code changes. Adding a new *operation* is hard: every class needs a new function.

With a variant it is the other way round. Adding a new operation is easy: write one new `std::visit`. Adding a new type is hard: every visit must handle it, and the compiler points them out.

So ask which will grow. A set of shapes that users of your library will extend is open: use an interface. The kinds of value in a spreadsheet cell, fixed by you, are closed: use a variant.
:::

::: context why-if-constexpr Why a normal if is not enough
In a normal `if`, both branches are compiled, even the one that will never run. Inside a generic lambda stamped out for `int`, a branch that calls `x.size()` would fail to compile, because an `int` has no `.size()`, even though that branch could never run for an int.

`if constexpr` needs a condition the compiler can work out while compiling, such as `std::is_same_v<X, std::string>`. It then throws away the branch that does not apply before checking it, so each stamped-out copy contains only code that makes sense for its type. The `constexpr` in its name is the next lesson's subject: work done by the compiler.
:::

template <class... Fs> struct overloaded : Fs... { using Fs::operator()...; };

std::string type_name(const Value& v) {
    return std::visit(overloaded{
        [](int) { return std::string("int"); },
        [](double) { return std::string("double"); },
        [](const std::string&) { return std::string("string"); },
    }, v);
}

std::string to_text(const Value& v) {
    return std::visit(overloaded{
        [](int i) { return std::to_string(i); },
        [](double d) {
            std::ostringstream out;
            out << d;
            return out.str();
        },
        [](const std::string& s) { return "\"" + s + "\""; },
    }, v);
}

std::optional<Value> add(const Value& a, const Value& b) {
    return std::visit([](const auto& x, const auto& y) -> std::optional<Value> {
        using X = std::decay_t<decltype(x)>;
        using Y = std::decay_t<decltype(y)>;
        constexpr bool xs = std::is_same_v<X, std::string>;
        constexpr bool ys = std::is_same_v<Y, std::string>;
        if constexpr (xs && ys) {
            return Value(x + y);
        } else if constexpr (xs || ys) {
            return std::nullopt;
        } else if constexpr (std::is_same_v<X, int> && std::is_same_v<Y, int>) {
            return Value(x + y);
        } else {
            return Value(static_cast<double>(x) + static_cast<double>(y));
        }
    }, a, b);
}

=== cpp3-12 | constexpr: work done by the compiler
--- teach
Last lesson, `if constexpr` let the compiler choose a branch while it was building your program. This lesson goes further: whole functions that the compiler runs for you, so the finished program already contains the answers.

### Two different moments

Picture the times table printed inside the cover of an old exercise book. Somebody worked out 7 × 8 once, before the book was printed. Every student who looks it up gets 56 instantly, with no working out.

A program's life has two moments like that:

- **Compile time**: while the compiler is turning your code into a program. This happens once, when you build.
- **Run time**: while the finished program is running. This happens every time someone starts it.

Anything worked out at [[compile time|two-moments]] is like the printed table: done once, then free forever after.

### A function the compiler can run

Put the word **`constexpr`**, short for "constant expression", in front of a function, and the function **can** run at compile time:

```cpp
constexpr int square(int x) { return x * x; }
```

It is still an ordinary function. The difference shows up when you call it somewhere that needs a constant: a value that must be known while compiling. There, the compiler runs the function itself, and the finished program already holds the answer.

### Places that need a constant

**A `constexpr` variable.** Marking a variable `constexpr` says "work this out at compile time":

```cpp
constexpr int nine = square(3);        // computed by the compiler: 9
```

**The size of a `std::array`.** `std::array<T, N>`, from `<array>`, is a fixed-size array: `T` is the element type and `N` how many there are. `N` is part of the type, so it must be a compile-time constant:

```cpp
std::array<int, square(4)> grid{};     // an array of 16 ints, all 0
```

**A `static_assert`.** You met `static_assert` in the class templates lesson: a check the compiler does while compiling. If the condition is false, the program does not build.

```cpp
static_assert(square(5) == 25);        // checked at compile time: a wrong answer
                                       // is a compile error, not a runtime bug
```

### The same function at run time

A `constexpr` function works at run time too. Call it with a value that is only known once the program runs, such as a number the user types, and it runs then, like any function:

```cpp
int n = read_number();                 // only known at run time
int m = square(n);                     // the same function, now at run time
```

So `constexpr` means "may run at compile time", not "always does". To be sure the work happens at compile time, use the result where a constant is needed, for example in a `constexpr` variable.

### What a constexpr function may contain

Modern `constexpr` functions can contain loops, `if`, local variables and even `std::array`: most ordinary code. What they cannot do includes:

- **I/O**, input and output: no `std::cout`, no reading files.
- **`static` locals**, variables that keep their value between calls.
- **[[Undefined behaviour|ub-rejected]]**. At run time, undefined behaviour can quietly give garbage. During compile-time evaluation, the compiler **rejects** it. That is a nice bonus: overflow inside a `static_assert` is a compile error instead of garbage.

```cpp
static_assert(square(100000) > 0);     // does not compile: 100000 * 100000
                                       // is too big for an int
```

### Why bother?

- **Speed:** the work is done once, [[when you build|tables-in-rom]], not every time the program runs.
- **Safety:** `static_assert` turns facts about your code into [[checks that run on every build|checks-every-build]].
- **Types need constants:** array sizes and template arguments must be known at compile time.

### consteval: compile time only

**`consteval`** goes further: the function *must* run at compile time. Calling it with a run-time value is a compile error.

```cpp
consteval int cube(int x) { return x * x * x; }

constexpr int c = cube(3);   // fine: 27, worked out by the compiler
int m = cube(n);             // error: n is only known at run time
```

`constexpr` is the flexible default. Reach for `consteval` only when running at run time would be a mistake.

### Loops, not deep recursion

The compiler is not a fast place to run code, and it [[stops after a set amount of work|step-limits]]. A good shape for compile-time maths is **iteration**, a loop that keeps a few running values, rather than deep recursion. For example, Fibonacci numbers with two running values:

```cpp
constexpr long long fib(int n) {
    long long a = 0, b = 1;            // fib(0) and fib(1)
    for (int i = 0; i < n; ++i) {
        long long next = a + b;
        a = b;
        b = next;
    }
    return a;
}
```

This takes `n` steps. The textbook version, where `fib(n)` calls `fib(n - 1)` and `fib(n - 2)`, repeats the same work over and over and grows exponentially: far too slow for the compiler.

**Watch out:** a `constexpr` function can only call other functions at compile time if they are `constexpr` too. If `count_primes_below` is `constexpr` but the `is_prime` it calls is not, using `count_primes_below(30)` as an array size fails, with an error like "non-constexpr function 'is_prime' cannot be used in a constant expression". Mark every helper on the path.

::: context ub-rejected The compiler catches what the program would not
While compiling, the compiler follows every step of a `constexpr` call exactly, so it notices undefined behaviour, such as a signed number overflowing, that a running program would skip straight past.

This lesson's own `fib` gives a surprise. `fib(92)` is 7,540,113,804,746,346,429, which fits in a `long long`. But the loop always works one number ahead: to return `fib(92)` it also computes `fib(93)` in `next`, and that is too big. So `static_assert(fib(92) > 0)` does not compile, while at run time the same call would overflow silently, which is undefined behaviour. The largest this loop can safely give is `fib(91)`.
:::

::: context tables-in-rom Tables baked into the program
A `constexpr` table, such as a list of sine values or a checksum table, is finished before the program exists, so it becomes part of the program file itself. On a small embedded computer it can sit in read-only memory next to the code: it takes no time to set up when the computer starts, and a stray write cannot change it. That is one reason embedded programmers use `constexpr` wherever they can.
:::

::: context checks-every-build Checks that cost nothing to run
A `static_assert` runs on every build, on every computer that compiles the code, and costs nothing once the program is running. That makes it a favourite in embedded and flight software, where memory layouts must match exactly. A common use is checking that a message format has the size the other side expects, for example `static_assert(sizeof(Packet) == 16);`. If someone adds a field later, the build stops at once, instead of the spacecraft and the ground station quietly misreading each other's data.
:::

::: context step-limits How much work the compiler will do
Compilers cap compile-time evaluation, so a mistake like an endless loop cannot hang the build forever. By default, GCC stops after 33,554,432 operations and Clang after 1,048,576 steps; both also limit how deep calls can nest, to 512 by default. Flags such as `-fconstexpr-ops-limit` (GCC) and `-fconstexpr-steps` (Clang) raise the limits.

The recursive Fibonacci makes 40,730,022,147 calls to work out `fib(50)`, far past either limit. The loop version takes 50 steps.
:::

=== cpp3-13 | Errors without exceptions
--- teach
Last lesson, `constexpr` let the compiler do work while it builds your program, and a wrong answer in a `static_assert` stopped the build. Some mistakes cannot be caught that early, though: a settings file with a typo in it only shows up when the program runs. This lesson is about what a function should do when something goes wrong while the program is running, and how to tell its caller exactly what happened.

### Go or no go, and why

Picture a launch countdown. The flight director asks each station in turn: "Go or no go?" Most answer "go". When one says "no go", the next question is always "why?", and the answer has to be specific: "pressure low in tank two", not "something is wrong".

A function that can fail is in the same spot. It needs a way to say "it worked, here is the answer" or "it failed, and here is why".

Many languages, C++ included, have **[[exceptions|exceptions-off]]**: a way for a function to stop in the middle and jump straight back to some code much further up that handles the problem. But many C++ codebases, including games, embedded systems (small computers built into a device, like a flight computer) and this checker, are built with exceptions **switched off**. Here, `throw` and `try`, the words that use exceptions, do not even compile.

So the error travels back the ordinary way: in the **return value**, like any other answer. The function's return type then says "this can fail", and the compiler makes sure the caller deals with it.

### Three shapes of answer

There are [[three common shapes|three-shapes]] for an answer that can fail. Go from the simplest to the richest, and pick the simplest one that tells the caller enough.

**1. A `bool` or an error code.** `true` means it worked, `false` means it did not. That is fine when the caller cannot do anything smarter with the reason anyway.

```cpp
bool open_valve(int id);        // true: opened, false: did not
```

**2. `std::optional<T>`**, from the intermediate course: a value, or nothing. It is right when there is only one way to fail ("not found"), or when the reason does not matter.

```cpp
std::optional<int> find_sensor(const std::string& name);   // an id, or std::nullopt
```

**3. A result type.** A **result type** holds either the value you wanted *or* an explanation of what went wrong. In C++ you build one from `std::variant<T, Error>`, the variant from the variants lesson: exactly one of the two. It is right when the caller needs to know *what* went wrong: which line, which field, what message.

```cpp
std::variant<Settings, ParseError> load(const std::string& text);   // settings, or an error
```

### Building a result type

The error half is usually a small struct of your own that carries the details:

```cpp
struct ParseError {
    int line;              // which line of the text was wrong
    std::string message;   // what was wrong with it
};
```

A function that returns `std::variant<int, ParseError>` can `return` either kind of thing. The variant is built from whatever you return, so there is nothing extra to write:

```cpp
std::variant<int, ParseError> check_fuel(int percent, int line) {
    if (percent < 0 || percent > 100) return ParseError{line, "fuel out of range"};
    return percent;        // the good case: the variant now holds an int
}
```

`ParseError{line, "fuel out of range"}` builds a `ParseError` in one go: the values in the curly braces fill the members in the order they are listed in the struct, so `line` first, then `message`.

### Reading a result

The caller asks which one it got, with `std::get_if` from the variants lesson:

```cpp
auto result = load(text);
if (auto* err = std::get_if<ParseError>(&result)) {
    std::cout << "line " << err->line << ": " << err->message << "\n";
} else {
    const Settings& s = std::get<Settings>(result);
    // ... use s ...
}
```

Read it one piece at a time:

- `&result`, with `&` read "the address of", hands `get_if` a pointer to the variant.
- `std::get_if<ParseError>` gives back a pointer to the `ParseError` inside, or `nullptr` (a pointer to nothing) if the variant holds a `Settings` instead.
- `auto* err = …` stores that pointer. Doing it inside the `if` makes the test "is `err` a real pointer?", so the first branch runs only when there is an error.
- `err->line`, with `->` read "arrow", reads a member through a pointer.
- In the `else` branch there is certainly no error, so `std::get<Settings>` is safe there.

With `check_fuel(120, 4)` in place of `load(text)`, and `int` in place of `Settings`, this prints:

```
line 4: fuel out of range
```

### Four habits that make this style work

**Return early, on the first error, with as much context as you have.** The moment something is wrong, `return` the error. Line numbers are gold: "line 3: unknown key: colour" tells a person exactly where to look.

**Validate everything once, at the [[boundary|check-at-the-edge]].** Check the text completely where it enters the program. Then every other part of the program can trust a `Settings` it receives, without checking it again.

**Mark such functions `[[nodiscard]]`.** Written in front of a function, `[[nodiscard]]` ("no discard": do not throw the result away) asks the compiler to [[warn anyone who ignores the result|nodiscard-warning]]:

```cpp
[[nodiscard]] bool arm_engine();

arm_engine();              // warning: ignoring return value
bool ok = arm_engine();    // fine: the answer is kept
```

**Separate parsing from using.** A **parser** is a function that reads text and turns it into values. A parser that returns a result does not print anything and does not end the program. It hands back the result, and its caller decides what to do.

### Reading a settings file

The task is a parser for a small settings file, one `key = value` per line:

```
# server
host = example.org
port=8080
```

You have every tool for it already. `std::istringstream` from `<sstream>` and `std::getline` read a string one line at a time, as in the string streams lesson. Count the lines as you go, starting from 1. The starter's `trim` removes the spaces at both ends of a string. A line that is empty after trimming, or starts with `#`, is skipped.

To split a line, find the first `=` with `find`, then take the text before it and after it with `substr`. If there is no `=`, `find` gives `std::string::npos`, the "not found" value from the basics lesson on finding text:

```cpp
std::string l = "port = 8080";
std::size_t eq = l.find('=');                  // 5
std::string key = trim(l.substr(0, eq));       // "port"
std::string value = trim(l.substr(eq + 1));    // "8080"
```

`substr(0, eq)` takes `eq` characters from the start. `substr(eq + 1)` takes everything after the `=`.

For the [[port number|port-numbers]], read the digits by hand, the way `parse_int` did in the optional lesson: every character must be a digit, allow at most five of them (so the number can never overflow), then check that it lies from 1 to 65535.

**Watch out:** skipped lines still count. A blank line or a `#` comment is line 2 or line 5 like any other, so add 1 to your line counter for *every* line you read, before you decide to skip it. If you count only the lines you use, every error after a blank line points at the wrong line. And the "missing host" check can only happen after the loop, once every line has been read.

::: context exceptions-off What exceptions are, and why some teams switch them off
With exceptions, a function in trouble writes `throw` and some error value, and the program jumps back up through every function call until it reaches a `try` block with a matching `catch`, which handles it. That is handy, but it has costs that matter on small or strict computers: extra code in the program, time that is hard to predict while the jump happens, and paths out of a function that you cannot see by reading it. So many teams build with a compiler switch, `-fno-exceptions` for g++ and clang, that turns them off. Google's C++ style guide says "We do not use C++ exceptions", and many game studios and embedded teams do the same. This checker compiles with that switch, so `throw` gives the error "cannot use 'throw' with exceptions disabled".

::: context check-at-the-edge Check once, where data comes in
The edge of a program is where outside data arrives: a file, a keyboard, a radio link. Anything there can be wrong. If every function deep inside the program re-checked its inputs to be safe, the checks would be scattered, easy to forget and hard to test. The double square brackets, `[[ ]]`, hold an *attribute*: a note to the compiler that does not change what the code does. `[[nodiscard]]` arrived in C++17. ::: context port-numbers Why a port stops at 65535
A computer can run many network programs at once, so each one listens on a numbered *port*, like flats in one building sharing a street address. Web servers usually listen on port 80, which is why the task makes 80 the default. The port number is sent as 16 bits, and 16 bits can count from 0 to 2^16 − 1, which is 65535. Port 0 is reserved and never used for a real connection, so a valid setting is 1 to 65535. Five digits cover every valid port, which is why the parser can stop at five digits and still never overflow an `int`.

#include <cctype>
#include <sstream>
#include <string>
#include <variant>

struct Config {
    std::string host;
    int port = 80;
    bool verbose = false;
};

struct ConfigError {
    int line;
    std::string message;
};

std::string trim(const std::string& s) {
    std::size_t a = 0, b = s.size();
    while (a < b && std::isspace(static_cast<unsigned char>(s[a]))) ++a;
    while (b > a && std::isspace(static_cast<unsigned char>(s[b - 1]))) --b;
    return s.substr(a, b - a);
}

bool parse_port(const std::string& s, int& out) {
    if (s.empty() || s.size() > 5) return false;
    int n = 0;
    for (char c : s) {
        if (!std::isdigit(static_cast<unsigned char>(c))) return false;
        n = n * 10 + (c - '0');
    }
    if (n < 1 || n > 65535) return false;
    out = n;
    return true;
}

[[nodiscard]] std::variant<Config, ConfigError> parse_config(const std::string& text) {
    Config config;
    bool have_host = false;
    std::istringstream in(text);
    std::string raw;
    int line = 0;
    while (std::getline(in, raw)) {
        ++line;
        std::string l = trim(raw);
        if (l.empty() || l[0] == '#') continue;
        std::size_t eq = l.find('=');
        if (eq == std::string::npos) return ConfigError{line, "expected key = value"};
        std::string key = trim(l.substr(0, eq));
        std::string value = trim(l.substr(eq + 1));
        if (key == "host") {
            if (value.empty()) return ConfigError{line, "empty host"};
            config.host = value;
            have_host = true;
        } else if (key == "port") {
            if (!parse_port(value, config.port)) return ConfigError{line, "bad port"};
        } else if (key == "verbose") {
            if (value == "true") config.verbose = true;
            else if (value == "false") config.verbose = false;
            else return ConfigError{line, "bad verbose"};
        } else {
            return ConfigError{line, "unknown key: " + key};
        }
    }
    if (!have_host) return ConfigError{0, "missing host"};
    return config;
}

=== cpp3-14 | Custom comparators and sorting
--- teach
Last lesson, a result type carried a clear error report back to the caller. This lesson is about putting things in the order *you* choose: by more than one key, some keys highest first, and without the mistake that quietly breaks `std::sort`.

### Your own "comes before"

Picture lining a class up for a photo: shortest at the front, and when two people are the same height, alphabetical by name. You are not using one fixed rule like "smaller number first". You are giving your own answer to the question "does this person stand before that one?"

In the lambdas lesson you gave `std::sort` exactly that answer. `std::sort` puts things in order with `<` unless you hand it a **comparator**: a function `comp(a, b)` that returns true when `a` must come **before** `b`.

```cpp
std::vector<std::string> words = {"pear", "fig", "apple"};
std::sort(words.begin(), words.end(), [](const std::string& a, const std::string& b) {
    return a.size() < b.size();       // shorter words first
});
// words is now {"fig", "pear", "apple"}
```

### Sorting by two keys

Sorting by several keys is where people get tangled. Say you want astronauts sorted by last name, and by first name when the last names match. Written out by hand, that is:

```cpp
if (a.last != b.last) return a.last < b.last;   // last names decide, if they differ
return a.first < b.first;                        // otherwise first names decide
```

With three or four keys, this grows long and easy to get wrong. There is a cleaner way.

A **[[tuple|tuples]]** is a small, fixed bundle of values, which may be of different types, like `("Ride", "Sally")`. **`std::tie`**, from `<tuple>`, builds a tuple out of the variables you give it. It holds references to them, so nothing is copied.

Tuples compare **left to right**, the way words compare in a dictionary: the first entries decide, and only when they are equal do the second entries get a say. That is called **[[lexicographic order|dictionary-order]]**, "dictionary order". So one line does the whole job:

```cpp
struct Person { std::string first, last; };
// ... a std::vector<Person> people holding four astronauts ...
std::sort(people.begin(), people.end(), [](const Person& a, const Person& b) {
    return std::tie(a.last, a.first) < std::tie(b.last, b.first);
});
// Buzz Aldrin, Neil Armstrong, Anna Ride, Sally Ride
```

The two Rides tie on the last name, so their first names decide: Anna before Sally.

### One key highest first

To sort one key **descending** (highest first), swap `a` and `b` for that key only. Here is a leaderboard with points highest first, and names A to Z for equal points:

```cpp
return std::tie(b.points, a.name) < std::tie(a.points, b.name);
```

Look at the first position. On the left it has `b.points`, on the right `a.points`. So the test there is "is `b` smaller than `a`?", which is the same as "is `a` bigger?". A bigger score comes first. The names are not swapped, so they still go A to Z.

With three keys, `std::tie(a.dept, b.salary, a.name) < std::tie(b.dept, a.salary, b.name)` means department ascending (A to Z), salary descending, name ascending. Only the middle key is swapped.

### Behave like `<`, never like `<=`

A comparator has to be a **[[strict weak ordering|strict-weak]]**. In practice that means: it behaves like `<`, never like `<=`. Asking "does `x` come before itself?" must give false: `comp(x, x)` must be false.

**Watch out:** writing `<=`, say `a.salary <= b.salary`, is the classic mistake. Then two equal salaries each claim to come before the other. The C++ rules call that **undefined behaviour** for `std::sort`: you may get a wrong order, or the sort may read outside the vector and crash. It can look fine on small tests and fail on big ones. Always use `<`, and break ties with another key.

### Keeping ties in their original order

`std::sort` promises nothing about the order of elements that are equal under your comparator. They may come out shuffled. **`std::stable_sort`** takes the same arguments but is **[[stable|stable-sorting]]**: equal elements keep their original order.

```cpp
std::vector<std::string> w = {"pear", "fig", "kiwi", "apple", "yam"};
std::stable_sort(w.begin(), w.end(), [](const std::string& a, const std::string& b) {
    return a.size() < b.size();
});
// {"fig", "yam", "pear", "kiwi", "apple"}
```

"fig" and "yam" are both 3 letters, so they stay in the order they came in. So do "pear" and "kiwi".

### Only the top few

Sometimes you want only the best few: a top 10 out of a million. Sorting all million is wasted work. **`std::partial_sort(first, middle, last, comp)`** puts only the elements from `first` up to `middle` in order: the smallest ones by your comparator, sorted. The rest are left in some unspecified order after them. It is [[cheaper than a full sort|partial-cost]] when the top part is small.

```cpp
std::vector<int> s = {40, 95, 12, 77, 60, 88};
std::partial_sort(s.begin(), s.begin() + 3, s.end(), [](int a, int b) { return a > b; });
// s[0], s[1], s[2] are now 95, 88, 77
```

Here the comparator says "bigger comes first", so the first three are the three highest.

`s.begin() + 3` must not go past `s.end()`. If someone asks for a top 10 of a list of 4, first shrink the 10 down to the list's size. `std::min(x, y)`, from `<algorithm>`, gives the smaller of two values of the same type, so `k = std::min(k, v.size());` keeps `k` from passing the end.

### Containers take comparators too

A `std::set` keeps its elements sorted, with `<` unless you name another rule. Its comparator is a type: a small struct whose `operator()`, the function-call operator from the operator overloading lesson, answers "comes before?".

```cpp
struct ByLength {
    bool operator()(const std::string& a, const std::string& b) const {
        return a.size() < b.size();
    }
};

std::set<std::string, ByLength> s = {"fig", "pear", "yam", "kiwi", "apple"};
// s holds only "fig", "pear", "apple"
```

A set treats two strings of equal length as [[the same key|equal-means-same]], because "neither comes before the other" means equal. So "yam" and "kiwi" were never added. Choose comparators for containers with care.

::: context tuples Pairs, triples, tuples
A pair holds two values, and you have used `std::pair` with maps. A tuple is the same idea for any number of values: the word comes from the ends of "double", "triple", "quadruple", and so on, so an "n-tuple" holds n values. `std::tuple` arrived in C++11. `std::tie` makes a tuple of *references*: `std::tie(a.last, a.first)` does not copy the two strings, it only points at them, so building one inside a comparator that `std::sort` calls millions of times costs almost nothing.
:::

::: context dictionary-order How two tuples compare
Two tuples compare the way a dictionary orders words: look at the first entries; if they differ, they decide. Only if they are equal do you move on to the second entries, and so on. Here the last names tie, so the first names decide.

::: context strict-weak Why a less-or-equal test can crash a sort
"Strict" means nothing comes before itself. "Weak" means ties are allowed: two different things may be equal, as long as equal behaves sensibly (if `a` ties with `b` and `b` ties with `c`, then `a` ties with `c`). `std::sort` leans on this for speed. In common library versions its fastest inner loop scans forward, without checking where the vector ends, until the comparator says false, trusting that the middle value it compares against will stop it. With `<=`, a long run of equal values never produces that false, and the scan walks off the end of the vector into memory it does not own.
:::

::: context stable-sorting Stable sorts and two-step sorting
A stable sort never reorders elements that compare equal. That gives a handy trick: to sort by department and then by name, you can first sort by name, then stable-sort by department. Within each department the names stay in the order the first sort left them. Spreadsheets behave like this when you click one column's sort after another. `std::stable_sort` may need extra memory to do this, which is one reason `std::sort` does not promise it.
:::

::: context partial-cost How much partial_sort saves
The C++ standard says `std::partial_sort` makes about n × log₂(k) comparisons, where n is the number of elements and k the number you want in order. A full sort makes about n × log₂(n). For the top 10 out of a million, that is about 3.3 million comparisons instead of about 20 million: roughly six times less work, and the gap grows as the list grows.
:::

::: context equal-means-same Equal to a set means "already here"
A `std::set` never asks "are these two equal?" with `==`. It asks the comparator both ways: if `comp(a, b)` is false and `comp(b, a)` is false too, neither comes before the other, so the set treats them as the same key and keeps only the first. With `ByLength`, every 3-letter word is "the same" as "fig". If you really want every word kept, ordered by length, break the tie inside the comparator: compare the lengths, and when they are equal, compare the words themselves.
:::

#include <algorithm>
#include <string>
#include <tuple>
#include <vector>

struct Employee {
    std::string name;
    std::string dept;
    int salary;
};

void sort_staff(std::vector<Employee>& staff) {
    std::sort(staff.begin(), staff.end(), [](const Employee& a, const Employee& b) {
        return std::tie(a.dept, b.salary, a.name) < std::tie(b.dept, a.salary, b.name);
    });
}

std::vector<std::string> top_earners(std::vector<Employee> staff, std::size_t k) {
    k = std::min(k, staff.size());
    std::partial_sort(staff.begin(), staff.begin() + k, staff.end(), [](const Employee& a, const Employee& b) {
        return std::tie(b.salary, a.name) < std::tie(a.salary, b.name);
    });
    std::vector<std::string> names;
    for (std::size_t i = 0; i < k; ++i) names.push_back(staff[i].name);
    return names;
}

std::vector<std::string> by_length(std::vector<std::string> words) {
    std::stable_sort(words.begin(), words.end(), [](const std::string& a, const std::string& b) {
        return a.size() < b.size();
    });
    return words;
}

=== cpp3-15 | Problem solving: binary search on the answer
--- teach
Last lesson, you put data in exactly the order you wanted. Sorted data has a superpower: you can find things in it very fast. This lesson uses that superpower twice, first to search a sorted vector, and then, in a cleverer way, to search for the answer to a problem.

### Halving

Play "guess my number" between 1 and 100, where each wrong guess is answered "higher" or "lower". The smart first guess is 50. Whatever the answer, half the numbers are gone. Guess the middle of what is left, again and again, and you always win within 7 guesses.

That is **binary search**: look at the middle, throw away the half that cannot contain the answer, repeat. It only works on **sorted** data, because only then does the middle tell you which half to keep.

It is fast. In the big-O notation from the intermediate course, binary search is **O(log n)**: doubling the data adds only one more step. [[A million items take about 20 steps|twenty-halvings]].

### Binary search, ready-made

The standard library has binary search built in, in `<algorithm>`. Both of these functions take the start and end of a sorted range and a value, and give back an iterator: a position in the vector.

- **`std::lower_bound`** finds the first element that is **greater than or equal to** the value.
- **`std::upper_bound`** finds the first element that is **greater than** the value.

```cpp
std::vector<int> v = {1, 3, 3, 3, 8};
auto first = std::lower_bound(v.begin(), v.end(), 3);   // first element >= 3: index 1
auto last  = std::upper_bound(v.begin(), v.end(), 3);   // first element >  3: index 4
```

Subtracting one iterator from another, with `-` read "minus", gives the number of steps between them. So `first - v.begin()` is 1, the index. And `last - first` is 4 − 1 = 3: [[how many 3s there are|bounds-picture]]. Together the two bounds fence in every copy of the value.

That difference comes out as a wide whole-number type made for distances in memory, not as an `int`. To return it as an `int`, convert it with `static_cast<int>(last - first)`.

### Searching for the answer itself

Now the bigger idea: **binary search on the answer**.

Many problems ask for "the smallest X that works". Often two things are true:

- checking whether one particular X works is easy;
- the answers have a shape: every X below some point fails, and every X from there on works.

Here is an example. Packages must be shipped **in their order**, within D days. Each day, the ship carries the next packages in line, and the day's total weight cannot go over the ship's **capacity**, the most it can carry. What is the smallest capacity that gets every package delivered in time?

### Step 1: check one capacity

Checking one capacity is easy. Fill each day [[greedily|greedy-check]]: keep loading the next package until it would not fit, then start a new day. Count the days you used. That is one pass over the packages, O(n).

```cpp
bool fits(const std::vector<int>& weights, int days, long long cap) {
    int used = 1;              // we start on day 1
    long long load = 0;        // weight on the ship today
    for (int w : weights) {
        if (load + w > cap) {  // this package does not fit today
            ++used;            // so start a new day
            load = 0;
        }
        load += w;
    }
    return used <= days;
}
```

With packages 1 to 10 and 5 days, capacity 14 needs 6 days, so it fails. Capacity 15 fits.

### Step 2: the range and its shape

The answer lies between two limits:

- A capacity below the **heaviest** package never works: that package could never be loaded.
- The **sum** of all the packages always works: everything goes in one day.

And if capacity C works, C + 1 works too, because a bigger ship never needs more days. So as C grows, "works?" goes fail, fail, …, fail, **work**, work, work. That shape is exactly what binary search needs: we are looking for the [[first "work"|fail-then-work]].

### Step 3: why it is worth it

**Brute force** means trying every possibility in turn. Here it would try every capacity from the heaviest package upward. With 200,000 packages of 10,000 kg each and 2 days, the answer is 1,000,000,000 kg, so brute force tries about a billion capacities, and each check walks all 200,000 packages. That is about 200 trillion steps: days of computer time.

Binary search over `[heaviest, total]`, the range from the heaviest to the total, needs about 31 checks. That is about 6 million steps: a blink.

### Step 4: the search loop

In plain steps, the search is:

```
lo = heaviest, hi = total
while lo < hi:
    mid = lo + (hi - lo) / 2
    if works(mid): hi = mid       # mid might be the answer
    else:          lo = mid + 1   # mid is too small
answer = lo
```

This is not C++. It is **pseudocode**: the steps written plainly, so you can see the idea before the syntax. `lo` and `hi` fence in where the answer can still be.

- If `mid` works, the answer is `mid` or something smaller. Keep `mid` in the range: `hi = mid`.
- If `mid` fails, the answer is bigger than `mid`. Drop it: `lo = mid + 1`.
- Every pass shrinks the range, and when `lo` meets `hi` only one candidate is left. That is the answer.

The middle is written `lo + (hi - lo) / 2` rather than `(lo + hi) / 2`. They mean the same, but the second can [[overflow when both are big|midpoint-bug]].

### Step 5: watch the types

The two ends of the range come from tools you know from the algorithms lesson: `*std::max_element(…)` for the heaviest package, and `std::accumulate(…, 0LL)` from `<numeric>` for the total.

**Watch out:** 200,000 × 10,000 is 2,000,000,000. The largest `int` is 2,147,483,647, so that total is right at the edge. A few more packages, or a little more weight, and an `int` overflows. Use `long long` for the total, the capacity and the day's load. And remember that `std::accumulate` adds in the type of its starting value: start from `0LL`, not `0`, or the sum is done in `int` anyway.

::: context twenty-halvings Why a million takes about 20 steps
Each step halves what is left. Count how many halvings it takes to get from a million down to one: 1,000,000, then 500,000, 250,000, 125,000, … Twenty halvings would shrink 2^20 = 1,048,576 items to one, and a million is a little less than that, so 20 steps are enough. For a billion items it is about 30 steps. That is what O(log n) means in practice: the data can grow a thousand times while the work grows by only about ten steps.
:::

::: context greedy-check Why filling each day is safe
A *greedy* method makes the choice that looks best right now and never goes back. Greedy methods are often wrong, but here it is safe. The packages must go in order, so the only choice each day is where to stop. Stopping early can only push packages to later days, and it never helps: whatever a cleverer plan does, loading as much as fits today leaves the same or less for the days after. So if the greedy plan needs more than D days, no plan can do it in D.

::: context fail-then-work The shape that makes it work
Draw every capacity on a line and mark each one fail or work. Binary search finds that boundary by testing the middle and keeping the half where it must be. If the shape were mixed, testing one spot would tell you nothing about its neighbours, and the trick would fail. The same idea runs `git bisect` from the advanced Git course: the commits go "good, good, …, bad, bad", and it finds the first bad one by halving.

::: context midpoint-bug A bug that hid for years
`(lo + hi) / 2` adds the two ends first. If both are large, their sum can be bigger than the type can hold, and it overflows before the division ever happens. `lo + (hi - lo) / 2` never makes a number bigger than `hi`. This is a real, famous bug: in 2006 Joshua Bloch reported that the binary search in Java's standard library had used `(low + high) / 2` for years, and it failed on arrays of more than about a billion elements. The same slip is in the binary search of Jon Bentley's classic book *Programming Pearls*.
:::

Both are checked on big inputs, so they need binary search. The starter's versions give correct answers, but they are far too slow.

--- solution
#include <algorithm>
#include <numeric>
#include <vector>

bool fits(const std::vector<int>& weights, int days, long long cap) {
    int used = 1;
    long long load = 0;
    for (int w : weights) {
        if (load + w > cap) {
            ++used;
            load = 0;
        }
        load += w;
    }
    return used <= days;
}

long long min_capacity(const std::vector<int>& weights, int days) {
    long long lo = *std::max_element(weights.begin(), weights.end());
    long long hi = std::accumulate(weights.begin(), weights.end(), 0LL);
    while (lo < hi) {
        long long mid = lo + (hi - lo) / 2;
        if (fits(weights, days, mid)) hi = mid;
        else lo = mid + 1;
    }
    return lo;
}

int count_in_range(const std::vector<int>& sorted, int lo, int hi) {
    if (lo > hi) return 0;
    auto first = std::lower_bound(sorted.begin(), sorted.end(), lo);
    auto last = std::upper_bound(sorted.begin(), sorted.end(), hi);
    return static_cast<int>(last - first);
}

=== cpp3-16 | Design: composition over inheritance
--- teach
Last lesson was about finding answers fast. This last lesson of the course is about design: how to arrange classes so that a program stays easy to grow. It brings together interfaces, `unique_ptr` and moving, all from earlier in this course.

### "Is a" and "has"

Think about how a spacecraft is built. Engineers do not design a new "spacecraft with a camera, two solar panels and a radio" from nothing each time. They take a spacecraft body and bolt parts onto it: a camera, panels, a radio. The spacecraft **has** a camera. It is not a kind of camera.

Classes can be related in those same two ways.

- **Inheritance** says "**is a**": a `Circle` *is a* `Shape`, as in the virtual functions lesson. `class Circle : public Shape` makes `Circle` a kind of `Shape`, usable anywhere a `Shape` is expected.
- **Composition** says "**has**": an object holds other objects as its parts, and uses them to do its work.

It is tempting to use inheritance for "has" or "can do" too. That is where designs [[rot|is-a-test]].

### How inheritance gets out of hand

Suppose robots can fly or swim. With inheritance you write a class for each: `FlyingRobot` and `SwimmingRobot`, both deriving from `Robot`.

Then someone needs a robot that does both. You write `FlyingSwimmingRobot`, copying code from the other two.

Add driving, and you need `DrivingRobot`, `FlyingDrivingRobot`, `SwimmingDrivingRobot`, `FlyingSwimmingDrivingRobot`… Each new ability [[doubles the number of classes|class-explosion]], and every copied piece of code is a chance for the copies to drift apart: fix a bug in one, forget the other.

### A robot that has abilities

With composition, a robot *has* a list of abilities. Each ability is a small object behind an interface:

```cpp
class Ability {
public:
    virtual ~Ability() = default;
    virtual std::string verb() const = 0;
};

class Fly : public Ability {
public:
    std::string verb() const override { return "flies"; }
};
```

That is exactly the shape of `Shape` in the virtual functions lesson: a pure virtual function (`= 0`) that every ability must provide, and a virtual destructor so that deleting a `Fly` through an `Ability` pointer runs the right destructor.

The robot keeps its abilities in a vector of `unique_ptr<Ability>`, so it owns them, and they are deleted with it:

```cpp
class Robot {
public:
    explicit Robot(std::string name) : name_(std::move(name)) {}

    Robot& add(std::unique_ptr<Ability> a) {
        abilities_.push_back(std::move(a));
        return *this;               // returning *this lets calls chain
    }

private:
    std::string name_;
    std::vector<std::unique_ptr<Ability>> abilities_;
};
```

A robot is now assembled from parts while the program runs:

```cpp
Robot r("Otto");
r.add(std::make_unique<Fly>()).add(std::make_unique<Swim>());
```

### Returning `*this` to chain calls

Inside a member function, **`this`** is a [[pointer to the object the function was called on|this-pointer]]. So `*this`, with the star read "the thing it points at", is that object itself.

`add` returns `Robot&`, a reference to the same robot. That is why `r.add(…)` can be followed straight away by `.add(…)`: the second call runs on whatever the first returned, which is `r` again. Writing calls one after another like this is called **method chaining**.

**Watch out:** a `unique_ptr` cannot be copied, only moved. `abilities_.push_back(a);` does not compile; the error mentions a "deleted function", the copy that `unique_ptr` forbids. Write `abilities_.push_back(std::move(a));`, as in the moving lesson.

### Joining words with commas

To describe a robot as `"Otto: flies, swims"`, you join the verbs with `", "` between them. Put the comma before every word except the first:

```cpp
std::vector<std::string> parts = {"flies", "swims", "drives"};
std::string out;
for (std::size_t i = 0; i < parts.size(); ++i) {
    if (i > 0) out += ", ";   // no comma before the first word
    out += parts[i];
}
// out is "flies, swims, drives"
```

### What changed, and what did not

Now three abilities are three small classes, and any combination is free: no new class for "flies and drives". [[Inheritance has not gone away|composition-rule]]. It is still used for what it is good at: a narrow **interface** (`Ability`) with interchangeable implementations. What went away is inheritance used to **share code** between concrete classes.

A rule of thumb: inherit to be *used as* the base (that is **polymorphism**, one piece of code working with many types); compose to *reuse* behaviour. When you catch yourself naming a class after a combination of features, like `FlyingSwimmingRobot`, that is the signal to compose instead.

### Two things in the starter

The starter uses two things you may not have met. Neither survives the redesign.

- **`protected`** members can be used by derived classes but not by outside code. It sits between `public` and `private`. The starter's `name_` is `protected` so that `FlyingRobot` can read it. [[Many style guides avoid it|protected-data]].
- **`using Robot::Robot;`** inside a derived class lets it reuse its base's constructors, so `FlyingRobot("Otto")` works without writing a constructor of its own.

::: context is-a-test A test for "is a"
A good test for inheritance: can the derived thing be used *everywhere* the base is expected, without surprising anyone? Computer scientist Barbara Liskov stated this idea in 1987, and it is now called the *Liskov substitution principle*; she later won the Turing Award, computing's highest prize. A `Circle` passes: any code that asks a `Shape` for its area works with a circle. "A flying robot is a robot" sounds right in words, but really it is a robot that *has* a way to fly. When the thing you want to share is an ability, not an identity, reach for composition.
:::

::: context class-explosion Counting the classes
With one class per combination, every ability can be in or out, so n abilities give 2 × 2 × … × 2 = 2^n combinations. One more ability doubles the count. With composition, you write one class per ability, so the count only grows by one.

::: context this-pointer Where this comes from
When you write `r.add(…)`, the compiler quietly passes the address of `r` into `add`, and inside the function that address is called `this`. That is how a member function knows *which* robot's `abilities_` to change: `abilities_` really means `this->abilities_`. Its type here is `Robot*`, a pointer to a robot. Returning `*this` by reference hands back the very same robot, not a copy, which is why the chained second `add` changes `r` too.
:::

::: context composition-rule An old piece of advice
"Favor object composition over class inheritance" is one of the best-known lines in *Design Patterns* (1994), a book by Erich Gamma, Richard Helm, Ralph Johnson and John Vlissides. Flight software often follows the same idea. NASA JPL's F Prime framework, which ran on the Ingenuity helicopter on Mars, builds a program out of separate components connected through well-defined ports, rather than one deep family tree of classes. Game engines do the same: in Unity, a game object is given its behaviour by the components attached to it.
:::

::: context protected-data Why protected data is avoided
`protected` data can be changed by every class that derives from the base, including ones written years later by someone else. So the base can no longer keep its own rules, the way the classes lesson in the intermediate course kept theirs with `private` members. The C++ Core Guidelines, a widely used rule book, say to avoid protected data for that reason. Protected *functions* are less of a problem, because the base still decides what they do.
:::

Replace the starter's class hierarchy with composition. No `main`: the checker supplies it.

- `class Ability`: an interface with `virtual std::string verb() const = 0;` and a virtual destructor.
- `Fly`, `Swim` and `Drive`: three classes deriving from `Ability`, whose verbs are `"flies"`, `"swims"` and `"drives"`.
- `class Robot`, with:
  - `explicit Robot(std::string name)`;
  - `Robot& add(std::unique_ptr<Ability> ability)`, which stores the ability and returns `*this`;
  - `std::size_t ability_count() const`, the number of abilities added;
  - `std::string act() const`, which returns the name, `": "` and the verbs in the order they were added, joined with `", "`: for example `"Otto: flies, swims"`. With no abilities it returns `"Otto: idles"`.

--- solution
#include <memory>
#include <string>
#include <utility>
#include <vector>

class Ability {
public:
    virtual ~Ability() = default;
    virtual std::string verb() const = 0;
};

class Fly : public Ability {
public:
    std::string verb() const override { return "flies"; }
};

class Swim : public Ability {
public:
    std::string verb() const override { return "swims"; }
};

class Drive : public Ability {
public:
    std::string verb() const override { return "drives"; }
};

class Robot {
public:
    explicit Robot(std::string name) : name_(std::move(name)) {}

    Robot& add(std::unique_ptr<Ability> ability) {
        abilities_.push_back(std::move(ability));
        return *this;
    }

    std::size_t ability_count() const { return abilities_.size(); }

    std::string act() const {
        if (abilities_.empty()) return name_ + ": idles";
        std::string out = name_ + ": ";
        for (std::size_t i = 0; i < abilities_.size(); ++i) {
            if (i > 0) out += ", ";
            out += abilities_[i]->verb();
        }
        return out;
    }

private:
    std::string name_;
    std::vector<std::unique_ptr<Ability>> abilities_;
};
--- hint
`Robot` stops being a base class. Give it a `private` member `std::vector<std::unique_ptr<Ability>> abilities_;` next to `name_`, and write `Ability`, `Fly`, `Swim` and `Drive` above it, the way `Shape` and `Circle` were written in the virtual functions lesson.
--- hint
`add` moves the pointer into the vector with `abilities_.push_back(std::move(ability));` and then does `return *this;`, so `r.add(…).add(…)` chains. `ability_count` returns `abilities_.size()`.
--- hint
In `act`, return `name_ + ": idles"` if the vector is empty. Otherwise start from `name_ + ": "` and loop over the indexes: add `", "` when `i > 0`, then add `abilities_[i]->verb()`.
