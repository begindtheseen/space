=== pyp-01 | Expense tracker 1: planning and parsing commands
--- teach
The expert course ended with a calculator. A tokenizer cut `2 + 3 * 4` into pieces, and a recursive-descent parser worked out what the pieces meant. You now know every idea you need to build real programs. This projects course is where you build them.

Everything here uses what the three courses before it taught: the idioms of the intermediate course (comprehensions, sorting with `key=`, f-string formatting), the classes and algorithms of the advanced one (dataclasses, special methods), and the design habits of the expert one (a pure core, a thin shell, injected dependencies, tests that catch bugs).

The course has two parts:

- **Three projects**, each a real program built over four lessons. **Each lesson starts from where the last one finished**: the code in the editor is your finished program from the lesson before, and you add the next piece.
- **Four capstones**, where you get only a [[specification|specification]] and design everything yourself.

### The expense tracker

Picture a small notebook where you write down every bit of money you spend: how much, on what, and a word about it. The first project is that notebook as a program. You drive it by typing commands:

```
add 12.50 food lunch with Sam
add 3.20 transport bus
total food
report
```

Line by line: spend 12.50 on food (the note says "lunch with Sam"); spend 3.20 on transport; ask how much went on food in total; ask for a summary of everything.

### Plan before you type

A program this size has four jobs. Each one gets its own lesson and its own [[layer of code|layers]]:

1. **Parse**: turn a line of text into a structured command, or reject it with a clear reason.
2. **Model**: store expenses and answer questions about them.
3. **Report**: turn the stored data into readable output.
4. **Run**: the loop that reads input, calls the layers above, and prints results.

Keeping these apart means each one can be tested on its own. It also means a change to the report format never breaks parsing. This lesson writes layer 1.

### Money is kept in whole cents

You met the trap in the floating-point lesson: `0.1 + 0.2` is not `0.3` in floating point. Money must add up exactly. So this program stores every amount as a whole number of **cents**, an `int`: `12.50` becomes `1250`. It turns cents back into a decimal string only for display, in the next lesson. Storing money as [[whole cents|integer-money]] is what real payment systems do.

### Turning text into cents, step by step

The user types an amount as text, like `"12.5"`. You met `partition` in the intermediate course. It cuts a string at the first `.` and gives back [[three pieces|partition-pieces]]: the part before, the dot itself, and the part after. If there is no dot, the last two pieces are empty strings.

```python
"12.5".partition(".")     # ('12', '.', '5')
"12".partition(".")       # ('12', '', '')
```

The part after the dot needs one more step. `"5"` after the dot means 5 tenths, which is 50 cents, not 5 cents. The string method **`ljust`** ("left-justify") fixes that. `s.ljust(2, "0")` puts `s` on the left and pads it on the right with `"0"` until it is 2 characters long. A string that is already long enough is left alone.

```python
"5".ljust(2, "0")         # '50'  pad on the right: 5 tenths is 50 cents
"50".ljust(2, "0")        # '50'  already 2 long, unchanged
"".ljust(2, "0")          # '00'  no decimals at all: 0 cents
```

Now put it together. For `"12.5"`: the whole part is `"12"`, the padded fraction is `"50"`, so the cents are `12 * 100 + 50 = 1250`. Check it makes sense: twelve and a half dollars is 1250 cents.

### Which amounts to reject

An amount must be digits, with an optional `.` and at most two decimal places. Each bad example below breaks one rule. (Remember that `isdigit()` is `False` for an empty string.)

- `"abc"`: the whole part is not digits.
- `"-5"`: the minus sign is not a digit.
- `"12.345"`: three decimal places.
- `"1."`: there is a dot, but nothing after it, so the fraction is `""`.
- `".5"`: nothing before the dot, so the whole part is `""`.
- `"0"` and `"0.00"`: these read fine, but they come to zero cents. An expense of nothing is a mistake, so reject it too.

### The error policy

A command-line tool must never crash on a typo. So the parser **raises** `ValueError` with a message the user can act on, like `usage: add <amount> <category> [note]`. A message that shows the right way to type a command is called a [[usage message|usage-line]]. The parser does not print anything. The run loop (lesson 4) will catch the error and print it. `ValueError` is the [[right exception to raise here|why-valueerror]].

### Reading one command line

`line.split()` with no argument splits on any run of spaces and throws away spaces at both ends. So extra spaces never matter:

```python
"add 12.50 Food lunch   with Sam".split()
# ['add', '12.50', 'Food', 'lunch', 'with', 'Sam']
```

The first word is the command. The rest are its **arguments**: the values that go with it. `add` needs at least two (an amount and a category), and everything after those is the note. `" ".join(words)` glues the note words back together with single spaces, and joining an empty list gives `""`.

Commands are **case-insensitive**: `ADD`, `Add` and `add` all mean the same. Lowercase the word with `.lower()` before you compare it. Categories are lowercased too, so `Food` and `food` land in the same pile.

### The shape of a parsed command

A parsed command is a small dict. Its shape is your [[contract|contract]] between the parser and the rest of the program: the other layers will rely on exactly these keys.

```python
{"cmd": "add", "amount": 1250, "category": "food", "note": "lunch with Sam"}
{"cmd": "total", "category": None}
{"cmd": "report"}
```

`total` with no category means "the total of everything", so its category is `None`.

**Watch out:** trying to handle every command in one long function that parses, stores and prints. It works for three commands and becomes impossible to follow at ten. Parse here, and only parse.

::: context specification What a specification is
A **specification**, or "spec", is a written description of what a program must do, without saying how. It lists the inputs, the outputs, and what should happen in every case, including the awkward ones. Engineers write specs before they write code, so that everyone agrees on the goal. Flight software for spacecraft starts from requirements documents that can run to hundreds of pages, and every piece of code must trace back to a requirement. In the capstones you get a short spec and nothing else.
:::

::: context integer-money Why money is counted in cents
An `int` in Python is always exact, however big it gets. A float is only the nearest value it can store, so adding thousands of float prices lets tiny errors pile up until a total is off by a cent. That is why many payment systems store amounts as whole numbers of the smallest unit: cents, or pence, or yen. The expert course showed the other safe choice, `Decimal`. Cents are simpler here, because every amount in this program has at most two decimal places.
:::

::: context partition-pieces partition always gives three pieces
`partition` never fails and never changes how many pieces it gives back: always three. That is why `whole, dot, frac = text.partition(".")` is safe for any text at all. The middle piece tells you whether the dot was found: it is `"."` if it was, and `""` if it was not.

::: context usage-line How to read a usage line
Usage lines follow a convention that Unix tools have used for decades. Words in angle brackets, like `<amount>`, are placeholders: type a real value there, not the word "amount". Anything in square brackets, like `[note]`, is optional. Plain words, like `add`, are typed exactly as shown. So `usage: add <amount> <category> [note]` means "type add, then an amount, then a category, and a note if you like". Many command-line tools print a line of the same shape when you give them the wrong arguments.
:::

::: context why-valueerror The right type, the wrong value
Python has many built-in exceptions, and picking the matching one tells the reader what went wrong. `ValueError` means "this is the right kind of thing, but its value is not acceptable". The amount is a string, as expected, but `"abc"` is not a valid amount. A `TypeError` would mean the wrong kind of thing altogether, like a list where a string belongs. Because every layer raises `ValueError` for bad input, the run loop can catch that one kind and let real bugs through.
:::

::: context contract A contract between two parts of a program
In everyday life a contract is an agreement: I do this, you do that. In code it is an agreement about shapes. The parser promises that an `add` command always comes back as a dict with the keys `cmd`, `amount`, `category` and `note`, with the amount already in cents. The rest of the program promises to rely on nothing else. As long as both sides keep their promise, either side can be rewritten without breaking the other.
:::
--- task
Write the parsing layer: two functions.

`to_cents(text)` turns a string amount into whole cents: `"12.50"` → `1250`, `"3"` → `300`, `"0.5"` → `50`. It raises `ValueError` for anything that is not digits with an optional `.` and at most two decimal places (such as `"abc"`, `"12.345"`, `"-5"`, `"1."`), and for zero.

`parse_command(line)` returns one of the three dicts shown in the lesson:

- Command words are case-insensitive, and categories are lowercased.
- The note is the rest of the words joined by single spaces, or `""` if there are none.

It raises `ValueError` with exactly these messages:

- an empty line: `"empty command"`
- `add` with fewer than two arguments: `"usage: add <amount> <category> [note]"`
- `total` with more than one argument: `"usage: total [category]"`
- `report` with any argument: `"usage: report"`
- an unknown command: `"unknown command: <word>"`, with the word as it was typed.
--- hint
Two functions, two jobs. In `to_cents`, cut the text with `partition`, check the rules from the lesson one by one, and build the cents. In `parse_command`, split the line into words; the first word (lowercased) is the command and the rest are its arguments.
--- hint
`whole, dot, frac = text.partition(".")`. The text is bad if the whole part is not digits, or there was a dot and the fraction is not digits, or the fraction is longer than 2. Otherwise the cents are `int(whole) * 100 + int(frac.ljust(2, "0"))`; raise if that is not more than zero.
--- hint
In `parse_command`: `words = line.split()`; if the list is empty, raise `"empty command"`. Then `cmd, args = words[0].lower(), words[1:]`. Give each command its own `if` that checks `len(args)` before returning its dict. If no `if` matched, raise `f"unknown command: {words[0]}"`.

# Expense tracker, step 1: understand one command.
# Amounts are kept in whole cents (ints), never floats.


def to_cents(text):
    """Turn "12.50" into 1250. Only positive amounts with at most 2 decimals."""
    whole, dot, frac = text.partition(".")
    if not whole.isdigit() or (dot and not frac.isdigit()) or len(frac) > 2:
        raise ValueError(f"bad amount: {text}")
    cents = int(whole) * 100 + int(frac.ljust(2, "0"))
    if cents <= 0:
        raise ValueError(f"amount must be positive: {text}")
    return cents


def parse_command(line):
    """Turn one command line into a dict, or raise ValueError saying what is wrong."""
    words = line.split()
    if not words:
        raise ValueError("empty command")
    cmd, args = words[0].lower(), words[1:]
    if cmd == "add":
        if len(args) < 2:
            raise ValueError("usage: add <amount> <category> [note]")
        return {"cmd": "add", "amount": to_cents(args[0]), "category": args[1].lower(), "note": " ".join(args[2:])}
    if cmd == "total":
        if len(args) > 1:
            raise ValueError("usage: total [category]")
        return {"cmd": "total", "category": args[0].lower() if args else None}
    if cmd == "report":
        if args:
            raise ValueError("usage: report")
        return {"cmd": "report"}
    raise ValueError(f"unknown command: {words[0]}")

=== pyp-02 | Expense tracker 2: the ledger
--- teach
Last lesson you wrote the parser: a line of text goes in, a tidy dict comes out. Now comes layer 2, the model: somewhere to keep expenses, and a set of questions you can ask about them.

Picture a club's cash book, kept by one treasurer. Anyone who spends club money tells the treasurer, and anyone who wants to know the balance asks the treasurer. Nobody else writes in the book. That way, if the club makes a new rule ("receipts over 50 need a signature"), only the treasurer has to learn it.

### One record: a dataclass

Each expense is a small, fixed bundle of fields: an amount, a category and a note. That is exactly what a [[dataclass|dataclass-recall]] is for:

```python
from dataclasses import dataclass

@dataclass
class Expense:
    amount: int        # cents
    category: str
    note: str = ""
```

`note: str = ""` gives the note a **default**: if you leave it out, it is `""`. So `Expense(300, "bus")` works, and its note is empty. The field with a default [[must come last|defaults-last]].

### One owner: the Ledger

The collection of expenses belongs to a class called `Ledger` (a ledger is an account book). It keeps a list, and *every* change and every question goes through its methods:

```python
class Ledger:
    def __init__(self):
        self.expenses = []
```

That gives the rules [[one home|encapsulation]]. If you later need to reject duplicate entries or keep an audit log, there is exactly one place to change.

### Answer questions from the data, do not store answers

It is tempting to keep a running `self.total` and update it on every `add`. But [[stored answers go stale|derived-data]] the moment someone adds a `remove` method and forgets to update them. Working out `total()` from the list whenever you are asked is always right. For a personal expense list, it is plenty fast.

```python
def total(self, category=None):
    return sum(e.amount for e in self.expenses if category is None or e.category == category)
```

Read the `if` part aloud: "count this expense if no category was asked for, or if its category is the one asked for". So `total()` adds up everything, and `total("food")` adds up only food.

### Categories: sorted, no duplicates

A set keeps only one copy of each value, and `sorted` turns it into a list in alphabetical order. A set comprehension does both jobs in one line:

```python
sorted({c for c in ["rent", "food", "rent"]})    # ['food', 'rent']
```

### Formatting cents for people

People want to read `1,234.56`, not `123456`. Two operators you know split the cents into whole units and the leftover cents:

```python
cents = 123456
cents // 100      # 1234   whole units
cents % 100       # 56     cents left over
```

(That is the same pair `divmod(cents, 100)` gives.) Then an f-string formats each part:

```python
f"{cents // 100:,}.{cents % 100:02d}"    # '1,234.56'
```

- `:,` puts a comma between every group of three digits, the [[thousands separator|thousands-separator]].
- `:02d` means: `d`, a whole number; `2`, at least 2 characters wide; `0`, fill any gap with zeros. This is **zero padding**. It makes 5 cents show as `.05`, [[not .5|zero-padding]].

### len() for your own class

You met special methods in the advanced course. Defining `__len__` lets callers write `len(ledger)` to ask how many expenses there are. That reads naturally, and it is what Python programmers expect from anything that [[holds a collection|dunder-len]].

**Watch out:** letting other code reach in and edit `ledger.expenses` directly, like `ledger.expenses.append(...)`. It works until the day the ledger needs to enforce a rule, and then that code slips past it. Go through the methods.

::: context dataclass-recall What @dataclass writes for you
You met dataclasses in the advanced course. The `@dataclass` line reads the annotated fields (`amount: int` and so on) and writes three methods for you: `__init__`, so `Expense(1250, "food", "lunch")` works; `__repr__`, so printing one shows `Expense(amount=1250, category='food', note='lunch')`; and `__eq__`, so two expenses with the same fields count as equal. That last one is what lets a check compare `ledger.add(...)` with `Expense(1250, "food", "lunch")`.
:::

::: context defaults-last Why the default goes on the last field
The fields become the parameters of `__init__`, in the order you wrote them. A call like `Expense(300, "bus")` fills them from the left. If a field with a default came before one without, Python could not tell which values you meant to skip. So a dataclass refuses to be created: you get a `TypeError` saying a non-default argument follows a default argument. Ordinary functions have the same rule, which you met with default arguments in the intermediate course.
:::

::: context encapsulation One home for the rules
Programmers call this **encapsulation**: the data lives inside an object, and the outside world may use it only through that object's methods. It is the treasurer and the cash book. The payoff comes later. In the library project you will add rules like "a member may not borrow more than three books", and each rule goes in one method instead of being copied to every place that touches the data.
:::

::: context thousands-separator Commas, dots and countries
A **thousands separator** splits a long number into groups of three digits, so `1234567` reads at a glance as `1,234,567`. The `:,` format always uses a comma and a dot. Many countries swap them: in Germany the same amount is written `1.234,56`. Programs that serve people around the world use locale settings to pick the right style. This tracker keeps it simple, with one style everywhere.
:::

::: context dunder-len What len() really calls
When you write `len(something)`, Python calls `something.__len__()` and hands back what it returns. Lists, strings, dicts and sets all have that method, which is why `len` works on all of them. Giving `Ledger` its own `__len__` makes it join that family. One bonus you get for free: an object with `__len__` and no `__bool__` counts as false in an `if` when its length is 0, so `if ledger:` means "if there are any expenses".
:::

=== pyp-03 | Expense tracker 3: reports
--- teach
Last lesson the ledger learned to store expenses and total them. Now comes layer 3: a report that answers "where did the money go?" at a glance. Here is what the finished report looks like for four expenses:

```
rent          1,200.00
food             57.50
transport         3.20
----------------------
TOTAL         1,260.70
```

Making it takes three steps, and each is a standard technique.

### Step 1: aggregate

To **aggregate** means to gather things into groups and combine each group into one number. Here: group the expenses by category, and [[sum each group|aggregate]]. A plain dict with `get` does it in one pass through the list:

```python
totals = {}
for e in expenses:
    totals[e.category] = totals.get(e.category, 0) + e.amount
```

`totals.get(e.category, 0)` means "the total so far for this category, or 0 if this is the first time we have seen it". For expenses of 1250 food, 320 bus and 4500 food, `totals` ends up as `{'food': 5750, 'bus': 320}`.

### Step 2: order

Biggest spending first is the most useful order. For equal totals, order by name, so the report comes out [[the same every time|deterministic]]. A report whose rows shuffle around is hard to compare from month to month.

One sort with a **tuple key** does both. `totals.items()` gives `(category, total)` pairs; call each pair `kv`, for "key and value":

```python
rows = sorted(totals.items(), key=lambda kv: (-kv[1], kv[0]))
```

The key for each pair is a tuple of two things, and Python [[compares tuples|tuple-key]] one item at a time:

- `-kv[1]` is minus the total. `sorted` puts small keys first, and flipping the sign turns the biggest total into the smallest key. So the biggest spending comes first.
- `kv[0]` is the category name. It only matters when two totals are equal, and then names go in alphabetical order.

```python
totals = {"food": 5750, "art": 500, "zoo": 500, "rent": 120000}
sorted(totals.items(), key=lambda kv: (-kv[1], kv[0]))
# [('rent', 120000), ('food', 5750), ('art', 500), ('zoo', 500)]
```

### Step 3: lay out

**Fixed-width columns** make numbers [[line up|fixed-width]], so the eye can scan them. You met the format codes in the intermediate course. `:<12` means "left-align in 12 characters"; `:>10` means "right-align in 10 characters". Names go on the left; amounts go on the right, so their decimal points line up.

```python
f"{'food':<12}{'57.50':>10}"     # 'food             57.50'
```

That row is 12 + 10 = 22 characters wide. So the dividing rule under the rows is `"-" * 22`: a string times a number repeats it, giving 22 dashes.

### Return lines, do not print them

`report()` returns a list of strings. Printing is the run loop's job. A method that returns data can be tested by comparing lists, reused in a different interface (a web page, an email), and combined with other output. A method that prints [[can only be looked at|return-not-print]].

### Handle the empty case on purpose

A report on no data should say so, instead of printing a header, a rule and a total of zero, or crashing on `max()` of an empty list. Deciding what happens with no data at all is one of the [[edge cases|edge-cases]] every program needs.

**Watch out:** forgetting ties. Sorting only by amount makes the order of equal totals depend on the order they were added, and your tests (and your users) see it change.

::: context aggregate Aggregating is everywhere
"Aggregate" comes from Latin for "gathering into a flock". Every dashboard you have seen does it: steps per day, sales per month, fuel used per engine burn. Databases have it built in; in the SQL course you meet `GROUP BY`, which does exactly what this loop does. The loop needs only one pass through the list, however many categories there are, because the dict finds each running total straight away.
:::

::: context deterministic Same input, same output
A program is **deterministic** when the same input always gives exactly the same output. It is what makes tests possible: a check that compares the report with an expected list only works if the report cannot come out in a different order next time. Flight software is held to this very strictly, because engineers must be able to replay a recorded flight in simulation and see the computer make exactly the same decisions it made in the air.
:::

=== pyp-04 | Expense tracker 4: the program
--- teach
Last lesson the ledger learned to write its own report. Every layer exists now, but nothing joins them together yet. This lesson writes layer 4, the loop that makes them a program: read commands, run them, and collect what happened.

```python
def run(lines):
    ledger = Ledger()
    out = []
    for line in lines:
        ...
    return out
```

`run` gets a list of command lines and gives back a list of output lines. The `...` is what you fill in, one step at a time.

### Step 1: skip blank lines and comments

First, `line.strip()` removes spaces from both ends. Then a blank line, or a line starting with `#`, is skipped with `continue` before it ever reaches the parser. So an input file can be laid out with blank lines and [[annotated for humans|comment-lines]]:

```
# September
add 12.50 food lunch with Sam

add 3.20 transport bus
```

### Step 2: the error boundary

Picture a shop where every worker at the back can hand a problem up to the front desk, but only the front desk talks to customers. The layers below the loop work that way. Each one raises `ValueError` when something is wrong, and knows nothing about screens or users.

The run loop is the **error boundary**: the [[one place that reports problems|error-boundary]]. It catches the error, turns it into an `error: ...` line, and carries on with the next command. One typo must never lose the rest of someone's input.

```python
try:
    command = parse_command(line)
except ValueError as err:
    out.append(f"error: {err}")
    continue
```

`f"error: {err}"` puts the exception's message into the line, so `add abc food` becomes `error: bad amount: abc`.

Catch only what you expect: `ValueError` from parsing. An unexpected `TypeError` is a bug in *your* code, and [[hiding it|narrow-except]] would make it much harder to find.

### Step 3: do each command

Now `command` is one of the three dicts from lesson 1. Branch on `command["cmd"]`:

- `add`: store it in the ledger, and produce `added 12.50 to food`.
- `total`: the label is `total` when the category is `None`, or `total food` when there is one, then a colon and the amount.
- `report`: the report is already a list of lines, so add them all to `out` with `out.extend(...)`. That [[adds each line separately|extend-vs-append]], where `append` would add the whole list as one item.

### Step 4: the thin shell

`run(lines)` returns output instead of printing, for the same reason as `report()`: it can be tested with a list of lines in and a list of lines out, with no keyboard involved. The real program is then a thin shell around it:

```python
if __name__ == "__main__":
    for line in run(sys.stdin.read().splitlines()):
        print(line)
```

You met both parts in the expert course. `sys.stdin.read()` reads everything the user typed or piped in (it needs `import sys` at the top), and `.splitlines()` cuts it into a list of lines. The [[name guard|name-guard]] means the loop runs when the file is executed as a program, but not when another file imports its functions. In a real terminal you could [[feed it a whole file|redirect]] of commands.

### Look back

That is the whole program: four layers, each small, each testable, each with one job. Look back at how little each lesson needed to change the ones before it. That is [[what a good structure buys you|structure-pays]].

**Watch out:** forgetting the `continue` after appending the error line. The loop then goes on to use `command`, which still holds the *previous* line's command. A typo after `add 5 food` would quietly add another 5 to food. On the very first line there is no previous command, and the program crashes.

::: context comment-lines Why input files allow comments
Many files that programs read allow comment lines that start with `#`: Python code itself, Bash scripts, `.gitignore` files and lots of settings files. The program skips them, but people reading the file see the notes. A month of expenses kept in a text file with `# September` and `# October` headings is easier to check by eye, and the program does not care.
:::

::: context narrow-except Why not catch everything
It is tempting to write `except Exception:` so that nothing can ever crash the loop. But then a typo in your own code, like a misspelled variable, turns into a polite `error:` line and the program carries on with wrong results. Nobody finds out until the totals are wrong. A crash with a traceback is annoying, but it points straight at the bug. Catch the errors you planned for, and let the rest be loud.
:::

::: context extend-vs-append append adds one item, extend adds many
`out.append(x)` adds `x` as one new item, even when `x` is a list. `out.extend(x)` goes through `x` and adds each of its items separately.

```python
out = ["x"]; out.append(["a", "b"])    # ['x', ['a', 'b']]
out = ["x"]; out.extend(["a", "b"])    # ['x', 'a', 'b']
```

With `append`, the whole report would sit inside `out` as one list, and printing it would show brackets and quotes instead of five neat lines.
:::

::: context name-guard The guard, once more
When you run the file, Python sets `__name__` to `"__main__"`, so the guarded block runs and reads standard input. When a test file imports this one to call `run` or `parse_command`, `__name__` is the module's own name instead, and the block is skipped. Without the guard, importing the file would sit waiting for input that never comes.
:::

# Expense tracker, step 4: the program.
import sys
from dataclasses import dataclass


def to_cents(text):
    """Turn "12.50" into 1250. Only positive amounts with at most 2 decimals."""
    whole, dot, frac = text.partition(".")
    if not whole.isdigit() or (dot and not frac.isdigit()) or len(frac) > 2:

    if cents <= 0:

def parse_command(line):
    """Turn one command line into a dict, or raise ValueError saying what is wrong."""
    words = line.split()
    if not words:
        raise ValueError("empty command")
    cmd, args = words[0].lower(), words[1:]
    if cmd == "add":
        if len(args) < 2:
            raise ValueError("usage: add <amount> <category> [note]")
        return {"cmd": "add", "amount": to_cents(args[0]), "category": args[1].lower(), "note": " ".join(args[2:])}
    if cmd == "total":
        if len(args) > 1:
            raise ValueError("usage: total [category]")
        return {"cmd": "total", "category": args[0].lower() if args else None}
    if cmd == "report":
        if args:
            raise ValueError("usage: report")
        return {"cmd": "report"}
    raise ValueError(f"unknown command: {words[0]}")


@dataclass
class Expense:
    amount: int
    category: str
    note: str = ""


def format_cents(cents):
    """1250 -> "12.50", 123456 -> "1,234.56"."""
    return f"{cents // 100:,}.{cents % 100:02d}"


class Ledger:
    def __init__(self):
        self.expenses = []

    def add(self, amount, category, note=""):
        expense = Expense(amount, category, note)
        self.expenses.append(expense)
        return expense

    def total(self, category=None):
        return sum(e.amount for e in self.expenses if category is None or e.category == category)

    def categories(self):
        return sorted({e.category for e in self.expenses})

    def __len__(self):
        return len(self.expenses)

    def by_category(self):
        totals = {}
        for e in self.expenses:
            totals[e.category] = totals.get(e.category, 0) + e.amount
        return totals

    def report(self):
        if not self.expenses:
            return ["no expenses"]
        rows = sorted(self.by_category().items(), key=lambda kv: (-kv[1], kv[0]))
        lines = [f"{category:<12}{format_cents(total):>10}" for category, total in rows]
        lines.append("-" * 22)
        lines.append(f"{'TOTAL':<12}{format_cents(self.total()):>10}")
        return lines


def run(lines):
    """Run every command line; return the output lines. Never crashes on bad input."""
    ledger = Ledger()
    out = []
    for line in lines:
        line = line.strip()
        if not line or line.startswith("#"):
            continue
        try:
            command = parse_command(line)
        except ValueError as err:
            out.append(f"error: {err}")
            continue
        if command["cmd"] == "add":
            ledger.add(command["amount"], command["category"], command["note"])
            out.append(f"added {format_cents(command['amount'])} to {command['category']}")
        elif command["cmd"] == "total":
            category = command["category"]
            label = "total" if category is None else f"total {category}"
            out.append(f"{label}: {format_cents(ledger.total(category))}")
        else:
            out.extend(ledger.report())
    return out


if __name__ == "__main__":
    for output_line in run(sys.stdin.read().splitlines()):
        print(output_line)

=== pyp-05 | Markdown converter 1: inline formatting with regular expressions
--- teach
You finished the expense tracker: four small layers, each with one job and each tested on its own. The second project uses the same habits on a new kind of problem: turning text written in Markdown into a web page.

**Markdown** is a plain-text way of marking up writing. You have probably typed it without knowing its name: put stars around a word in a chat message and it comes out bold. [[READMEs on code sites|markdown-origin]], chat apps and note apps all use it.

A web browser does not read Markdown, though. It reads **HTML**, the language web pages are written in. HTML wraps text in **[[tags|html-tags]]**, words inside angle brackets: `<strong>` means "bold starts here" and `</strong>`, with a slash, means "bold ends here".

So the converter rewrites one into the other. Markdown on the left, HTML on the right:

```
**bold**        <strong>bold</strong>
*italic*        <em>italic</em>
`code`          <code>code</code>
[text](url)     <a href="url">text</a>
```

The third line is a **code span**: text between two backticks (the ` key, top left on most keyboards), shown in a code font.

Markdown has two kinds of formatting. **Inline** formatting happens *inside* a line, like making one word bold. **Block** structure is how lines group into headings, paragraphs, lists and code. This lesson does the inline kind. The next three lessons do the blocks.

### Step 1: escape the text first

Some characters mean something special in HTML. `<` starts a tag. So if your text says `a < b`, the browser tries to read `< b` as the start of a tag, and the text comes out broken.

**[[Escaping|why-escape]]** means swapping each special character for a safe code that the browser shows as the plain character. These codes are called **entities**: a short name between `&` and `;`.

| Character | Entity | Read it as |
|---|---|---|
| `&` | `&amp;` | ampersand |
| `<` | `&lt;` | less than |
| `>` | `&gt;` | greater than |
| `"` | `&quot;` | quote |

`str.replace` does each swap. The order matters: replace `&` **first**. Every entity you make contains an `&`, so if the `&` swap came later, it would turn each `&lt;` you had just made into `&amp;lt;`:

```python
"a < b".replace("<", "&lt;").replace("&", "&amp;")    # 'a &amp;lt; b'   wrong order
"a < b".replace("&", "&amp;").replace("<", "&lt;")    # 'a &lt; b'       right
```

### Step 2: describe a shape, not exact text

`replace` needs the exact text to look for. But `**bold**` could have any words between its stars. You need to describe a *shape*: "two stars, some text, two stars".

A **[[regular expression|regex-history]]** (regex for short) is a small language for describing shapes of text. Python runs them with the `re` module, which you import at the top of the file:

```python
import re

re.findall(r"\d+", "3 cats and 12 dogs")    # ['3', '12']
```

Read the pattern `\d+` piece by piece. `\d` means "one digit, 0 to 9". `+` means "one or more of the thing just before". So `\d+` is a run of digits, and `re.findall` returns every run it finds, in a list.

The `r` in front of the quote makes a **[[raw string|raw-strings]]**: Python leaves every backslash alone and hands it to `re` untouched. Write every pattern as a raw string.

### Step 3: find and replace, keeping a group

`re.sub(pattern, replacement, text)` finds every match of the pattern in the text and replaces it. ("sub" is short for substitute.)

```python
re.sub(r"\*\*(.+?)\*\*", r"<b>\1</b>", "a **b** c")    # 'a <b>b</b> c'
```

That pattern is a first try at bold. Piece by piece:

- `\*` is a real star. A bare `*` in a pattern means "repeat", so a star you want to *find* needs a backslash in front. `\*\*` is two real stars.
- `.` is any one character.
- `+?` is "one or more, but as few as possible". Step 4 explains the `?`.
- `( )` round brackets make a **group**: they capture the part of the match inside them. In the replacement, `\1` means "whatever group 1 captured".

So it finds two stars, some text, two stars, and the replacement keeps only the text, wrapped in tags.

Here are all the pieces this project uses:

| Pattern | Matches |
|---|---|
| `\*` | a real `*` (a bare `*` means "repeat") |
| `.` | any one character |
| `\S` | any one character that is not a space |
| `+` | one or more of the thing before |
| `*` | zero or more of the thing before |
| `?` | the thing before is optional (zero or one) |
| `+?`, `*?` | like `+` and `*`, but as **few** as possible |
| `( )` | a group; the replacement calls it `\1`, `\2` and so on |
| `[^\]]` | any one character except `]` |

### Step 4: greedy and lazy

Plain `+` is **greedy**: it grabs as much text as it can. In `"**a** and **b**"`, a greedy pattern runs from the first `**` all the way to the *last* one, and swallows ` and ` into the bold:

```python
re.sub(r"\*\*(.+)\*\*", r"<b>\1</b>", "**a** and **b**")     # '<b>a** and **b</b>'
re.sub(r"\*\*(.+?)\*\*", r"<b>\1</b>", "**a** and **b**")    # '<b>a</b> and <b>b</b>'
```

Adding `?` after `+` makes it **[[lazy|greedy-lazy]]**: it takes as little as it can, so it stops at the first closing `**`.

### Step 5: say exactly what counts as emphasis

`5 * 3 * 2` is arithmetic, not italic. Markdown agrees: emphasis needs a non-space character just inside each star. A loose pattern gets this wrong:

```python
re.sub(r"\*(.+?)\*", r"<em>\1</em>", "5 * 3 * 2")    # '5 <em> 3 </em> 2'   wrong
```

This pattern states the rule exactly:

```
\*(\S|\S.*?\S)\*
```

Read it as: a star; then *either* a single non-space character, *or* a non-space, as little as possible of anything, and another non-space; then a star. The `|` bar means "or". The regex tries the left side first, which is why `*a* or *b*` gives two short matches instead of one long one.

`re.compile(pattern)` turns a pattern into a **pattern object** you can keep in a variable and reuse. Its `.sub` works like `re.sub`, minus the pattern argument:

```python
EM = re.compile(r"\*(\S|\S.*?\S)\*")
EM.sub(r"<em>\1</em>", "5 * 3 * 2")     # '5 * 3 * 2'   left alone
EM.sub(r"<em>\1</em>", "*a* or *b*")    # '<em>a</em> or <em>b</em>'
```

A name in capitals, like `EM`, is Python's way of saying [[this is a constant|constants]]: set once at the top of the file and never changed.

Bold uses the same idea with two stars on each side: `\*\*(\S|\S.*?\S)\*\*`. Run bold **before** italic. Otherwise the italic pattern takes the first star of `**bold**` as an opening star and makes a mess: `<em>*bold</em>*`.

### Step 6: links

A link is written `[text](url)`. Its pattern is

```
\[([^\]]+)\]\(([^)\s]+)\)
```

In pieces:

- `\[` is a real `[`. Square brackets mean something in a pattern too, so a real one needs a backslash.
- `([^\]]+)` is group 1, the link text: one or more characters that are not `]`. Square brackets with `^` just inside mean "any one character *except* these".
- `\]\(` is a real `]` and then a real `(`.
- `([^)\s]+)` is group 2, the URL: one or more characters that are not `)` and not a space (`\s` is any space character).
- `\)` is a real `)`.

The replacement puts group 2 in the tag and group 1 between the tags:

```python
LINK = re.compile(r"\[([^\]]+)\]\(([^)\s]+)\)")
LINK.sub(r'<a href="\2">\1</a>', "see [the docs](https://example.com)")
# 'see <a href="https://example.com">the docs</a>'
```

### Step 7: code spans are left alone

A code span is never formatted: backticks around `a*b*c` must give `a*b*c`, stars and all, not italics. It is still escaped, though: a `<` inside code must still become `&lt;`, so the browser shows it as a plain `<`. So cut the code spans out *before* formatting anything.

`re.split(pattern, text)` cuts the text wherever the pattern matches. Usually the matched parts are thrown away. But when the pattern is wrapped in a group, `re.split` **keeps** them in the list:

```python
re.split(r"(`[^`]+`)", "use `a*b*c` here")    # ['use ', '`a*b*c`', ' here']
```

Inside the group, the pattern is a backtick, then one or more characters that are not backticks, then a backtick: one code span. The list always takes turns: ordinary text, code, ordinary text, code, and so on. So the code spans land at the **[[odd positions|odd-positions]]** of the list: 1, 3, 5.

That gives `inline` its shape. Loop over the pieces with `enumerate`. At an odd position (`i % 2 == 1`), cut off the two backticks with `part[1:-1]`, escape what is left and wrap it in `<code>` tags. At an even position, escape and then format: links, then bold, then italic. Finally join all the pieces with `"".join(...)`.

**Watch out:** formatting first and escaping after. Then the `<strong>` tags you just added get escaped too, and the page shows the text `<strong>` instead of bold. Always escape first, then add tags.

::: context why-escape Escaping keeps a page safe
Escaping is not only about looks. Picture a website that shows visitors' comments without escaping them. Someone types a comment containing a `<script>` tag, and every browser that shows the page runs that person's program. This attack is called **cross-site scripting**, and it is one of the most common security bugs on the web. Escaping every piece of text before it goes into HTML shuts the door: the script shows up as harmless text.

::: context regex-history An old idea in every toolbox
The mathematician Stephen Kleene described "regular expressions" in the 1950s, as a way of writing down which strings a simple machine accepts. In 1968 Ken Thompson built them into a text editor, and later tools such as `grep` (a Unix command that finds lines matching a pattern) made them part of every programmer's toolbox. Today nearly every language has them. The details differ a little between languages, but `\d`, `+`, `*`, `?`, groups and square brackets mean the same thing almost everywhere.
:::

::: context raw-strings Why the r matters
In an ordinary Python string, a backslash starts an escape: `"\n"` is a newline, and `"\b"` is a backspace character. In a regex, `\b` means something else (the edge of a word), so an ordinary string would quietly hand `re` the wrong thing. It is worse in a replacement: in an ordinary string `"\1"` becomes an invisible character with code 1, not "group 1". A raw string, `r"\1"`, keeps the backslash and the 1 exactly as typed. Newer versions of Python even warn you about backslashes they do not recognise in ordinary strings.
:::

::: context odd-positions Why code always lands on odd positions
`re.split` always puts the text *before* the first match at position 0, even when there is none. If the line starts with code, position 0 is an empty string:

```python
re.split(r"(`[^`]+`)", "`x` and `y`")
# ['', '`x`', ' and ', '`y`', '']
```

So the pattern never shifts: even positions (0, 2, 4) are ordinary text, possibly empty, and odd positions (1, 3) are code. Formatting an empty string gives an empty string, so the empty pieces do no harm.

EM = re.compile(r"\*(\S|\S.*?\S)\*")
LINK = re.compile(r"\[([^\]]+)\]\(([^)\s]+)\)")

    return text.replace("&", "&amp;").replace("<", "&lt;").replace(">", "&gt;").replace('"', "&quot;")


def format_text(text):

    text = LINK.sub(r'<a href="\2">\1</a>', text)
    text = STRONG.sub(r"<strong>\1</strong>", text)

        if i % 2 == 1:

        else:
            out.append(format_text(part))
    return "".join(out)

=== pyp-06 | Markdown converter 2: headings and paragraphs
--- teach
Last lesson, `inline` turned the formatting *inside* one line into HTML. Now the converter learns the document's **blocks**: the big pieces a page is built from. This lesson does two of them, headings and paragraphs.

This Markdown

```
# Title

This is one paragraph
that spans two lines.

## Section
Another paragraph.
```

becomes this HTML:

```
<h1>Title</h1>
<p>This is one paragraph that spans two lines.</p>
<h2>Section</h2>
<p>Another paragraph.</p>
```

`<h1>` is a heading of [[level 1|heading-levels]], the biggest; `<h2>` is level 2, a size smaller; and so on down to `<h6>`. `<p>` is a paragraph.

The rules:

- A line that starts with one to six `#` and then a space is a heading. The number of `#` is its level.
- Ordinary lines that come one after another form one paragraph. Their text is joined with single spaces.
- A blank line ends a paragraph. A heading also ends any paragraph before it.

### Step 1: recognise a heading

A regular expression can state the heading rule exactly:

```
^(#{1,6})\s+(.*)$
```

In pieces:

- `^` means "the start of the line". It matches no character; it pins the pattern to the beginning.
- `(#{1,6})` is group 1: between one and six `#`. Curly braces give a count: "at least 1, at most 6 of the thing before".
- `\s+` is one or more spaces.
- `(.*)` is group 2: the rest of the text.
- `$` means "the end of the line".

`pattern.match(line)` tries the pattern at the start of the line. It returns a **[[match object|match-objects]]** if the line fits, or `None` if it does not. A match object hands back the groups:

```python
HEADING = re.compile(r"^(#{1,6})\s+(.*)$")

m = HEADING.match("## Part two")
m.group(1)          # '##'
len(m.group(1))     # 2, the level
m.group(2)          # 'Part two'

HEADING.match("#hashtag")          # None: no space after the #
HEADING.match("####### seven")     # None: seven is too many
```

`None` counts as false in an `if`, so `if m:` reads "if the line is a heading".

**Watch out:** matching headings with `line.startswith("#")`. Then `#hashtag` and `####### seven` become headings too. The regex says the rule exactly.

### Step 2: a paragraph needs a buffer

When you see the first line of a paragraph, you cannot write its `<p>` yet. You do not know where it ends. It is like a friend reading your texts aloud: they wait until you have finished the message, not after each word.

So collect the paragraph's lines in a list, called a **[[buffer|buffer-word]]**: a holding place for data that is not ready to go out yet. When something ends the paragraph (a blank line, a heading, or the end of the input) you **flush** the buffer: write it out and empty it.

```python
paragraph = []

def flush():
    if paragraph:
        html.append(f"<p>{inline(' '.join(paragraph))}</p>")
        paragraph.clear()
```

`' '.join(paragraph)` glues the lines together with single spaces, and `inline` formats the result. The `if paragraph:` means an empty buffer writes nothing, so calling `flush()` is always safe.

### Step 3: flush lives inside convert

`flush` is defined *inside* `convert`, so it can see `convert`'s lists `html` and `paragraph`. It is a closure, from the first lesson of the expert course.

It empties the list with `paragraph.clear()`, not `paragraph = []`. That is [[the closure rule|closure-rule]] again: assigning to a name inside `flush` would make a brand-new local variable inside `flush`, and the shared list outside would never be emptied. `.clear()` changes the shared list itself, so no `nonlocal` is needed.

### Step 4: the loop, and the end

The main loop looks at each line once and decides what it is:

```python
for raw in md.splitlines():
    line = raw.strip()
    # blank line  -> flush()
    # heading     -> flush(), then add the <h1> ... <h6> line
    # anything else -> paragraph.append(line)
flush()        # the last paragraph is still waiting
```

`raw.strip()` removes spaces at both ends, so an indented line and a line of only spaces are treated like the others.

**Don't forget the end.** When the loop finishes, the [[last paragraph|last-block]] is still sitting in the buffer, because nothing came after it to end it. One more `flush()` after the loop writes it out. Losing the final block is the most common bug in this kind of code.

At the very end, `"\n".join(html)` puts one block on each line of the result.

::: context heading-levels Six levels, like an outline
HTML has exactly six heading levels, `<h1>` to `<h6>`, and Markdown's one to six `#` map onto them. They work like an outline: `<h1>` is the title of the page, `<h2>` a section, `<h3>` a part of that section. Headings are not only for looks. Screen readers, the programs that read a page aloud for blind users, let people jump from heading to heading, and search engines use them to understand what a page is about.
:::

::: context match-objects match, search, and why ^ is still worth writing
`pattern.match(text)` only looks for the pattern at the very start of the text. Its cousin `pattern.search(text)` looks anywhere. So with `match`, the `^` is not strictly needed, but writing it makes the pattern say "start of line" out loud to whoever reads it next. A match object's `group(0)` is the whole matched text; `group(1)`, `group(2)` are the round-bracket groups, counted by their opening bracket from the left.
:::

def format_text(text):

    text = LINK.sub(r'<a href="\2">\1</a>', text)
    text = STRONG.sub(r"<strong>\1</strong>", text)
    return EM.sub(r"<em>\1</em>", text)


def inline(text):

    parts = re.split(r"(`[^`]+`)", text)
    out = []
    for i, part in enumerate(parts):
        if i % 2 == 1:
            out.append(f"<code>{escape(part[1:-1])}</code>")
        else:
            out.append(format_text(part))

HEADING = re.compile(r"^(#{1,6})\s+(.*)$")


def convert(md):
    html = []
    paragraph = []

    def flush():
        if paragraph:
            html.append(f"<p>{inline(' '.join(paragraph))}</p>")
            paragraph.clear()

    for raw in md.splitlines():
        line = raw.strip()
        heading = HEADING.match(line)
        if not line:
            flush()
        elif heading:
            flush()
            level = len(heading.group(1))
            html.append(f"<h{level}>{inline(heading.group(2).strip())}</h{level}>")
        else:
            paragraph.append(line)
    flush()
    return "\n".join(html)

=== pyp-07 | Markdown converter 3: lists
--- teach
Your converter now handles headings and paragraphs. Next comes a third kind of block that spans several lines: the list.

This Markdown

```
- milk
- eggs

1. mix
2. bake
```

becomes this HTML:

```
<ul>
<li>milk</li>
<li>eggs</li>
</ul>
<ol>
<li>mix</li>
<li>bake</li>
</ol>
```

`<ul>` is a [[bullet list|list-tags]] ("unordered list"), `<ol>` is a numbered list ("ordered list"), and each `<li>` is one list item.

The rules:

- A line starting with `- ` or `* ` (a dash or star, then a space) is a bullet item.
- A line starting with a number, a dot and a space is a numbered item.
- Items of the same kind that come one after another form one list.
- Anything else ends the list: a blank line, a heading, ordinary text, or an item of the *other* kind.

### Step 1: two new patterns

```
^[-*]\s+(.*)$         a bullet item
^\d+\.\s+(.*)$        a numbered item
```

`[-*]` is one character that is either `-` or `*`. Inside square brackets a star is only a star, so it needs no backslash. `\d+` is one or more digits, and `\.` is a real dot (a bare `.` would mean "any character"). In both, `\s+` insists on at least one space, and group 1 is the item's text.

That space matters, because stars also mean italics. `* item`, star then space, is a bullet. `*word* starts here` is a paragraph that begins with an italic word:

```python
BULLET = re.compile(r"^[-*]\s+(.*)$")
BULLET.match("* eggs").group(1)        # 'eggs'
BULLET.match("*word* starts here")     # None: no space after the star
```

### Step 2: the converter remembers something

Until now, each line decided its own fate. A list item is different: what to do with it depends on what came before. If no list is open, the item must *start* one (`<ul>`, then `<li>`). If a list of the same kind is already open, it only adds an `<li>`.

A program where the same input means different things depending on what it remembers is a **[[state machine|state-machine]]**. What it remembers is its **state**. A phone's power button is an everyday one: the same press wakes a sleeping phone and locks an awake one.

Here the state is one variable:

```python
list_kind = None      # None (no list open), "ul" or "ol"
```

### Step 3: a helper that changes the state

```python
def list_item(kind, text):
    nonlocal list_kind
    if list_kind != kind:
        flush()                    # close whatever was open
        html.append(f"<{kind}>")
        list_kind = kind
    html.append(f"<li>{inline(text)}</li>")
```

If the open list is not this kind (no list, or the other kind), it flushes, opens a new list and records the new state. Then it adds the item.

This helper *assigns* to `list_kind`, so it needs **[[nonlocal|nonlocal-again]]**, unlike `flush` last lesson, which only changed a list. Without it, `list_kind = kind` would make a new variable inside `list_item`.

### Step 4: flush closes lists too

Extend `flush()` so that after writing any paragraph it also closes an open list:

```python
if list_kind:
    html.append(f"</{list_kind}>")
    list_kind = None
```

`flush` now assigns to `list_kind` too, so it also needs `nonlocal list_kind` as its first line. The payoff: every place that already calls `flush()` (a blank line, a heading, the end of the input) now closes lists as well, without changing any of them.

### Step 5: ordinary text right after a list

One case is left. An ordinary line straight after a list goes into the paragraph buffer, and nothing has closed the list. When `flush()` runs later, it writes the paragraph first and closes the list second, so the paragraph lands *inside* the list:

```
<ul>
<li>a</li>
<p>then text</p>
</ul>
```

The fix: in the "ordinary line" branch, if a list is open, call `flush()` first, then add the line to the paragraph.

**Watch out:** the two ways lists go wrong are ordinary text being swallowed into the list, and a list that is never closed. Test both: text right after a list, and a list at the very end of the input.

One variable and a few rules about when it changes: that is a whole state machine. The same shape, with more states, is how [[flight software|state-machines-later]] is organised.

::: context list-tags The browser does the numbering
In `<ol>` the browser numbers the items itself: 1, 2, 3. That is why your converter throws the typed numbers away. `22. two` becomes plain `<li>two</li>`, shown as number 2 if it is the second item. `<ul>`, `<ol>` and `<li>` are three of the oldest tags in HTML. Real Markdown also allows `+` as a bullet and lists inside lists (by indenting), which this converter leaves out.

import re

STRONG = re.compile(r"\*\*(\S|\S.*?\S)\*\*")
EM = re.compile(r"\*(\S|\S.*?\S)\*")
LINK = re.compile(r"\[([^\]]+)\]\(([^)\s]+)\)")


def escape(text):
    """Make text safe to put inside HTML. The & must be replaced first."""
    return text.replace("&", "&amp;").replace("<", "&lt;").replace(">", "&gt;").replace('"', "&quot;")


def format_text(text):
    text = escape(text)
    text = LINK.sub(r'<a href="\2">\1</a>', text)
    text = STRONG.sub(r"<strong>\1</strong>", text)
    return EM.sub(r"<em>\1</em>", text)


def inline(text):
    """Code spans first, so nothing inside backticks is formatted."""
    parts = re.split(r"(`[^`]+`)", text)
    out = []
    for i, part in enumerate(parts):
        if i % 2 == 1:
            out.append(f"<code>{escape(part[1:-1])}</code>")
        else:
            out.append(format_text(part))
    return "".join(out)


HEADING = re.compile(r"^(#{1,6})\s+(.*)$")


def convert(md):
    html = []
    paragraph = []

    def flush():
        if paragraph:
            html.append(f"<p>{inline(' '.join(paragraph))}</p>")
            paragraph.clear()

    for raw in md.splitlines():
        line = raw.strip()
        heading = HEADING.match(line)
        if not line:
            flush()
        elif heading:
            flush()
            level = len(heading.group(1))
            html.append(f"<h{level}>{inline(heading.group(2).strip())}</h{level}>")
        else:
            paragraph.append(line)
    flush()
    return "\n".join(html)

import re

STRONG = re.compile(r"\*\*(\S|\S.*?\S)\*\*")
EM = re.compile(r"\*(\S|\S.*?\S)\*")
LINK = re.compile(r"\[([^\]]+)\]\(([^)\s]+)\)")

    return text.replace("&", "&amp;").replace("<", "&lt;").replace(">", "&gt;").replace('"', "&quot;")


def format_text(text):
    text = escape(text)
    text = LINK.sub(r'<a href="\2">\1</a>', text)
    text = STRONG.sub(r"<strong>\1</strong>", text)
    return EM.sub(r"<em>\1</em>", text)


def inline(text):
    """Code spans first, so nothing inside backticks is formatted."""
    parts = re.split(r"(`[^`]+`)", text)
    out = []
    for i, part in enumerate(parts):
        if i % 2 == 1:
            out.append(f"<code>{escape(part[1:-1])}</code>")
        else:
            out.append(format_text(part))
    return "".join(out)


HEADING = re.compile(r"^(#{1,6})\s+(.*)$")
BULLET = re.compile(r"^[-*]\s+(.*)$")
NUMBERED = re.compile(r"^\d+\.\s+(.*)$")


def convert(md):
    html = []
    paragraph = []
    list_kind = None

    def flush():
        nonlocal list_kind
        if paragraph:
            html.append(f"<p>{inline(' '.join(paragraph))}</p>")
            paragraph.clear()
        if list_kind:
            html.append(f"</{list_kind}>")
            list_kind = None

    def list_item(kind, text):
        nonlocal list_kind
        if list_kind != kind:
            flush()
            html.append(f"<{kind}>")
            list_kind = kind
        html.append(f"<li>{inline(text)}</li>")

    for raw in md.splitlines():
        line = raw.strip()
        heading = HEADING.match(line)
        bullet = BULLET.match(line)
        numbered = NUMBERED.match(line)
        if not line:
            flush()
        elif heading:
            flush()
            level = len(heading.group(1))
            html.append(f"<h{level}>{inline(heading.group(2).strip())}</h{level}>")
        elif bullet:
            list_item("ul", bullet.group(1))
        elif numbered:
            list_item("ol", numbered.group(1))
        else:
            if list_kind:
                flush()
            paragraph.append(line)
    flush()
    return "\n".join(html)

=== pyp-08 | Markdown converter 4: code blocks and the command line
--- teach
Your converter handles inline formatting, headings, paragraphs and lists. The last feature is the **fenced code block**: lines of code between two [[fences|fence-name]], each fence a line of three backticks. A language name may follow the opening fence. Here is a Markdown document with one code block; the line numbers on the left are only there to talk about, they are not part of the text:

```
line 1:  ```python
line 2:  if x < 3:
line 3:      print("*not italic*")
line 4:  ```
```

Line 1 is the opening fence, with the language `python`. Line 4 is the closing fence.

Inside a fence, *nothing* is Markdown. No headings, no lists, no emphasis, and every space of indentation must survive, because in Python the indentation is part of the code. The only job is to escape it. The output is

```
<pre><code class="language-python">if x &lt; 3:
    print(&quot;*not italic*&quot;)</code></pre>
```

`<pre>` means "[[preformatted|pre-tag]]": show the text exactly as it is, spaces and line breaks included. The **[[class|language-class]]** attribute records the language. Without a language name, the tag is plain `<code>`.

### Step 1: recognise a fence

The opening fence is three backticks, maybe some spaces, maybe a language name. Its pattern:

```
^```\s*([\w+-]*)\s*$
```

In pieces:

- `^` and `$` pin it to the whole line.
- Three backticks are three real backticks. A backtick means nothing special in a regex, so it needs no backslash.
- `\s*` is zero or more spaces.
- `([\w+-]*)` is group 1, the language: zero or more characters that are `\w` (a "word character": a letter, a digit or `_`), `+` or `-`. The `+` and `-` let `c++` and `objective-c` through. The `*` means it may be empty, when there is no language.

```python
FENCE = re.compile(r"^```\s*([\w+-]*)\s*$")
FENCE.match("```python").group(1)    # 'python'
FENCE.match("```").group(1)          # ''   no language
FENCE.match("``` c++").group(1)      # 'c++'
```

### Step 2: a loop that can jump ahead

Inside a code block, lines must not be stripped or read as Markdown. So the one-line-at-a-time `for` loop no longer fits. When you see an opening fence, you want to **[[consume|consume-lines]]** every line up to the closing fence in one go, and a `for` loop always hands you the very next line.

The fix is the index loop from the tokenizer lesson: keep a number `i` pointing at the current line, like a finger on the page. A branch can then move the finger as far as it needs. Here is its shape (the `if` line is written in words):

```python
lines = md.splitlines()
i = 0
while i < len(lines):
    if opening fence:
        i += 1                                 # step past the opening fence
        while i < len(lines) and lines[i].strip() != "```":
            code.append(escape(lines[i]))      # the raw line, not stripped
            i += 1
        ...
    i += 1          # the next line; after a code block, this steps past the closing fence
```

The rest of the branches (blank, heading, bullet, numbered, text) stay as they were. Only the loop around them changes, and every line of them still works on the stripped `line = lines[i].strip()`.

### Step 3: a fence that is never closed

If the closing fence never comes, the code block runs to the end of the document. You get that for free: the inner loop's first test, `i < len(lines)`, becomes false at the end and the loop stops. That test must come [[first|short-circuit]], before the word `and`, so that `lines[i]` is never read past the last line.

### Step 4: build the block

A code block closes any open paragraph or list first, so call `flush()` before collecting. When the inner loop ends, put the whole block into *one* entry of `html`: the opening tags, the code lines joined with `"\n"`, and the closing tags.

```python
attr = f' class="language-{language}"' if language else ""
html.append(f"<pre><code{attr}>" + "\n".join(code) + "</code></pre>")
```

`attr` is either the class attribute (with a space in front) or nothing at all.

**Watch out:** stripping the code lines, or running them through `inline`. Both are easy to do by accident, because every other branch uses the stripped `line`. Only the fence *test* strips (`lines[i].strip()`); what you store is `escape(lines[i])`, the raw line.

### Step 5: the command line

Like the expense tracker, the converter becomes a program by adding a thin shell. Read all of standard input, convert it, print it:

```python
if __name__ == "__main__":
    print(convert(sys.stdin.read()))
```

You need `import sys` at the top. Because `convert` takes a string and returns a string, the shell is one line, and everything that matters can be tested without it. On a real computer you would [[pipe a file through it|pipes]].

With this lesson you have built a real tool: a document converter with inline formatting, block structure, state, a mode for code, and a command-line interface. It is about a hundred lines, blank lines included, and each part can be tested on its own.

::: context fence-name Why "fence"
The three backticks stand like a fence around the code, marking where Markdown stops and starts again. Fenced code blocks were popularised by GitHub's version of Markdown and later written into CommonMark. The first Markdown had only one way to show code: indent every line by four spaces. Fences are easier to type and leave room for a language name. CommonMark also allows fences of three tildes (`~~~`), which this converter does not handle.
:::

::: context pre-tag Normally HTML ignores your spaces
In ordinary HTML, the browser squashes any run of spaces and line breaks into a single space, which is why joining paragraph lines with spaces was fine. That would ruin code. Inside `<pre>`, spaces and line breaks are kept exactly, and the text is usually shown in a fixed-width font, where every character takes the same room so columns line up. That is also why the code lines are joined with `"\n"` inside a single `<pre>` element.
:::

::: context language-class What the class is for
`class="language-python"` does not change anything by itself. It is a label that other programs read. Syntax highlighters, small programs that colour keywords, strings and comments, look for a class starting with `language-` to know which rules to use. CommonMark recommends exactly this form, so your converter's output works with the common highlighters.
:::

::: context consume-lines One index, jumping ahead
The outer loop normally moves the index by one. The code branch moves it many lines at once, so the lines inside the fence are never seen by the other branches.

::: context short-circuit Why the order inside the and matters
Python works out `a and b` from left to right, and stops as soon as the answer is known. If `a` is false, the whole thing is false, so `b` is never looked at. This is called **short-circuiting**. In the inner loop's test, `i < len(lines)` comes first. Once `i` reaches the end, that part is false, and `lines[i]` is never read. Swap the two parts and an unclosed fence crashes with `IndexError`.
:::

::: context pipes Using it for real
Save the program as `md.py`. In a terminal, `python3 md.py < notes.md > notes.html` feeds the file `notes.md` into standard input with `<`, and sends everything printed into `notes.html` with `>`. With `|`, the "pipe", one program's output becomes the next one's input: `cat notes.md | python3 md.py`. The program never knows or cares where its text came from, which is the whole point of reading standard input.
:::

    paragraph = []
    list_kind = None

    def flush():
        nonlocal list_kind
        if paragraph:
            html.append(f"<p>{inline(' '.join(paragraph))}</p>")

            html.append(f"</{list_kind}>")

            flush()
            html.append(f"<{kind}>")
            list_kind = kind
        html.append(f"<li>{inline(text)}</li>")

    lines = md.splitlines()
    i = 0
    while i < len(lines):
        line = lines[i].strip()

=== pyp-09 | Library system 1: the data model
--- teach
Last lesson finished the Markdown converter: a pure `convert` function that turns text into HTML, with a one-line shell around it. The third project is bigger in a different way. It is a lending library: books, members, loans, rules, and saving everything to disk. You will build it over four lessons, one layer at a time. This first lesson builds the layer everything else stands on: the data.

Picture a small library before computers. There is a card for every book and a card for every member. Behind the desk sits a clerk. You never walk round the desk and scribble on the cards yourself; you ask the clerk, and the clerk follows the library's rules. Your program will work the same way.

The classes and rules that describe the real-world thing a program is about (its **[[domain|domain-word]]**) are called a **domain model**. Most business software is exactly this: a domain model with rules, plus **persistence**, which means saving the data so it is still there after the program stops. Persistence is lesson 3.

**Step 1: find the nouns.** Read a description of the problem and underline the nouns: *books*, *members*, *loans*, *the library*. Each noun is a candidate for a class. Loans are next lesson. This one builds books, members and the library.

**Step 2: decide what identifies each one.** An **identifier** (an **id** for short) is a value that picks out exactly one record and never changes. A book is identified by its **[[ISBN|isbn]]**. A member is identified by a **member id**, such as `"m1"`. Ids are what you use as [[dict keys|ids-as-keys]], and what other records store when they need to point at something.

A book is only data, so it is a dataclass. Remember from the advanced course: `@dataclass` reads the annotated fields and writes `__init__`, `__repr__` and `__eq__` for you.

```python
from dataclasses import dataclass

@dataclass
class Book:
    isbn: str
    title: str
    author: str
    copies: int = 1

print(Book("111", "Dune", "Frank Herbert"))
# Book(isbn='111', title='Dune', author='Frank Herbert', copies=1)
```

`copies` is how many physical copies of the book the library owns. It has a default of `1`, so it must come last: fields with defaults go after fields without. `Member` has the same shape with two fields, `member_id` and `name`.

**Step 3: one object owns the collections.** The `Library` class is the clerk. It holds two dicts: `books` maps each ISBN to its `Book`, and `members` maps each member id to its `Member`. Every change goes [[through its methods|one-door]]. That is where the rules live, such as "a member id cannot be used twice" and "adding a book that already exists adds copies". A second delivery of *Dune* does not make a second card; it raises the count on the first one:

```python
lib = Library()
lib.add_book(Book("111", "Dune", "Frank Herbert", 2))
lib.add_book(Book("111", "Dune", "Frank Herbert", 3))
print(lib.books["111"].copies)     # 5
```

**Step 4: an exception of your own.** When the library refuses something, the code that called it needs to tell "the library said no" apart from "there is a bug". You built exception classes in the intermediate course. Here one line of body is enough (`pass` means "nothing to add"):

```python
class LibraryError(Exception):
    pass
```

Now the code that talks to the user can [[catch just this kind of failure|catching-one-kind]] and show its message:

```python
try:
    lib.add_book(Book("222", "Emma", "Jane Austen", 0))
except LibraryError as err:
    print("refused:", err)     # refused: a book needs at least one copy
```

A real bug, like a `TypeError` from a typo, is not a `LibraryError`, so it is not caught. It still stops the program, and you get to see it.

**Step 5: keep your own copy.** The advanced course's debugging lesson showed **aliasing**: two names pointing at one object, so a change through one shows through the other. If `add_book` stored the caller's own `Book` object, the library and the caller would [[share one object|aliasing-picture]]:

```python
store = {}
mine = Book("111", "Dune", "Frank Herbert")
store["111"] = mine              # the SAME object, not a copy
store["111"].copies += 4
print(mine.copies)               # 5: your Book changed too
```

It works the other way too: the caller could change the library's record without asking the clerk. The fix is `replace` from the `dataclasses` module. `replace(book)` makes a new object with the same fields. You can also change some fields as you copy, by naming them:

```python
from dataclasses import replace

mine = Book("111", "Dune", "Frank Herbert")
stored = replace(mine)           # a new Book with the same fields
stored.copies += 4
print(mine.copies, stored.copies)     # 1 5
print(replace(mine, copies=4))
# Book(isbn='111', title='Dune', author='Frank Herbert', copies=4)
```

So the library stores `replace(book)`, and owns its [[own record|shallow-replace]].

**Step 6: lookups that fail loudly.** `book(isbn)` returns the record, or raises `LibraryError("no such book: ...")` if there is none. `member(member_id)` does the same for members. Every later method can call these and trust the answer, instead of repeating `if isbn not in self.books` everywhere. Stopping with a clear message at the first sign of trouble is called [[failing fast|fail-fast]].

```python
lib.book("999")
# LibraryError: no such book: 999
```

**Step 7: a search.** `find_by_author(text)` finds books whose author *contains* some text, ignoring upper and lower case. The trick is to lowercase both sides before using `in`:

```python
"austen" in "JANE AUSTEN".lower()     # True
sorted(["Persuasion", "Emma"])        # ['Emma', 'Persuasion']
```

**Watch out:** keying things by name. Two members can both be called Sam, and titles get corrected. Ids do not change. With names as keys, the second Sam silently replaces the first, because assigning to an existing dict key overwrites it:

```python
members = {}
members["Sam"] = Member("m1", "Sam")
members["Sam"] = Member("m2", "Sam")    # the first Sam is gone
print(len(members))                     # 1
```

Programmers who study a domain talk to the people who work in it, learn their words, and use the same words as class and method names. When the code speaks the domain's language, the librarian and the programmer can read the rules together and spot a wrong one.

::: context one-door One door in
Making every change go through an object's methods is called **encapsulation**: the data is wrapped up, and the methods are the only door in. Python does not lock the door. Any code *could* write `lib.books["111"].copies = 0`. The convention is that it does not, and a good design gives it no reason to.

The payoff is that each rule is written in one place. If the library later decides that no book may have more than 50 copies, you change `add_book`, and every part of the program obeys the new rule at once.

::: context catching-one-kind Why one exception class helps
`except LibraryError` catches `LibraryError` and any subclass of it, and nothing else. So the caller can write one `except` that handles every "the library refused" case, whether the book was missing, the member was unknown or a rule was broken.

The alternative is worse in both directions. `except Exception` would also swallow real bugs and hide them. Catching `ValueError` would mix the library's refusals with errors from `int("abc")` and other unrelated code. Your own class draws a clear line around "failures that belong to this domain".
:::

::: context shallow-replace replace copies one level deep
`replace` makes a **shallow** copy, like `list(x)` in the aliasing lesson: a new `Book`, but each field still points at the same value as before. For a `Book` that is fine. Its fields are strings and an int, and those can never be changed in place, only replaced. So nothing is left to share by accident.

If a dataclass had a list field, say `tags`, the copy and the original would share that one list. Then you would need `copy.deepcopy`, which copies all the way down. Knowing which of your fields can change in place tells you which copy you need.
:::

::: context fail-fast Fail fast
**Failing fast** means stopping with a clear message at the first moment something is wrong, instead of carrying on with bad data. A missing book found in `book()` gives "no such book: 999" right there. A missing book discovered three functions later gives a confusing `KeyError` or `None` somewhere else, and you have to work backwards to find the cause.

Flight software follows the same idea through fault detection: a sensor reading that makes no sense is flagged at once and the system moves to a safe response, rather than letting the bad number travel on into the guidance calculations.
:::

# Library system, step 1: the data model.
from dataclasses import dataclass, replace


class LibraryError(Exception):
    pass


@dataclass
class Book:
    isbn: str
    title: str
    author: str
    copies: int = 1


@dataclass
class Member:
    member_id: str
    name: str


class Library:
    def __init__(self):
        self.books = {}
        self.members = {}

    def add_book(self, book):
        if book.copies < 1:
            raise LibraryError("a book needs at least one copy")
        if book.isbn in self.books:
            self.books[book.isbn].copies += book.copies
        else:
            self.books[book.isbn] = replace(book)
        return self.books[book.isbn]

    def add_member(self, member):
        if member.member_id in self.members:
            raise LibraryError(f"member {member.member_id} already exists")
        self.members[member.member_id] = member

    def book(self, isbn):
        if isbn not in self.books:
            raise LibraryError(f"no such book: {isbn}")
        return self.books[isbn]

    def member(self, member_id):
        if member_id not in self.members:
            raise LibraryError(f"no such member: {member_id}")
        return self.members[member_id]

    def find_by_author(self, text):
        text = text.lower()
        return sorted(b.title for b in self.books.values() if text in b.author.lower())

=== pyp-10 | Library system 2: loans and rules
--- teach
Last lesson built the library's data: `Book`, `Member`, and a `Library` that owns them and refuses bad changes with a `LibraryError`. But a library exists to *lend* books, and that is this lesson.

Lending comes with **[[rules|business-rules]]**. A member can borrow at most three books. A member cannot borrow the same book twice at once. Nobody can borrow a book when every copy is already out. Rules like these are the heart of most real software, and they deserve care. This lesson has five small ideas, one step each.

**Step 1: a loan is a record too.** A **loan** links one member to one book, with a **due date**: the day the book must come back.

```python
from dataclasses import dataclass
from datetime import date

@dataclass
class Loan:
    member_id: str
    isbn: str
    due: date
```

Notice what it stores: the member's **id** and the book's **ISBN**, not the `Member` and `Book` objects themselves. Ids never change. They are easy to save to a file, which is next lesson. And the book's title and copies live in exactly one place, the `Book` in `library.books`, so there is only one copy of them to keep up to date. When you need the full record, you [[look it up by its id|lookup-by-id]].

All the library's loans go in one list, `self.loans`, which starts empty.

**Step 2: derive, do not duplicate.** How many copies of a book are available to borrow right now? You could store a number, `available`, on each book, and remember to change it on every checkout and every return. Or you could **derive** it, which means work it out from data you already have:

```
available = copies - (number of loans of that ISBN)
```

In Python, counting the matching loans is a `sum` of one `1` for each match:

```python
sum(1 for loan in self.loans if loan.isbn == isbn)
```

The worked-out answer can never disagree with the loans, because it *is* the loans. A stored count can [[drift away from the truth|drift]] the first time someone forgets to update it. Keep a **single source of truth** wherever you can: each fact stored in one place only.

**Step 3: check every rule before changing anything.** `checkout(member_id, isbn, today)` has five things to check: the member exists, the book exists, the member does not already have this book, the member has fewer than three loans, and a copy is available. Only after all five pass does it add the loan.

The order matters. If the method added the loan first and checked afterwards, a failed check would leave a loan that should never have existed. When a method either does everything or [[changes nothing at all|all-or-nothing]], the data can never be left half-updated.

`any(...)` is handy for the "already has this book" check. It is `True` if at least one item is true:

```python
any(loan.isbn == isbn for loan in current)    # does any current loan have this ISBN?
```

**Step 4: time is an input.** The due date is 14 days after today. You could call `date.today()` inside `checkout`. But then a test like "does a loan made on 1 March fall due on 15 March?" could only be run on 1 March. So `checkout` takes `today` as an argument. That is the dependency injection idea from the expert course's design lesson: the method is *given* the date instead of reaching for the clock.

To add days to a date you need a **timedelta**: a length of time, such as "14 days". It lives in the same `datetime` module as `date`. A date plus a timedelta is a new date, and it [[knows about the calendar|calendar-aware]]:

```python
from datetime import date, timedelta

print(date(2026, 3, 1) + timedelta(days=14))     # 2026-03-15
print(date(2026, 12, 25) + timedelta(days=14))   # 2027-01-08
```

**Step 5: name your numbers.** `14` and `3` in the middle of a method say nothing about what they mean. **Named constants** at the top of the file do:

```python
LOAN_DAYS = 14
MAX_LOANS = 3
```

The capital letters are a convention that says "this never changes while the program runs". Each rule now has [[one place to change it|magic-numbers]]: if the library moves to three-week loans, you edit one line.

**Returning a book** is the checkout in reverse: find the loan with that member id and ISBN, take it out of the list, and give it back. `enumerate` gives you the position of each loan, and `self.loans.pop(i)` removes the item at position `i` and returns it. If no loan matches, that is a `LibraryError` too.

**Watch out:** returning `True` or `False` from `checkout` to mean "it worked" or "it was refused". The caller has to check the answer, and one day will forget, and then the program carries on as if a refused loan went through. A raised `LibraryError` [[cannot be ignored silently|silent-failure]], and its message says *why* it was refused.

::: context business-rules Where the rules come from
Programmers call rules like "at most three loans" **business rules**: they come from the people who run the library, not from Python. A different library might allow five loans, or none at all for members who owe fines.

That is why the rules deserve care. They change more often than anything else in the program, and getting one wrong costs real people something. Keeping them in named constants and a few clearly written methods means a librarian could read them with you and say "yes, that is our rule".
:::

::: context lookup-by-id Following an id to its record
A loan says `isbn="111"`. To show the title, the program follows that id: `library.books["111"].title`. Databases do the same thing on a large scale. A table of loans stores a book's id in each row, and that stored id is called a **foreign key**, because it is the key of a row in a *different* table.

The big advantage shows up when a record changes. If a title is corrected, it is corrected in one `Book`, and every loan that points at it sees the new title at once. Nothing has to be updated in the loans.
:::

::: context all-or-nothing Go or no-go before you commit
Before a rocket launch, the launch director polls every team: range, weather, propulsion, guidance. Each answers "go" or "no go". Only when every answer is "go" does the countdown continue. Nobody fuels half the rocket and then asks the weather team.

`checkout` works the same way: every check first, then one change. Databases have a name for an operation that either happens completely or not at all: a **transaction**. You will meet the word again whenever data is saved somewhere that must never be left half-written.
:::

::: context calendar-aware Dates handle the calendar for you
Adding 14 to the day number by hand would give "32 March", which does not exist. A `date` plus a `timedelta` rolls over into the next month, and the next year, and gets February right in leap years:

```python
from datetime import date, timedelta
print(date(2028, 2, 20) + timedelta(days=14))    # 2028-03-05
```

2028 is a leap year, so February has 29 days, and 14 days after 20 February is 5 March. Calendar arithmetic is full of traps like this, which is why engineers use the library instead of writing their own.
:::

::: context magic-numbers Magic numbers
A bare number in the middle of code, like `if len(current) >= 3`, is nicknamed a **magic number**: it works, but nobody can tell why it is 3, or whether the 3 in some other method is the same rule or a different one.

A named constant answers both questions. `MAX_LOANS` says what the number means, and every place that uses the rule uses the same name. Change it once, and the whole program follows.
:::

::: context silent-failure Refusals that cannot be missed
Some older languages, such as C, often report failure by returning a special value, like `-1`. Nothing forces the caller to look at it, and forgotten checks of this kind are a well-known source of bugs: the program carries on with a result that never happened.

An exception turns that around. If nobody catches a `LibraryError`, the program stops and prints it. The only way to ignore it is to write an `except` on purpose, and then you have at least decided to.
:::

# Library system, step 2: loans and rules.
from dataclasses import dataclass, replace
from datetime import date, timedelta

LOAN_DAYS = 14
MAX_LOANS = 3


class LibraryError(Exception):
    pass


@dataclass
class Book:
    isbn: str
    title: str
    author: str
    copies: int = 1


@dataclass
class Member:
    member_id: str
    name: str


@dataclass
class Loan:
    member_id: str
    isbn: str
    due: date


class Library:
    def __init__(self):
        self.books = {}
        self.members = {}
        self.loans = []

    def add_book(self, book):
        if book.copies < 1:
            raise LibraryError("a book needs at least one copy")
        if book.isbn in self.books:
            self.books[book.isbn].copies += book.copies
        else:
            self.books[book.isbn] = replace(book)
        return self.books[book.isbn]

    def add_member(self, member):
        if member.member_id in self.members:
            raise LibraryError(f"member {member.member_id} already exists")
        self.members[member.member_id] = member

    def book(self, isbn):
        if isbn not in self.books:
            raise LibraryError(f"no such book: {isbn}")
        return self.books[isbn]

    def member(self, member_id):
        if member_id not in self.members:
            raise LibraryError(f"no such member: {member_id}")
        return self.members[member_id]

    def find_by_author(self, text):
        text = text.lower()
        return sorted(b.title for b in self.books.values() if text in b.author.lower())

    def available(self, isbn):
        book = self.book(isbn)
        return book.copies - sum(1 for loan in self.loans if loan.isbn == isbn)

    def loans_of(self, member_id):
        self.member(member_id)
        return [loan for loan in self.loans if loan.member_id == member_id]

    def checkout(self, member_id, isbn, today):
        current = self.loans_of(member_id)
        self.book(isbn)
        if any(loan.isbn == isbn for loan in current):
            raise LibraryError(f"{member_id} already has {isbn}")
        if len(current) >= MAX_LOANS:
            raise LibraryError("loan limit reached")
        if self.available(isbn) < 1:
            raise LibraryError(f"no copies of {isbn} available")
        loan = Loan(member_id, isbn, today + timedelta(days=LOAN_DAYS))
        self.loans.append(loan)
        return loan

    def return_book(self, member_id, isbn):
        for i, loan in enumerate(self.loans):
            if loan.member_id == member_id and loan.isbn == isbn:
                return self.loans.pop(i)
        raise LibraryError(f"{member_id} has not borrowed {isbn}")

=== pyp-11 | Library system 3: saving and loading with JSON
--- teach
Last lesson the library learned to lend: loans with due dates, and rules checked before anything changes. But everything lives in the program's [[memory|memory-vs-disk]]. When the program stops, every book, member and loan is gone. A library that forgets everything overnight is not much use.

The data needs to be **persisted**: written down somewhere, as text in a file, and read back later. Think of the clerk copying every card into a notebook at closing time, and copying them back onto fresh cards in the morning. This lesson writes the notebook. It takes seven small steps.

**Step 1: meet JSON.** **[[JSON|json-history]]** is a way of writing data as plain text. It looks almost exactly like Python's dicts and lists, humans can read it, and nearly every programming language understands it. Python's `json` module turns data into JSON text and back:

```python
import json

text = json.dumps({"name": "Ada", "tags": ["x", "y"], "active": True})
print(text)          # {"name": "Ada", "tags": ["x", "y"], "active": true}

data = json.loads(text)
print(data["tags"])  # ['x', 'y']
```

`json.dumps` ("dump string") turns data into a string of JSON text. `json.loads` ("load string") reads JSON text and gives back dicts and lists. Notice one small change: Python's `True` is written `true` in JSON, and Python's `None` is written `null`.

**Step 2: what JSON can hold.** JSON only knows six kinds of thing: **dicts (with string keys), lists, strings, numbers, booleans and null**. A `Book` or a `date` is none of those. So anything else must be converted on the way out, and rebuilt on the way in:

| Python | Out (to JSON) | In (from JSON) |
|---|---|---|
| dataclass | `dataclasses.asdict(obj)` | `Book(**d)` |
| `date` | `d.isoformat()` gives `"2026-03-15"` | `date.fromisoformat(s)` |
| tuple, set | a list | rebuild if you need the type |

Here are the first two rows in action. `asdict` turns a dataclass into a dict of its fields. Going back, `Book(**d)` uses the double star from the `*args, **kwargs` lesson: it spreads the dict out into keyword arguments, so it means `Book(isbn="1", title="Dune", ...)`.

```python
from dataclasses import asdict

d = asdict(Book("1", "Dune", "Frank Herbert", 2))
print(d)          # {'isbn': '1', 'title': 'Dune', 'author': 'Frank Herbert', 'copies': 2}
print(Book(**d))  # Book(isbn='1', title='Dune', author='Frank Herbert', copies=2)
```

A date becomes text written [[year first|iso-dates]], and comes back as a real `date`:

```python
from datetime import date

print(date(2026, 3, 15).isoformat())           # 2026-03-15
print(repr(date.fromisoformat("2026-03-15")))  # datetime.date(2026, 3, 15)
```

**Step 3: design the file format on purpose.** Write down the shape of your save file, because other programs, and future versions of yours, will [[depend on it|format-promise]]. Here it is a dict of three lists:

```
{"books": [...], "members": [...], "loans": [...]}
```

Books and members are dicts of their fields. A loan is `{"member_id": ..., "isbn": ..., "due": "YYYY-MM-DD"}`, with its date as text.

**Step 4: make the output stable.** Two extra arguments to `json.dumps` make it write the same text for the same data, every time. `indent=2` puts each item on its own line, indented by two spaces. `sort_keys=True` writes the keys of every dict in A-to-Z order:

```python
print(json.dumps({"b": 2, "a": [1, 2]}, indent=2, sort_keys=True))
# {
#   "a": [
#     1,
#     2
#   ],
#   "b": 2
# }
```

Stable text is easy to read, and easy to [[compare with an older save|stable-diffs]].

**Step 5: build from the class.** Loading makes a brand-new library, so it cannot be an ordinary method: there is no library object yet to call it on. A **class method** is a method you call on the class itself. You write `@classmethod` above it, and its first parameter is the class, named **`cls`** by convention, instead of an object named `self`:

```python
class Library:
    @classmethod
    def from_json(cls, text):
        library = cls()      # the same as Library(): a new, empty library
        ...                  # fill it in
        return library

lib = Library.from_json(text)
```

A method like this, whose job is to build a new object from something, is called an **[[alternative constructor|cls-not-self]]**. You have already used one: `date.fromisoformat` builds a `date` from text.

Fill the new library in by calling `add_book` and `add_member` with rebuilt objects, so that loaded data passes through the same rules as everything else.

**Step 6: the round trip is the test.** The one property that matters most for saving and loading is this: load what you saved, and you get the same library back. `Library.from_json(lib.to_json())` must behave exactly like `lib`. Testing that [[there and back|round-trip]] catches almost every mistake at once.

**Step 7: do not trust the file.** Code that reads a file crosses a **[[trust boundary|trust-boundary]]**: the data comes from outside your program. A save file can be cut off halfway, edited by hand, or written by an older version. Each kind of damage raises a different error:

- broken text makes `json.loads` raise `json.JSONDecodeError`, which is a kind of `ValueError`;
- a missing key, like `data["books"]` in `{}`, raises `KeyError`;
- a wrong or missing field makes building the dataclass raise `TypeError`;
- a bad date, like `date.fromisoformat("someday")`, raises `ValueError`.

The caller should not have to know all of these. So catch them all, and raise one clear `LibraryError("corrupt save file: ...")`:

```python
try:
    data = json.loads(text)
    ...
except (ValueError, KeyError, TypeError) as err:
    raise LibraryError(f"corrupt save file: {err}") from err
```

A tuple of classes after `except` catches any of them. The words **`from err`** at the end [[keep the original error attached|raise-from]] as the cause, so if this ever shows up as a traceback, you still see what really went wrong inside.

**Watch out:** loading by putting the parsed dicts straight into `self.books`. Everything seems to work, until some code asks for `book.title` on what is really a dict, and gets `AttributeError: 'dict' object has no attribute 'title'`. Always rebuild real `Book`, `Member` and `Loan` objects when you load.

::: context memory-vs-disk Memory forgets, the disk remembers
A running program keeps its variables in the computer's **memory** (RAM). It is very fast, but it is cleared when the program ends or the power goes off. A **file** on a disk or SSD survives both, but it can only hold bytes, such as text.

So saving always means turning objects into text or bytes, and loading means turning them back. Spacecraft have the same split: fast working memory for the running software, and non-volatile storage for anything that must survive a reboot, such as logs and settings.
:::

::: context json-history Where JSON came from
JSON stands for **JavaScript Object Notation**. It grew out of the way the JavaScript language writes objects, and Douglas Crockford described it and gave it its name in the early 2000s. It is now an official standard.

It won because it is small: six kinds of value, a few pieces of punctuation, and nothing else. Web services send JSON to each other, programs keep their settings in it, and scientific and space tools use it too. Almost every language has a JSON reader built in or one install away.
:::

::: context iso-dates Why the year comes first
`2026-03-15` is the international standard way to write a date, from a standard called **ISO 8601**. Biggest unit first: year, then month, then day, each padded with zeros.

That order has a lovely property: sorting the text A to Z also sorts the dates from earliest to latest, because the most important part is compared first. `"2026-03-15" < "2026-11-02"` is `True`, and it is the right answer. It also avoids the confusion over whether `03/04` means 3 April or 4 March. Mission logs and spacecraft telemetry use this style for exactly those reasons.
:::

::: context format-promise A file format is a promise
Once you have saved files in some format, you have made a promise: files from today must still load next year. If a later version renames `"copies"` to `"count"`, every old save file breaks.

Real programs handle this by writing a version number into the file, such as `"version": 1`, and teaching the loader to read old versions too. You do not need that yet, but it is why the shape of the file deserves a moment's thought before the first save.
:::

::: context stable-diffs Comparing two saves
Engineers often keep data files in Git, which shows the lines that changed between two versions. If the keys came out in a different order every time, every save would look completely changed, even when only one book was added.

With `sort_keys=True` and `indent=2`, one new book adds a few lines and changes nothing else, so the difference between two saves shows exactly what really changed. Stable output also makes tests easy: two saves of the same data are the same string.
:::

::: context cls-not-self Why cls and not Library
Inside a class method, `cls` is whichever class the method was called on. Writing `cls()` instead of `Library()` matters when someone makes a subclass later. If `class BranchLibrary(Library)` inherits `from_json`, then `BranchLibrary.from_json(text)` builds a `BranchLibrary`, because `cls` is `BranchLibrary` in that call.

Alternative constructors are everywhere in Python's standard library: `date.fromisoformat`, `dict.fromkeys`, `int.from_bytes`. The name usually starts with "from", which is a good hint for yours.
:::

::: context round-trip There and back again
A **round trip** sends data out and brings it back, then checks nothing was lost on the way.

A second test goes the other way: save the new library again, and the text must match the first save exactly. Stable output from step 4 makes that possible.
:::

::: context trust-boundary Where trusted data ends
A **trust boundary** is any place where data enters your program from somewhere you do not control: a file, the keyboard, the network. Inside the boundary, your own methods made the data and it follows your rules. At the boundary, anything can arrive.

So the boundary is where you check. Spacecraft software does this with every command uplinked from the ground: before acting on one, it checks the message is complete and correctly formed, and it rejects anything else. A save file deserves the same suspicion.
:::

::: context raise-from What "from err" keeps
`raise NewError(...) from err` stores the old error on the new one, as its `__cause__`. If the new error is never caught, Python prints both tracebacks, joined by the line "The above exception was the direct cause of the following exception:".

```python
try:
    Library.from_json("{}")
except LibraryError as e:
    print(e)                # corrupt save file: 'books'
    print(repr(e.__cause__))  # KeyError('books')
```

So the caller gets one simple error to catch, and whoever is debugging still sees the real reason underneath.
:::

# Library system, step 3: saving and loading.
import json
from dataclasses import asdict, dataclass, replace
from datetime import date, timedelta

MAX_LOANS = 3

    pass


@dataclass
class Book:
    isbn: str
    title: str
    author: str
    copies: int = 1


@dataclass
class Member:
    member_id: str
    name: str


@dataclass

    member_id: str
    isbn: str

        self.books = {}
        self.members = {}
        self.loans = []

        if book.copies < 1:
            raise LibraryError("a book needs at least one copy")
        if book.isbn in self.books:
            self.books[book.isbn].copies += book.copies
        else:
            self.books[book.isbn] = replace(book)
        return self.books[book.isbn]

    def add_member(self, member):

            raise LibraryError(f"member {member.member_id} already exists")
        self.members[member.member_id] = member

    def book(self, isbn):
        if isbn not in self.books:
            raise LibraryError(f"no such book: {isbn}")
        return self.books[isbn]

    def member(self, member_id):
        if member_id not in self.members:
            raise LibraryError(f"no such member: {member_id}")
        return self.members[member_id]

    def find_by_author(self, text):
        text = text.lower()
        return sorted(b.title for b in self.books.values() if text in b.author.lower())

    def available(self, isbn):

        return [loan for loan in self.loans if loan.member_id == member_id]

    def checkout(self, member_id, isbn, today):
        current = self.loans_of(member_id)
        self.book(isbn)
        if any(loan.isbn == isbn for loan in current):
            raise LibraryError(f"{member_id} already has {isbn}")
        if len(current) >= MAX_LOANS:
            raise LibraryError("loan limit reached")
        if self.available(isbn) < 1:
            raise LibraryError(f"no copies of {isbn} available")
        loan = Loan(member_id, isbn, today + timedelta(days=LOAN_DAYS))
        self.loans.append(loan)
        return loan

    def return_book(self, member_id, isbn):
        for i, loan in enumerate(self.loans):
            if loan.member_id == member_id and loan.isbn == isbn:
                return self.loans.pop(i)
        raise LibraryError(f"{member_id} has not borrowed {isbn}")

    def to_json(self):
        data = {
            "books": [asdict(b) for b in self.books.values()],
            "members": [asdict(m) for m in self.members.values()],
            "loans": [{"member_id": l.member_id, "isbn": l.isbn, "due": l.due.isoformat()} for l in self.loans],
        }
        return json.dumps(data, indent=2, sort_keys=True)

    @classmethod
    def from_json(cls, text):
        try:
            data = json.loads(text)
            library = cls()
            for b in data["books"]:
                library.add_book(Book(**b))
            for m in data["members"]:
                library.add_member(Member(**m))
            for l in data["loans"]:
                library.loans.append(Loan(l["member_id"], l["isbn"], date.fromisoformat(l["due"])))
        except (ValueError, KeyError, TypeError) as err:
            raise LibraryError(f"corrupt save file: {err}") from err
        return library

=== pyp-12 | Library system 4: overdue loans and fines
--- teach
Last lesson the library learned to save itself as JSON and load itself back, and to refuse a damaged save file with one clear `LibraryError`. This last lesson adds what a librarian needs every morning: which books are overdue, what each member owes, and which books are due back soon. All three are built on one question about dates, so that comes first.

**Step 1: subtracting dates.** In lesson 2 you added a `timedelta` to a date to get a new date. It works the other way too: one date minus another gives a `timedelta`, the length of time between them. Its **`.days`** is that length as a whole number of days. If the second date is later than the first, `.days` is negative:

```python
from datetime import date

print((date(2026, 3, 20) - date(2026, 3, 15)).days)    # 5    five days late
print((date(2026, 3, 10) - date(2026, 3, 15)).days)    # -5   not due yet
```

Read `today - loan.due` as "how far past the due date is today?".

**Step 2: late days are never negative.** A loan that is not due yet is not "minus five days late"; it is just not late. And a book returned *on* its due date is not late either, because the difference is 0. Only positive differences count. `max(0, days)` says "the late days, but never below zero" in one step, because `max` picks the bigger of the two:

```python
max(0, 5)      # 5
max(0, -5)     # 0
```

**Step 3: one helper, used everywhere.** "How many days late is this loan?" is needed by the overdue list *and* by the fine. Write it once, as a method `days_late(loan, today)`, and call it from both. Then the two features are guaranteed to agree. Two slightly different copies of the same calculation, one with `>` and one with `>=`, is exactly how an [[off-by-one|off-by-one]] disagreement creeps in.

**Step 4: the overdue report, sorted on purpose.** `overdue(today)` gives one tuple per late loan: `(member name, book title, days late)`. The loan only stores ids, so you look the names up, as you learned in lesson 2: `self.members[loan.member_id].name` and `self.books[loan.isbn].title`.

A report is most useful with the worst cases first. Then, when two loans are equally late, by name, then by title, so that the same data [[always gives the same order|tie-breaks]]. That is the sort key trick from the sorting lesson: a tuple key, with a minus sign on the number you want largest-first:

```python
rows = [("Bo", "Emma", 1), ("Ada", "Dune", 5), ("Bo", "Ulysses", 5)]
print(sorted(rows, key=lambda r: (-r[2], r[0], r[1])))
# [('Ada', 'Dune', 5), ('Bo', 'Ulysses', 5), ('Bo', 'Emma', 1)]
```

`r[2]` is the days late, `r[0]` the name, `r[1]` the title. Ada and Bo are both 5 days late, so the name breaks the tie.

**Step 5: fines in [[cents|cents-again]], again.** The fine is 20 cents for each day each book is late. Store it as a constant, `FINE_PER_DAY = 20`, and keep the total as a whole number of cents, like the expense tracker did. Turning cents into "$1.40" is the interface's job, not the library's.

A worked example: Ada has two books. One was due on 15 March and the other on 18 March. On 20 March the first is 5 days late and the second 2 days late. That is 5 + 2 = 7 late days, and 7 × 20 = 140 cents. `fine` is the sum of `days_late(loan, today) * FINE_PER_DAY` over the member's loans, and `loans_of` already raises for an unknown member.

**Step 6: due soon.** `due_soon(today, within=3)` lists the books that come back in the next few days, so the library can send reminders. Here you want the *opposite* subtraction, `loan.due - today`: how many days until the due date. A loan counts if that number is from 0 (due today) up to `within`, [[both ends included|inclusive-window]]. Python can write that as one chained comparison:

```python
0 <= (loan.due - today).days <= within
```

Sort the matching loans soonest first, by the tuple `(loan.due, title)`, and return just the titles. Dates compare the way you would hope: an earlier date is smaller.

**Step 7: today stays an argument.** Every one of these methods depends on the date, and every one takes `today`. That is why testing them is easy: you can check "three days after the due date, the fine is 60" without [[waiting three days|fast-forward]].

**Watch out:** the direction of the subtraction. `today - loan.due` is positive when a loan is *late*; `loan.due - today` is positive when it is *not due yet*. Swap them and every late book looks early. When unsure, try one date you can check in your head.

With this lesson the library system is complete: a domain model with rules, saving and loading with a stable file format and a check on the way in, and reports that depend on time. And every part of it was tested without touching a real disk or a real clock.

::: context tie-breaks Why ties need a rule
If you sorted only by days late, two loans that are both 5 days late could come out in either order, depending on the order the loans happen to be in the list. Run the report twice and the lines might swap.

Adding the name and then the title as tie-breakers means every possible pair has a fixed order. The same data always prints the same report, which makes it easy to test, easy to compare with yesterday's, and less confusing for the person reading it.
:::

::: context cents-again Why money stays in whole cents
The expense tracker stored money as whole cents because decimal fractions are not stored exactly as floats: `0.1 + 0.2` gives `0.30000000000000004`, not `0.3`. Add up thousands of fines as floats and the total can end up a fraction of a cent off.

Whole numbers of cents are always exact, and `140` cents can be shown as "$1.40" at the very last moment, when it is printed. It is the same idea as keeping one unit throughout a calculation, which spacecraft engineers learned the hard way when a mix-up between pound-seconds and newton-seconds helped cause the loss of the Mars Climate Orbiter in 1999.
:::

# Library system, step 4: overdue loans and fines.
import json
from dataclasses import asdict, dataclass, replace
from datetime import date, timedelta

LOAN_DAYS = 14
MAX_LOANS = 3
FINE_PER_DAY = 20  # cents


class LibraryError(Exception):
    pass


@dataclass
class Book:
    isbn: str
    title: str
    author: str
    copies: int = 1


@dataclass
class Member:
    member_id: str
    name: str


@dataclass
class Loan:
    member_id: str
    isbn: str
    due: date


class Library:
    def __init__(self):
        self.books = {}
        self.members = {}
        self.loans = []

    def add_book(self, book):
        if book.copies < 1:
            raise LibraryError("a book needs at least one copy")
        if book.isbn in self.books:
            self.books[book.isbn].copies += book.copies
        else:
            self.books[book.isbn] = replace(book)
        return self.books[book.isbn]

    def add_member(self, member):
        if member.member_id in self.members:
            raise LibraryError(f"member {member.member_id} already exists")
        self.members[member.member_id] = member

    def book(self, isbn):
        if isbn not in self.books:
            raise LibraryError(f"no such book: {isbn}")
        return self.books[isbn]

    def member(self, member_id):
        if member_id not in self.members:
            raise LibraryError(f"no such member: {member_id}")
        return self.members[member_id]

    def find_by_author(self, text):
        text = text.lower()
        return sorted(b.title for b in self.books.values() if text in b.author.lower())

    def available(self, isbn):
        book = self.book(isbn)
        return book.copies - sum(1 for loan in self.loans if loan.isbn == isbn)

    def loans_of(self, member_id):
        self.member(member_id)
        return [loan for loan in self.loans if loan.member_id == member_id]

    def checkout(self, member_id, isbn, today):
        current = self.loans_of(member_id)
        self.book(isbn)
        if any(loan.isbn == isbn for loan in current):
            raise LibraryError(f"{member_id} already has {isbn}")
        if len(current) >= MAX_LOANS:
            raise LibraryError("loan limit reached")
        if self.available(isbn) < 1:
            raise LibraryError(f"no copies of {isbn} available")
        loan = Loan(member_id, isbn, today + timedelta(days=LOAN_DAYS))
        self.loans.append(loan)
        return loan

    def return_book(self, member_id, isbn):
        for i, loan in enumerate(self.loans):
            if loan.member_id == member_id and loan.isbn == isbn:
                return self.loans.pop(i)
        raise LibraryError(f"{member_id} has not borrowed {isbn}")

    def to_json(self):
        data = {
            "books": [asdict(b) for b in self.books.values()],
            "members": [asdict(m) for m in self.members.values()],
            "loans": [{"member_id": l.member_id, "isbn": l.isbn, "due": l.due.isoformat()} for l in self.loans],
        }
        return json.dumps(data, indent=2, sort_keys=True)

    @classmethod
    def from_json(cls, text):
        try:
            data = json.loads(text)
            library = cls()
            for b in data["books"]:
                library.add_book(Book(**b))
            for m in data["members"]:
                library.add_member(Member(**m))
            for l in data["loans"]:
                library.loans.append(Loan(l["member_id"], l["isbn"], date.fromisoformat(l["due"])))
        except (ValueError, KeyError, TypeError) as err:
            raise LibraryError(f"corrupt save file: {err}") from err
        return library

    def days_late(self, loan, today):
        return max(0, (today - loan.due).days)

    def overdue(self, today):
        rows = [
            (self.members[l.member_id].name, self.books[l.isbn].title, self.days_late(l, today))
            for l in self.loans
            if self.days_late(l, today) > 0
        ]
        return sorted(rows, key=lambda r: (-r[2], r[0], r[1]))

    def fine(self, member_id, today):
        return sum(self.days_late(l, today) * FINE_PER_DAY for l in self.loans_of(member_id))

    def due_soon(self, today, within=3):
        soon = [l for l in self.loans if 0 <= (l.due - today).days <= within]
        return [self.books[l.isbn].title for l in sorted(soon, key=lambda l: (l.due, self.books[l.isbn].title))]

=== pyp-13 | Capstone: a to-do manager with undo
--- teach
The library system is finished. For twelve lessons, every step was laid out for you, and the code in the editor was always your program from the lesson before. That changes now.

The last four lessons are **capstones**: projects that show you can build something on your own. For each one you get a [[specification|spec-reading]] and an empty file. There are no step-by-step instructions, and the checks test only what your program *does*, never how it is built inside. So the design is yours.

This first capstone is a to-do list with an **undo** button.

### How to approach a specification

Think of a builder handed a drawing of a finished house. The drawing says what the house must look like. It does not say which wall to build first. That part is the builder's job, and here it is yours. Five steps help.

**1. Read it twice, then write every behaviour as a one-line example.** A **behaviour** is one thing the program must do in one situation. Writing them down turns a paragraph of rules into a checklist you can tick off:

```
add("buy milk")                    returns 1
add("   ")                         raises ValueError
undo() with nothing to undo        returns False
```

**2. Choose the data model first.** The **data model** is what you store, and in what shape. Most of the difficulty of a program is [[decided right here|tables-first]]. For this to-do list, one good shape is a dict from each id to a small record, plus one counter holding the next id to hand out:

```python
items = {
    1: {"title": "pay rent", "priority": "high", "tags": {"home"}, "done": False},
    2: {"title": "email Sam", "priority": "normal", "tags": set(), "done": True},
}
next_id = 3
```

**3. Build a skeleton.** A **skeleton** is the class with every method written down but doing nothing yet: each body is `pass`. It already runs, so you can try it at once. Then make one behaviour work at a time, and try each one as you go.

```python
class TodoList:
    def __init__(self):
        pass

    def add(self, title, priority="normal", tags=()):
        pass
```

**4. Hunt for [[edge cases|edge-case]].** An edge case is an unusual input at the very edge of what is allowed: an empty title, an id that does not exist, marking something done twice, undoing when there is nothing left to undo. Bugs like to live there.

**5. [[Refactor|refactor]] once it works.** Refactoring means changing how the code is written without changing what it does: clearer names, repeated code moved into one small helper.

### Sorting the pending list

`pending()` must list the most important items first, and the oldest first among items of the same priority. You met this in the expense tracker's report: sort with a **tuple key**, and Python compares the first parts, then uses the second parts to break ties. Priorities are words, so turn each word into a rank number first:

```python
rank = {"high": 0, "normal": 1, "low": 2}
sorted([(rank["low"], 1), (rank["high"], 2)])     # [(0, 2), (2, 1)]
```

Ids count up, so a smaller id means an older item. A key of (rank, id) gives exactly the order the spec asks for.

### What undo has to remember

Undo means "put things back the way they were before my last change". Press it again and it goes back one more step. So the program must remember a whole history, newest last, and each undo takes the newest step off the end.

A list used this way (add to the end, take from the end) is a [[stack|undo-stack]], which you met in the typing lesson of the expert course. `append` pushes a step on; `pop()` takes the last one back off.

### Two ways to build undo

There are two classic designs for what goes on that stack.

**Snapshots.** Picture photographing a whiteboard before every change. To undo, you wipe the board and copy the last photo back onto it. In code: before every change, push a copy of the whole state; `undo()` pops the last copy and makes it the state again. It is simple and hard to get wrong. It costs memory, but a to-do list is tiny, so that does not matter here.

**Commands.** Picture a notebook where you write down each change instead: "added item 3", "marked item 1 done". To undo, you read the last line and do the opposite. In code, each change is recorded as a [[small object that knows how to reverse itself|command-pattern]]: an `add` is undone by removing the item, a `remove` by putting the item back. It uses less memory, and it needs more code.

Either is a good answer. Choose one on purpose, before you start typing.

### A snapshot must be a deep copy

If you choose snapshots, the copy has to be **deep**. The advanced course's aliasing lesson showed why. `dict(items)` makes a new outer dict, but the records inside it are the *same* objects as before. Change a record, and the "saved" one changes with it:

```python
import copy

items = {1: {"title": "a", "done": False}}
saved = dict(items)               # shallow copy: shares the inner record
items[1]["done"] = True
saved[1]["done"]                  # True: the saved copy changed too!

items = {1: {"title": "a", "done": False}}
saved = copy.deepcopy(items)      # deep copy: copies the records too
items[1]["done"] = True
saved[1]["done"]                  # False: the snapshot is safe
```

`copy.deepcopy` copies [[all the way down|deep-vs-shallow]], so nothing is shared.

### What undo must not touch

Not everything goes back. The spec says [[ids are never reused|ids-forever]], even after undoing an `add`. So keep the id counter *outside* the snapshots. Undoing an `add` removes the item, but the counter keeps counting: add "a" (id 1), add "b" (id 2), undo, add "c", and "c" gets id 3.

And only changes that really happened can be undone. An operation that raised an error changed nothing, so it must leave nothing in the history.

**Watch out:** saving the snapshot *before* checking the input. If `done(99)` pushes a snapshot and only then raises `KeyError`, the history now holds a step that changed nothing. The next `undo()` quietly "undoes" that empty step and returns `True`, and the change the user really wanted to undo is still there. Check everything first. Save the snapshot last, right before you change anything.

::: context ids-forever Why an id is never handed out twice
An id is a promise: "this number means this item". Other things may hold on to it: a reminder that says "item 2", a message, a line in a log. If item 2 is removed and a new item later gets id 2, all those old references now point at the wrong thing, and nothing warns you. So many systems never reuse an id, even when the item is gone. Many databases hand out ids from a counter that only ever goes up, for exactly this reason.

--- task
Build a class `TodoList` to this specification. How you store things inside it is up to you.

- `add(title, priority="normal", tags=())` adds an item and returns its id: 1, 2, 3, … Ids are never reused, even after `remove` or `undo`. The title is stripped; an empty title raises `ValueError`. `priority` must be `"low"`, `"normal"` or `"high"`, otherwise `ValueError`.
- `done(item_id)` marks an item done; `remove(item_id)` deletes it. An unknown id raises `KeyError`.
- `pending(tag=None)` returns the titles of items not done, `high` first, then `normal`, then `low`, and oldest first within the same priority. With a tag, only items that have that tag.
- `search(text)` returns the ids (ascending) of all items, done or not, whose title contains `text`, ignoring case.
- `undo()` reverses the most recent `add`, `done` or `remove` that has not been undone yet, and returns `True`; with nothing left to undo, it returns `False`. Failed operations (those that raised) are not undoable.
- `summary()` returns `"<n> pending, <m> done"`.
--- starter
# Capstone: design and build TodoList to the specification in the task.
--- solution
import copy

PRIORITIES = {"high": 0, "normal": 1, "low": 2}


class TodoList:
    def __init__(self):
        self._items = {}
        self._next_id = 1
        self._history = []

    def _snapshot(self):
        self._history.append(copy.deepcopy(self._items))

    def _get(self, item_id):
        if item_id not in self._items:
            raise KeyError(item_id)
        return self._items[item_id]

    def add(self, title, priority="normal", tags=()):
        title = title.strip()
        if not title:
            raise ValueError("title must not be empty")
        if priority not in PRIORITIES:
            raise ValueError(f"unknown priority: {priority}")
        self._snapshot()
        item_id = self._next_id
        self._next_id += 1
        self._items[item_id] = {"title": title, "priority": priority, "tags": set(tags), "done": False}
        return item_id

    def done(self, item_id):
        self._get(item_id)
        self._snapshot()
        self._items[item_id]["done"] = True

    def remove(self, item_id):
        self._get(item_id)
        self._snapshot()
        del self._items[item_id]

    def undo(self):
        if not self._history:
            return False
        self._items = self._history.pop()
        return True

    def pending(self, tag=None):
        rows = [
            (PRIORITIES[item["priority"]], item_id, item["title"])
            for item_id, item in self._items.items()
            if not item["done"] and (tag is None or tag in item["tags"])
        ]
        return [title for _, _, title in sorted(rows)]

    def search(self, text):
        text = text.lower()
        return sorted(item_id for item_id, item in self._items.items() if text in item["title"].lower())

    def summary(self):
        done = sum(1 for item in self._items.values() if item["done"])
        return f"{len(self._items) - done} pending, {done} done"

=== pyp-14 | Capstone: a calculator language with variables
--- teach
The to-do list stored things and changed them. This capstone goes back to the calculator you built at the end of the expert course, and grows it into a tiny programming language.

Remember the pieces. The tokenizer lesson cut text like `2 * (3 + 4)` into tokens. The parser lessons turned those tokens into a value by **recursive descent**: one method per grammar rule, each calling the next one down.

A calculator forgets everything after each answer. A language remembers. You will write an **[[interpreter|interpreter]]**: a program that reads lines one at a time, carries each one out, and keeps what it has learned for the next line. Here is a session with it (`>` marks what the user typed; the line under it is the reply):

```
> let rate = 1.5
rate = 1.5
> let hours = 8
hours = 8
> rate * hours
12
> max(rate, 2) ^ 2
4
> y + 1
error: unknown variable y
```

It has **variables** (names that hold values), **functions** like `max`, its own power operator `^`, and error messages instead of crashes. And it is designed by you, from the spec in the task.

### Same pipeline, new pieces

The expert course's plan still works: **tokenize, then parse and evaluate**, with one grammar rule for each level of precedence. Your parser can still work out each value as it goes, so parsing and evaluating happen together. [[Reuse the plan, not only the code|pipeline]]: each new feature slots into one stage of it.

### A new kind of token: names

A **name** is a word like `rate` or `total_2`. The spec's rule is the one Python uses for [[its own names|identifiers]]: a letter or an underscore first, then any number of letters, digits or underscores. So `total_2` is a name. `2total` is not: it is the number `2` followed by the name `total`, two tokens in a row, which is a syntax error.

As a regular expression, that rule is `[A-Za-z_]\w*`. Piece by piece: `[A-Za-z_]` is one letter or underscore; `\w` is one "word character", meaning a letter, a digit or an underscore; and `*` means zero or more of them.

```python
import re
re.match(r"[A-Za-z_]\w*", "total_2 * 2").group()     # 'total_2'
```

You can also grow the `while` loop from your tokenizer instead, the same way it collects the digits of a number.

### Tokens that say what kind they are

In the expert course a token was either a number or a string like `"+"`. Now a string might be an operator or a name, and the parser has to tell `"max"` from `"("` at a glance. A clean fix is to [[tag every token with its kind|tagged-tokens]]: make each token a pair of (kind, value).

```python
[("name", "rate"), ("op", "*"), ("num", 2)]      # the tokens of: rate * 2
```

The parser then asks "is the kind `"name"`?" instead of guessing from the value. The comma between function arguments is one more operator token: `,`.

### The grammar grows

Here is the grammar from the calculator lesson, with `**` replaced by `^`, a bigger `atom` and one new rule, `args`:

```
expr   := term   (("+" | "-") term)*
term   := unary  (("*" | "/") unary)*
unary  := "-" unary  |  power
power  := atom   ("^" unary)?
atom   := NUMBER  |  NAME "(" args ")"  |  NAME  |  "(" expr ")"
args   := expr  ("," expr)*
```

Only `atom` and `args` are new. In words:

- An atom that starts with a NAME is a **function call** if the next token is `(`, and a **variable** otherwise. Take the name, then peek at the next token to find out which.
- A call's `args` are one expression, then any number of "comma, expression". So `max(1, 7, 3)` has three arguments. `max()` has none, which this rule does not allow, so it is a syntax error.
- A variable is looked up in the interpreter's dict of variables. A name that is not in the dict is the error `unknown variable NAME`.

Everything above `atom` works as before. `^` groups from the right, so `2 ^ 3 ^ 2` is `2 ^ 9 = 512`. Unary minus is looser than `^`, so `-2 ^ 2` is `-(2 ^ 2) = -4`. And the right side of `^` goes through `unary`, so `2 ^ -1` is `0.5`.

### Calling a Python function from your language

Keep the functions in a dict from each name to the real Python function:

```python
import math
FUNCTIONS = {"sqrt": math.sqrt, "abs": abs, "min": min, "max": max}
```

Your parser collects a call's arguments into a list. A `*` in front of a list, inside a call, [[spreads the list out|star-unpack]] into separate arguments:

```python
args = [1, 7, 3]
FUNCTIONS["max"](*args)      # the same as max(1, 7, 3): 7
```

`sqrt` and `abs` take exactly one argument, so check how many you got before calling them. A name that is not in the dict is an unknown function.

### let is a statement

An **expression** is something that has a value, like `rate * 2`. A **statement** is an instruction that does something, like "store this value under this name". `let x = ...` is a [[statement|statement-expression]], so it is not part of the expression grammar at all. Recognise it first, before any parsing, with a regular expression:

```python
LET = re.compile(r"^let\s+([A-Za-z_]\w*)\s*=(.*)$")
LET.match("let rate = 1.5").groups()      # ('rate', ' 1.5')
LET.match("let 5 = 3")                    # None: 5 is not a name
```

Read the pattern left to right: `^let` means the line starts with `let`; `\s+` is one or more spaces; group 1 is a name; `\s*=` is any spaces and then an equals sign; group 2, `(.*)`, is everything after that. Group 2 is an ordinary expression, so hand it to your expression parser. A line that does not match is an expression line.

Two more rules from the spec. `let` cannot assign to a function name, so `let sqrt = 4` is an error. And the order matters: **evaluate first, store second.** If the right side fails, you never reach the store, and the old value survives. That is what "a failed `let` leaves the variable unchanged" asks for.

### State that lasts between lines

The variables live in the `Interpreter` object, in a dict such as `self.variables`, so they are still there on the next call to `execute`. Each line gets a fresh parser, handed that same dict to read from.

### Errors are part of the design

An interactive calculator must answer every line, even nonsense. That takes two parts:

1. **Your own exception class**, such as `class CalcError(Exception)`. Raise it for every deliberate error, with the exact messages the spec asks for, like `unknown variable y` and `division by zero`. Because the class is yours, a real bug (say a `NameError` from a typo in your code) cannot be mistaken for one of these.
2. **One place that catches it**: `execute`. It wraps all the work in `try`, and turns the error into the reply `f"error: {err}"`. This is the [[error boundary|error-boundary]] from the expense tracker again.

Check for division by zero yourself, in `term`, before you divide. Then the message is exactly `division by zero`. (Python's own message is different for floats: `1.0 / 0` says `float division by zero`.)

Python's maths can also raise errors of its own, and `execute` must turn those into replies too:

```python
math.sqrt(-1)       # ValueError: math domain error
2.0 ** 10000        # OverflowError: too big for a float
0 ** -1             # ZeroDivisionError
```

### Showing the answer

In Python, `7 / 2` is `3.5` and `6 / 2` is `3.0`. The spec wants `"3"`, not `"3.0"`: a float with a [[whole-number value|whole-floats]] prints without `.0`. A float can tell you whether it is whole:

```python
(3.0).is_integer()     # True
(3.5).is_integer()     # False
str(int(3.0))          # '3'
```

Ints already print without `.0`, so only floats need the check. Write it once, as a small helper that every reply goes through.

**Watch out:** do not compute `^` with Python's `^`. In Python, `^` [[means something else entirely|caret-xor]]: `2 ^ 3` is `1`, not `8`. Your language spells power `^`, but your code must compute it with `**`.

Plan the grammar on paper before you write code. Getting the grammar right is most of the work.

::: context identifiers The rules for names
Python's rule for a name is the one this language uses: start with a letter or underscore, then letters, digits or underscores. Names are **case-sensitive**, so `rate`, `Rate` and `RATE` are three different names. Most languages add one more rule: some words are **reserved** and cannot be names. In Python you cannot call a variable `if` or `for`. In this language, `let` plays that part, and so do the function names, which the spec forbids as `let` targets.
:::

::: context tagged-tokens Every token carries a label
Tagging tokens is how real tokenizers work. Python's own `tokenize` module labels each piece of `rate * 2` with a type: `NAME` for `rate`, `OP` for `*`, `NUMBER` for `2`. The label lets the parser decide what to do from the kind alone, and the value is there when it needs the details. It also means `("op", "(")` can never be confused with a name, whatever characters a name might one day be allowed to contain.
:::

::: context star-unpack The star in a call
You met `*args` in a function *definition*, where it gathers extra arguments into a tuple. In a function *call*, the star does the opposite: it spreads a list or tuple out into separate arguments. So `max(*[1, 7, 3])` is exactly `max(1, 7, 3)`. That is how your language can pass any number of arguments to `min` and `max` without knowing in advance how many there will be. A double star, `**`, does the same for a dict of keyword arguments.
:::

::: context statement-expression Statements and expressions
In Python, `x = 3` is a statement: it does something and has no value, so `y = (x = 3)` is a syntax error. Python 3.8 added the "walrus" operator, `:=`, which is an assignment that is also an expression. The keyword `let` comes from BASIC, where assignments were written `LET X = 5`. Starting the line with a keyword makes a statement easy to spot before any parsing happens, which is exactly why your interpreter can check for it first.
:::

::: context error-boundary One place turns errors into replies
Deep inside the parser, `atom` finds an unknown variable and raises. It does not know who is typing or how to show a message, and it should not. The error travels up through `power`, `unary`, `term` and `expr` untouched, until `execute` catches it and turns it into a reply. One catch, at the top, instead of error handling scattered through every method. The expense tracker's run loop was built the same way.
:::

::: context whole-floats Why 3.0 and 3 look different
Python keeps `int` and `float` as different types, even when they hold the same value: `6 / 2` is the float `3.0`, while `2 + 1` is the int `3`. A float stores every whole number exactly up to 9,007,199,254,740,992, which is 2 to the power 53, so `is_integer()` gives a reliable answer for the numbers a calculator meets. Showing `3` for both keeps the replies tidy, the way a pocket calculator shows `3`, not `3.0`.
:::

In Python, `^` is **exclusive or** (XOR), which works on the bits of whole numbers: each bit of the answer is 1 when the two bits differ. 2 is 010 in binary and 3 is 011, so `2 ^ 3` is 001, which is 1.

Build a class `Interpreter` with a method `execute(line)` that returns a string. The design inside is up to you.

- `let NAME = EXPR` evaluates `EXPR`, stores it in variable `NAME`, and returns `"NAME = VALUE"`. Otherwise, the line is an expression and the reply is its value.
- Expressions: numbers (`3`, `2.5`), variables, `+ - * /` with the usual precedence (left to right), `^` for power (right-associative, binding tighter than unary minus: `-2 ^ 2` is `-4`, `2 ^ -1` is `0.5`), unary minus, brackets, and the functions `sqrt(x)`, `abs(x)`, `min(a, b, ...)` and `max(a, b, ...)`.

- Errors never raise: they return a string starting with `"error: "`. Exactly `"error: unknown variable NAME"` for an undefined variable and `"error: division by zero"` for dividing by zero. # Capstone: design and build Interpreter to the specification in the task.
--- solution
import math
import re

TOKEN = re.compile(r"\s*(?:(\d+\.\d*|\.\d+|\d+)|([A-Za-z_]\w*)|(\S))")
FUNCTIONS = {"sqrt": math.sqrt, "abs": abs, "min": min, "max": max}


class CalcError(Exception):
    pass


def tokenize(text):
    tokens = []
    pos = 0
    text = text.rstrip()
    while pos < len(text):
        m = TOKEN.match(text, pos)
        number, name, op = m.groups()
        if number:
            tokens.append(("num", float(number) if "." in number else int(number)))
        elif name:
            tokens.append(("name", name))
        elif op in "+-*/^(),":
            tokens.append(("op", op))
        else:
            raise CalcError(f"unexpected character {op!r}")
        pos = m.end()
    return tokens


class Parser:
    def __init__(self, tokens, variables):
        self.tokens = tokens
        self.pos = 0
        self.variables = variables

    def peek(self):
        return self.tokens[self.pos] if self.pos < len(self.tokens) else (None, None)

    def take(self):
        token = self.peek()
        self.pos += 1
        return token

    def expect(self, op):
        if self.take() != ("op", op):
            raise CalcError(f"expected {op}")

    def parse(self):
        value = self.expr()
        if self.pos != len(self.tokens):
            raise CalcError("syntax error")
        return value

    def expr(self):
        value = self.term()
        while self.peek() in (("op", "+"), ("op", "-")):
            op = self.take()[1]
            right = self.term()
            value = value + right if op == "+" else value - right
        return value

    def term(self):
        value = self.unary()
        while self.peek() in (("op", "*"), ("op", "/")):
            op = self.take()[1]
            right = self.unary()
            if op == "/":
                if right == 0:
                    raise CalcError("division by zero")
                value = value / right
            else:
                value = value * right
        return value

    def unary(self):
        if self.peek() == ("op", "-"):
            self.take()
            return -self.unary()
        return self.power()

    def power(self):
        base = self.atom()
        if self.peek() == ("op", "^"):
            self.take()
            return base ** self.unary()
        return base

    def atom(self):
        kind, value = self.take()
        if kind == "num":
            return value
        if kind == "name":
            if self.peek() == ("op", "("):
                return self.call(value)
            if value not in self.variables:
                raise CalcError(f"unknown variable {value}")
            return self.variables[value]
        if (kind, value) == ("op", "("):
            result = self.expr()
            self.expect(")")
            return result
        raise CalcError("syntax error")

    def call(self, name):
        if name not in FUNCTIONS:
            raise CalcError(f"unknown function {name}")
        self.expect("(")
        args = [self.expr()]
        while self.peek() == ("op", ","):
            self.take()
            args.append(self.expr())
        self.expect(")")
        if name in ("sqrt", "abs") and len(args) != 1:
            raise CalcError(f"{name} takes one argument")
        if name == "sqrt" and args[0] < 0:
            raise CalcError("square root of a negative number")
        return FUNCTIONS[name](*args)


def show(value):
    if isinstance(value, float) and value.is_integer():
        return str(int(value))
    return str(value)


class Interpreter:
    LET = re.compile(r"^let\s+([A-Za-z_]\w*)\s*=(.*)$")

    def __init__(self):
        self.variables = {}

    def evaluate(self, text):
        tokens = tokenize(text)
        if not tokens:
            raise CalcError("empty expression")
        return Parser(tokens, self.variables).parse()

    def execute(self, line):
        line = line.strip()
        try:
            m = self.LET.match(line)
            if m:
                name = m.group(1)
                if name in FUNCTIONS or name == "let":
                    raise CalcError(f"cannot assign to {name}")
                value = self.evaluate(m.group(2))
                self.variables[name] = value
                return f"{name} = {show(value)}"
            return show(self.evaluate(line))
        except CalcError as err:
            return f"error: {err}"
        except (OverflowError, ValueError, TypeError) as err:
            return f"error: {err}"

=== pyp-15 | Capstone: a bank ledger with validation
--- teach
Your interpreter had to answer every line, even nonsense, without crashing. This capstone asks for something stricter. Money software is unforgiving: a lost cent is a bug report, and a transfer that happens only halfway is a disaster. The theme is **correctness under bad input**: the program stays right, whatever it is given.

You will build a small bank: accounts, deposits, withdrawals, transfers, and a statement for each account.

### Check once, at the door

Picture airport security. Every bag is checked once, at the entrance. After that, everyone inside the terminal is trusted, and nobody checks bags again at the café.

Programs can work the same way. The **boundary** is the place where values arrive from outside: from a user, a file, or another program. **Validate at the boundary**: check each value the moment it arrives, and turn it into a trusted form that the rest of the code can rely on. Then the inside of the program never has to [[worry about it again|boundary-trust]].

Here, amounts arrive as strings like `"12.34"`. At the boundary you check the format strictly and convert it to whole cents, an `int`, once. After that, no other code ever sees a string or a float.

### Strict means strict

The spec allows digits, then optionally a `.` with one or two decimals, with spaces around them allowed. So `"12"`, `"12.3"` and `" 12.34 "` are fine. Each of these must be refused with `ValueError`:

- `"12.345"`: three decimals.
- `"-5"`, `"abc"`, `"5."`, `""` and `" "`: not digits in the right shape.
- `"1e3"`: Python's `float("1e3")` reads it as `1000.0`, but it is not an amount in this format.
- `12.5`, which is not a string at all. Accepting floats would [[invite the rounding errors|float-money]] that storing cents is meant to avoid.

The expense tracker checked amounts piece by piece with `partition` and `isdigit()`. A regular expression can say the whole format in one line. It needs one new piece: `{1,2}` means "one or two times".

```python
import re
AMOUNT = re.compile(r"\d+(\.\d{1,2})?")
```

In words: `\d+` is one or more digits; `\.` is a real dot (a bare `.` would mean "any character"); `\d{1,2}` is one or two digits; and the `( )?` around the dot part makes that whole part optional.

### match or fullmatch

Here is a trap. `match` only checks that the pattern fits at the **start** of the string. It is happy if more text follows. `fullmatch` checks that the pattern fits the **whole** string:

```python
bool(AMOUNT.fullmatch("12.34"))     # True
bool(AMOUNT.fullmatch("12.345"))    # False: the 5 is left over
bool(AMOUNT.match("12.345"))        # True: "12.34" fits at the start
```

For validation you want [[fullmatch|match-vs-fullmatch]].

One step comes before the pattern: check that the value is a string at all, with `isinstance(amount, str)`. Otherwise `amount.strip()` on the float `12.5` crashes with `AttributeError`, not the `ValueError` the spec asks for.

Once the format is right, convert to cents the way the expense tracker did, with `partition(".")` and `ljust(2, "0")`.

### Showing cents as money

Balances are shown with two decimals and no thousands separator: `123450` cents is `"1234.50"`. That is the expense tracker's formatting without the `,`:

```python
cents = 123450
f"{cents // 100}.{cents % 100:02d}"      # '1234.50'
```

### Account numbers

Account numbers are `"ACC-0001"`, `"ACC-0002"`, and so on. Keep a counter of accounts opened, and pad it with the format `:04d`, which means "a whole number, at least four digits wide, [[padded with zeros|zero-padding]] on the left":

```python
f"ACC-{7:04d}"       # 'ACC-0007'
f"ACC-{123:04d}"     # 'ACC-0123'
```

### All or nothing

A transfer is two changes: take money from one account, give it to another. If the first happens and the second fails, the money has vanished.

An operation that happens completely or not at all is called **[[atomic|atomic]]**. The rule that makes an operation atomic: **check everything that can fail first, then make all the changes**, with nothing between the changes that can raise. For a transfer, that means: look up both accounts, check they are different, validate the amount, and check the balance. Only then change the two balances.

Here is the wrong order:

```python
src["balance"] -= cents               # the money leaves the source...
dst = self._account(target)           # ...then this raises KeyError
```

If `target` does not exist, the second line raises, and the money has left the source with nowhere to land. A failed transfer, whether to a missing account or for more than the balance, must leave *both* accounts, and both statements, exactly as they were.

### An audit trail

Real ledgers never overwrite a balance and forget. They record every movement. Here each account keeps a **statement**: a list of lines, one per movement, each ending with the balance after it:

```
open 10.00 -> 10.00
deposit 5.50 -> 15.50
withdraw 2.00 -> 13.50
```

Anyone can check the arithmetic line by line: 10.00 plus 5.50 is 15.50, minus 2.00 is 13.50. A record like this is called an [[audit trail|audit-trail]]. Add a line only after an operation has succeeded, so failed operations leave no trace.

### Different errors for different problems

The spec uses three kinds of error, because they mean three different things to the code that calls yours:

- `ValueError`: bad input, like `"12.345"`. A form would show the user a message and let them try again.
- `KeyError`: an account number that does not exist. That is probably a bug somewhere in the calling code.
- `InsufficientFunds`: a withdrawal or transfer bigger than the balance. This is a [[normal business outcome|expected-errors]], not a mistake.

`InsufficientFunds` is your own exception class, like `LibraryError` in the library system: `class InsufficientFunds(Exception):` with `pass` as its body.

### Design questions to settle first

Before you type, decide: How will you store an account (its name, its balance in cents, its statement lines)? How will you make account numbers? Where does validation live, so that it is written once and used by `open`, `deposit`, `withdraw` and `transfer`?

**Watch out:** writing the amount check in four places, slightly differently each time. Sooner or later one of them lets `"12.345"` through. Write one function that validates a string and converts it to cents, and one that also insists on more than zero. Deposits, withdrawals and transfers use the second; `open` uses only the first, because an account may start at zero.

::: context boundary-trust A spacecraft lost at a boundary

The navigation software, built by another team, read those numbers as newton-seconds, which are about 4.45 times smaller. Nothing checked the numbers where they crossed from one system to the other, so the trajectory was wrong, and the orbiter came in far too low. The boundary between two programs is exactly where a value must be checked, and turned into one agreed form.

::: context float-money The float version drifts
One of this lesson's checks deposits 0.10 a thousand times, then withdraws 0.07 a thousand times. In whole cents that is exact: 10,000 minus 7,000 is 3,000 cents, which is 30.00. With floats, the tiny error in each step piles up:

```python
b = 0.0
for _ in range(1000): b += 0.10
for _ in range(1000): b -= 0.07
b     # 30.00000000000196
```

Neither 0.10 nor 0.07 can be stored exactly in binary, as the floating-point lesson showed. A bank that did this across millions of accounts would be out by real money.
:::

::: context zero-padding Four digits is a minimum
The `0` in `:04d` says "pad with zeros", and the `4` is a minimum width, not a limit. So `f"{12345:04d}"` is `'12345'`: the 12,345th account still gets its number, just one digit longer. Zero-padding makes numbers the same length, so they line up in lists and sort correctly as text: `"ACC-0010"` comes after `"ACC-0009"`, while `"ACC-10"` would sort before `"ACC-9"`.
:::

The word comes from the Greek *atomos*, "uncuttable": an atomic operation cannot be split into a half that happened and a half that did not.

::: context audit-trail Why ledgers keep every line
Bookkeeping has worked this way for centuries. Luca Pacioli described double-entry bookkeeping in a mathematics book printed in 1494: every movement of money is written down twice, once where it left and once where it arrived, so the books can always be checked. Your transfer does the same with its `transfer-out` and `transfer-in` lines. Spacecraft keep audit trails too: every command sent and every event on board goes into a log, so that engineers can later work out exactly what happened and when.
:::

::: context expected-errors Errors that are not mistakes
Not every exception means something went wrong in the code. "Not enough money" is a normal answer a bank gives every day, just as "that book is out on loan" was in the library system. A separate exception class lets the calling code pick exactly that case, `except InsufficientFunds:`, and show a friendly message, while a `KeyError` from a real bug still stops the program loudly, where a test will catch it. Catching every exception with one broad `except` would hide the bugs along with the business outcomes.
:::
--- task
Build `class InsufficientFunds(Exception)` and `class Bank`, to this specification. The design inside is up to you.

- Amounts are strings of digits with an optional `.` and one or two decimals (`"12"`, `"12.3"`, `"12.34"`), surrounding spaces allowed. Anything else (including non-strings) raises `ValueError`. Balances are always shown as strings with two decimals and no thousands separator, like `"1234.50"`.
- `open(name, initial="0.00")` returns a new account number: `"ACC-0001"`, `"ACC-0002"`, … An empty name raises `ValueError`. The initial amount may be zero.
- `deposit(number, amount)` and `withdraw(number, amount)`: the amount must be more than zero (`ValueError`); withdrawing more than the balance raises `InsufficientFunds`.
- `transfer(source, target, amount)`: moves money between two different accounts (the same account twice is a `ValueError`); insufficient funds raises `InsufficientFunds`. A failed transfer changes nothing.
- An unknown account number raises `KeyError` everywhere.
- `balance(number)` returns the balance string. `total()` returns the sum of all balances.
- `statement(number)` returns a list of lines, one per movement: `"open 10.00 -> 10.00"`, `"deposit 5.50 -> 15.50"`, `"withdraw 2.00 -> 13.50"`, `"transfer-out 3.00 to ACC-0002 -> 10.50"`, `"transfer-in 3.00 from ACC-0001 -> 3.00"`. Each ends with the balance after that movement. Failed operations add no line.

# Capstone: design and build InsufficientFunds and Bank to the specification in the task.
--- solution
import re


class InsufficientFunds(Exception):
    pass


AMOUNT = re.compile(r"\d+(\.\d{1,2})?")


def parse_amount(text):
    """"12.34" -> 1234 cents. Only strings with at most two decimals."""
    if not isinstance(text, str) or not AMOUNT.fullmatch(text.strip()):
        raise ValueError(f"invalid amount: {text!r}")
    whole, _, frac = text.strip().partition(".")
    return int(whole) * 100 + int(frac.ljust(2, "0"))


def fmt(cents):
    return f"{cents // 100}.{cents % 100:02d}"


class Bank:
    def __init__(self):
        self._accounts = {}
        self._opened = 0

    def _account(self, number):
        if number not in self._accounts:
            raise KeyError(number)
        return self._accounts[number]

    def _positive(self, amount):
        cents = parse_amount(amount)
        if cents <= 0:
            raise ValueError("amount must be more than zero")
        return cents

    def _record(self, number, kind, cents, detail=""):
        account = self._accounts[number]
        account["history"].append(f"{kind} {fmt(cents)}{detail} -> {fmt(account['balance'])}")

    def open(self, name, initial="0.00"):
        if not isinstance(name, str) or not name.strip():
            raise ValueError("an account needs a name")
        cents = parse_amount(initial)
        self._opened += 1
        number = f"ACC-{self._opened:04d}"
        self._accounts[number] = {"name": name.strip(), "balance": cents, "history": []}
        self._record(number, "open", cents)
        return number

    def deposit(self, number, amount):
        account = self._account(number)
        cents = self._positive(amount)
        account["balance"] += cents
        self._record(number, "deposit", cents)

    def withdraw(self, number, amount):
        account = self._account(number)
        cents = self._positive(amount)
        if cents > account["balance"]:
            raise InsufficientFunds(f"{number} has only {fmt(account['balance'])}")
        account["balance"] -= cents
        self._record(number, "withdraw", cents)

    def transfer(self, source, target, amount):
        src = self._account(source)
        self._account(target)
        if source == target:
            raise ValueError("cannot transfer to the same account")
        cents = self._positive(amount)
        if cents > src["balance"]:
            raise InsufficientFunds(f"{source} has only {fmt(src['balance'])}")
        src["balance"] -= cents
        self._accounts[target]["balance"] += cents
        self._record(source, "transfer-out", cents, f" to {target}")
        self._record(target, "transfer-in", cents, f" from {source}")

    def balance(self, number):
        return fmt(self._account(number)["balance"])

    def statement(self, number):
        return list(self._account(number)["history"])

    def total(self):
        return fmt(sum(a["balance"] for a in self._accounts.values()))

=== pyp-16 | Capstone: a text adventure state machine
--- teach
Your bank refused bad input and kept every account exactly right. This is the last capstone, and the last lesson of the whole Python ladder. It ends with a game, and the game is built on one of the most useful ideas in software.

A **text adventure** is a game played entirely in words. The game describes a room; you type a command like `go north` or `take key`; the game replies. Here is the start of a game in the world from the starter (`>` marks what the player typed):

```
> look
A dusty hall. Exits: east, north. You see: lamp.
> go north
Shelves of old books. Exits: south. You see: key, map.
> take key
Taken: key.
> inventory
You carry: key.
```

### A state machine

Think of a vending machine. At any moment it is in some **state**: waiting, holding 50 cents, handing out a drink. Each thing you do (put in a coin, press a button) moves it to a new state, and it shows you a reply. A program shaped like that is a **[[state machine|state-machine]]**: it is always in some state, each input moves it to a new state, and the reply describes what happened.

A text adventure is one. Its state is which room you are in, what you carry, what lies in each room, and whether the game is over. Each command changes the state and gets a reply. The same shape runs vending machines, network connections, the checkout on a shopping site, and the characters in video games.

### Data and logic, kept apart

The rooms, exits and items are **data**: the `WORLD` dict in the starter. You could edit it, or load it from a JSON file the way the library system did, without touching any code. The rules, how `go`, `take` and `drop` work, are **logic**: your code.

Keep them apart, and your code works for [[any world with the same shape|data-driven]], not only the example. The checks try a different world too, so no room or item name from `WORLD` should appear anywhere in your class.

Here is one room from the starter:

```python
"kitchen": {
    "description": "It smells of bread.",
    "exits": {"west": "hall", "down": "cellar"},
    "items": [],
    "locked": {"down": "key"},
},
```

`exits` maps each direction to the room it leads to. `locked` is optional: it maps a direction to the item you must carry to go that way. Here, going `down` from the kitchen needs the `key`.

### Name the state before you code

List exactly what changes during play:

- the current room;
- the **inventory**, the items you carry;
- the items in each room, because taking and dropping move them;
- whether the game is over.

Everything else stays fixed: descriptions, exits, and which exit needs which item. Keep the changing state in the `Game` object, for example in `self.room`, `self.inventory` and `self.over`. The spec says `game.room` must be the name of the current room.

### Do not change the world you were given

Picture two games made from the same `WORLD` dict. The first player takes the lamp. If `take` removes `"lamp"` from the list inside the *shared* dict, the second game starts with the lamp already gone. That is [[the aliasing bug|aliasing-again]] from the advanced course, once more.

So make your own deep copy of the world when a game starts, and change only your copy:

```python
import copy
self.world = copy.deepcopy(world)
```

### Reading a command: parse, dispatch, handle

Three small steps, like the command dispatcher in the expert course's plugin lesson.

**1. Parse.** Lowercase the command, so `TAKE KEY` works too, and split it into words. The first word is the **verb**; the rest is what it acts on.

```python
"Go  North".lower().split()     # ['go', 'north']
"".split()                      # []: nothing typed at all
```

**2. Dispatch.** Look at the verb and pick the method that handles it. An `if` chain works, and so does [[a dict from verb to method|dispatch-table]].

**3. Handle.** Write one method per verb. Each one checks its own **preconditions** (the things that must be true before the action can happen: is there such an exit? is it locked? is the item here?) and returns the reply.

Some commands do not fit any verb. A verb that needs a word but has none (`go` on its own), a verb that takes no word but got one (`look around`), an empty line and any unknown verb all get `"I don't understand."`.

### Locked exits

Most rooms have no `"locked"` key at all, so `room["locked"]` would raise `KeyError`. `.get` with a default handles the missing key: `room.get("locked", {})` gives an empty dict when there is none. A second `.get` then finds the item a direction needs, or `None`:

```python
room = {"exits": {"up": "rim"}, "items": []}
room.get("locked", {}).get("up")       # None: nothing locks this way
```

So `go` checks, in order: does the exit exist? If it is locked, is its item in your inventory? Only then move, and reply with the new room's `look` text.

### The end state

Taking the goal item wins the game. From then on, every command gets the same reply, `"The game is over."`. So check "is the game over?" *first* in `do`, before any other logic runs. A check at the very top of a method that returns early is called a [[guard clause|guard-clause]].

### Exact output

The checker is a program, and it compares your replies [[character for character|exact-output]]: every full stop, every comma, every list in the right order. Read the spec closely for which lists are sorted:

- the exits in `look`: sorted;
- the items in a room: in the room's own order, with a dropped item added at the end;
- the inventory: sorted.

A room with no exits says `Exits: none.`. One tidy way to get that: `", ".join` of an empty list is `""`, and an empty string counts as false, so `or` moves on to its right side:

```python
", ".join(sorted({"north": "library", "east": "kitchen"})) or "none"    # 'east, north'
", ".join(sorted({})) or "none"                                          # 'none'
```

**Watch out:** putting the "game over" check anywhere but the top of `do`. Then, after the win, `look` still describes the cellar and `take` still works. The spec wants every command after the win to reply `"The game is over."`, so the guard goes first.

When this passes, you have climbed the whole Python ladder: from printing one line to a game engine that runs any world you give it. [[Where you go from here|where-next]] is up to you.

::: context dispatch-table A table of handlers
Methods are values, so a dict can hold them: `{"go": self.go, "take": self.take, "drop": self.drop}`. Dispatching is then one lookup, `handlers.get(verb)`, and `None` means an unknown verb. Adding a new verb means adding one method and one entry, without touching the dispatcher. Spacecraft handle commands from the ground the same way: each command has an id, a table maps ids to handlers, and an unknown id is rejected instead of guessed at.
:::

::: context guard-clause Guard clauses
A **guard clause** is an `if` at the top of a function that handles a special case and returns at once. Everything after it can then assume the special case is gone: the rest of `do` never has to ask "but what if the game is over?" again. Guards keep code flat, instead of nesting the whole method inside an `if not self.over:` block, and they put the most important rule where a reader sees it first.
:::

::: context exact-output When a program is the reader
People forgive a missing full stop; programs do not. Whenever output is read by another program, the format is part of the contract. Spacecraft send their measurements to the ground as **telemetry** in fixed formats, and ground software decodes every field by its exact position. If one field moves, every field after it is read wrong. The checks here compare whole strings, so `"Taken: key"` without its full stop fails just as surely as a wrong answer.
:::

The software on board is usually written in C or C++, because it must run in tight memory with exactly predictable timing. NASA JPL's F Prime flight software framework, for example, is written in C++, and much of the tooling around it is Python. The C++ courses here start from the ideas you now know: variables, loops, functions, classes, and the habit of designing before you type.

--- task
The starter defines `WORLD`, an example world. Build a class `Game(world)` that works for any world of that shape: `start`, `goal`, and `rooms`, each room with `description`, `exits`, `items` and optionally `locked`, which maps a direction to the item needed to go that way.

`game.room` is the current room's name. `game.do(command)` returns the reply (commands are case-insensitive):

- `look`: `"<description> Exits: <exits, sorted, comma-separated>."`, followed by `" You see: <items in the room's order>."` if the room has items. With no exits: `Exits: none.`
- `go <direction>`: moves and returns the new room's `look` text. No such exit: `"You can't go that way."`. A locked exit without its item in your inventory: `"The way <direction> is locked."`.
- `take <item>`: `"Taken: <item>."`, or `"There is no <item> here."`. Taking the goal item replies `"Taken: <item>. You win!"` and ends the game.
- `drop <item>`: puts it in the current room (at the end of its item list): `"Dropped: <item>."`, or `"You don't have <item>."`.
- `inventory`: `"You carry: <items, sorted>."` or `"You carry nothing."`.
- Anything else, including a verb missing its word: `"I don't understand."`. After the game is over, every command replies `"The game is over."`.

Creating or playing a game must not change the world dict it was given.

import copy

WORLD = {
    "start": "hall",
    "goal": "treasure",
    "rooms": {
        "hall": {
            "description": "A dusty hall.",
            "exits": {"north": "library", "east": "kitchen"},
            "items": ["lamp"],
        },
        "library": {
            "description": "Shelves of old books.",
            "exits": {"south": "hall"},
            "items": ["key", "map"],
        },
        "kitchen": {
            "description": "It smells of bread.",
            "exits": {"west": "hall", "down": "cellar"},
            "items": [],
            "locked": {"down": "key"},
        },
        "cellar": {
            "description": "Treasure glitters in the dark.",
            "exits": {"up": "kitchen"},
            "items": ["treasure"],
        },
    },
}


class Game:
    def __init__(self, world):
        self.world = copy.deepcopy(world)
        self.rooms = self.world["rooms"]
        self.room = self.world["start"]
        self.inventory = []
        self.over = False

    def look(self):
        room = self.rooms[self.room]
        exits = ", ".join(sorted(room["exits"])) or "none"
        text = f"{room['description']} Exits: {exits}."
        if room["items"]:
            text += f" You see: {', '.join(room['items'])}."
        return text

    def go(self, direction):
        room = self.rooms[self.room]
        if direction not in room["exits"]:
            return "You can't go that way."
        key = room.get("locked", {}).get(direction)
        if key and key not in self.inventory:
            return f"The way {direction} is locked."
        self.room = room["exits"][direction]
        return self.look()

    def take(self, item):
        items = self.rooms[self.room]["items"]
        if item not in items:
            return f"There is no {item} here."
        items.remove(item)
        self.inventory.append(item)
        if item == self.world.get("goal"):
            self.over = True
            return f"Taken: {item}. You win!"
        return f"Taken: {item}."

    def drop(self, item):
        if item not in self.inventory:
            return f"You don't have {item}."
        self.inventory.remove(item)
        self.rooms[self.room]["items"].append(item)
        return f"Dropped: {item}."

    def do(self, command):
        if self.over:
            return "The game is over."
        words = command.lower().split()
        if not words:
            return "I don't understand."
        verb, rest = words[0], " ".join(words[1:])
        if verb == "look" and not rest:
            return self.look()
        if verb == "inventory" and not rest:
            if not self.inventory:
                return "You carry nothing."
            return f"You carry: {', '.join(sorted(self.inventory))}."
        if verb == "go" and rest:
            return self.go(rest)
        if verb == "take" and rest:
            return self.take(rest)
        if verb == "drop" and rest:
            return self.drop(rest)
        return "I don't understand."
--- hint
State that changes: the current room, the inventory, each room's items, and whether the game is over. Deep-copy the world in `__init__` with `copy.deepcopy`, so the items can change safely.
--- hint
In `do`, check "game over" first. Then `words = command.lower().split()`; the verb is `words[0]` and the rest is `" ".join(words[1:])`. Call one method per verb, and reply `"I don't understand."` when a verb is missing its word or has one it should not.
--- hint
