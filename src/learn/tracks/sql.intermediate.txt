=== sql2-01 | Joining three tables
--- teach
At the end of the basics you joined two tables: each row of `requests` found its user in `users` through `user_id`. You also grouped rows, kept users with LEFT JOIN, changed data and named steps with `WITH`. This course asks harder questions of a bigger database. This first lesson lets you join three or four tables in one query.

Along the way, the course also teaches the traps that make a report quietly wrong: NULLs (empty values), joins that multiply rows, and text that looks equal but is not.

### The shop

The course uses a small online shop. Its database has six **tables**. A table is a grid: each **row** is one thing (one customer, one order), and each **column** is one fact about it (a name, a price).

- `customers`: `id`, `name`, `email`, `city`, `referred_by` (another customer's id, or NULL), `joined`
- `products`: `id`, `name`, `category`, `price`
- `orders`: `id`, `customer_id`, `placed` (the moment it was ordered, written as a `'YYYY-MM-DD HH:MM:SS'` [[timestamp|timestamp]]), `status` (`paid`, `shipped`, `cancelled` or `refunded`), `coupon`
- `order_items`: one row per product in an order: `order_id`, `product_id`, `qty` (how many), `unit_price` ([[what was actually charged|unit-price]] for one, which can differ from today's price)
- `payments`: `id`, `order_id`, `amount` (an order can have several payments; refunds are negative)
- `newsletter`: `email`, `signed_up`

Look at the columns that end in `_id`. `customer_id` in `orders` holds the `id` of a row in `customers`. A column that points at a row in another table is a **[[foreign key|foreign-key]]**: a link from one table to another.

### A receipt, followed back

Picture a paper receipt. Each line names a product and a quantity. The receipt belongs to one order, and the order belongs to one customer. To read one line in full, "Ada bought 3 Notebooks", you [[follow the links|join-chain]]: from the line to its order, from the order to its customer, and from the line to its product.

In the database, one line of a receipt is one row of `order_items`. On its own it holds only numbers. Here are its first three rows:

| order_id | product_id | qty |
| --- | --- | --- |
| 1 | 1 | 3 |
| 1 | 4 | 1 |
| 2 | 5 | 1 |

### One link at a time

You follow each link with one `JOIN`, and each `JOIN` gets its own `ON`. The `ON` says which rows belong together. Start with one link, from items to orders:

```sql
SELECT oi.order_id, o.customer_id, oi.qty
FROM order_items oi
JOIN orders o ON o.id = oi.order_id;
```

`oi` and `o` are the short nicknames (aliases) you met in the basics. `ON o.id = oi.order_id` means "pair each item with the order whose `id` equals the item's `order_id`". Now each item knows its customer's id:

| order_id | customer_id | qty |
| --- | --- | --- |
| 1 | 1 | 3 |
| 1 | 1 | 1 |
| 2 | 1 | 1 |

Add a second `JOIN` to turn that id into a name:

```sql
SELECT oi.order_id, c.name, oi.qty
FROM order_items oi
JOIN orders o    ON o.id = oi.order_id
JOIN customers c ON c.id = o.customer_id;
```

The new `ON` uses `o.customer_id`, a column that only arrived with the join before it. That is why the joins read as a chain, one link after another.

| order_id | name | qty |
| --- | --- | --- |
| 1 | Ada | 3 |
| 1 | Ada | 1 |
| 2 | Ada | 1 |

A third `JOIN` brings in the product. Here is the whole chain:

```sql
SELECT o.id, c.name, p.name AS product
FROM order_items oi
JOIN orders o    ON o.id = oi.order_id
JOIN customers c ON c.id = o.customer_id
JOIN products p  ON p.id = oi.product_id;
```

Read it as a chain: every item belongs to one order, every order to one customer, and every item names one product.

### Where to start

Put in `FROM` the table you want [[one row per result row|one-row-per]]. Here you want one row per item, so start from `order_items`. Then walk out along the foreign keys. Each item has exactly one order, one customer and one product, so these joins add columns but never add rows: 13 items go in, 13 rows come out.

### Two habits

First, give every table a short alias and put it in front of **every** column: `c.name`, `p.name`. Both `customers` and `products` have a column called `name`. Without the prefix, the database cannot tell which one you mean, and it [[stops with an error|ambiguous-column]].

Second, when two columns in the result would share a name, rename one with `AS`. `AS` means "call this column something else in the result". Above, `p.name AS product` keeps the product's name apart from the customer's `name`.

**Watch out:** each `ON` must pair the right two columns. `JOIN customers c ON c.id = o.id` runs without any error, but it matches customer 1 to order 1, customer 2 to order 2, and so on, which means nothing. Read every `ON` aloud: "this table's `id` equals the column in the other table that points at it".

::: context timestamp Dates written as text
A timestamp is a date and a time together, like `'2024-03-20 18:40:00'`: year, month, day, then hours, minutes and seconds. This shop stores them as text. The biggest part (the year) comes first and every part has a fixed width, with a zero in front where needed (`03`, not `3`). Because of that, sorting the text A-to-Z also sorts the moments from earliest to latest. This layout is an international standard called ISO 8601. Lesson 9 of this course shows the functions that do arithmetic with these dates.
:::

::: context unit-price Why an order stores its own price
Prices change. If an order only pointed at `products.price`, then raising the price of Headphones tomorrow would change what Ada paid last March, and every old report would shift. So the shop copies the price into `order_items` at the moment of sale. You can see the difference in this data: Headphones cost 89.00 today, but Ada's order 2 charged 80.10, because that order used the `SPRING10` coupon (10% off). Receipts, invoices and flight logs all work this way: record what happened, as it happened.
:::

::: context foreign-key Links between tables
You met these in the basics, where `requests.user_id` pointed at `users.id` and `REFERENCES users(id)` in `CREATE TABLE` declared the link. A foreign key is only a column of numbers, but it is what makes joins possible: the `ON` of almost every join pairs a foreign key with the `id` it points at. In this shop, `orders.customer_id`, `order_items.order_id`, `order_items.product_id` and `payments.order_id` are all foreign keys. The advanced course has a whole lesson on making the database enforce them.
:::

::: context join-chain The shop as a chain of links
Each arrow below is a foreign key. A query that starts at `order_items` can reach every other table by following arrows, one `JOIN` per arrow.

::: context one-row-per The grain of a query
Engineers call "what one row stands for" the **grain** of a result. Here the grain is one order item. Deciding the grain first tells you which table goes in `FROM`. It also gives you a free test: count the rows before and after each join. If a join you expected to only add columns suddenly adds rows, a link is not one-to-one, and your totals will come out too big. Lesson 14 of this course is a whole bug hunt built on exactly that.
:::

::: context ambiguous-column The error you get without a prefix
In SQLite, `SELECT name FROM order_items oi JOIN orders o ON o.id = oi.order_id JOIN customers c ON c.id = o.customer_id JOIN products p ON p.id = oi.product_id;` stops with `ambiguous column name: name`. "Ambiguous" means "could mean more than one thing". This error is a friendly one: it stops the query instead of guessing. Prefixing every column, even the ones that are not ambiguous today, keeps the query working if someone later adds a `name` column to another table.
:::
--- task
For every item in an order whose `status` is `'shipped'`, return four columns: the order id, the customer's name, the product's name and the quantity (`qty`). You will need `order_items`, `orders`, `customers` and `products`. Sort by order id, then by product name.
--- starter
SELECT oi.order_id, oi.product_id, oi.qty
FROM order_items oi;
--- solution

JOIN orders o    ON o.id = oi.order_id
JOIN customers c ON c.id = o.customer_id
JOIN products p  ON p.id = oi.product_id
WHERE o.status = 'shipped'
ORDER BY o.id, p.name;
--- hint
Start from `order_items oi`, one row per item, and add one `JOIN` for each link: first `orders`, then `customers`, then `products`.
--- hint

--- hint
Select `o.id, c.name, p.name AS product, oi.qty`, and finish with `ORDER BY o.id, p.name`.

=== sql2-02 | LEFT JOIN: where the filter goes
--- teach
Last lesson every join was an inner `JOIN`: it keeps only rows that find a match. In the basics you also met `LEFT JOIN`, which keeps every row of the [[left table|left-table]] and fills the other side with NULL when nothing matches. This lesson shows where to put a filter in a LEFT JOIN. There is a catch here that trips up almost everyone once.

### The picture

A teacher wants a list of every student with the number of homeworks they handed in on time, 0 for anyone with none. The teacher writes every student down, with each homework next to the name. Then every line where the homework was not on time gets crossed out. But a student with no homework at all has a blank on that line, and a blank is not "on time", so that line is crossed out too. Now they are missing from a list that was meant to include everyone.

### The LEFT JOIN keeps everyone

Here is every customer with their orders:

```sql
SELECT c.name, o.id, o.status
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
ORDER BY c.name, o.id;
```

The last four rows:

| name | id | status |
| --- | --- | --- |
| Dev | 6 | shipped |
| Eve | 7 | refunded |
| Finn | NULL | NULL |
| Gus | NULL | NULL |

Finn and Gus have no orders, so the order columns are **NULL**, which means "no value here".

### The query that looks right

You want every customer with their number of *live* orders: orders whose status is `paid` or `shipped`. `IN ('paid', 'shipped')` means "is one of these values". This looks right:

```sql
SELECT c.name, COUNT(o.id) AS live_orders
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.status IN ('paid', 'shipped')
GROUP BY c.id, c.name;
```

It returns only four rows: Ada 3, Ben 1, Cleo 1, Dev 1. Eve, Finn and Gus are gone.

### Why they vanish

A **clause** is one part of a query that starts with a keyword: the `FROM` clause, the `WHERE` clause. The database does the `FROM` and `JOIN`s first, and the `WHERE` [[runs after the join|run-order]].

So Finn reaches the `WHERE` with `o.status` = NULL. `NULL IN ('paid', 'shipped')` is not true. It is [[unknown|unknown]], and `WHERE` keeps only rows where the condition is true. Finn is thrown away. Gus goes the same way. Eve's only order was refunded, and `'refunded' IN ('paid', 'shipped')` is false, so Eve goes too. The LEFT JOIN kept them; the WHERE undid it.

### The fix: put it in ON

Put conditions about the **right-hand** table (the one after `LEFT JOIN`) inside its `ON`, joined with `AND`:

```sql
LEFT JOIN orders o ON o.customer_id = c.id AND o.status IN ('paid', 'shipped')
```

Now the condition decides which orders *match*. It no longer removes customers. Eve's refunded order does not match, so Eve [[stays with NULLs|on-never-drops]], like Finn and Gus:

| name | id | status |
| --- | --- | --- |
| Dev | 6 | shipped |
| Eve | NULL | NULL |
| Finn | NULL | NULL |
| Gus | NULL | NULL |

`COUNT(o.id)` skips NULLs, so those three [[count as 0|count-column]].

The rule of thumb: in a LEFT JOIN, conditions about the right table go in `ON`; conditions about the left table go in `WHERE`. For example, `WHERE c.city = 'London'` is fine in `WHERE`: it picks which customers you want.

**Watch out:** the wrong version gives no error and plausible numbers. It is only missing people. Count the rows you expect before you trust a result: 7 customers should give 7 rows.

::: context left-table Which table is "left"
The left table is the one written first, before the words `LEFT JOIN`. In `FROM customers c LEFT JOIN orders o`, `customers` is on the left and every customer is kept; `orders` is on the right and only fills in where it matches. Swap them and the promise swaps too. Read `LEFT JOIN` as "keep everything I already have, and add what matches".
:::

::: context run-order Written order and running order
You write `SELECT` first, but the database works out the rows starting from `FROM`. It builds the joined rows, then filters them with `WHERE`, then groups them. Lesson 4 of this course lists the whole order step by step. For this lesson, the key point is that `WHERE` only ever sees rows the joins have already built, NULL-filled ones included, and it can throw any of them away.
:::

::: context unknown True, false, and unknown
In SQL a comparison has three possible results: true, false, or unknown. Any comparison with NULL is unknown, because the database cannot say whether a missing value equals something. Even `NULL = NULL` is unknown. You can see it in SQLite: `SELECT NULL IN ('paid', 'shipped');` returns NULL, not 0 or 1. `WHERE` keeps a row only when its condition is true, so both false and unknown rows are dropped. Lesson 10 is a debugging lesson built entirely on this.
:::

::: context on-never-drops ON matches, WHERE removes
The two clauses do different jobs. `ON` answers "which right-hand rows go with this left-hand row?" If the answer is "none", a LEFT JOIN still keeps the left row, with NULLs. `WHERE` answers "which finished rows stay?", and it can remove anything.

Putting a right-table condition in `WHERE` quietly turns your LEFT JOIN back into an inner join. Lesson 17 lists this among the checks for any report.

::: context count-column Why COUNT(o.id) and not COUNT(*)
You saw this in the basics. `COUNT(*)` counts rows, and Finn still has one row, full of NULLs, so `COUNT(*)` would give Finn 1. `COUNT(o.id)` counts only the rows where `o.id` is not NULL, so Finn gets 0. After a LEFT JOIN, count a column from the right-hand table, ideally its `id`, which is never NULL in a real match.
:::

=== sql2-03 | Self-joins
--- teach
Last lesson you kept every customer with a LEFT JOIN, even when no order matched. So far every join has linked two *different* tables. This lesson shows how to join a table to itself, for when a table [[points at itself|referral-tree]].

### The picture

Picture a class list where each student has a "buddy" column holding another student's number. To find out who Sam's buddy is by name, you read Sam's buddy number, then run your finger back up the *same* list to find that number. One list, used twice: once to read the student, once to look up the buddy.

### A table that points at itself

In `customers`, `referred_by` holds the id of the customer who brought this one in: someone who recommended the shop to them. That is a **[[referral|referral]]**.

| id | name | referred_by |
| --- | --- | --- |
| 1 | Ada | NULL |
| 2 | Ben | 1 |
| 3 | Cleo | 1 |
| 4 | Dev | 2 |
| 5 | Eve | NULL |
| 6 | Finn | 4 |
| 7 | Gus | NULL |

Ben's `referred_by` is 1, so Ada referred Ben. To show the referrer's *name* instead of a number, join `customers` to itself. This is a **self-join**: a table joined to itself.

### Two aliases, two parts

Give the table two different aliases, so SQL knows [[which copy you mean|two-aliases]]:

```sql
SELECT c.name, r.name AS referrer
FROM customers c
JOIN customers r ON r.id = c.referred_by;
```

`c` is "the customer", `r` is "the referrer": the same table, playing two parts. Read the `ON` aloud: "the referrer's `id` equals this customer's `referred_by`". The result:

| name | referrer |
| --- | --- |
| Ben | Ada |
| Cleo | Ada |
| Dev | Ben |
| Finn | Dev |

Employees and their managers, categories and their parent categories, replies and the message they answer: these are all self-joins.

### Who goes missing

As with any inner join, rows with no match are dropped. Ada, Eve and Gus have `referred_by` = NULL, and [[NULL matches nothing|null-no-match]], so they disappear. Whether that is right depends on the question:

- "Who referred whom?" The inner join is fine.
- "List every customer with their referrer." Use `LEFT JOIN`. The customers nobody referred come back, with `referrer` = NULL.

**Watch out:** the direction of the `ON` matters. `ON c.id = r.referred_by` also runs, but it answers a different question: "whom did each customer refer?" It gives Ada twice (for Ben and for Cleo) and never mentions Eve. Say the `ON` in words before you run it.

::: context two-aliases Why the aliases are required
With two copies of the same table, every column name exists twice. === sql2-04 | GROUP BY in depth
--- teach
Last lesson you joined a table to itself. In the basics you met `GROUP BY` and `HAVING`. This lesson opens them up: you will see the order the database runs a grouped query in, which tells you where each filter goes, and how to count correctly after a join. The next lesson adds a few more grouping tools.

### The picture

Picture a pile of paper orders on a desk, and a summary to write. First you throw out the cancelled ones. Then you sort the rest into piles, one per customer. Then you count each pile. Then you put away the piles that are too small. Only then do you write the summary sheet, and put its lines in order.

### The order the database works in

A grouped query runs [[in the same order|run-order]]:

1. `FROM` and the `JOIN`s build one wide set of rows.
2. `WHERE` drops rows.
3. `GROUP BY` sorts the rows that are left into buckets, one bucket per value.
4. The **aggregates** run once per bucket. An aggregate is a function that turns many rows into one value: `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`.
5. `HAVING` drops buckets.
6. `SELECT` shapes the output, then `ORDER BY` sorts it.

Here it is on `orders` alone. `<>` means "not equal".

```sql
SELECT customer_id, COUNT(*) AS orders
FROM orders
WHERE status <> 'cancelled'
GROUP BY customer_id
HAVING COUNT(*) >= 2;
```

- `WHERE` drops order 3, Ben's cancelled one. Seven orders are left.
- `GROUP BY` makes five buckets: customer 1 has orders 1, 2 and 8; customers 2, 3, 4 and 5 have one order each.
- `COUNT(*)` counts each bucket: 3, 1, 1, 1, 1.
- `HAVING` keeps buckets with at least 2.

| customer_id | orders |
| --- | --- |
| 1 | 3 |

### Where each filter goes

That order explains the rules. `WHERE` cannot use `SUM(...)` or `COUNT(...)`, because at step 2 the sums [[do not exist yet|misuse-aggregate]]. `HAVING` runs at step 5, after they exist, so it can.

A condition that does not need an aggregate, such as `category = 'home'`, could go in either place. Put it in `WHERE`, where it [[throws rows away early|filter-early]].

### Counting different values

`COUNT(DISTINCT x)` counts the *different* values of `x`. `DISTINCT` means "each value once".

This matters after a join. Once `order_items` is joined in, there is one row per order *item*, so `COUNT(*)` counts items. That is rarely the number you want to call "orders" or "customers". Here are the buyers per category, over every order:

```sql
SELECT p.category, COUNT(*) AS item_rows, COUNT(DISTINCT o.customer_id) AS buyers
FROM order_items oi
JOIN orders o   ON o.id = oi.order_id
JOIN products p ON p.id = oi.product_id
GROUP BY p.category;
```

| category | item_rows | buyers |
| --- | --- | --- |
| electronics | 4 | 3 |
| home | 4 | 4 |
| stationery | 5 | 3 |

Ada bought two different electronics items, so Ada makes [[two rows but one buyer|count-distinct]].

**Watch out:** after a join, `COUNT(*)` counts joined rows. It gives no error; the number is only too big. Ask "one row of what?" and use `COUNT(DISTINCT ...)` on the id you really mean.

::: context run-order Why it runs in that order
You write `SELECT` first because it reads well, not because it happens first. The order in this lesson is the *logical* order: the answer always comes out as if the steps ran like that. Inside, a real database may do things in a cleverer order to go faster, but it never changes the answer. When a query surprises you, walking these six steps with pencil and paper nearly always finds the reason.
:::

::: context misuse-aggregate The error you get
Try `SELECT customer_id FROM orders WHERE COUNT(*) > 1 GROUP BY customer_id;` in SQLite. It stops with `misuse of aggregate: COUNT()`. The database is telling you it cannot count at the `WHERE` step, because the buckets have not been made yet. The fix is to move the condition to `HAVING`, which goes after `GROUP BY`.
:::

::: context filter-early Why WHERE is the better place
Every row that `WHERE` drops is a row that never has to be sorted into a bucket. On this shop's 13 items that makes no difference. On a table of flight telemetry, with millions of readings, it does. A condition in `WHERE` can also let the database use shortcuts (indexes, which you meet in the advanced course) to skip unwanted rows without reading them at all. `HAVING` only sees the buckets after all that work is done.
:::

::: context count-distinct Rows, and different values
The four electronics rows come from three people. `COUNT(*)` counts every row; `COUNT(DISTINCT o.customer_id)` counts each customer once.

=== sql2-04b | GROUP BY: expressions, NULLs and extra columns
--- teach
Last lesson you grouped by a column, `category`, and learned where `WHERE` and `HAVING` go. This lesson adds three more things about grouping: grouping by a value you work out, where NULLs land, and which extra columns you may put in the `SELECT`.

### The picture

Picture sorting a year of receipts into monthly envelopes. You do not care about the exact day or time on each receipt. You only read the month from the date, and that decides the envelope.

### Grouping by an expression

An **expression** is anything that works out a value: a column, a sum like `qty * unit_price`, or a function call. You can group by an expression, not only by a column.

`substr(placed, 1, 10)` takes a piece of the text in `placed`: starting at character 1, 10 characters long. `substr` is short for "substring", a piece of a string (text). From `'2024-04-07 20:10:00'` it gives `'2024-04-07'`, the day. Lesson 8 covers text functions properly.

```sql
SELECT substr(placed, 1, 10) AS day, COUNT(*) AS orders
FROM orders
GROUP BY substr(placed, 1, 10);
```

Every order placed on 7 April lands in one bucket, whatever its time:

| day | orders |
| --- | --- |
| 2024-03-02 | 1 |
| 2024-03-20 | 1 |
| 2024-03-21 | 1 |
| 2024-04-07 | 2 |
| 2024-05-15 | 1 |
| 2024-05-28 | 1 |
| 2024-06-01 | 1 |

Notice that you [[repeat the expression|group-alias]] in `GROUP BY`. Take the first 7 characters instead and you get the month, like `'2024-03'`.

### NULLs get one group of their own

Some customers have no city. When you group by `city`, [[all the NULLs fall into one group|null-group]]:

```sql
SELECT city, COUNT(*) AS customers
FROM customers
GROUP BY city;
```

| city | customers |
| --- | --- |
| NULL | 2 |
| Berlin | 1 |
| London | 2 |
| Paris | 2 |

The NULL group is Cleo and Finn. If a report should not show it, filter it out with `WHERE city IS NOT NULL`.

### Which extra columns you may select

The rule from the basics: every column in the `SELECT` is either in the `GROUP BY` or inside an aggregate. Here is one refinement.

A **primary key** is the column that tells every row apart, like `customers.id`: no two customers share one. Grouping by a table's primary key also lets you select that table's other columns:

```sql
SELECT c.id, c.name, COUNT(o.id) AS orders
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.id;
```

`c.name` is not grouped or aggregated, but this is fine. Each group is exactly one customer, so it has exactly one name. [[PostgreSQL accepts this too|functional-dependency]].

SQLite goes further, and this part is a trap. It lets you select *any* column that is neither grouped nor aggregated, and it [[silently picks a value|bare-columns]] from some row in the group:

```sql
SELECT city, name, COUNT(*) FROM customers GROUP BY city;
```

The London group holds Ada and Dev, but only one name comes back, and nothing tells you which. Other databases reject this query, and so should you. When in doubt, add the column to the `GROUP BY`.

**Watch out:** group by the piece you mean. `GROUP BY placed` makes one group per exact timestamp, and here every order has a different one, so every group holds a single order. To count per month, group by the [[month piece|month-buckets]].

::: context group-alias Grouping by the name you gave it
In this lesson the whole expression is written again in `GROUP BY`. That works in every database. SQLite and PostgreSQL also let you group by the name you gave the column with `AS`, so `GROUP BY day` does the same job. You will see that shortcut in later lessons, such as `GROUP BY domain` in lesson 8. Some databases, such as Microsoft SQL Server, do not allow it, so writing the expression out is the safe habit.
:::

::: context null-group Why the NULLs stick together
You learned that `NULL = NULL` is unknown, not true. So why do the NULLs share one group? Because the SQL standard makes a special rule for grouping: `GROUP BY` and `DISTINCT` treat all NULLs as the same value. Otherwise every NULL would get a group of its own, which would be useless. The NULL group is often a sign of missing data worth a look. In lesson 8 a missing email turns into exactly this kind of NULL group.
:::

::: context functional-dependency Why the primary key is enough
If you know a customer's `id`, you know their `name`, because only one row has that id. Database people say `name` is *functionally dependent* on `id`: one determines the other. The SQL standard allows selecting such columns, and PostgreSQL has accepted them since version 9.1 (2011). It only works for columns of the table whose primary key you grouped by; `o.status` would still be refused, because one customer can have many orders.
:::

::: context bare-columns SQLite's "bare columns"
A column in a grouped query that is neither grouped nor aggregated is called a bare column. SQLite's documentation says a bare column takes its value from an arbitrary row of the group. There is one exception: with `MIN(...)` or `MAX(...)`, the bare columns come from the row that holds the minimum or maximum. So `SELECT city, name, MAX(joined) FROM customers GROUP BY city;` gives the newest customer in each city. That is handy, but it only works in SQLite and it is easy to misread. MySQL rejects bare columns by default, and PostgreSQL always does.
:::

This is the task's grouping as a picture. Each order's timestamp is cut to its first 7 characters, and orders with the same piece share a bucket.

=== sql2-05 | Subqueries: a value, or a list
--- teach
Last lesson you sorted orders into monthly buckets. This lesson goes back to an idea from the end of the basics, the subquery, and gives it a second shape. Before, a subquery gave back one value. Now it can give back a whole list, and you can ask "is this row's id on that list?".

### The picture

Picture a party with a guest list at the door. The person at the door does not care how many times your name was written on the list. They only ask one question: is your name on it, yes or no? If yes, you go in, once.

### A quick reminder: one value

A **subquery** is a whole `SELECT` in round brackets, used inside another query. What it gives back decides where it can go.

A subquery that gives back one row with one column is a **[[scalar|scalar-word]] subquery**: a single value. It can sit anywhere a single value can, even in the `SELECT` list:

```sql
SELECT name, price,
       price - (SELECT AVG(price) FROM products) AS above_avg
FROM products;
```

The inner query works out the average price, 26.625, once. Then every product is compared with it:

| name | price | above_avg |
| --- | --- | --- |
| Notebook | 4.5 | -22.125 |
| Fountain pen | 32.0 | 5.375 |
| Headphones | 89.0 | 62.375 |

(Five more rows follow, one for each other product.)

### The new shape: a list

A subquery that gives back **one column of many rows** is a list. Run this one on its own first. It gives the customer id of every shipped order:

```sql
SELECT customer_id FROM orders WHERE status = 'shipped';
```

It returns `1`, `1`, `2`, `4`. Customer 1, Ada, shipped two orders, so 1 appears twice.

A list pairs with `IN`. You met `IN ('paid', 'shipped')` in the basics: it means "matches any value in this list". Now the list is a subquery:

```sql
SELECT name FROM customers
WHERE id IN (SELECT customer_id FROM orders WHERE status = 'shipped');
```

| name |
| --- |
| Ada |
| Ben |
| Dev |

For each customer, `IN` asks a yes-or-no question: is this customer's `id` [[on that list|membership]]? Ada's id, 1, is on it, so Ada is in the answer, once. It does not matter that 1 is on the list twice.

### Why not a join?

You could get the same names with a join. But a join multiplies:

```sql
SELECT c.name
FROM customers c
JOIN orders o ON o.customer_id = c.id
WHERE o.status = 'shipped';
```

This gives Ada, Ada, Ben, Dev. A join makes one row per *matching order*, so a customer with two shipped orders [[appears twice|join-fanout]]. You could bolt on `DISTINCT`, which drops repeated rows (the lesson DISTINCT, UNION and UNION ALL covers it), to undo the damage. `IN` never makes the copies in the first place.

### Subqueries inside subqueries

The list can be built from anything: a join, or another subquery. SQL does not mind how deep it goes. Who bought the headphones, product 5?

```sql
SELECT name FROM customers
WHERE id IN (
  SELECT customer_id FROM orders
  WHERE id IN (SELECT order_id FROM order_items WHERE product_id = 5)
);
```

Read it from the inside out. The innermost query finds the orders that contain product 5 (orders 2 and 6). The middle one turns those orders into customer ids (1 and 4). The outer one turns ids into names: Ada and Dev. A query built like this often reads [[close to the question you were asked|real-questions]].

**Watch out:** the list must hold the *same kind* of id as the column you test. `WHERE id IN (SELECT id FROM orders ...)` compares customer ids with **order** ids. SQLite gives no error; it quietly returns the wrong customers. Run the inner query on its own and ask: are these customer ids? A subquery in `IN` must also give back exactly one column. `IN (SELECT * FROM orders)` stops with the error `sub-select returns 5 columns - expected 1`.

You may be wondering about [[the opposite, NOT IN|not-in-later]], for "not on the list". It exists, and it has a trap of its own.

::: context scalar-word Where "scalar" comes from
In maths and physics, a **scalar** is a single number, like a temperature or a mass. It is the opposite of a vector, which has several parts, like a velocity with a direction. The word comes from "scale": a scalar only makes things bigger or smaller. Databases borrowed it for "one single value". A scalar subquery is one that promises one row with one column. If it finds no rows at all, its value is NULL.
:::

::: context membership A list, not a count
`IN` only checks membership: is the value there, yes or no. Duplicates on the list change nothing, and the list's order changes nothing.

::: context join-fanout Rows that multiply
A join pairs each row on the left with every matching row on the right. One customer with two matching orders becomes two rows. This is called **fan-out**, and it is behind many wrong reports: sums counted twice, customers listed twice. The lesson Debugging: the join that double-counts hunts down one of these. Whenever you only want to know *whether* a match exists, not *what* it is, a subquery with `IN` (or `EXISTS`, next lesson) avoids the problem.
:::

::: context real-questions How engineers use it
Mission teams ask questions shaped exactly like this. "Which spacecraft had a critical alert this week?" is: spacecraft whose id is in the list of craft ids from this week's critical alerts. "Which users hit an error today?" is: users whose id is in the list of user ids from today's error log. Inside, databases like PostgreSQL often turn an `IN (subquery)` into a special join, called a semi-join, that stops at the first match. You write the clear version, and the database finds a fast way to run it.
:::

::: context not-in-later The opposite has a trap
`NOT IN` keeps the rows whose value is *not* on the list. It works, until the list contains a NULL. Then it quietly returns no rows at all. The lesson Problem solving: finding what is missing shows why, and gives a safer way to ask.
:::

=== sql2-06 | Correlated subqueries and EXISTS
--- teach
Last lesson a subquery built a list, and `IN` checked each customer against it. That subquery ran once and gave the same list to every row. This lesson meets a subquery that gives a *different* answer for each row, and a new word, `EXISTS`, that asks "is there at least one?".

### The picture

Picture a school where each class has its own average test score. To find the students who beat *their own class's* average, you cannot use one number for everyone. For each student you look up their class, work out that class's average, and compare. The scrap-paper step changes from row to row.

### Averages per category

Products come in three categories, and each has its own average price. You can see them with `GROUP BY`:

```sql
SELECT category, AVG(price) FROM products GROUP BY category;
```

| category | AVG(price) |
| --- | --- |
| electronics | 47.75 |
| home | 21.0 |
| stationery | 18.1666... |

### A subquery that looks at the outer row

Now find each product priced above the average *of its own category*:

```sql
SELECT p.name, p.price
FROM products p
WHERE p.price > (SELECT AVG(x.price) FROM products x WHERE x.category = p.category);
```

| name | price |
| --- | --- |
| Fountain pen | 32.0 |
| Desk lamp | 45.0 |
| Headphones | 89.0 |

The inner query mentions `p.category`, which belongs to the *outer* row. A subquery that reaches out to the outer row like this is a **[[correlated|correlated-word]] subquery**. It runs (in idea, at least) [[once for every outer row|per-row]].

Walk through two rows. For the Fountain pen, `p.category` is `'stationery'`. The inner query averages the stationery prices: 18.17. Is 32 bigger? Yes, so it stays. For the Mug, `p.category` is `'home'`. The home average is 21. Is 9 bigger? No, so it goes.

The two aliases matter. `products` appears twice, once outside as `p` and once inside as `x`. Without [[two different names|alias-clash]], SQL cannot tell the product being tested from the products being averaged.

### EXISTS: is there at least one?

Picture knocking on a door. You only want to know if anyone is home. You do not need to know who, or how many.

`EXISTS (subquery)` is true when the subquery returns **at least one row**. It never looks at *what* is in the rows, so people write [[SELECT 1|select-one]] inside it: the 1 is a placeholder that means "a row, any row".

```sql
SELECT c.name
FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id AND o.status = 'refunded');
```

For each customer, the inner query looks for a refunded order of theirs. Only Eve has one, so the answer is Eve.

`EXISTS` is nearly always correlated: here `o.customer_id = c.id` ties it to the outer customer. And it can stop at the first matching row, which makes it cheap.

### EXISTS as a yes/no column

In SQLite, `EXISTS (...)` is also a value: [[1 for yes, 0 for no|true-is-one]]. So it can go in the `SELECT` list and make a yes/no column:

```sql
SELECT c.name,
       EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id) AS has_orders
FROM customers c;
```

Ada, Ben, Cleo, Dev and Eve get `1`. Finn and Gus have no orders, so they get `0`.

**Watch out:** the link to the outer row is what makes the subquery correlated. Leave out `o.customer_id = c.id` and the inner query no longer asks about *this* customer. It asks "is there a refunded order anywhere?", which is yes, so every customer comes back. When an `EXISTS` returns every row, check the link first.

::: context correlated-word What "correlated" means
To be correlated is to be connected: when one thing changes, the other changes with it. A correlated subquery is connected to the outer query: when the outer row changes, the inner query's answer changes too. The subqueries in the last lesson were not correlated. They could run on their own, pasted into an empty editor. A correlated one cannot, because `p.category` means nothing without an outer `p`. That is a quick test for which kind you have.
:::

::: context per-row Once for every row
In idea, the database runs the inner query again for each outer row, with that row's values filled in.

::: context alias-clash When the names clash
If you write `WHERE category = category` inside the subquery, SQL reads both names as the *inner* table's column, because a plain column name belongs to the nearest `FROM`. Every product equals itself, so the condition is always true and you get the average of all products, not of the category. No error warns you. Giving each copy its own alias, and prefixing every column with it, makes the link impossible to get wrong.
:::

::: context select-one Why SELECT 1
`EXISTS` only counts whether rows come back, and ignores their contents. `SELECT *`, `SELECT o.id` or `SELECT 'hello'` would all give the same answer. Writing `SELECT 1` tells the next person who reads your query: the columns here do not matter. It is a habit, not a rule, and you will see it in almost every codebase that uses `EXISTS`.
:::

::: context true-is-one Yes and no as numbers
SQLite has no separate true/false type. A condition that is true has the value 1, and false has the value 0. You can see it for yourself: `SELECT 5 > 3;` returns 1. That is why `EXISTS` can sit in the `SELECT` list. Its opposite, `NOT EXISTS`, comes back in the lesson Problem solving: finding what is missing, where it is the safest way to find rows with no match.
:::

=== sql2-07 | CASE: decisions inside a query
--- teach
Last lesson `EXISTS` gave you a yes/no column, 1 or 0. This lesson lets you choose *any* value from a condition: a label like `'premium'` or `'budget'`, worked out row by row.

### The picture

Picture a post office sorting parcels. The rule on the wall says: 20 kg or more goes to the heavy shelf; 5 kg or more goes to the medium shelf; everything else goes to the light shelf. The clerk reads the rules top to bottom and stops at the first one that fits.

### The CASE expression

`CASE` does the same inside a query. It checks conditions in order and gives back the value of the first one that is true:

```sql
SELECT name, price,
       CASE
         WHEN price >= 50 THEN 'premium'
         WHEN price >= 10 THEN 'standard'
         ELSE 'budget'
       END AS tier
FROM products;
```

Read each part in words:

- `CASE` starts the decision.
- `WHEN price >= 50 THEN 'premium'` means "if the price is 50 or more, the answer is `'premium'`".
- `ELSE 'budget'` is the answer when no `WHEN` was true.
- `END` closes the decision, and `AS tier` names the new column.

| name | price | tier |
| --- | --- | --- |
| Notebook | 4.5 | budget |
| Fountain pen | 32.0 | standard |
| Headphones | 89.0 | premium |

(Five more products follow.) This form, with a full condition after each `WHEN`, is called the **[[searched|case-names]] CASE**.

### The first true WHEN wins

A price of 89 is `>= 50`, and it is also `>= 10`. Both are true, but `CASE` stops at the first. So order matters: put the [[narrowest condition first|if-else]]. Swap the two `WHEN`s and the headphones become `'standard'`, because `price >= 10` is now checked first.

### Leaving out ELSE

Without an `ELSE`, a row that matches no `WHEN` gets NULL:

```sql
SELECT name, CASE WHEN price >= 50 THEN 'premium' END AS tier
FROM products;
```

Only Headphones gets `'premium'`. The other seven get NULL. That is usually a sign you forgot a case, so write the `ELSE`.

### The short form

When you compare one expression with fixed values, there is a shorter form. The expression goes straight after `CASE`, and each `WHEN` holds a value to compare it with:

```sql
SELECT id, status,
       CASE status WHEN 'paid' THEN 'open' WHEN 'shipped' THEN 'done' ELSE 'closed' END AS stage
FROM orders;
```

Orders 5 and 8 are `'open'`, the shipped orders are `'done'`, and the cancelled and refunded ones fall through to `'closed'`. The short form has [[one trap with NULL|case-null]].

### CASE on a group

`CASE` works anywhere an expression does: in `SELECT`, in `ORDER BY`, even inside `SUM(...)`. In a grouped query it can test an aggregate:

```sql
SELECT customer_id, COUNT(*) AS orders,
       CASE WHEN COUNT(*) >= 2 THEN 'regular' ELSE 'new' END AS kind
FROM orders
GROUP BY customer_id;
```

Customers 1 and 2 have 3 and 2 orders, so they are `'regular'`. The other three are `'new'`. Put `CASE` inside `SUM` and you can [[count only some rows|conditional-sum]].

### Edges on purpose

Bugs live on the edges. "Orders of 25 or more are medium" means `>= 25`. An order of exactly 25.00 must land in medium. Decide each [[edge|half-open]] on purpose, then find a row that sits on it and check where it lands.

**Watch out:** `>` and `>=` differ only on the edge, so a wrong one passes almost every test. `WHEN total > 25` sends an order of exactly 25.00 to the wrong bucket, and nothing warns you. Read the rule aloud: "25 or more" is `>= 25`; "more than 25" is `> 25`.

::: context case-names Searched and simple
The SQL standard names the two forms. The **searched** CASE has a full condition after each `WHEN`, so it can test anything: `price >= 50`, `city IS NULL`, `EXISTS (...)`. The **simple** CASE (the short form) names one expression after `CASE` and compares it with a value in each `WHEN`, using `=`. Every simple CASE can be written as a searched one, but not the other way round. When unsure, use the searched form.
:::

::: context if-else Like if, else if, else
If you have written Python or JavaScript, `CASE` is an `if`, `else if`, `else` chain. There is one difference. In those languages an `if` is a statement: it *does* things. `CASE` is an expression: it *is* a value, like `2 + 3` is a value. That is why it can sit inside `SELECT`, `ORDER BY` or `SUM(...)`. The rule "narrowest first" is the same in every language: `if score >= 50` before `if score >= 10`, or the second test swallows everything.
:::

::: context case-null The short form and NULL
The short form compares with `=`, and `NULL = NULL` is not true. So `CASE coupon WHEN NULL THEN 'none' ELSE coupon END` never gives `'none'`: for an order with no coupon, it falls through to `ELSE coupon`, which is NULL. Use the searched form for NULLs: `CASE WHEN coupon IS NULL THEN 'none' ELSE coupon END`. The lesson Debugging: the rows NULL made disappear digs into why NULL behaves this way.
:::

::: context conditional-sum Counting some rows
`SUM(CASE WHEN status = 'shipped' THEN 1 ELSE 0 END)` adds 1 for every shipped order and 0 for the rest. On this shop it gives 4. With one such column per status, a single query makes a whole summary row: shipped, paid, cancelled, refunded side by side. Reports and dashboards are full of this pattern; people call it **conditional aggregation**. Engineers use it the same way, for example to count how many telemetry readings in each pass were in the warning range.
:::

::: context half-open Buckets without gaps
The task's sizes are buckets on a number line. Each one includes its lower edge and stops right before the next one.

=== sql2-08 | Working with text
--- teach
Last lesson `CASE` turned numbers into labels. This lesson works on text itself. Real text is messy, with capitals, stray spaces and missing values, and a report on messy text quietly comes out wrong. Here you learn to clean text and cut pieces out of it.

### The picture

Picture a sign-up sheet where people wrote their own email addresses. One wrote in capitals. One left a space before it. One left it blank. Before you can count how many use each email provider, you tidy every line the same way.

### Text functions

A piece of text is called a **[[string|string-word]]**. A **function** is a named tool: you give it values in brackets and it gives one value back. You have used `COUNT`, `ROUND` and `substr` already. SQLite has a set of functions for strings. Here they are one at a time.

### lower and upper: change case

`lower(s)` gives the string `s` in small letters, and `upper(s)` in capitals. In SQLite they change [[only the plain letters A to Z|sqlite-ascii]]:

```sql
SELECT email, lower(email) FROM customers WHERE id = 2;
```

| email | lower(email) |
| --- | --- |
| BEN@Mail.com | ben@mail.com |

### trim: remove spaces at the ends

`trim(s)` removes spaces from both ends of a string. `ltrim` removes them from the left end only, and `rtrim` from the right end only:

```sql
SELECT trim('  hi  '), ltrim('  hi  '), rtrim('  hi  ');
```

This gives `'hi'`, `'hi  '` and `'  hi'`.

### length: count the characters

`length(s)` counts the characters in `s`. Spaces count. That makes it a good way to *see* [[invisible spaces|stray-spaces]]:

```sql
SELECT email, length(email), length(trim(email)) FROM customers WHERE id IN (4, 6);
```

| email | length(email) | length(trim(email)) |
| --- | --- | --- |
|  dev@work.io | 12 | 11 |
| finn@Work.io  | 13 | 12 |

Dev's email has a space at the front and Finn's has one at the end. You cannot see them in the table, but `length` can.

### substr: cut out a piece

You met `substr(s, start, n)` when you grouped by month. It gives the piece of `s` that begins at position `start` and is `n` characters long. Positions [[count from 1|count-from-one]]. Leave out `n` and you get everything to the end:

```sql
SELECT substr('2024-03-20', 6, 2), substr('ada@mail.com', 5);
```

This gives `'03'` and `'mail.com'`.

### instr: find where something is

`instr(s, t)` gives the position where `t` first appears in `s`, or 0 if it does not appear at all. `instr('ada@mail.com', '@')` is 4, because `@` is the fourth character.

### Putting them together

Functions can go inside each other. The innermost one runs first. Here is everything after the `@` in each email:

```sql
SELECT email, substr(email, instr(email, '@') + 1) AS domain FROM customers;
```

For `'ada@mail.com'`, `instr` finds the `@` at position 4. Adding 1 gives 5. `substr` from position 5 to the end gives `'mail.com'`. That part after the `@` is called the **domain**.

### Clean before you compare or group

To `GROUP BY`, `'Mail.com'`, `'mail.com'` and `'Work.io '` (with a space) are all different strings. Group the raw domains and you get six groups, where there should be three providers:

| domain | COUNT(*) |
| --- | --- |
| NULL | 1 |
| Mail.com | 1 |
| Work.io  | 1 |
| mail.com | 2 |
| post.org | 1 |
| work.io | 1 |

A report grouped on raw text quietly splits one bucket into several. **Normalise** first, which means making every value follow the same form: wrap it in `lower(trim(...))`.

### NULL goes in, NULL comes out

Look at that first group, NULL. Cleo has no email, and every text function given NULL [[gives back NULL|null-in-null-out]]. A missing email has no domain, so it makes a NULL group of its own. Filter it out with `WHERE email IS NOT NULL`.

**Watch out:** clean the value in the same expression you group by. Writing `lower(...)` in the `SELECT` but grouping on the raw `email` still makes the split groups. Here, giving the cleaned expression a name with `AS domain` and then writing `GROUP BY domain` keeps the two the same.

::: context string-word Why text is a "string"
Programmers call text a string because it is a string of characters, one after another, like beads on a thread. A character is one letter, digit, space or symbol. The word is used in nearly every programming language: Python's `str`, JavaScript's `String`. In SQL you write a string between single quotes, `'like this'`. The quotes are not part of the string; they only show where it starts and ends.
:::

::: context sqlite-ascii Only plain letters change case
In SQLite, `lower` and `upper` only change the 26 plain English letters, A to Z. Accented letters are left alone: `lower('ÉCOLE')` gives `'École'`. Other databases, like PostgreSQL, handle every alphabet. For email addresses this rarely matters. For people's names, like "Óscar" or "Zoë", it does, and it is worth knowing before you trust a cleaned column.
:::

::: context stray-spaces Where stray spaces come from
Most stray spaces arrive by copy and paste: someone copies an address from an email and picks up a space at the end. Phones add them too, after an autocomplete. People cannot see them, but a computer compares every character, so `'finn@work.io'` and `'finn@work.io '` are different. That is why careful apps trim and lower-case an email when the user signs up, before storing it. Cleaning at the door is cheaper than cleaning every report afterwards.
:::

::: context count-from-one Counting from 1
SQL counts positions in a string from 1: the first character is at position 1. Python and JavaScript count from 0, so the same first character is at index 0 there. Moving between languages, this is an easy slip that shifts every piece by one. In SQLite, `substr('ada', 1, 1)` is `'a'`. In Python, `'ada'[0]` is `'a'`.
:::

::: context null-in-null-out NULL passes through
NULL means "no value known". Ask for the lower-case version of an unknown value, and the honest answer is still unknown. So `lower(NULL)`, `trim(NULL)`, `length(NULL)` and `substr(NULL, 1, 3)` all give NULL. The same rule holds for arithmetic: `NULL + 1` is NULL. It spreads quietly through a long expression, so one missing value can blank out a whole column. The lesson Debugging: the rows NULL made disappear shows how to catch and replace it.
:::

=== sql2-08b | Building text: joining, replacing and LIKE
--- teach
Last lesson you cleaned text and cut pieces out of it. This lesson goes the other way: gluing strings together and swapping one piece for another. It ends with how SQLite compares text, where `=` and `LIKE` do not agree about capitals.

### The picture

Picture filling in name badges: "Hello, my name is ____". The words on the badge are the same every time. Only the name changes. SQL can build text the same way, row by row, from fixed words and column values.

### || joins strings

Two bars, `||`, join two strings into one. Joining strings end to end is called **[[concatenation|concat-word]]**:

```sql
SELECT name || ' from ' || city AS badge FROM customers;
```

| badge |
| --- |
| Ada from London |
| Ben from Paris |
| NULL |
| Dev from London |

Notice the spaces inside `' from '`. `||` adds nothing of its own, so without them you would get `AdafromLondon`.

The third row is Cleo, who has no city. A NULL anywhere in `||` [[makes the whole result NULL|concat-null]], the same as it did with the text functions.

### replace swaps pieces

`replace(s, a, b)` gives `s` with every `a` replaced by `b`:

```sql
SELECT replace('2024-03-20', '-', '/');
```

This gives `'2024/03/20'`: both dashes changed. If `a` does not appear, the string comes back unchanged.

### Functions and || together

You can mix them. The cleaned email of each customer, in angle brackets after the name, the way email programs show it:

```sql
SELECT name || ' <' || lower(trim(email)) || '>' AS sender
FROM customers WHERE email IS NOT NULL;
```

Ben's row becomes `Ben <ben@mail.com>`.

### = and LIKE disagree about capitals

`=` compares strings exactly, character by character. Capitals count:

```sql
SELECT name FROM customers WHERE email = 'BEN@MAIL.COM';
```

This finds nobody, because Ben's email is stored as `'BEN@Mail.com'`.

`LIKE` compares with a pattern. You met it in the basics, where `%` means "any run of characters". In SQLite, `LIKE` also [[ignores case for plain letters|like-case]]:

```sql
SELECT name FROM customers WHERE email LIKE 'BEN@MAIL.COM';
```

This finds Ben. With a `%`, `WHERE email LIKE '%@work.io%'` finds Dev and Finn, even with Finn's capital W and trailing space.

So the two can give different answers on the same data. If you mean "equal, ignoring case", say so: `lower(email) = 'ben@mail.com'` works in every database.

**Watch out:** one NULL in a chain of `||` blanks the whole result, with no error. Before you build text from a column, ask whether that column can be NULL. Filter those rows out with `IS NOT NULL`, or give the NULL a stand-in value, which the lesson Debugging: the rows NULL made disappear shows with `COALESCE`.

In the task you put `||` and `replace` together to write email addresses in a form [[that hides them from spam robots|hide-from-bots]].

::: context concat-word What "concatenation" means
The word comes from Latin: *con*, "together", and *catena*, "chain". Concatenating is chaining strings together, end to end. Many databases also have a function for it, `concat(a, b, ...)`, and SQLite added one in version 3.44 (2023). The two differ on NULL: `concat` skips a NULL as if it were empty text, while `||` makes the whole result NULL. The bars `||` are the SQL standard's way, so you will see them everywhere.
:::

::: context concat-null How one NULL blanks the badge
`||` works through the chain from left to right. Once a NULL joins in, every later step stays NULL.

::: context like-case Why LIKE ignores case
SQLite's `LIKE` ignores the difference between capital and small letters, but only for the 26 plain English letters. So `'x' LIKE 'X'` is true, while `'é' LIKE 'É'` is false. Other databases differ: in PostgreSQL, `LIKE` is case-sensitive, and it has a separate `ILIKE` for ignoring case. Because the behaviour depends on the database, `lower(...)` on both sides is the safe habit. One more pattern symbol: `_` in a `LIKE` pattern means "exactly one character", so `'abc' LIKE 'a_c'` is true.
:::

Web pages sometimes write email addresses as `ada at mail.com` instead of `ada@mail.com`. Programs that crawl the web collecting addresses for spam look for the `@`, so swapping it for `' at '` hides the address from the simplest of them, while a person can still read it. It is a small defence, not a strong one, but it is a neat example of `replace`, and it is exactly what the task builds.
:::

=== sql2-09 | Dates and times
--- teach
Last lesson, in Working with text, you cleaned up messy email addresses with `lower`, `trim` and `substr`. Now you meet the other kind of value almost every table has: dates and times. By the end of this lesson you will build a monthly sales report, with one row per month.

Think of a pile of forms, each dated in the corner. If everyone writes the year first, then the month, then the day, always with two digits (2024-03-20), you can sort the pile alphabetically and it comes out in time order too.

**Step 1: dates are stored as text.** SQLite has no separate date type. A date is stored as text in **[[ISO format|iso-8601]]**: the year, the month and the day, biggest part first, joined by dashes. A time can follow after a space, as hours:minutes:seconds on a 24-hour clock, so `18:40:00` is twenty to seven in the evening. Look at the `placed` column of `orders`:

```sql
SELECT id, placed FROM orders;
```

| id | placed |
| --- | --- |
| 1 | 2024-03-02 10:15:00 |
| 2 | 2024-03-20 18:40:00 |
| 3 | 2024-03-21 09:05:00 |
| … | … |

Because the biggest part comes first and every part has a [[fixed width|fixed-width]], sorting this text A to Z also sorts it oldest to newest. `ORDER BY placed` works with no extra help.

**Step 2: `strftime` pulls out pieces.** `strftime(format, time)` (say it "[[string-format-time|strftime-name]]") takes a time and writes it out in the shape you ask for. The format is text with **placeholders**: a `%` sign followed by a letter, each standing for one piece of the date.

| Placeholder | Means | For `'2024-03-20 18:40:00'` |
| --- | --- | --- |
| `%Y` | the year, 4 digits | 2024 |
| `%m` | the month, 2 digits | 03 |
| `%d` | the day of the month | 20 |
| `%H` | the hour, 00 to 23 | 18 |
| `%W` | the week of the year | 12 |
| `%w` | the weekday, 0 is Sunday | 3 (a Wednesday) |

Anything in the format that is not a placeholder is copied as it is, like the dash here. (Everything after `--` on a line is a **comment**: a note for people, which the database ignores. Here it shows the answer.)

```sql
SELECT strftime('%Y-%m', '2024-03-20 18:40:00');   -- '2024-03'
```

**Step 3: group by the month.** For a monthly report, give `GROUP BY` that expression. Every timestamp in March turns into the same text, `'2024-03'`, so all of March lands in one bucket. It is the same trick as grouping by `substr(placed, 1, 7)` in GROUP BY in depth. SQLite lets you group by [[the name you gave with AS|group-by-alias]]:

```sql
SELECT strftime('%Y-%m', placed) AS month, COUNT(*) AS orders
FROM orders
GROUP BY month;
```

| month | orders |
| --- | --- |
| 2024-03 | 3 |
| 2024-04 | 2 |
| 2024-05 | 2 |
| 2024-06 | 1 |

**Step 4: the join trap comes back.** Money lives in `order_items`, one row per item. Once you join `orders` to `order_items`, there is one row per *item*, so `COUNT(*)` counts items, not orders. `COUNT(DISTINCT o.id)` counts the *different* order ids instead. In March, order 1 has two items, so:

```sql
SELECT COUNT(*) AS item_rows, COUNT(DISTINCT o.id) AS orders
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
WHERE strftime('%Y-%m', o.placed) = '2024-03';
```

| item_rows | orders |
| --- | --- |
| 4 | 3 |

This is how engineers build any [[report by time|time-buckets]]: turn each timestamp into its bucket, group, and count the right thing.

**Watch out:** grouping by `placed` itself makes one group per exact second, so almost every order sits alone in its own group. Group by `strftime('%Y-%m', placed)` to get months.

::: context iso-8601 A worldwide way to write dates
ISO format is short for ISO 8601, an international standard for writing dates and times, first published in 1988. It fixes the order as year, month, day, from biggest unit to smallest, so 2024-03-02 can only mean 2 March 2024. That matters because 03/02/2024 means 2 March in Britain and 3 February in the United States. Flight software, mission logs and the web all use ISO 8601 for this reason: when a timestamp crosses from one team, country or program to another, nobody has to guess.
:::

::: context fixed-width Why the zeros matter
Text is sorted one character at a time, from the left, the way a dictionary is. That only matches time order if every date has the same shape. Write September as `9` instead of `09` and it goes wrong: `'2024-10-01'` sorts before `'2024-9-30'`, because at the sixth character `1` comes before `9`. You can check it: `SELECT '2024-10-01' < '2024-9-30';` returns 1, meaning true. The leading zeros in `2024-09-30` keep every part the same width, so the comparison is always fair.
:::

::: context strftime-name An old name that stuck
`strftime` is short for "string format time". The name, and the `%` codes, come from the C programming language's standard library, where a function called `strftime` has formatted dates since the 1980s. Many languages copied it, so the same codes work far beyond SQLite: Python's `datetime` objects have a `strftime` method that understands `%Y`, `%m` and `%d` in the same way. Learn the codes once and you can read date formats in a lot of code.
:::

::: context group-by-alias Naming a group once
In SQLite you can write `GROUP BY month` after `AS month` in the `SELECT`, instead of repeating the whole `strftime('%Y-%m', placed)`. PostgreSQL and MySQL allow this too. Some databases do not: Microsoft SQL Server wants the full expression repeated in `GROUP BY`. If a query that works in SQLite fails somewhere else with "invalid column name", this is a likely reason. Repeating the expression always works everywhere.
:::

::: context time-buckets Buckets of time
A spacecraft's computer might log a temperature reading every second. Nobody reads millions of rows one by one, so engineers group them into buckets (per minute, per hour, per orbit) and look at the count, average or maximum in each bucket. The pattern is the one in this lesson: turn each timestamp into its bucket, then group. `strftime('%Y-%m-%d %H', t)` makes hourly buckets.

=== sql2-09b | Date arithmetic and date ranges
--- teach
Last lesson you pulled the month out of a timestamp with `strftime` and grouped orders by it. This lesson does arithmetic with dates: moving a date forward or back, counting the days between two dates, and picking out every row inside a range of dates.

Think of a wall calendar. You can put your finger on the 20th and count ten days forward, or jump back to the 1st of the month. SQLite's date functions do the same moves for you, and they know how long every month is.

**Step 1: `date()` keeps the date part.** Given a timestamp, `date(...)` returns only the year-month-day. A `SELECT` with no `FROM` works out its values once and returns one row, which is a handy way to try a function:

```sql
SELECT date('2024-03-20 18:40:00');   -- '2024-03-20'
```

**Step 2: modifiers move the date.** Any extra text you pass after the time is a **modifier**: an instruction that moves the date before it is returned.

```sql
SELECT date('2024-03-20', '+10 days');        -- '2024-03-30'
SELECT date('2024-03-20', '-1 day');          -- '2024-03-19'
SELECT date('2024-03-20', 'start of month');  -- '2024-03-01'
```

**Step 3: months are uneven.** `'+1 month'` adds one to the month number and keeps the day. When that day does not exist, SQLite [[rolls over into the next month|month-rollover]]:

```sql
SELECT date('2024-01-31', '+1 month');   -- '2024-03-02' (no 31 February!)
```

31 February would be two days after 29 February (2024 is a leap year), so you land on 2 March.

**Step 4: the days between two dates.** `julianday(time)` turns a date into one plain number: a count of days since a [[starting point long ago|julian-day]]. Subtract two of them and you get the days in between:

```sql
SELECT julianday('2024-03-20') - julianday('2024-03-02');   -- 18.0
```

The answer has a decimal point because times of day become fractions of a day: 18:00 is three quarters of the way through a day, so it adds 0.75.

**Step 5: today.** `date('now')` is [[today's date|now-is-utc]]. Its answer changes every day, so it is great in an app and useless in a check with a fixed answer.

**Step 6: a range of dates.** To pick every order placed in April, compare the text directly. `>=` means "greater than or equal to" and `<` means "less than":

```sql
SELECT id, placed FROM orders
WHERE placed >= '2024-04-01' AND placed < '2024-05-01';
```

| id | placed |
| --- | --- |
| 4 | 2024-04-07 14:30:00 |
| 5 | 2024-04-07 20:10:00 |

This works because ISO text sorts in time order. Read it as "from the first moment of April, up to but not including the first moment of May". It is also faster on big tables than wrapping the column in a function such as `strftime('%Y-%m', placed) = '2024-04'`, because the database can use an [[index|index-preview]] for it.

**Watch out:** `placed <= '2024-04-30'` looks like "up to the end of April", but it misses every order placed *during* 30 April. As text, `'2024-04-30 18:00:00'` is longer than `'2024-04-30'` and starts the same, so it sorts after it. End a range with `<` and the first moment you do *not* want, `'2024-05-01'`, as a [[half-open range|half-open]].

::: context month-rollover Why dates roll over
SQLite handles `'+1 month'` in two moves: add one to the month number, then fix any day that does not exist by counting on into the next month. From 31 January 2024 that gives "31 February", which is two days past 29 February, so 2 March. In 2023, which was not a leap year, the same step from 31 January lands on 3 March: `SELECT date('2023-01-31', '+1 month');` returns `'2023-03-03'`. For "the last day of this month" use `date(x, 'start of month', '+1 month', '-1 day')`, which never overflows.
:::

::: context julian-day Days counted from long ago
A Julian day number counts days from noon on 1 January 4713 BC, a starting point astronomers chose centuries ago so that every recorded event gets a positive number. Astronomers still use it to time observations, because subtracting two numbers is easier than juggling months and leap years. `SELECT julianday('2024-03-20');` returns 2460389.5. The .5 is there because Julian days begin at noon, so midnight falls halfway through one.
:::

::: context now-is-utc Whose today?
`date('now')` uses UTC, the world's reference clock (the time in London outside summer time). If you are in California late in the evening, it may already be tomorrow in UTC. Mission control centres and servers usually store every timestamp in UTC for this reason, so that events from different places line up, and only convert to local time when they show a time to a person. SQLite can do that too, with the `'localtime'` modifier.
:::

::: context index-preview A shortcut through a big table
An **index** is like the index at the back of a book: a separate, sorted list that tells the database where to find rows with a given value, so it can jump straight to them instead of reading every row. A sorted list of `placed` values lets it jump to the first April order and stop at the first May one. If you wrap the column in a function, the sorted list no longer matches what you are asking about, so it reads every row. You will build indexes and watch this happen in the advanced course.
:::

::: context half-open Include the start, exclude the end
A range that includes its start but not its end is called half-open. Written this way, April and May meet without a gap or an overlap: April ends exactly where May begins, so every moment belongs to one month only. The same habit shows up in programming, where a loop over 0 up to (not including) 10 runs ten times.

=== sql2-10 | Debugging: the rows NULL made disappear
--- teach
Last lesson you picked out a range of dates. This lesson is a debugging case: a query that returns too few rows, and the cause is NULL. You will see how `WHERE` really treats NULL, how to fix the filter, and two functions, `COALESCE` and `NULLIF`, that turn missing values into readable labels.

A quick reminder from LEFT JOIN and NULL: **NULL** means "no value here". The box on the form was left empty. It is not zero, and it is not an empty piece of text. In `orders`, the `coupon` column is NULL for orders where no coupon was used.

**The bug report.** Marketing asked for every order that did **not** use the `SPRING10` coupon, with a readable label for the coupon. This query came back with only two orders. (`!=` means "not equal to", and `<>` [[means the same thing|not-equal-signs]].)

```sql
SELECT id, coupon AS coupon_label
FROM orders
WHERE coupon != 'SPRING10'
ORDER BY id;
```

| id | coupon_label |
| --- | --- |
| 4 | WELCOME5 |
| 7 | (blank) |

There are eight orders and two used `SPRING10`, so six were expected. Here is a [[way to debug|debug-by-counting]] any query that returns too few rows.

**Step 1: reproduce and count.** Count what should be there:

```sql
SELECT COUNT(*) FROM orders;   -- 8
```

8 − 2 = 6 were expected and 2 came back, so four orders went missing.

**Step 2: look at what went missing.**

```sql
SELECT id, coupon FROM orders;
```

| id | coupon |
| --- | --- |
| 1 | NULL |
| 2 | SPRING10 |
| 3 | NULL |
| 4 | WELCOME5 |
| 5 | SPRING10 |
| 6 | NULL |
| 7 | (empty text) |
| 8 | NULL |

The missing orders are 1, 3, 6 and 8, and every one has `coupon` = NULL.

**Step 3: check your assumption.** The query assumes `coupon != 'SPRING10'` is true when there is no coupon. Picture a clerk asked "is the coupon on this form something other than SPRING10?" when the coupon box is empty. The honest answer is "I don't know, nothing was written". SQL answers the same way.

This is **[[three-valued logic|three-valued]]**: in SQL a comparison can be true, false, or **unknown**. Any comparison with NULL is unknown: `NULL = 'x'`, `NULL != 'x'`, even `NULL = NULL`. SQLite shows unknown as NULL:

```sql
SELECT NULL = NULL, NULL != 'x';   -- NULL, NULL
```

And `WHERE` keeps a row only when its condition is **true**. Unknown is thrown away exactly like false. So `coupon != 'SPRING10'` silently drops every order with no coupon. Adding `NOT` does not rescue it: `NOT (coupon = 'SPRING10')` is still unknown for those rows, because "not unknown" is still unknown.

**Step 4: fix the filter.** Here are three fixes, the most explicit first:

```sql
WHERE coupon IS NULL OR coupon <> 'SPRING10'
WHERE coupon IS NOT 'SPRING10'        -- SQLite: IS / IS NOT treat NULL as a value
WHERE COALESCE(coupon, '') <> 'SPRING10'
```

- The first says it out loud: keep the row if there is no coupon, or if the coupon is something else. `IS NULL` is always true or false, never unknown.
- The second uses a SQLite shortcut. `IS` and `IS NOT` can compare with any value, and they treat NULL as an ordinary value, so an empty coupon "is not" SPRING10. Other databases spell this [[IS DISTINCT FROM|is-distinct-from]].
- The third uses `COALESCE`, the next step.

**Step 5: `COALESCE` fills a gap.** `COALESCE(a, b, …)` returns the first of its values that is not NULL. You met it as `COALESCE(x, 0)`. It also makes labels:

```sql
SELECT id, COALESCE(coupon, 'none') AS coupon_label FROM orders;
```

Orders 1, 3, 6 and 8 now say `none`. Order 7 still shows a blank.

**Step 6: the empty string.** Order 7's coupon is `''`, the **[[empty string|empty-string]]**: text with no characters in it. That is not NULL. Something was written, it is only empty. So `COALESCE` leaves it alone. `NULLIF(x, y)` gives NULL when `x` equals `y`, and `x` otherwise, so `NULLIF(coupon, '')` turns `''` into NULL. Put `trim` inside so a coupon made only of spaces counts as blank too:

```sql
COALESCE(NULLIF(trim(coupon), ''), 'none')
```

Read it from the inside out: trim the spaces; if what is left is `''`, make it NULL; if it is NULL, use `'none'`.

| coupon | trim, then NULLIF | label |
| --- | --- | --- |
| WELCOME5 | WELCOME5 | WELCOME5 |
| NULL | NULL | none |
| (empty text) | NULL | none |

**Watch out:** `!=` or `<>` on a column that can be NULL quietly drops the NULL rows. Whenever a column may be NULL, ask "what should happen to rows with no value?" and write the answer into the `WHERE`.

::: context not-equal-signs Two ways to write "not equal"
`<>` is the "not equal" sign in the SQL standard: read it as "less than or greater than", which is another way of saying "different". `!=` comes from programming languages like C, Python and JavaScript. SQLite, PostgreSQL, MySQL and most other databases accept both, and they behave the same way, including with NULL. Pick one and use it consistently in a project.
:::

::: context debug-by-counting Count before you guess
When a result looks wrong, the fastest path is rarely staring at the query. Work out how many rows there *should* be, count how many you got, then look at exactly the rows that went missing and ask what they have in common. Here every missing row had the same thing: an empty coupon. Engineers checking flight telemetry do the same: if a downlink should hold 600 frames and the database has 590, the first job is to find the ten missing frames, not to rewrite the code.
:::

::: context three-valued True, false and unknown
Ordinary logic has two values. SQL adds a third, unknown, so that a missing value never pretends to be known. `AND` and `OR` still give a sure answer when they can: false `AND` anything is false, and true `OR` anything is true. `SELECT NULL OR 1;` returns 1 and `SELECT NULL AND 0;` returns 0. Otherwise unknown spreads. Orange cells are unknown.

=== sql2-11 | DISTINCT, UNION and UNION ALL
--- teach
Last lesson you made NULL and blank coupons behave. This lesson is about duplicates: how to remove repeated rows from a result, and how to stack two results into one list. By the end you will build one mailing list from two tables.

Picture two guest lists for a party, one from you and one from a friend. You want a single list with everybody on it, and every name only once.

**Step 1: `DISTINCT` removes repeats.** `SELECT DISTINCT` returns each different row once. `DISTINCT` means "different".

```sql
SELECT city FROM customers;            -- 7 rows
SELECT DISTINCT city FROM customers;   -- 4 rows
```

| city (DISTINCT) |
| --- |
| London |
| Paris |
| NULL |
| Berlin |

London, Paris and NULL each appeared twice. Notice that the two [[NULLs count as one|nulls-in-distinct]].

**Step 2: `DISTINCT` looks at whole rows.** A row is a duplicate only when *every* selected column matches, not only the first:

```sql
SELECT DISTINCT city, referred_by FROM customers;   -- 7 rows
```

Ada is London with no referrer, and Dev is London referred by customer 2. Those are different pairs, so both stay. In fact all seven pairs differ, so nothing is removed.

**Step 3: `UNION ALL` stacks two results.** `UNION ALL` puts the rows of a second `SELECT` underneath the rows of the first. The two `SELECT`s must return the [[same number of columns|same-shape]], and the column names come from the first one.

```sql
SELECT email FROM customers
UNION ALL
SELECT email FROM newsletter;
```

This returns 12 rows: 7 from `customers` (Cleo's NULL email included) and then 5 from `newsletter`. `ada@mail.com` is on both lists, so it appears twice.

**Step 4: `UNION` stacks and removes repeats.** Leave out the `ALL` and `UNION` removes duplicate rows from the combined result, including duplicates that were both on the *same* side. The same query with `UNION` returns 11 rows, with `ada@mail.com` once.

Which to use? `UNION ALL` keeps every row, and it is [[cheaper|union-cost]] because it never checks for repeats. It is the right choice when you want to count everything, or when you know the parts cannot overlap. Use `UNION` when repeats should go.

**Step 5: one `ORDER BY`, at the very end.** An `ORDER BY` after the last `SELECT` sorts the whole combined result. It uses the column names from the first `SELECT`:

```sql
SELECT email FROM customers
UNION
SELECT email FROM newsletter
ORDER BY email;
```

**Step 6: repeats must match exactly.** `DISTINCT` and `UNION` compare values character by character. `'BEN@Mail.com'` and `'ben@mail.com'` are different strings, and so are `'Zoe@mail.com '` (with a space at the end) and `'zoe@mail.com'`. Neither will be merged. When you mean "the [[same address|email-case]]", clean each side first with `lower(trim(email))` from Working with text, so the union compares tidy values.

**Watch out:** each `SELECT` in a union is separate. A `lower(trim(...))` or a `WHERE` written on the first `SELECT` does nothing to the second, so clean both sides.

`UNION` also has [[two relatives|set-operations]], `INTERSECT` and `EXCEPT`, which combine whole results in other ways.

::: context nulls-in-distinct NULL meets NULL
Last lesson said `NULL = NULL` is unknown, not true. Yet `DISTINCT` keeps only one NULL city. That is on purpose: for removing duplicates, the SQL standard says two NULLs are "not distinct" from each other, so they count as the same. `GROUP BY` does the same thing, which is why all the NULLs landed in one group in GROUP BY in depth, and `UNION` does too. So the rule has two halves: comparisons with `=` treat NULL as unknown, while `DISTINCT`, `GROUP BY` and `UNION` treat NULLs as one value.
:::

::: context same-shape When the columns do not line up
If the two sides have different numbers of columns, SQLite refuses to run the query and tells you why: "SELECTs to the left and right of UNION ALL do not have the same number of result columns". The column *names* on the second side do not matter, only how many there are and their order. So `SELECT name FROM products UNION ALL SELECT email FROM newsletter` runs happily and mixes product names with email addresses in one column. SQL trusts you to line up columns that mean the same thing.
:::

::: context union-cost Why removing repeats costs more
To find duplicates, the database has to compare every row with the others. In practice it sorts all the rows or builds a lookup table of them, then drops the repeats. `UNION ALL` skips that work and passes the rows straight through. On a few rows the difference is invisible. On millions of log rows from a fleet of satellites it can be the difference between a quick query and a slow one.

Strictly, the rules for email say the part before the `@` could be case-sensitive, so `BEN@` and `ben@` might be two mailboxes. You will see `EXCEPT` again in the advanced course, checking that a redesigned set of tables still holds exactly the same data as the old one.

=== sql2-12 | Pagination with LIMIT and OFFSET
--- teach
Last lesson you built one long mailing list. Long lists are where this lesson comes in: apps show them a page at a time. You will fetch any page with `LIMIT` and `OFFSET`, learn why the sort needs a tie-breaker, and meet a faster way to reach deep pages.

Think of search results: the first page shows results 1 to 10, and "next" shows 11 to 20. Splitting a long list into pages like this is called **[[pagination|pagination-apis]]**.

**Step 1: `OFFSET` skips rows.** You know `LIMIT n` keeps the first `n` rows. `OFFSET k` skips `k` rows first. Together, `LIMIT n OFFSET k` means "skip `k` rows, then return the next `n`". Here are all eight products, most expensive first:

| position | name | price |
| --- | --- | --- |
| 1 | Headphones | 89.00 |
| 2 | Desk lamp | 45.00 |
| 3 | Fountain pen | 32.00 |
| 4 | Planner | 18.00 |
| 5 | Bookends | 9.00 |
| 6 | Mug | 9.00 |
| 7 | USB cable | 6.50 |
| 8 | Notebook | 4.50 |

With 3 products per page, page 1 is positions 1 to 3, page 2 is 4 to 6, page 3 is 7 and 8. To reach page `p`, skip the pages before it: skip (`p` − 1) × 3 rows. Page 3 skips (3 − 1) × 3 = 6 rows:

```sql
SELECT name, price FROM products
ORDER BY price DESC, name
LIMIT 3 OFFSET 6;   -- page 3: USB cable, Notebook
```

Page 3 has only two rows. The last page is often short, and that is fine.

**Step 2: the tie-breaker.** Bookends and Mug both cost 9.00. `ORDER BY price DESC` on its own does not say which comes first, so the database [[may choose differently from one query to the next|tie-order]]. With pages of 5, Mug could be position 5 when page 1 is fetched and Bookends position 5 when page 2 is fetched. Then Bookends appears on no page, and Mug on both.

The fix is a **tie-breaker**: one more column at the end of the `ORDER BY` that settles every tie. `ORDER BY price DESC, name` means "by price, high to low, and where prices are equal, by name A to Z". Always end the `ORDER BY` with something unique, such as the name here or the `id` in general, so the order is fully decided.

**Step 3: `OFFSET` has a cost.** To skip 10,000 rows, the database still has to find those 10,000 rows in order and throw them away. It is like reaching page 500 of a book by counting pages from the start, instead of opening it at a bookmark.

**Step 4: keyset pagination.** The bookmark version is **[[keyset pagination|keyset-apis]]**: remember the last row you showed, and ask for the rows that come after it. Say the last row on page 2 was `('Mug', 9.0)`. In the order "price high to low, then name A to Z", a row comes after Mug if it is cheaper, or if it costs the same and its name comes [[later in the alphabet|text-order]]:

```sql
SELECT name, price FROM products
WHERE price < 9.0 OR (price = 9.0 AND name > 'Mug')
ORDER BY price DESC, name
LIMIT 3;
```

The brackets keep the "same price and later name" parts together. The result is USB cable and Notebook, the same as page 3 above, with nothing skipped. Keyset pagination also stays correct when rows are added while someone is paging. With `OFFSET`, a new expensive product pushes every row down one place, so the reader sees one product twice.

**Watch out:** `OFFSET` counts rows, not pages. Page 2 of 3 per page is `OFFSET 3`, not `OFFSET 2`. And without a tie-breaker, products with equal prices can repeat or vanish between pages.

::: context pagination-apis Pages in real apps
Almost every app that shows a list pages it, because sending ten thousand rows to a phone at once is slow and wasteful. Web services usually let the app ask for a page size. GitHub's public API, for example, takes a `per_page` setting, 30 by default and at most 100, and a `page` number. Behind a request like that is often a query shaped like this lesson's: `ORDER BY … LIMIT per_page OFFSET (page − 1) × per_page`.
:::

::: context tie-order Why ties have no fixed order
SQL promises exactly the order you ask for, and nothing more. When two rows tie on every `ORDER BY` column, the database may return them either way, depending on how it happened to read the rows: which index it used, how the data sits on disk, or whether several workers read the table in parallel. The same query can give a different order after the table changes or the database is upgraded. A test that passes today can fail next month, which is why the tie-breaker is a habit, not an extra.
:::

::: context keyset-apis Cursors in real services
Keyset pagination is also called the "seek method", and in web services it often appears as a **cursor**: a token that stands for "the last row you saw". Stripe's API, for example, takes a `starting_after` value holding the id of the last object on the previous page. Slack's API hands back a `next_cursor` to pass in the next request. Both let a client walk through huge lists quickly, without the service counting past every earlier row.
:::

::: context text-order How text compares
`>` and `<` work on text by comparing one character at a time from the left, using each character's code number. `'Mug' > 'Bookends'` is true because M comes after B. In SQLite's normal comparison, every capital letter comes before every lower-case letter and a space comes before both, so `'Z' < 'a'` is true. That is why the product names here, which all start with a capital, sort in plain alphabetical order, and why messy text should be cleaned before it is compared.
:::
--- task

--- starter

LIMIT 3;
--- solution

FROM products

--- hint

--- hint

--- hint

=== sql2-13 | Changing data with conditions
--- teach
`UPDATE` and `DELETE` get their power from `WHERE`, and `WHERE` can use everything you have learned — including subqueries into other tables:

```sql
-- cancel paid orders from customers who have no email on file
UPDATE orders SET status = 'cancelled'
WHERE status = 'paid'
  AND customer_id IN (SELECT id FROM customers WHERE email IS NULL);
```

`SET` can compute from the row's current values: `SET price = price * 1.1` uses each row's own price. Money is floating point here, so round what you store: `ROUND(price * 1.1, 2)`.

`INSERT` can take its rows from a query instead of `VALUES`:

```sql
INSERT INTO newsletter (email, signed_up)
SELECT lower(trim(email)), date('now') FROM customers WHERE city = 'Paris';
```

The safe routine for any change:

1. Write the `SELECT` with the exact `WHERE` you plan to use, and check it returns exactly the rows you mean.
2. Change `SELECT …` to `UPDATE … SET …` or `DELETE`, keeping the `WHERE` word for word.
3. Query again to confirm the effect.

A subquery on the **same** table you are changing is allowed, but be careful: it sees the table as it was before the statement started.
--- task
Make two changes:

1. Raise the price of every `stationery` product by 10%, rounded to 2 decimals.
2. Delete every newsletter row whose email (lower-cased and trimmed) belongs to a customer (compare the customer's email lower-cased and trimmed too) — they already hear from us.
--- starter
-- 1. Raise stationery prices by 10%.

-- 2. Remove subscribers who are already customers.
--- solution
UPDATE products
SET price = ROUND(price * 1.1, 2)
WHERE category = 'stationery';

DELETE FROM newsletter
WHERE lower(trim(email)) IN (
  SELECT lower(trim(email)) FROM customers WHERE email IS NOT NULL
);
--- hint
`UPDATE products SET price = ROUND(price * 1.1, 2) WHERE category = 'stationery';`
--- hint
`DELETE FROM newsletter WHERE lower(trim(email)) IN (SELECT … FROM customers …);` — normalise both sides.
--- check query | Stationery prices went up 10%
SELECT name, price FROM products WHERE category = 'stationery' ORDER BY id
=> [["Notebook", 4.95], ["Fountain pen", 35.2], ["Planner", 19.8]]
--- check query | Other prices did not change
SELECT SUM(price) FROM products WHERE category <> 'stationery'
=> [[158.5]]
--- check query | Only non-customers are left on the newsletter
SELECT email FROM newsletter ORDER BY signed_up
=> [["zoe@mail.com"], ["Zoe@mail.com "], ["max@post.org"]]

=== sql2-14 | Debugging: the join that double-counts
--- teach
**The bug report.** Finance runs this report of what each customer ordered and what they paid. Ada's items come to 127.60 and she paid 127.60, but the report says she paid 175.10. Ben's numbers are both inflated too.

The cause is called **fan-out**. Joining a table multiplies rows: an order with 2 items becomes 2 rows. Join payments on as well and an order with 2 items **and** 2 payments becomes 2 × 2 = 4 rows — every item paired with every payment. `SUM` then adds each payment once per item and each item once per payment.

How to find it:

1. **Pick one wrong number and shrink the query to it.** Add `WHERE c.name = 'Ada'`.
2. **Remove the aggregation and look at the raw rows** — `SELECT o.id, oi.product_id, p.amount …`. You will see the same payment repeated.
3. **Count rows per key.** If a row you expected once appears several times, a join is fanning out.

The fix is not `DISTINCT` inside `SUM` — two genuinely different payments of the same amount would then merge. The fix is to **aggregate each child table down to one row per order first**, then join those one-row-per-order results. A `WITH` can hold several named steps, separated by commas:

```sql
WITH items AS (
  SELECT order_id, SUM(qty * unit_price) AS items_total
  FROM order_items GROUP BY order_id
), paid AS (
  SELECT order_id, SUM(amount) AS paid_total
  FROM payments GROUP BY order_id
)
SELECT …
FROM orders o
JOIN items i     ON i.order_id = o.id
LEFT JOIN paid p ON p.order_id = o.id
```

Joining one-to-one pieces cannot multiply anything. The general rule: never sum across two independent one-to-many joins at once.
--- task
Fix the report so each customer with orders shows their correct `items_total` and `paid_total` (both over all their orders, rounded to 2 decimals). Keep the columns `name`, `items_total`, `paid_total`. Customers whose orders have no payments at all should show `0` paid.
--- starter
SELECT c.name,
       ROUND(SUM(oi.qty * oi.unit_price), 2) AS items_total,
       ROUND(SUM(p.amount), 2) AS paid_total
FROM customers c
JOIN orders o       ON o.customer_id = c.id
JOIN order_items oi ON oi.order_id = o.id
LEFT JOIN payments p ON p.order_id = o.id
GROUP BY c.id;
--- solution
WITH items AS (
  SELECT order_id, SUM(qty * unit_price) AS items_total
  FROM order_items
  GROUP BY order_id
), paid AS (
  SELECT order_id, SUM(amount) AS paid_total
  FROM payments
  GROUP BY order_id
)
SELECT c.name,
       ROUND(SUM(i.items_total), 2) AS items_total,
       ROUND(COALESCE(SUM(p.paid_total), 0), 2) AS paid_total
FROM customers c
JOIN orders o    ON o.customer_id = c.id
JOIN items i     ON i.order_id = o.id
LEFT JOIN paid p ON p.order_id = o.id
GROUP BY c.id;
--- hint
Add `WHERE c.name = 'Ada'` and select the raw rows without `SUM`. Which payment appears twice, and why?
--- hint
Sum `order_items` per order in one `WITH` step and `payments` per order in another; each then has one row per order.
--- hint
Join `orders` to both steps and sum those per customer. Ben's cancelled order has no payment, so wrap the paid sum in `COALESCE(…, 0)` only where it could be NULL.
--- check result | Correct totals; Ben paid 58, Eve's refund nets to 0
[["Ada", 127.6, 127.6], ["Ben", 90.0, 58.0], ["Cleo", 37.8, 37.8], ["Dev", 107.0, 107.0], ["Eve", 45.0, 0.0]]

=== sql2-15 | Problem solving: the second-highest salary
--- schema
CREATE TABLE employees (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  dept TEXT NOT NULL,
  salary INTEGER
);
INSERT INTO employees (id, name, dept, salary) VALUES
  (1,  'Ana', 'eng',    120000),
  (2,  'Bo',  'eng',    120000),
  (3,  'Cy',  'eng',     95000),
  (4,  'Di',  'eng',     80000),
  (5,  'Ed',  'sales',   70000),
  (6,  'Flo', 'sales',   70000),
  (7,  'Gia', 'ops',     60000),
  (8,  'Hal', 'sales',   55000),
  (9,  'Ivy', 'design',  65000),
  (10, 'Jo',  'eng',     NULL),
  (11, 'Kit', 'design',  65000);
--- teach
This lesson's database has one table, `employees` (`id`, `name`, `dept`, `salary`). Contractors have a NULL salary.

**The problem.** For each department, find the second-highest salary. "Second-highest" means the second-highest *distinct* amount: if two people share the top salary, the answer is the next amount below it. A department with fewer than two distinct salaries has no second-highest, and should show NULL rather than vanish.

How to approach a problem like this:

1. **Restate it with examples.** eng earns 120000, 120000, 95000, 80000 (and one NULL). The second-highest is 95000, not 120000.
2. **Try the obvious answer and find where it breaks.** `ORDER BY salary DESC LIMIT 1 OFFSET 1` returns the second *row* — 120000 again, because of the tie. It also works on one department at a time only.
3. **Rephrase.** "The second-highest salary" is "the highest salary that is below the highest salary". That is two MAXes, one inside the other:

```sql
SELECT MAX(salary) FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);
```

4. **Generalise.** Make it per department with a correlated subquery, and drive the query from the list of departments so every department appears, even the ones with no answer. A subquery in `FROM` — `(SELECT DISTINCT dept FROM employees) d` — works like a table, as long as you give it an alias. `MAX` over no rows returns NULL — exactly the "no answer" you want.

5. **Check the edge cases against the data:** a tie at the top (eng, sales), a department with one person (ops), a department where everyone earns the same (design), and NULL salaries (MAX ignores them).
--- task
Return one row per department: `dept` and `second_salary` (the second-highest distinct salary, or NULL if there is none). Sort by `dept`.
--- starter
SELECT dept, salary AS second_salary
FROM employees
ORDER BY salary DESC
LIMIT 1 OFFSET 1;
--- solution
SELECT d.dept,
       (SELECT MAX(e.salary)
        FROM employees e
        WHERE e.dept = d.dept
          AND e.salary < (SELECT MAX(salary) FROM employees WHERE dept = d.dept)
       ) AS second_salary
FROM (SELECT DISTINCT dept FROM employees) d
ORDER BY d.dept;
--- hint
For one department: the MAX salary that is less than the MAX salary.
--- hint
Drive the query from `(SELECT DISTINCT dept FROM employees) d`, so every department gets a row.
--- hint
Put the "max below the max" in a scalar subquery in the SELECT list, correlated on `e.dept = d.dept` (the inner MAX needs `dept = d.dept` too).
--- check result | design NULL, eng 95000, ops NULL, sales 55000
ordered
[["design", null], ["eng", 95000], ["ops", null], ["sales", 55000]]

=== sql2-16 | Problem solving: finding what is missing
--- teach
**The problem.** Sales wants to win back customers who have never bought anything. "Bought" means an order that is `paid` or `shipped`: a customer whose only order was refunded or cancelled has not really bought.

This is an **anti-join**: rows in one table with *no* match in another. You cannot find them with an ordinary join, because a join only produces rows that match. There are three standard ways to ask for a missing match:

```sql
-- 1. NOT EXISTS: clearest, and safe with NULLs
SELECT c.name FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

-- 2. LEFT JOIN, then keep the rows where the right side is missing
SELECT c.name FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;

-- 3. NOT IN: works, until the list contains a NULL
SELECT c.name FROM customers c
WHERE c.id NOT IN (SELECT customer_id FROM orders);
```

The trap in option 3: `x NOT IN (1, 2, NULL)` means `x <> 1 AND x <> 2 AND x <> NULL`, and the last comparison is *unknown*, so the whole condition is never true. Try "customers who never referred anyone":

```sql
SELECT name FROM customers
WHERE id NOT IN (SELECT referred_by FROM customers);  -- no rows at all!
```

`referred_by` is NULL for several customers, so the list contains NULL and the answer is empty — without any error. Prefer `NOT EXISTS`; it has no such trap.

A wrong turn many people take first: `JOIN orders … WHERE status NOT IN ('paid', 'shipped')`. That finds customers who have *some* order that is not a purchase — a different question.
--- task
Return the names of the customers who have **no** order with status `paid` or `shipped` (including customers with no orders at all), alphabetically.
--- starter
SELECT DISTINCT c.name
FROM customers c
JOIN orders o ON o.customer_id = c.id
WHERE o.status NOT IN ('paid', 'shipped')
ORDER BY c.name;
--- solution
SELECT c.name
FROM customers c
WHERE NOT EXISTS (
  SELECT 1 FROM orders o
  WHERE o.customer_id = c.id AND o.status IN ('paid', 'shipped')
)
ORDER BY c.name;
--- hint
The starter finds Ben, who has bought (order 4), and misses Finn and Gus, who have no orders to join.
--- hint
Ask per customer whether a purchase exists: `WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id AND …)`.
--- check result | Eve (refunded only), Finn and Gus
ordered
[["Eve"], ["Finn"], ["Gus"]]

=== sql2-17 | Design: choosing the joins for a report
--- teach
Every report is a set of decisions about joins. Make them on purpose, from the requirements, before you write a line:

| The requirement says… | Use |
| --- | --- |
| "only X that have a Y" | `JOIN` (inner) |
| "every X, with its Y if there is one" | `LEFT JOIN` from X |
| "every X and every Y, matched where possible" | `FULL OUTER JOIN` (SQLite 3.39+) |
| "every combination of X and Y" | `CROSS JOIN` — calendars, grids |
| "X that has no Y" | `NOT EXISTS` / anti-join |

Then three questions for each LEFT JOIN:

1. **Which rows must survive?** That is the table you start `FROM`. Everything else hangs off it.
2. **Where does each filter go?** A condition on a LEFT-joined table goes in its `ON`, or it turns the join back into an inner join (lesson 2).
3. **Could this join multiply rows?** If two one-to-many tables hang off the same row, aggregate one of them first (lesson 14). Count rows as you add each join.

Then decide what "nothing" looks like: `COUNT(o.id)` gives 0 for no matches, `MAX(...)` gives NULL, and `SUM(...)` gives NULL unless you `COALESCE` it.

Build the query one join at a time and run it after each step. A report that is wrong usually went wrong at one specific join, and you will see it the moment it happens.
--- task
Build the **account review**: one row for **every** customer, sorted by name, with columns `name`; `referrer` (the referring customer's name, or NULL); `live_orders` (their number of `paid` or `shipped` orders, 0 if none); and `last_order` (the date — `'YYYY-MM-DD'`, no time — of their most recent `paid` or `shipped` order, or NULL).
--- starter
SELECT c.name, r.name AS referrer, COUNT(o.id) AS live_orders, MAX(o.placed) AS last_order
FROM customers c
JOIN customers r ON r.id = c.referred_by
JOIN orders o    ON o.customer_id = c.id
WHERE o.status IN ('paid', 'shipped')
GROUP BY c.id, c.name, r.name
ORDER BY c.name;
--- solution
SELECT c.name,
       r.name AS referrer,
       COUNT(o.id) AS live_orders,
       date(MAX(o.placed)) AS last_order
FROM customers c
LEFT JOIN customers r ON r.id = c.referred_by
LEFT JOIN orders o
  ON o.customer_id = c.id AND o.status IN ('paid', 'shipped')
GROUP BY c.id, c.name, r.name
ORDER BY c.name;
--- hint
"Every customer" means both joins must be `LEFT JOIN`s from `customers`.
--- hint
The status filter belongs in the orders join's `ON`, not in `WHERE`.
--- hint
`date(MAX(o.placed))` drops the time; it stays NULL when there are no live orders.
--- check result | All seven customers, with NULLs and zeros where nothing matched
ordered
[["Ada", null, 3, "2024-06-01"], ["Ben", "Ada", 1, "2024-04-07"], ["Cleo", "Ada", 1, "2024-04-07"], ["Dev", "Ben", 1, "2024-05-15"], ["Eve", null, 0, null], ["Finn", "Dev", 0, null], ["Gus", null, 0, null]]
