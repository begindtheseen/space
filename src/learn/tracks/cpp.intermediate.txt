=== cpp2-01 | const correctness
--- teach
The basics course ended with pointers: a raw pointer like `int*` to [[look at something|look-only-pointers]], and a `std::unique_ptr` to own it. Looking at a thing without changing it is the idea this lesson starts from.

This course turns what you learned in the basics into careful, everyday modern C++: the standard library's containers and algorithms, classes that guard their own rules, and the debugging habits that catch C++'s quiet bugs. It opens with the keyword that makes code safe to pass around: `const`.

### A promise the compiler holds you to

Picture lending a friend your model rocket inside a glass case. They can look at every fin and every decal, but they cannot pick it up and bend anything. `const` (short for constant) is that glass case.

You met it on variables in the basics course. After `const double pi = 3.14159;`, any line that tries to change `pi` is a compile error. So `const` is a promise, and it is one the [[compiler holds you to|const-in-flight-rules]]: break it, and the program does not build. On plain variables it is handy. On **references** and on **member functions** it matters far more.

### const on a reference parameter

You have written this kind of parameter since the vector lesson:

```cpp
int total(const std::vector<int>& v);   // reads v, never copies it
```

The `&` (read "reference to") means the function works on the caller's own vector, with no copy. The `const` means it promises not to change it. Together they tell whoever calls `total` three things: "I need to look at your object, I will not change it, and I will not copy it."

### const on a member function

In the classes lesson, `Account` had `int balance() const`. That `const`, written *after* a member function's parameter list, is the same promise made by a member function: calling it leaves the object unchanged.

Here is a small class with one member function of each kind:

```cpp
class Wallet {
public:
    void add(int cents) { cents_ += cents; }   // changes the object
    int cents() const { return cents_; }       // only looks
private:
    int cents_ = 0;
};
```

- `add` changes `cents_` (`+=` is "add to"), so it has no `const`.
- `cents()` only reads, so it gets one. A member function like this, which hands back a piece of the object's data, is called a **getter**.
- `int cents_ = 0;` gives the member its starting value right where it is declared, so every new wallet starts empty.

### Why it matters: a const reference only allows const calls

Here is a function that takes a wallet by `const` reference. It is a **free function**: an ordinary function that is not a member of any class.

```cpp
void show(const Wallet& w) {
    std::cout << w.cents();   // fine: cents() is const
    w.add(5);                 // compile error: add() is not const
}
```

Through a `const Wallet&`, the compiler lets you call [[only the member functions marked const|const-view]]. It stops at the second line. clang, the compiler in this app, says:

```text
error: 'this' argument to member function 'add' has type 'const Wallet', but function is not marked const
```

That is exactly what you want: `show` promised not to change the wallet, and the compiler caught it trying.

### The mistake people really make

**Watch out:** the common mistake is the reverse. You write a getter and **forget** the `const`:

```cpp
int cents() { return cents_; }   // no const
```

The class still works on its own, so you do not notice. But the moment someone passes a `Wallet` around the normal way, by `const Wallet&`, every call to that getter fails to compile. The getter only reads, but you never promised that, so the compiler has to assume it might write.

### The rule of thumb

- Parameters you only read: `const T&`. Here `T` stands for any type, as in `const std::string&` or `const Wallet&`. For small things like `int` or `double`, a plain copy is fine.
- Member functions that only read: mark them `const`.
- Loops that only read: `for (const auto& x : items)`. The `auto` lets the compiler work out the element type, the `&` skips the copy, and the `const` promises not to change anything.

### Inside a const member function

A `const` member function cannot change any member. It can also only call *other* `const` member functions of the same object, because calling one without `const` might change the object behind its back.

How does the compiler keep track? Every member function gets a hidden pointer called **this**: the address of the object it was called on. In `w.cents()`, `this` points at `w`. Inside a `const` member function, [[this points at a const object|this-pointer]], so every change through it is refused. That is why the error above talks about the "'this' argument".

### Two tools the task needs

The task keeps its readings in a vector, so here are two small tools you will meet in its solution and all through this course.

First, `v.size()` returns a `std::size_t`, an **unsigned** whole-number type: one that can never be negative. When your function returns an `int`, [[convert it|size-t-to-int]] with the `static_cast` from the arithmetic lesson:

```cpp
int count() const { return static_cast<int>(readings_.size()); }
```

Second, `std::min_element`, from the header `<algorithm>`, finds the smallest element for you. You hand it `v.begin()` and `v.end()`, which mark the start and the end of the vector, so together they mean "search the whole thing". It gives back an **[[iterator|iterator-preview]]**: a position in the vector, used like a pointer. So put `*` in front to get the value, the way `*p` followed a pointer in the pointers lesson:

```cpp
std::vector<int> r = {12, -3, 7};
int low = *std::min_element(r.begin(), r.end());   // -3
```

`std::max_element` works the same way and finds the largest. The next lessons cover algorithms and iterators properly.

::: context look-only-pointers const works on pointers too
The same promise fits pointers. `const int* p` is a look-only pointer: you may read `*p`, but `*p = 0;` is a compile error. Careful code writes the "raw pointers to look at things" rule from the pointers lesson exactly this way. Reading the type from right to left helps: `const int* p` is "p is a pointer to an int that is const". A `const` after the star, as in `int* const p`, means something else: the pointer itself can never be moved to point somewhere new, though the int it points at can still change.
:::

::: context const-in-flight-rules Why flight-software rules love const
`const` costs nothing while the program runs: all the checking happens while it compiles. Yet it catches a whole family of bugs, such as a function that was only meant to read a table of sensor limits but changed one by accident. That is why careful coding standards ask for it. MISRA C++, a rule book used for car, aircraft and spacecraft software, says that a variable which is never changed shall be declared `const`, and that a pointer or reference parameter shall be to `const` when the function does not change what it refers to. The C++ Core Guidelines say the same: make objects and member functions `const` by default.
:::

::: context const-view A read-only window onto the same object
A `const Wallet&` does not make the wallet itself unchangeable. It is a read-only window onto it. The caller still holds the wallet under its own name and can call `add` whenever it likes. Only code that sees the wallet through the `const` window is limited to the `const` member functions.

::: context this-pointer The hidden pointer called this
When you write `w.cents()`, C++ quietly hands the function a pointer to `w`, named `this`. Inside the function, `cents_` is short for `this->cents_`. The arrow `->` follows a pointer and then picks a member; it means the same as `(*this).cents_`. In an ordinary member function of `Wallet`, `this` has the type `Wallet*`. In a `const` one it has the type `const Wallet*`, a look-only pointer, so any line that writes a member is refused.
:::

::: context size-t-to-int Why convert size() to an int
A `std::size_t` is 8 bytes on a 64-bit computer, so it can count up to 18446744073709551615. An `int` is 4 bytes and stops at 2147483647. `static_cast<int>` is safe as long as the vector holds fewer elements than that, which a list of thermometer readings always will. The cast also says out loud "I know these two types differ". Mixing them without saying so draws warnings: with this app's `-Wall -Wextra`, comparing an `int` counter with `v.size()` gives "comparison of integers of different signs".
:::

::: context iterator-preview Why the task promises at least one reading
`std::min_element` searches from `begin()` up to, but not including, `end()`. If there are several equal smallest values, it points at the first one. For an empty vector there is nothing to find, so it gives back `end()`, a mark one past the last element that is not an element at all. Putting `*` in front of that is undefined behaviour, like following `nullptr`. That is why the task lets you assume at least one reading. Iterators get their own lesson soon, "Iterators and range-for".
:::

Finish the `Thermometer` class in the starter so it is const-correct. It keeps its readings in a private vector called `readings_`.

- `int count() const` returns how many readings there are.

Then fix the free function `range_of` so its parameter is `const Thermometer& t`, and make it return `highest - lowest`. For the readings 12, -3 and 7 that is 12 - (-3) = 15. For a single reading it is 0.

Add `#include <algorithm>` at the top for `std::min_element` and `std::max_element`. The checks use your class through a `const Thermometer&`, and also make a `const Thermometer` with no readings, whose `count()` must be 0. No `main`.

class Thermometer {

    int count() { return 0; }

--- solution
#include <algorithm>
#include <vector>

class Thermometer {
public:
    void record(int reading) { readings_.push_back(reading); }
    int count() const { return static_cast<int>(readings_.size()); }
    int lowest() const { return *std::min_element(readings_.begin(), readings_.end()); }
    int highest() const { return *std::max_element(readings_.begin(), readings_.end()); }
private:
    std::vector<int> readings_;
};

int range_of(const Thermometer& t) {
    return t.highest() - t.lowest();
}

=== cpp2-02 | Debugging: the function that changed a copy
--- teach
Last lesson, `const` stopped a function from changing something it was only meant to look at. This lesson is about the opposite bug: a function that is *meant* to change your data, runs without a single complaint, and changes nothing.

### Bugs that make no noise

Some [[bugs|where-bug-comes-from]] make no noise at all. The program compiles, it runs, and it does nothing: no error, no crash, the numbers are still the old ones. Guessing at a bug like that can waste an afternoon. It calls for a method.

### A method instead of guesswork

An **assumption** is something you believe is true but have not checked. A silent bug always hides behind one. So debug in four steps:

1. **Reproduce** it with the [[smallest input you can|smallest-input]]: one or two items, numbers you can check in your head.
2. **Check your assumptions**, one at a time. "The function runs" — does it? [[Print something inside it|prints-and-debuggers]]. "It changes my data" — print the data inside the function *and* straight after the call.
3. **Narrow down** to the first place where what you see differs from what you expect.
4. **Fix the cause**, not the [[symptom|cause-not-symptom]]. Returning the changed vector and assigning it back would make the output right, but it hides a design mistake that will bite again.

### The classic silent bug: working on a copy

In the references lesson you saw that C++ hands a function a photocopy unless you ask for a reference. In C++ the classic silent bug is exactly that: **working on a copy**. Two places make copies without saying so. "By value" means "as a copy":

```cpp
void reset(std::vector<int> v) {     // 1. a by-value parameter copies the caller's vector
    for (int x : v) {                // 2. a by-value loop variable copies each element
        x = 0;
    }
}
```

Both copies are changed, and then thrown away when the function ends. The caller's vector never sees a thing.

### Following the method

Step 2 says: print inside, and print after. Here is what that looks like:

```cpp
void reset(std::vector<int> v) {
    for (int x : v) {
        x = 0;
        std::cout << "inside: " << x << "\n";   // prints 0, twice
    }
}

std::vector<int> d = {4, 5};
reset(d);
std::cout << "after: " << d[0] << "\n";          // prints 4
```

Inside the loop you see zeros. After the call, the caller's vector is unchanged. That gap, right inside and wrong outside, is [[exactly where the copy is|where-the-copy-is]].

### The fix: a reference at each copy point

Put a reference at *each* copy point: `std::vector<int>& v` for the parameter, and `for (int& x : v)` for the loop.

```cpp
void reset(std::vector<int>& v) {
    for (int& x : v) {
        x = 0;
    }
}
```

Fixing only one of the two still leaves the bug. Fix only the parameter, and the loop still zeroes a copy of each element. That is why step 2 matters: check again after every change you make.

`auto` follows the same rule. `for (auto item : items)` copies each element, the same as `for (int x : v)`. `for (auto& item : items)` makes `item` a reference, so changes stick.

**Watch out:** the compiler rarely warns you. In the tiny `reset` above, clang does print `warning: variable 'x' set but not used`, a clue worth reading. But once the loop changes a member of a struct, as in `item.price_cents = …`, there is no warning at all. Only your method finds it.

::: context where-bug-comes-from Where the word bug comes from
Engineers called faults "bugs" long before computers; Thomas Edison used the word in letters in the 1870s. In September 1947, the team running the Harvard Mark II computer found a real moth stuck in one of its relays. They taped it into their logbook with the note "First actual case of bug being found." Grace Hopper, who worked on that machine and later helped create the language COBOL, loved telling the story. The logbook page is now at the Smithsonian's National Museum of American History.
:::

::: context smallest-input Why a tiny input helps
With two items and round prices, you know the right answer before you run anything: 10% off 1000 is 900. With a thousand items you would need the program to check the program. A small failing case is also quick to run again after every change. Programmers call it a *minimal reproducible example*, and it is what you attach to a bug report so someone else can see the bug for themselves.
:::

::: context prints-and-debuggers Prints, debuggers and telemetry
Adding print lines is the oldest debugging tool, and still one of the most used. Programs called debuggers, such as gdb and lldb, can instead pause a running program at any line and show every variable, without editing the code at all. Either way the idea is the same: stop guessing and look at the real values. Delete your print lines once the bug is fixed. A spacecraft does a version of this all the time: it sends a stream of measurements called *telemetry* back to Earth, so engineers can see inside a program running millions of kilometres away.
:::

::: context cause-not-symptom Symptom or cause
The *symptom* is what you see going wrong; the *cause* is why. Here, making the function return its changed vector, so the caller writes `cart = apply_discount(cart, 10);`, would make the prices right. But the function's name and its `void` return promise to change the caller's vector in place, and the next person who calls it that normal way hits the same bug again. Accident investigators at NASA hunt for the *root cause* of every mishap for the same reason: a symptom that is patched over comes back somewhere else.
:::

::: context where-the-copy-is Three boxes, two copies
The caller's `d` is copied into the parameter `v`, and each element of `v` is copied again into `x`. The zero lands in the last box only. Printing inside the loop looks at `x`; printing after the call looks at `d`.

=== cpp2-03 | std::vector and <algorithm>
--- teach
Last lesson you fixed a loop that changed copies instead of the real elements. Most loops you will ever write do one of a handful of jobs: sort, find, count, change every element, add them all up. This lesson hands you ready-made versions of those jobs.

### Loops with names

Think of a toolbox. You could file a piece of wood flat by hand every time, or you could pick up the plane that was made for it. The headers `<algorithm>` and `<numeric>` are that toolbox. They hold tested, named loops called **algorithms**: each one is a recipe of steps for one job.

Using them makes your code say *what* it does ("sort these") instead of *how* ("compare these two, swap them, move on…"). It also removes a whole class of [[off-by-one mistakes|off-by-one]], because you never write the counting yourself.

### A range: begin() and end()

Every algorithm works on a **range**: a `begin()` and an `end()` iterator. You met the pair in the const correctness lesson, with `std::min_element`. `v.begin()` marks the first element and `v.end()` marks the spot one past the last, so together they mean "the whole vector". The next lesson looks at iterators closely.

### Sorting

`std::sort` puts the elements of a range in order, smallest first. It [[changes the vector in place|how-sort-works]]:

```cpp
#include <algorithm>
#include <vector>

std::vector<int> v = {5, 1, 4, 2};
std::sort(v.begin(), v.end());   // v is now {1, 2, 4, 5}
```

To put the largest first, hand `sort` a third thing: the rule for comparing. `std::greater<int>()`, from the header `<functional>`, is a [[ready-made "is a greater than b?"|function-objects]], so sorting with it puts the largest first:

```cpp
#include <functional>

std::sort(v.begin(), v.end(), std::greater<int>());   // v is now {5, 4, 2, 1}
```

### Adding them all up

`std::accumulate`, from `<numeric>`, adds every element of a range to a starting value, and gives back the total:

```cpp
#include <numeric>

long long total = std::accumulate(v.begin(), v.end(), 0LL);   // 12
```

The third argument, `0LL`, is the starting value: zero, written as a `long long`. A **long long** is a whole-number type that is wider than `int`. It takes 8 bytes and reaches about 9.2 quintillion. The letters `LL` on the end of a number make it a `long long`.

**Watch out:** `accumulate` adds in the type of its **starting value**. `0` means `int`, which [[overflows past about 2 billion|overflow]]; `0LL` means `long long`. Add up two readings of 2,000,000,000 starting from `0` and the answer is garbage. Start from `0LL` and it is 4,000,000,000.

### Small rules: lambdas

The next algorithms each take a small rule, like "is this number over 3?". You write the rule as a **lambda**: a small unnamed function written right where you need it. You have been reading lambdas in the check lines since the references lesson.

```cpp
[](int x) { return x > 3; }
```

Read it as "given an int `x`, return whether `x` is greater than 3". The `[]` starts it, `(int x)` is its parameter, and the body in `{ }` works out the answer. Lambdas get their own lesson later in this course; for now read each one as "given x, return this".

### Finding the first match

`std::find_if` walks the range and gives back an iterator to the first element for which the rule says `true`:

```cpp
auto it = std::find_if(v.begin(), v.end(), [](int x) { return x > 3; });
if (it != v.end()) {
    // *it is the first element over 3
}
```

**Watch out:** when nothing matches, `find_if` returns `end()`, the stopping mark, which is not an element. Always compare with `v.end()` before you use `*it`.

### Counting matches

`std::count_if` counts the elements for which the rule says `true`. Here the rule uses `%` (remainder): `x % 2 == 0` means "x is even".

```cpp
auto n = std::count_if(v.begin(), v.end(), [](int x) { return x % 2 == 0; });   // 2
```

In `{5, 4, 2, 1}`, the even ones are 4 and 2, so `n` is 2. The count comes back as a wide signed whole-number type, so to return it from an `int` function, convert it: `static_cast<int>(n)`.

### Using a variable from outside

A lambda can only see its own parameters, unless you name an outside variable in its square brackets. This is called **capturing** the variable:

```cpp
int bar = 2;
auto m = std::count_if(v.begin(), v.end(), [bar](int x) { return x >= bar; });   // 3
```

`[bar]` lets the lambda read `bar`. In `{5, 4, 2, 1}`, three values are at least 2. Leave out the `bar` in the brackets and clang stops with `variable 'bar' cannot be implicitly captured`.

### Changing every element into a new vector

`std::transform` reads each element, runs the rule on it, and writes the result somewhere else:

```cpp
std::vector<int> out(v.size());
std::transform(v.begin(), v.end(), out.begin(), [](int x) { return x * 10; });
// out is {50, 40, 20, 10}
```

The third argument, `out.begin()`, is where the writing starts. `transform` does not make room; it writes over elements that must already exist. So first make `out` the right size: `std::vector<int> out(v.size());` makes a vector holding `v.size()` zeros. [[Round brackets here, not curly ones|round-vs-curly]].

### A short if/else that gives a value

One more piece of syntax that the solutions use from here on is the **conditional operator**: `condition ? a : b`. Read the `?` as "if so" and the `:` as "otherwise". It gives `a` when the condition is true and `b` when it is false:

```cpp
int fuel = 12;
std::string status = fuel < 10 ? "low" : "ok";   // "ok"
```

So `return it == v.end() ? -1 : *it;` is a short if/else that produces a value: `-1` when nothing was found, the element otherwise.

::: context off-by-one Where off-by-one mistakes hide
A hand-written loop has three places to slip: where it starts, where it stops, and how it steps. Use `<=` where you meant `<` and the loop reads one element past the end of the vector. An algorithm takes the whole range as `begin()` and `end()`, so there is no counter to get wrong. The debugging lesson "Debugging: off by one, out of range", later in this course, is all about the ones that still get through.
:::

::: context how-sort-works How fast is std::sort?
Sorting by comparing neighbours over and over is slow on long lists: roughly n × n comparisons for n elements. Since C++11, `std::sort` must finish in about n × log₂(n) comparisons. For a million readings that is about 20 million comparisons instead of a trillion. Library writers usually build it as *introsort*, a mix of quicksort, heapsort and insertion sort. Equal elements may come out in any order; `std::stable_sort` keeps them in their original order when that matters.
:::

::: context function-objects Rules you can hand over
`std::greater<int>` is a type whose objects can be called like a function: `std::greater<int>()(5, 2)` is `true`, because 5 is greater than 2. The `()` after `std::greater<int>` makes one such object, and `sort` calls it every time it needs to compare two elements. An object that acts like a function is called a *function object*. A lambda is a quick way to write one yourself, which is why the two can be used in the same places.
:::

::: context overflow Overflow, and a rocket lost to it
An `int` holds at most 2,147,483,647. Going past that in a signed type is *overflow*, and in C++ it is undefined behaviour: the rules say nothing about the result. A `long long` reaches 9,223,372,036,854,775,807. On 4 June 1996, the first Ariane 5 rocket veered off course about 37 seconds after lift-off and destroyed itself. Its guidance software converted a 64-bit floating-point number (a decimal, like a `double`) into a 16-bit whole number, the value was too big to fit, and the error shut the guidance system down. The code had come from Ariane 4, whose slower flight never produced such a big number.
:::

::: context round-vs-curly Round brackets or curly braces
For a vector of ints, the kind of bracket changes the meaning. `std::vector<int> out(4)` means "make 4 elements", all zero. `std::vector<int> out{4}` means "make a vector holding the one value 4". `transform` needs the first kind: slots that already exist, ready to be written over.

=== cpp2-04 | Iterators and range-for
--- teach
Last lesson every algorithm took `v.begin()` and `v.end()`, and `std::find_if` handed back an `it` that you compared with `v.end()` before using `*it`. This lesson opens those up: what an iterator is, and how the range-for loop you have used since the vector lesson is built out of them.

### A bookmark in a container

Picture a bookmark in a book. It is not a page; it marks one. You can read the page it marks, and you can move it forward one page at a time.

An **iterator** is a bookmark for a container: a [[position in it|why-iterators]]. It behaves like a pointer from the pointers lesson:

- `*it` is the element at that position. Read it "the thing it points at".
- `++it` moves it to the next element. Read it "step it forward", like `i++` in a counting loop.

```cpp
std::vector<int> v = {7, 3, 9};
auto it = v.begin();        // it marks the 7
++it;                       // now it marks the 3
std::cout << *it << "\n";   // prints 3
```

`auto` saves you writing the real type, which is `std::vector<int>::iterator`: "the iterator type from vector of int" (`::` is the scope operator, read "from").

### begin() and end()

Every container gives you two iterators:

- `begin()` — the first element.
- `end()` — one **past** the last. It is a stopping mark, never an element: do not `*` it.

### The half-open range

Maths has a short way to write "from here, up to but not including there": `[begin, end)`. The square bracket means "this one is included"; the round bracket means "stop right before this one". A range like this is called a **[[half-open range|half-open]]**.

That shape is why an empty container has `begin() == end()`: with no elements, the first position and the stopping mark are the same place. It is also why loops read "while not at the end":

```cpp
std::vector<int> v = {7, 3, 9};
for (auto it = v.begin(); it != v.end(); ++it) {
    std::cout << *it << "\n";
}
```

This is the counting `for` loop from the loops lesson, with an iterator in place of the counting number. It starts at `begin()`, keeps going while `it != v.end()` (`!=` is "is not equal to"), and steps with `++it`. It prints 7, 3 and 9, one per line.

### Range-for is that loop, written for you

The **range-for** loop is exactly that loop, [[written for you by the compiler|range-for-inside]]. Each time around, the loop variable is set from `*it`. So the way you declare the loop variable decides whether you get a copy:

```cpp
for (int x : v)               // x is a copy of each element
for (int& x : v)              // x IS each element: changes stick
for (const auto& s : names)   // no copy, read-only: the default for strings and bigger things
```

Changing the elements through `int& x` is fine. Adding or removing elements while you loop is [[not fine at all|invalidation]].

### From an iterator back to an index

Algorithms give back iterators, but sometimes you want the position as a number, an index. `std::distance(a, b)`, from the header `<iterator>`, counts how many steps it takes to get from `a` to `b`:

```cpp
auto it = std::max_element(v.begin(), v.end());   // points at 9
auto index = std::distance(v.begin(), it);        // 2
```

If the largest value appears more than once, `std::max_element` points at the *first* one. Like `count_if`'s count, the distance comes back as a wide signed whole-number type, so convert it with `static_cast<int>` to return it from an `int` function.

### Walking backwards

`rbegin()` and `rend()` walk backwards (the `r` is for reverse). `rbegin()` marks the last element, `++` moves toward the front, and `rend()` is the stopping mark right before the first. A `std::string` is a container of characters, so it has all four:

```cpp
std::string s = "abc";
for (auto it = s.rbegin(); it != s.rend(); ++it) {
    std::cout << *it;   // prints cba
}
```

### The same both ways?

`std::equal(a, b, c)`, from `<algorithm>`, compares the range from `a` to `b`, element by element, with the range that starts at `c`. It gives `true` only if every pair matches.

That makes "is it the same both ways?" a one-liner. `std::equal(s.begin(), s.end(), s.rbegin())` [[compares the start going forwards with the end going backwards|palindrome-pairs]]. It compares characters exactly, so `'L'` and `'l'` count as different.

### Is it empty?

`v.empty()` is `true` when a container has no elements. It means the same as `v.size() == 0`, but says what you mean. Strings have it too: `w.empty()` is `true` for `""`. Put `!` ("not", from the decisions lesson) in front to ask the opposite:

```cpp
std::string w = "ada";
if (!w.empty()) {
    // w has at least one character, so w[0] is safe
}
```

**Watch out:** `end()` is not an element, so check before you follow an iterator that might be `end()`. On an empty vector, `std::max_element` gives back `end()`, and putting `*` in front of that is undefined behaviour. The same goes for `w[0]` on an empty string: there is no first letter there that you may change. Check `v.empty()` or `w.empty()` first.

::: context why-iterators One idea for every container
A vector keeps its elements in one row, but a `std::map` usually keeps its keys in a tree, and other containers link elements together in chains. Each kind of container supplies its own iterators, and they all answer to the same `*`, `++`, `==` and `!=`. So one `std::find_if` or `std::count_if` works on all of them. This design is the heart of the Standard Template Library (STL), created by Alexander Stepanov and Meng Lee and voted into the draft C++ standard in 1994.
:::

::: context half-open The stopping mark sits past the end
For `{7, 3, 9}`, `begin()` marks the 7 and `end()` marks the empty spot after the 9. For a vector, the number of elements is always `end() - begin()`, here 3, with no plus or minus one to remember. For an empty vector, both marks sit at the same spot.

::: context range-for-inside What the compiler writes for you
The range-for loop arrived in C++11. For `for (int x : v) { … }`, the compiler writes roughly this: take `v.begin()` and `v.end()`, then loop `for (auto it = v.begin(); it != v.end(); ++it) { int x = *it; … }`. Seen that way, it is clear why `int x` is a copy (it is a new `int` filled from `*it`) and why `int& x` is not (it is another name for `*it`). Anything with `begin()` and `end()` works in a range-for: vectors, strings, maps and sets.
:::

::: context invalidation Why you must not grow a vector while looping over it
When a vector runs out of room, `push_back` moves every element to a bigger block of memory. Every iterator into the old block, including the hidden one inside a range-for, now marks memory that is no longer the vector's. Using it is undefined behaviour. This is called *iterator invalidation*. The safe habit: while looping over a container, change its elements, but do not add or remove any. Build a new vector instead, or collect the changes and make them after the loop.
:::

::: context palindrome-pairs Forwards and backwards at once
`std::equal` moves two iterators together: one from `s.begin()` going forwards, one from `s.rbegin()` going backwards. For `"level"` it compares l with l, e with e, v with v, e with e, and l with l, all equal, so the answer is `true`. For `"ab"` the very first pair, a and b, differ, so it is `false`. An empty string has no pairs to disagree, so it counts as a palindrome.

=== cpp2-05 | std::map, std::unordered_map and std::set
--- teach
In the iterators lesson you walked through a container one position at a time, with `begin()`, `end()` and `*it`. In the basics course you met `std::map`, which finds a value by its key instead of by its position. This lesson adds two close relatives of the map, shows how to choose between all three, and uses iterators to look things up.

### Three containers for "look it up"

Think of three everyday lists. A phone's contact list is kept in alphabetical order, so you can read it top to bottom. A cloakroom hands you a ticket and finds your coat straight away, but the coats hang in no particular order. And a guest list at a door only answers one question: is this name on it?

C++ has one container for each:

| Container | Holds | Order | Lookup |
| --- | --- | --- | --- |
| `std::map<K, V>` | key → value | sorted by key | O(log n) |
| `std::unordered_map<K, V>` | key → value | none you can rely on | O(1) on average |
| `std::set<T>` | unique values | sorted | O(log n) |

`K` stands for the key's type, `V` for the value's type and `T` for the type of the things stored. The last column says how the time to find something grows as the container fills up. It is written in [[big-O notation|big-o]]: **O(log n)**, read "order log n", means that doubling the number of items adds only about one more step; **O(1)**, read "order one", means about the same few steps however many items there are.

### std::set: each value once

A **std::set** is a sorted collection in which every value appears at most once. Add a value that is already there and nothing happens. It needs `#include <set>`.

```cpp
std::set<std::string> seen = {"b", "a", "b"};   // {"a", "b"}: the second "b" vanishes
seen.insert("c");                               // now {"a", "b", "c"}
seen.contains("a");                             // true
```

`.insert(x)` adds a value. `.contains(x)` answers true or false and never changes the set; it is [[new in C++20|contains-cpp20]].

### std::unordered_map: fast, in no fixed order

A **std::unordered_map** works like a `std::map` from the outside: keys, values, and `[ ]`. Inside, it is built as a [[hash table|hash-table]] instead of a sorted tree, which makes lookups faster but gives up the order. It needs `#include <unordered_map>`.

Counting works exactly as it did with `std::map`, because a missing key starts at 0. Here `words` is a `std::vector<std::string>`:

```cpp
std::unordered_map<std::string, int> count;
for (const auto& w : words) count[w]++;         // each word's count goes up by one
```

### Finding a key, and the arrow ->

`.find(key)` looks for a key without ever adding one. Like the algorithms in the iterators lesson, it gives back an iterator: a position pointing at the matching element, or `end()` if there is none. So always compare with `end()` before you use it:

```cpp
auto it = count.find("pear");
if (it != count.end()) {
    std::cout << it->first << " " << it->second << "\n";   // pear and its count
}
```

Each element of a map is a **pair**: a key and a value stuck together. `first` is the key and `second` is the value.

`->`, read "arrow", means "follow this, then take the member". [[Written out the long way|arrow-operator]], `it->first` is `(*it).first`: `*it` follows the iterator to the pair, and `.first` takes the key out of it. The arrow works the same way on pointers.

### Building one container from another

Every one of these containers can be made straight from a range, a begin and an end:

```cpp
std::vector<std::string> words = {"pear", "fig", "pear"};
std::set<std::string> s(words.begin(), words.end());      // {"fig", "pear"}
std::vector<std::string> back(s.begin(), s.end());        // {"fig", "pear"}, sorted
```

The middle line makes a set from the vector, which removes the repeats and sorts what is left. The last line makes a new vector from the set, in the set's order.

### Letters: isalpha and tolower

In the strings lesson you used `std::toupper` and `std::isdigit` from `<cctype>`. Two more helpers live there:

- `std::isalpha(c)` is true when `c` is a letter, `a` to `z` or `A` to `Z`.
- `std::tolower(c)` gives the lowercase version: `'A'` becomes `'a'`, and anything that is not a capital letter comes back unchanged.

As with `std::toupper`, hand them an `unsigned char` and turn the answer back into a `char`:

```cpp
char c = 'Q';
unsigned char u = static_cast<unsigned char>(c);
if (std::isalpha(u)) {
    std::cout << static_cast<char>(std::tolower(u));   // prints q
}
```

### Keeping the best so far

To find the biggest value in a map, walk through every pair and remember the best one you have seen. To break a tie, compare the keys too: `<` on two strings asks "does this one come first alphabetically?"

```cpp
std::map<std::string, int> fuel = {{"tank-b", 40}, {"tank-a", 40}, {"tank-c", 12}};
std::string fullest;   // the best name so far
int most = 0;          // its amount
for (const auto& [name, kg] : fuel) {
    if (kg > most || (kg == most && name < fullest)) {
        fullest = name;
        most = kg;
    }
}
// fullest is "tank-a": it ties with tank-b and comes first
```

Read the `if` as: "this one has more, **or** it has the same amount and its name comes first". A `std::map` already hands you its pairs in key order, so here the tie rule changes nothing. It matters with an `unordered_map`, whose pairs come in no fixed order.

### How to choose

- Only need fast lookups? `unordered_map`.
- Also need the keys in order, say for a sorted report or "the smallest key over 10"? `map`.
- Only care whether something is there? `set`.

**Watch out:** two things trip people up. First, `m[key]` **inserts** the key when it is missing, even when you only meant to read it; use `find` or `contains` to only look. Second, an `unordered_map` walks through its pairs in an [[unpredictable order|unordered-order]]. If your answer depends on order, like breaking ties alphabetically, you have to decide that order yourself, with a comparison like `name < fullest`.

::: context big-o Counting steps, not seconds
Big-O notation describes how the work grows as the data grows, ignoring the exact speed of any one computer. O(log n) comes from halving: a sorted tree can throw away about half of what is left at every step, and you can halve a million only about 20 times before one item is left. So a map of a million keys needs about 20 steps, and a map of two million about 21. O(1) means a fixed number of steps whether the container holds ten items or ten million. A plain search through a vector, looking at every element, is O(n): twice the data, twice the work.
:::

::: context contains-cpp20 Versions of C++
C++ is updated every three years, and each version is named after its year: C++11, C++14, C++17, C++20, C++23. `.contains` arrived in C++20, and this app compiles your code as C++20. In older code you will see `s.count(x)` used for the same job: for a set or a map it gives 1 when `x` is there and 0 when it is not, which works as true or false in an `if`.
:::

::: context arrow-operator Why the arrow exists
The brackets in `(*it).first` are needed, because without them C++ would read `*it.first` as `*(it.first)`, which means something else entirely. Typing the brackets every time is clumsy, so the C language, which C++ grew out of, added `->` as a shorthand for "follow, then take a member". You will see it constantly on pointers to structs and classes, and later in the advanced course on smart pointers, which behave like pointers that clean up after themselves.
:::

::: context unordered-order Why the order is unpredictable
An `unordered_map` walks its buckets in bucket order, and which bucket a key lands in depends on its hash and on how many buckets there are right now. When the table grows, it moves every key into a new, bigger set of buckets, so the order can change after one more insert. It can also differ between compilers. Code that happens to print the right order on your computer can fail on someone else's. Flight software aims to be *deterministic*, meaning the same input always gives the same output, so engineers never let a result depend on an order nobody chose.

#include <map>
#include <set>
#include <string>
#include <unordered_map>
#include <vector>

std::vector<std::string> unique_sorted(const std::vector<std::string>& words) {
    std::set<std::string> s(words.begin(), words.end());
    return std::vector<std::string>(s.begin(), s.end());
}

std::map<char, int> letter_counts(const std::string& text) {
    std::map<char, int> counts;
    for (char c : text) {
        unsigned char u = static_cast<unsigned char>(c);
        if (std::isalpha(u)) counts[static_cast<char>(std::tolower(u))]++;
    }
    return counts;
}

std::string most_common(const std::vector<std::string>& words) {
    std::unordered_map<std::string, int> counts;
    for (const auto& w : words) counts[w]++;
    std::string best;
    int best_count = 0;
    for (const auto& [word, n] : counts) {
        if (n > best_count || (n == best_count && word < best)) {
            best = word;
            best_count = n;
        }
    }
    return best;
}

=== cpp2-06 | Classes that keep their own rules
--- teach
Last lesson you chose between ready-made containers. This lesson goes back to a type you design yourself. In the basics course you built an `Account` class with private data, a constructor and member functions. Now you will build a class whose whole job is to keep a rule true, whatever anyone does with it.

### A rule that is always true

Picture a digital clock. It can show 07:05 or 23:59, but never 07:75 and never 25:00. That is a rule about every clock, all the time.

A rule like that is called an **[[invariant|invariant-word]]**: something that is true of every object of a class, always. A class keeps its invariant in three ways:

1. The **constructor** makes the rule true the moment the object is born.
2. Every **member function** that changes the data leaves the rule true when it finishes.
3. The data is **private**, so no code outside the class can reach in and break it.

If the data were public, any line of the program could set the minutes to 75. With a class, the only ways in are the constructor and the member functions, so those are the only places the rule has to be enforced.

### A small example: a countdown timer

Here is a timer whose rule is "the seconds left are never negative":

```cpp
class Timer {
public:
    explicit Timer(int seconds) : seconds_(seconds < 0 ? 0 : seconds) {}
    void tick() { if (seconds_ > 0) --seconds_; }
    bool done() const { return seconds_ == 0; }
private:
    int seconds_;   // rule: never negative
};
```

Go through it one piece at a time:

- The constructor uses the conditional operator from the algorithms lesson: `seconds < 0 ? 0 : seconds` gives `0` when the starting value is negative, and the value itself otherwise. So `Timer t(-5);` starts at 0, and the rule is true from the first moment.
- `tick()` counts down by one, but only while there is something left. `--seconds_`, read "decrement", takes one away; it is the opposite of `++`. The `if` guard means the count can never go below 0.
- `done()` only looks, so it is marked `const`, as in the const correctness lesson.

Two habits from the basics course matter here. The **member initialiser list**, `: seconds_(…)`, gives each member its first value before the constructor body runs; prefer it to assigning in the body. And `explicit` on a constructor that takes one value stops surprise conversions like `Timer t = 5;`.

### Store the data in the shape that makes the rule easy

Now the clock. You could store hours and minutes as two numbers, but then every function has to juggle both: adding 70 minutes means carrying into the hours, and the hours then wrap past 23.

A neater trick is to store **one** number: the total minutes since midnight. A day has 24 × 60 = 1440 minutes, so the rule becomes "the total is always in [0, 1440)". That bracket notation is the [[half-open range|half-open-day]] from the iterators lesson: from 0, up to but **not** including 1440.

Hours and minutes then come straight out with whole-number division and remainder:

```cpp
int total = 125;         // 125 minutes after midnight
int h = total / 60;      // 2
int m = total % 60;      // 5, so the time is 02:05
```

### Wrapping any number onto the clock

Every time the total changes, it has to be brought back into [0, 1440). The remainder `%` nearly does it: `1500 % 1440` is `60`, which is 01:00 the next day.

But remember from the basics course that [[% keeps the sign of the left side|remainder-sign]]. So `-1 % 1440` is `-1`, not `1439`. One minute before midnight should be 23:59, and a plain `%` gets it wrong.

The fix is a formula that works for every whole number, negative or not. To wrap `x` into [0, n):

```cpp
((x % n) + n) % n
```

Follow it for `x = -1` and `n = 1440`:

1. `-1 % 1440` is `-1`.
2. Add 1440: `1439`.
3. `1439 % 1440` is `1439`. That is 23:59.

And for `x = 60`, a number already in range:

1. `60 % 1440` is `60`.
2. Add 1440: `1500`.
3. `1500 % 1440` is `60` again. The last `%` undoes the extra 1440 when it was not needed.

### Numbers into text

`std::to_string`, from `<string>`, turns a number into text: `std::to_string(7)` is `"7"`. A clock shows two digits, so add a `"0"` in front when the number is below 10:

```cpp
std::string s = std::to_string(7);   // "7"
if (7 < 10) s = "0" + s;             // "07"
```

Your clock will have a member function called `to_string` too. That is allowed: inside the class, writing `std::to_string` with the `std::` in front makes it clear you mean the library's one.

### static: belongs to the class, not to one object

Some helpers do not need any particular clock. Wrapping a number is the same sum for every clock there is. A member marked **static** belongs to the class itself, not to any one object:

```cpp
class Clock {
    // ...
private:
    static constexpr int kDay = 24 * 60;
    static int wrap(int m) { return ((m % kDay) + kDay) % kDay; }
};
```

- `static int wrap(int m)` is a [[static member function|static-members]]: a helper that works without an object, so it cannot see any one clock's data. It only uses its parameter.
- `static constexpr int kDay = 24 * 60;` is one constant that every `Clock` shares. **constexpr** means its value is [[known while compiling|constexpr-meaning]], before the program ever runs (the advanced course covers it properly). Constants are often named `kLikeThis`, with a small `k` in front.

Both sit in the `private:` part, because they are the class's own tools, not something other code needs.

**Watch out:** the invariant has to be restored in **every** place the data changes. It is easy to wrap the total in the constructor and then forget in `add_minutes`; the clock works until someone adds 90 minutes at 23:00. Put the wrapping in one helper and call it everywhere the total changes.

::: context invariant-word A word from mathematics
"Invariant" means "does not vary". Mathematicians use it for something that stays the same while everything else changes: however you cut up a pizza, the total amount of pizza is invariant. Programmers borrowed it for the rules a class promises to keep. Careful teams write their invariants down and check them. NASA's Jet Propulsion Laboratory, in its "Power of Ten" rules for safety-critical code, asks for at least two assertions per function on average: checks that stop the program loudly if a rule that should always be true turns out to be false.
:::

::: context half-open-day Why 1440 itself is left out
Minute 0 is midnight, 00:00. Minute 1439 is 23:59. Minute 1440 would be midnight again, the start of the next day, so it must wrap back to 0. A half-open range makes that automatic: the day has exactly 1440 allowed values, 0 to 1439, and the range [0, 1440) names them by writing the first one and the first one that is *not* allowed.

::: context remainder-sign Why C++ keeps the sign
C++ division of whole numbers cuts toward zero, so `-1 / 1440` is `0`. The remainder is then defined so that division and remainder always fit back together: `(a / b) * b + a % b` equals `a`. With `a = -1` that forces `a % b` to be `-1`. Other languages choose differently: in Python, `-1 % 1440` is `1439`. The same formula wraps compass headings too: `((h % 360) + 360) % 360` turns a heading of -90 degrees into 270.
:::

::: context static-members One copy for the whole class
Every `Clock` object has its own `total_`: two clocks, two totals. A static member has exactly one copy, shared by the whole class, however many clocks exist, even none at all. That is why a static member function has no object to work on, and cannot use `total_` or call `hours()`. From outside the class you would call a public one with the scope operator, read "from": `Clock::wrap(90)`, "wrap from Clock".
:::

::: context constexpr-meaning Worked out by the compiler
When the compiler sees `constexpr int kDay = 24 * 60;`, it works out 1440 itself while it builds your program, and writes that number wherever `kDay` is used. Nothing is multiplied while the program runs, and nothing can change `kDay` afterwards. Flight software leans on values like this: a fixed table size or a sensor's limit that is known for certain before launch should be a constant the compiler checks, not a variable that something might overwrite.
:::

=== cpp2-07 | Overloading and default arguments
--- teach
Last lesson your `Clock` turned numbers into text with `std::to_string`. You may have noticed that `std::to_string(7)` and `std::to_string(2.5)` both work, although one gets an `int` and the other a `double`. That is because `std::to_string` is not one function but several with the same name. This lesson shows how to write functions like that yourself, and how to let a caller leave out an argument.

### One name, several functions

In everyday speech one word can mean different things, and you tell which from what follows it: "play the piano" and "play football". C++ does the same with function names.

**Overloading** means giving several functions the same name, as long as their parameter lists differ: a different number of parameters, or different types.

```cpp
std::string area(int side)           { return "square"; }
std::string area(int w, int h)       { return "rectangle"; }
std::string area(double radius)      { return "circle"; }
```

Each version is a separate function. The return type alone does not count: two functions that differ only in what they return cannot share a name, because the call looks the same for both.

### How the compiler picks one

When you call `area`, the compiler looks at the arguments and picks the version that fits them best. This choosing is called **overload resolution**, and it happens while [[compiling|name-mangling]], not while the program runs.

```cpp
area(3);       // "square"    — 3 is an int: exact match
area(3, 4);    // "rectangle" — the only one with two parameters
area(1.5);     // "circle"    — 1.5 is a double: exact match
```

When no version is an exact match, the compiler ranks how much each argument would have to change. Roughly, from best to worst:

1. an **exact match**: the argument already has the parameter's type;
2. a **[[promotion|promotion]]**: a small, safe widening, like `char` to `int` or `float` to `double`;
3. a **standard conversion**: a change built into the language, like `int` to `double`, or *anything pointer-like* to `bool`;
4. a **user-defined conversion**: a change some class provides, like making a `std::string` out of a `const char*`.

If two versions tie for best, the call is **ambiguous**, read "could mean either", and it does not compile:

```cpp
long big = 3;
area(big);     // compile error: call to 'area' is ambiguous
```

A `long` is a bigger kind of whole number. Turning it into an `int` and turning it into a `double` are both standard conversions, so neither version wins.

### The string literal trap

That ranking hides a famous trap. A [[string literal|string-literal]] such as `"hi"`, text in double quotes, is not a `std::string`. C++ stores it as a row of `char`s and hands it over as a `const char*`: a pointer to its first character.

Now suppose there are two overloads, one for `bool` and one for `const std::string&`:

```cpp
std::string f(bool b)               { return "bool"; }
std::string f(const std::string& s) { return "string"; }

f("hi");       // "bool"!
```

Turning a pointer into a `bool` is a standard conversion (rank 3). Building a `std::string` from it is a user-defined conversion (rank 4). The standard conversion wins, so `f("hi")` quietly calls the `bool` version: any pointer that is not `nullptr` counts as `true`. No error and no warning.

The cure is an overload that takes `const char*` exactly. It wins because it is an exact match, and it can hand the work on to the string version:

```cpp
std::string f(const char* s) { return f(std::string(s)); }   // now f("hi") is "string"
```

`std::string(s)` builds a real `std::string` from the pointer, so the call inside picks the `const std::string&` version.

### Default arguments

Sometimes the difference between two versions is only a value the caller usually does not care about. A **default argument** is a value written into the parameter list, used whenever the caller leaves that argument out:

```cpp
std::string greet(const std::string& name, const std::string& greeting = "Hello") {
    return greeting + ", " + name;
}
greet("Ada");            // "Hello, Ada"
greet("Ada", "Hi");      // "Hi, Ada"
```

Two rules:

- Defaults go on the **rightmost** parameters only. The caller leaves arguments off the end, so C++ fills them in from the right.
- A default is written **once**. If the function has a separate [[declaration|declaration-once]] (a line announcing it, without its body), the default goes there and not on the body.

Use defaults for the common case. Use overloads when the *work* differs by type.

### Two tools for padding text

The task pads text on the left, which needs two more things.

`std::string(n, c)` makes a string of `n` copies of the character `c`:

```cpp
std::string stars(3, '*');    // "***"
```

And `s.size()` is a `std::size_t`, which is unsigned: it can never be negative. So `width - s.size()` goes badly wrong when `s` is already longer than `width`: instead of a negative number, it wraps round to a gigantic positive one. Check `s.size() >= width` first, and only subtract when the answer cannot be negative.

One last thing you will see in the task's starter: `describe(double)` builds its text with a [[string stream|to-string-double]] rather than `std::to_string`. It already works, so leave it as it is.

**Watch out:** the literal trap bites whenever a function has a `bool` overload (or any other overload a pointer converts to) next to a `std::string` one. Test the overloads with a plain `"text"` argument, not only with a `std::string` variable, because that is how people will call them.

::: context name-mangling How one name becomes several
The computer that runs your program never sees the name `area` on its own. The compiler gives each version a longer hidden name that spells out its parameter types. With g++ on Linux, `int area(int)` becomes `_Z4areai`, `int area(int, int)` becomes `_Z4areaii`, and `int area(double)` becomes `_Z4aread`: the `4` is the length of "area", and the letters after it are the parameter types. This is called **name mangling**. It is how the parts of a large program, compiled separately, still find the right version of each other's functions.
:::

::: context promotion Widening without losing anything
A promotion moves a value into a bigger type that can hold every value of the smaller one, so nothing is ever lost. A `char` is one byte and an `int` is usually four, so every `char` fits in an `int`. A `float` keeps about 7 significant digits and a `double` about 15, so every `float` fits in a `double`. A conversion like `double` to `int` is different: it can throw away the fraction or overflow, which is why C++ ranks it lower than a promotion.
:::

::: context string-literal What "hi" really is
In memory, `"hi"` is three bytes in a row: `'h'`, `'i'`, and a hidden zero byte that marks the end (the basics course mentioned it in the strings lesson). Its type is "array of 3 const chars". When you pass an array to a function, C++ passes a pointer to its first element instead, a rule called **decay**. That is how `"hi"` arrives as a `const char*`, and why it can turn into a `bool`.

=== cpp2-08 | enum class
--- teach
Last lesson you gave several functions one name and let the compiler pick by type. This lesson makes a new kind of type: one whose values are a short list of names you choose.

### A value that can only be one of a few things

A traffic light is red, amber or green. Nothing else. A compass direction is north, east, south or west. A rocket is on the pad, climbing, coasting or landed.

You could store these as numbers, 0 for red, 1 for amber, 2 for green, but then nothing stops a `7` sneaking in, and nobody reading `if (light == 2)` knows what 2 means. Better to give the values names and let the compiler check them.

An **enumeration** is a type whose values are a fixed list of names. Each name in the list is an **enumerator**. Modern C++ writes one with `enum class`:

```cpp
enum class Light { Red, Amber, Green };

Light now = Light::Red;
```

The first line makes a new type, `Light`, with exactly three values, and ends with `};` like a struct. The second makes a `Light` variable. `Light::Red` uses the scope operator `::`, read "from", as in `std::cout`: "Red from Light".

### Scoped names

The names live *inside* the enum, which is what "class" in `enum class` gives you: they are **scoped**. You must write `Light::Red`, never plain `Red`, so two enums can both have a `Red` without clashing:

```cpp
enum class Light { Red, Amber, Green };
enum class Alarm { Green, Red };      // fine: Light::Red and Alarm::Red are different
```

The [[older plain enum|plain-enum]] does not do this, which is one reason modern code prefers `enum class`.

### A number underneath, but not an int

Underneath, each enumerator is a whole number, counting from 0 in the order you listed them: `Red` is 0, `Amber` is 1, `Green` is 2.

But an `enum class` does **not** silently turn into an `int`. This does not compile:

```cpp
if (now == 2) { }    // compile error: a Light is not an int
```

That error catches real mistakes. When you do want the number, ask for it with `static_cast`, and turn a number back into the enum the same way:

```cpp
int n = static_cast<int>(Light::Amber);     // 1
Light l = static_cast<Light>(2);            // Light::Green
```

### switch: one branch for each value

To act on each value, use a **switch**. It compares one value with a list of `case` labels and jumps straight to the one that matches:

```cpp
std::string meaning(Light l) {
    switch (l) {
        case Light::Red:   return "stop";
        case Light::Amber: return "wait";
        case Light::Green: return "go";
    }
    return "";
}
```

Read it as: "look at `l`; in the case it is `Light::Red`, return `"stop"`", and so on. Each label ends with a colon `:`.

A case that does not `return` must end with **break**, which jumps out of the switch. Without it, the code **falls through**: it carries on running the next case's code too.

```cpp
switch (l) {
    case Light::Red:   std::cout << "stop\n"; break;
    case Light::Amber: std::cout << "wait\n"; break;
    case Light::Green: std::cout << "go\n";   break;
}
```

A `default:` label catches any value that no case lists.

The `return "";` after the first switch is never reached, because every value has a case. It is there because a `Light` can be forced to hold a number that is not on the list, such as `static_cast<Light>(7)`, and some compilers (g++, for one) warn that the function could end without returning anything.

### A free check from the compiler

Leave out the `default:` label and the compiler checks your cases for you. If you forget one, clang and g++ both warn, with a warning called `-Wswitch`:

```
warning: enumeration value 'Amber' not handled in switch [-Wswitch]
```

That is a [[free check every time|wswitch-check]] someone adds a new value to the enum later: every switch that forgot it lights up.

### Turning through the list with arithmetic

Sometimes the order of the list means something. For compass directions listed as North, East, South, West, [[turning right is moving one step along the list|compass-numbers]], and turning left is one step back. From West, turning right wraps round to North.

That is the wrapping you did on the clock, with 4 in place of 1440. Turn the enum into its number, add, wrap with `% 4`, and turn it back:

```cpp
enum class Direction { North, East, South, West };

Direction right_of_west = static_cast<Direction>((static_cast<int>(Direction::West) + 1) % 4);
// West is 3; 3 + 1 is 4; 4 % 4 is 0: North
```

To step back one, add 3 instead of subtracting 1. Three steps forward round a circle of four is the same as one step back, and it never goes negative. From North: 0 + 3 is 3, and 3 % 4 is 3, which is West. Subtracting would give 0 - 1, which is -1, and `-1 % 4` is `-1` in C++, which is not a direction at all.

### An enum inside a struct

An enum is a type like any other, so a struct can have one as a member, the way a spacecraft's record of its state might hold its [[current mode|flight-modes]] next to its position:

```cpp
struct Position {
    int x;
    int y;
    Direction facing;
};

Position p{0, 0, Direction::North};   // at (0, 0), facing North
p.y++;                                // one step north: now at (0, 1)
p.facing = Direction::East;
```

On a grid, a step North is `y + 1`, South is `y - 1`, East is `x + 1` and West is `x - 1`.

**Watch out:** forgetting `break` at the end of a case. The code compiles, and the program runs the next case as well. If the North case in a robot's switch forgot its `break`, an `'F'` while facing North would move the robot north *and then* east. Every case ends in `break` or `return`.

::: context plain-enum The older plain enum
Before C++11, C++ only had the plain `enum`, which it inherited from C: `enum Light { Red, Amber, Green };`. Its names spill out into the surrounding code, so you write plain `Red`, and a second enum with a `Red` in it will not compile. Its values also turn into `int` without asking, so `if (light == 2)` compiles happily. `enum class`, added in C++11, fixed both. You will still meet plain enums in older code and in C libraries.
:::

::: context wswitch-check Why leaving out default helps
A `default:` label means "anything else", so it also catches a value you forgot, silently. Without one, the compiler knows the full list of enumerators and can tell you which ones have no case. This matters most in big programs: add `Flashing` to `Light` a year from now, and every switch on a `Light`, in every file, is flagged at the next build. The app compiles with `-Wall`, which turns this warning on. Flight-software teams often go further and treat every warning as an error, so the program will not build until each new value is handled everywhere.
:::

::: context compass-numbers Four directions, four numbers
Put the numbers round a circle and turning becomes counting: right is +1, left is +3, and `% 4` brings 4 back to 0. The same idea works for any list that goes round in a loop, like the days of the week (`% 7`) or the clock's minutes (`% 1440`).

An `enum class` with a switch that the compiler checks is exactly how such a list of modes is written in modern C++.

=== cpp2-09 | std::optional: maybe a value
--- teach
Last lesson, `enum class` let a value be exactly one of a few named things. This lesson handles a different kind of answer: one that might not exist at all.

### When a function has no answer

Picture asking a librarian for a book. Usually they hand it to you. Sometimes the honest answer is "we do not have it". A function can be in the same spot. "Read this text as a number" has no answer for `"abc"`. "Find this name in the list" has no answer when the name is not there.

Older C++ code handles that with a **[[magic value|magic-values]]**: an ordinary-looking value, like `-1`, `0` or `""`, that everyone agrees to read as "no answer".

```cpp
int find_age(const std::string& name) {
    if (name == "Ada") return 36;
    return -1;   // magic value: "not found"
}
```

That works until `-1` is a real answer. A temperature of −1 degrees is a real reading, not "missing".

### A box that may be empty

Now picture a parcel with a window in it. You can see at a glance whether something is inside or whether it is empty. **`std::optional<T>`** is that parcel: a value that either holds one `T` or holds nothing, where `T` stands for any type you choose. Read `std::optional<int>` as "maybe an int". The type inside goes in angle brackets, the way it does in `std::vector<int>`, and it needs `#include <optional>`. Optional is one of the [[newer parts of C++|optional-history]].

```cpp
#include <optional>
#include <string>

std::optional<int> find_age(const std::string& name) {
    if (name == "Ada") return 36;    // a box holding 36
    return std::nullopt;             // an empty box
}
```

Returning `36` puts 36 in the box for you. **`std::nullopt`**, read "null optional", means the empty box: "no value".

### Looking inside

Before you use the value, ask whether there is one. An optional used as a condition is true when it holds a value:

```cpp
auto age = find_age("Bob");
if (age) {                  // true only when there is a value
    std::cout << *age;      // the star takes the value out
}
```

The star `*` in front, read "the value in", takes the value out of the box. It is the same symbol you used to [[follow a pointer|star-again]] in the basics course.

### A fallback value

Often you want "the value, or else this". **`value_or`** gives exactly that: the value if there is one, otherwise the fallback you hand it.

```cpp
int years = find_age("Bob").value_or(0);   // 0: Bob has no age
int ada = find_age("Ada").value_or(0);     // 36
```

### Comparing an optional

An optional compares directly with a value, and with `std::nullopt`:

```cpp
find_age("Ada") == 36             // true
find_age("Bob") == std::nullopt   // true
find_age("Bob") == 0              // false: an empty box equals no number
```

**Watch out:** never put `*` in front of an optional you have not checked. With nothing inside, `*age` is **undefined behaviour**: C++ makes no promise about what happens, and [[no error message will tell you|empty-star]]. Check with `if (age)` first, or use `value_or`.

### Decide the edge cases first

Before you write a parser (a function that reads text and turns it into a value), decide which texts count. Is `""` a number? Is a lone `"-"`? Is `" 7"`, with a space in front? Write your answers down first. That is half the work, and each answer becomes a test.

The parser in this lesson accepts an optional minus sign, then one to nine digits, and nothing else. Nine is the limit because [[ten digits can overflow an int|nine-digits]].

### From digit characters to a number

The text `"42"` is two characters, `'4'` and `'2'`, not the number 42. You already know `std::isdigit`, from `<cctype>`, which is true for a digit character; convert to `unsigned char` first, as in the basics strings lesson.

To get a digit's value, subtract the character `'0'`. Because the digit characters are [[stored as numbers in order|digit-codes]], `'7' - '0'` is 7.

Then build the number from left to right: multiply what you have so far by 10 and add the next digit.

```cpp
std::string s = "472";
int value = 0;
for (char c : s) {
    value = value * 10 + (c - '0');
}
// value went 0, 4, 47, 472
```

For a leading minus, remember that you saw one, read the digits, and flip the sign at the end with the conditional operator from the algorithms lesson: `negative ? -value : value`.

An optional can hold any type. A function that returns `std::optional<std::size_t>` puts an index in the box with an ordinary `return i;`, and returns `std::nullopt` when there is no index to give.

::: context magic-values The trouble with magic values
A value that secretly means "no answer" is also called a *sentinel*. You have met one already: `std::string::npos`, the huge number `find` returns for "not found". That one is safe, because no real string is that long. Most sentinels are not safe. If `-1` means "missing", a real −1 gets mistaken for missing. Worse, a caller who forgets to check does arithmetic with the −1 as if it were real, and the compiler cannot help, because −1 is an ordinary `int`. An `std::optional<int>` cannot be added to an `int` at all: you must take the value out first, which forces you to think about the empty case.
:::

::: context optional-history Where optional came from
`std::optional` joined the standard library in C++17, the version of C++ published in 2017. It grew out of `boost::optional`, from the Boost libraries, a large free collection where many ideas are tried before they enter the standard. Other languages have the same idea under other names: Rust has `Option`, and Swift writes a maybe-int as `Int?`. The idea is always the same: the type itself says the value might be missing, so the missing case cannot be forgotten.
:::

::: context star-again The same star, a similar job
In the pointers lesson, `*p` followed a pointer to the value it points at. Optional borrows that symbol on purpose, because the job is similar: `*age` means "the thing inside". An optional and a pointer can both be empty, and using `*` on an empty one is a mistake in both cases. The difference is where the value lives. An optional keeps its value inside itself, so there is no separate memory, no `new` and no `delete`.
:::

::: context empty-star Why the star does not check
`*age` does no checking, for the same reason `v[i]` does no checking: checking costs a little time on every use, and C++ lets you skip it when you have already checked. There is a checked way, `age.value()`, which stops the program with an error when the box is empty, much like `v.at(i)` for vectors. Stopping loudly is far better than carrying on with a garbage number, which is why careful code checks first and uses `*` only inside the `if`.
:::

::: context nine-digits Why stop at nine digits
The largest `int` is 2,147,483,647, which has ten digits. Every nine-digit number, up to 999,999,999, fits easily, but many ten-digit numbers, such as 9,999,999,999, do not. Building a number past the largest `int` is overflow, which is undefined behaviour. Allowing at most nine digits is a simple rule that makes overflow impossible, at the cost of turning away a few numbers that would fit. Overflow has cost rockets: in 1996, Ariane 5 Flight 501 was destroyed about 40 seconds after launch when a 64-bit floating-point value was converted to a 16-bit integer that could not hold it. A debugging lesson later in this course comes back to overflow.
:::

::: context digit-codes Characters are small numbers
Inside the computer, every `char` is stored as a number, its *character code*. In ASCII, the code used for plain English text, `'0'` is 48, `'1'` is 49, and so on up to `'9'`, which is 57. So `'7' - '0'` is 55 − 48, which is 7. The C++ standard promises that the ten digit characters always sit next to each other in order, on every computer, so subtracting `'0'` is always correct. It makes no such promise for letters.

#include <cctype>
#include <optional>
#include <string>
#include <vector>

std::optional<int> parse_int(const std::string& s) {
    std::size_t i = 0;
    bool negative = false;
    if (i < s.size() && s[i] == '-') {
        negative = true;
        ++i;
    }
    std::size_t digits = s.size() - i;
    if (digits == 0 || digits > 9) return std::nullopt;
    int value = 0;
    for (; i < s.size(); ++i) {
        if (!std::isdigit(static_cast<unsigned char>(s[i]))) return std::nullopt;
        value = value * 10 + (s[i] - '0');
    }
    return negative ? -value : value;
}

std::optional<std::size_t> index_of(const std::vector<std::string>& v, const std::string& target) {
    for (std::size_t i = 0; i < v.size(); ++i) {
        if (v[i] == target) return i;
    }
    return std::nullopt;
}

int sum_valid(const std::vector<std::string>& items) {
    int total = 0;
    for (const auto& item : items) {
        total += parse_int(item).value_or(0);
    }
    return total;
}

--- hint

Otherwise build the number with `value = value * 10 + (s[i] - '0');`, and at the end return `negative ? -value : value`. `index_of` is a plain loop over the indexes that does `return i;` on the first match and `return std::nullopt;` after the loop.
--- hint
`sum_valid` keeps a running `total` and, for each item, adds `parse_int(item).value_or(0)`: a string that does not parse adds 0.

=== cpp2-10 | Lambdas and captures
--- teach
Last lesson, `std::optional` gave functions a way to say "no answer". You have been reading small unnamed functions since the basics course, in the checks, and you wrote a few for `count_if` and `find_if` in the algorithms lesson. This lesson covers them properly, including how they reach the variables around them.

### A function written on the spot

Picture a sticky note with one instruction on it, stuck right where you need it, instead of a full recipe filed away in a book. A **lambda** is that: a small function with no name, written right where it is used.

```cpp
auto square = [](int x) { return x * x; };
int s = square(5);   // 25
```

It has three parts. The square brackets `[]` are the **capture list** (more on that in a moment). The round brackets `(int x)` are the parameters, as in any function. The curly braces `{ … }` are the body. You can keep a lambda in an `auto` variable and call it like any function.

### Capturing a copy

A lambda's body cannot see the local variables around it unless you list them in the brackets. That list is the capture list: it says which outside variables the lambda may use. A plain name, like `[limit]`, **captures by copy**: the lambda keeps its own copy, taken at the moment the lambda is made.

```cpp
int limit = 10;
auto over = [limit](int x) { return x > limit; };
limit = 0;
bool b = over(5);   // false: the lambda kept its own 10
```

Changing `limit` afterwards does not reach the lambda. Each lambda you make is an [[object that carries its captures|closure]] around with it.

### Handing a lambda to an algorithm

The everyday use is handing a lambda to an algorithm. **`std::copy_if`**, from `<algorithm>`, copies every element that passes a test. It takes the range (`begin()` and `end()`), a place to write, and the test:

```cpp
std::vector<int> v = {4, 15, 8, 23};
int limit = 10;
std::vector<int> out;
std::copy_if(v.begin(), v.end(), std::back_inserter(out),
             [limit](int x) { return x > limit; });
// out is {15, 23}, in their original order
```

**`std::back_inserter(out)`**, from `<iterator>`, is the place to write: [[it calls push_back for you|back-inserter]], so `out` grows by one for each value that passes.

### Capturing by reference

Sometimes the lambda should change a variable outside it. Put `&` in front of the name, read "reference to", exactly as in the references lesson. Now the lambda uses the caller's own variable, not a copy:

```cpp
std::vector<int> v = {3, 1, 2};
int calls = 0;
std::sort(v.begin(), v.end(), [&calls](int a, int b) { ++calls; return a < b; });
// calls now holds how many times sort compared two values
```

Here is every kind of capture in one table:

| Capture | Meaning |
| --- | --- |
| `[]` | nothing from outside |
| `[limit]` | a copy of `limit`, taken when the lambda is made |
| `[&total]` | a reference to `total`: the lambda can change it |
| `[=]` / `[&]` | everything it uses, by copy / by reference |
| `[n = 0]` | a new variable living inside the lambda |

The two short forms `[=]` and `[&]` save typing, but [[naming each capture|capture-all]] shows the reader exactly what the lambda touches.

### A lambda with its own memory

The last row is an **init capture**: `[n = 0]` makes a brand-new variable `n` that belongs to the lambda, starting at 0. The copies a lambda holds are read-only unless you mark the lambda **`mutable`**, which means "allowed to change its own copies". Together they give a lambda **state**: a value it remembers between calls.

```cpp
auto next_id = [id = 100]() mutable { return id++; };
next_id();   // 100
next_id();   // 101
```

Without `mutable`, clang stops with "cannot assign to a variable captured by copy in a non-mutable lambda". Two lambdas made separately each get their own `id`, so they count separately.

A function can hand back a lambda. The lambda's type has no name you could write, so declare the function's return type as `auto` and let the compiler fill it in:

```cpp
auto make_greeter() {
    return [](const std::string& name) { return "Hello, " + name; };
}
```

**Watch out:** do not capture a local variable **by reference** in a lambda that outlives it. When the function that made the lambda ends, its local variables are gone, and the reference [[dangles|dangling]]: it names memory that no longer holds that variable. Using it is undefined behaviour, and it compiles without complaint.

```cpp
auto make_bad() {
    int count = 0;
    return [&count]() { return ++count; };   // count dies when make_bad ends
}
```

When a lambda leaves the function that made it, for instance when you return it, capture by value or with an init capture.

### Sorting with a lambda

`std::sort` can take a third argument, a **comparator**: a lambda that gets two values `a` and `b` and returns true when `a` should come **before** `b`. With `a < b` you get the usual smallest-first order. Change the test, and you change the order.

To sort by how close each value is to some target, compare distances. **`std::abs`**, from `<cstdlib>`, gives the size of a number without its sign: `std::abs(3 - 8)` is 5. And when two distances are equal, [[say which comes first|strict-order]], or the order of those two is up to `sort`. Here, sorting by closeness to 0 (the size of each value), with the smaller value first on a tie:

```cpp
std::vector<int> v = {3, -1, -3, 2};
std::sort(v.begin(), v.end(), [](int a, int b) {
    int da = std::abs(a);
    int db = std::abs(b);
    if (da != db) return da < db;   // closer to 0 comes first
    return a < b;                   // same distance: smaller value first
});
// v is {-1, 2, -3, 3}
```

::: context closure What the compiler builds
A lambda is shorthand. For each lambda, the compiler writes a small class with no name you can use: every captured variable becomes a member of it, and the body becomes the function that runs when you call it. The object made from that class is called a *closure*. That is why each counter made by the same code has its own count: each is its own object with its own member.

::: context back-inserter Writing past the end, safely
Algorithms like `copy_if` write through an iterator: "put the value here, then move one along". If you passed `out.begin()` of an empty vector, there would be no room, and writing there would be undefined behaviour. The algorithms lesson avoided that by making `out` the right size first. When you do not know how many values will pass the test, that is impossible, so `std::back_inserter` gives a different kind of iterator: writing through it calls `out.push_back(value)`, and the vector grows exactly as needed.
:::

::: context capture-all Name what you capture
`[=]` and `[&]` capture whatever the body happens to use, which hides from the reader what the lambda depends on. The C++ Core Guidelines, a widely used rule book, suggest capturing by reference for lambdas used right there, such as one handed straight to `std::sort`, and avoiding reference captures for lambdas that are stored or returned. Naming each capture makes that choice visible, one variable at a time.
:::

::: context dangling Why the reference dangles
A function's local variables live in a piece of memory set aside for that call, and the piece is handed back the moment the function returns. A reference captured from inside still points at that spot, but the spot now belongs to whatever runs next. Reading it may give the old value, a stranger's number, or a crash; writing it can damage another function's data. Compilers often cannot see this mistake. Sanitizer tools, which add checks while the program runs, catch many cases, but the dependable fix is to capture by value.
:::

::: context strict-order The rules a comparator must follow
`std::sort` trusts its comparator to behave like "less than". In particular, it must return false when `a` and `b` are equal. So write `<`, never `<=`: with `<=`, two equal values would each claim to come before the other, and the C++ rules call sorting with such a comparator undefined behaviour. Breaking ties with a second test, as here, keeps the comparator a proper "less than" and makes the result the same on every computer.
:::

=== cpp2-11 | Processing text with string streams
--- teach
Last lesson you handed small lambdas to algorithms. This lesson turns to text. Real input is messy: extra spaces, blank lines, fields separated by commas, a number with junk stuck to it. Here you learn to cut text into pieces, clean each piece, and check it.

### Reading from a string

In the basics map lesson you read words out of a string with a **`std::istringstream`** (input string stream, from `<sstream>`). It reads from a string exactly as `std::cin` reads from the input, and `>>`, read "get from", reads any type:

```cpp
std::istringstream in("3 apples 4.5");
int n;
std::string what;
double w;
in >> n >> what >> w;   // n is 3, what is "apples", w is 4.5
```

Each `>>` skips spaces, then reads the next piece as the type of its variable.

### When a read fails

If the next text is not a number, `in >> n` **fails**. A stream that has failed counts as false in a condition, so you can test a read directly. After a failed read, `n` is set to 0, and [[the stream stops reading|failed-read]].

```cpp
std::istringstream bad("abc");
int n;
if (!(bad >> n)) {
    // "abc" is not a number: we get here
}
```

The `!` means "not", so the condition reads "if the read did not work".

### One line at a time

`std::getline(stream, line)`, from the basics course, reads up to the end of a line. In a `while` loop it reads every line of a block of text, and stops when the lines run out:

```cpp
std::istringstream text("first\nsecond\n");
std::string line;
while (std::getline(text, line)) {
    // runs twice: line is "first", then "second"
}
```

The `\n` is the [[newline character|escapes]], written inside quotes as a backslash and `n`.

### Up to any character

Give `getline` a third argument, a `char`, and it reads up to that character instead of the end of the line. The separator itself is thrown away:

```cpp
std::istringstream row("ALT,4200,OK");
std::string field;
while (std::getline(row, field, ',')) {
    // field is "ALT", then "4200", then "OK"
}
```

**Watch out:** this way of splitting quietly [[drops a trailing empty field|trailing-field]]. Splitting `"a,b,"` gives two fields, `"a"` and `"b"`, not three, and splitting `""` gives none at all. When empty fields matter, cut the string yourself with `find` and `substr`.

### Cutting by hand with find and substr

You know `find` and `substr` from the basics course. Find the separator, then cut on either side of it:

```cpp
std::string s = "key=value";
auto eq = s.find('=');                 // 3, or std::string::npos if there is none
std::string key = s.substr(0, eq);     // "key"
std::string val = s.substr(eq + 1);    // "value"
```

`find` can also take a second number: the index to start looking from. That lets you find the next separator after the one you already found:

```cpp
std::string t = "a,b,c";
t.find(',');      // 1
t.find(',', 2);   // 3: starts looking at index 2
```

To split a whole string, keep a `start` index. Find the next separator from `start`, take the piece between them, and move `start` to just after the separator. When `find` gives `npos`, there are no more separators, and everything from `start` to the end is the last field, even if it is empty.

### Trimming whitespace

**Whitespace** means the invisible characters: spaces, tabs (`\t`) and newlines (`\n`). **Trimming** a string means removing whitespace from both ends and keeping everything between. `std::isspace` from `<cctype>` recognises [[all kinds of whitespace|whitespace-kinds]]; convert to `unsigned char` first, as always.

The idea is two indexes that walk inward. One starts at the front and steps forward past whitespace:

```cpp
std::string s = "  hi";
std::size_t a = 0;
while (a < s.size() && std::isspace(static_cast<unsigned char>(s[a]))) ++a;
// a is 2, so s.substr(a) is "hi"
```

The other starts at the end and steps backward the same way. What is left between them is the trimmed string.

### Is the whole field a number?

`>>` stops reading a number at the first character that is not part of it. So `"12abc"` reads as 12, and the read **succeeds**. To be sure the whole field was a number, check two things: the read worked, **and** nothing but spaces is left afterwards.

```cpp
std::istringstream num(" 42 ");
int n;
if (num >> n) {
    num >> std::ws;      // skip any spaces after the number
    if (num.eof()) {
        // the whole field was a number
    }
}
```

`std::ws`, "skip white space", which you met in the basics course, eats spaces. Then **`eof()`**, short for [["end of file"|eof]], is true when the stream has reached the end of its text. For `"12abc"`, the `abc` is still there, so `eof()` is false and you know to reject it.

::: context failed-read What a failed read does
When `>>` cannot read what you asked for, the stream sets a "failed" flag inside itself. Since C++11, the variable you were reading into is set to 0. While the flag is set, every later `>>` on that stream also fails and reads nothing, until you call `in.clear()`. That is why `while (in >> w)` stops cleanly at the first bad piece or the end of the text. It is also why the check in this lesson gives each score its own small stream: one bad line cannot jam the reading of the next.
:::

::: context escapes Characters you cannot type in quotes
Some characters cannot be typed straight into a string, so C++ writes them with a backslash and a letter, called an *escape sequence*. `\n` is the newline, `\t` a tab, `\\` a real backslash and `\"` a double quote inside a string. Each one is a single character, even though you type two: `"a\nb"` has three characters, and its `size()` is 3.
:::

::: context trailing-field The field that goes missing
`getline` stops when there is nothing left to read. After `"a,b,"` it has read `a` and `b`, and the last comma leaves nothing after it, so the loop ends: there is no empty third field. In a spreadsheet file, though, `a,b,` means three columns with the third empty. Dropping it quietly shifts meaning. If a telemetry row lists readings in fixed columns and the last reading is missing, a program that loses the empty field may read the wrong number of columns and misplace everything after.

::: context whitespace-kinds More whitespace than you think
`std::isspace` is true for six characters: space, tab `\t`, newline `\n`, carriage return `\r`, and two rarely seen ones, vertical tab `\v` and form feed `\f`. The carriage return matters in practice. Text files saved on Windows end each line with `\r\n`, so `getline`, which stops at `\n`, leaves a stray `\r` at the end of every line. It is invisible when printed, but `"ALT\r"` is not equal to `"ALT"`. Trimming each field removes it.
:::

::: context eof Why "end of file"
Streams were first used mostly for reading files, so reaching the end of the text is called *end of file*, even when the stream reads from a string. `eof()` becomes true only once a read has actually bumped into the end. That is why the check reads with `>> std::ws` first: skipping the trailing spaces runs into the end, and only then does `eof()` report it.

#include <cctype>
#include <map>
#include <sstream>
#include <string>
#include <vector>

std::vector<std::string> split(const std::string& s, char sep) {
    std::vector<std::string> out;
    std::size_t start = 0;
    while (true) {
        std::size_t at = s.find(sep, start);
        if (at == std::string::npos) {
            out.push_back(s.substr(start));
            return out;
        }
        out.push_back(s.substr(start, at - start));
        start = at + 1;
    }
}

std::string trim(const std::string& s) {
    std::size_t a = 0;
    std::size_t b = s.size();
    while (a < b && std::isspace(static_cast<unsigned char>(s[a]))) ++a;
    while (b > a && std::isspace(static_cast<unsigned char>(s[b - 1]))) --b;
    return s.substr(a, b - a);
}

std::map<std::string, int> parse_scores(const std::string& text) {
    std::map<std::string, int> scores;
    std::istringstream lines(text);
    std::string line;
    while (std::getline(lines, line)) {
        std::size_t colon = line.find(':');
        if (colon == std::string::npos) continue;
        std::string name = trim(line.substr(0, colon));
        if (name.empty()) continue;
        std::istringstream num(line.substr(colon + 1));
        int score;
        if (!(num >> score)) continue;
        num >> std::ws;
        if (!num.eof()) continue;
        scores[name] = score;
    }
    return scores;
}

--- hint
For `trim`, keep one index `a` at the front and one index `b` at `s.size()`. Move `a` forward while `s[a]` is whitespace, move `b` backward while `s[b - 1]` is whitespace (never letting them cross), then return `s.substr(a, b - a)`.

=== cpp2-11b | Building text with std::ostringstream
--- teach
Last lesson you took text apart: splitting it, trimming it, and reading numbers out of it. This lesson goes the other way and builds text up, with numbers written exactly the way you want them.

### Writing to a string

Picture writing on a notepad instead of shouting across the room. `std::cout` sends text straight to the screen. A **`std::ostringstream`** (output string stream, from `<sstream>`) collects the text instead, and hands it over as a `std::string` when you ask. You write to it with `<<`, read "put to", exactly as you write to `std::cout`. Then **`.str()`** gives you everything written so far:

```cpp
std::ostringstream out;
out << "ALT=" << 4200 << " m";
std::string line = out.str();   // "ALT=4200 m"
```

Numbers turn into text on their own, the same way they do when you print them.

### A fixed number of decimal places

Readings often need a set number of decimal places. The header `<iomanip>` (input/output manipulators) has the tools. **`std::fixed`** says "write numbers with a decimal point, never in [[the e-notation style|scientific]]". **`std::setprecision(n)`**, with `std::fixed`, says "exactly `n` digits after the point". The number is rounded to fit:

```cpp
std::ostringstream out;
out << std::fixed << std::setprecision(1) << 3.14159;
// out.str() is "3.1"
```

These settings [[stay on the stream|sticky]] until you change them, so every later `double` written to `out` also gets one decimal place. They even add zeros: with `std::setprecision(2)`, the value 7.0 is written `7.00`.

**Watch out:** `std::setprecision` without `std::fixed` means something else: the number of *significant* digits, counted from the first non-zero digit. With `std::setprecision(2)` alone, 3.14159 becomes `3.1`, which looks right, but 1234.5 becomes `1.2e+03`. Always put `std::fixed` in front when you mean decimal places.

### A list with separators

To write a list like `3, 1, 4`, put the separator **before** every item except the first. Then there is no stray separator at either end:

```cpp
std::vector<int> v = {3, 1, 4};
std::ostringstream out;
for (std::size_t i = 0; i < v.size(); ++i) {
    if (i > 0) out << ", ";
    out << v[i];
}
// out.str() is "3, 1, 4"
```

An empty vector writes nothing, and one value is written alone. You will use these tools again at the end of this course, when [[a report gets its own function|comes-back]].

::: context scientific What 1.2e+03 means
`1.2e+03` is *scientific notation*, the computer way of writing $1.2 \times 10^3$, which is 1200. The `e` stands for "exponent": the power of ten. Very large and very small numbers are easier to read this way: the distance to the Moon, about 384,400 km, is 3.844e+05 km. Without `std::fixed`, a stream switches to this style whenever a number has more digits before the point than the precision allows, or is very small, so a column of readings can suddenly change style halfway down. `std::fixed` stops that.
:::

::: context sticky Settings that stay
`std::fixed` and `std::setprecision` change the stream itself, not just the next number, so they stay until you change them again. That is handy for writing a whole table. It is also a trap if you share `std::cout` with other code: set it to one decimal place, and every number printed afterwards has one decimal place. A fresh `std::ostringstream` for each piece of text keeps the settings from leaking. One manipulator is different: `std::setw`, which sets a column width, applies only to the next item.
:::

::: context comes-back Where this comes back
The design lesson at the end of this course has you tidy up a program that builds a report of readings. Its summary line uses exactly these tools: an `std::ostringstream`, `std::fixed` and `std::setprecision(1)`. Building the text in a string first, instead of printing it straight away, also makes a function easy to test, because a check can compare the string it returns.
:::

=== cpp2-12 | Debugging: off by one, out of range
--- teach
Last lesson you built text with a string stream. This one is a debugging lesson: you get a bug report and a broken function, and your job is to find the cause and fix it there. The bug is the most common one in loops.

### The fence-post mistake

A fence 10 metres long, with a post every metre, needs 11 posts, not 10: one at each end. Counting the gaps when you meant the posts, or the other way round, is so easy that it has a name. An **off-by-one** error means a loop runs one time too many, or one time too few. It is also called a [[fence-post error|fence-post]].

In C++ it is dangerous, because `v[i]` does no checking, as you saw in the basics vector lesson. Reading one past the end does not stop the program. It reads [[whatever memory happens to be there|past-the-end]] (undefined behaviour) and carries on with a wrong number.

### A method for loops that misbehave

**1. Reproduce small.** Pick an input so small that you can work out the right answer by hand. `{1, 2, 3, 4}` is better than a thousand readings.

**2. Trace the boundaries.** Write down the first and last value of every loop variable, and the largest index it touches. For a `v` of size 4, the valid indexes are 0 to 3. Anything that reaches 4 is a bug:

```cpp
for (std::size_t i = 0; i <= v.size(); ++i) {   // i runs 0, 1, 2, 3, 4
    sum += v[i];                                // v[4] is past the end
}
```

`<=`, "less than or equal", lets `i` reach `v.size()` itself. `<`, "less than", stops one earlier, at the last real index.

**3. Check the edge inputs.** Try an empty vector, a vector of one element, and the sizes where the loop condition flips from true to false. Bugs cluster at the edges.

**4. Make out-of-range loud while you look.** Swap `v[i]` for `v.at(i)`. `at` checks the index, and when it is out of range it [[stops the program at once|at-cost]] with an `std::out_of_range` error, instead of handing back garbage.

### Windows of values

The function in this lesson's bug report adds up **windows**: every run of `k` values that sit next to each other. For `{1, 2, 3, 4}` and `k` of 2, the windows are `{1, 2}`, `{2, 3}` and `{3, 4}`, and their sums are 3, 5 and 7.

A window starting at index `i` uses `v[i]` up to `v[i + k - 1]`: exactly `k` values. A vector of size 4 has 4 − 2 + 1 = 3 windows of size 2, starting at 0, 1 and 2.

### The sneakier trap: unsigned wrap-around

`v.size()` gives a `std::size_t`, which is **unsigned**: it cannot be negative. So when an answer would go below zero, it does not. It [[wraps round to a huge number|wrap-around]] instead:

```cpp
std::vector<int> v = {1, 2};
std::size_t k = 3;
std::size_t gap = v.size() - k;   // not -1: 18446744073709551615
```

A loop like `for (i = 0; i <= v.size() - k; ++i)` then runs almost forever, reading far outside the vector.

### Fix the cause

The cause-level fix is to write the condition so it never subtracts at all. `i <= v.size() - k` and `i + k <= v.size()` say the same thing when nothing wraps, because you move `k` to the other side. The second form only adds, so it cannot go below zero, and when `k` is bigger than the vector it is false straight away.

Then handle the impossible cases up front. A window of size 0 holds nothing, so when `k == 0`, return an empty result before the loop.

**Watch out:** do not patch the symptom. Adding `if (k > v.size()) return {};` in front of the wrong condition makes the crash go away for today's input, but the risky subtraction is still there, one careless edit away from wrapping again. Rewrite the condition itself. And do not wait for the compiler: `-Wall -Wextra` gives no warning for either version, so the tracing is up to you.

::: context fence-post Why "fence post"
The name comes from exactly the puzzle in the explanation: a straight fence of 10 sections needs 11 posts. In code, it shows up whenever you mix up counting things with counting the gaps between them. A range from index 3 to index 7, both included, holds 7 − 3 + 1 = 5 values, not 4. The window count in this lesson, `size - k + 1`, has the same "+ 1" for the same reason.

::: context past-the-end What sits one past the end
A vector's elements sit side by side in one block of memory. The bytes right after the last element belong to something else: spare room the vector has reserved, or another variable entirely. Reading there gives you whatever those bytes hold, and writing there can quietly damage other data. Tools called sanitizers catch many of these reads while the program runs; with g++ or clang you turn one on with `-fsanitize=address`. They slow the program down, so they are used while testing, not in the final build.
:::

::: context at-cost Why [] does not check
Checking every index takes a comparison each time, and in a tight loop over millions of values C++ lets you skip it. `at` is the checked version for when you want safety over speed. Flight software aims to make the check unnecessary instead. NASA JPL's "Power of Ten" rules require every loop to have a fixed upper bound that a checking tool can prove, and ask code to check that the values handed to a function are valid. A loop whose bound can wrap around to 18 quintillion breaks both rules.
:::

::: context wrap-around A counter that rolls over
Picture a car's trip counter rolling back from 000.0 to 999.9 when it goes backwards: an unsigned number going below 0 wraps to its largest value. On a 64-bit computer that is 18,446,744,073,709,551,615, which is 2⁶⁴ − 1. So 2 − 3 gives that number, not −1. C++ defines this wrap-around for unsigned numbers on purpose, so there is no warning. Many experts, including C++'s creator Bjarne Stroustrup, have said that making sizes unsigned was a mistake. C++20 added `std::ssize(v)`, which gives the size as a signed number that can go below zero.
:::

=== cpp2-13 | Debugging: overflow and uninitialised values
--- teach
Last lesson, "Debugging: off by one, out of range", you chased loops that ran one step too far and a subtraction that wrapped round to a huge number. Those bugs often end in a crash, which at least tells you something is wrong. This lesson is about two bugs that give you a number that is quietly **wrong**, with no crash and no error message to point at them.

### Bug one: a number too big for its box

Picture the mileage counter in an old car. It has six digits, so after 999,999 miles it rolls over to 000,000. The car did not travel backwards; the counter ran out of room.

An `int` is a box of fixed size too. It holds whole numbers up to 2,147,483,647, about 2 billion. Going past the top is called **integer overflow**: a result too big for the type that holds it.

```cpp
int a = 2000000000;    // 2 billion: fits
int b = 2000000000;    // fits
int c = a + b;         // 4 billion does not fit in an int
```

For an `int`, which can be negative (a **signed** type), overflow is **[[undefined behaviour|ub-overflow]]**: the C++ rules make no promise at all about what happens. In practice you usually get a [[large negative number|wrap-around]]. Here `c` usually comes out as -294,967,296. But the compiler is also allowed to assume overflow never happens, and plan the rest of the program around that, so the wrong answer can change from one build to the next.

### The fix: a box big enough for the result

The cure is to pick a type big enough for the **result**, not only for the inputs. The basics course met `long long`, which goes up to about 9 × 10¹⁸ (a 9 with 18 more digits after it). Two `int`s that each fit can still add up to a total that does not, so think about the biggest total, not the biggest single value. Real systems have failed because a count kept growing until it [[outgrew its type|boeing-counter]].

### Where overflow hides: std::accumulate

A classic hiding place is `std::accumulate`, from the `<numeric>` header, which you met in the `<algorithm>` lesson. It adds up a range, and it does the adding in the **type of its starting value**, the last thing you pass it:

```cpp
std::vector<int> v = {2000000000, 2000000000};
std::accumulate(v.begin(), v.end(), 0);     // int arithmetic: overflows
std::accumulate(v.begin(), v.end(), 0LL);   // long long: 4000000000
```

The only difference is the starting value. `0` on its own is an `int`. The letters `LL` stuck on the end, read "long long", make `0LL` a [[long long zero|literal-types]], so every step of the adding happens in the big box.

**Watch out:** declaring the function as returning `long long` does not help. The damage is done inside, during the adding, before the result is converted to `long long` on the way out. The same is true of a plain sum:

```cpp
long long r = a + b;                            // still overflows: a + b is int arithmetic
long long s = static_cast<long long>(a) + b;    // 4000000000
```

In the second line, `static_cast<long long>(a)` turns `a` into a `long long` first, so the `+` happens in the big box.

### Bug two: a variable with no starting value

`int lowest;` does not mean zero. A local variable made without a starting value (an **initialiser**) holds [[whatever was left in that memory|leftover-memory]]. Reading it before you store something in it is undefined behaviour too: the program may seem to work today and fail tomorrow.

```cpp
int lowest;            // no initialiser: leftover junk
int count = 0;         // initialised: really 0
```

### How to hunt both

- **Read the warnings.** Compile with `-Wall` ("warn all") and `-Wextra` ("warn extra"), the way this checker does. Compilers flag many uninitialised reads, but [[not every one|warnings-not-enough]], so a clean compile is not proof.
- **Test the edges** where these bugs live: very large values, lists that are all negative or all positive, and a list with a single element.
- **Fix the cause.** For "smallest so far", start from the first real element, `temps[0]`. Do not start from 0, which breaks on all-positive data: for `{5, 7, 9}` nothing is below 0, so you would get 0, a temperature that is not even in the list. And do not start from a guess like 1000, which breaks the day every reading is above it.

```cpp
int lowest = temps[0];   // a value that is really in the list
```

::: context ub-overflow What "undefined" lets the compiler do
Because signed overflow is undefined, the compiler may assume it never happens, and use that to make code faster. For example, it may decide that `x + 1 > x` is always true for an `int x` and delete the check completely, even though with wrap-around it would be false for the largest `int`. So a test you wrote to catch overflow can vanish from the program. That is why the fix is to prevent overflow with a big enough type, not to detect it afterwards. Unsigned types, like `std::size_t` from the last lesson, are different: their wrap-around is defined by the rules, which is why that bug was predictable.
:::

::: context wrap-around Why too big turns negative
An `int` is 32 bits. In the pattern computers use for signed numbers, called two's complement, the counting runs up to 2,147,483,647 and the very next bit pattern means -2,147,483,648, the most negative `int`. So on real machines, stepping past the top usually lands you at the bottom, like the car's mileage counter rolling over. 4,000,000,000 is 4,294,967,296 too much for 32 bits, and 4,000,000,000 − 4,294,967,296 = −294,967,296.

::: context boeing-counter A counter that grounded airliners
In 2015 the US Federal Aviation Administration ordered a fix for the Boeing 787. A software counter in the generator control units, which manage the plane's electrical power, would overflow if the units stayed powered on for 248 days without a restart. When that happened, the units could go into a safe mode and the aircraft could lose all its electrical generators, even in flight. The number 248 is no accident: counting hundredths of a second, a signed 32-bit counter runs out after 2,147,483,647 ÷ 100 ÷ 86,400 ≈ 248.6 days. Until the software was fixed, airlines had to switch the power off and on at regular intervals.
:::

::: context literal-types Numbers written in code have types too
A number typed straight into code is called a **literal**, and each one has a type. `0` is an `int`, `0LL` is a `long long`, and `0.0` is a `double`. That matters for `std::accumulate` in both directions. Add up a vector of `double`s with a starting value of `0` and every step is cut back to a whole number: summing `{0.5, 0.5, 0.5}` gives 0, not 1.5. Start from `0.0` and you get 1.5. The rule is the same one: the starting value picks the type of the adding.
:::

::: context leftover-memory Why C++ does not clean up for you
A function's local variables live in a scratch area of memory called the stack, which is reused over and over as functions are called and return. A new variable gets space that some earlier function was using, and whatever that function left there is still sitting in it. Setting every new variable to zero would cost a little time, and C++ was designed not to spend time you did not ask for. Variables declared outside every function are different: they always start at zero. Coding rules for cars and aircraft, such as MISRA, forbid reading any variable before it has been given a value.
:::

::: context warnings-not-enough Warnings help, but do not catch everything
With the same flags, g++ warns that `lowest` in this lesson's starter "may be used uninitialized", but clang++, the compiler this app runs, says nothing about it: the read happens inside a loop, which is harder to analyse. So treat warnings as free help, and still test. NASA JPL's "Power of Ten" rules for safety-critical code ask for every warning to be turned on from the first day, and for the code to compile with no warnings at all.
:::

=== cpp2-14 | Problem solving: two that add up
--- teach
In the last lesson, "Debugging: overflow and uninitialised values", you were handed a broken program and a bug report. This lesson hands you only a problem. There is no code yet: you design the **[[algorithm|algorithm-word]]**, the step-by-step method, yourself.

### A reliable way in

Engineers attack a new problem in four steps:

1. **Restate** the problem in your own words and pin down exactly what the answer looks like.
2. **Work examples** by hand, including the awkward ones: the same value twice, negative numbers, no answer at all.
3. **Brute force first.** What is the obvious solution, and how slow is it?
4. **Find the pattern** that removes the wasted work.

### Step 1: restate it

Given a list of numbers and a target, find two **different positions** whose values add up to the target.

For `{2, 7, 11, 15}` and target 9, the answer is positions 0 and 1, because 2 + 7 = 9. Notice the answer is the positions, not the values.

### Step 2: work some examples

- `{3, 3}` with target 6: positions 0 and 1. The same value may appear twice.
- `{3, 2, 4}` with target 6: positions 1 and 2 (2 + 4). Not 0 and 0: 3 + 3 is 6, but that uses one position twice.
- `{1, 2, 3}` with target 100: no answer.

### Step 3: brute force

**Brute force** means trying every possibility. Here that is every pair of positions, with two loops, one inside the other:

```cpp
for (int i = 0; i < n; ++i)
    for (int j = i + 1; j < n; ++j)
        if (nums[i] + nums[j] == target) { /* found */ }
```

Starting `j` at `i + 1` means each pair is tried once and never a position with itself. That is about n²/2 pairs (n² is read "n squared", n times n), so [[the work grows very fast|pairs-grow]]. For 10 numbers it is nothing. For 200,000 numbers it is 20 **billion** pairs, far too slow.

### Step 4: find the pattern

Walk through the numbers once, from left to right. When you are standing on value `x` at position `j`, you need some **earlier** value equal to `target - x`. That missing partner is called the **complement**.

So the question at each step is: "have I already seen `target - x`, and where?" Keep a notebook of every earlier value and the position where you first saw it. Then the question is one lookup. In plan form:

```
seen = {}                         value -> first position it appeared
for j, x in numbers:
    if (target - x) in seen: answer is (seen[target - x], j)
    if x not in seen: seen[x] = j
```

This is a plan, not C++ yet. `for j, x in numbers` means "for each position `j` and the value `x` sitting there", and `seen` is the notebook.

Trace `{2, 7, 11, 15}` with target 9. At position 0, `x` is 2 and you need 7: the notebook is empty, so write down "2 is at 0". At position 1, `x` is 7 and you need 2: the notebook says 0. The answer is `{0, 1}`.

Two small choices do a lot of work:

- **Look before you write.** Checking the notebook *before* adding `x` stops a number pairing with itself. In `{3, 2, 4}` with target 6, if you wrote "3 is at 0" first and then looked for 3, you would find position 0 and answer `{0, 0}`.
- **Keep only the first position.** Keeping the first place each value appeared gives the smallest `i` for that `j`. And because `j` walks upward and you stop at the first match, the answer you return has the smallest `j` too.

This walks the list once, so the time grows in step with the length of the list. In the [[notation programmers use|big-o]] that is O(n), against O(n²) for brute force. 200,000 numbers take a blink.

### The C++ tools

The notebook is a `std::unordered_map<int, int>`: value to first position. From the maps lesson you know a [[lookup in it is fast|hash-lookup]] on average, and that `find` or `contains` looks without inserting:

```cpp
std::unordered_map<int, int> first_seen;
auto it = first_seen.find(target - x);
if (it != first_seen.end()) {
    // found: it->second is the position
}
```

`find` gives back an iterator, which equals `end()` (read `!=` as "is not equal to") when the key is missing. The arrow `->` means "follow the iterator, then take the member", so `it->second` is the stored value, here the position.

To write in the notebook, `m.emplace(key, value)` inserts only when the key is missing. It **never overwrites**, so the first position stays:

```cpp
first_seen.emplace(2, 0);   // 2 is at 0
first_seen.emplace(2, 5);   // ignored: 2 is already there
```

**Watch out:** `first_seen[x] = j` would overwrite, replacing the first position with the latest one. That breaks the "smallest `i`" rule.

### Returning two numbers

The answer is two numbers, so the function returns a **`std::pair<int, int>`** (from the `<utility>` header): [[two values carried as one|pair-type]]. `return {i, j};` builds one, and `.first` and `.second` read it back:

```cpp
std::pair<int, int> p = {0, 1};
std::cout << p.first << " " << p.second << "\n";   // prints 0 1
```

One last detail: positions go into a pair of `int`s, so loop with an `int j` and compare it with `static_cast<int>(nums.size())`. Comparing an `int` straight with `nums.size()`, which is unsigned, earns a warning with this checker's flags.

His book on calculating with the Hindu-Arabic numerals, the digits 0 to 9 we use today, was translated into Latin, and his name, written Algoritmi, became the word for a step-by-step method of calculating. The word "algebra" comes from the title of another of his books.

::: context big-o Big-O: how the work grows
Programmers describe speed by how the work grows as the input grows, written with a capital O, read "order of". O(n) means the work grows in step with n: twice the numbers, about twice the time. O(n²) means it grows with n squared: twice the numbers, about four times the time. O(1) means the time does not grow with n at all. The notation ignores small constant factors, like the ÷ 2 in n²/2, because the shape of the growth is what decides whether 200,000 items take a millisecond or an hour.
:::

::: context hash-lookup How a hash map finds a key so fast
An `unordered_map` is a **hash table**. It keeps many small buckets, and a function called a hash turns each key into a bucket number. To look up a key, it hashes the key and checks only that one bucket, instead of searching everything. Two keys can land in the same bucket, so a bucket sometimes holds a few entries; that is why the speed is O(1) "on average" rather than always. The table grows and spreads its keys over more buckets as you add them, to keep the buckets short.
:::

::: context pair-type A pair is a tiny struct
`std::pair<int, int>` is a ready-made struct with two members, named `first` and `second`. The two types can differ: `std::pair<std::string, int>` holds a name and a number. You have used pairs already without seeing the name: every element of a `std::map` or `std::unordered_map` is a pair, which is why `it->first` is the key and `it->second` the value. When the two parts have real meanings, like a low and a high reading, a struct with named members reads better; the design lesson next shows that.
:::

=== cpp2-15 | Design: give repeated work a name
--- teach
Last lesson, "Problem solving: two that add up", you designed an algorithm from a blank page. This lesson starts from code that already works, mostly, and gives it a better shape.

### Why copies go wrong

Imagine a checklist copied onto three clipboards. Someone finds a mistake and fixes it on one clipboard, and forgets the other two. Now the three disagree, and nobody knows which is right.

Copy-pasted code is the same: a [[bug waiting to happen|dry]]. Three blocks that "do the same thing" drift apart the first time someone edits one and forgets the others. And the one they forgot is usually the wrong one.

**Refactoring** means [[changing the shape of code|refactoring-word]] without changing what it does. For duplicated blocks, work in four steps.

### Step 1: find what varies

Line the copies up side by side and spot the differences:

```cpp
out << "morning: min " << lo << "\n";   // copy 1
out << "noon: min " << lo << "\n";      // copy 2
```

Here only the data and a label differ. Those differences become the function's **parameters**; everything the copies share becomes its body.

### Step 2: name the idea

A function name should say **what** it computes, not **how**: `summarize`, not `loop_and_min_max`. A reader should be able to guess what `summarize(readings)` gives back without opening it.

### Step 3: return a meaningful type

When a function produces several related values, a small `struct` with named members is the clearest thing to return:

```cpp
struct Range { int low; int high; };
```

It beats the alternatives. Three [[output parameters|out-params]] (references the function writes its answers into) make every call longer and harder to read. A `std::pair` of a `std::pair` makes the reader decode `r.second.first`. A struct lets them write `r.low`.

### Step 4: replace each copy with a call

Swap every copy for a call to the new function, then re-run the checks. They are your [[safety net|regression]]: behaviour must not change, except for fixing bugs the duplication was hiding.

### One place to get it right

Here is a whole function that returns a `Range`:

```cpp
Range range_of(const std::vector<int>& v) {        // one place to get it right
    auto [lo, hi] = std::minmax_element(v.begin(), v.end());
    return {*lo, *hi};
}
```

Read it slowly, because two pieces are new:

- `std::minmax_element`, from `<algorithm>`, finds the smallest and the largest in one walk through the range. Like `max_element` in the iterators lesson, it gives back iterators, not values: a pair of them, the first pointing at the smallest element and the second at the largest.
- `auto [lo, hi] = ...` is a **[[structured binding|structured-binding]]**: it unpacks a pair into two new variables with names you choose. Here `lo` is the pair's first part and `hi` its second.

Then `*lo` follows the iterator to the value, and `return {*lo, *hi};` fills the `Range` in member order: `low` first, then `high`. For `{4, -1, 9, 3}` you get low -1 and high 9.

**Watch out:** on an empty vector there is no smallest element, and both iterators are `end()`. Following `end()` with `*` is undefined behaviour. So a function like this only works on a non-empty list, and the code that calls it must check `empty()` first.

### Computing apart from presenting

A good split has one function for **computing** and one for **presenting**. The computing one returns numbers:

```cpp
Summary s = summarize(readings);   // numbers: min, max, mean
```

The presenting one turns them into text. It uses a `std::ostringstream` from the string streams lesson, set up with `std::fixed << std::setprecision(1)` so the mean always shows one decimal place:

```cpp
std::string line = format_line("noon", readings);   // "noon: min 10, max 20, mean 15.0\n"
```

You can then test each one on its own, and [[reuse the numbers|compute-present]] somewhere that does not want text at all.

::: context dry Don't Repeat Yourself
Programmers have a name for this rule: **DRY**, short for "Don't Repeat Yourself". It comes from the 1999 book *The Pragmatic Programmer* by Andy Hunt and Dave Thomas, who put it as: every piece of knowledge should have one single, clear home in a system. When a fact lives in two places, sooner or later someone changes one and not the other. DRY is about knowledge, not about lines that happen to look alike: two blocks that look the same today but mean different things can stay separate.
:::

::: context refactoring-word Where "refactoring" comes from
The word borrows from algebra. Factoring rewrites 6x + 6y as 6(x + y): a different shape, the same value. Refactoring does the same to code. Martin Fowler's 1999 book *Refactoring* made the word famous, with a catalogue of small, safe steps. One of them, pulling repeated code out into its own function, is exactly what this lesson does. Each step is small enough to check before taking the next, so the program works after every one.
:::

::: context out-params Answers through references
An **output parameter** is a reference parameter that the function writes a result into, the way `capitalize_all` changed the caller's vector in the iterators lesson. `void range_of(const std::vector<int>& v, int& low, int& high)` works, but every caller must first make empty variables to receive the answers, and a reader of a call like `range_of(v, a, b)` cannot tell which arguments go in and which come out. Returning a struct makes the answer obvious, and the compiler usually builds the returned struct straight in the caller's space, so it costs nothing extra.
:::

::: context regression Tests as a safety net
A bug that creeps back into code that used to work is called a **regression**, and checks that you re-run after every change are regression tests. They are what make refactoring safe: change the shape, run the checks, and if any check fails you know that step broke something, while it is still small and fresh. The checks on this page are regression tests for `report`. Flight software teams re-run huge suites of them automatically on every change.
:::

::: context structured-binding Unpacking a pair
Structured bindings arrived in C++17. They work on a `std::pair`, on a struct, and on the elements of a map: `for (const auto& [name, score] : scores)` walks a map and gives each key and value its own name, instead of `.first` and `.second`. The names are yours to choose, and the order follows the parts: first, then second.
:::

The same numbers can feed a chart, a log file and a warning light, and changing how a screen looks never touches the flight code.

--- task
`report` works, mostly, but its three copied blocks hide a copy-paste bug. Refactor it into these pieces:

- `struct Summary { int min; int max; double mean; };`
- `Summary summarize(const std::vector<int>& readings)`: the smallest value, the largest value and the mean (the average: the total divided by how many there are). It is only called with a non-empty list.
- `std::string format_line(const std::string& label, const std::vector<int>& readings)`: returns `"label: min 1, max 5, mean 3.0\n"`, with the real label and numbers and the mean to one decimal place. For an empty list it returns `"label: no readings\n"` instead.
- `report` returns the three lines, morning then noon then night, each built with `format_line`.

Keep at most one loop in the whole file. No `main`: the checker supplies it.

#include <iomanip>
#include <sstream>
#include <string>
#include <vector>

std::string report(const std::vector<int>& morning, const std::vector<int>& noon, const std::vector<int>& night) {
    std::ostringstream out;
    out << std::fixed << std::setprecision(1);

    int lo = morning[0], hi = morning[0];
    long long sum = 0;
    for (int x : morning) { if (x < lo) lo = x; if (x > hi) hi = x; sum += x; }
    out << "morning: min " << lo << ", max " << hi << ", mean " << static_cast<double>(sum) / morning.size() << "\n";

    lo = noon[0]; hi = noon[0];
    sum = 0;
    for (int x : noon) { if (x < lo) lo = x; if (x > hi) hi = x; sum += x; }
    out << "noon: min " << lo << ", max " << hi << ", mean " << static_cast<double>(sum) / noon.size() << "\n";

    lo = night[0]; hi = night[0];
    sum = 0;
    for (int x : night) { if (x < lo) lo = x; if (x > hi) hi = x; sum += x; }
    out << "night: min " << lo << ", max " << hi << ", mean " << static_cast<double>(sum) / noon.size() << "\n";

    return out.str();
}
--- solution
#include <iomanip>
#include <sstream>
#include <string>
#include <vector>

struct Summary {
    int min;
    int max;
    double mean;
};

Summary summarize(const std::vector<int>& readings) {
    Summary s{readings[0], readings[0], 0.0};
    long long sum = 0;
    for (int x : readings) {
        if (x < s.min) s.min = x;
        if (x > s.max) s.max = x;
        sum += x;
    }
    s.mean = static_cast<double>(sum) / readings.size();
    return s;
}

std::string format_line(const std::string& label, const std::vector<int>& readings) {
    if (readings.empty()) return label + ": no readings\n";
    Summary s = summarize(readings);
    std::ostringstream out;
    out << std::fixed << std::setprecision(1);
    out << label << ": min " << s.min << ", max " << s.max << ", mean " << s.mean << "\n";
    return out.str();
}

std::string report(const std::vector<int>& morning, const std::vector<int>& noon, const std::vector<int>& night) {
    return format_line("morning", morning) + format_line("noon", noon) + format_line("night", night);
}
