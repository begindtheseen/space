=== py3-01 | Iterators and the iterator protocol
--- teach
Last lesson you took one long function apart into small ones, each doing one job. That finished the intermediate course: you can now write Python the way experienced people do. This course opens the hood. You will see how Python's own features work underneath, so you can build your own, and you will meet the algorithms that decide whether a program finishes at all.

We start with something you have used since the basics: the `for` loop. In py2-11 you met the word *iterator*, a ticket machine that prints the next ticket only when you press the button. This lesson shows you the button, and how to build a machine of your own.

### Two roles: the book and the bookmark

Picture a book and a bookmark. The book holds all the pages. You can read it as many times as you like, and two friends can read it at the same time, as long as each has their own bookmark. The bookmark knows only one thing: where you are. You move it forward page by page, and when it reaches the end, that bookmark is finished.

Python's loops use the same two roles:

- An **iterable** is the book: anything you can loop over. Lists, strings, dicts and ranges are all iterables.
- An **iterator** is the bookmark: the object that hands out the values one at a time and remembers where it is.

The agreement between the two, a short list of rules both sides follow, is called the **[[iterator protocol|protocol-word]]**. Every `for` loop in Python runs on it. Once you know it, lots of things stop being magic: generators (next lesson), files, `zip`, `range`, and dict views (the `d.keys()`, `d.values()` and `d.items()` you loop over).

### iter() and next(): pressing the button yourself

Two built-in functions let you work the protocol by hand:

- **`iter(thing)`** asks an iterable for a new iterator: a fresh bookmark at page one.
- **`next(it)`** asks an iterator for its next value, and moves it forward one step.

```python
it = iter([10, 20])
print(next(it))    # 10
print(next(it))    # 20
next(it)           # StopIteration: there is nothing left
```

When nothing is left, `next` has no value to give back. Instead it raises an exception called **[[StopIteration|stop-signal]]**, which means "this iterator is finished". It is an exception, like `ValueError`, but here it is not a mistake. It is the normal way an iterator says "that was the last one".

### What a for loop really does

A `for` loop is exactly those two calls, made for you. This loop:

```python
for x in things:
    print(x)
```

runs [[roughly like this|for-underneath]]:

```python
it = iter(things)          # get a fresh bookmark
while True:                # repeat forever...
    try:
        x = next(it)       # ...asking for the next value
    except StopIteration:
        break              # ...until there is none: leave the loop
    print(x)               # the body of the for loop
```

`while True` would repeat forever on its own. The `break` inside `except StopIteration` is the only way out. So the loop ends at the moment the iterator raises `StopIteration`, and Python catches that exception for you. That is why you never see it when you write an ordinary `for` loop.

### The methods behind the two functions

`iter()` and `next()` work by calling special methods, the double-underscore kind you met with `__init__` and `__repr__`:

- `iter(thing)` calls `thing.__iter__()`, read "dunder iter". An iterable must have an `__iter__` method, and it must return an iterator.
- `next(it)` calls `it.__next__()`, read "dunder next". An iterator must have a `__next__` method. It returns the next value, or raises `StopIteration` when there are none left.
- An iterator has an `__iter__` method too, and it [[returns itself|returns-self]]: `return self`.

### Building your own: a book and its bookmark

Here are two classes that together give out the square numbers 1, 4, 9 and so on. `Squares` is the book. `SquaresIterator` is its bookmark.

```python
class Squares:                      # an iterable: the book
    def __init__(self, n):
        self.n = n
    def __iter__(self):
        return SquaresIterator(self.n)

class SquaresIterator:              # its iterator: the bookmark
    def __init__(self, n):
        self.i = 0
        self.n = n
    def __iter__(self):
        return self
    def __next__(self):
        if self.i >= self.n:
            raise StopIteration
        self.i += 1
        return self.i * self.i

print(list(Squares(3)))    # [1, 4, 9]
print(list(Squares(3)))    # [1, 4, 9]   again: a fresh iterator each time
```

Read `SquaresIterator` one method at a time:

- `__init__` stores where the bookmark is, `self.i = 0`, and where to stop, `self.n`.
- `__iter__` returns `self`, because this object *is* the iterator.
- `__next__` first checks whether it is finished. `>=` means "greater than or equal to", so once `self.i` has reached `self.n`, it raises `StopIteration`. Otherwise it moves forward (`self.i += 1`, "add one to `self.i`") and returns that number times itself.

`Squares.__iter__` makes a **brand new** `SquaresIterator` every time it is asked. `list(...)` loops over whatever you give it, so each `list(Squares(3))` gets its own fresh bookmark, starting at 0.

### Why two roles?

An iterator remembers *where it is*, so it can be walked only once. When it reaches the end, it [[stays at the end|one-shot]]. An iterable hands out a *fresh* iterator each time, so you can loop over it again and again, and even have two loops over it at the same moment:

```python
sq = Squares(2)
for a in sq:
    for b in sq:
        print(a, b)
# 1 1
# 1 4
# 4 1
# 4 4
```

Each `for` asked `sq` for its own bookmark, so the inner loop starting over did not disturb the outer one.

**Watch out:** the mistake people make is writing a class whose `__iter__` returns `self`, and then expecting to loop over it twice. That class is an iterator, and iterators are one-shot. There is no error; the second loop is empty:

```python
it = SquaresIterator(3)
print(list(it))    # [1, 4, 9]
print(list(it))    # []   the bookmark was already at the end
```

::: context protocol-word An agreement, not a thing
A protocol is a set of rules that two sides agree to follow, so they can work together without knowing anything else about each other. Diplomats have protocols for meetings; the internet runs on protocols for sending messages. Python's iterator protocol is tiny: have `__iter__`, have `__next__`, raise `StopIteration` at the end. Any object that follows it works in a `for` loop, with `list`, `sum`, `max`, `zip` and everything else that loops. None of those functions need to know what your class is.
:::

::: context stop-signal Why an exception, and not a special value?
Why not return `None` at the end? Because `None` could be a real value in the list. `[1, None, 3]` is a fine list, and a loop over it must not stop at the second item. Any value you picked as the "end" marker could turn up as real data somewhere. An exception is not a value at all, so it can never be confused with one. That is why Python chose to signal the end this way.
:::

::: context for-underneath Why "roughly"
The real `for` loop is built into Python itself, not written in Python, so it is a little faster than the `while` version. But it does exactly the same steps: one `iter()` at the start, then `next()` again and again until `StopIteration`. This is why a `for` loop works on so many different things. A list, a string (one letter at a time), a dict (one key at a time) and a `range` all give out iterators, so the same loop handles them all.

::: context returns-self Why an iterator hands back itself
A `for` loop always starts by calling `iter()` on whatever you give it. If you give it a bookmark instead of a book, it still asks for a bookmark, and `return self` answers "use me". Without that line, you could not write `for x in it:` when `it` is already an iterator, and many tools, like `zip` and `list`, would refuse it.
:::

::: context one-shot Streams that only come once
Some data really is one-shot. Telemetry, the stream of readings a spacecraft sends down to the ground, arrives packet after packet, and each packet passes by once. Ground software reads a stream like that the way an iterator works: take the next packet, handle it, move on. When a program needs to go back over the data, it has to store it first, in a list or a file. Knowing which of your objects are books and which are bookmarks tells you when you need to do that.
:::

Write two classes that count down, built the same way as `Squares` and `SquaresIterator`:

- `CountdownIterator(n)` is the **iterator**. Its `__init__` stores the number it is on. Its `__iter__` returns `self`. Its `__next__` returns `n` the first time, then `n - 1`, and so on down to `1`. After `1`, it raises `StopIteration`.
- `Countdown(n)` is the **iterable**. Its `__init__` stores `n` as `self.n`. Its `__iter__` returns a brand new `CountdownIterator(self.n)` every time, so a `Countdown` can be looped over more than once.

For example, `list(Countdown(3))` is `[3, 2, 1]`, and `list(Countdown(0))` is `[]`.
--- starter

--- solution
class CountdownIterator:
    def __init__(self, n):
        self.current = n

    def __iter__(self):
        return self

    def __next__(self):
        if self.current <= 0:
            raise StopIteration
        value = self.current
        self.current -= 1
        return value


class Countdown:
    def __init__(self, n):
        self.n = n

    def __iter__(self):
        return CountdownIterator(self.n)
--- hint

--- hint
`Countdown.__iter__` is one line: `return CountdownIterator(self.n)`. Making a new iterator there is what lets a `Countdown` be looped over twice.

=== py3-02 | Generators and pipelines
--- teach
Last lesson you built an iterator by hand: two classes, three dunder methods, a counter to move, and a `StopIteration` to raise at the end. It works, but it is a lot of writing for "hand out 3, then 2, then 1". This lesson shows the short way, which Python programmers use nearly all the time.

Picture a storyteller who reads one page aloud, then stops and waits, finger on the spot, until you say "go on". Nothing is lost while they wait. When you ask again, they carry on from exactly where they stopped.

### yield: a function that pauses

**`yield`** is a keyword that works like `return`, with one difference. `return` hands back a value and ends the function for good. `yield` hands back a value and **pauses** the function, keeping its place and all its variables, until someone asks for the next value.

Any function with `yield` inside it is a **generator function**. Calling it does not run it. Instead it gives you a **[[generator|generator-word]]**: an iterator, ready to run the function's body a piece at a time.

```python
def countdown(n):
    while n > 0:
        yield n
        n -= 1

g = countdown(3)
print(next(g))     # 3
print(list(g))     # [2, 1]
```

Here is what happened, [[step by step|pause-resume]]:

1. `countdown(3)` made the generator `g`. None of the body has run yet.
2. The first `next(g)` ran the body from the top, as far as `yield n`. It handed out `3` and paused there, with `n` still 3.
3. `list(g)` kept calling `next`. Each time, the body woke up right after the `yield`, took one off `n` (`n -= 1`), went round the `while` loop, and paused at the next `yield`: first with 2, then with 1.
4. After 1, `n` became 0, so `while n > 0` ("while n is greater than 0") was false and the function reached its end. The generator then raised `StopIteration` for you, and `list` stopped.

Those six lines do everything the two classes did last lesson. A generator is an iterator, so it follows the same protocol: `next()` works on it, `for` loops work on it, and it is used up after one pass.

### return inside a generator: stop early

A `return` inside a generator function ends it straight away. It hands out no value; the generator is finished, and the loop reading it stops:

```python
def until_stop(words):
    for w in words:
        if w == "STOP":
            return        # finished: no more values
        yield w

print(list(until_stop(["go", "up", "STOP", "down"])))    # ['go', 'up']
```

`"down"` never came out, and the generator never even looked at it.

### Lazy: only when asked

A generator does no work until someone asks for a value, and then only enough work for that one value. Programmers call that **lazy**. You can watch it happen by putting a `print` inside:

```python
def noisy(items):
    for x in items:
        print("making", x)
        yield x

g = noisy([1, 2, 3])    # prints nothing: the body has not started
print(next(g))
# making 1
# 1
```

Only one "making" line appeared, because only one value was asked for.

Laziness is why a generator can walk through a log with a million lines while holding only [[one line at a time in memory|memory-cost]]. It even means a generator can be endless. `count()` from py2-11 counts 0, 1, 2 and on forever:

```python
from itertools import count, islice

def evens():
    for n in count():
        if n % 2 == 0:
            yield n

print(list(islice(evens(), 4)))    # [0, 2, 4, 6]
```

`%` is "remainder", so `n % 2 == 0` means "n divided by 2 leaves nothing over": n is even. `evens()` never ends, but that is fine, because `islice` asks for only 4 values and then stops asking.

### Pipelines: small stages, joined up

A generator function can take any iterable, including another generator, and yield new values. So you can chain small stages together, each doing one job, and the values flow through them one at a time. That chain is called a **pipeline**, like [[pipes in the Terminal|shell-pipes]].

```python
def non_blank(lines):
    for line in lines:
        if line.strip():
            yield line.strip()

def as_ints(lines):
    for line in lines:
        yield int(line)

lines = ["3", "", "4", "  5 "]
print(sum(as_ints(non_blank(lines))))    # 12
```

Read the last line from the inside out. `non_blank` passes on each line that is not blank, stripped of its spaces: `"3"`, `"4"`, `"5"`. `as_ints` turns each one into a whole number. `sum` adds them: 3 + 4 + 5 = 12. At no point does a list of all the lines exist. `sum` asks `as_ints` for a value, `as_ints` asks `non_blank`, and `non_blank` takes the next line from the list.

### Generator expressions

In py2-03 you wrote a comprehension with no square brackets inside `"".join(...)`, and the course promised to explain it. Here it is. A comprehension in **round brackets** is a **[[generator expression|genexpr-brackets]]**: it makes a generator, not a list.

```python
nums = [1, 2, 3]
squares = (x * x for x in nums)
print(squares)            # <generator object <genexpr> at 0x...>
print(sum(squares))       # 14
print(sum(x * x for x in nums))    # 14   the same, written inside the call
```

The first `print` shows the generator itself, not its values, because nothing has been worked out yet. When a generator expression is the only thing inside a call like `sum(...)` or `max(...)`, you can leave out its own brackets. That adds up the squares without ever building a list.

### Asking for one value at a time

A lazy stage should never take more from its input than it needs. Each value you pull out of an iterator is gone from it:

```python
it = iter([1, 2, 3])
for x in it:
    if x == 2:
        break
print(list(it))    # [3]   the loop took 1 and 2; only 3 is left
```

If a stage takes one extra value "to check whether there is more", that value is lost for whoever reads the iterator next. So hand a value out as soon as you have it, and stop the moment you are done.

To know when you are done, it helps to count what you have handed out. `enumerate(items, start=1)` from py2-02 numbers the items starting from 1, so the number next to each item says how many you have had so far:

```python
for i, word in enumerate(["a", "b", "c"], start=1):
    print(i, word)
# 1 a
# 2 b
# 3 c
```

**Watch out:** calling a generator function runs *none* of its body; it only makes the generator. So a mistake inside, like `int("abc")`, does not show up when you call it. It shows up later, when the first value is asked for, often somewhere far away in the code. And a generator is an iterator, so it is used up after one pass, like the `SquaresIterator` last lesson.

::: context generator-word What the object really is
A generator is an object Python builds for you. It holds the function's code, its local variables, and a marker for the line it paused on. It has `__iter__` (which returns itself) and `__next__` (which runs the body to the next `yield`), so it follows exactly the iterator protocol from last lesson. You write a normal-looking function; Python writes the iterator class. You can check the type with `type(countdown(3))`, which shows `<class 'generator'>`.
:::

::: context pause-resume Taking turns
A generator and the code reading it take turns. The reader calls `next`; the generator runs until `yield`, hands over one value, and freezes. Then the reader runs again. Only one of them is running at any moment.

::: context memory-cost Why memory matters
Memory is where a running program keeps its values. A list keeps all of its items in memory at once, so a list of ten million log lines needs room for ten million lines. A generator keeps one. On a laptop that can be the difference between a program that finishes and one that runs out of room. On a spacecraft's flight computer, which has far less memory than a laptop, programs are written to handle data as a stream for this reason.
:::

::: context shell-pipes The same idea, fifty years apart
If you have done the Terminal course's pipes lesson, you have already built pipelines: `sort names.txt | uniq -c`, where `|` sends one command's output into the next. Pipes were added to Unix in 1973, pushed for by Doug McIlroy, who wanted programs to connect "like a garden hose". Python generator pipelines follow the same plan: small stages that each do one thing, joined together, with data flowing through a little at a time.
:::

::: context genexpr-brackets Square brackets or round?
The only difference in writing is the brackets. `[x * x for x in nums]` builds the whole list at once and keeps it, so you can use it as often as you like. `(x * x for x in nums)` makes a lazy generator, which works out each value when asked and can be used once. Choose the list when you need the values more than once, and the generator when you only pass through them once, especially if there are a lot of them.
:::
--- task
Write three generator functions. Each one uses `yield`, not a list.

- `read_numbers(lines)` goes through `lines`, strips each line, and yields the whole number (`int`) on it. It skips blank lines, lines starting with `#`, and lines that are not whole numbers (where `int(line)` raises `ValueError`). For example, `["10", " -4 ", "# note", "abc"]` gives 10, then -4.
- `running_total(nums)` yields the running total after each number: for `[3, 1, 4]` that is 3, then 4, then 8.
- `take(n, items)` yields the first `n` items of any iterable, **including an endless one** like `count()`, then stops. If `n` is 0 or less, it yields nothing. If there are fewer than `n` items, it yields all of them.

All three must be lazy: they must not take more from their input than they need. In particular, `take` must stop as soon as it has yielded `n` items, without reading one more.
--- starter
def read_numbers(lines):
    return [int(line) for line in lines]


def running_total(nums):
    return []


def take(n, items):
    return list(items)[:n]
--- solution
def read_numbers(lines):
    for line in lines:
        line = line.strip()
        if not line or line.startswith("#"):
            continue
        try:
            yield int(line)
        except ValueError:
            continue


def running_total(nums):
    total = 0
    for n in nums:
        total += n
        yield total


def take(n, items):
    if n <= 0:
        return
    for i, item in enumerate(items, start=1):
        yield item
        if i >= n:
            return
--- hint
Each function is a `for` loop with a `yield` inside, like `non_blank` and `as_ints`. In `read_numbers`, strip the line first; then `continue` skips it if it is blank (`not line`) or `line.startswith("#")`.
--- hint
Put only `int(line)` inside `try`, with `except ValueError:` doing `continue`, and `yield` the number when it works. `running_total` keeps a `total` that starts at 0, adds each number to it, and yields `total` each time round the loop.
--- hint
For `take`: if `n <= 0` ("n is less than or equal to 0"), `return` before the loop. Then loop with `for i, item in enumerate(items, start=1):`, `yield item`, and straight after, `if i >= n: return`. Do not go round the loop again to check for more, or you will read one item too many.

=== py3-03 | Debugging: the iterator that ran dry
--- teach
Last lesson you learned that a generator is used up after one pass, like the bookmark that reaches the end of the book. This lesson is about the bug that comes from forgetting that. It is a sneaky one: there is no error message at all. A value that should be there is empty, and nothing tells you why.

Some bugs make no sense until you know what to suspect. The debugging steps from the intermediate course still work here: reproduce it, shrink it, check your assumptions, look carefully, then fix the cause.

### Reproduce and shrink

First, cut the program down to the [[fewest lines that still go wrong|shrink]]:

```python
nums = (n for n in [3, 1, 2])
print(max(nums))       # 3
print(sorted(nums))    # []    where did the numbers go?
```

Three lines, and the bug is still there. That is small enough to think about.

### Check your assumptions

The hidden assumption is "`nums` is a collection of numbers, like a list". It is not. The round brackets made a *generator*, a one-shot iterator. `max` walked it to the end to find the biggest number, and nothing was left for `sorted`.

Generators are not the only one-shot things. Many built-in tools hand back [[an iterator, not a list|one-shot-list]]:

- `zip(a, b)`, which pairs up two lists (from py2-02);
- `enumerate(items)`, which numbers the items (also py2-02);
- `reversed(items)`, which walks a list backwards;
- `map(f, items)`, which calls a function `f` on each item, and `filter(f, items)`, which keeps the items where `f` gives true;
- an open file, when you read it line by line (later in the course);
- anything a generator function returns.

Each of these works perfectly the first time you loop over it, and is empty the second time.

### Look carefully

To find out what you really have, print its type:

```python
nums = (n for n in [3, 1, 2])
print(type(nums))      # <class 'generator'>
```

But be careful what you print. `print(list(nums))` shows the values, and it also *uses up the iterator*. Then the real code after it finds nothing. So adding a debug print can change what the program does. A bug that changes when you look at it is called a **[[heisenbug|heisenbug]]**. Print the type, not the contents. Or turn the values into a list first and print the list.

### Fix the cause

If you need the values more than once, turn them into a list **once, where they are made**. A list can be read as often as you like:

```python
nums = list(n for n in [3, 1, 2])     # or [n for n in [3, 1, 2]]
print(max(nums), sorted(nums))        # 3 [1, 2, 3]
```

Fixing it where the values are made matters. If you add `list(...)` only in front of `sorted`, it is too late: `max` has already emptied the iterator.

If the data is [[too big to keep in a list|list-or-one-pass]], there are two other fixes. You can change the code so it needs only one pass, working out both results in the same loop:

```python
count = 0
biggest = None
for n in (n for n in [3, 1, 2]):
    count += 1
    if biggest is None or n > biggest:
        biggest = n
print(count, biggest)     # 3 3
```

Or you can make a fresh iterator for each pass, by calling the generator function again.

### Two tools you will meet in the task

The task's code uses two tricks you may not have seen:

- `sum(1 for _ in records)` counts the items. It adds up one `1` for each item. `_` is the name for "a value I am ignoring", from py2-14. Because it loops over `records`, it uses `records` up.
- `max(items, key=len, default="")` finds the longest item. `key=len` works as in py2-05, comparing by length. `default=""` is what `max` gives back when `items` is empty; without it, `max` of nothing raises `ValueError`.

```python
print(max(["a", "ccc", "bb"], key=len, default=""))    # ccc
print(max([], key=len, default=""))                    # (an empty line: the default "")
```

The task also sorts pairs with `key=lambda p: -p[1]`. The minus sign turns each score negative, so the highest score sorts first. And because Python's sort is [[stable|stable-again]], two people with the same score stay in the order they started in.

**Watch out:** the real mistake is fixing the symptom instead of the cause. It is tempting to see the empty result and patch the line that shows it, or to swap the two lines so the broken one runs first. Then the *other* result is empty instead. Find where the iterator is made, and make a list there.

::: context shrink Why smaller is faster
A short example that still shows the bug is often called a minimal reproducible example. Shrinking a program to one is often most of the work of debugging: each line you cut away without losing the bug is one line that cannot be the cause. It is also exactly what you would post if you asked someone for help, because nobody can read three hundred lines, but anyone can read three.
:::

::: context heisenbug Named after a physicist
The name is a joke about Werner Heisenberg, a physicist whose uncertainty principle is often described as "measuring something disturbs it". Programmers have used the word since the 1980s for bugs that vanish or change when you try to look at them. Adding a print that uses up an iterator is one cause. Others are timing: a bug that only happens when the program runs at full speed can disappear when a debugger slows it down.

::: context list-or-one-pass Choosing a fix
A list is the easy fix, and for a few thousand items it is the right one. The price is memory: every item is kept at once. When the data is huge, like a long recording of sensor readings, working out everything in one pass keeps only a few numbers at a time, a count and a biggest-so-far. Engineers pick between these all the time. Neither is always right; it depends on how big the data is and how many times you need it.
:::

=== py3-04 | Decorators
--- teach
Last lesson you hunted an iterator that ran dry. This lesson goes back to something you used in py2-10: the `@property` line above a `def`. A context note there said that a line starting with `@` is a *decorator*, which wraps the function below it. Now you will write decorators of your own.

Picture wrapping a present. The present inside does not change. The wrapping adds something around it: a bow, a label, a card. A decorator does that to a function. The original function still does its job, and the wrapping adds something before it runs or after it finishes.

To build one, you need a few small ideas first. Take them one at a time.

### Functions are values

In Python, a function is a value, like a number or a list. Its name is a variable that points at it. Written *without* brackets, the name means the function itself. *With* brackets, it means "call it now".

```python
def double(x):
    return x * 2

f = double          # no brackets: f now points at the same function
print(f(5))         # 10
```

Because a function is a value, you can [[pass it to another function|first-class]], as an argument:

```python
def apply_twice(func, x):
    return func(func(x))

print(apply_twice(double, 3))    # 12   double(double(3)) is double(6)
```

### A function that makes a function

A function can also build a new function inside itself and hand it back with `return`:

```python
def make_adder(n):
    def add(x):
        return x + n
    return add

add5 = make_adder(5)
print(add5(10))     # 15
```

Look at what is strange here. By the time `add5(10)` runs, `make_adder` has already finished. Yet `add` still knows that `n` is 5. A function defined inside another function keeps using the outer function's variables, even after the outer one has returned. The inner function, together with the variables it remembers, is called a **[[closure|closure]]**.

### A wrapper

Now put those ideas together. Here is a function that takes a function and returns a new one that wraps it:

```python
def shout(func):
    def wrapper(name):
        result = func(name)          # call the original
        return result.upper()        # add something after
    return wrapper

def greet(name):
    return f"hello, {name}"

greet = shout(greet)
print(greet("ada"))     # HELLO, ADA
```

After `greet = shout(greet)`, the name `greet` points at `wrapper`. When you call it, `wrapper` calls the original `greet`, which it remembers as `func` (a closure again), and makes the result upper case. A function like `shout`, which takes a function and gives back a wrapped one, is a **decorator**.

### The @ line is shorthand

Writing `greet = shout(greet)` after every function is clumsy, so Python has a shorthand. The `@` sign, read "at", on the line above a `def`:

```python
@shout
def greet(name):
    return f"hello, {name}"

print(greet("ada"))     # HELLO, ADA
```

`@shout` means exactly `greet = shout(greet)`, done straight after the `def`. That is all the `@` line does.

### Passing every argument through

The `wrapper` above takes exactly one argument, `name`, so `shout` only works on functions that take one argument. To make a decorator that works on *any* function, the wrapper collects whatever it is given, with the bags from py2-06:

```python
def wrapper(*args, **kwargs):
    return func(*args, **kwargs)
```

In the `def` line, `*args` collects the positional arguments into a tuple and `**kwargs` collects the keyword arguments into a dict. In the call `func(*args, **kwargs)`, the stars do the opposite: they **unpack** the bags. `*args` spreads the tuple back out as separate positional arguments, and `**kwargs` spreads the dict back out as keyword arguments:

```python
def show(a, b, c=0):
    return a, b, c

args = (1, 2)
kwargs = {"c": 3}
print(show(*args, **kwargs))    # (1, 2, 3)   the same as show(1, 2, c=3)
```

So the original gets exactly the arguments the caller wrote, whatever they were.

### Return the original's result

A wrapper must `return` what the original returned. If it calls `func(...)` and forgets the `return`, the decorated function quietly gives back `None`, and nothing warns you.

### functools.wraps: keep the original's name

Every function knows its own name, in the attribute `__name__` ("dunder name"). A plain wrapper hides it:

```python
@shout
def greet(name):
    return f"hello, {name}"

print(greet.__name__)    # wrapper
```

That is [[confusing in error messages|wraps-why]], debuggers and any tool that looks functions up by name. The fix comes with Python. Import the `functools` module, and put `@functools.wraps(func)` above the wrapper's `def`. It copies the original's name, docstring and other details onto the wrapper:

```python
import functools

def shout(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        result = func(*args, **kwargs)
        return result.upper()
    return wrapper

@shout
def greet(name):
    return f"hello, {name}"

print(greet("ada"))      # HELLO, ADA
print(greet.__name__)    # greet
```

That is the full shape of a decorator. Nearly every decorator you write will look like this.

### Keeping something on the wrapper

A function is an object, so you can store your own [[attribute on it|function-attribute]], with a dot, the same way you store `self.n` on an object. That lets a wrapper keep a value between calls:

```python
def remember_last(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        wrapper.last = func(*args, **kwargs)
        return wrapper.last
    wrapper.last = None          # set once, when the decorator runs
    return wrapper

@remember_last
def double(x):
    return x * 2

print(double.last)    # None   nothing has been called yet
double(4)
print(double.last)    # 8
```

`wrapper.last = None` runs once, straight after `wrapper` is defined and before it is returned. The line inside `wrapper` runs on every call, and it can use the name `wrapper`, because by then the function exists.

### Decorators with arguments: one more layer

Sometimes a decorator needs a setting, like `@repeat(3)`, "run it three times". Here the brackets matter. Python first *calls* `repeat(3)`, and whatever that returns is the decorator that wraps the function. So a [[decorator with arguments needs three layers|three-layers]]:

```python
def repeat(times):              # layer 1: takes the setting
    def decorator(func):        # layer 2: takes the function
        @functools.wraps(func)
        def wrapper(*args, **kwargs):   # layer 3: takes the call's arguments
            return [func(*args, **kwargs) for _ in range(times)]
        return wrapper
    return decorator

@repeat(3)
def roll():
    return 4

print(roll())     # [4, 4, 4]
```

`@repeat(3)` means `roll = repeat(3)(roll)`: call `repeat(3)` to get `decorator`, then call `decorator(roll)` to get `wrapper`. Each layer is a closure over the layer outside it. That is how `wrapper` still knows `times` and `func` long after `repeat` and `decorator` have returned.

### Catching any error, and sending it on

Your task has a decorator that tries a function again when it fails. It needs two more pieces of the `try` statement.

`except Exception:` catches almost [[any error|exception-family]]. `Exception` is the parent class of `ValueError`, `ZeroDivisionError` and the others, the same way your own `LedgerError` was the parent of `InsufficientFunds` in py2-08.

A `raise` with nothing after it, a **bare raise**, is allowed only inside an `except` block. It raises again the exact exception being handled, so it carries on up to the caller as if you had never caught it:

```python
def divide(a, b):
    try:
        return a / b
    except Exception:
        print("could not divide")
        raise                 # send the same error on

divide(1, 0)
# could not divide
# ZeroDivisionError: division by zero
```

And remember that a `return` inside `try` ends the whole function at once, even from inside a loop. A decorator that [[retries|retry-real]] uses all three: a `for` loop over the tries, `return func(...)` inside `try`, and a bare `raise` only when the last try has failed.

**Watch out:** the real mistake with decorators that take arguments is leaving the brackets off: `@repeat` instead of `@repeat(3)`. Python then calls `repeat(roll)`, so the function itself arrives as `times`, and `roll` becomes `decorator`. Nothing fails on that line. The error comes later, far from the cause, when you call `roll()`. If a decorator takes a setting, it always needs brackets.

::: context first-class Functions as ordinary values
Programmers say Python has first-class functions: a function can go anywhere a value can go. You can store it in a variable, put it in a list or dict, pass it in, and hand it back. You have already done this without the name: `sorted(words, key=len)` in py2-05 passed the function `len` to `sorted`, without brackets, so that `sorted` could call it on each word.
:::

::: context closure A backpack of variables
Think of the inner function packing a small backpack when it is made. Into the backpack go the outer variables it uses. When the outer function returns, its other variables are thrown away, but the backpack stays with the inner function.

::: context wraps-why Names in tracebacks
When something goes wrong, the traceback (py2-09) lists each function by its name. If ten different functions are all decorated and all called `wrapper`, the traceback and any logs full of "wrapper" tell you nothing. Test tools, documentation tools and the `help()` function also read `__name__` and the docstring. `functools.wraps` costs one line and keeps all of them working.
:::

::: context function-attribute Functions are objects too
Everything in Python is an object, and most objects let you attach attributes with a dot. You met this with `__defaults__` in py2-07, a value Python stores on every function. Your own attributes work the same way. `wrapper.last` is an ordinary attribute on the function object, and every call to the wrapper sees the same one, because there is only one wrapper function.
:::

::: context three-layers Three layers, three moments
Each layer runs at a different moment. `repeat(3)` runs once, when Python reaches the `@repeat(3)` line. `decorator(roll)` runs straight after, once, while the `def` is being finished. `wrapper()` runs every time anyone calls `roll()`. So: the setting goes in first, then the function, then the call's arguments, one layer for each. `functools.wraps(func)` is itself a decorator with an argument, which is why it has brackets.
:::

::: context exception-family What Exception does not catch
`Exception` sits near the top of Python's family tree of errors, with almost every error you will meet below it. A few special exceptions sit outside it on purpose. `KeyboardInterrupt`, raised when you press Ctrl+C to stop a program, is one. That way `except Exception:` does not stop you from stopping a program that is stuck retrying forever. `StopIteration` from py3-01, on the other hand, is inside the `Exception` family.
:::

::: context retry-real Retries in real systems
Many failures do not last: a network message is lost, a server is busy for a moment. So real software often tries again a few times before giving up, exactly like your `retry` decorator. Many systems also wait a little longer after each failed try, called exponential backoff, so they do not flood a busy server. The limit matters as much as the retry: giving up after a set number of tries and reporting the last error is what stops a program from hanging forever.
:::

def count_calls(func):

=== py3-05 | Context managers
--- teach
Last lesson you wrapped a function in a decorator, so extra code ran before and after every call. This lesson does the same thing for a *block* of code. You will learn the `with` statement, which runs set-up code before a block and clean-up code after it, and you will build your own things that work with it.

Think of borrowing a library book. You check it out, you read it, and you give it back. Giving it back must happen whatever else happens: if you finished it, if you got bored halfway, or if you spilled juice on it. Programs borrow things all the time and must give them back.

### The problem: clean-up that gets skipped

In the exceptions lesson you met `finally`, the block that runs every time. It is the place for [[clean-up|resource-cleanup]]. Here is a file opened and closed by hand:

```python
f = open("notes.txt", "w")
try:
    f.write("hi")
finally:
    f.close()        # runs even if write() raised
```

`open(name, "w")` opens a file for writing ("w" is for write) and gives back a file object `f`. `f.close()` hands the file back to the computer. The `try` / `finally` makes sure the close happens. It works, but it is four lines of ceremony, and it is easy to forget.

### `with` does the `finally` for you

The **`with` statement** runs a block of code and guarantees the clean-up afterwards, whatever happens inside the block:

```python
with open("notes.txt", "w") as f:
    f.write("hi")
# the file is closed here, even if write() had raised
```

Read it as "with this file open, call it `f`, do the indented block". When the block ends, the file is closed. That is true if the block finished normally, and also if it raised an exception. The object after `with` is called a **context manager**: an object that knows how to set something up and how to clean it up again.

### The two methods behind `with`

Like the `for` loop in the iterators lesson, `with` runs on a small agreement, a [[protocol|protocol-word]]. Any object can work with `with` if it has two special methods:

- **`__enter__`** (say "dunder enter") does the set-up. Whatever it returns is what `as` puts in the variable.
- **`__exit__`** (say "dunder exit") does the clean-up. It is always called when the block ends.

So the statement

```python
with manager as value:
    body
```

does roughly this:

```python
value = manager.__enter__()
try:
    body
except BaseException as e:
    if not manager.__exit__(type(e), e, e.__traceback__):
        raise                   # __exit__ returned false: let it propagate
else:
    manager.__exit__(None, None, None)
```

Read it slowly, one piece at a time.

1. First `__enter__()` runs, and its result goes into `value`.
2. Then the body runs inside a `try`.
3. If the body raises anything at all, the `except` catches it. [[BaseException|base-exception]] is the parent at the very top of the exception family, so every exception is caught here. Python then calls `__exit__` with three details about the exception: its class, `type(e)`; the exception object itself, `e`; and its [[traceback|traceback-object]], `e.__traceback__`.
4. If the body raised nothing, the `else` runs, and `__exit__` is called with three `None`s, meaning "no error".

Look at the `raise` on its own line. A bare `raise` inside an `except` re-raises the exception it caught, as in the `retry` decorator you wrote last lesson. Here it runs only if `__exit__` returned something false, and then the exception carries on upward ("propagates") to whoever called this code.

### What `__exit__` gives back

That return value is the one decision `__exit__` makes about an exception:

- return `True` and the exception is **swallowed**: it stops right there, and the program carries on after the `with` block as if nothing happened;
- return `False` (or `None`, or nothing at all) and the exception carries on upward, to whoever can catch it.

Here is a small context manager written as a class. It prints an opening tag on the way in and a closing tag on the way out, like the tags around a web page's text:

```python
class Tag:
    def __init__(self, name):
        self.name = name
    def __enter__(self):
        print(f"<{self.name}>")
        return self
    def __exit__(self, exc_type, exc, tb):
        print(f"</{self.name}>")
        return False          # never hide errors

with Tag("b"):
    print("bold")
# <b>
# bold
# </b>
```

The three parameters of `__exit__` are named `exc_type`, `exc` and `tb`: the exception's class, the exception, and the traceback. Now see what happens when the block fails:

```python
try:
    with Tag("b"):
        print("bold")
        1 / 0
except ZeroDivisionError:
    print("caught it")
# <b>
# bold
# </b>
# caught it
```

The closing tag still printed. Then, because `__exit__` returned `False`, the `ZeroDivisionError` carried on and the outer `except` caught it. If `__exit__` had returned `True`, the error would have [[vanished at the end of the block|swallow-risk]], and "caught it" would never print.

### Checking the kind of exception: `issubclass`

A context manager that swallows errors should swallow only the kinds it was asked to. `__exit__` receives the exception's *class*, so it needs a test on classes. **`issubclass(A, B)`** is `True` when class `A` is class `B` or a child of it, in the family tree from the exceptions lesson:

```python
issubclass(KeyError, KeyError)       # True: a class counts as its own subclass
issubclass(KeyError, LookupError)    # True: KeyError is a child of LookupError
issubclass(ValueError, LookupError)  # False
issubclass(KeyError, (ValueError, LookupError))   # True: matches one in the tuple
```

As with `isinstance`, the second argument can be a tuple of classes, and the answer is `True` if any one of them matches. Be careful: when there was no error, `exc_type` is `None`, and `issubclass(None, ...)` raises a `TypeError`. So test `exc_type is not None` first.

### The shortcut: `@contextmanager`

Writing a class with two methods is a lot of ceremony for something small. The standard library's `contextlib` module has a decorator that builds a context manager from a generator, like the ones you wrote in the generators lesson. The generator must `yield` [[exactly once|one-yield]]:

- code **before** the `yield` is the set-up, the `__enter__` part;
- the `yield` is where the body of the `with` block runs;
- code **after** the `yield` is the clean-up, the `__exit__` part.

```python
from contextlib import contextmanager

@contextmanager
def tag(name):
    print(f"<{name}>")
    try:
        yield
    finally:
        print(f"</{name}>")

with tag("i"):
    print("hi")
# <i>
# hi
# </i>
```

Whatever you `yield` becomes the `as` value. A bare `yield`, like this one, yields `None`.

Here is the new part. If the block raises an exception, Python raises that exception inside the generator, *at the `yield`*, as if the `yield` line itself had raised it. That is why the `yield` sits inside `try` / `finally`: the `finally` runs, prints the closing tag, and the exception carries on upward.

### Two tools for the task

The task needs two more small things.

**Removing a key from a dict.** `del settings[key]` ("delete") removes that key, and its value, from the dict:

```python
settings = {"mode": "live", "x": 1}
del settings["x"]
print(settings)       # {'mode': 'live'}
```

**A marker for "not there".** `settings.get(key, default)` returns the value, or `default` when the key is missing. But if the default is `None`, you cannot tell "missing" from "the value really was `None`". The fix is a [[unique marker object|sentinel-object]]. `object()` makes a brand-new plain object that is equal to nothing else, and you test for it with `is`:

```python
_MISSING = object()
old = settings.get("speed", _MISSING)
print(old is _MISSING)     # True: "speed" was not in the dict
```

**Watch out:** the most common mistake with `@contextmanager` is leaving out the `try` / `finally` around the `yield`. Without it, the clean-up works every time you test it with good input. Then the first time the block raises, the exception comes out at the `yield`, the code after it never runs, and the clean-up is silently skipped. That is exactly the moment clean-up matters, and it is how programs end up [[leaving things changed|restore-state]] that should have been put back.

::: context resource-cleanup Borrowed things must go back
Programmers call anything a program borrows from the computer a resource: an open file, a network connection, a lock that stops two parts of a program changing the same data at once. The operating system lets each program hold only a limited number of open files at a time. A program that forgets to close them slowly runs out, and then fails in a place that has nothing to do with the real mistake. In flight software this matters even more, because one program may run for months without a restart.

::: context protocol-word An agreement, not a family
A protocol is a set of methods Python agrees to call. The iterator protocol was `__iter__` and `__next__`. The context manager protocol is `__enter__` and `__exit__`. Your class does not have to inherit from anything special. If it has the two methods, `with` accepts it. Python programmers call this duck typing: "if it walks like a duck and quacks like a duck, treat it as a duck".
:::

::: context base-exception The top of the family tree
`Exception` is not the very top of Python's exception family. Above it sits `BaseException`. A few special exceptions are children of `BaseException` but not of `Exception`: `KeyboardInterrupt`, raised when you press Ctrl+C to stop a program, and `SystemExit`, raised to end the program. `with` catches `BaseException` so that clean-up happens even for those.

::: context traceback-object The red text, as an object
Every exception carries a traceback object in its `__traceback__` attribute. It holds the chain of frames you learned to read in the traceback lesson: which functions were running and on which lines. When an exception is never caught, Python prints that object as the red text. Most context managers ignore the `tb` parameter, but a logging tool might use it to write down where an error happened before letting it carry on.
:::

::: context swallow-risk Hiding an error on purpose
Swallowing an exception is sometimes right: "delete this file if it exists" should not fail when the file is already gone. The standard library has a ready-made tool for that, `contextlib.suppress`, and the `Suppress` class in the task is your own version of it. But a context manager that returns `True` for every exception hides real bugs, the way a smoke alarm with the battery taken out hides a fire. Swallow only the exact kinds you expect.
:::

::: context one-yield Why exactly one yield
The decorator runs your generator up to the first `yield` when the block starts, and resumes it once when the block ends. So it needs exactly one `yield`. A generator that never yields gives `RuntimeError: generator didn't yield`, and one that yields a second time gives `RuntimeError: generator didn't stop`. Behind the scenes, `@contextmanager` builds an object with `__enter__` and `__exit__` that does this driving for you, so both ways of writing a context manager end up using the same protocol.
:::

::: context sentinel-object A value that can only mean one thing
In the basics you met a sentinel: a special value that means "stop here" and can never be real data. `object()` is the safest sentinel there is. Each call makes a new object, and `is` compares identity, so `_MISSING` is only ever `is` itself. No value stored in a dict by anyone else can be mistaken for it. The underscore at the front of `_MISSING` is the same "inside detail" convention as `_balance` in the properties lesson.
:::

::: context restore-state Put everything back the way you found it
Test code often changes a setting for one test: a clock set to a fixed time, a simulator switched into a fault mode, a configuration value changed. If the test fails and the setting is not put back, every test after it runs in the wrong conditions, and the failures pile up far from the cause. Python's own testing tools include `unittest.mock.patch.dict`, which does what `temp_setting` does: change a dict for the length of a block, then restore it.
:::

=== py3-06 | Dataclasses and enums
--- teach
Last lesson you used a decorator, `@contextmanager`, to build a whole context manager out of a small generator. This lesson uses two more ready-made tools that save you writing the same code again and again. `@dataclass` writes the usual methods of a class for you, and `Enum` gives you a fixed set of named choices.

Think of a paper form, like a library card application. It has fixed boxes: name, date of birth, address. Nobody redraws the boxes for each new person; the form is printed once and filled in many times. A dataclass is that printed form for your objects.

### The ceremony of a class that holds data

Many classes exist only to hold a few pieces of data. From the lesson on classes that behave you know what a good one needs: an `__init__` to store the data, a `__repr__` so it prints well, and an `__eq__` so `==` compares the data. Written by hand, even a tiny class is long:

```python
class Item:
    def __init__(self, name, price):
        self.name = name
        self.price = price

    def __repr__(self):
        return f"Item(name={self.name!r}, price={self.price!r})"

    def __eq__(self, other):
        if not isinstance(other, Item):
            return NotImplemented
        return (self.name, self.price) == (other.name, other.price)
```

(The `!r` inside the f-string means "use `repr` here", so a string shows with its quotes.) Every field's name is typed several times. Add a field and you must remember to change three methods. Code like this, repeated with small changes, is called [[boilerplate|boilerplate]].

### `@dataclass` writes those methods for you

**`@dataclass`**, from the `dataclasses` module, is a [[decorator you put on a class|class-decorator]]. It reads the list of fields and writes `__init__`, `__repr__` and `__eq__` for you:

```python
from dataclasses import dataclass

@dataclass
class Item:
    name: str
    price: float

print(Item("tea", 2.5))                  # Item(name='tea', price=2.5)
print(Item("tea", 2.5) == Item("tea", 2.5))   # True
```

Those two short lines inside the class are the whole list of **fields**, the pieces of data each object holds. `Item("tea", 2.5)` works because the dataclass wrote an `__init__` that takes `name` and `price` in that order and stores them as `self.name` and `self.price`.

### Type annotations

`name: str` is read "name, of type str". It is a **[[type annotation|annotations]]**: a label that records what type a field is meant to hold. `price: float` says the price is meant to be a float. For a list, `list[str]` means "a list of strings".

Python does **not** check annotations when the program runs:

```python
print(Item("tea", "cheap"))    # Item(name='tea', price='cheap')   no error
```

The expert course shows the tools that do check them. `@dataclass` uses the annotations only to find the fields: a line with a name, a colon and a type is a field.

### Default values

A field can have a default, written with `=`, like a default argument in a function:

```python
@dataclass
class Item:
    name: str
    price: float = 0.0

print(Item("bag"))     # Item(name='bag', price=0.0)
```

Fields with defaults must come **after** fields without them, for the same reason as in a `def` line. Putting `price: float = 0.0` above `name: str` stops with a `TypeError` saying that a non-default argument follows a default argument.

### A list as a default: `field(default_factory=list)`

Remember the mutable default argument bug? A default of `[]` is made once, and then every call [[shares that one list|mutable-default]]. A dataclass would have the same problem, so it refuses a plain `= []`:

```python
@dataclass
class Item:
    name: str
    tags: list[str] = []
# ValueError: mutable default <class 'list'> for field tags is not allowed: use default_factory
```

The fix is `field(default_factory=list)`. A **factory** is something that makes new things. `default_factory=list` means "each time a new object is made without tags, call `list()` to make it a fresh empty list":

```python
from dataclasses import dataclass, field

@dataclass
class Item:
    name: str
    price: float
    tags: list[str] = field(default_factory=list)

a = Item("tea", 2.5)
b = Item("jam", 7.5)
a.tags.append("hot")
print(a.tags, b.tags)       # ['hot'] []   each has its own list
print(a)                    # Item(name='tea', price=2.5, tags=['hot'])
```

Note that you pass `list` itself, with no brackets. The dataclass calls it later, once per object.

### Your own methods still work

A dataclass is still an ordinary class. Below the fields you can write methods as usual, with `self`:

```python
@dataclass
class Item:
    name: str
    price: float

    def discount(self):
        self.price = self.price / 2

tea = Item("tea", 2.5)
tea.discount()
print(tea.price)       # 1.25
```

### `frozen=True`: read-only objects

`@dataclass(frozen=True)` makes objects that cannot be changed once they are made. Trying to set a field raises `FrozenInstanceError`:

```python
@dataclass(frozen=True)
class Point:
    x: float
    y: float

p = Point(1, 2)
p.x = 5      # dataclasses.FrozenInstanceError: cannot assign to field 'x'
```

A frozen dataclass is also **[[hashable|hashable]]**: Python can work out a hash for it, so it can go in a set and be a dict key. An ordinary dataclass cannot; `hash(Item("tea", 2.5))` raises `TypeError: unhashable type: 'Item'`.

```python
print(len({Point(1, 2), Point(1, 2), Point(2, 1)}))   # 2   the two equal points count once
```

### `order=True`: comparing with `<`

`@dataclass(order=True)` adds `<`, `>`, `<=` and `>=`. They compare the fields in order: the first field first, and only if that is a tie, the second, like the tuple keys in the sorting lesson:

```python
@dataclass(order=True)
class Version:
    major: int
    minor: int

print(Version(1, 2) < Version(1, 3))           # True: major ties, 2 < 3
print(sorted([Version(2, 0), Version(1, 5)]))  # [Version(major=1, minor=5), Version(major=2, minor=0)]
```

### Enums: a fixed set of named values

Now the second tool. Suppose tasks have a priority, and you store it as a string: `"low"`, `"medium"` or `"high"`. One day someone types `"hihg"`. Nothing complains. The task silently matches none of your `if` checks.

An **enum** (short for *enumeration*, a numbered list of choices) is a [[fixed set of named values|enum-modes]]. You make one as a class that inherits from `Enum`. Each line inside is one **member**: a name, `=`, and its value:

```python
from enum import Enum

class Color(Enum):
    RED = 1
    GREEN = 2
```

Now you pass `Colour.RED` around instead of a string. A typo like `Colour.REDD` is an immediate [[AttributeError|fail-loudly]], not a silent wrong answer.

Each member knows its name and its value, and you can look members up either way:

```python
Color.RED            # <Color.RED: 1>
Color.RED.name       # 'RED'
Color.RED.value      # 1
Color(2)             # <Color.GREEN: 2>   look up by value, with round brackets
Color["GREEN"]       # <Color.GREEN: 2>   look up by name, with square brackets
list(Color)          # [<Color.RED: 1>, <Color.GREEN: 2>]
len(Color)           # 2
```

An enum class is iterable, so `list(Colour)` gives every member in the order they were written, and `len` counts them. Asking for a value that is not there, like `Colour(5)`, raises `ValueError: 5 is not a valid Colour`.

### Comparing enum members

A member is not the same thing as its value. Compare members with members:

```python
print(Color.RED == Color.RED)     # True
print(Color.RED is Color(1))      # True: there is only one RED
print(Color.RED == 1)              # False
```

`is` works because [[each member exists only once|enum-singleton]]. When you really need the number, use `.value`.

Plain enum members also cannot be compared with `<`: `Colour.RED < Colour.GREEN` raises `TypeError`. So to sort by an enum, sort on its `.value`. From the sorting lesson you know the minus trick for "biggest first" inside a tuple key. For a list of tasks that each have a `.priority` (an enum member) and a `.title`:

```python
sorted(tasks, key=lambda t: (-t.priority.value, t.title))
```

Read the key as: "highest value first (minus flips the order), then titles A to Z to break ties".

**Watch out:** comparing an enum member to its raw value. `Colour.RED == 1` is `False`, with no error, so an `if` like that is quietly never true. Compare members with members (`==` or `is`), and use `.value` only when you really need the number.

::: context boilerplate Words stamped out again and again
The word comes from printing. Newspapers were once sent ready-made text, like adverts and syndicated columns, already cast on metal printing plates, to print without changing a word. Programmers borrowed it for code that is the same in every class except for a few names. Boilerplate is not only dull to write. When you add a field, it is easy to update `__init__` and forget `__eq__`, and then two objects that differ in that field compare equal.
:::

::: context class-decorator A decorator on a class
In the decorators lesson a decorator took a function and gave back a new one. A decorator can sit above a `class` too. Python builds the class, hands it to `dataclass`, and keeps what comes back under the same name. `dataclass` reads the annotated fields, writes the methods, attaches them to the class and returns it. `@dataclass(frozen=True)` has brackets because it takes settings, the same extra layer as `@repeat(3)`.
:::

::: context annotations Labels for readers and tools
Annotations also work on function parameters and results: `def area(width: float, height: float) -> float:`. The `->`, read "returns", labels the result. Python stores them but does not check them. Separate tools called type checkers, such as mypy, read the annotations and warn you before the program runs, for example when you pass a string where a float is expected. Large teams writing safety-critical code rely on checks like these, because a mistake found before a program runs is far cheaper than one found in flight.
:::

::: context hashable Why only frozen objects can be keys
You met hashes when you first used sets: a set or dict turns each item into a number, its hash, and uses it to choose the shelf the item lives on. The hash is worked out from the data. If an object's data could change after it went on a shelf, its hash would change too, and Python would look for it on the wrong shelf and never find it. So, by default, a dataclass only gets a hash when it is frozen and its data can never change. Tuples and strings can be keys for the same reason: they never change.
:::

::: context enum-modes Named modes on a spacecraft
Flight software is full of fixed sets of choices. A spacecraft is in exactly one mode at a time, such as a normal operations mode or a safe mode, and each command it accepts is one of a fixed list. Writing these as named constants, rather than loose strings or bare numbers, means a misspelt mode is caught when the code is checked or first run, not discovered in orbit. The `.value` numbers are still useful when a mode has to be sent to the ground as a small number inside a telemetry packet.
:::

::: context fail-loudly Fail early, fail loudly
Engineers prefer a mistake that stops the program with a clear error over one that quietly gives a wrong answer. `Colour.REDD` stops at once, on the exact line with the typo, and the traceback names it. A string `"hihg"` travels on through the program and causes trouble somewhere else, much later, where the real cause is hard to find. It is the same idea as fixing bad data at its source in the traceback lesson.
:::

::: context enum-singleton Only one of each
When Python builds the `Colour` class, it makes each member exactly once. `Colour.RED`, `Colour(1)` and `Colour["RED"]` all hand back that same object, which you can check with `id`. That is why `is` is safe for enum members, even though for most values you should use `==`. It is also why a member can safely be a dict key or go in a set.
:::

=== py3-07 | Special methods: making your own types feel built in
--- teach
Last lesson `@dataclass` wrote `__init__`, `__repr__` and `__eq__` for you. Those are three of Python's special methods. There are many more, and this lesson shows the most useful ones. With them, your own objects can work with `len`, square brackets, `for` loops, `+`, `*`, `abs` and sets, the same way lists and numbers do.

Think of a wall socket. Any lamp, phone charger or kettle works in it, as long as it has the right plug. The socket does not care what the device is. Python's syntax is the socket, and special methods are the plug: give your class the right method, and the matching piece of syntax works on it.

### Syntax is method calls in disguise

Why does `len(x)` work on a list, `x[0]` on a string and `a + b` on numbers? Because those types define **[[special methods|dunder-word]]**, the methods with two underscores on each side of the name, also called *dunder* methods. When you write a piece of syntax, Python turns it into a call to one of them:

| You write | Python calls |
|---|---|
| `len(v)` | `v.__len__()` |
| `v[i]` | `v.__getitem__(i)` |
| `for x in v` | `v.__iter__()` |
| `x in v` | `v.__contains__(x)` |
| `a + b` | `a.__add__(b)` |
| `a * 3` | `a.__mul__(3)` |
| `3 * a` | `a.__rmul__(3)` (after `int.__mul__` gives up) |
| `a == b` | `a.__eq__(b)` |
| `hash(a)` | `a.__hash__()` |
| `abs(a)` | `a.__abs__()` |
| `bool(a)` | `a.__bool__()` (or `__len__` if there is no `__bool__`) |

Define them and your objects work with the whole language: `sum`, `sorted`, `in`, sets, dict keys. Giving `+` or `*` a meaning for your own class is called [[operator overloading|operator-overloading]]. The rest of this lesson takes the table a few rows at a time.

### Length, square brackets and loops

Here is a small class that holds some items in a tuple. Three special methods each hand the job over to the tuple:

```python
class Shelf:
    def __init__(self, *items):
        self.items = tuple(items)

    def __len__(self):
        return len(self.items)

    def __getitem__(self, index):
        return self.items[index]

    def __iter__(self):
        return iter(self.items)

s = Shelf("a", "b", "c")
print(len(s))        # 3      Python called s.__len__()
print(s[0], s[-1])   # a c    Python called s.__getitem__(0), then (-1)
print(list(s))       # ['a', 'b', 'c']
print("b" in s)      # True
```

`__init__` uses `*items`, the star from the `*args` lesson, so `Shelf` takes any number of items. `__iter__` returns an iterator, exactly as in the iterators lesson: `iter(self.items)` asks the tuple for one. There is no `__contains__` here, yet `in` still works: Python [[falls back|fallbacks]] to looping over the object and comparing each item.

### Adding two objects: `__add__`

When you write `a + b`, Python calls `a.__add__(b)`. The left side is `self`, and the right side arrives as the parameter, usually called `other`:

```python
class Money:
    def __init__(self, cents):
        self.cents = cents
    def __add__(self, other):
        if not isinstance(other, Money):
            return NotImplemented
        return Money(self.cents + other.cents)
    def __repr__(self):
        return f"Money({self.cents})"

print(Money(150) + Money(75))     # Money(225)
```

You met `NotImplemented` with `__eq__` in the lesson on classes that behave. It is a special value, not an error. Returning it tells Python "I don't know how to do this", so Python can [[try the other operand's method|reflected-ops]], and raise a clear `TypeError` if neither knows:

```python
Money(150) + 5
# TypeError: unsupported operand type(s) for +: 'Money' and 'int'
```

Notice that `__add__` builds a **new** `Money` and returns it. It does not touch `self.cents`. After `total = a + b`, the value `a` must be the same as before, exactly as with numbers. Subtraction works the same way, with **`__sub__`** for `a - b`.

### Numbers on the right: `__rmul__`

Multiplying by a number works the same way: `a * 3` calls `a.__mul__(3)`. But `3 * a` is harder, because now the number is on the left. Python first asks the number: `int.__mul__(3, a)`. An `int` has never heard of your class, so it returns `NotImplemented`. Python then tries the **reflected** method on the right-hand side, `a.__rmul__(3)` (the "r" is for "right").

For multiplying by a number, the answer is the same whichever side the number is on. So you can give the one method [[a second name|method-alias]] inside the class:

```python
class Money:
    # ... __init__, __add__ and __repr__ as before ...
    def __mul__(self, k):
        if not isinstance(k, int):
            return NotImplemented
        return Money(self.cents * k)

    __rmul__ = __mul__

print(Money(2) * 3)     # Money(6)
print(3 * Money(2))     # Money(6)
```

The line `__rmul__ = __mul__` says "the method called `__rmul__` is the same function as `__mul__`".

### Equal things need equal hashes

When you met sets, you learned that a set or dict turns each item into a number, its **hash**, to decide which shelf it lives on. `hash(x)` gives that number. The rule that keeps sets and dicts working is:

**Objects that compare equal must have equal hashes.**

If two equal objects had different hashes, a set would put them on different shelves and keep both, and a dict could not find a key you know is there. To stop that happening by accident, when your class defines `__eq__`, Python sets `__hash__` to `None`. That makes the objects **unhashable**:

```python
class Pair:
    def __init__(self, a, b):
        self.components = (a, b)
    def __eq__(self, other):
        if not isinstance(other, Pair):
            return NotImplemented
        return self.components == other.components

print(Pair(1, 2) == Pair(1, 2))   # True
{Pair(1, 2)}                      # TypeError: unhashable type: 'Pair'
```

To fix it, define **`__hash__`** yourself. [[Hash the same data you compare|hash-rule]], and only if that data cannot change. A tuple never changes, and a tuple of numbers can be hashed, so a class that keeps its data in a tuple can hand the job over:

```python fragment
    def __hash__(self):          # inside class Pair
        return hash(self.components)

print(len({Pair(1, 2), Pair(1, 2)}))   # 1   equal pairs count once
```

### Length as a number, and true or false

**`__abs__`** runs for `abs(a)`. For numbers, `abs` is the size without the sign: `abs(-7)` is `7`. For your own class, you decide what "size" means.

**`__bool__`** runs for `bool(a)`, and also whenever your object sits after `if` or `while`. It must return `True` or `False`. If a class has no `__bool__`, Python uses `__len__` instead: length 0 means false, as for an empty list. That is why `bool(Shelf())` is `False`.

Two built-ins help here. **`any(xs)`** is `True` if at least one item of `xs` is truthy. **`all(xs)`** is `True` if every item is:

```python
print(any([0, 0, 3]))    # True: 3 is truthy
print(any([0, 0, 0]))    # False: every one is 0
print(all([1, 2, 0]))    # False: 0 is falsy
```

### Slices arrive as a `slice` object

`__getitem__` receives whatever is inside the square brackets. For `v[2]` that is the number `2`. For `v[1:3]` it is a [[slice object|slice-object]], a small value that holds the start and the stop:

```python
class Show:
    def __getitem__(self, index):
        return index

print(Show()[2])      # 2
print(Show()[1:3])    # slice(1, 3, None)
```

The `None` is the step, which was not given. `isinstance(index, slice)` lets `__getitem__` handle both kinds: return one item for a number, and a new object of your own class for a slice. A tuple understands a slice object directly, so `self.items[index]` works for both.

### Building a new object from pieces

The last trick joins two things you know. A generator expression, from the generators lesson, makes values one at a time. A star in a call, from the lesson on spreading arguments, spreads values out into separate arguments. Together they build a new object:

```python
a = (1, 2)
b = (10, 20)
print(list(zip(a, b)))                    # [(1, 10), (2, 20)]
print(Shelf(*(x + y for x, y in zip(a, b))).items)   # (11, 22)
```

Read the last line from the inside out. `zip(a, b)` pairs the items up. The generator expression adds each pair. The `*` spreads the results out, so the call is `Shelf(11, 22)`.

For a `repr` of any number of values, `", ".join(...)` glues strings together with a comma and a space between them:

```python
print(", ".join(repr(c) for c in (1, 2.5)))    # 1, 2.5
```

For the length of a [[vector|vectors-in-flight]], you need a square root. `math.sqrt`, from the standard library lesson, gives it: `math.sqrt(3 * 3 + 4 * 4)` is `5.0`.

**Watch out:** making `__add__` change `self` and return it. It looks fine at first, but after `c = a + b`, `a` has changed too, and every other variable that holds `a` sees the change. `a + b` must never modify `a`. Always build and return a new object.

::: context dunder-word Double underscore, spoken fast
"Dunder" is short for "double underscore", so `__len__` is read "dunder len". Python keeps names shaped like this for itself. You write them, but you almost never call them yourself: you write `len(v)`, and Python finds `__len__`. Do not invent new names of this shape for your own ordinary methods, because a future version of Python might give that name a meaning of its own.
:::

::: context operator-overloading One symbol, many meanings
To overload something is to give it more than one job. `+` already means "add" for numbers, "join" for strings and lists, and now whatever you choose for your class. Used well, it lets maths code read like maths. The NumPy library, used throughout science and engineering, gives its arrays `__add__`, `__mul__` and friends, so `a + b` adds two whole arrays of numbers item by item.
:::

::: context fallbacks Python tries the next best thing
For `x in v`, Python looks for `__contains__` first. If there is none, it loops over `v` with `__iter__` and compares each item with `==`. For `bool(v)`, it looks for `__bool__`, then `__len__`. If a class has neither, every object of it counts as true. These fallbacks mean a few well-chosen methods give you a lot of behavior for free. Write the specific method only when you can do the job faster or differently.
:::

::: context reflected-ops Asking the other side
For `a + b`, Python first tries `a.__add__(b)`. If that returns `NotImplemented`, it tries the right-hand side's reflected method, `b.__radd__(a)`. Only if that also returns `NotImplemented`, or does not exist, does Python raise `TypeError`. This is how `3 * v` ends up calling `v.__rmul__(3)`.

::: context method-alias Functions are values, even in a class
You saw in the decorators lesson that functions are values you can pass around and store under names. The inside of a class is a list of names too: each `def` makes a function and stores it under that name. `__rmul__ = __mul__` stores the same function under a second name. Python then finds it when it looks up `__rmul__`, and `self` and `k` arrive exactly as they would for `__mul__`. It only works because `k * v` and `v * k` mean the same thing; for subtraction, `k - v` and `v - k` differ, so a reflected method would need its own code.
:::

::: context hash-rule Why equal objects need equal hashes
A set looks an item up by working out its hash and going to that shelf. Suppose two equal vectors had different hashes. `Vector(1, 2)` goes on shelf 7. Later you ask whether `Vector(1, 2)` is in the set, a different object with equal data, and its hash sends Python to shelf 3. Nothing is there, so the answer is "no", even though an equal vector is in the set.

::: context slice-object The colon, packed into a value

--- solution
import math


class Vector:
    def __init__(self, *components):
        self.components = tuple(components)

    def __repr__(self):
        return f"Vector({', '.join(repr(c) for c in self.components)})"

    def __len__(self):
        return len(self.components)

    def __iter__(self):
        return iter(self.components)

    def __getitem__(self, index):
        if isinstance(index, slice):
            return Vector(*self.components[index])
        return self.components[index]

    def _check(self, other):
        if not isinstance(other, Vector):
            return False
        if len(other) != len(self):
            raise ValueError("vectors must have the same length")
        return True

    def __add__(self, other):
        if not self._check(other):
            return NotImplemented
        return Vector(*(a + b for a, b in zip(self, other)))

    def __sub__(self, other):
        if not self._check(other):
            return NotImplemented
        return Vector(*(a - b for a, b in zip(self, other)))

    def __mul__(self, k):
        if not isinstance(k, (int, float)):
            return NotImplemented
        return Vector(*(a * k for a in self))

    __rmul__ = __mul__

    def __eq__(self, other):
        if not isinstance(other, Vector):
            return NotImplemented
        return self.components == other.components

    def __hash__(self):
        return hash(self.components)

    def __abs__(self):
        return math.sqrt(sum(a * a for a in self))

    def __bool__(self):
        return any(self.components)

=== py3-08 | functools: partial, reduce and lru_cache
--- teach
Last lesson you gave your own `Vector` class special methods, so that `+`, `len` and `abs` worked on it like on a built-in type. A few lessons before that, in the decorators lesson, you saw that a function is a value: you can hand it to another function and get a new function back. This lesson opens a drawer of the standard library built for exactly that kind of work. It is called `functools`, short for "function tools", and it is full of [[functions that work on other functions|higher-order]].

You will meet three of its tools, one at a time:

- `partial`, which fills in some of a function's arguments ahead of time,
- `reduce`, which boils a whole list down to one value,
- `lru_cache`, which lets a function remember answers it has already worked out.

You bring them in the usual way, with an import at the top of the file:

```python
from functools import partial, reduce, lru_cache
```

### partial: fill in some arguments now

Think of the speed-dial button on a phone. The number is already stored in it, so you press one button instead of typing ten digits. **`partial`** does that for a function. It takes a function and some of its arguments, and it gives you back a **new function** with those arguments already filled in. You give the rest later, when you call it.

Here is a small function to practice on. `**` means "to the power of", so `base ** exp` is `base` multiplied by itself `exp` times:

```python
def power(base, exp):
    return base ** exp

power(9, 2)        # 81   (9 times 9)
```

Now fill in `exp` ahead of time:

```python
square = partial(power, exp=2)
square(9)          # 81
square(5)          # 25
```

`square` is a new function. When you call `square(9)`, it calls `power(9, exp=2)` for you. The original `power` does not change.

### partial with positional arguments

You can also fill in arguments by position, with no name. Those fill the parameters from the left, so they become the *first* arguments. Python has a built-in function `pow` that works like our `power`: `pow(10, 3)` is 10 to the power of 3, which is 1000. Filling in its first argument fixes the base:

```python
ten_to_the = partial(pow, 10)
ten_to_the(3)      # 1000   same as pow(10, 3)
ten_to_the(2)      # 100
```

One more example, with a function you know well. `int("101")` turns text into the number one hundred and one. With the setting `base=2`, `int` reads the text as a [[binary number|binary]] instead:

```python
int_from_binary = partial(int, base=2)
int_from_binary("101")   # 5
```

`partial` is handy wherever a tool wants a function of **one** argument and yours takes more. In the sorting lesson, `key=` wanted exactly that, and a callback, a function handed over to be called later, often does too.

**Watch out:** positional values fill parameters from the left. `partial(power, 2)` fixes `base`, not `exp`, so it makes "2 to the power of something", not "something squared". When in doubt, fill in by name, as in `partial(power, exp=2)`.

### reduce: boil a list down to one value

Picture adding up a shopping receipt on a calculator. You start at 0. You add the first price and look at the running total. You add the next price to that total, and the next, until the receipt ends. The last running total is the answer.

**`reduce`** does exactly that. It takes three things: a function that combines two values, a sequence, and a **start value**. It keeps a running result, and for each item it calls the function with the running result and the item. Whatever the function hands back becomes the new running result. This is also called [[folding|fold]] a list.

The combining function takes **two** arguments. You met lambdas with one parameter in the sorting lesson; a lambda can have two, separated by a comma. Read `lambda acc, x: acc + x` as "given `acc` and `x`, hand back `acc + x`". The name `acc` is short for [[accumulator|accumulator]], the running result.

```python
reduce(lambda acc, x: acc + x, [1, 2, 3, 4], 0)    # 10
```

Step by step:

| Step | acc (running result) | x (next item) | acc + x |
|---|---|---|---|
| 1 | 0 (the start value) | 1 | 1 |
| 2 | 1 | 2 | 3 |
| 3 | 3 | 3 | 6 |
| 4 | 6 | 4 | 10 |

That is `((((0 + 1) + 2) + 3) + 4)`, which is 10. The list has ended, so `reduce` hands back the last running result.

With `*` (times) instead of `+` you get a product. Start at 1, because multiplying by 1 changes nothing, the way adding 0 changes nothing:

```python
reduce(lambda acc, x: acc * x, [2, 3, 4], 1)    # 24   (2 times 3 times 4)
reduce(lambda acc, x: acc * x, [], 1)           # 1    empty list: you get the start value
```

**Always give a start value.** Without one, `reduce` uses the first item as the start, and on an empty list it has nothing to start from:

```python
reduce(lambda acc, x: acc + x, [])
# TypeError: reduce() of empty iterable with no initial value
```

For plain sums and products, `sum()` and `math.prod()` from the standard library lesson are easier to read. `reduce` earns its place when the combining step is your own, like the next one.

**Watch out:** the combining function always gets the running result *first* and the next item *second*. Mix them up and you get wrong answers, often with no error at all.

### reduce with functions: chaining them together

Here is where `reduce` shines. Functions are values, so a function can hand back a new function. This lambda takes two functions, `f` and `g`, and hands back a new function that runs `g` first and then `f` on the result:

```python
combine = lambda f, g: lambda x: f(g(x))

add_one = lambda x: x + 1
square = lambda x: x * x

both = combine(add_one, square)
both(3)          # 10   add_one(square(3)) = add_one(9) = 10
```

Read `f(g(x))` from the inside out: `g` runs first, `f` second. So the function written on the **right** runs first. Putting functions inside each other like this is called [[composing|compose-word]] them.

To chain a whole list of functions, `reduce` with `combine`. The start value is a function that hands back whatever it is given, `lambda x: x`, called the **[[identity function|identity]]**:

```python
chain = reduce(combine, [add_one, square], lambda x: x)
chain(3)         # 10   add_one(square(3))
```

Step by step: first `combine(identity, add_one)` makes "add one". Then `combine` of that with `square` makes "square, then add one". So the rightmost function in the list runs first, and the leftmost runs last. With an empty list you get back the start value, the identity function, which returns its argument unchanged.

### lru_cache: remember answers

Think of a times table you have learned by heart. Nobody works out 7 times 8 from scratch every time; you remember 56. **`lru_cache`** gives a function that kind of memory. It is a decorator, like the ones you wrote in the decorators lesson. It takes a setting, so it is written with brackets, like `@repeat(3)` was. It stores every answer, filed under the arguments that produced it. Call the function again with the same arguments, and you get the stored answer at once, without running the body.

```python
from functools import lru_cache

@lru_cache(maxsize=None)
def slow_square(n):
    print("computing", n)
    return n * n

slow_square(4)   # prints "computing 4", returns 16
slow_square(4)   # returns 16 at once, nothing printed
slow_square.cache_info()   # CacheInfo(hits=1, misses=1, maxsize=None, currsize=1)
```

A **cache** is a store of answers kept for later. `cache_info()` reports how it is doing:

- **hits**: calls answered from the store (the second call),
- **misses**: calls that had to run the body (the first call),
- **maxsize**: how many answers it may keep; `None` means no limit (the [[LRU in the name|lru]] is about what happens when there is a limit),
- **currsize**: how many answers it holds now.

This only makes sense for a [[pure function|pure]], one whose answer depends only on its arguments. Cache a function that reads the clock or a file, and it will keep handing back an old answer after the real one has changed.

**Watch out:** the arguments must be hashable, the same rule as for dict keys and set items. Numbers, strings and tuples are fine. A list is not: `slow_square([1])` stops with `TypeError: unhashable type: 'list'`.

### A cached function that calls itself

A function is allowed to call **itself** on a smaller version of the same problem. This is called **recursion**. It needs a stopping case, where it answers without calling itself again. Here is a function that counts how many times you can halve a number before you reach 1. `//` is whole-number division, so `8 // 2` is 4:

```python
@lru_cache(maxsize=None)
def halvings(n):
    if n == 1:
        return 0                    # the stopping case: already at 1
    return 1 + halvings(n // 2)     # one halving, plus the halvings of what is left

halvings(8)      # 3   (8 -> 4 -> 2 -> 1)
halvings.cache_info()    # CacheInfo(hits=0, misses=4, maxsize=None, currsize=4)
halvings(16)     # 4
halvings.cache_info()    # CacheInfo(hits=1, misses=5, maxsize=None, currsize=5)
```

`halvings(8)` asked for 8, 4, 2 and 1: four misses. Then `halvings(16)` ran its body once, asked for `halvings(8)`, and got it straight from the store: one hit. For a function that calls itself many times on the same numbers, those hits save a lot of work. Your task uses this on [[a famous number puzzle|collatz]]. (A later lesson goes much deeper into recursion.)

::: context higher-order Functions that handle functions
A function that takes a function as an argument, or hands one back, is called a higher-order function. You have used several already: `sorted` takes a `key=` function, and every decorator takes a function and returns a new one. They are useful because they let you write the *pattern* once ("do this to each item", "remember the answers") and plug in the details as a function. Many languages have them, and much of `functools` is higher-order functions.
:::

::: context binary Counting in twos
We count in tens: each place in a number is worth ten times the one to its right. Binary counts in twos: the places are worth 1, 2, 4, 8 and so on, and each digit is 0 or 1. So "101" in binary is one 4, no 2s and one 1, which is 5. Computers store everything in binary. Spacecraft telemetry often arrives as raw bits, and code that unpacks it uses exactly this kind of conversion; `int(text, base=16)` does the same for hexadecimal, which counts in sixteens.

::: context accumulator The running result
To accumulate means to pile up, like snow on a rolling snowball. An accumulator is the variable that holds the pile so far. You have written them before without the name: `total = 0` before a loop, then `total += x` inside it. `reduce` is that same loop, packed into one call: the start value is `total = 0`, and the combining function is the `total + x` step.
:::

::: context compose-word Composing functions
In maths, putting one function inside another is called composition, and it is often written f ∘ g, read "f after g". It means "do g, then do f to the result". The order surprises people at first, because you read f first but it runs last. Programmers compose small functions to build a pipeline, the same idea as the generator pipelines from earlier in this course.
:::

::: context identity A function that does nothing, on purpose
`lambda x: x` hands back exactly what it was given. That sounds useless, but it plays the same part for functions that 0 plays for adding and 1 plays for multiplying: combining with it changes nothing. That makes it the right start value for chaining functions, and it is also the right answer when there are no functions to chain at all.
:::

::: context lru Least recently used
LRU stands for "least recently used". If you give the cache a limit, say `@lru_cache(maxsize=100)`, and it is full when a new answer arrives, it throws away the answer that has gone unused the longest. That keeps memory in check while holding on to the answers you keep asking for. With no brackets at all, `@lru_cache` uses a limit of 128. Since Python 3.9, `functools.cache` is a short name for `lru_cache(maxsize=None)`.
:::

::: context pure Pure functions
A pure function works like a formula: the same inputs always give the same output, and it changes nothing outside itself. `n * n` is pure. A function that reads a sensor, the time or a file is not, because its answer can change while its arguments stay the same. Engineers like pure functions for more than caching: they are the easiest code to test, because a test only has to check inputs against outputs.
:::

::: context collatz The Collatz puzzle
Start from any whole number. If it is even, halve it. If it is odd, multiply by 3 and add 1. Repeat. The mathematician Lothar Collatz asked in 1937 whether every starting number reaches 1 in the end. Computers have checked an enormous range of starting numbers and all of them get there, yet nobody has proved it is always true. The chains wander: 27 takes 111 steps and climbs past 9,000 before it comes down. Many chains pass through the same numbers, which is exactly why a cache helps.
:::

=== py3-09 | Debugging: aliasing and shared state
--- teach
Last lesson `lru_cache` refused lists as arguments, because a list can change after it has been stored. This lesson is a bug hunt about that same fact: what goes wrong when something that can change is shared by two names. You met the start of this story in the intermediate course, in the mutable default argument bug. Here you will see the same cause hiding in three new places, and learn the tools that fix it for good.

### Names are labels, not boxes

It is tempting to picture a variable as a box with a value inside. In Python that picture is wrong, and the wrong picture causes the bugs in this lesson. A variable is a **name tied to an object**, like a luggage label tied to a suitcase. The name `a` is not the list; it is a label pointing at the list. The pointing is called a [[reference|reference]].

Two labels can be tied to the same suitcase. Then anything you put in the suitcase through one label shows up when you open it through the other. Two names for one object is called **aliasing**. An alias is a second name for the same thing, like a nickname.

```python
a = [1, 2]
b = a          # no copy: b is another name for the same list
b.append(3)
a              # [1, 2, 3]   changed, though you only touched b
a is b         # True        the very same object
```

`b = a` never makes a copy. It ties a second label to the list that `a` already points at.

### The debugging tool: is

When two things change together that should not, ask: **are they the same object?** You met the tools in the mutable default lesson. `a is b` asks "are these the very same object?", and `id(a) == id(b)` asks the same thing with the object's identity number. `==` does not help here, because it only asks whether the values are equal, and a copy has equal values too.

### Where aliasing hides: multiplying a list of lists

`[0] * 3` makes a list holding three zeros: `*` on a list means "repeat the contents this many times". That works well:

```python
row = [0] * 3             # [0, 0, 0]
```

Now try to build a grid of 2 rows by repeating a row:

```python
grid = [[0] * 3] * 2      # looks like [[0, 0, 0], [0, 0, 0]]
grid[0][0] = 9            # change one cell in row 0
grid                      # [[9, 0, 0], [9, 0, 0]]   row 1 changed too!
grid[0] is grid[1]        # True
```

The outer `* 2` repeats what is in the list, and what is in the list is a *reference* to one inner row. So you get [[two references to one row|grid-rows]], not two rows.

Why was `[0] * 3` fine? It also holds three references to the same `0`. But a number can never be changed, only replaced, so sharing it is harmless. Sharing only bites when the shared object is **mutable**, meaning it can be changed in place, like a list or a dict. (Numbers, strings and tuples are [[immutable|immutable]]: they cannot.)

The fix is to build each row separately, with a comprehension:

```python
grid = [[0] * 3 for _ in range(2)]    # the inner [0] * 3 runs once per row
grid[0][0] = 9
grid                                  # [[9, 0, 0], [0, 0, 0]]
```

The comprehension runs `[0] * 3` again on every pass, so each pass makes a brand-new list. The loop variable is written `_`, a [[name that means "not used"|underscore]], because we need the loop to run twice but never look at the counter.

### Where aliasing hides: dict.fromkeys

`dict.fromkeys(keys, value)` builds a dict with every key set to the same value:

```python
dict.fromkeys(["ada", "lin"], 0)     # {'ada': 0, 'lin': 0}
```

With a number, that is fine. With a list, every key gets the **same** list:

```python
inv = dict.fromkeys(["ada", "lin"], [])
inv["ada"].append("sword")
inv                                  # {'ada': ['sword'], 'lin': ['sword']}
```

`[]` ran once, when you called `fromkeys`, and made one list. A dict comprehension runs `[]` once per key, so each key gets its own:

```python
inv = {name: [] for name in ["ada", "lin"]}
```

### Shallow copies and deep copies

Sometimes you really do want a copy. Python has several ways to copy a list or dict: `list(x)`, `x.copy()`, `x[:]` (a slice from start to end) and `copy.copy(x)`. All of them make a **shallow copy**: a new outer container, but holding references to the *same* objects inside.

Picture photocopying a page of a notebook that has a sticky note stuck on it. You get a new page, but the sticky note is not copied: both pages now point at the one sticky note. For data with nothing changeable inside it, like a list of numbers, a shallow copy is enough. For **nested** data, a list or dict with other lists or dicts inside, you need **`copy.deepcopy`**, from the `copy` module. It copies the container, then everything inside it, then everything inside *that*, all the way down:

```python
import copy

state = {"round": 1, "scores": {"ada": 0}}
shallow = state.copy()
deep = copy.deepcopy(state)

state["scores"]["ada"] = 5
shallow["scores"]     # {'ada': 5}   shares the inner dict with state
deep["scores"]        # {'ada': 0}   has its own inner dict
```

`shallow` is a new dict, so `shallow is state` is `False`. But `shallow["scores"] is state["scores"]` is `True`: [[the inner dict is shared|shallow-picture]].

**Watch out:** `.copy()` looks like it should protect you, and for a flat list it does. For nested data it copies only the top layer. If you copy something and then a change still leaks through, check with `is` whether the *inner* objects are shared.

### Fix the cause

When you see "changing one thing changed another", find the line where the second name was created, and decide on purpose: should these two share one object, or should one be a copy? Then fix it there.

There is a second rule that prevents many of these bugs. A function should not quietly change data it was handed, unless that is its whole job and its name says so. `place(board, ...)` in the task is allowed to change the board: placing a mark is what it is for. A function called `snapshots` is not allowed to change the state it was given, because the caller does not expect a [[side effect|side-effect]].

::: context reference Names point at objects
A reference is the link from a name to an object in memory. Assignment, `b = a`, copies the reference, never the object. The same happens when you pass a list to a function (the parameter becomes one more name for the caller's list), put it in another list, or store it in a dict. This makes Python fast, since nothing big is copied unless you ask, but it means you must decide when you want a real copy.
:::

::: context immutable Can it change?
Mutable means "can be changed in place": lists, dicts and sets have methods like `append`, `update` and `add` that change the object itself. That is why sharing an immutable object is always safe, and why only immutable things can be dict keys.

You will see `_` in unpacking too, as in `for _, price, _ in items`, which keeps only the middle value of each tuple.

=== py3-10 | Design: composition over inheritance, and the strategy pattern
--- teach
Last lesson you learned to decide on purpose which objects share what, instead of letting it happen by accident. This lesson is about the same kind of decision one level up: how to build a class out of other objects. It is a design lesson, so the code is small, and the ideas are what you keep.

Think of a torch that takes batteries. The torch does not care which brand of battery is inside. Anything that fits the slot and gives power will do, and you can swap one for another without buying a new torch. That is the idea at the heart of this lesson.

### Two ways to get new behavior

Say you have an online shop, and an `Order` class works out the cost of an order. Now you want express shipping too. There are two ways to give a class new behavior.

**Inheritance** says "an `ExpressOrder` *is an* `Order`, with one method changed". You met subclasses in the exceptions lesson, where `TooHeavy` was a kind of `ShippingError`. Here it would look like this:

```python
class ExpressOrder(Order):          # ExpressOrder inherits everything from Order
    def shipping_cost(self):        # ...except this method, which it replaces
        return 9.99
```

Writing a method in the subclass with the same name as one in the parent **[[overrides|override]]** it: the subclass's version is used instead.

**Composition** says "an `Order` *has a* shipping method, and asks it for the cost". The shipping method is a separate object, stored inside the order, like the battery inside the torch.

### Why inheritance multiplies

Inheritance looks natural at first. Then the wishes pile up: express shipping, gift wrap, discounts. Each can be on or off, so every mix needs its own class: `ExpressOrder`, `GiftWrappedOrder`, `ExpressGiftWrappedOrder`, and in the end `ExpressGiftWrappedDiscountedOrder`. That is [[one class for every combination|explosion]].

Worse, an order cannot change its shipping method. An object's class is fixed when it is made. A customer who switches from standard to express would need a whole new object of a different class.

### Composition: plug the part that changes

With composition, each part that varies becomes an object you plug in:

```python
class Order:
    def __init__(self, items, shipping):
        self.items = items
        self.shipping = shipping      # any object with a cost(order) method

    def shipping_cost(self):
        return self.shipping.cost(self)
```

Read the last line slowly, because it has two different objects in it. `self` is the order. `self.shipping` is the shipping object stored inside it. So `self.shipping.cost(self)` means "shipping object, here is me, the order: what do I cost to ship?". The order passes *itself* in, so the shipping object can look at the order's items, subtotal or weight.

Here are two shipping objects. Each has a method `cost`, which takes `self` (the shipping object, as in every method) and `order` (the order that is asking):

```python
class Flat:
    def __init__(self, fee):
        self.fee = fee                # its own setting
    def cost(self, order):
        return self.fee

class Free:
    def cost(self, order):
        return 0

items = [("tea", 4.0, 0.2), ("mug", 9.0, 0.4)]   # (name, price, weight in kg)
o = Order(items, Flat(3.50))
o.shipping_cost()       # 3.5
o.shipping = Free()     # swap the part, keep the same order
o.shipping_cost()       # 0
```

### The strategy pattern

This way of building is called the **strategy pattern**. A **strategy** is one of a family of interchangeable objects that all have the same method, here `cost(order)`. The code that uses it picks one while the program is running, at [[run time|run-time]], and can swap it any time.

`Order` does not know or care which strategy it has. It only calls `.cost(self)`. So adding a new shipping method means writing one new small class, and `Order` does not change at all. The strategy pattern is one of the classic [[design patterns|design-patterns]].

Strategy objects have another strength: they can carry their own settings, like `Flat(3.50)` carries its fee. A chain of `if`s cannot do that neatly. You could make `Flat(2.00)` for one shop and `Flat(5.00)` for another, with no new code.

### When to use which

**Inherit** when the child really *is* a kind of the parent and uses nearly all of it. Python's own `TimeoutError` is a subclass of `OSError`: a timeout really is a kind of operating-system error.

**Compose** when one *part* of the behavior varies, like how shipping is priced.

A useful warning sign, which programmers call a [[code smell|code-smell]]: an `if` / `elif` chain that checks a type name or a mode string, like `if self.shipping == "express":`. When that chain shows up, and especially when it is repeated in several methods, it is asking to become strategy objects.

### Any object with the right method will do

In Python, a strategy does not need to share a parent class with the others. Any object that has a `cost(order)` method works. That is the "if it quacks like a duck" idea you met with `StringIO` in the text-processing lesson, called [[duck typing|duck-typing]]. And when a strategy has only one method and no settings, a plain function often does the job: if `Order` called `self.shipping(self)` instead, you could pass `Order(items, lambda order: 0)`. In the task, though, `Order` calls `.cost(...)`, so each strategy is a small class.

**Watch out:** in a strategy's `cost` method, the order is the parameter `order`, not `self`. When you move code out of `Order` into a strategy, every `self.subtotal()` must become `order.subtotal()`, because inside the strategy `self` is the shipping object, which has no subtotal.

::: context override Replacing a parent's method
When Python looks up a method on an object, it looks in the object's own class first and only then in the parent class. So a method in the subclass with the same name "wins", and the parent's version is never reached for that object. This is called overriding. The subclass can still call the parent's version with `super()`, as your exception classes did with `super().__init__(...)`.
:::

::: context run-time While the program runs
Programmers split a program's life in two. "When you write it" is when the code and its classes are fixed. "Run time" is while the program is running, when choices can depend on what the user clicked or what a sensor read. A subclass is chosen when you write the code. A strategy object can be chosen, and swapped, at run time.
:::

::: context design-patterns Named solutions
A design pattern is a well-known shape of code for a problem that keeps coming back, with a name so people can talk about it. The strategy pattern was one of 23 patterns in the 1994 book *Design Patterns*, by Erich Gamma, Richard Helm, Ralph Johnson and John Vlissides, often called the "Gang of Four". The same book gave the advice in this lesson's title: favor object composition over class inheritance.
:::

::: context code-smell Something smells off
A code smell is not a bug. The code works, but something about its shape hints that it will be painful to change later. The phrase is credited to Kent Beck and was made popular by Martin Fowler's book *Refactoring*. A repeated `if` chain on a mode string is a classic smell: add a new mode and you must hunt down every chain and add a branch to each one, and forgetting one is a bug.
:::

::: context duck-typing Built from parts
Duck typing means Python only checks that an object has the method it calls, not what class it belongs to. That makes composition easy: any part with the right method fits the slot. === py3-11 | Recursion, memoisation and dynamic programming
--- teach
Last lesson you built an `Order` out of small parts that you could swap in and out. That was about how to *organize* code. The last four lessons of this course are about **algorithms**: step-by-step methods for solving a problem, and the choice of method often decides whether a program answers in a blink or never answers at all. The first one is a function that calls itself.

### A problem with a smaller problem inside

Picture a line of friends, each holding some coins, and you want the total. You could say: "the total is my coins plus the total of everyone behind me." The friend behind you says the same thing about the people behind *them*, and so on down the line. The last friend has nobody behind them, so they answer with their own coins and nothing more. Then the answers pass back up the line, each friend adding their own coins, until the total reaches you.

A function that works like this is **recursive**: it solves a problem by calling itself on a smaller version of the same problem. Doing it is called **recursion**. It needs two parts:

- a **base case**: a version of the problem so small that you can answer it directly, with no more calls;
- a **recursive case**: a step that makes the problem smaller and trusts the call to solve the rest.

```python
def total(nums):
    if not nums:                        # base case: the list is empty
        return 0
    return nums[0] + total(nums[1:])    # recursive case: a shorter list

print(total([3, 1, 4]))   # 8
```

Read it line by line. `if not nums:` is true when the list is empty, because an empty list counts as false. An empty list adds up to 0, so that is the base case. Otherwise, `nums[0]` is the first number, and `nums[1:]` is a slice holding every number *after* the first. The function adds the first number to the total of the rest.

Here is what happens for `[3, 1, 4]`. Each call [[waits for the answer|call-stack]] of the one it made:

```python fragment
total([3, 1, 4])
= 3 + total([1, 4])
= 3 + (1 + total([4]))
= 3 + (1 + (4 + total([])))
= 3 + (1 + (4 + 0))
= 8
```

**Watch out:** every recursive call must move closer to the base case. If you forget the base case, or the list never gets shorter, the function calls itself forever. Python stops it at its [[recursion limit|recursion-limit]], about 1000 calls deep, with `RecursionError: maximum recursion depth exceeded`.

### The trap: doing the same work again and again

The **Fibonacci numbers** start 0, 1, and each one after that is the sum of the two before it: 0, 1, 1, 2, 3, 5, 8, 13, and so on. Here is the textbook recursive version:

```python
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

print(fib(10))   # 55
```

The line uses a one-line `if`. Read it as: "give back `n` if `n` is less than 2; otherwise give back `fib(n - 1)` plus `fib(n - 2)`." So `fib(0)` is 0 and `fib(1)` is 1: those are the base cases.

It is correct, but hopeless for big numbers. Look at the [[tree of calls|fib-tree]] that `fib(5)` makes. It asks for `fib(4)` and `fib(3)`. But `fib(4)` *also* asks for `fib(3)`. So `fib(3)` is worked out twice, `fib(2)` three times, and the waste grows with every step up: each `n` makes about 1.6 times as many calls as the one before, not far off doubling. `fib(40)` makes over 300 million calls (331,160,281, to be exact).

### Memoisation: remember each answer

The fix is to remember each answer the first time you work it out, and hand back the remembered answer after that. This is called **[[memoisation|memo-word]]**. You already have the tool: `@lru_cache` from the functools lesson.

```python
from functools import lru_cache

@lru_cache(maxsize=None)
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

print(fib(40))   # 102334155, instantly
```

Now every `fib(k)` is computed once. For `fib(40)` the real work runs only 41 times, once for each `k` from 0 to 40. Every other request is answered from the cache.

### Dynamic programming

That is the heart of **[[dynamic programming|dp-name]]**, or **DP** for short. A **subproblem** is a smaller version of the problem you are solving, like `fib(38)` inside `fib(40)`. When a problem breaks into *overlapping* subproblems, meaning the same smaller questions come up again and again, solve each one once and reuse the answer.

### Top-down and bottom-up

Memoised recursion is called **top-down**: you start from the big question and recurse down towards the small ones. It has a weakness. The recursion limit, about 1000 calls deep, still applies, so the memoised `fib(5000)` crashes with `RecursionError`.

The other way is **bottom-up**: fill a table with a loop, starting from the smallest subproblem and working upwards. No function calls itself, so there is no depth to run out of:

```python
def fib(n):
    table = [0, 1]
    for k in range(2, n + 1):
        table.append(table[k - 1] + table[k - 2])
    return table[n]

print(fib(10))   # 55
```

When `table[k]` is being worked out, `table[k - 1]` and `table[k - 2]` are already there, because the loop filled them first. That ordering is the whole trick of bottom-up DP.

### Worked example: the fewest coins

You have coins worth 1, 3 and 4, as many of each as you like, and you want to make 6 using as few coins as possible.

The method that feels natural is **[[greedy|greedy]]**: always grab the biggest coin that fits. That gives 4, then 1, then 1: three coins. But 3 + 3 makes 6 with *two* coins. Greedy fails. (The starter code for this lesson is exactly that greedy method.)

So think in subproblems instead. The best way to make an amount `a` is *one coin `c`, plus the best way to make what is left, `a - c`*, for whichever coin gives the fewest in total. Written as a recipe (almost Python, but not code to run):

```python fragment
best[0] = 0
best[a] = 1 + min(best[a - c] for each coin c <= a)
```

`best[a]` means "the fewest coins that make amount `a`". Making 0 needs no coins. The `1 +` counts the coin `c` you used, and `c <= a` (said "c is less than or equal to a") skips coins too big to fit.

Fill the table bottom-up, from 0 to 6. Every value you need is already there when you need it:

| a | each coin c that fits: best[a - c] + 1 | best[a] |
| --- | --- | --- |
| 0 | (none needed) | 0 |
| 1 | c=1: 0 + 1 = 1 | 1 |
| 2 | c=1: 1 + 1 = 2 | 2 |
| 3 | c=1: 2 + 1 = 3; c=3: 0 + 1 = 1 | 1 |
| 4 | c=1: 1 + 1 = 2; c=3: 1 + 1 = 2; c=4: 0 + 1 = 1 | 1 |
| 5 | c=1: 1 + 1 = 2; c=3: 2 + 1 = 3; c=4: 1 + 1 = 2 | 2 |
| 6 | c=1: 2 + 1 = 3; c=3: 1 + 1 = 2; c=4: 2 + 1 = 3 | 2 |

The answer is `best[6]`, which is 2: the 3 + 3.

### Starting the table at infinity

Some amounts cannot be made at all. With only 2-coins, you can never make 3. To handle that, start every entry except `best[0]` at **infinity**: `float("inf")`, the same value as `math.inf` from the standard library lesson, a float bigger than every number. Any real count of coins beats it. If an entry is still infinity at the end, no mix of coins reached it, and the answer is `-1`.

```python
amount = 3
best = [0] + [float("inf")] * amount
print(best)   # [0, inf, inf, inf]
```

`[float("inf")] * amount` repeats the one-item list `amount` times, and `+` joins it onto `[0]`.

Now the filling loop, run on coins `[1, 3, 4]` and amount 6. The outer loop goes through the amounts, the inner loop tries every coin, and an entry is replaced whenever a coin gives a smaller count:

```python
coins = [1, 3, 4]
amount = 6
best = [0] + [float("inf")] * amount
for a in range(1, amount + 1):
    for c in coins:
        if c <= a and best[a - c] + 1 < best[a]:
            best[a] = best[a - c] + 1
print(best)   # [0, 1, 2, 1, 1, 2, 2]
```

That is the table above, row by row.

### Counting the ways

A different question about the same coins: *how many* different ways are there to make an amount? Take coins 1 and 2, and amount 3. The ways are 1 + 1 + 1 and 1 + 2. We count 1 + 2 and 2 + 1 as the *same* way, because they use the same coins. A choice where order does not matter is a **combination**, so the answer is 2 combinations.

Keep a list `ways`, where `ways[a]` is the number of combinations that make `a`. There is exactly one way to make 0: use no coins. So `ways` starts as `[1, 0, 0, 0]`.

Here is the twist: to count `1 + 2` and `2 + 1` as one way, **loop over the coins on the outside**. Then each coin is only ever added after the coins before it, so every combination is built in one order only:

```python
coins = [1, 2]
amount = 3
ways = [1] + [0] * amount
for c in coins:
    for a in range(c, amount + 1):
        ways[a] += ways[a - c]
print(ways)   # [1, 1, 2, 2]
```

`+=` means "add to": `ways[a] += ways[a - c]` adds the number of ways to make `a - c` onto `ways[a]`, because each of those ways plus one coin `c` makes `a`. The inner loop starts at `c`, since a coin cannot help make an amount smaller than itself. Step by step:

- After coin 1: `[1, 1, 1, 1]`. Using only 1s, there is one way to make each amount.
- After coin 2: `ways[2]` gains `ways[0]` and becomes 2 (1 + 1, and 2). `ways[3]` gains `ways[1]` and becomes 2 (1 + 1 + 1, and 1 + 2).

**Watch out:** swap the two loops, amounts outside and coins inside, and you get `ways[3] == 3`, because now 1 + 2 and 2 + 1 are [[counted separately|loop-order]]. The code looks almost the same, so this mistake is easy to make and hard to spot.

Both tables take about (amount × number of coins) steps, where × means "times". For an amount of 10,000 and a handful of coins, that is well under a second.

::: context recursion-limit Why there is a limit, and who avoids recursion
Every waiting frame uses memory. Without a limit, a runaway recursion would eat memory until the whole program crashed, so Python stops at a set depth: 1000 by default (`sys.getrecursionlimit()` tells you). It can be raised with `sys.setrecursionlimit`, but a loop is usually the better answer. Safety-critical software is stricter still. NASA's Jet Propulsion Laboratory published coding rules for flight software, "The Power of Ten" by Gerard Holzmann, and rule 1 forbids recursion, because a program that might call itself too deeply is hard to prove safe before launch.
:::

::: context memo-word A memo to yourself
The word comes from "memo", a note you write so you do not have to remember something. The computer scientist Donald Michie named "memo functions" in 1968: functions that keep a note of every answer they have given. British books usually spell it memoisation and American ones memoization; both mean the same thing. It is not "memorisation", although that is a fair way to picture it.
:::

::: context dp-name A name chosen to sound impressive
Richard Bellman worked out dynamic programming at the RAND Corporation in the 1950s. He later wrote that he picked the name partly because it sounded impressive and hard to object to, not because it describes the idea well. "Programming" here means planning, as in a TV programme schedule, not writing code. Bellman's ideas grew into optimal control, the branch of engineering that works out the best way to steer a system, and they still sit underneath methods used to plan rocket and spacecraft trajectories.
:::

::: context greedy Grab the best thing now
A greedy method makes the choice that looks best right now and never goes back to reconsider. It is fast and sometimes perfect: with US coins (1, 5, 10 and 25 cents), taking the biggest coin that fits always gives the fewest coins. But for coins like 1, 3 and 4 it goes wrong, because the best first step depends on what comes after. DP looks at every choice for every smaller amount, so it cannot be fooled that way.
:::

::: context loop-order Why the loop order changes the count
With amounts on the outside, every amount tries every coin as its *last* coin. So 3 can end with a 2 (after making 1, as 1 + 2) or end with a 1 (after making 2, which includes 2 + 1): the two orders become two separate ways. With coins on the outside, the 2-coins are only added after all the 1-coins have been placed, so a combination is only ever built as "all the 1s, then all the 2s". Each combination is counted once. Counting orders has its own use, for example counting the different sequences of steps up a staircase, so neither loop is wrong in general. Only one of them answers this question.
:::

=== py3-12 | Big-O: code that finishes
--- teach
Last lesson, the plain recursive `fib(40)` made over 300 million calls, and the memoised one did the real work 41 times. Same answer, wildly different waiting time. This lesson gives you a way to talk about that difference, and to spot it by reading code, before you run it.

### How the work grows

Picture a party. If every guest shakes hands with every other guest, 10 guests make 45 handshakes, but 1,000 guests make 499,500. If instead every guest waves once, 10 guests make 10 waves and 1,000 guests make 1,000 waves. Both parties get bigger by the same amount, but the work grows in completely different ways.

**Big-O notation** is a short way to write how the work grows as the input grows. The letter `n` stands for the size of the input, such as how many items are in the list. Big-O ignores **constant factors**, meaning fixed multipliers: 3 steps per item and 1 step per item both count as "grows in step with n". What it cares about is the *shape* of the growth. Read O(n) aloud as "O of n", or "[[order n|big-o-name]]".

| Big-O | Name | 1,000 items | 1,000,000 items |
|---|---|---|---|
| O(1) | constant | 1 | 1 |
| O(log n) | logarithmic | 10 | 20 |
| O(n) | linear | 1,000 | 1,000,000 |
| O(n log n) | sorting | 10,000 | 20,000,000 |
| O(n²) | quadratic | 1,000,000 | 1,000,000,000,000 |

Row by row:

- **O(1), constant**: the same work however big the input is, like looking up one key in a dict.
- **O(log n), logarithmic**: the number of times you can [[halve n|logarithm]] before you get down to 1. That grows very slowly: about 10 for a thousand, about 20 for a million.
- **O(n), linear**: a fixed amount of work per item, like one pass of a `for` loop.
- **O(n log n)**: what a good sort, like `sorted()`, costs.
- **O(n²), quadratic**: said "O of n squared" (the small ² means "squared", n times n). Every item paired with every other item, like the handshakes.

Python does, [[very roughly|step-speed]], ten million simple steps a second. So O(n²) on a million items is a million million steps, which is about 100,000 seconds: more than a day. That is not "slow". For any real use, it never finishes.

### Know the cost of what you call

Quadratic code rarely looks like two loops. Usually it is one loop, with a second loop **hidden** inside a single operation. These are the costs to know:

| Operation | list | set / dict |
|---|---|---|
| `x in c` | O(n): checks every item | O(1) [[on average|hash-average]] |
| `c.append(x)` / `c.add(x)` | O(1) | O(1) |
| `c.insert(0, x)`, `c.pop(0)` | O(n) | n/a |
| `sum(c[a:b])` | O(b - a) | n/a |

- `x in c` on a list looks at the items one by one until it finds `x`. On a set or dict it jumps straight to the answer.
- `append` adds to the end of a list, and `add` adds to a set. Both are quick.
- `insert(0, x)` and `pop(0)` work at the *front* of a list, so every other item must shift along one place, as in the deque note of the standard library lesson.
- `sum(c[a:b])` copies the slice from position `a` up to (not including) `b`, then adds each number in it: `b - a` numbers, so O(b - a). "n/a" means "not available": sets have no positions, so there is nothing to insert at or slice.

### A hidden loop in real code

This innocent-looking loop removes duplicates, keeping the first of each:

```python
result = []
for x in items:
    if x not in result:      # hidden loop: checks every item in result
        result.append(x)
```

The `for` runs once per item, n times. Inside it, `x not in result` checks through the list, which can hold up to n items. That is n times n: O(n²).

The fix is to keep a `set` beside the list. The set answers "have I seen this?" instantly, and the list keeps the order, which a set [[does not remember|set-order]]:

```python
items = [3, 1, 3, 2]
seen = set()
for x in items:
    if x not in seen:
        seen.add(x)
        print("first time:", x)
# first time: 3
# first time: 1
# first time: 2
```

Now every step inside the loop is O(1), so the whole loop is O(n).

### Precompute to answer many questions

Suppose you will be asked, over and over, for the sum of `nums[lo:hi]` for different `lo` and `hi`. Summing each slice is O(n) per question. With 200,000 questions about a list of 100,000 numbers, that is billions of steps.

Think of the distance markers along a highway. To know how far it is from marker 40 to marker 75, nobody measures the road again: you subtract, 75 - 40 = 35. The markers are totals worked out once, from the start of the road.

Do the same with numbers. Build **prefix sums** once: `prefix[i]` is the sum of the first `i` numbers. Then any range sum is [[one subtraction|mile-markers]]:

```python
nums   = [3, 1, 4, 1, 5]
prefix = [0, 3, 4, 8, 9, 14]      # prefix[i] = sum(nums[:i])
# sum(nums[1:4]) == prefix[4] - prefix[1] == 9 - 3 == 6
```

Why does that work? `prefix[4]` is the first four numbers, 3 + 1 + 4 + 1. `prefix[1]` is the first one, 3. Take the first away and you are left with 1 + 4 + 1, which is `nums[1:4]`, and that is 6. Notice that `prefix` has one more entry than `nums`, because it starts with the sum of zero numbers, 0.

To build it, start with `[0]` and keep adding the next number to the last total:

```python
nums = [3, 1, 4, 1, 5]
prefix = [0]
for n in nums:
    prefix.append(prefix[-1] + n)
print(prefix)   # [0, 3, 4, 8, 9, 14]
```

`prefix[-1]` is the last item in the list: a negative index counts from the end. Building the table is O(n) once, and after that each question is O(1), instead of O(n) per question.

**Watch out:** the common mistake is testing only on tiny inputs. Everything is fast on ten items, so the O(n²) version passes every small test and then [[freezes on real data|deadlines]]. Always ask: *what happens when this is 100,000?*

::: context big-o-name What the O stands for
The O stands for "order", as in "on the order of a thousand", meaning roughly that size. Mathematicians used the notation for over a century before programmers borrowed it; Paul Bachmann introduced it in 1894. Big-O deliberately drops details: an algorithm that takes 3n + 7 steps is O(n), because for big n the 3 and the 7 hardly matter next to how the n grows. That is why you can compare two methods before measuring either.
:::

A million halves about twenty times. So an O(log n) method barely notices the input growing: double the input and it takes one more step. You will build one of these in the binary search lesson.

::: context step-speed Why only roughly
How many steps a second depends on the computer and on what a "step" is: adding two numbers is quicker than looking up a key in a dict. Ten million a second is a fair rule of thumb for plain Python, and good enough for the question that matters: seconds, hours or years? One million squared is 1,000,000,000,000 steps; at ten million a second that is 100,000 seconds, a little over 27 hours.
:::

::: context hash-average What "on average" means here
A set or dict works out a number from each item, called a hash, and uses it to choose a slot to store the item in. Looking something up means working out the same hash and going straight to that slot. Now and then two different items want the same slot, and then Python has to check a few extra places. That is rare, so the time is the same "on average" however big the set is, even though an unlucky lookup is a little slower.
:::

::: context set-order Sets forget the order
A set only remembers *what* is in it, not the order the items arrived in, so printing a set can show them in any order. That is why the fix keeps both: the set for fast checks, the list for the order. There is another neat way: dicts *do* remember the order keys were added, so `list(dict.fromkeys(items))` also removes duplicates and keeps the first of each. Writing the loop yourself first is how you learn why it works.
:::

=== py3-13 | Problem solving: shortest path on a grid (BFS)
--- teach
Last lesson you learned to ask how the work grows, and to watch for hidden loops like `pop(0)`. This lesson puts that to use on a famous puzzle: "what is the fewest number of moves from here to there?" It comes up in games, maps, mazes, robots and networks. When every move costs the same, the answer is **breadth-first search**, or **BFS**.

### The idea: ripples in a pond

Drop a stone in a still pond. The ripples spread out in rings, and the ring that reaches a leaf first got there by the shortest way.

BFS explores a map the same way, [[in rings|ripple-grid]]. First it visits every square 1 step from the start, then every square 2 steps away, then 3, and so on. The first time it reaches the goal, it got there by a shortest route, because every shorter distance was fully explored before. "Breadth" means width: the search goes wide, ring by ring, before it goes far.

### The grid

A grid is a list of equal-length strings. `#` is a wall and `.` is open floor:

```python
grid = ["S#.",
        ".#.",
        "..E"]
print(grid[2][1])   # .   row 2, column 1
```

`grid[r]` is row `r`, a string, and `grid[r][c]` is the character in column `c` of that row. So a square's position is the pair `(r, c)`, [[row first|row-col]], stored as a tuple. `len(grid)` is the number of rows and `len(grid[0])`, the length of the first row, is the number of columns.

### Finding the start

Before searching, find where `S` is. Two nested loops with `enumerate` visit every square along with its row and column number:

```python
grid = ["S#.", ".#.", "..E"]
for r, row in enumerate(grid):
    for c, ch in enumerate(row):
        if ch == "S":
            print("start", (r, c))
        elif ch == "E":
            print("goal", (r, c))
# start (0, 0)
# goal (2, 2)
```

### The four neighbors

From a square you can move down, up, right or left. Write each move as a change in row and a change in column, `(dr, dc)`:

- `(1, 0)`: one row down;
- `(-1, 0)`: one row up;
- `(0, 1)`: one column right;
- `(0, -1)`: one column left.

```python
r, c = 1, 2
for dr, dc in ((1, 0), (-1, 0), (0, 1), (0, -1)):
    nr, nc = r + dr, c + dc
    print((nr, nc))
# (2, 2)
# (0, 2)
# (1, 3)
# (1, 1)
```

`nr` and `nc` are short for "new row" and "new column". Two of those four are no good in the grid above: `(1, 3)` is off the right edge, and `(1, 1)` is a wall.

### Checking a neighbor before you step there

A neighbor is worth visiting only if it is inside the grid, is not a wall, and has not been seen already:

```python
0 <= nr < rows and 0 <= nc < cols and grid[nr][nc] != "#" and (nr, nc) not in seen
```

- `0 <= nr < rows` is a chained comparison, read "`nr` is at least 0 *and* less than `rows`". It says the row is inside the grid. The same for the column.
- `!=` means "is not equal to", so `grid[nr][nc] != "#"` means "not a wall".
- `(nr, nc) not in seen` means "not visited yet". `seen` is a set, so this check is O(1).

The order matters. Python checks the parts of an `and` from left to right and stops at the first false one, so `grid[nr][nc]` is only read once the bounds are known to be good. That is important, because a negative index does not fail in Python: it quietly [[wraps around|negative-wrap]] to the other side of the grid.

### The queue: first in, first out

To explore in rings, keep the squares waiting to be visited in a **queue**: [[first in, first out|fifo]], like a line at a shop. New squares join at the back; the next square to visit leaves from the front.

Use a `deque` from the standard library lesson. `queue.append(x)` joins the back and `queue.popleft()` takes from the front, both in O(1). A plain list's `pop(0)` would shift every other item along, which is O(n), last lesson's hidden loop.

Each item in the queue is a pair: a square, and how many steps it took to get there, like `((0, 0), 0)`. Taking one out, you can unpack both parts in one line, with brackets that match its shape:

```python
from collections import deque

queue = deque([((0, 0), 0)])
(r, c), dist = queue.popleft()
print(r, c, dist)   # 0 0 0
```

### The whole search

```python
from collections import deque

def steps_to(grid, start, goal):
    rows, cols = len(grid), len(grid[0])
    queue = deque([(start, 0)])
    seen = {start}
    while queue:
        (r, c), dist = queue.popleft()
        if (r, c) == goal:
            return dist
        for dr, dc in ((1, 0), (-1, 0), (0, 1), (0, -1)):
            nr, nc = r + dr, c + dc
            if 0 <= nr < rows and 0 <= nc < cols and grid[nr][nc] != "#" and (nr, nc) not in seen:
                seen.add((nr, nc))
                queue.append(((nr, nc), dist + 1))
    return -1
```

Read it in order. The queue starts holding the start square at distance 0, and `seen` starts holding the start square. `while queue:` keeps going as long as the queue is not empty. Each time round, take the front square. If it is the goal, its distance is the answer. Otherwise, queue every good neighbor at one more step. If the queue runs empty without reaching the goal, the goal cannot be reached, and the answer is `-1`.

On `["S..E"]`, starting at `(0, 0)` with the goal at `(0, 3)`: the queue hands out `(0, 0)` at 0 steps, then `(0, 1)` at 1, then `(0, 2)` at 2, then `(0, 3)` at 3, which is the goal. The answer is 3.

Three details make it correct and fast:

- **`deque.popleft()`, not `list.pop(0)`.** Removing from the front of a list shifts every other item along; a deque does it in O(1).
- **Mark squares as seen when you *add* them to the queue**, not when you take them out. Otherwise the same square can be queued many times, once from each neighbor that finds it.
- **Check the bounds before indexing.** A negative index does not fail in Python; it quietly wraps around to the other side of the grid.

Every square is added to the queue at most once, so BFS is O(rows × cols), where × means "times": the work grows in step with the number of squares.

**Watch out:** the common mistake is using **depth-first search**, DFS, for shortest paths. DFS follows one path as far as it goes before backing up, using recursion or a **stack** (last in, first out). It finds *a* path, not the shortest, and exploring every path to compare them is [[exponential|dfs-paths]]. When every step costs the same, reach for BFS and a queue. When steps cost [[different amounts|weighted-maps]], you need a bigger tool.

::: context row-col Why row comes before column
In a list of strings, you must pick the row (which string) before you can pick the column (which character in it), so `grid[r][c]` puts the row first. That is the opposite of graph paper in maths class, where you write (x, y) with the across-number first. Mixing the two up is one of the most common grid bugs, so pick names that say which is which, like `r` and `c`, never `x` and `y` for a grid.
:::

::: context negative-wrap Index -1 is a real square
In Python, `row[-1]` is the last character of the row, not an error. So from column 0, a step left gives column -1, and without a bounds check `grid[r][-1]` reads the square on the far right edge, as if the grid were wrapped round a tube. The search could then walk "through" the edge of the map and report a route that does not exist. One of this lesson's checks, "does not wrap around the edges", makes sure yours never does. (An index that is too big, like column 3 in a 3-wide row, does fail, with an `IndexError`; only negative ones slip through quietly.)
:::

::: context fifo Queue versus stack
A queue is first in, first out, like a line at a shop: whoever has waited longest is served next. A stack is last in, first out, like a pile of plates: the newest goes on top and comes off first. BFS uses a queue, so every square in ring 1 is visited before any square in ring 2. Swap it for a stack and the search dives down one path instead.

::: context dfs-paths Why trying every path explodes
Exponential means that each extra step multiplies the work, instead of adding to it. A path has a choice at almost every square, so the number of different paths explodes as the grid grows. On a 300 by 300 open grid, like the one the checks use, even the shortest routes from corner to corner number about 10 to the power 178, far more than the atoms in the whole universe (about 10 to the power 80). BFS never compares paths at all: it visits each square once.
:::

::: context weighted-maps When steps cost different amounts
If some moves cost more than others, like climbing a hill versus walking on flat ground, the first route to arrive is no longer always the cheapest. Then engineers use Dijkstra's algorithm, published by Edsger Dijkstra in 1959, which is BFS with a priority queue that always takes the cheapest square next, or A*, created in 1968 for Shakey, an early mobile robot, which also aims the search towards the goal. Path planning for robots and planetary rovers is built on these ideas.
:::

--- solution
from collections import deque


def shortest_path(grid):
    rows, cols = len(grid), len(grid[0])
    start = goal = None
    for r, row in enumerate(grid):
        for c, ch in enumerate(row):
            if ch == "S":
                start = (r, c)
            elif ch == "E":
                goal = (r, c)
    queue = deque([(start, 0)])
    seen = {start}
    while queue:
        (r, c), dist = queue.popleft()
        if (r, c) == goal:
            return dist
        for dr, dc in ((1, 0), (-1, 0), (0, 1), (0, -1)):
            nr, nc = r + dr, c + dc
            if 0 <= nr < rows and 0 <= nc < cols and grid[nr][nc] != "#" and (nr, nc) not in seen:
                seen.add((nr, nc))
                queue.append(((nr, nc), dist + 1))
    return -1

=== py3-14 | Problem solving: binary search
--- teach
Last lesson, BFS searched a grid by spreading out ring by ring. This last lesson is about searching data that is already in order, and doing it astonishingly fast.

### Throw away half every time

Play a game: a friend thinks of a whole number from 1 to 100, and after each guess tells you "higher" or "lower". The smart first guess is 50, because whatever the answer, half the numbers are gone. Then 25 or 75, and so on. You never need more than 7 guesses.

Looking up a word in a paper dictionary works the same way. You do not start at page one. You open it in the middle, see whether your word comes before or after, and throw away half the book. Repeat, and a million pages take about [[twenty looks|halving]].

That method is **binary search**: look at the middle, throw away the half that cannot hold the answer, repeat. ("Binary" means "in two": every step splits the range in two.) It is O(log n), the logarithmic row of last lesson's table, and it only works on data that is **[[sorted|sorted-needed]]**, in order from smallest to largest.

### The most useful question

The version that is most useful in practice does not ask "is `x` here?". It asks "**where is the first position whose value is at least `x`?**" "At least" means "greater than or equal to", written `>=`. One answer to that question does several jobs:

```python
nums = [1, 3, 3, 3, 8]
# first position with a value >= 3 is 1
# first position with a value >= 4 is 4
```

- **Is it there?** If the position is inside the list and holds `x`, then `x` is in the list: `nums[1] == 3`, so 3 is there.
- **Where would it go?** It is the place to insert `x` and keep the list sorted: 4 belongs at position 4, before the 8.
- **How many are there?** The first position at least 4, minus the first position at least 3, is how many 3s there are: 4 - 1 = 3.

### The code

```python
def first_at_least(nums, target):
    lo, hi = 0, len(nums)          # the answer is somewhere in [lo, hi]
    while lo < hi:
        mid = (lo + hi) // 2
        if nums[mid] < target:
            lo = mid + 1           # mid and everything left of it is too small
        else:
            hi = mid               # mid might be the answer; keep it
    return lo
```

Line by line:

- `lo, hi = 0, len(nums)` sets two variables at once: `lo` (low) is 0 and `hi` (high) is the length of the list. The answer is some position from `lo` to `hi`, and the comment writes that range as `[lo, hi]`.
- `while lo < hi:` keeps going while the range still holds more than one possible answer.
- `mid = (lo + hi) // 2` is the middle position. `//` is whole-number division, so the middle is rounded down to a whole number.
- If `nums[mid] < target` (the middle value is less than the target), then `mid` is too small, and so is everything to its left, because the list is sorted. The answer must be to the right: `lo = mid + 1`.
- Otherwise the middle value is at least the target. `mid` itself might be the answer, so keep it in the range: `hi = mid`.
- When `lo == hi`, the range has closed on one position, and that is the answer.

Here it is on `[1, 3, 3, 3, 8]` with target 3:

| lo | hi | mid | nums[mid] | less than 3? | change |
| --- | --- | --- | --- | --- | --- |
| 0 | 5 | 2 | 3 | no | hi = 2 |
| 0 | 2 | 1 | 3 | no | hi = 1 |
| 0 | 1 | 0 | 1 | yes | lo = 1 |
| 1 | 1 | | | | stop: answer 1 |

### The invariant

The whole trick is the **[[invariant|invariant-word]]**: a fact that stays true every time round the loop. Here it is "the answer lies between `lo` and `hi`". Each branch keeps that true while making the range smaller, and the loop ends when `lo == hi`, which is the answer.

If every value is smaller than `target`, the answer is `len(nums)`, one past the end: "insert it at the very end". That is why `hi` starts at `len(nums)` and not at `len(nums) - 1`. Each time round, the range [[shrinks by about half|loop-bound]], so for a million numbers the loop runs about 20 times.

### Binary search on the answer

The same idea works when there is no list at all, only a yes-or-no question whose answer flips once: "no, no, no, yes, yes" or "yes, yes, yes, no, no".

Take this one: "what is the largest whole number `r` with `r * r <= n`?" That is the **integer square root** of `n`, the square root rounded down. The answer is somewhere from 0 to `n`. For a guess `mid`: if `mid * mid <= n`, the answer is at least `mid`, so `lo = mid`; otherwise the answer is below `mid`, so `hi = mid - 1`. Halve until the range closes.

This time you are looking for the *last* value that passes, not the first. That changes one detail: round the middle **up**, with `mid = (lo + hi + 1) // 2`. Why? Say `lo` is 4 and `hi` is 5. Rounding down gives `mid = 4`; if 4 passes, `lo = mid` sets `lo` to 4 again, nothing changes, and the loop runs forever. Rounding up gives `mid = 5`, and either branch shrinks the range.

Here is `n = 17`. The answer should be 4, because 4 × 4 = 16 fits and 5 × 5 = 25 does not:

| lo | hi | mid | mid * mid | at most 17? | change |
| --- | --- | --- | --- | --- | --- |
| 0 | 17 | 9 | 81 | no | hi = 8 |
| 0 | 8 | 4 | 16 | yes | lo = 4 |
| 4 | 8 | 6 | 36 | no | hi = 5 |
| 4 | 5 | 5 | 25 | no | hi = 4 |
| 4 | 4 | | | | stop: answer 4 |

### Why not n ** 0.5?

`**` means "to the power of", and the power 0.5 is the square root. But `n ** 0.5` gives a float, and a float only keeps [[about 16 significant digits|float-digits]]. For big numbers it goes wrong:

```python
n = 10 ** 30 - 1
print(int(n ** 0.5))   # 1000000000000000   wrong: that squared is bigger than n
```

The right answer is 999999999999999. Python whole numbers, though, [[have no size limit|int-size]], so `mid * mid <= n` is exact even for numbers with forty digits. Binary search with whole numbers never rounds anything.

**Watch out:** the common mistakes are loops that never end because you wrote `lo = mid` where you needed `mid + 1` (or forgot to round up); off-by-one answers from mixing up "first at least" with "last below"; and forgetting that the input must be sorted.

The standard library has this built in, in the [[bisect module|bisect-module]]; you will use it in the expert course. Writing it yourself once is how you learn to trust it.

::: context sorted-needed Why it must be sorted
Throwing away the left half is only safe because the list is in order: if the middle value is too small, everything to its left is smaller still. In an unsorted list, the answer could be anywhere, and binary search will confidently give a wrong answer, with no error to warn you. If the data is not sorted, sort it once with `sorted()`, O(n log n), and then every search after that is O(log n).
:::

::: context invariant-word A fact that never changes
"Invariant" means "not varying". It is a promise the loop keeps every time round. To trust a loop, check three things: the invariant is true before the loop starts, each time round keeps it true, and when the loop stops, the invariant tells you the answer. Programmers who write safety-critical code often write invariants down, and test them with `assert` statements, so the program stops loudly the moment a promise is broken.

::: context loop-bound A loop that is sure to end
Every time round, either `lo` goes up or `hi` comes down, and the range roughly halves, so the loop must end, after about log n steps. Flight-software rules care about this a great deal. Rule 2 of NASA JPL's "Power of Ten" coding rules says every loop must have a fixed upper bound on how many times it can run, so nobody has to wonder whether it might spin forever in flight. Binary search is a loop whose limit you can work out in advance.
:::

::: context float-digits Where floats run out of room
A float stores a number in a fixed 64 bits, and the digits get 53 bits' worth of room. That is enough for about 15 to 16 significant digits, and every digit after that is rounded away. `10 ** 30 - 1` is thirty nines; as a float it rounds to the same value as `1e30`, and its square root comes out as `1e15`. That is off by one, which for a square root check is plain wrong.
:::

::: context int-size Numbers that never overflow
In many languages, whole numbers live in a fixed number of bits and break when they grow too big: that is called overflow. In 2006, Joshua Bloch reported that the binary search in Java's standard library had a hidden overflow bug: `(lo + hi) / 2` went wrong once `lo + hi` passed about two billion. Python whole numbers grow as big as they need to, so `(lo + hi) // 2` is always safe in Python.
:::

::: context bisect-module The ready-made version
`bisect` means "cut in two". Its function `bisect_left(nums, x)` gives exactly what your `first_at_least` gives: the first position whose value is at least `x`. `bisect_right` gives the first position whose value is *greater* than `x`, and `insort` puts a value into a sorted list at the right place. Now that you have written the loop yourself, you know what they do inside and why they need sorted input.
:::
