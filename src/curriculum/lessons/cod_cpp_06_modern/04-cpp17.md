Think of the yearly update to the phone in your pocket. Most of the new features are small: a better way to share a photo, a setting that finally lives where you expect it. None of them is a revolution. But a year later you cannot imagine going back, because each small change removed a little daily friction, and a few of them removed a way to make a mistake.

C++17 is that kind of update. The standard came out in 2017, on the **[[three-year schedule|three-year-train]]** the language has kept since C++11. It added no single giant idea the way C++11 added move semantics or C++20 would add concepts. What it added was a long list of tools that make ordinary code shorter and harder to get wrong.

It also matters for a practical reason. Flight software moves slowly, and many flight teams treat C++17 as the newest standard their certified compilers and coding rules fully cover. So the features in this lesson are the modern C++ you are most likely to meet on a real vehicle today.

You have already met most of them. Structured bindings and `std::optional` came up in the STL module, lesson 05. `std::string_view` was lesson 04 there, and parallel algorithms were lesson 09. `if constexpr` and fold expressions were in the templates module, lessons 07 and 03. So this lesson does not teach them from zero. It lays them out as one map, says *why* each exists, names the traps, and says which ones flight code uses. Two new pieces get full treatment: the `if`-with-initializer, and **CTAD**, which lets a class work out its own template arguments.

## Structured bindings: name the parts at once

A function hands you back a pair, a tuple or a small struct. Before C++17 you took it apart one piece at a time: `.first`, `.second`, `std::get<0>`, `std::get<1>`. Every one of those is a chance to grab the wrong piece.

A **structured binding** declares several names at once, one for each part of an object:

```cpp
const auto [value, t_ms] = reading;     // read: "const auto, value and t_ms, from reading"
```

It works on three kinds of thing:

- a plain array, where each name gets one element;
- a **tuple-like** type — `std::pair`, `std::tuple`, `std::array` — where each name gets one `get<i>`;
- a struct or class whose data members are all public, where the names follow the members **in declaration order**.

The number of names must match the number of parts exactly. Two names for a three-member struct is a compile error, which is a good thing.

Here is what really happens. The compiler makes one **[[hidden object|hidden-object]]** from the expression on the right, and each name becomes another name for one part of it. The `auto` in front says how that hidden object is made:

- `auto [a, b] = r;` makes the hidden object a copy of `r`. Changing `a` changes the copy, not `r`.
- `auto& [a, b] = r;` makes the hidden object a reference to `r`. Now writing `a = 2.5` writes into `r` itself.
- `const auto& [a, b] = r;` looks at `r` without copying and without allowing changes. For a big struct, this is the one to reach for.

::: warning The names follow the order, not the meaning
`auto [max, min] = std::minmax(a, b);` compiles without a word, and gives you the minimum in a variable called `max`. Bindings match by position. The compiler has no idea what your names mean. Read the order off the type (or the struct's member list) every time, and prefer a struct with well-named members over a bare tuple for anything that crosses an interface.
:::

## `if` and `switch` with an initializer

Here is a pattern you will see in every codebase older than 2017:

```cpp
auto it = channels.find(id);
if (it != channels.end()) {
    use(it->second);
}
// ... forty lines later ...
it->second.value = 0.0;    // compiles; if the find failed, this is undefined behaviour
```

The variable `it` was made only to be checked. But it lives on after the check, all the way to the end of the function. Forty lines later someone uses it again, forgetting that it may be `end()`.

C++17 lets the `if` itself hold the declaration:

```cpp
if (auto it = channels.find(id); it != channels.end()) {
    use(it->second);
} else {
    log_missing(id);                 // it is visible here too
}
// it does not exist here: any use is a compile error
```

Read `if (init; condition)` as "if, after doing *init*, the *condition* holds". The part before the semicolon is an **init statement**. Whatever it declares is in scope for the condition, the `if` branch and the `else` branch, and nowhere else. The idea is the same one `for (int i = 0; ...)` has always used: a name should live exactly as long as it is useful.

`switch` gets the same form:

```cpp
switch (const auto status = imu.read_status(); status.mode) {
    case Mode::Nominal:  run_filter(status); break;
    case Mode::Degraded: run_coast(status);  break;
    default:             safe_hold();        break;
}
```

Put these two features together with `std::optional` and a whole family of error-handling code shrinks. That family has a name worth knowing: the **[[sentinel value|sentinel]]** pattern, where a function signals "no answer" by returning a special number such as $-999$ that could be mistaken for data.

::: key Three C++17 features that reduce bug risk, and how
`std::optional` removes the sentinel-value and uninitialised-out-parameter pattern; structured bindings remove index and `get<>` mistakes; if-init scopes a result to the branch that checks it, so it cannot be misused afterwards.
:::

::: example Removing a sentinel, an out-parameter and a stray iterator
A ground station keeps the latest reading of each telemetry channel. The old lookup function returns a `bool` and writes through a pointer. The new one returns `std::optional<Reading>`, and the caller uses if-init and a structured binding.

```cpp
#include <cstdint>
#include <cstdio>
#include <map>
#include <optional>

struct Reading {
    double value;
    std::uint32_t t_ms;
};

const std::map<int, Reading> latest{
    {7, {68.4, 120'000}},    // chamber pressure, bar
    {9, {-182.6, 120'004}},  // LOX tank temperature, deg C
};

// Old shape: a bool, an out-parameter, and a sentinel for "no data".
bool lookup_old(int id, double* out_value) {
    std::map<int, Reading>::const_iterator it = latest.find(id);
    if (it == latest.end()) { *out_value = -999.0; return false; }
    *out_value = it->second.value;
    return true;
}

// New shape: the answer is either a Reading or nothing.
std::optional<Reading> lookup(int id) {
    if (auto it = latest.find(id); it != latest.end()) return it->second;
    return std::nullopt;
}

int main() {
    double v;
    lookup_old(8, &v);                         // return value ignored
    std::printf("old: channel 8 = %.1f\n", v); // prints the sentinel as data

    for (int id : {7, 8, 9}) {
        if (const auto r = lookup(id); r) {
            const auto [value, t_ms] = *r;
            std::printf("new: channel %d = %.1f at t = %u ms\n", id, value, t_ms);
        } else {
            std::printf("new: channel %d has no data\n", id);
        }
        // r and value do not exist here: the compiler stops any use of them.
    }
}
```

Compiled with `g++ -std=c++20 -Wall -Wextra -O2`, with no warnings, it prints:

```text
old: channel 8 = -999.0
new: channel 7 = 68.4 at t = 120000 ms
new: channel 8 has no data
new: channel 9 = -182.6 at t = 120004 ms
```

Walk through it.

1. **The old call.** Channel 8 does not exist. `lookup_old` returns `false`, but the caller never looks. Then it prints $-999.0$ as if it were a real pressure. Nothing in the language objected.
2. **The new function.** `lookup` returns `std::optional<Reading>`. There is no out-parameter to forget, no pointer that could be null, and no half-written output: either the whole `Reading` comes back, or `std::nullopt` does.
3. **The if-init.** `const auto r = lookup(id); r` makes `r` and then tests it. An empty optional converts to `false`. Inside the branch, `*r` is safe because the test has passed.
4. **The binding.** `const auto [value, t_ms] = *r;` names both members, in the order `Reading` declares them.
5. **The scope.** After the `if`/`else`, the names `r`, `value` and `t_ms` are gone.

Sanity check: channels 7 and 9 exist in the map and print their values; channel 8 does not and says so. The old function printed a number for a channel that has no data. That is the bug class that disappeared.
:::

The old function has one more cheap fix, also from C++17: the **[[attribute|nodiscard]]** `[[nodiscard]]`. Write `[[nodiscard]] bool lookup_old(...)` and the ignored call above draws a warning from g++: "ignoring return value of 'bool lookup_old(int, double*)', declared with attribute 'nodiscard' [-Wunused-result]". Many flight projects put `[[nodiscard]]` on every function that returns a status.

## The vocabulary types: optional, variant, any

C++17 added three types that say something about a value's *shape*. You met them in the STL module (lesson 05) and in the RAII module (lesson 12).

- **`std::optional<T>`**: a `T`, or nothing. The `T` is stored inside the optional itself, next to a flag, so there is no heap allocation. On this machine `sizeof(std::optional<double>)` is 16: 8 bytes of `double` and a flag, padded.
- **`std::variant<A, B, C>`**: exactly one of a fixed list of types, with `std::visit` to handle each case. Also stored in place, no allocation. It is the safe replacement for a C `union` with a separate tag.
- **`std::any`**: any type at all, decided at run time. To hold anything, it must be able to allocate: libstdc++ stores a value inside the `any` only if it fits in one pointer's worth of space, and anything bigger goes on the heap. Asking an `any` which type it holds, with `.type()`, needs **[[run-time type information|rtti]]**; with `-fno-rtti`, g++ reports "'class std::any' has no member named 'type'".

The rule of thumb for flight code: `optional` and `variant` are welcome, because they are fixed-size and checked by the compiler. `any` is rare, because both its allocation and its run-time typing are the kind of thing flight rules forbid. If you know the list of possible types, you want a `variant`.

## `string_view`, and why `std::string` stays out of the fast loop

`std::string_view` is a pointer and a length that look at characters someone else owns. The STL module's lesson 04 covered it with its sibling `std::span`, including the **dangling-view** trap: a view of a temporary string points at freed memory the moment the statement ends.

What it adds here is a reason. `std::string` owns its characters, and to own an unknown number of them it sometimes allocates. Most libraries keep short strings inside the string object itself, in a **[[small-string buffer|sso]]**, and allocate only when the text is longer. On g++ 13 with libstdc++, a 15-character string needs no allocation and a 16-character one needs one. Another library, LLVM's libc++, keeps up to 22 characters on a 64-bit machine. The standard sets no number at all.

::: key Why std::string is usually banned in a hard real-time path
It allocates once the content exceeds its small-string buffer, and the threshold is implementation-defined. Fixed-capacity character buffers, or `string_view` over static storage, give the same capability with bounded behaviour.
:::

So a flight task names its modes and channels with `std::string_view` constants over **static storage** — text baked into the program image, such as a string literal — or with a fixed `std::array<char, 32>` buffer. Both have a size known before launch.

## Compile-time tools: `if constexpr` and fold expressions

Two C++17 features work entirely inside the compiler. You met both in the templates module.

**`if constexpr`** (templates lesson 07) is an `if` whose condition is decided while compiling. The branch not taken is thrown away and never compiled for that type. That is how one template can print a float one way and an integer another. It is also how a flight codebase selects code for one processor or another with no run-time test at all.

A **fold expression** (templates lesson 03) applies one operator across a whole parameter pack. `(xs + ... + 0)` — read "xs, plus dot dot dot, plus zero" — adds every argument, and gives $0$ when there are none. `(put(f), ...)` calls `put` on each argument in order: the **comma fold**.

Here are both at once, in a tiny telemetry logger:

```cpp
#include <cstdio>
#include <type_traits>

template <class T>
void put(const T& x) {
    if constexpr (std::is_floating_point_v<T>) std::printf("%.4f ", static_cast<double>(x));
    else if constexpr (std::is_integral_v<T>)  std::printf("%lld ", static_cast<long long>(x));
    else                                       std::printf("%s ", x);
}

template <class... Fields>
void log_frame(const Fields&... f) {
    (put(f), ...);          // a comma fold: put each field, left to right
    std::printf("\n");
}

template <class... Ts>
constexpr auto sum(Ts... xs) { return (xs + ... + 0); }

int main() {
    log_frame("GYRO", 3, 0.0125, -2.5f);
    static_assert(sum(1, 2, 3) == 6);
    std::printf("%d\n", sum());
}
```

It prints `GYRO 3 0.0125 -2.5000` and then `0`. The string took the last branch, the `3` the integer branch, and both floating-point values the first. The `static_assert` passed while compiling, so `sum` never ran for it at all. Neither feature costs anything at run time, which is why flight code uses both freely.

## CTAD: let the constructor name the type

A function template works out its `T` from the arguments you pass. Before C++17, a class template could not, so the library grew helper functions whose only job was deduction: `std::make_pair(1, 2.5)` existed so you did not have to write `std::pair<int, double>`. The templates module (lesson 01) introduced the fix.

**Class template argument deduction**, or **CTAD**, lets you write `std::pair p{1, 2.0};` and the compiler deduces `std::pair<int, double>` from the constructor arguments. It looks at the class's constructors as if each were a function template, deduces from the arguments, and uses the result.

Sometimes the constructors alone would deduce the wrong thing, or nothing. Then the class author writes a **[[deduction guide|deduction-guide]]**, a one-line rule of the form "when constructed from these argument types, the class is this":

```cpp
Label(const char*) -> Label<std::string>;   // read: "a Label made from a const char* is a Label of string"
```

::: key CTAD: what it is and what to watch for
Class template argument deduction lets you write `std::pair p{1, 2.0}` without spelling out the types. Watch for deduction that picks a surprising type, especially with initializer lists and with types that decay, which is why library authors write deduction guides.
:::

::: example Seven deductions, two of them surprising
```cpp
#include <array>
#include <cstdio>
#include <string>
#include <type_traits>
#include <utility>
#include <vector>

template <class T>
struct Label {
    T text;
    Label(T t) : text(t) {}
};
Label(const char*) -> Label<std::string>;   // the deduction guide

int main() {
    std::pair p{1, 2.0};
    std::pair q{"LOX", 3};
    std::array a{1.0, 2.0, 3.0};
    std::vector v{10, 20, 30};
    std::vector w{v};                  // one argument: a vector
    std::vector x{v.begin(), v.end()}; // two arguments in braces: iterators
    std::vector y(v.begin(), v.end()); // the same two in parentheses
    Label l{"ENGINE_1"};

    using It = std::vector<int>::iterator;
    std::printf("p is pair<int, double>        %d\n", std::is_same_v<decltype(p), std::pair<int, double>>);
    std::printf("q is pair<const char*, int>   %d\n", std::is_same_v<decltype(q), std::pair<const char*, int>>);
    std::printf("a is array<double, 3>         %d\n", std::is_same_v<decltype(a), std::array<double, 3>>);
    std::printf("w is vector<int>              %d  (%zu elements)\n", std::is_same_v<decltype(w), std::vector<int>>, w.size());
    std::printf("x is vector<iterator>         %d  (%zu elements)\n", std::is_same_v<decltype(x), std::vector<It>>, x.size());
    std::printf("y is vector<int>              %d  (%zu elements)\n", std::is_same_v<decltype(y), std::vector<int>>, y.size());
    std::printf("l is Label<std::string>       %d\n", std::is_same_v<decltype(l), Label<std::string>>);
}
```

Output, identical with g++ 13 and clang++ 18 (a `1` means "yes, that is the type"):

```text
p is pair<int, double>        1
q is pair<const char*, int>   1
a is array<double, 3>         1
w is vector<int>              1  (3 elements)
x is vector<iterator>         1  (2 elements)
y is vector<int>              1  (3 elements)
l is Label<std::string>       1
```

Line by line:

1. **`p`**: `1` is an `int`, `2.0` a `double`. No surprise.
2. **`q`**: `"LOX"` is an array of four `const char`, but `pair`'s constructor takes its arguments by value, and an array passed by value **decays** to a pointer to its first element. So the pair holds a `const char*`, not a string. If the literal's storage were not static, this would dangle.
3. **`a`**: CTAD counts the elements for you: `std::array<double, 3>`.
4. **`w`**: one vector inside braces. You might fear a vector *of* vectors, but the rules prefer copying, so `w` is a plain copy of `v`.
5. **`x`**: the first surprise. Braces prefer the initializer-list constructor (lesson 02's gotcha), so the two iterators became the two *elements*. `x` is a vector of 2 iterators.
6. **`y`**: parentheses select the range constructor, so `y` holds the 3 ints.
7. **`l`**: without the guide, `Label{"ENGINE_1"}` would deduce `Label<const char*>`. (Delete the guide and that line prints `0`.) With it, the label owns a `std::string` of 8 characters.

Sanity check: every line printed `1`, so each type is what the comments claim, and the element counts (3, 2, 3) match the explanation.
:::

::: warning Braces plus iterators
`std::vector x{first, last}` never means "copy this range". With CTAD it makes a vector of two iterators, and with an explicit `std::vector<int>` it is usually a compile error. Use parentheses for ranges. This is the same initializer_list preference from lesson 02, now wearing a disguise.
:::

In flight code, CTAD is fine for local variables where the deduced type is plain to see, like `std::array a{1.0, 2.0, 3.0}`. In an interface, spell the type out. A reviewer should not have to run the deduction rules in their head to know what a function takes.

## The rest of the list

**`std::filesystem`** (header `<filesystem>`) gives paths, directory listings, file sizes and copies, portably. It grew out of the **[[Boost library|boost]]** of the same name. It belongs in ground tools, and in the housekeeping code of vehicles whose computers run Linux, such as the task that rotates log files. It does not belong in a control loop: a `path` is a string that allocates, and every call touches the operating system. Most functions come in two forms, one that throws `std::filesystem::filesystem_error` and one that takes a `std::error_code&` and reports failure through it. In a build with exceptions turned off, use the `error_code` form.

**Parallel algorithms** add an execution policy as the first argument, as in `std::sort(std::execution::par, v.begin(), v.end())`. The STL module's lesson 09 covered what each policy permits, the promise you make about data races, and the fact that libstdc++ needs Intel's TBB library to run anything in parallel. They are for ground tools and big offline analyses, not for a 1 kHz task, where the thread start-up alone would blow the timing budget.

**Guaranteed copy elision** changed what `return T{...};` means. Since C++17 the returned object is built directly in the caller's storage, with no copy or move at all, even for a type that cannot be copied or moved. It deserves a whole lesson, and it gets one: the next.

A few smaller C++17 additions you will see in flight code: `[[maybe_unused]]` and `[[fallthrough]]` (attributes that silence a warning on purpose), `inline` variables (a constant defined once in a header), nested namespaces (`namespace gnc::nav { }`), and `std::clamp(x, lo, hi)`, which limits an actuator command to its range.

## Check yourself

::: check
Rewrite this fragment so that `it` cannot be used after the check, and say what bug the rewrite prevents.

```cpp
auto it = gains.find(axis);
if (it != gains.end()) apply(it->second);
```
:::

::: answer
Move the declaration into the `if`:

```cpp
if (auto it = gains.find(axis); it != gains.end()) apply(it->second);
```

Now `it` exists only in the condition and the branches. The bug it prevents is a later use of `it` in the same function when the lookup failed: dereferencing `end()` is undefined behaviour, and in the old form it compiles without complaint. In the new form, any later use of `it` is a compile error ("'it' was not declared in this scope").
:::

::: check
`struct Att { double roll, pitch, yaw; };` and `Att a{0.1, 0.2, 0.3};`. What does each of these do to `a.pitch`?

```cpp
auto  [r1, p1, y1] = a;  p1 = 9.0;
auto& [r2, p2, y2] = a;  p2 = 5.0;
```
:::

::: answer
The first makes a hidden **copy** of `a` and names its parts, so `p1 = 9.0` changes the copy; `a.pitch` stays $0.2$. The second makes the hidden object a **reference** to `a`, so `p2` is another name for `a.pitch`, and `p2 = 5.0` sets `a.pitch` to $5.0$. In both cases the names follow declaration order: roll, pitch, yaw.
:::

::: check
A mode table stores names as `std::string`. The longest name is `"GUIDANCE_TERMINAL_DESCENT"`, 25 characters. On g++ 13, does building that string allocate? Would it on a library with a 22-character buffer? What would you use instead in a 1 kHz task?
:::

::: answer
Yes on both: 25 is more than libstdc++'s 15 characters and more than 22. The deeper problem is that the threshold is implementation-defined, so even a shorter name might allocate on another toolchain. In the task, store the names as `std::string_view` constants over string literals (static storage, no allocation, no ownership) or in a fixed `std::array<char, 32>` buffer. Either way the size is known before launch.
:::

::: check
What types do these deduce, and which one should you change?

```cpp
std::pair t{"TANK_P", 2.5f};
std::vector samples{raw.begin(), raw.end()};   // raw is a std::vector<double>
```
:::

::: answer
`t` is `std::pair<const char*, float>`: the string literal decays to a pointer, and `2.5f` is a `float`, not a `double`. `samples` is a `std::vector` of two `std::vector<double>::iterator`s, because braces prefer the initializer-list constructor. Change the second one to parentheses, `std::vector samples(raw.begin(), raw.end());`, which deduces `std::vector<double>` and copies the data. For the first, if you want to own the text, write `std::pair<std::string, double>` in full, or add a deduction guide to your own type.
:::

::: check
Your team's ground tool deletes old log files with `std::filesystem::remove(p)`. The tool is being moved into a build with `-fno-exceptions`. What must change, and why?
:::

::: answer
The one-argument `remove(p)` reports failure (say, permission denied) by throwing `std::filesystem::filesystem_error`. With exceptions off, a throw cannot be caught; it ends the program. Use the overload that takes an error code: `std::error_code ec; std::filesystem::remove(p, ec); if (ec) log_failure(ec);`. The failure becomes an ordinary value you check, like the `std::optional` in this lesson's first example.
:::

## Summary

| Idea | Meaning | Rule or fact |
|---|---|---|
| Structured binding | several names for the parts of one object | `auto`/`auto&`/`const auto&` decides copy or reference; order is declaration order |
| if/switch init | `if (init; cond)` | the name lives only in the condition and both branches |
| `std::optional<T>` | a `T` or nothing | stored in place; replaces sentinels and out-parameters |
| `std::variant`, `std::any` | one of a list; anything | variant is fixed-size; any may allocate and uses RTTI |
| `std::string_view` | non-owning text view | beware dangling; `std::string` allocates past an implementation-defined size |
| `if constexpr`, folds | compile-time branch; one operator over a pack | zero run-time cost |
| CTAD | class deduces its template arguments | watch decay and brace lists; deduction guides fix it |
| `std::filesystem` | portable files and paths | ground tools; use the `error_code` overloads without exceptions |
| Parallel algorithms | execution policies | permission, not a promise; needs TBB with libstdc++ |
| Guaranteed copy elision | `return T{...};` builds in the caller | next lesson |

Next lesson takes the last line of that table and opens it up: what "guaranteed copy elision" really guarantees, what it does not (named return values), and how to count every copy and move when you return a 1 MB state array.

`const auto [value, t_ms] = *r;` does not make two new variables. It makes one unnamed object, here a copy of `*r`, and `value` and `t_ms` become names for its two members. With `auto&` the unnamed object would be a reference to `*r` itself, so writing through a name would change the original.

::: context sentinel A value that means "not a value"
A sentinel is an ordinary-looking number given a special meaning: $-1$ for "not found", $-999$ for "no reading", $0$ for "not set". The trouble is that the type cannot tell the special number from a real one. A pressure of $-999$ bar is physically impossible, so a human might notice, but code that averages readings will happily include it. An `std::optional` keeps "no value" outside the set of numbers entirely.
:::

::: context nodiscard Attributes in double brackets
An attribute is a note to the compiler written in double square brackets, such as `[[nodiscard]]` or `[[fallthrough]]`. It does not change what correct code does. It changes what the compiler warns about. `[[nodiscard]]` on a function means "a caller that throws this result away is probably wrong". C++17 added it, and C++20 let you add a reason: `[[nodiscard("check the status")]]`.
:::

::: context rtti Run-time type information
RTTI is the extra data the compiler stores so a program can ask, while running, what type an object really is: `typeid`, `dynamic_cast`, and `std::any::type()` all use it. It costs space in the program image for every class that needs it. Many flight builds turn it off with `-fno-rtti`; lesson 09 of this module explains why, alongside turning off exceptions.
:::

::: context sso Where a short string keeps its letters

::: context deduction-guide Why the arrow
A deduction guide borrows the look of a function declaration with a **trailing return type**, `auto f(int) -> double`, which C++11 introduced. Read `Label(const char*) -> Label<std::string>;` as a pretend function: "called with a `const char*`, it produces a `Label<std::string>`". The compiler never calls it. It only uses it to choose the template arguments, then runs the real constructor.
:::

::: context boost Where std::filesystem came from
Boost is a large, free collection of C++ libraries, peer-reviewed and widely used since the late 1990s. Several of its libraries became standard ones after years of real use: smart pointers, `std::optional`, `std::variant`, `std::any` and `std::filesystem` all have Boost ancestors. When a new standard feature looks strangely polished for something brand new, Boost is often why.
:::
