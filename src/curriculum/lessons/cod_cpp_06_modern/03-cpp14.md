When a family moves house, the big truck carries the beds, the sofa and a hundred boxes. A week later, somebody drives back for what got left behind: the can opener, the shower curtain, the phone charger. That second trip is small, and it is the one that makes the new house livable.

**C++14** was that second trip. C++11 was enormous and had rough edges: lambdas that could not take "any type", functions whose return type you had to spell out even when the compiler knew it, a `make_shared` with no `make_unique` beside it, and `constexpr` functions limited to one `return` statement. C++14 fixed those, added a few small conveniences, and changed almost nothing else. It is the **[[smallest of the modern standards|minor-release]]**, and one of the most widely used: a great deal of embedded and safety-critical C++ is written to it today.

Last lesson finished C++11 with brace initialisation. This one covers C++14's four headline features, then its small additions that make register-level flight code easier to read. You met several already, in the STL module's lambdas lesson and the memory module's smart-pointer lesson, so this lesson keeps those parts short and spends its time on the why and the gotchas.

## Generic lambdas

A C++11 lambda had to name the type of every parameter. Sorting a vector of pairs meant writing the pair type out in full, twice:

```cpp
[](const std::pair<std::uint16_t, double>& a, const std::pair<std::uint16_t, double>& b) { ... }
```

A **generic lambda**, new in C++14, writes `auto` instead: `[](const auto& a, const auto& b) { return a.first < b.first; }`. Read `[](auto x)` as "a lambda taking `x` of any type". The STL module (lesson 10) showed what happens underneath: the closure's `operator()` becomes a **[[template|generic-picture]]**, and the compiler writes a separate version for each argument type the lambda is called with.

Two consequences follow, and both matter for flight code.

- **No run-time cost.** Each version is an ordinary function chosen while compiling. There is no dynamic typing and no dispatch.
- **Code size grows with the number of types.** Call a generic lambda with `int`, `float` and `double` and you get three copies of its body in the binary. On a processor with a small flash memory, that can matter.

## Init-capture

C++11 lambdas could capture a variable only by copy or by reference. There was no way to *move* something into a lambda, so a lambda could not own a `std::unique_ptr`. The usual workaround was a `std::shared_ptr`, paying for a heap control block and atomic counting only because a lambda could not accept a move.

C++14's **init-capture** creates a new member of the closure and says how to initialise it: `[buf = std::move(data)]`, read "capture a new member `buf`, initialised by moving from `data`". The right-hand side can be any expression, evaluated once when the lambda is created. You met it in the STL module's lambdas lesson, together with its everyday uses such as `[n = samples.size()]`. The example after the `make_unique` section below puts it to work.

## Return type deduction: auto and decltype(auto)

In C++11 a lambda with a single `return` could deduce its return type, but an ordinary function could not. The nearest thing was the **trailing return type**, `auto scale(T a, U b) -> decltype(a * b)`, read "auto scale, returning the type of a times b", which still made you write the type as an expression.

C++14 lets any function say `auto` and let the body decide:

```cpp
auto fact(int n) {                 // first return fixes the type: int
    if (n <= 1) return 1;
    return n * fact(n - 1);        // recursion is fine after that
}
```

The rules are few and strict.

1. **Every `return` must deduce the same type.** `if (kn < 0.0) return 0; return kn;` fails, because `0` is an `int` and `kn` is a `double`. g++ says `inconsistent deduction for auto return type: 'int' and then 'double'`. Write `return 0.0;`.
2. **The compiler must see the body before the call.** A caller in another file cannot use `auto f();` from a header unless the definition is in the header too, because the return type lives in the body. This pushes code into headers, which **[[costs build time|header-bodies]]**.
3. **Recursion needs a `return` first.** `fact` above works because the first `return 1;` fixes the type before the recursive call. Write it as one line, `return n <= 1 ? 1 : n * fact(n - 1);`, and g++ reports `use of 'auto fact(int)' before deduction of 'auto'`.
4. **Plain `auto` deduces the way `auto x = expr;` does:** references and top-level `const` are dropped. An `auto` function returns a value, never a reference.

That fourth rule is usually what you want. When it is not, C++14 has **`decltype(auto)`**, read "decl-type auto". It deduces the type using the rules of `decltype`, which keep references exactly as the returned expression has them.

::: example auto against decltype(auto)
A telemetry table has two accessors. One should hand back a copy of a channel; the other should let a caller write into it.

```cpp
#include <array>
#include <cstdio>
#include <type_traits>

struct Telemetry {
    std::array<double, 4> channel{};

    auto           get_copy(int i) { return channel[i]; }  // auto: drops the reference
    decltype(auto) get_ref(int i)  { return channel[i]; }  // decltype(auto): keeps it
};

int main() {
    Telemetry t;
    static_assert(std::is_same<decltype(t.get_copy(0)), double>::value, "a copy");
    static_assert(std::is_same<decltype(t.get_ref(0)), double&>::value, "a reference");

    double c = t.get_copy(0);
    c = 5.0;                 // changes the local copy only
    t.get_ref(1) = 7.0;      // writes through the reference into channel[1]
    std::printf("channel[0] = %.1f, channel[1] = %.1f, c = %.1f\n", t.channel[0], t.channel[1], c);
}
```

Built with `g++ -std=c++14 -Wall -Wextra -O2`, it prints:

```text
channel[0] = 0.0, channel[1] = 7.0, c = 5.0
```

Step by step:

1. `channel[i]` on a `std::array<double, 4>` returns `double&`, a reference to the element.
2. `get_copy` uses plain `auto`, which drops the `&`, so it returns a `double`. The first `static_assert` proves it while compiling.
3. `get_ref` uses `decltype(auto)`, which keeps the `&`, so it returns `double&`. The second `static_assert` proves that.
4. Writing `c = 5.0` changes only the local copy, so `channel[0]` stays `0.0` (the `{}` zeroed the array). Writing through `get_ref(1)` reaches into the object, so `channel[1]` becomes `7.0`.

Sanity check: try `t.get_copy(0) = 5.0;` and g++ refuses with `lvalue required as left operand of assignment`. A returned `double` is a temporary, not a place in memory, so there is nothing to assign to.
:::

::: warning Parentheses change what decltype(auto) returns
`decltype` has **[[two rules|decltype-rules]]**: for a plain name it gives the declared type; for any other expression, including a name in parentheses, it gives a reference if the expression refers to an object. So:

```cpp
decltype(auto) last_reading() {
    double x = 101.3;
    return (x);          // parentheses: decltype((x)) is double&
}
```

returns a `double&` to a local that dies at the closing brace. g++ warns `reference to local variable 'x' returned [-Wreturn-local-addr]`. Without the parentheses it would return a `double`. Use `decltype(auto)` only in forwarding code, where "return exactly what the inner call returned" is the point, and never put a returned name in parentheses.
:::

For flight code the advice is conservative. `auto` return types are fine for short local helpers and for templates, where the type genuinely depends on the arguments. On a public interface — a function other teams call — write the type out. A reviewer reading `double read_chamber_kpa();` knows the contract; one reading `auto read_chamber_kpa();` has to go and find the body.

::: key Return type deduction (C++14)
`auto f()` deduces the return type from the body; all returns must agree; the body must be visible to the caller; plain `auto` strips references and top-level `const`. `decltype(auto)` keeps the exact type of the returned expression, references included, and `return (x);` then returns a reference.
:::

## make_unique, at last

C++11 gave you `std::make_shared<T>(args...)` but no `std::make_unique`. You had to write `std::unique_ptr<Imu> p(new Imu(3, 400.0));`, with a naked `new` in the middle of your code — as the tour program in lesson 1 did. **[[It was an oversight|make-unique-oversight]]**, and so many projects filled the gap themselves that the few lines below appear, under one name or another, in a great many C++11 codebases:

```cpp
namespace legacy {
template <typename T, typename... Args>
std::unique_ptr<T> make_unique(Args&&... args) {
    return std::unique_ptr<T>(new T(std::forward<Args>(args)...));
}
}
```

It uses the **variadic templates** and **perfect forwarding** you met in the templates module (lesson 3): `Args&&... args` accepts any arguments, and `std::forward` passes each one on as it came. C++14 put the real `std::make_unique` into `<memory>`. When you modernise a legacy file, replacing a home-made `make_unique` with the standard one is an easy first change.

Why was it worth adding, when the explicit form works? The memory module's smart-pointer lesson gave three reasons: it names the type once, it keeps `new` out of application code, and it closes an **exception-safety** hole. Here is that hole, because it was the strongest argument at the time.

Consider a call with two arguments, `send(std::unique_ptr<Packet>(new Packet), make_header())`. Before C++17, the compiler was allowed to **[[interleave the argument work|interleaving]]**: run `new Packet`, then call `make_header()`, and only then build the `unique_ptr`. If `make_header()` threw an exception in the middle, the `Packet` was already allocated but not yet owned by anything, so nothing freed it. A leak, from a line that looked perfectly safe. `send(std::make_unique<Packet>(), make_header())` cannot leak, because the `new` and the ownership happen together inside one function call that finishes before anything else starts.

C++17 changed the evaluation rules so that one argument is completed before another begins, which closes the hole even for the explicit form. `make_unique` is still the right habit: it never depended on the reader knowing which standard they are on, and flight coding rules that ban naked `new` are easier to check when there is none.

One more detail: `std::make_unique<double[]>(n)` makes an array of `n` doubles, all set to zero. (C++20 added `std::make_unique_for_overwrite` for the case where you will fill the array yourself and do not want to pay for the zeroing.)

::: example make_unique, init-capture and a generic lambda together
```cpp
#include <cstdio>
#include <memory>
#include <utility>

struct Buffer {
    explicit Buffer(int n) : size(n) { std::printf("Buffer(%d) acquired\n", n); }
    ~Buffer() { std::printf("Buffer(%d) released\n", size); }
    int size;
};

int main() {
    auto buf = std::make_unique<Buffer>(256);            // make_unique: C++14

    auto scaled = [b = std::move(buf)](auto factor) {    // init-capture + generic lambda
        return b->size * factor;
    };

    std::printf("buf is %s\n", buf ? "still set" : "empty");
    std::printf("scaled(2)   = %d\n", scaled(2));        // int version
    std::printf("scaled(0.5) = %.1f\n", scaled(0.5));    // double version
    std::printf("leaving main\n");
}
```

Built with `g++ -std=c++14 -Wall -Wextra -pedantic -O2`, it prints:

```text
Buffer(256) acquired
buf is empty
scaled(2)   = 512
scaled(0.5) = 128.0
leaving main
Buffer(256) released
```

Follow the ownership.

1. `make_unique` allocates one `Buffer` of 256 and hands it to `buf`.
2. The init-capture `b = std::move(buf)` moves the pointer into the closure. `buf` is now null, which the third line confirms: `empty`.
3. `scaled(2)` calls the `int` version of the template call operator: $256 \times 2 = 512$, an `int`. `scaled(0.5)` calls a second, `double` version: $256 \times 0.5 = 128.0$.
4. When `main` ends, the closure is destroyed, its `b` member is destroyed, and the `Buffer` is released — after `leaving main`, not before. RAII, carried inside a lambda.

Sanity check: one "acquired" and one "released", so exactly one owner at every moment. Compile the same file with `-std=c++11` and g++ fails at the first C++14 feature, with `'make_unique' is not a member of 'std'`, then complains about `auto` in a lambda parameter.
:::

## Variable templates

A class can be a template and a function can be a template. C++14 lets a **variable** be one too:

```cpp
template <typename T>
constexpr T pi_v = T(3.141592653589793238462643383279502884L);
```

Read `pi_v<float>` as "pi, as a float". This declares a whole family of constants, one per type, each computed while compiling. `pi_v<float>` is $\pi$ rounded to a `float`; `pi_v<double>` is $\pi$ rounded to a `double`. Before C++14 you had to write a class template with a static member, or a function template `pi<T>()`, to get the same effect.

Why care about the type? Because mixing types silently costs you. On a flight processor whose floating-point unit only handles single precision in hardware, `angle * 3.141592653589793` promotes the whole expression to `double`, and every `double` operation then runs in slow software emulation. `angle * pi_v<float>` stays in `float`. A variable template gives each type the constant in its own precision, with no casts at the call site.

You have used the most common variable templates already: the type-trait helpers like `std::is_same_v<A, B>` from the templates module (lesson 5). Those `_v` names were added in C++17, but the language feature that makes them possible is C++14's. C++20 finally put $\pi$ itself in the **[[standard library|numbers-header]]**.

::: key Variable templates
A variable template, `template <typename T> constexpr T pi_v = T(...);`, is a family of variables, one per type. `pi_v<float>` and `pi_v<double>` are separate constants, each in its own precision. The standard `_v` trait helpers are variable templates.
:::

## Relaxed constexpr

Lesson 1 showed C++11's limit: a `constexpr` function body was essentially one `return` statement, so any loop had to become recursion. C++14 relaxed that. A `constexpr` function may now have local variables, `if` and `switch`, `for` and `while` loops, several `return` statements, and it may change its own local variables. What it still may not do (in C++14) includes `goto`, `try` blocks, `static` local variables and calls to non-`constexpr` functions.

Here is the difference, with a factorial written as a loop:

```cpp
constexpr unsigned long long factorial_loop(unsigned n) {
    unsigned long long r = 1;
    for (unsigned i = 2; i <= n; ++i) r *= i;
    return r;
}
static_assert(factorial_loop(10) == 3628800ULL, "10! is 3628800");
```

With `-std=c++14` it compiles. With `-std=c++11 -pedantic`, g++ 13 stops with `body of 'constexpr' function ... not a return-statement`, and clang 18 with `statement not allowed in constexpr function`. The recursive version from lesson 1 still works in both; C++14 made the loop version legal too.

This is the change that made compile-time tables practical. A CRC table, a sine lookup table or a gain schedule can be built by an ordinary-looking loop, checked with `static_assert`, and stored in read-only memory, with no start-up code at all. The templates module (lesson 7) built exactly such a table, using the still-more-relaxed rules of C++20.

(Also: a C++11 `constexpr` member function was implicitly `const`; since C++14 you write `const` yourself.)

## Binary literals and digit separators

Flight software talks to hardware through **registers**: bytes and words where each bit means something. A status byte from a star tracker might use bit 7 for "solution valid" and bits 0 to 3 for "number of stars locked". C++11 made you write those masks in hexadecimal, `0x80` and `0x0F`, and translate to bits in your head.

C++14 added **binary literals**, with the prefix `0b`: `0b10000000`. It also added the **digit separator**, a single quote you may put between any digits to group them: `0b1000'0000`, `86'400'000`, `0x0000'FFFF`. The compiler ignores the separators completely; they are for the human reading the code. It is a quote, not a comma or underscore, **[[for a reason|separator-choice]]**.

::: example A star-tracker status byte, and a table computed while compiling
```cpp
#include <chrono>
#include <cstdint>
#include <cstdio>

template <typename T>
constexpr T pi_v = T(3.141592653589793238462643383279502884L);   // a variable template

// Status byte from a star tracker (bit 7 = valid, bits 3-0 = stars locked)
constexpr std::uint8_t kValidMask = 0b1000'0000;
constexpr std::uint8_t kStarsMask = 0b0000'1111;

constexpr int count_bits(std::uint32_t v) {      // C++14: loops and locals allowed
    int n = 0;
    while (v != 0) { n += static_cast<int>(v & 1u); v >>= 1; }
    return n;
}
static_assert(count_bits(0b1011'0110) == 5, "five bits set");

int main() {
    using namespace std::chrono_literals;

    std::printf("pi_v<float>  = %.10f\n", static_cast<double>(pi_v<float>));
    std::printf("pi_v<double> = %.10f\n", pi_v<double>);

    std::uint8_t status = 0b1000'0111;
    std::printf("valid=%d stars=%d\n", (status & kValidMask) != 0, status & kStarsMask);

    constexpr long kSamplesPerDay = 86'400'000;           // 1 kHz for 24 h
    std::printf("samples per day = %ld\n", kSamplesPerDay);

    auto period = 1ms;                                    // std::chrono::milliseconds
    std::printf("period = %lld us\n",
        static_cast<long long>(std::chrono::duration_cast<std::chrono::microseconds>(period).count()));
}
```

Built with `g++ -std=c++14 -Wall -Wextra -pedantic -O2`, it prints:

```text
pi_v<float>  = 3.1415927410
pi_v<double> = 3.1415926536
valid=1 stars=7
samples per day = 86400000
period = 1000 us
```

Line by line:

1. The two $\pi$ values differ from the eighth digit on. A `float` keeps about 7 significant decimal digits, so `pi_v<float>` is off from the true $\pi$ by about $8.74 \times 10^{-8}$, a relative error of about $2.8 \times 10^{-8}$. The `double` is right to all ten printed places.
2. The status byte `0b1000'0111` has bit 7 set, so `status & kValidMask` is nonzero: valid. Its low four bits are `0111`, which is $4 + 2 + 1 = 7$ stars.
3. `count_bits` uses a local variable and a `while` loop, both new in C++14 `constexpr`. The `static_assert` checks it while compiling: `1011'0110` has five ones.
4. $1000\,\mathrm{samples/s} \times 86400\,\mathrm{s} = 86{,}400{,}000$ samples per day, and the separators make the size readable at a glance.
5. `1ms` is a **[[chrono literal|chrono-literals]]**, another C++14 addition, and converts to 1,000 microseconds.

Sanity check: every printed value can be checked by hand in a minute, and every constant was fixed while compiling: no start-up work, no heap.
:::

## The rest of C++14, and what flight code keeps

A few smaller additions are worth recognising when you see them:

- `std::exchange(obj, new_value)` sets `obj` and returns its old value in one step; it makes move constructors shorter.
- The `[[deprecated]]` attribute marks a function or type as on its way out, and the compiler warns wherever it is used.
- The `std::chrono` literals (`1ms`, `250us`, `2s`) and the `std::string` literal `"text"s`.
- Aggregates may have default member initialisers, from last lesson.

For a flight team, C++14 is an easy yes. Almost everything in it is decided while compiling: generic lambdas become ordinary functions, `auto` return types are fixed at build time, variable templates and relaxed `constexpr` produce constants, and binary literals and separators vanish entirely. `make_unique` still allocates, so it lives in initialisation code, not in the control loop. This is one reason a whole safety standard, the **[[AUTOSAR C++14 guidelines|autosar-cpp14]]**, was written around this exact version.

## Check yourself

::: check
Rewrite this C++11 lambda as a C++14 generic lambda, and say how many versions of its call operator the compiler generates for the two calls shown.

`auto mag2 = [](double x, double y) { return x * x + y * y; };` then `mag2(3, 4)` and `mag2(0.5f, 1.5f)`.
:::

::: answer
`auto mag2 = [](auto x, auto y) { return x * x + y * y; };`

The call operator is now a template with two independent type parameters. `mag2(3, 4)` stamps out an `(int, int)` version returning `int` $25$. `mag2(0.5f, 1.5f)` stamps out a `(float, float)` version returning `float` $0.25 + 2.25 = 2.5$. Two versions, both chosen while compiling. (With the original C++11 lambda, both calls would have converted to `double` and used one function.)
:::

::: check
Why does this fail to compile, and what is the smallest fix?

```cpp
auto safe_div(double a, double b) {
    if (b == 0.0) return 0;
    return a / b;
}
```
:::

::: answer
The two `return` statements deduce different types: `0` is an `int`, and `a / b` is a `double`. An `auto` function needs every return to deduce the same type, and g++ reports `inconsistent deduction for auto return type: 'int' and then 'double'`. The smallest fix is `return 0.0;`. Alternatively, write the return type out: `double safe_div(double a, double b)`, which converts the `0` for you and is clearer on an interface anyway.
:::

::: check
A teammate writes `decltype(auto) front(std::vector<int>& v) { return v[0]; }` and a second function `decltype(auto) count() { int n = 4; return (n); }`. What does each return, and which one is a bug?
:::

::: answer
`v[0]` is an expression that refers to an element, and `vector<int>::operator[]` returns `int&`, so `front` returns `int&`, a reference into the caller's vector. That is fine and is the point of `decltype(auto)`: `front(v) = 9;` changes the vector.

In `count`, `(n)` is a parenthesised name, so `decltype((n))` is `int&`, and the function returns a reference to the local `n`, which is destroyed at the closing brace. Any use of the result is undefined behaviour; g++ warns `reference to local variable 'n' returned`. Remove the parentheses (then it returns `int`) or use plain `auto`.
:::

::: check
Before C++17, how could `log_packet(std::unique_ptr<Packet>(new Packet), stamp())` leak, and why can `log_packet(std::make_unique<Packet>(), stamp())` never leak?
:::

::: answer
The compiler was allowed to evaluate the pieces of different arguments in any interleaved order. One legal order was: run `new Packet` (the object now exists on the heap), then call `stamp()`, then construct the `unique_ptr`. If `stamp()` threw, the exception left the call before any `unique_ptr` owned the `Packet`, so nothing ever deleted it.

With `make_unique`, the allocation and the taking of ownership both happen inside one function call. A function call runs to completion before other argument work resumes, so by the time `stamp()` can run, the `Packet` is already owned, and if `stamp()` throws, the `unique_ptr` temporary is destroyed and frees it. C++17's rule that one argument finishes before another starts closes the hole for the explicit form too.
:::

::: check
Write a variable template `deg2rad_v` that gives the factor $\pi / 180$ in any floating-point type, and a C++14 `constexpr` function that counts how many entries a sine table needs for a given step in degrees over $0$ to $360$, inclusive of both ends. Check it for a step of 5 degrees.
:::

::: answer
```cpp
template <typename T>
constexpr T deg2rad_v = T(3.141592653589793238462643383279502884L) / T(180);

constexpr int table_entries(int step_deg) {
    int n = 0;
    for (int a = 0; a <= 360; a += step_deg) ++n;   // a loop: legal since C++14
    return n;
}
static_assert(table_entries(5) == 73, "0, 5, ..., 360");
```

The angles are $0, 5, 10, \dots, 360$: that is $\frac{360}{5} + 1 = 73$ entries, counting both ends. In C++11 the loop would be rejected; it would have to be written as recursion or as the formula `360 / step_deg + 1`. `deg2rad_v<float>` and `deg2rad_v<double>` are then separate constants, each rounded in its own type, so a single-precision control law never silently promotes to `double`.
:::

## Summary

| Idea | Meaning | Rule or fact |
| --- | --- | --- |
| C++14 | the small release that completed C++11 | almost all compile-time; widely used in safety-critical code |
| generic lambda | `[](auto x) { ... }` | call operator is a template; one version per argument type |
| init-capture | `[b = std::move(buf)]` | moves a move-only object into the closure |
| `auto` return | type deduced from the body | all returns agree; body must be visible; strips references |
| `decltype(auto)` | keeps the exact returned type | `return (x);` returns a reference |
| `std::make_unique` | missing in C++11, added in C++14 | no naked `new`; no leak from interleaved arguments before C++17 |
| variable template | `pi_v<T>` | a constant per type, each in its own precision |
| relaxed `constexpr` | locals, loops, `if`, several returns | compile-time tables written as ordinary loops |
| `0b` and `'` | binary literals, digit separators | `0b1000'0000`; separators are ignored by the compiler |

Next lesson is C++17, a much bigger step: structured bindings, `if` with an initialiser, `std::optional` and `std::variant`, `string_view`, and the rule that makes returning big objects free.

::: context minor-release A small standard on purpose
After the long wait for C++11, the committee planned C++14 as a minor release that completed and corrected C++11, with the next major revision to follow in 2017. That plan held, and it set the pattern since: every three years a standard ships with whatever is ready. For teams, a small standard is good news. Compilers supported C++14 fully within a year or two of its publication, and upgrading from C++11 rarely breaks anything.
:::

::: context header-bodies Why the body has to travel with the name
A normal function can be declared in a header and defined in one `.cpp` file, because its declaration already states the return type; the linker joins the call to the body later. An `auto` function's return type is not known until the compiler has read the body. So every file that calls it must see the body, which means putting it in the header, where every including file recompiles it. The templates module's lesson on build cost covers the same trade-off for templates.
:::

::: context decltype-rules The two faces of decltype
`decltype(x)` with a bare variable name reports how `x` was declared: `double x;` gives `double`. Any other expression is judged by its **value category**: an lvalue expression gives `T&`, an expiring value (such as `std::move(x)`) gives `T&&`, and a pure temporary gives `T`. The parenthesised `(x)` is no longer a bare name; it is an expression that names an object, an lvalue, so `decltype((x))` is `double&`. One pair of parentheses, a different type.
:::

::: context make-unique-oversight How a helper got left out
Herb Sutter, then the convener of the C++ committee, wrote in his "Guru of the Week" column that C++11's lack of `make_unique` was partly an oversight. The function is only a few lines long, and `make_shared` had arrived in the same standard, so the gap was noticed quickly. Stephan T. Lavavej proposed adding it, and it went into C++14.
:::

::: context numbers-header Pi in the standard library
C++20 added the header `<numbers>`, with `std::numbers::pi` (a `double`) and `std::numbers::pi_v<T>` for any floating-point type, plus `e`, `sqrt2`, `ln2`, `phi` and a few more. They are variable templates, exactly like the one in this lesson. Before C++20, code relied on `M_PI`, a macro many C libraries provide but the C++ standard never required, which is why portable flight code often defined its own constants.
:::

::: context separator-choice Why a quote mark
A comma already means something inside an expression, so `1,000` could not work. An underscore, as Python and Rust use, would clash with user-defined literal suffixes, which in your own code must begin with an underscore: `0x1_ab` could then be read two ways. The single quote had no meaning in the middle of a number, so it was free. It looks odd for a week and then reads naturally.
:::

::: context chrono-literals Units written into numbers
With `using namespace std::chrono_literals;` in scope, `1ms`, `250us`, `2s` and `10min` are durations with their units attached. They make scheduling code say what it means: `next_wake += 1ms;` cannot be mistaken for one second. The STL module's clock lesson used them throughout, and they are one of the least controversial C++14 features in flight code, since they cost nothing at run time.
:::

::: context autosar-cpp14 A rulebook named after a standard
The AUTOSAR consortium, from the automotive industry, published its "Guidelines for the use of the C++14 language in critical and safety-related systems" in 2017. Aerospace teams often borrowed it, because the older JSF and MISRA C++:2008 rules predate modern C++. MISRA C++:2023, which targets C++17, later absorbed much of AUTOSAR's work. The real-time module compares these standards in detail.
:::
