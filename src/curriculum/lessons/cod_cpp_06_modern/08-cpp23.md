Think of the seats in a theater. Your ticket says "row C, seat 7". But the box office computer does not store a grid. It stores one long list of seats, numbered from the first seat of row A to the last seat of the back row. To find your seat it does one small sum: skip two full rows, then count seven more. The grid lives in your head and on the ticket. The memory is one straight line.

Keep that picture. It is one of three tools C++23 added that matter to flight software, and the lesson is organised around them:

- **`std::expected`**, the value-or-error box you met in the STL module's error-handling lesson, now with more ways to chain steps;
- **`std::mdspan`**, the theater's trick in code: a grid-shaped view onto a flat buffer;
- **`std::print`**, a type-safe replacement for `printf`.

**C++23** is the standard the committee [[finished in 2023|cpp23-timeline]]. It is smaller than C++20 — more a tidy-up than a revolution — and, as lesson 07 found for modules, compilers and libraries arrive at it at different speeds. So every section here says honestly what g++ 13, the compiler installed for this course, does and does not ship.

## What g++ 13 actually has

Every C++23 feature is either **language** (the compiler understands new syntax) or **library** (a new header or class in the standard library). g++ 13 comes with its own library, **libstdc++ 13**. The clang 18 installed here uses that same library, because no other is installed. Built with `-std=c++23`:

| Feature | g++ 13 | clang 18 with libstdc++ 13 |
| --- | --- | --- |
| `std::expected` | yes | no — the header comes out empty |
| `std::mdspan` | no header | no header |
| `std::print`, `std::println` | no header | no header |
| `std::generator` (lesson 07) | no header | no header |
| deducing `this` | no | yes |
| `m[i, j]` with two indices | yes | yes |
| `std::to_underlying`, `std::byteswap`, `std::unreachable` | yes | yes |

Why is clang missing `std::expected` with a library that has it? libstdc++ 13's `<expected>` checks that the compiler reports full C++20 concepts support, and clang 18 reports a slightly older level, so the header's contents are switched off and `std::expected` is an undeclared name. It is a small, real example of the [[support matrix|support-matrix]] problem: a feature is usable only when your compiler *and* your library *and* your flags all agree.

::: key
Before using a C++23 feature, check it against your exact compiler and standard library, not the standard. On g++ 13: `std::expected` yes (with `-std=c++23`); `std::mdspan`, `std::print` and `std::generator` no.
:::

## std::expected, grown up

The STL module's error-handling lesson built the basics. As a reminder, **`std::expected<T, E>`**, read "expected T, or error E", from `<expected>`, holds either a value of type `T` or an error of type `E`, in its own storage with no heap. `return x;` stores a value, `return std::unexpected(e);` stores an error, `if (r)` asks which one, `*r` reads the value and `r.error()` the error, and `r.and_then(f)` runs the next step that can fail, passing an error straight through.

That lesson's point was the flight point: the error is part of the function's type, so the caller cannot miss that a failure is possible, and nothing is thrown.

::: key
`std::expected` returns either a value or an error in one object, giving exception-free error propagation with the error type in the signature. It is the C++23 form of the pattern flight code has hand-rolled for decades.
:::

`and_then` is one of four **[[monadic operations|monadic]]** — member functions that each take a function and apply it to one side of the box. Here are all four, sorted by which side they touch and what the function must return:

| Call | Runs `f` when `r` holds… | `f` must return | Use it for |
| --- | --- | --- | --- |
| `r.and_then(f)` | a value | an `expected` | a next step that can fail |
| `r.transform(f)` | a value | a plain value | a next step that cannot fail |
| `r.or_else(f)` | an error | an `expected` | recovering from the error |
| `r.transform_error(f)` | an error | a plain error | converting the error to another type |

And one more for the end of a chain: `r.value_or(d)`, read "value or d", gives the value if there is one and the default `d` if not. It never throws and never aborts.

::: example A pressure reading with a backup sensor
A chamber pressure transducer reports a raw 12-bit count, 0 to 4,095, where 4,095 means 1,000 kPa. Reading it can fail two ways. Converting counts to kilopascals cannot fail. If the primary sensor fails, the program reads the backup instead.

```cpp
#include <cstdint>
#include <cstdio>
#include <expected>

enum class SensorError { no_reply, out_of_range };

const char* name(SensorError e) {
    return e == SensorError::no_reply ? "no_reply" : "out_of_range";
}

// Step 1: ask a pressure transducer for its raw 12-bit count (0 to 4095).
// Negative "raw" values stand in for a sensor that did not answer.
std::expected<std::uint16_t, SensorError> read_counts(int raw) {
    if (raw < 0) return std::unexpected(SensorError::no_reply);
    if (raw > 4095) return std::unexpected(SensorError::out_of_range);
    return static_cast<std::uint16_t>(raw);
}

// Step 2 (cannot fail): counts to pressure in kPa, 0 to 1000 kPa full scale.
double to_kpa(std::uint16_t counts) { return counts * (1000.0 / 4095.0); }

// Recovery: if the primary failed, try the backup sensor instead.
std::expected<double, SensorError> backup(SensorError why) {
    std::printf("    primary failed (%s), using backup\n", name(why));
    return read_counts(2048).transform(to_kpa);
}

int main() {
    const int tests[] = {1638, -1, 5000};
    for (int raw : tests) {
        std::printf("raw %d:\n", raw);
        std::expected<double, SensorError> p =
            read_counts(raw).transform(to_kpa).or_else(backup);
        if (p) std::printf("    pressure %.1f kPa\n", *p);
    }

    // transform_error changes the error type; value_or gives a safe default.
    std::expected<double, int> coded =
        read_counts(-1).transform(to_kpa).transform_error(
            [](SensorError e) { return 100 + static_cast<int>(e); });
    std::printf("fault code %d, fallback %.1f kPa\n",
                coded.error(), coded.value_or(0.0));
}
```

Built with `g++ -std=c++23 -Wall -Wextra -O2 -fno-exceptions`:

```text
raw 1638:
    pressure 400.0 kPa
raw -1:
    primary failed (no_reply), using backup
    pressure 500.1 kPa
raw 5000:
    primary failed (out_of_range), using backup
    pressure 500.1 kPa
fault code 100, fallback 0.0 kPa
```

Follow `read_counts(raw).transform(to_kpa).or_else(backup)`, read "read counts, transform to kPa, or else backup", for each input:

1. `1638` is in range, so `read_counts` holds the value 1638. `transform` sees a value, calls `to_kpa`, and wraps the plain `double` it returns back into an `expected`. `or_else` sees a value and does nothing.
2. `-1` fails in step 1 with `no_reply`. `transform` sees an error and passes it through without calling `to_kpa`. `or_else` sees an error, so it calls `backup`, which reads 2,048 counts from the other sensor.
3. `5000` fails with `out_of_range`, and follows the same road as `-1`.

In the last part, `transform_error` turns the `SensorError` into an `int` fault code for telemetry: `no_reply` is enumerator 0, so the code is $100 + 0 = 100$. `value_or(0.0)` returns the default because there is no value.

Sanity check the numbers: $1638 \times 1000 / 4095 = 400.0$, and $1638$ is $40\%$ of $4095$, so 40% of full scale. $2048 \times 1000/4095 \approx 500.12$, a hair over half — right, since 2,048 is a hair over half of 4,095. The whole program was built with `-fno-exceptions`, and nothing needed a `catch`.
:::

::: warning
`and_then` and `transform` are easy to swap. If you write `.and_then(to_kpa)`, where `to_kpa` returns a plain `double`, g++ 13 stops with `static assertion failed: the function passed to std::expected<T, E>::and_then must return a std::expected`. The rule: the function for `and_then` can fail, so it returns an `expected`; the function for `transform` cannot, so it returns a plain value. The same pairing holds for `or_else` and `transform_error`. And `or_else`'s function must return an `expected` with the same value type — `backup` returns `std::expected<double, SensorError>` because the chain holds a `double` by then.
:::

## std::mdspan: a grid laid over a line

Back to the theater. A 3-by-3 **matrix** — nine numbers in three rows and three columns, like a rotation matrix — is stored in a flight computer the same way the seats are: nine `double`s in one flat, preallocated buffer. The grid is how you think about it. The line is how memory holds it.

To find row $r$, column $c$ in a buffer stored row after row, skip $r$ whole rows of 3 and step $c$ more:

$$
\text{index}(r, c) = 3r + c.
$$

Row 1, column 2 is at index $3 \cdot 1 + 2 = 5$. Storing row after row is called **row-major** order. Storing column after column instead is **[[column-major|column-major]]** order, where the index is $r + 3c$.

**`std::mdspan`** (C++23, header `<mdspan>`), read "M-D span", for multidimensional span, is that sum packaged as a type. It is a **non-owning multidimensional view**: it holds a pointer to your buffer plus the shape, and turns `m[r, c]` into the right element. It never allocates, never copies and never frees. You met its one-dimensional cousin, `std::span`, in the STL module: a pointer plus a length. `mdspan` is a pointer plus a shape plus a rule for turning indices into an offset. That rule is the **layout**: `std::layout_right` is row-major and the default; `std::layout_left` is column-major; `std::layout_stride` allows any fixed step in each direction.

The shape is given by **extents**, and each extent can be fixed at compile time or given at run time. Fixed extents cost no storage at all.

::: key
`std::mdspan` is a non-owning multidimensional view over contiguous storage with configurable layout. It lets you treat a preallocated buffer as a matrix or a tensor without copying or owning it, which is precisely the flight-code access pattern.
:::

Here is how it is written. **libstdc++ 13 has no `<mdspan>`**, so this fragment could not be compiled here; it follows the standard's interface and needs a newer library (check the compiler support tables before relying on it):

```cpp
#include <array>
#include <cstddef>
#include <mdspan>

std::array<double, 9> buffer{};   // storage you own, e.g. static

// Shape fixed at compile time: 3 by 3, row-major (layout_right) by default.
std::mdspan<double, std::extents<std::size_t, 3, 3>> R(buffer.data());

// Or let the constructor deduce the type from run-time sizes.
std::mdspan M(buffer.data(), 3, 3);

void set_corner() {
    R[2, 2] = 1.0;                       // writes buffer[8]
    // R.extent(0) == 3 rows, R.extent(1) == 3 columns, R.rank() == 2
}
```

The `R[2, 2]` with two indices inside one pair of brackets is itself new in C++23: a **multidimensional subscript operator**, `operator[]` taking more than one argument. Before C++23, `a[2, 2]` meant something else entirely, so matrix libraries used `m(2, 2)` instead. Unlike `<mdspan>`, this language feature *is* in g++ 13, so you can build a tiny stand-in to see the idea run.

::: example A 3-by-3 view over a flat buffer
This `Mat3View` is a hand-made, fixed-size, row-major version of what `std::mdspan<double, std::extents<std::size_t, 3, 3>>` does.

```cpp
#include <array>
#include <cstddef>
#include <cstdio>

// A tiny, hand-made stand-in for std::mdspan<double, 3x3>: it owns nothing,
// it only remembers where the numbers are and how to find row r, column c.
class Mat3View {
public:
    explicit Mat3View(double* data) : data_(data) {}
    double& operator[](std::size_t r, std::size_t c) const {   // C++23: two indices
        return data_[r * 3 + c];                                // row-major layout
    }
private:
    double* data_;
};

int main() {
    // Nine numbers in one flat, preallocated buffer: a rotation of 90 degrees
    // about the z axis, stored row after row.
    std::array<double, 9> buffer = {0, -1, 0,
                                    1,  0, 0,
                                    0,  0, 1};
    Mat3View R(buffer.data());

    const double v[3] = {1.0, 2.0, 3.0};   // a vector in the body frame
    double out[3] = {};
    for (std::size_t r = 0; r < 3; ++r)
        for (std::size_t c = 0; c < 3; ++c)
            out[r] += R[r, c] * v[c];

    std::printf("R*v = (%.1f, %.1f, %.1f)\n", out[0], out[1], out[2]);

    R[2, 2] = 5.0;                       // writes through the view...
    std::printf("buffer[8] = %.1f\n", buffer[8]);   // ...into the buffer
    std::printf("sizeof(Mat3View) = %zu bytes\n", sizeof(Mat3View));
}
```

Built with `g++ -std=c++23 -Wall -Wextra -O2`:

```text
R*v = (-2.0, 1.0, 3.0)
buffer[8] = 5.0
sizeof(Mat3View) = 8 bytes
```

Step by step:

1. The buffer holds the matrix row by row: row 0 is $(0, -1, 0)$, row 1 is $(1, 0, 0)$, row 2 is $(0, 0, 1)$. That is a quarter turn about the $z$ axis.
2. Each output component is one row times the vector. Row 0: $0 \cdot 1 + (-1) \cdot 2 + 0 \cdot 3 = -2$. Row 1: $1 \cdot 1 + 0 + 0 = 1$. Row 2: $0 + 0 + 1 \cdot 3 = 3$.
3. `R[2, 2] = 5.0` goes to index $3 \cdot 2 + 2 = 8$, and printing `buffer[8]` shows 5.0: the view wrote into memory it does not own.
4. The view is 8 bytes — one pointer. The shape lives in the code, as it would with `mdspan`'s compile-time extents.

Sanity check: turning the $x$ axis a quarter turn about $z$ should give the $y$ axis, and $y$ should go to $-x$. The input $(1, 2, 3)$ is 1 of $x$ and 2 of $y$, so the result should be 1 of $y$ and 2 of $-x$, with $z$ unchanged: $(-2, 1, 3)$. It is.
:::

Why does GNC care? A Kalman filter's covariance, a guidance law's gain matrix, a 3-D table of aerodynamic coefficients: all are grids, and flight code stores all of them in buffers allocated once at start-up. `mdspan` gives each buffer a matrix-shaped face without a copy, an allocation or an owner — the same buffer can be read as $6 \times 6$ by one routine and passed as flat telemetry by another.

::: warning
A view does not keep its buffer alive. If the `std::array` goes out of scope while an `mdspan` (or `Mat3View`) still points at it, every access through the view is undefined behavior — exactly like a dangling `std::span` or `std::string_view`. Keep views no longer-lived than their storage; in flight code, point them at static buffers.
:::

## std::print: printf without the traps

`printf` has served C and C++ for fifty years, and it has one famous trap: the format string and the arguments are checked by nobody but you. Pass a `double` where the string says `%d` and the result is undefined behavior. g++ does check literal format strings with `-Wformat`, which `-Wall` turns on, but not strings built at run time. `std::cout << x` is type-safe but wordy, and awkward for column layout.

Lesson 06 introduced C++20's **`std::format`** from `<format>`: `{}` placeholders, filled by type-checked arguments, with specs like `{:.1f}` for one decimal. It returns a `std::string`. C++23's **`std::print(fmt, args...)`**, from `<print>`, formats the same way and writes straight to the standard output; **`std::println`** does the same and adds a newline. So `std::println("chamber {:.1f} kPa", p);` prints one line.

**libstdc++ 13 has no `<print>`** — `#include <print>` fails with `print: No such file or directory`. It arrived in libstdc++ 14. Until then, `std::format` plus `std::fputs` does the same job.

::: example Printing with format on g++ 13
```cpp
#include <cstdio>
#include <format>

int main() {
    // Until <print> arrives (libstdc++ 14), std::format plus fputs does the job:
    std::fputs(std::format("chamber {:.1f} kPa, valve {}%\n", 400.0, 35).c_str(), stdout);

    // With no std::string at all: format into a fixed buffer you own.
    char line[32];
    auto res = std::format_to_n(line, sizeof line - 1, "T+{:>4}s {:+.2f}", 12, -0.5);
    *res.out = '\0';
    std::printf("[%s] (%td chars)\n", line, res.size);
}
```

Built with `g++ -std=c++20 -Wall -Wextra -O2`:

```text
chamber 400.0 kPa, valve 35%
[T+  12s -0.50] (13 chars)
```

Line one: `{:.1f}` printed 400.0 with one decimal and `{}` printed 35 as an integer, each chosen from the argument's type. Line two uses **`std::format_to_n`**, which writes at most `n` characters through an output iterator — here a plain `char` array — and never builds a `std::string`. `{:>4}` right-aligns 12 in four columns, `{:+.2f}` forces a sign and two decimals. It returns `out`, where writing stopped, and `size`, the length the full text would have had.

Sanity check the count: `T+` (2), `  12` (4), `s` (1), a space (1), `-0.50` (5) makes $2 + 4 + 1 + 1 + 5 = 13$, and 13 fits in the 31 characters allowed, so nothing was cut off.
:::

::: key
`std::print` and `std::println` (C++23, `<print>`) are type-checked `printf`: `std::format` syntax, written straight to output. Not in libstdc++ 13; use `std::format` with `std::fputs`, or `std::format_to_n` into a fixed buffer.
:::

Flight code rarely prints at all: telemetry leaves the vehicle as packed binary, and ground software turns it into text. Where on-board text is needed — an event log, a debug port — `std::format` returning a `std::string` can reach the heap once the text outgrows the string's small internal buffer, so `format_to_n` into a fixed array is the bounded choice.

## Smaller things worth knowing

A few more C++23 items, each small enough for a paragraph.

**Deducing `this`.** A member function can name the object it was called on as an explicit first parameter, written `this Self& self`. One template then serves both the `const` and the non-`const` object, where you used to write two near-identical overloads. g++ 13 does not support it (`expected identifier before 'this'`); clang 18 does:

```cpp
#include <cstdio>

struct Telemetry {
    int seq = 0;

    // One function instead of a const and a non-const overload:
    // "self" is the object the function was called on, with its real type.
    template <typename Self>
    auto& counter(this Self& self) { return self.seq; }
};

int main() {
    Telemetry t;
    t.counter() = 41;             // Self is Telemetry: returns int&
    ++t.counter();
    const Telemetry& view = t;
    std::printf("seq = %d\n", view.counter());   // Self is const Telemetry
    // view.counter() = 0;        // would not compile: returns const int&
}
```

Built with `clang++ -std=c++23 -Wall -Wextra -O2`, it prints `seq = 42`. Un-comment the last line and clang refuses: `cannot assign to return value because function 'counter<const Telemetry>' returns a const value`. It also lets you write CRTP-style code (the RAII and templates modules) without a template base class.

**Utilities that do work on g++ 13.** `std::to_underlying(e)`, from `<utility>`, gives an `enum class` value's underlying integer without spelling out the type in a `static_cast`. `std::byteswap(x)`, from `<bit>`, reverses the [[bytes of an integer|byteswap]], the everyday job of converting telemetry between big-endian and little-endian. `std::unreachable()`, from `<utility>`, tells the compiler a point can never be reached:

```cpp
#include <bit>
#include <cstdint>
#include <cstdio>
#include <utility>

enum class Mode : std::uint8_t { standby = 1, ascent = 2, coast = 3 };

const char* mode_name(Mode m) {
    switch (m) {
    case Mode::standby: return "standby";
    case Mode::ascent:  return "ascent";
    case Mode::coast:   return "coast";
    }
    std::unreachable();   // promise: every Mode value is handled above
}

int main() {
    Mode m = Mode::ascent;
    std::printf("mode %s = %d\n", mode_name(m), std::to_underlying(m));

    std::uint32_t word = 0x0A0B0C0D;   // as the CPU holds it
    std::printf("%08X -> %08X\n", static_cast<unsigned>(word),
                static_cast<unsigned>(std::byteswap(word)));
}
```

With `g++ -std=c++23 -Wall -Wextra -O2` it prints `mode ascent = 2` and `0A0B0C0D -> 0D0C0B0A`.

::: warning
`std::unreachable()` is a promise, not a check. If a corrupted byte ever makes `m` equal to 7, reaching `std::unreachable()` is undefined behavior, and the optimiser may have removed any code that would have coped. A radiation-flipped bit is exactly how "impossible" values reach flight code. In a flight build, end such a `switch` with a defined fault response — return `"invalid"`, raise a fault flag — rather than `std::unreachable()`.
:::

The rest, in a line each: **`import std;`** and **`std::generator`** you met in lesson 07; **`std::stacktrace`** (`<stacktrace>`) captures the call stack for a crash report, and g++ 13 has it if you link with `-lstdc++exp`; `std::ranges::to` (turn a range into a container) and **`std::flat_map`** (a sorted map in one contiguous array) are not in libstdc++ 13.

## Check yourself

::: check
A function `std::expected<Attitude, ImuError> read_imu()` feeds `double heading(const Attitude&)`, which cannot fail. Then `std::expected<double, ImuError> check_heading(double)` validates the result. Write the chain, and say which member function joins each step.
:::

::: answer
`read_imu().transform(heading).and_then(check_heading)`. `heading` returns a plain `double` and cannot fail, so it joins with `transform`, which wraps its result back into an `expected<double, ImuError>`. `check_heading` can fail and returns an `expected`, so it joins with `and_then`. If `read_imu` fails, both later steps are skipped and the `ImuError` comes out the end.
:::

::: check
A 4-by-4 matrix is stored row-major in a flat array of 16 `float`s. At what index is row 2, column 3? Where would it be if the same buffer were read column-major?
:::

::: answer
Row-major: skip 2 whole rows of 4, then 3 more: $4 \cdot 2 + 3 = 11$. Column-major: skip 3 whole columns of 4, then 2 more: $2 + 4 \cdot 3 = 14$. Same buffer, different element — which is why an `mdspan` carries its layout (`layout_right` or `layout_left`) in its type, and why handing a row-major buffer to column-major code silently transposes the matrix.
:::

::: check
Your ground-tools teammate writes `std::println("{}", x);` and it fails to compile on the project's g++ 13 build machine with `print: No such file or directory`. What is wrong, and what do you suggest that works today?
:::

::: answer
Nothing is wrong with the code; `<print>` is C++23 and libstdc++ 13 does not have it (it arrived in libstdc++ 14). With g++ 13, `std::fputs(std::format("{}\n", x).c_str(), stdout);` gives the same type-checked formatting, since `<format>` is present. If heap use matters, `std::format_to_n` into a fixed `char` array avoids building a `std::string`.
:::

::: check
Why can `std::mdspan` treat a static 36-element buffer as a $6 \times 6$ covariance matrix without breaking a no-allocation-after-start-up rule? What must you still be careful of?
:::

::: answer
`mdspan` is non-owning: it holds only a pointer to the buffer plus its shape and layout, so making one never allocates, copies or frees anything — with compile-time extents it is one pointer. Element $(r, c)$ is computed from the index sum, here $6r + c$ for row-major. The care: the view must not outlive the buffer, or every access is undefined behavior, as with a dangling `span`.
:::

::: check
A reviewer sees `std::unreachable();` after a `switch` over a mode enum in flight code. Why might they ask you to change it, and to what?
:::

::: answer
`std::unreachable()` tells the compiler the point cannot be reached, and reaching it is undefined behavior. A memory upset or a bad command can put an out-of-range value in an enum, so in flight "cannot happen" must still be handled. Replace it with a defined response: return an "invalid" result, set a fault flag, or command a safe mode.
:::

## Summary

| Idea | Meaning | Rule or fact |
| --- | --- | --- |
| `std::expected<T, E>` | a value or an error, no heap | C++23; g++ 13 with `-std=c++23` |
| `and_then` / `transform` | next step that can / cannot fail | `and_then`'s function returns an `expected` |
| `or_else` / `transform_error` | recover from / convert the error | `value_or(d)` for a safe default |
| `std::mdspan` | non-owning multidimensional view | pointer + extents + layout; not in libstdc++ 13 |
| Row-major index | where $(r, c)$ lives in a flat buffer | $\text{cols} \cdot r + c$ (`layout_right`) |
| `m[i, j]` | multidimensional subscript | C++23 language feature; works in g++ 13 |
| `std::print`, `std::println` | type-checked printing | `<print>`, libstdc++ 14; use `format` today |
| Deducing `this` | explicit object parameter | clang 18 yes, g++ 13 no |
| `std::unreachable()` | promise a point is never reached | undefined behavior if reached |

::: context cpp23-timeline Finished in 2023, published in 2024
The committee completed the technical work on C++23 in early 2023, which gives the standard its name. The formal publication by ISO, as the document ISO/IEC 14882:2024, came in 2024. That gap is normal: the number names the year the content was settled, and compilers had already begun implementing the features long before either date, as the proposals were accepted one by one.
:::

::: context support-matrix Compiler, library and flags must all agree
A C++ feature can be blocked in three independent places. The compiler must understand the syntax. The standard library must contain the header and class. And the flags must ask for the right standard: `std::expected` on g++ 13 exists only with `-std=c++23`, and under `-std=c++20` the header is empty. The cppreference compiler support tables track all of this, feature by feature. Flight teams record the answer for their pinned toolchain in the coding standard.

::: context monadic A word borrowed from functional programming
"Monadic" comes from functional languages such as Haskell, where types like `Maybe` (a value or nothing) and `Either` (a value or an error) are chained with standard operations. You do not need the theory. The practical idea is the conveyor belt: each step gets the value if there is one, and an error rides past every remaining step untouched to the end. `std::optional` gained the same `and_then`, `transform` and `or_else` in C++23.

::: context column-major Two ways to lay out a grid
Row-major means row 0's elements come first, then row 1's. Column-major means column 0's elements come first. C and C++ built-in arrays are row-major. Fortran and MATLAB are column-major, and so is the Eigen library by default, which the Eigen module later in this track uses. Mixing the two without noticing gives you the transpose of the matrix you meant.

::: context byteswap Big-endian telemetry on a little-endian computer
Most flight and ground processors today are little-endian: they store an integer's lowest byte first. Many telemetry and network formats are big-endian, highest byte first. So `0x0A0B0C0D` held by the CPU as the bytes `0D 0C 0B 0A` must go on the wire as `0A 0B 0C 0D`. The memory module's lesson on endianness did this with shifts and masks; `std::byteswap` is the one-call version, and it compiles to a single instruction on common processors.
