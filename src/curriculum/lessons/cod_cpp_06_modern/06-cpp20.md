Picture a city that, in the same year, opens a subway, rebuilds its water mains, and also repaints every street sign so that you can read them from a block away. The subway and the water mains change how the whole city works, and they take years to reach every neighbourhood. The street signs help everyone the next morning.

C++20 is that year. Four of its features are infrastructure: **concepts**, **ranges**, **modules** and **coroutines**. Each changes how large programs are written, and two of them (modules and coroutines) are still reaching the neighbourhoods. Around them sit many street signs: `std::span`, `std::format`, the spaceship operator, designated initializers, `constinit` and `consteval`, `std::atomic_ref`. Those you can use tomorrow.

As with the last lesson, you have met most of these already, in the STL and templates modules. This lesson puts them on one map, adds the two you have not seen in full (designated initializers and `atomic_ref`), and answers a practical question for each: does it belong inside a 1 kHz control task? Where the answer depends on your compiler, it says what g++ 13, the compiler on this course's machine, really does. Before relying on any of these on an embedded toolchain, check the **[[compiler support tables|support-tables]]**.

## Concepts: a sign at the gate

You met concepts in the templates module, lesson 06. A **concept** is a named, compile-time yes-or-no test on a type, such as `std::floating_point<T>`. Writing it in a template's header puts a sign at the gate: only types that pass may enter.

```cpp
template <std::floating_point T>
T mean(std::span<const T> xs);
```

Call that with a span of `int`s and g++ 13 answers at the call site, in words: `no matching function for call to 'mean(std::span<const int>)'`, then `constraints not satisfied`, then `the expression 'is_floating_point_v<_Tp> [with _Tp = int]' evaluated to 'false'`. Compare that with the page of substitution failures an unconstrained template produces deep inside its body.

For flight code, concepts are pure gain. They cost nothing at run time, they turn the rules of a template (a matrix's scalar type must be floating-point, a sensor driver must provide `read()`) into checked code rather than a comment, and they make the error point at the caller's mistake.

## Ranges: pipelines that allocate nothing

The STL module's lesson 13 covered ranges. The **ranges** library does two things. It gives every algorithm a version that takes a whole container, `std::ranges::sort(v)` instead of `std::sort(v.begin(), v.end())`, which removes the classic bug of mixing one container's `begin` with another's `end`. And it adds **views**: lazy pipelines such as `xs | std::views::filter(ok)`, read "xs, piped through a filter by ok", which produce elements on demand and own nothing.

Views allocate no memory, so they are allowed in a control loop. They carry the same dangling hazard as `span` and `string_view`: a view of a temporary container outlives its data. And some of the most convenient pieces are C++23, needing `-std=c++23` on g++ 13; `std::ranges::to` is missing from g++ 13 altogether.

## `std::span`: the pointer and length, glued

The STL module's lesson 04 met `std::span` in full: a view of a contiguous run of elements, holding a pointer and a count, with a *fixed extent* form (`std::span<const double, 3>`) whose length is part of the type.

Here is why it matters so much that it gets a flashcard of its own. For forty years, C and C++ functions took buffers as two separate parameters, `const uint8_t* p, int n`. Nothing tied them together. A caller could pass a 9-byte buffer with a count of 64, or a null pointer with a count of 8. Each of those is a real class of defect, and each disappears when the pair becomes one object.

::: key What std::span replaces, and why flight code likes it
The pointer-plus-length pair. It cannot be mismatched, it carries its size for bounds checking in debug builds, and it owns nothing, so it introduces no allocation.
:::

"Bounds checking in debug builds" deserves a closer look, because the standard's `span::operator[]` does *not* check. What checks is the library, when you ask it to. With libstdc++ you define the macro `_GLIBCXX_ASSERTIONS` (compile with **[[-D_GLIBCXX_ASSERTIONS|glibcxx-assertions]]**) and indexing past the end stops the program at once, with a message, instead of reading whatever sits next in memory. Because a span carries its size, the library *can* check. A bare pointer cannot be checked by anyone.

## `std::format`: typed, checked formatting

You met `std::format` in the basics module (lesson 12). It uses `{}` placeholders like Python's f-strings, checks the format string against the argument types **at compile time**, and never reads the wrong type off the stack the way a mismatched `printf` can. The design came from the open-source **[[{fmt} library|fmt-library]]**.

Check your compiler before using it. **g++ 13 has `<format>`**: on this machine, `std::format` compiles and runs with g++ 13.3.0 and `-std=c++20`, and the feature-test macro `__cpp_lib_format` is `202110L`. GCC 12 and earlier did not ship it. `std::print`, which formats and writes in one call, is C++23 and is *not* in g++ 13: `#include <print>` fails with "No such file or directory". Lesson 08 returns to it.

For flight code, the catch is that `std::format` returns a `std::string`, which may allocate (lesson 04). Its sibling `std::format_to_n` writes into a buffer you provide and stops at the size you give. Same checked format strings, bounded memory.

::: example A telemetry line in a fixed buffer, and a bounds check
```cpp
#include <array>
#include <cstdint>
#include <cstdio>
#include <format>
#include <span>

// One telemetry line, formatted into a fixed buffer: no heap, bounded length.
std::size_t format_line(std::span<char> out, std::uint32_t t_ms,
                        std::span<const double, 3> rate) {
    auto r = std::format_to_n(out.data(), static_cast<std::ptrdiff_t>(out.size() - 1),
                              "t={:>8} gyro=[{:+.4f} {:+.4f} {:+.4f}]",
                              t_ms, rate[0], rate[1], rate[2]);
    *r.out = '\0';          // r.out: one past the last character written
    return static_cast<std::size_t>(r.size);   // r.size: length it wanted
}

int main(int argc, char**) {
    std::array<char, 64> line{};
    const std::array<double, 3> rate{0.0125, -0.0031, 0.25};

    std::size_t n = format_line(line, 120'004, rate);
    std::printf("%s  (%zu chars)\n", line.data(), n);

    std::array<char, 24> small{};
    n = format_line(small, 120'004, rate);
    std::printf("%s  (wanted %zu chars, buffer holds %zu)\n", small.data(), n, small.size() - 1);

    std::span<const double> s{rate};
    const std::size_t i = static_cast<std::size_t>(argc) + 2;   // 3 with no arguments
    std::printf("s[2] = %.2f\n", s[2]);
    std::fflush(stdout);                          // get the lines out before any abort
    std::printf("s[%zu] = %.2f\n", i, s[i]);      // one past the end
}
```

Built with `g++ -std=c++20 -Wall -Wextra -O2`, no warnings:

```text
t=  120004 gyro=[+0.0125 -0.0031 +0.2500]  (41 chars)
t=  120004 gyro=[+0.012  (wanted 41 chars, buffer holds 23)
s[2] = 0.25
s[3] = 0.00
```

Built again with `-D_GLIBCXX_ASSERTIONS` added:

```text
t=  120004 gyro=[+0.0125 -0.0031 +0.2500]  (41 chars)
t=  120004 gyro=[+0.012  (wanted 41 chars, buffer holds 23)
s[2] = 0.25
/usr/include/c++/13/span:288: constexpr std::span<_Type, _Extent>::element_type& std::span<_Type, _Extent>::operator[](size_type) const [with _Type = const double; long unsigned int _Extent = 18446744073709551615; reference = const double&; size_type = long unsigned int]: Assertion '__idx < size()' failed.
```

Walk through it:

1. **Two spans in, no copies.** `format_line` takes a writable `std::span<char>` for the output and a fixed-extent `std::span<const double, 3>` for the rates. Both `std::array`s convert automatically; a `std::array<double, 4>` would not compile.
2. **The format string.** `{:>8}` right-aligns the time in 8 characters; `{:+.4f}` prints a sign and 4 decimals. The first line has 41 characters: count `t=`, eight for `  120004`, and `gyro=[...]`. The function returns `r.size`, the length the full text *wanted*.
3. **Truncation, not overflow.** The 24-byte buffer leaves room for 23 characters plus the terminating zero. `format_to_n` wrote exactly 23 (`t=  120004 gyro=[+0.012`) and stopped. It still reports that 41 were wanted, so the caller can notice the truncation. Nothing was written past the buffer.
4. **The bad index, release build.** `s[3]` is one past the end. Without assertions it read the next 8 bytes of the stack and printed `0.00`. That is undefined behavior, not a real value: clang++ 18 built the same code and printed `s[3] = -1845.65`.
5. **The bad index, checked build.** With `_GLIBCXX_ASSERTIONS`, the span compared the index with its size (`__idx < size()`) and stopped the program, pointing at the failed check. The shell reported "Aborted" and an exit status of 134.

Sanity check: $41 > 23$, so the second line had to be cut short, and it was cut at exactly 23 characters. The one line that differs between the two builds is the out-of-bounds read, the only line with a bug.
:::

## Three-way comparison: one operator, six answers

The RAII module (lesson 09) introduced `operator<=>`, read "the spaceship operator". Instead of yes or no, `a <=> b` answers *which way*: less, equivalent or greater. Its result compares with zero, so `(a <=> b) < 0` means `a` is less.

Its big use is `= default`. Before C++20, a type that needed ordering had six hand-written operators — `==`, `!=`, `<`, `<=`, `>`, `>=` — and it was easy to update five and forget one, so that `a < b` and `b > a` disagreed. Defaulting the spaceship makes the compiler compare the members in declaration order, the way a dictionary compares words letter by letter.

How each of the six is produced is worth getting exactly right:

- `<`, `<=`, `>` and `>=`, the four **relational** operators, are **rewritten** in terms of `<=>`: `a < b` becomes `(a <=> b) < 0`.
- `==` is **separate**. It does not go through `<=>`, because equality can often be decided more **[[cheaply|equality-cheaper]]** than ordering. You get a defaulted `==` either by defaulting it yourself, `bool operator==(const T&) const = default;`, or automatically: when you default `<=>` and declare no `==`, the compiler declares a defaulted `==` for you.
- `!=` is rewritten as `!(a == b)`.

::: key What the spaceship operator generates
Defaulting `operator<=>` gives you the relational operators from a member-wise comparison, plus `==` when you default that too (or leave the compiler to default it alongside `<=>`), and `!=` from `==`: all six. It removes a large block of boilerplate that was a classic place for an inconsistent comparison bug.
:::

The result type says how strong the ordering is: `std::strong_ordering` for integers, `std::partial_ordering` for anything containing a `double`, because a NaN compares as neither less, equal nor greater. A defaulted `<=>` picks the weakest category among the members.

## Designated initializers: name each field as you set it

Picture a form with labeled boxes: "Name: ___", "Date: ___". You can fill it in without remembering which box comes third. Compare a form with no labels, where you must know the order by heart.

A **designated initializer** puts the labels on a brace list. For a plain struct with public members, an **[[aggregate|aggregate]]**:

```cpp
struct LoopConfig {
    std::uint32_t rate_hz = 1000;
    double kp = 0.0;
    double ki = 0.0;
    double kd = 0.0;
    bool   saturate = true;
};

constexpr LoopConfig pitch{.rate_hz = 500, .kp = 2.4, .kd = 0.15};
```

Read `.kp = 2.4` as "the member kp is 2.4". The rules:

- The designators must appear in **declaration order**. You may skip members; you may not go backwards.
- A skipped member gets its default member initializer (`ki` above becomes `0.0`, `saturate` becomes `true`), or zero if it has none.
- **Narrowing** is still an error: `.rate_hz = 2.5` would not compile, exactly as in lesson 02's braces.
- You cannot mix designated and positional values in one list, and C++ has no nested (`.a.b = 1`) or array (`[3] = 1`) designators. C has had designators, with all of those, since **[[C99|c-designators]]**; C++ took a stricter subset.

Why flight code likes them: a gain table written positionally, `{500, 2.4, 0.0, 0.15, true}`, silently changes meaning when someone inserts a member in the middle of the struct. Written with designators, the same change either still means the right thing or refuses to compile.

::: example A config, a version check and a filtered mean
```cpp
#include <compare>
#include <concepts>
#include <cstdint>
#include <cstdio>
#include <ranges>
#include <span>
#include <vector>

struct LoopConfig {
    std::uint32_t rate_hz = 1000;
    double kp = 0.0;
    double ki = 0.0;
    double kd = 0.0;
    bool   saturate = true;
};

struct Version {
    int major, minor, patch;
    auto operator<=>(const Version&) const = default;
};

template <std::floating_point T>
T mean_of_valid(std::span<const T> xs, T lo, T hi) {
    auto ok = [=](T x) { return x >= lo && x <= hi; };
    T sum = 0;
    int n = 0;
    for (T x : xs | std::views::filter(ok)) { sum += x; ++n; }
    return n ? sum / static_cast<T>(n) : T{0};
}

int main() {
    constexpr LoopConfig pitch{.rate_hz = 500, .kp = 2.4, .kd = 0.15};
    std::printf("rate %u Hz, kp %.2f, ki %.2f, kd %.2f, saturate %d\n",
                pitch.rate_hz, pitch.kp, pitch.ki, pitch.kd, pitch.saturate);

    constexpr Version flown{2, 7, 1}, candidate{2, 10, 0};
    std::printf("candidate newer: %d, same: %d\n", candidate > flown, candidate == flown);

    std::vector<double> temps{21.4, 21.9, -999.0, 22.3, 950.0, 21.8};
    std::printf("mean of valid: %.3f\n",
                mean_of_valid(std::span<const double>{temps}, -50.0, 150.0));
}
```

With `g++ -std=c++20 -Wall -Wextra -O2`, no warnings:

```text
rate 500 Hz, kp 2.40, ki 0.00, kd 0.15, saturate 1
candidate newer: 1, same: 0
mean of valid: 21.850
```

Line by line:

1. **The config.** Three members named, two skipped. `ki` took its default `0.0`, `saturate` its default `true` (printed as `1`). The whole object is `constexpr`, built by the compiler.
2. **The version.** The defaulted `<=>` compares `major` first ($2 = 2$), then `minor`: $10 > 7$, so the candidate is newer. Comparing the text `"2.10.0"` with `"2.7.1"` character by character would have said the opposite, because the character `1` sorts before `7`. `==` works too, though only `<=>` was written: the compiler declared a defaulted `==` alongside it.
3. **The mean.** `std::floating_point` admits `double`. The view skips $-999.0$ (a sentinel) and $950.0$ (a spike) without copying anything, leaving $21.4, 21.9, 22.3, 21.8$. Their sum is $87.4$, and $87.4 / 4 = 21.85$.

Sanity check: the four valid temperatures all sit between 21.4 and 22.3, and 21.85 is between them. Had the sentinel been included, the mean would have gone far below zero.

Now swap the order of two designators, `LoopConfig bad{.kp = 2.4, .rate_hz = 500};`, and g++ refuses: "designator order for field 'LoopConfig::rate_hz' does not match declaration order in 'LoopConfig'".
:::

::: warning The order rule is not a style preference
In C, `{.kp = 2.4, .rate_hz = 500}` is legal. People who move between C and C++ write it, and g++ 13 rejects it as an error, as the example showed. clang++ accepts it with only a warning, `-Wreorder-init-list`, so code that builds on one compiler can fail on the other. Keep designators in declaration order, always.
:::

## `constinit` and `consteval`

The templates module (lesson 07) covered both. In one line each:

- **`consteval`** marks an **immediate function**: every call must be evaluated by the compiler. Use it for table builders and validators that must never exist in the flight binary as run-time code.
- **`constinit`** on a variable with static storage says it must be initialized before any code runs, during static initialization, or the build fails. Unlike `constexpr`, the variable is not `const`: a `constinit` counter can still change. It closes the "static initialization order fiasco" for that variable.

Both cost nothing at run time, and both belong in flight code.

## The rest, briefly: modules, coroutines, `atomic_ref`

**Modules** replace `#include` — pasting a header's text into every file that uses it — with `import`, which loads an interface the compiler has already processed once. They promise faster builds and an end to macros leaking between headers. On g++ 13 they are still experimental: you need the flag `-fmodules-ts`, the compiler writes its compiled **[[module interfaces|module-interface]]** into a `gcm.cache` directory, and `import std;` does not work. A two-file module compiled and ran on this machine with that flag; without it, g++ says "'import' does not name a type". Why adoption across the industry is slow is the subject of the next lesson.

**Coroutines** are functions that can pause (`co_await`, `co_yield`) and later resume where they stopped. They make asynchronous code read like straight-line code. But the paused function's local variables must live somewhere while it waits, in a **[[coroutine frame|coroutine-frame]]** that the compiler allocates on the heap unless it can prove the allocation away. That is why you will rarely see them inside a hard real-time task; the next lesson takes this up too.

**`std::atomic_ref<T>`** gives atomic operations on an ordinary object that was not declared `std::atomic`. For a counter inside a plain struct shared between an interrupt handler and a task, `std::atomic_ref<std::uint32_t>{health.frames_bad}.fetch_add(1)` updates it atomically, and the struct keeps its plain layout. The object must be aligned to `std::atomic_ref<T>::required_alignment`, which on this machine is 4 bytes for `std::uint32_t` and 8 for `double`. While any `atomic_ref` to an object exists, every access to it must go through an `atomic_ref`. The **[[concurrency module|concurrency-bridge]]** explains why that rule matters.

A few smaller C++20 pieces you will meet in flight code: `std::bit_cast` and `std::endian` from `<bit>` (reinterpret the bytes of a float safely, and ask the machine's byte order, both useful for telemetry packing), `std::erase_if` (STL module, lesson 09), and `using enum` inside a `switch`.

## Check yourself

::: check
A legacy function is `bool unpack(const uint8_t* p, int n, Frame* out);`. Name four distinct defects its signature allows, and a C++17/C++20 signature that removes them.
:::

::: answer
Defects: (1) `p` and `n` can disagree, so the function reads past the buffer; (2) `p` can be null; (3) the caller can ignore the `bool` and use `*out` anyway; (4) on failure `*out` may be half-written; also `out` itself can be null. A better signature is `std::optional<Frame> unpack(std::span<const std::uint8_t> bytes);`. The span makes the pointer and the length one object that cannot be mismatched, and is checkable in debug builds. The optional replaces the flag and the out-parameter: there is either a whole `Frame` or none, so nothing can be used unchecked or half-written.
:::

::: check
Your team's toolchain is GCC 13. A colleague wants to replace a flight task's `snprintf` calls with `std::format`. What do you tell them?
:::

::: answer
`<format>` is available in g++ 13 with `-std=c++20`, so it will compile, and its format strings are checked at compile time, which removes the type-mismatch bugs `snprintf` allows. But `std::format` returns a `std::string`, which allocates when the text exceeds the small-string buffer, and allocation is usually banned in the task. Use `std::format_to_n` into a fixed `std::array<char, N>` instead: same checking, bounded memory, and it reports truncation through `.size`. `std::print` is not an option on g++ 13 at all.
:::

::: check
`struct TimeTag { std::uint32_t s; std::uint16_t sub; auto operator<=>(const TimeTag&) const = default; };` Which of `a < b`, `a >= b`, `a == b` and `a != b` compile, and which function does each one call?
:::

::: answer
All four compile. `a < b` becomes `(a <=> b) < 0` and `a >= b` becomes `(a <=> b) >= 0`: both call the defaulted `<=>`. `a == b` calls a defaulted `operator==`, which the compiler declared because `<=>` was defaulted and no `==` was written; it compares `s` and then `sub` for equality. `a != b` is rewritten as `!(a == b)`.
:::

::: check
Given `struct Limits { double min_c = -40.0; double max_c = 85.0; int retries = 3; };`, what are the members of `Limits L{.max_c = 70.0};`? Does `Limits M{.retries = 5, .min_c = -20.0};` compile with g++ 13?
:::

::: answer
`L.min_c` is $-40.0$ (its default), `L.max_c` is $70.0$, `L.retries` is $3$ (its default). `M` does not compile with g++ 13: `retries` is declared after `min_c`, so naming it first breaks the declaration-order rule, and g++ reports that the designator order does not match. Write `Limits M{.min_c = -20.0, .retries = 5};`.
:::

::: check
Why would a 1 kHz attitude task happily use concepts, views and `constinit`, but avoid coroutines?
:::

::: answer
Concepts and `constinit` act entirely at compile time and cost nothing at run time. Views compute elements on demand and allocate nothing. A coroutine needs a frame to hold its state while it is paused, and the compiler puts that frame on the heap unless it can prove it unnecessary; its pause-and-resume control flow is also harder to bound for worst-case timing. Allocation and hard-to-analyze timing are exactly what a hard real-time task forbids.
:::

## Summary

| Idea | Meaning | Rule or fact |
|---|---|---|
| Concepts | named compile-time tests on types | clear errors at the call site; zero run-time cost |
| Ranges and views | whole-range algorithms; lazy pipelines | views own nothing, allocate nothing, can dangle |
| `std::span` | pointer plus length in one object | cannot be mismatched; checkable with `_GLIBCXX_ASSERTIONS` |
| `std::format` | typed `{}` formatting | in g++ 13; returns `std::string`; `format_to_n` for fixed buffers; no `std::print` |
| `operator<=>` | three-way comparison | four relational from `<=>`, `==` defaulted separately or alongside, `!=` from `==` |
| Designated initializers | `{.field = value}` | declaration order, skips allowed, no narrowing |
| `consteval`, `constinit` | forced compile time; static init | both zero run-time cost |
| Modules | `import` instead of `#include` | g++ 13: `-fmodules-ts`, experimental |
| Coroutines | functions that pause | frame is heap-allocated unless elided |
| `std::atomic_ref` | atomic access to a plain object | alignment rule; all access atomic while it exists |

Next lesson looks at the two features this one kept brief: why modules are taking years to adopt and what they will change, and why coroutines are rare in flight code.

::: context support-tables Check before you rely on it
cppreference.com keeps tables showing, feature by feature, which versions of GCC, Clang and Microsoft's compiler support each part of each standard, for the language and the library separately. Embedded toolchains often lag the desktop by years, and a certified compiler may be older still. The cheap habit is to look up every feature you plan to use in those tables, and then confirm with a two-line test program on the compiler you actually fly.
:::

::: context glibcxx-assertions A cheap safety net in the library
Defining `_GLIBCXX_ASSERTIONS` switches on precondition checks inside libstdc++: indexing a `vector`, `array`, `span` or `string` out of range, calling `front()` on an empty container, and many more. A failed check prints the condition and aborts. The checks are much lighter than libstdc++'s full debug mode, `_GLIBCXX_DEBUG`, and they do not change the layout of any type, so checked and unchecked code can be linked together. Many teams keep them on in every test build.
:::

::: context fmt-library Where std::format came from
`std::format` is based on {fmt}, an open-source formatting library started by Victor Zverovich. It proved the design in real projects, including compile-time checking of format strings, before being proposed for the standard. {fmt} is still maintained and still runs ahead of the standard, which makes it a common choice for projects stuck on a compiler without `<format>`.
:::

::: context equality-cheaper Why equality can skip the ordering work
To say which of two vectors comes first, you must walk the elements until two differ. To say whether they are equal, you can first compare their lengths, and if the lengths differ you are done without reading a single element. That is why C++20 keeps `==` separate from `<=>`.

::: context aggregate What counts as an aggregate
An aggregate is a class with no user-declared constructors, no private or protected non-static data members, no virtual functions, and no virtual, private or protected base classes. In practice: a plain struct of public fields, with or without default member initializers. Arrays are aggregates too. Designated initializers work only on aggregates, because the braces set the members directly rather than calling a constructor.
:::

::: context c-designators Borrowed from C, with stricter rules
C99, the 1999 revision of C, introduced designated initializers, and C programmers have used them for decades for exactly this job: device tables and configuration structs. C allows designators in any order, nested ones like `.pos.x = 1`, array ones like `[4] = 7`, and mixing with positional values. C++20 kept only the in-order, one-level form, so that initialization order always matches declaration order.
:::

::: context module-interface Pasting text versus loading a summary
With `#include`, every source file re-reads and re-parses the full text of every header it uses, thousands of times across a large build. With a module, the compiler processes the interface once and saves a compiled summary; each importer loads the summary. The catch is that the build system must now build modules in the right order.

::: context coroutine-frame Where a paused function keeps its things
An ordinary function's locals live in its stack frame, which disappears when it returns. A coroutine can return to its caller while paused and be resumed later, so its locals must outlive that stack frame. The compiler moves them into a separate frame object, by default obtained with `operator new`.

::: context concurrency-bridge Where atomic_ref comes back
The concurrency module covers the C++ memory model: what "atomic" really promises, the memory orderings (relaxed, acquire and release, sequentially consistent), and `is_lock_free`. `atomic_ref` returns there, for the common flight case of a plain struct in shared memory or a buffer filled by hardware, where you cannot change the declared type to `std::atomic` but still need race-free access.
:::
