Picture the car your family drove for thirteen years. Then a new model arrives. The pedals are in the same place and the steering wheel turns the same way, so you already know how to drive it. But it has a backup camera, a chime that nags until you buckle up, and a light that warns you when you drift out of your lane. None of that makes the car faster. It makes a whole list of accidents harder to have.

That is what **C++11** did to C++. It was the first big revision of the language since the original standard of 1998, and it kept almost every old program working. What it added were tools that let the compiler catch mistakes that used to reach testing, or flight: a pointer mixed up with a number, an override that silently overrides nothing, a buffer that nobody frees.

You have already used most of these tools. Five modules taught them one at a time, where they were needed. This module steps back and draws the map: which standard added what, why each feature exists, where people slip, and which parts flight teams actually allow inside a 1 kHz control loop. This lesson covers C++11. The next one takes its most surprising feature, brace initialisation, on its own. After that come C++14, 17, 20 and 23.

## Thirteen years, then a new language

The first **ISO standard** for C++ — the official rulebook, agreed by an international committee — came out in 1998, so people call it **C++98**. A small bug-fix edition followed in 2003, **C++03**. Then nothing big for eight more years. The next standard was planned for the 2000s, so its working name was "C++0x". It slipped to 2011 and became **C++11**.

Since then the **[[committee|standards-timeline]]** has shipped a new standard every three years: C++14, C++17, C++20, C++23. Many teams still call everything from 2011 on "modern C++", and the older style "C++98-style". When you open a legacy flight codebase, the two styles often sit side by side in the same file.

Here is the list this lesson walks through. Each feature gets the same three questions: what it is, what defect it prevents, and where you met it before.

## Saying less: auto, range-for and lambdas

These three make code shorter. Shorter matters because every character you type is a character you can get wrong.

**`auto`** tells the compiler to work out a variable's type from its starting value. The type is still fixed while compiling, exactly as if you had typed it. `auto it = table.find(key);` saves you from spelling `std::map<std::uint16_t, Channel>::iterator` and from getting it slightly wrong.

The **range-based for loop**, `for (const auto& s : samples)`, read "for each `s` in `samples`", visits every element without an index. No index means no off-by-one error and no `i` compared against the wrong container's size.

A **lambda** is a small unnamed function written where it is used: `[](double p) { return p > limit; }`. Before C++11 you had to write a whole named class with an `operator()` somewhere else in the file, so people wrote hand-rolled loops instead of using `std::count_if` or `std::sort`. Lambdas made the standard algorithms practical.

::: warning `auto` copies unless you say otherwise
`auto` drops references and top-level `const`. If `frame()` returns a `const Frame&`, then `auto f = frame();` makes a full copy of the `Frame`, and changing `f` changes only the copy. The same holds in a loop: `for (auto f : frames)` copies every element. Write `const auto&` when you mean "look at it", and plain `auto` when you really want your own copy.
:::

## Ownership in the type: move semantics and smart pointers

Before C++11, handing a big object to someone else meant copying it. Returning a `std::vector` of ten thousand samples from a function could copy all ten thousand. Programmers dodged the cost with out-parameters and raw pointers, and those brought their own bugs.

C++11 added a second kind of reference, the **[[rvalue reference|rvalue-name]]**, written `T&&` and read "T double-ampersand". It binds to objects that are about to disappear, such as a temporary, or anything you mark with `std::move`. A class can then offer a **[[move constructor|move-picture]]**: instead of copying the other object's buffer, it takes the buffer's pointer and leaves the other object empty. Moving a vector is three pointer copies, whatever its size.

`std::move(x)` does not move anything by itself. It is a cast that says "you may treat `x` as disposable". The move happens only if the receiving type has a move constructor or move assignment. After a move, the source is in a **valid but unspecified** state: you may assign to it or destroy it, but do not read it and expect the old value. (A few types promise more. A moved-from `std::vector` is guaranteed empty, and a moved-from `std::unique_ptr` is guaranteed null.)

Move semantics made a safe **smart pointer** possible. C++98's `std::auto_ptr` had tried, but without moves it had to steal ownership when *copied*, so it broke inside containers; C++11 deprecated it and C++17 removed it. Its replacement, `std::unique_ptr`, owns one object and cannot be copied, only moved, so ownership has exactly one holder at a time and the type system enforces it. `std::shared_ptr`, standardised from the Boost library, counts its owners and frees the object when the last one lets go. Both come from the memory module. One gap: C++11 gave you `std::make_shared` but forgot `std::make_unique`. You will see why that mattered in lesson 3.

::: key C++11 ownership
`T&&` is an rvalue reference; `std::move` is only a cast; a moved-from object is valid but unspecified. `std::unique_ptr` is move-only single ownership at zero cost over a raw pointer; `std::shared_ptr` is reference-counted shared ownership. C++11 had `make_shared` but no `make_unique`.
:::

## Saying exactly what you mean: nullptr, enum class, override and final

Three features in C++11 exist for one reason: to turn a silent mistake into a compile error.

### nullptr

In C++98, a null pointer was written `0` or `NULL`. Both are integers. `NULL` is a **[[macro|null-macro]]** that the compiler's library defines as an integer constant, not a pointer. That is harmless until a function is **overloaded** — two functions with the same name and different parameter types. Then the compiler picks the overload that fits an integer best.

C++11 added **`nullptr`**, a null pointer with its own type, `std::nullptr_t`. It converts to every pointer type and to no integer type. The memory module (lesson 2) introduced it. Here is the bug it removes, run for real.

::: example Which overload runs?
A logging helper has two overloads, one for a number and one for a text label. A caller wants "no label":

```cpp
#include <cstddef>
#include <cstdio>

void log_value(int v)         { std::printf("int overload: %d\n", v); }
void log_value(const char* s) { std::printf("pointer overload: %s\n", s ? s : "(null)"); }

int main() {
    log_value(0);        // meant "no string"; which one runs?
    log_value(nullptr);  // C++11
    // log_value(NULL);  // see below
}
```

Compiled with `g++ -std=c++20 -Wall -Wextra -O2`, it prints:

```text
int overload: 0
pointer overload: (null)
```

Step by step:

1. `log_value(0)`: the literal `0` is an `int`. The `int` overload is an exact match, so it wins. The caller wanted the pointer version and got the number version, with no warning at all.
2. `log_value(nullptr)`: `nullptr` cannot become an `int`, so only the pointer overload is possible. It prints `(null)`, which is what the caller meant.
3. Now uncomment the `NULL` line. g++ 13 refuses to compile:

```text
error: call of overloaded 'log_value(NULL)' is ambiguous
```

On g++ and clang, `NULL` is a built-in integer the size of a `long`. It converts equally well to `int` and to a pointer, so the call is ambiguous. On a compiler that defines `NULL` as plain `0`, the same line compiles and quietly calls the `int` overload.

Sanity check: in no case does `NULL` reach the pointer overload unambiguously. Only `nullptr` does. That is why modern coding standards ban `NULL` and `0` as null pointers.
:::

### enum class

An old C-style enum has two problems. Its names spill into the surrounding scope, so `enum Mode { Idle, Boost };` and `enum Valve { Closed, Idle };` in the same namespace collide: g++ says `'Idle' conflicts with a previous declaration`. And it converts silently to `int`, so you can compare a flight mode with a valve state, or add 3 to a mode, and the compiler says nothing.

A **scoped enumeration**, written `enum class`, fixes both:

```cpp
enum class FlightMode { Idle, Boost, Coast };
enum class ValveState { Closed, Idle };

int main() {
    FlightMode m = FlightMode::Boost;
    ValveState v = ValveState::Idle;     // no clash: each Idle lives inside its own enum
    int n = static_cast<int>(m);         // converting to a number must be asked for
    // int bad = m;                      // error: no implicit conversion
    // if (m == v) {}                    // error: different types
    return n == 1 && v == ValveState::Idle ? 0 : 1;
}
```

You write `FlightMode::Boost`, read "FlightMode's Boost". Getting the number out needs a visible `static_cast`. C++11 also lets you choose the underlying integer, `enum class ChannelId : std::uint8_t`, which matters when the value goes into a telemetry packet with a fixed layout.

### override and final

In a class hierarchy, a derived class replaces a base-class virtual function by declaring one with exactly the same signature. "Exactly" is the trap. Forget a `const`, use `float` where the base used `double`, and you have written a *new* function that **[[hides|name-hiding]]** the old one. Calls through a base pointer still run the base version.

C++11's **`override`** says "this must replace a base virtual function". If it does not, the build fails:

```cpp
struct Sensor {
    virtual ~Sensor() = default;
    virtual double read(int channel) const = 0;
};

struct Gyro final : Sensor {
    double read(int channel) override { return channel * 0.01; }  // forgot const
};
```

g++ 13 stops with `error: 'double Gyro::read(int)' marked 'override', but does not override`. **`final`** on a class, as on `Gyro` here, forbids deriving from it; on a virtual function it forbids further overriding. Besides stating intent, `final` lets the compiler turn some virtual calls into direct ones, because it knows no subclass can exist.

::: key Saying what you mean
`nullptr` has type `std::nullptr_t` and converts to any pointer and to no integer, so it always picks the pointer overload. `enum class` names are scoped (`FlightMode::Boost`) and never convert implicitly to `int`. `override` turns a signature mismatch into a compile error; `final` forbids further derivation or overriding.
:::

## Compile time and fixed size: constexpr and std::array

**`constexpr`** marks a value or function the compiler may compute while it builds the program. A `constexpr` variable is a true compile-time constant, typed and scoped, unlike a `#define`. The basics and templates modules covered what it promises.

What they did not stress is how narrow C++11's version was. In C++11, the body of a `constexpr` function could hold essentially **one `return` statement** (plus things like `static_assert` and type aliases). No local variables, no loops, no `if` statements. Anything iterative had to be written as recursion, with the conditional operator `?:` (read "if-then-else in one expression") for branches:

```cpp
// C++11 rules: the body of a constexpr function is one return statement.
constexpr unsigned long long factorial(unsigned n) {
    return n <= 1 ? 1ULL : n * factorial(n - 1);
}

static_assert(factorial(10) == 3628800ULL, "10! is 3628800");
```

That compiles with `-std=c++11`, and `static_assert` proves the answer while compiling. Write the same thing with a `for` loop and a C++11 compiler rejects it. C++14 lifted the limit, and lesson 3 shows the error and the fix.

**`std::array`** is a fixed-size array that knows its own size, does not decay to a pointer when passed to a function, and can be copied and compared like any value. It costs exactly what a C array costs: `std::array<double, 6>` is 48 bytes, all of them samples. It never allocates memory of its own; it lives wherever you put it, usually on the stack or inside another object. That is why flight code likes it for state vectors and small buffers.

## Time and threads: chrono and std::thread

**`std::chrono`** puts units on time. A `std::chrono::milliseconds` cannot be passed where a `std::chrono::seconds` is expected without a conversion the compiler checks, and a lossy conversion must be asked for with `duration_cast`. It also brought **`steady_clock`**, the clock that never jumps backwards, which the STL module (lesson 12) made the rule for measuring intervals. A lot of timing bugs are unit bugs: a number meant as microseconds read as milliseconds is a factor of 1,000.

**`std::thread`** gave C++ a portable way to start a thread for the first time, together with a **[[memory model|memory-model]]** that says what one thread is guaranteed to see of another's writes. Before C++11 the language did not officially know threads existed; you used an operating-system library such as POSIX threads.

```cpp
#include <cstdio>
#include <thread>

void log_worker(int id) { std::printf("logger %d running\n", id); }

int main() {
    std::thread t(log_worker, 1);   // starts running log_worker(1) now
    t.join();                       // wait here until it finishes
    std::printf("joined\n");
}
```

It prints `logger 1 running`, then `joined`. One rule to hold on to now: a `std::thread` that is still joinable when it is destroyed calls `std::terminate` and ends the program. You must `join` it (wait for it) or `detach` it (let it go). The **[[concurrency module|thread-bridge]]** is where threads, locks and atomics get their full treatment.

::: example One program, nothing newer than C++11
This small chamber-pressure monitor uses most of the list at once. Every line compiles with `-std=c++11`.

```cpp
#include <algorithm>
#include <array>
#include <chrono>
#include <cstdio>
#include <memory>
#include <utility>
#include <vector>

enum class Health { Ok, OutOfRange };                 // scoped enum

constexpr double kMaxChamberKpa = 10000.0;            // compile-time constant

Health classify(double kpa) {
    return (kpa < 0.0 || kpa > kMaxChamberKpa) ? Health::OutOfRange : Health::Ok;
}

struct Filter {
    virtual ~Filter() = default;                      // = default
    virtual double step(double x) = 0;
};

struct LowPass final : Filter {                       // final: no further subclasses
    explicit LowPass(double a) : alpha(a) {}
    double step(double x) override {                  // override: checked by the compiler
        if (!primed) { y = x; primed = true; }
        y += alpha * (x - y);
        return y;
    }
    double alpha;
    double y = 0.0;                                   // default member initialisers
    bool primed = false;
};

int main() {
    std::array<double, 6> chamber_kpa = {9650.0, 9702.5, 9688.0, 12500.0, 9710.0, 9695.5};

    std::unique_ptr<Filter> filter(new LowPass(0.5)); // C++11 has no make_unique
    std::vector<double> log;

    for (auto p : chamber_kpa) {                      // range-for, auto
        if (classify(p) == Health::Ok) log.push_back(filter->step(p));
    }

    auto n_bad = std::count_if(chamber_kpa.begin(), chamber_kpa.end(),
                               [](double p) { return classify(p) != Health::Ok; });  // lambda

    std::vector<double> archived = std::move(log);   // move: steals the buffer
    std::printf("kept %zu samples, rejected %ld, log now holds %zu\n",
                archived.size(), static_cast<long>(n_bad), log.size());
    for (auto y : archived) std::printf("%.2f ", y);
    std::printf("\n");

    std::chrono::milliseconds period(1);              // a 1 kHz loop period
    auto us = std::chrono::duration_cast<std::chrono::microseconds>(period).count();
    std::printf("period = %lld us\n", static_cast<long long>(us));
}
```

Built with `g++ -std=c++11 -Wall -Wextra -pedantic -O2` (and again with `-std=c++20`, and with clang), every build prints the same:

```text
kept 5 samples, rejected 1, log now holds 0
9650.00 9676.25 9682.12 9696.06 9695.78 
period = 1000 us
```

Walk through it.

1. The reading $12500\,\mathrm{kPa}$ is above the $10000\,\mathrm{kPa}$ limit, so `classify` says `OutOfRange`. Five readings are kept, and the lambda passed to `count_if` counts one rejection.
2. The filter starts at the first sample, $9650$. Each step moves halfway toward the new reading: $9650 + 0.5 \times (9702.5 - 9650) = 9676.25$. Next, $9676.25 + 0.5 \times (9688 - 9676.25) = 9682.125$, which `%.2f` prints as `9682.12`. Then $9696.0625$ and $9695.78125$.
3. `std::move(log)` hands the vector's buffer to `archived`. No sample is copied, and `log` is left empty — size 0, as the standard guarantees for a moved-from vector.
4. One millisecond converts to 1,000 microseconds without a cast, because that direction cannot lose information.

Sanity check: the filtered values stay between the smallest and largest good readings, $9650$ and $9710$, as a smoothing filter's output must.
:::

## What else arrived, and what flight code keeps

The topic list is the headline, but C++11 was huge. It also brought **variadic templates** (templates module, lesson 3), `static_assert`, the type traits header, `= default` and `= delete` (RAII module, lesson 6), `noexcept`, `alignas`, `thread_local`, the unordered containers, `<random>`, `std::atomic`, delegating constructors, and brace initialisation, which is next lesson's whole subject.

Which of these does a flight team allow inside a hard real-time task? Most of them, because most cost nothing at run time.

- **Kept everywhere:** `auto`, range-for, `nullptr`, `enum class`, `override`, `final`, `constexpr`, `std::array`, `static_assert`, `std::chrono` durations, and lambdas that do not allocate. These are compile-time checks or zero-cost wrappers.
- **Kept, with care:** move semantics and `std::unique_ptr` for objects created during initialisation. The move is free; the allocation behind it is what the rules restrict.
- **Restricted:** `std::shared_ptr` (a heap control block and atomic counting on every copy), `std::vector` growth after start-up, and `std::thread` inside a control task. Flight software usually creates its threads once, at start-up, through the operating system's own interface, with priorities set by hand.

Safety standards reflect this history. The **[[JSF rules|coding-standards-history]]** for the F-35, written before C++11 existed, could only describe the C++98 language. Later standards were written for modern C++ from the start. Lesson 9 of this module turns all of this into an actual flight subset.

## Check yourself

::: check
A legacy header has `void set_label(int code);` and `void set_label(const char* text);`. A caller writes `set_label(NULL);` to clear the label. Describe what can happen on two different compilers, and give the fix.
:::

::: answer
`NULL` is an integer constant, never a pointer type. On g++ and clang it is a built-in integer the size of a `long`, which converts equally well to `int` and to `const char*`, so the call is rejected as ambiguous. On a compiler that defines `NULL` as `0`, the `int` overload is an exact match and is called silently, setting label code 0 instead of clearing the text. Neither outcome calls the pointer version on purpose. The fix is `set_label(nullptr);`: `std::nullptr_t` converts to any pointer type and to no integer, so only the pointer overload can match.
:::

::: check
Why does `for (auto f : frames)` where `frames` is a `std::vector` of 2 KB telemetry frames cost far more than `for (const auto& f : frames)`? What would each loop do if its body wrote `f.crc = 0;`?
:::

::: answer
`auto` deduces a plain `Frame`, so each pass copy-constructs a new 2 KB frame from the element; with 1,000 frames that is about 2 MB of copying per loop. `const auto&` binds a reference to each element and copies nothing.

With `auto`, `f.crc = 0;` compiles and changes only the copy, so the vector is untouched — a silent bug if you meant to change it. With `const auto&` it does not compile, because the reference is `const`. To change the elements in place, write `auto& f`.
:::

::: check
The base class has `virtual void set_gain(double k);`. A derived class declares `void set_gain(float k) override;`. What does the compiler do, and what would happen at run time if the word `override` were missing?
:::

::: answer
With `override`, the build fails: `set_gain(float)` has a different parameter type, so it replaces nothing, and g++ reports that it is marked `override` but does not override.

Without `override`, it compiles. The derived class now has a brand-new function `set_gain(float)` that hides the base one. A call through a base pointer, `Controller* c = &derived; c->set_gain(0.5);`, runs the *base* version, so the derived class's gain logic never executes. g++ 13 does print a `-Woverloaded-virtual` warning under `-Wall` that the base function "was hidden", but a warning can scroll past; the `override` error cannot.
:::

::: check
Write a C++11-legal `constexpr` function that returns the sum $1 + 2 + \dots + n$ for an `unsigned n`, and a `static_assert` that checks it for $n = 100$.
:::

::: answer
C++11 allows one `return` statement, so the loop becomes recursion and the branch becomes `?:`:

```cpp
constexpr unsigned sum_to(unsigned n) {
    return n == 0 ? 0u : n + sum_to(n - 1);
}
static_assert(sum_to(100) == 5050u, "1 + ... + 100");
```

The check value comes from Gauss's formula $\frac{n(n+1)}{2} = \frac{100 \cdot 101}{2} = 5050$. The recursion is 100 levels deep, far inside the compiler's default limit of 512 nested `constexpr` calls on g++.
:::

::: check
After `std::vector<double> b = std::move(a);`, a teammate writes `if (!a.empty()) process(a[0]);`. After `Telemetry t2 = std::move(t1);` for your own class `Telemetry`, they write `process(t1.value);`. Which one is safe to rely on?
:::

::: answer
The vector line is safe: the standard guarantees a vector left behind by its move constructor is empty, so `a.empty()` is true and nothing is processed. The `Telemetry` line is not something to rely on. A moved-from object of a general type is only "valid but unspecified". Unless `Telemetry` documents what its move leaves behind, `t1.value` could be the old value, a zero, or anything else. Assign `t1` a new value before reading it again.
:::

## Summary

| Idea | Meaning | Rule or fact |
| --- | --- | --- |
| C++11 | first major revision after C++98/03 | a new standard every three years since |
| `auto`, range-for | deduced types, index-free loops | `auto` drops `&` and top-level `const`; write `const auto&` to avoid copies |
| lambda | an unnamed function object written in place | made the standard algorithms practical |
| `T&&`, `std::move` | rvalue reference; a cast to "disposable" | moved-from objects are valid but unspecified |
| smart pointers | `unique_ptr`, `shared_ptr` | C++11 had `make_shared` but no `make_unique` |
| `nullptr` | a typed null pointer | converts to pointers only; `NULL` is an integer |
| `enum class` | scoped, strongly typed enum | no implicit conversion to `int`; can fix the underlying type |
| `override`, `final` | intent checked by the compiler | a signature mismatch becomes a compile error |
| C++11 `constexpr` | compile-time functions | body limited to one `return` statement |
| `std::array` | fixed-size array as a value | same cost as a C array; no decay, no heap |
| `std::chrono`, `std::thread` | typed time; portable threads | unjoined `std::thread` at destruction calls `std::terminate` |

::: context rvalue-name Where "rvalue" comes from
The names are older than C++. In C, an **lvalue** was something that could stand on the *left* of an assignment, like a variable, and an **rvalue** something that could only stand on the *right*, like `2 + 3` or a function's returned value. C++ refined the categories, but the idea survives: an lvalue has a name and an address you can come back to; an rvalue is a temporary that is about to vanish. Stealing from something about to vanish harms nobody, which is the whole logic of a move.
:::

::: context move-picture What a move really moves
A `std::vector` object is small: on a 64-bit machine it holds three pointers (begin, end, end of capacity), 24 bytes, while its samples live in a separate heap buffer. Copying duplicates the buffer. Moving copies only the three pointers into the new vector and sets the old one's to null. The samples never move at all.

::: context null-macro Why NULL was never a pointer
In C, `NULL` is often defined as `((void*)0)`, a real pointer, and C lets a `void*` turn into any other pointer silently. C++ forbids that silent conversion, so a C++ library cannot define `NULL` that way. It has to be an integer constant that the compiler treats as a null pointer when a pointer is expected: plain `0`, `0L`, or g++'s built-in `__null`. The integer type is the whole problem, and `nullptr` was the committee's way out without breaking the millions of lines that use `NULL`.
:::

::: context memory-model Why a language needs a memory model
Modern processors and compilers reorder memory reads and writes to go faster. In one thread you never notice, because the reordering keeps that thread's own results right. A second thread watching the same memory can notice. A memory model is the contract that says which orders another thread is allowed to see, and what you must write (a mutex, an atomic) to forbid the rest. Before C++11, threaded C++ relied on each compiler's and operating system's own promises.
:::

::: context coding-standards-history The rulebooks and their C++ versions
The JSF Air Vehicle C++ Coding Standards, written for the F-35 program and published in 2005, describe C++ as it was before C++11. MISRA C++:2008 was also based on C++03. The AUTOSAR C++14 guidelines, from the automotive world, were written for C++14, and MISRA C++:2023 targets C++17 and absorbed much of AUTOSAR's work. So the version of C++ a project uses often decides which rulebook it can follow. The real-time module covers these standards in detail.
