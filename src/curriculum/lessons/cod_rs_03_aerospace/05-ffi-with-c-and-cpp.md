Think about a travel plug adapter. Your phone charger has one shape of plug; the wall in another country has a different socket. Nobody rebuilds the charger or rewires the hotel. A small adapter, with an agreed shape on each side, lets the two work together. What matters is that both sides agree exactly on the shape: pin sizes, spacing, voltage. Get one of those wrong and nothing works, or something burns.

Real flight software is a very large, very old house full of C and C++ sockets. A flight team with ten years of C++ and a stack of certification evidence is not going to rewrite it all in Rust, and should not. If Rust comes in at all, it comes in as one new part at a time, plugged into the existing code through an adapter. That adapter is the **FFI**, the foreign function interface: the rules that let a function written in one language be called from another. For Rust and C the agreed plug shape is the **C ABI**.

This lesson builds both directions for real. First, a Rust module compiled into a library and called from a C program, with the C header generated by a tool. Then a C function called from a Rust program, with the Rust declarations generated by another tool. Everything was built with Rust 1.94.1 (2024 edition), gcc and g++ 13.3, `cbindgen` 0.29.4, `bindgen` 0.73.2 and the `cc` crate 1.5.1, and every output shown is copied from a real run.

## The agreed plug shape: the C ABI

When one compiled function calls another, both must agree on details nobody writes in the source code: which processor registers carry the arguments, where the return value goes, who cleans up the stack, how big an `int` is. That set of agreements is an **[[ABI|abi]]**, an application binary interface. The API is what the code *says*; the ABI is what the machine code *does*.

Rust's own ABI is deliberately unstable. The compiler may reorder struct fields or change how arguments are passed from one version to the next, because it only has to agree with itself. C's ABI, on the other hand, is fixed for each platform, and almost every language can speak it. So when Rust talks to anyone else, it speaks C.

Three pieces of Rust syntax make a function C-shaped.

- **`extern "C"`** on a function (read "extern C") tells the compiler to use C's calling convention for it.
- **`#[unsafe(no_mangle)]`** keeps the function's name exactly as written in the compiled file, so a C linker can find it.
- **`#[repr(C)]`** on a struct lays out its fields in the order written, with C's padding rules, so a C compiler and Rust agree on where each field lives. You met it with `Frame` in the last lesson.

Why is the name a problem at all? Rust, like C++, rewrites function names into longer unique ones, a process called **[[name mangling|name-mangling]]**, so that two functions called `saturate` in different modules do not collide. Here is what `nm`, a tool that lists the names in a compiled file, shows for two functions in a crate called `nav`, one plain and one marked `no_mangle`:

```text
0000000000000000 T _ZN3nav8saturate17h0fe7724078cc92f2E
0000000000000000 T gnc_saturate
```

A C program looking for `saturate` would never find the first one. It finds `gnc_saturate` at once. Because C has no modules, give every exported name a prefix like `gnc_`, the way C libraries do.

In the 2024 edition, `no_mangle` must be wrapped in `unsafe(...)`. The reason is that two exported functions with the same name in one program cause undefined behavior, and the compiler cannot check that for you. Write the old spelling and you get:

```text
error: unsafe attribute used without unsafe
 --> src/main.rs:1:3
  |
1 | #[no_mangle]
  |   ^^^^^^^^^ usage of unsafe attribute
  |
help: wrap the attribute in `unsafe(...)`
  |
1 | #[unsafe(no_mangle)]
  |   +++++++         +
```

::: key The three markers
`extern "C"` picks C's calling convention; `#[unsafe(no_mangle)]` keeps the symbol name as written so C can link to it; `#[repr(C)]` gives a struct C's field order and padding. Only C-compatible types cross the boundary: integers, floats, raw pointers, and `repr(C)` structs and enums, never `String`, `Vec` or `&str`.
:::

## Rust called from C: the new module in an old house

Picture the existing C flight code as the house. You want to add one new room, a small GNC helper module written in Rust. The plan has four steps.

1. Write the functions in Rust with the three markers.
2. Build them as a **[[static library|staticlib]]**, an archive of compiled code (a `.a` file on Linux) that the C linker can pull into its program.
3. Generate a C header file from the Rust source with **cbindgen**, so nobody has to type the declarations by hand.
4. Include the header in the C code and add the library to the link line.

Step 1 and 2 happen in the Rust crate. In `Cargo.toml` you ask for a static library, and you make panics abort (the reason comes below):

```toml
[lib]
crate-type = ["staticlib"]

[profile.release]
panic = "abort"
```

Then `src/lib.rs`:

```rust
//! GNC helpers written in Rust, callable from C.

/// State for a rate limiter. `repr(C)` lays the fields out
/// exactly as a C compiler would, in this order.
#[repr(C)]
pub struct RateLimiter {
    /// Largest change allowed per call.
    pub max_step: f64,
    /// Output of the previous call.
    pub last: f64,
}

/// Clamp `x` into the range `[lo, hi]`.
#[unsafe(no_mangle)]
pub extern "C" fn gnc_saturate(x: f64, lo: f64, hi: f64) -> f64 {
    x.clamp(lo, hi)
}

/// Move `state.last` toward `cmd` by at most `state.max_step`.
/// Returns the new output, or 0.0 if `state` is null.
#[unsafe(no_mangle)]
pub extern "C" fn gnc_rate_limit(state: *mut RateLimiter, cmd: f64) -> f64 {
    // SAFETY: the C caller promises `state` is null or points to a live,
    // exclusively owned RateLimiter for the duration of this call.
    let Some(s) = (unsafe { state.as_mut() }) else {
        return 0.0;
    };
    let step = (cmd - s.last).clamp(-s.max_step, s.max_step);
    s.last += step;
    s.last
}

/// Mean of `len` samples starting at `samples`.
/// Returns 0 on success and writes the mean to `*out`;
/// returns -1 if a pointer is null or `len` is 0.
///
/// # Safety
/// `samples` must point to `len` readable f64 values, and `out`
/// must point to one writable f64.
#[unsafe(no_mangle)]
pub unsafe extern "C" fn gnc_mean(samples: *const f64, len: usize, out: *mut f64) -> i32 {
    if samples.is_null() || out.is_null() || len == 0 {
        return -1;
    }
    // SAFETY: checked non-null above; the caller promises `len` values.
    let xs = unsafe { core::slice::from_raw_parts(samples, len) };
    let mean = xs.iter().sum::<f64>() / len as f64;
    unsafe { *out = mean };
    0
}
```

Look at the edge of each function. C has no references, no slices and no `Option`, so what arrives is raw pointers and lengths. The first thing each function does is turn them into safe Rust types, checking what it can: `as_mut()` turns a raw pointer into `Option<&mut RateLimiter>`, giving `None` for null, and `from_raw_parts` turns a pointer plus a length into a slice. After that line, everything is ordinary safe Rust with the borrow checker fully on. This is the "safe wrapper around a small unsafe core" pattern from the last module's unsafe lesson, applied at a language border. Errors come back the C way, as a status number, because a Rust `Result` means nothing to C.

`cargo build --release` produces `target/release/libgnc_rs.a`.

Step 3 is cbindgen. A small `cbindgen.toml` sets the options:

```toml
language = "C"
include_guard = "GNC_RS_H"
usize_is_size_t = true
cpp_compat = true
```

`cbindgen --config cbindgen.toml --output gnc_rs.h` reads the Rust source and writes this header (doc comments trimmed here; cbindgen copies them over as C comments):

```c
#ifndef GNC_RS_H
#define GNC_RS_H

#include <stdarg.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdlib.h>

typedef struct RateLimiter {
  double max_step;
  double last;
} RateLimiter;

#ifdef __cplusplus
extern "C" {
#endif // __cplusplus

double gnc_saturate(double x, double lo, double hi);

double gnc_rate_limit(struct RateLimiter *state, double cmd);

int32_t gnc_mean(const double *samples, size_t len, double *out);

#ifdef __cplusplus
}  // extern "C"
#endif  // __cplusplus

#endif  /* GNC_RS_H */
```

Notice the translations: `f64` became `double`, `*mut RateLimiter` became `struct RateLimiter *`, `*const f64` became `const double *`, and, thanks to `usize_is_size_t`, `usize` became `size_t`. The header is generated from the source every build, so it can never drift out of date the way a hand-written one can.

::: example The C flight code calls the Rust module
Step 4. Here is the existing C code, now calling the new room:

```c
/* The existing C flight code: it calls the new Rust module. */
#include <stdio.h>
#include "gnc_rs.h"

int main(void) {
    printf("saturate(1.7, -1, 1) = %.2f\n", gnc_saturate(1.7, -1.0, 1.0));

    RateLimiter fin = { .max_step = 0.5, .last = 0.0 };
    for (int i = 0; i < 4; i++) {
        double out = gnc_rate_limit(&fin, 2.0);
        printf("step %d: fin angle = %.2f deg\n", i, out);
    }

    double gyro[4] = { 0.010, 0.012, 0.011, 0.015 };
    double mean = 0.0;
    int rc = gnc_mean(gyro, 4, &mean);
    printf("gnc_mean rc=%d mean=%.4f rad/s\n", rc, mean);
    printf("gnc_mean(NULL) rc=%d\n", gnc_mean(NULL, 4, &mean));
    return 0;
}
```

Compile and link it with gcc, pointing at the Rust library:

```text
gcc -Wall -O2 flight_main.c -L target/release -lgnc_rs -o flight
./flight
```

`-L` adds a folder to search and `-lgnc_rs` means "link `libgnc_rs.a`". The output:

```text
saturate(1.7, -1, 1) = 1.00
step 0: fin angle = 0.50 deg
step 1: fin angle = 1.00 deg
step 2: fin angle = 1.50 deg
step 3: fin angle = 2.00 deg
gnc_mean rc=0 mean=0.0120 rad/s
gnc_mean(NULL) rc=-1
```

Check each line. $1.7$ clamped to $[-1, 1]$ is $1.00$. The fin is commanded to $2$ degrees but may move only $0.5$ per call, so it takes four calls: $0.5, 1.0, 1.5, 2.0$. The mean of the gyro samples is

$$
\frac{0.010 + 0.012 + 0.011 + 0.015}{4} = \frac{0.048}{4} = 0.012 \,\mathrm{rad/s},
$$

matching `0.0120`. And the null pointer gets a clean `-1` instead of a crash, because the Rust side checked.
:::

On a desktop, a Rust static library also needs a few system libraries at the final link. Ask the compiler which, with `cargo rustc --release -- --print native-static-libs`; here it answered `-lgcc_s -lutil -lrt -lpthread -lm -ldl -lc`. gcc added those automatically in this small example, but a real build system should list them. For a `no_std` library built for a microcontroller, the list is empty.

::: warning A panic must never cross the border
Rust unwinding, the stack cleanup a panic performs, cannot pass through C frames. Since Rust 1.81, a panic that reaches the edge of an `extern "C"` function aborts the whole program on purpose. A tiny exported function that indexes `table[i]` with `i = 7` on a three-element table printed:

```text
thread '<unnamed>' (29729) panicked at p.rs:4:5:
index out of bounds: the len is 3 but the index is 7
...
panic in a function that cannot unwind
...
thread caused non-unwinding panic. aborting.
```

and the C program died with exit code 134, never reaching its next line. So design the border so it cannot panic: check inputs, use `get(i)` instead of `[i]`, and return a status code. Setting `panic = "abort"` makes the policy explicit and removes the unwinding code.
:::

### C++ callers, and names again

Most large flight codebases are C++, not C. C++ can call the same functions, but C++ mangles names too. Without the `extern "C"` block in the header, g++ looks for the C++-mangled name `_Z12gnc_saturateddd` and the link fails:

```text
nav.cpp:(.text.startup+0x21): undefined reference to `gnc_saturate(double, double, double)'
collect2: error: ld returned 1 exit status
```

That is why the header wraps the declarations in `extern "C" { ... }` when compiled as C++, which `cpp_compat = true` turned on. With it, the same C++ program linked and printed `saturate = -1.00`. The C ABI stays the meeting point: C++ classes, templates and exceptions do not cross it. For richer, type-checked bridges between Rust and C++, the [[cxx crate|cxx-crate]] generates both sides of the boundary from one description.

## C called from Rust: reusing trusted code

The other direction matters as much. The old house contains code that has flown, been tested for years, and carries certification evidence: a checksum routine, a telemetry packer, a sensor calibration table. A new Rust module should call that code, not rewrite it.

Here is a small C checksum, **[[CRC-16|crc16]]**, the kind of function every telemetry link uses to detect corrupted packets:

```c
#ifndef CRC16_H
#define CRC16_H
#include <stddef.h>
#include <stdint.h>

/* CRC-16/CCITT-FALSE over `len` bytes: poly 0x1021, start 0xFFFF. */
uint16_t crc16_ccitt(const uint8_t *data, size_t len);

#endif
```

```c
#include "crc16.h"

uint16_t crc16_ccitt(const uint8_t *data, size_t len) {
    uint16_t crc = 0xFFFF;
    for (size_t i = 0; i < len; i++) {
        crc ^= (uint16_t)data[i] << 8;
        for (int b = 0; b < 8; b++) {
            crc = (crc & 0x8000) ? (uint16_t)((crc << 1) ^ 0x1021) : (uint16_t)(crc << 1);
        }
    }
    return crc;
}
```

Rust needs a declaration of the C function, an `extern` block, the way C needed a header. **bindgen** writes it from the header, the mirror image of cbindgen. Running `bindgen csrc/crc16.h --allowlist-function crc16_ccitt` printed:

```rust
/* automatically generated by rust-bindgen 0.73.2 */

unsafe extern "C" {
    pub fn crc16_ccitt(data: *const u8, len: usize) -> u16;
}
```

Every function in an `extern` block is `unsafe` to call, because the compiler cannot see inside the C code and cannot check that you pass the right pointer and length. (`--allowlist-function` keeps bindgen from also translating everything the header includes.)

Two more pieces build and link the C file. The `cc` crate compiles C code from a **[[build script|build-script]]**, a `build.rs` file that cargo compiles and runs before building your crate. After `cargo add --build cc`:

```rust
fn main() {
    // Compile the C file into a static library and tell cargo to link it.
    cc::Build::new().file("csrc/crc16.c").compile("crc16");
    println!("cargo:rerun-if-changed=csrc/crc16.c");
    println!("cargo:rerun-if-changed=csrc/crc16.h");
}
```

::: example A safe Rust wrapper around the C checksum
The bindgen output is saved as `src/crc16_sys.rs`. The rest of the program wraps the one unsafe call in a safe function:

```rust
mod crc16_sys; // generated by bindgen from csrc/crc16.h

/// Safe wrapper: a slice always carries a valid pointer and its length.
pub fn crc16(data: &[u8]) -> u16 {
    // SAFETY: `data.as_ptr()` points to `data.len()` readable bytes,
    // and crc16_ccitt only reads them and keeps no copy of the pointer.
    unsafe { crc16_sys::crc16_ccitt(data.as_ptr(), data.len()) }
}

fn main() {
    let check = crc16(b"123456789");
    println!("crc16(\"123456789\") = {:#06x}", check);

    let frame = [0x01u8, 0x2a, 0x00, 0x7f];
    println!("crc16(frame) = {:#06x}", crc16(&frame));
    println!("crc16(empty) = {:#06x}", crc16(&[]));
}
```

`cargo run` compiled the C file, linked it, and printed:

```text
crc16("123456789") = 0x29b1
crc16(frame) = 0x3c0b
crc16(empty) = 0xffff
```

How do you know the numbers are right? The string `123456789` is the standard test input for checksums, and `0x29b1` is the published check value for CRC-16/CCITT-FALSE. An independent Python version of the same algorithm also gave `0x29b1` and `0x3c0b`. The empty input returns the starting value `0xFFFF` untouched, since the loop never runs.

Why is the wrapper safe? A Rust slice `&[u8]` always carries a valid pointer and its true length, so the caller cannot pass a wrong pair. The one thing Rust cannot check, that the C function reads only `len` bytes and does not keep the pointer, is written in the `SAFETY` comment, where a reviewer can confirm it against the C source.
:::

::: warning Allocate and free on the same side
Rust and C may use different memory allocators. Memory that Rust allocated must be freed by Rust, and memory C allocated must be freed by C. Passing a Rust `Box` to C's `free`, or a `malloc` pointer to Rust's `drop`, is undefined behavior. When a Rust object must live on the C side, export a pair of functions, such as `gnc_filter_new()` returning a pointer and `gnc_filter_free(ptr)` taking it back, and let C hold the pointer as an [[opaque handle|opaque-handle]] it never looks inside. In flight code the usual answer is simpler still: C owns the storage, often a `static`, and passes a pointer in, as `gnc_rate_limit` did.
:::

## The realistic path into a flight codebase

Put the two directions together and you have the only adoption route that works for a large existing codebase. Picture renovating a house one room at a time while the family keeps living in it.

1. Choose one small, well-bounded module with a clear interface: a filter, a parser for an uplinked command, a checksum, a telemetry packer. Parsers of untrusted input are a favorite, because memory-safety bugs there are the most dangerous.
2. Write it in Rust behind an `extern "C"` interface, with `repr(C)` types and status-code errors.
3. Build it as a `staticlib`, generate its header with cbindgen, and link it into the **existing** build. CMake and Make can call cargo as one more step (the Corrosion project packages this for CMake).
4. Where the new module needs existing C, call it through bindgen declarations and safe wrappers.
5. Put the new module through the **same** review, testing, coverage and verification process as the code around it. The existing certification evidence for everything else stays valid, because nothing else changed.

What does not work: rewriting the codebase, which throws away years of flight heritage and evidence; or running Rust as a separate program talking to the C++ over messages, which adds a new failure mode to a system that did not need one.

::: key How to call Rust from an existing C flight codebase
Expose functions as extern C with no_mangle, build a staticlib, generate a C header with cbindgen, and link it into the existing build. This incremental module-by-module path is the only realistic adoption route for a large legacy codebase.
:::

::: note Why the border is where the risk concentrates
Inside the Rust module, the compiler checks ownership and bounds. Inside the C code, the existing reviews and tools do their job. The border belongs to neither: the compiler takes your word for every `extern` declaration and every pointer that crosses. That is why the border should be thin (few functions, simple types), generated by tools rather than typed by hand, checked on entry (null pointers, lengths, ranges), and documented with `SAFETY` comments. A thin, generated, checked border keeps the trusted part small enough to review.
:::

## Check yourself

::: check
A colleague exports `pub fn gnc_clamp(x: f64) -> f64` from a Rust staticlib, and the C build fails with "undefined reference to `gnc_clamp`". Name the two things missing from the Rust function, and what each does.
:::

::: answer
It needs `extern "C"`, so it uses the C calling convention, and `#[unsafe(no_mangle)]`, so its symbol is named exactly `gnc_clamp` instead of a mangled name like `_ZN...gnc_clamp17h...E`. The link error comes from the missing `no_mangle`: the linker searched for `gnc_clamp` and the library only contained the mangled name. Without `extern "C"` it might link but pass arguments the wrong way.
:::

::: check
What is the difference between what cbindgen does and what bindgen does? Which one did you need in each direction?
:::

::: answer
cbindgen reads Rust source and writes a C header, so C or C++ code can call Rust. bindgen reads a C header and writes Rust `extern` declarations, so Rust can call C. Rust called from C used cbindgen (to make `gnc_rs.h`); C called from Rust used bindgen (to make `crc16_sys.rs`). The names are mirror images: "c" first means the output is C.
:::

::: check
Why does `gnc_rate_limit` take `*mut RateLimiter` rather than `&mut RateLimiter`, and what does its first statement do about it?
:::

::: answer
A C caller can pass any pointer, including null, and a Rust reference promises it is never null and always valid. Declaring a reference would let C break that promise without anyone noticing. So the function takes a raw pointer and immediately converts it with `state.as_mut()`, which gives `None` for null; the function returns `0.0` in that case and otherwise continues with a real `&mut RateLimiter`. The remaining promise, that a non-null pointer is valid and not used elsewhere during the call, is stated in the `SAFETY` comment.
:::

::: check
Your exported function divides by `len` and someone passes `0`, or indexes a slice past its end. What happens at the border if a panic occurs, and how should the function be written instead?
:::

::: answer
The panic cannot unwind into C, so the program aborts (Rust 1.81 and later abort when a panic reaches the edge of an `extern "C"` function). The function should check its inputs first and return an error status, as `gnc_mean` returns `-1` for a zero length, and use non-panicking operations such as `slice.get(i)` inside.
:::

::: check
A manager proposes: "Let's run the new Rust navigation code as its own process and talk to the C++ flight software over a socket, so the two never touch." Give two reasons the staticlib-behind-extern-C route is usually the better plan.
:::

::: answer
First, it slots into the existing build, scheduler and verification process as one more module, so the rest of the system and its certification evidence are unchanged; a new process adds a new scheduling and communication path that must itself be designed, timed and verified. Second, a function call has no message-passing delay or new failure modes (lost messages, a crashed peer), which matters inside a hard real-time loop. The C ABI is the thin, well-understood interface both sides already share.
:::

## Summary

| Idea | Meaning | Fact to remember |
|---|---|---|
| ABI | Machine-level calling agreement | Rust's is unstable; C's is the common language |
| `extern "C"` | C calling convention | On exported functions and on imported declarations |
| `#[unsafe(no_mangle)]` | Keep the symbol name | 2024 edition requires the `unsafe(...)` |
| `#[repr(C)]` | C struct layout | Only C-compatible types cross the border |
| `staticlib` | `.a` archive for a C linker | `crate-type = ["staticlib"]`, `panic = "abort"` |
| cbindgen | Rust source to C header | `cpp_compat` adds the C++ `extern "C"` guard |
| bindgen | C header to Rust declarations | Calls are `unsafe`; wrap them in safe functions |
| `cc` + `build.rs` | Compile C inside a cargo build | Runs before the crate compiles |
| Panics at the border | Cannot unwind into C | Aborts; return status codes instead |
| Adoption path | One module at a time | Rust behind extern C, same build and verification |

::: context name-mangling Reading a mangled name
`_ZN3nav8saturate17h0fe7724078cc92f2E` is not random. `_ZN ... E` wraps a nested name; each part is preceded by its length: `3nav` is the crate, `8saturate` the function, and `17h0fe7724078cc92f2` is a 17-character hash that keeps different versions of the same crate apart. C++ uses the same scheme, and adds the argument types: `_Z12gnc_saturateddd` is a 12-letter name taking three `d`s, three doubles. That is how C++ overloading works, and why C, with no overloading, needs no mangling. The command `c++filt` turns such names back into readable form.
:::

::: context staticlib Static library or dynamic library
A static library is copied into the final program when it is linked, so the program carries everything it needs. A dynamic library (`cdylib` in Rust, a `.so` or `.dll`) is loaded when the program starts. Flight software on microcontrollers almost always links statically, because there is no operating system to load libraries, and because a single fixed image is what gets tested and certified. Note that a desktop Rust staticlib carries its own copy of the standard library, which is why the one in this lesson was about 20 MB before the linker threw away the unused parts; a `no_std` one is tiny.
:::

::: context cxx-crate Beyond plain C
The `cxx` crate, by David Tolnay, lets you describe a Rust–C++ boundary once, in a Rust module, and generates matching code on both sides. It can pass C++ `std::string`, `std::unique_ptr` and Rust `String`, `Box` and slices safely, and it checks both sides agree at build time. It is widely used where C++ and Rust live together at scale. For a small flight module, plain `extern "C"` with cbindgen is often preferred because it is simpler to review.
:::

::: context crc16 A checksum that catches noise
A cyclic redundancy check treats the message bits as a long binary polynomial, divides it by a fixed one (here $0x1021$, meaning $x^{16} + x^{12} + x^5 + 1$), and keeps the 16-bit remainder. The receiver recomputes it; if a single bit, or any burst of up to 16 bits, flipped in transit, the remainders differ. CRC-16/CCITT variants are specified in space standards such as the CCSDS telecommand and telemetry frame formats, which is why nearly every spacecraft radio link has one.
:::

::: context build-script Code that runs before your code
`build.rs` is an ordinary Rust program that cargo compiles and runs before compiling the crate itself. It can compile C sources (with `cc`), run bindgen, or generate tables. It talks back to cargo by printing lines that start with `cargo:`: `cargo:rerun-if-changed=csrc/crc16.c` means "only run me again if this file changes", which keeps rebuilds fast. The `cc` crate prints the linking instructions for you after `compile("crc16")`, so the library is linked automatically.
:::

::: context opaque-handle A claim ticket
An opaque handle is like a coat-check ticket: you hold it, you hand it back to get your coat, but you never see the cloakroom. C gets a pointer to a type it only knows by name (`typedef struct Filter Filter;`), with no fields visible, and every operation goes through exported functions. C cannot poke at Rust's fields or free the memory with the wrong allocator, because it never knows the size or layout.
